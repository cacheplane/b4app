# Repository instructions

This repository is the Personal Agent Workspace: a native Swift macOS app, an iOS companion, a coordinator service, and the `agent-workspace` CLI for Codex, Claude Code, and B4 conversations. The requirement source is `docs/roadmaps/Personal_Agent_Workspace_Technical_Spec_and_Roadmap.md`. Read it and the decision log (`docs/decisions/`, one file per decision; `docs/decisions.md` describes the layout) before changing architecture. The spec says Electron; decision D-001 replaced that with Swift at the owner's direction.

## Commands

- `swift build` and `swift test` for every library, the coordinator, and the CLI.
- `swift format lint --strict --recursive Sources Tests Apps Package.swift` before committing; `swift format format --in-place --recursive ...` fixes layout.
- `cd Hub && source <(./scripts/test-db.sh) && cargo test --workspace --locked` runs the hub's tests against a throwaway PostgreSQL (needs `./Scripts/fetch-postgres.sh` first); `./scripts/test-db.sh --stop` stops it. Each checkout and worktree gets its own cluster (its own data directory and port), so sessions in other worktrees never stop or share yours; run one `cargo test` per checkout at a time, since `#[sqlx::test]` names databases after the test and two runs of the same test on one cluster drop each other's. Also `cargo fmt --all -- --check` and `cargo clippy --workspace --all-targets --locked -- -D warnings` from `Hub/`. CI's `hub` job runs the same.
- `docker compose up -d` in `Hub/` runs a local hub on `localhost:8080` (copy `.env.example` to `.env` and fill in both passwords and `B4HUB_SECRET_KEY`, `openssl rand -base64 32`, first; `serve` also needs `B4HUB_WEBAUTHN_RP_ID`, which `.env.example` sets to `local.b4.run` with `B4HUB_SIGNUP=open`; the README's "Hub (optional)" has the seed and enroll steps). `agent-workspace hub join|status|leave` links a Mac to it.
- The Compose hub writes notifications to `Hub/push-spool` by default (`B4HUB_PUSH_SENDER=spool`); `./Scripts/sim-push.sh` pushes each one to the booted Simulator (`B4APP_SIM_DEVICE` picks one when several are booted). `B4HUB_PUSH_SENDER=apns` in `Hub/.env` sends through Apple instead, with `B4HUB_APNS_KEY_ID`, `B4HUB_APNS_TEAM_ID`, and `B4HUB_APNS_KEY_HOST_PATH` (the `.p8`, mounted read-only; never put the key in `.env`).
- `./Scripts/generate-project.sh` regenerates `B4App.xcodeproj` (gitignored) from `project.yml`; needs `brew install xcodegen`.
- `xcodebuild build -project B4App.xcodeproj -scheme B4App-macOS -destination 'platform=macOS'` and the same with `-scheme B4App-iOS -destination 'generic/platform=iOS Simulator'`.
- Flavours (`prod`, `beta`, `local`; `Flavor` in `WorkspacePlatform`, `PhoneFlavor` in `WorkspaceMirror` for the phone): each has its own hub, site domain, bundle ids, data directory, LaunchAgent label, keychain group, and URL scheme (the README's "Build flavours"). A process outside an `.app` is local unless `B4APP_FLAVOR` says otherwise, so a dev coordinator talks to `http://localhost:8080`; only an explicit local flavour (environment or bundle) with no `B4APP_DATA_DIR` adopts the owner's pre-flavour `b4app` data. `B4App-macOS` and `B4App-iOS` build local in Debug and prod in Release, and the `-Beta` schemes build beta. `Config/Flavor-*.xcconfig` holds each flavour's bundle id, site domain, URL scheme, and App Group. `B4APP_FLAVOR=beta ./Scripts/package.sh` and `./Scripts/upload-ios.sh` take the flavour (default `prod`); `B4APP_CHECK_PROFILES_ONLY=1 B4APP_TEAM_ID=<team>` on `package.sh` checks the profiles without building or signing.
- `./Scripts/test-ios-layout.sh` runs the iOS layout UI tests (CI's "iOS navigation and banner regression tests") on this checkout's own Simulator, "B4App Layout <n>", made on first use, so sessions in other worktrees never kill each other's runs; run one per checkout at a time, and `--stop` deletes the Simulator. Extra arguments go to `xcodebuild` (`-only-testing:WorkspaceLayoutTests/BannerLayoutTests`).
- `.build/debug/agent-workspace doctor --json` runs the CLI; it spawns `.build/debug/b4app-coordinator` beside it when no coordinator is listening. Set `B4APP_RUNTIME_DIR` and `B4APP_DATA_DIR` to keep experiments out of the real data directory; keep the runtime dir under `$TMPDIR`, since a Unix socket path is limited to 104 bytes.
- `B4APP_LIVE_CODEX=1 swift test --filter CodexLive` and `B4APP_LIVE_CLAUDE=1 swift test --filter ClaudeLive` run the opt-in live checks (real inference, need `codex login` / `claude auth login`). CI never sets them. Fixture tests use `Tests/CodexAdapterTests/Fixtures/fake-codex.py` and `Tests/ClaudeAdapterTests/Fixtures/fake-claude.py`.

## Layout

- `Sources/WorkspaceProtocol` and `Sources/WorkspaceClient` are Foundation-only and link on iOS. Never import AppKit, NIO, GRDB, or Subprocess there.
- `Sources/WorkspaceUI` is SwiftUI shared by both apps; it talks only to `WorkspaceClient` and never imports `WorkspaceMirror`, `WorkspaceSync`, or `WorkspaceStorage`.
- A thread's row state is `ThreadState` (`Sources/WorkspaceProtocol/Attention.swift`: `approve`, `reply`, `failed`, `finished`, `working`, `quiet`; `Attention.state(of:)` and `Attention.ordered`), drawn by `ThreadMark` (`Sources/WorkspaceUI/Theme/ThreadMark.swift`), which the iOS widget (`Apps/iOSWidget/`) shares with `animated: false`; the badge (`needsYouCount`) is unchanged by it (D-204). `ThreadRow`, `ArrivalTracker` and `Theme/ArrivalTrace.swift` make the single-line row and its arrival trace, and `Sources/WorkspaceUI/TopBar.swift` is the Mac's top bar (view options, search, new thread).
- The list's arrangement, the sidebar setting (Shown, Collapsed or Hidden for the threads that do not need you), Show archived and density (normal or dense) are one synced row, `viewSettings` (id `view`; `ViewSettings` in `WorkspaceProtocol`, `viewSettings.get` and `.set`; hub migrations `0019`, `0020` and `0022`, coordinator `0013` and `0015`, mirror schema 10; D-208, D-213, D-218; hub migration `0020` keeps one row per user, stored as `view:<userId>`, while devices see `view`). The old values `small` and `tiny` are read leniently (`tiny` as dense), and density is set on the Display page of Settings (`Sources/WorkspaceUI/DisplaySettingsView.swift`), on the Mac and the phone. Dense draws a thread's turns as the message, one line for the steps, and the answer (`Sources/WorkspaceUI/DenseTranscript.swift`, which reads `DisplayItem` and `Turn` rows only; D-223). `Sources/WorkspaceUI/ListLayout.swift` (`ListLayout.build`) builds the list from the threads, environments and settings; the views only draw it.
- `Sources/WorkspacePlatform` holds paths, executable lookup, process running, and the singleton lock; it re-exports `WorkspaceSecrets`.
- `Sources/WorkspaceSecrets` (secret references and the Keychain store; Foundation and Security, both platforms), `Sources/WorkspaceSync` (hub wire types and HTTP client; Foundation only), and `Sources/WorkspaceMirror` link on iOS.
- `Sources/WorkspaceStorage` is the only module that opens the coordinator's PostgreSQL store (it also reads a retired pre-0.2 SQLite file once, for the import), and only the coordinator uses it.
- `Sources/WorkspaceMirror` is the only module that keeps a SQLite store (the phone's mirror of the synced tables), and only the iOS app uses it.
- `Sources/Coordinator/Accounts/` (`AccountManager`, `AccountScope`, `AccountCommands`, `LegacyAdoption`) is the only owner of the account lifecycle: sign-in, sign-out, log-out, adoption, and the per-account scope (the account's database, sessions, servers, environments, `HubSync`, and relay), which nothing outside the scope's gate may use. Store commands answer `signed_out` while no scope is open; a new router method must be placed in `Router.needsAccount`. `AccountRegistry` in `WorkspaceStorage` is the `registry` database of the accounts that signed in (its own migrations, `Sources/WorkspaceStorage/SQL/registry/`), keyed on the hub's `userId`.
- `Sources/WorkspaceMirror/MirrorAccount.swift` is the phone's account (sign-in, log-out, pairing and the merge, its token and link); `WorkspaceUI` reaches it only through the `AccountHost` protocol (`Sources/WorkspaceUI/SignIn/AccountHost.swift`), which the app conforms it to. The passkey and Apple sheets are in `Sources/WorkspaceUI/SignIn/`; on the Mac every hub call they lead to goes through the coordinator's `account.*` commands.
- `Sources/Coordinator/HubSync/` is the only code that talks to the hub from the Mac, apart from the unauthenticated sign-in calls in `Accounts/AccountCommands.swift` (account calls that need a token go through `HubSync`'s client). Besides the push and pull, it holds the relay: `HubLink.swift` (the Mac's WebSocket link, watched-thread streaming, catch-up), `RelayExecutor.swift` (runs the five relayed methods through `SessionService`), `Pairing.swift` (`hub.pair` and `hub.pairStatus`), and `KeepAwake.swift` (the power assertion).
- `Sources/WorkspaceSync/{RelayWire,RelayLink,HubLinkConnection}.swift` are the relay's wire types, its reconnecting link (shared by the Mac and the phone, each building its own), and the WebSocket seam (`URLSessionHubLinkConnection` in production, a fake in tests); `Sources/WorkspaceMirror/MirrorRelay.swift` is the phone's side. `HubURL` lives in `WorkspaceProtocol` (the pair-link parser needs it), not `WorkspaceSync`.
- `NIOWebSocket` and `NIOHTTP1` are linked only by the `WorkspaceSyncTests` target, for the fake hub; never import them in a shipped target.
- `Hub/` is the Rust hub (Cargo workspace: `b4hub-core`, `b4hub-db`, `b4hub`), its Dockerfile and Compose file, and `Hub/API.md`, the wire reference. The relay is `Hub/crates/b4hub/src/relay/` (`link.rs`, `registry.rs`, `route.rs`, `limits.rs`) and `routes/pairing.rs`; its state is in memory, and on more than one instance every link of one user is served by one instance (`instances.rs`, D-085), while long-polls on any instance are woken, and links whose session ended are closed, over `LISTEN` / `NOTIFY` (`signals.rs`, `notify.rs`, `b4hub-db/src/signals.rs`, D-161, D-162). Sign-in is `routes/auth.rs` (passkeys), `routes/apple.rs`, `routes/me.rs` (the account routes), `apple.rs` (Apple's client and the AES-GCM seals), `auth_limits.rs` (the per-IP limits), and `b4hub-db/src/{accounts,ceremonies}.rs`. `Tests/Fixtures/sync/changes.json`, `Tests/Fixtures/sync/relay.json`, `Tests/Fixtures/sync/auth.json` (the sign-in and account routes; `AuthWireTests` and the hub's `auth_fixture` test), and `Tests/Fixtures/sync/push.json` are the contracts both languages decode; edit one only when both suites are updated.
- Notifications (M8f): `Hub/crates/b4hub-core/src/push.rs` decides which changes notify and builds the payload, `Hub/crates/b4hub-db/src/push.rs` holds push tokens and the `notifications_sent` ledger and runs the detection inside `changes::push`, and `Hub/crates/b4hub/src/push.rs` is the `PushSender` (`spool` for the Simulator; `apns` is `ApnsSender`, HTTP/2 to Apple with a cached ES256 provider token, configured by `B4HUB_APNS_KEY_ID`, `B4HUB_APNS_TEAM_ID`, and `B4HUB_APNS_PRIVATE_KEY` or `_FILE`, and `serve` refuses to start on a bad one). Every notification has a key (`request:<id>` or `turn:<id>`) and carries the badge; `b4hub-db/src/push.rs` also withdraws a notification once its request is answered or expired, its turn is read, or its thread is deleted (`notifications_sent.withdrawn_at`, a background push naming the keys), and computes the badge (SQL, checked against `Tests/Fixtures/sync/attention.json`). `Scripts/sim-push.sh` feeds the spool to `xcrun simctl push`; a real APNs push never wakes a Simulator app, so there the backstop clears withdrawn notifications. `Infra` carries the APNs secrets behind `INCLUDE_APNS_SECRETS` in `Infra/taskdefs/features.env`. On the phone, `Sources/WorkspaceMirror/PushEnvironment.swift` picks `sandbox` or `production` from the build and `MirrorNotifications.swift` (`stillOutstanding`, `needsYouCount`) judges a delivered notification from the mirror (no `UserNotifications` there); `Apps/iOS/B4App/AppDelegate.swift` handles notifications and background wakes, and `MirrorHost` removes withdrawn and ended notifications and sets the badge (the backstop, never while the sync is parked), `Sources/WorkspaceMirror/MirrorLocation.swift` puts the mirror in the App Group, and `Apps/iOSWidget/` is the `B4App-iOSWidget` extension, which reads the mirror read-only through `MirrorGlance`. The App Group id (`B4APP_APP_GROUP`) and URL scheme are per flavour in `Config/Flavor-*.xcconfig`; the entitlements are the flavour's `B4APP_IOS_ENTITLEMENTS` file and `Apps/iOSWidget/B4AppWidget.entitlements`.
- `Sources/Coordinator` is the service both the app and the CLI talk to over the Unix socket; `Sources/CoordinatorMain` is its executable.
- `Sources/CodexAdapter`, `ClaudeAdapter`, `B4Adapter`: one per native runtime. `Apps/` holds the two thin app targets.
- Fake runtimes for tests live under `Tests/<Adapter>Tests/Fixtures/` (`fake-codex.py`, `fake-claude.py`, `fake-b4.py`, plus `fake-b4-cli.py` and `fake-node.sh` for managed servers: `Tests/CoordinatorTests/FakeB4Project.swift` builds a scratch project whose `node_modules/@b4run/cli/dist/index.js` is the fake CLI and sets `B4APP_NODE_PATH` to the shim); the coordinator tests reuse them by path. Live tests are gated by `B4APP_LIVE_CODEX`, `B4APP_LIVE_CLAUDE`, `B4APP_LIVE_B4_URL`, and `B4APP_LIVE_LAUNCHCTL` (the legacy LaunchAgent boot-out against the real `launchctl`, with a throwaway job label).
- `Sources/Coordinator/SessionService.swift` is also the only maker of thread folders (`appFolder(forThread:)`, under `PlatformPaths.threadFoldersDir`, D-203); the `appFolders` table that records them is local to the Mac, never synced, and a thread in one has no environment. It is the only writer of turns, display items, and runtime requests; adapters emit `AdapterEvent`s with native ids and the session service maps them to app ids. `Sources/Coordinator/LocalServerService.swift` is the only owner of managed server processes (`ManagedProcess` in `WorkspacePlatform`); it never signals a process whose identity it has not verified.

## Decisions and gate records

- A decision is one file, `docs/decisions/D-NNN-<slug>.md`: its first line is the dated topic heading `## YYYY-MM-DD (topic)`, then a blank line, then the entry as one `- **D-NNN Title.** ...` bullet with its nested lines (the log's style; read a recent file first). A gate record is one file, `docs/verification/YYYY-MM-DD-<slug>.md`, whose first line is `## YYYY-MM-DD: <title>`. Slugs are lowercase a-z, 0-9 and hyphens. Never add an entry to `docs/decisions.md` or `docs/verification.md`; they describe the layout, and `Scripts/docs-index.sh --check` fails when an entry is there.
- Take the number when you open the pull request, not when the branch starts: `Scripts/docs-index.sh --next` prints the first number after the highest on `origin/main`, in your tree, and in open pull requests (through `gh`, when it is signed in). If main takes your number before you merge, rename the file (and the number inside it) and push; never renumber an entry that is on main.
- Amend an earlier decision from the new decision's file ("amends D-NNN"); do not edit the earlier file.
- `Scripts/docs-index.sh --check` must pass (CI's "Workflow and shell lint" job runs it). Plain `Scripts/docs-index.sh` writes the newest-first indexes `docs/decisions/index.md` and `docs/verification/index.md`, which are gitignored: a committed index would conflict between pull requests as the two logs did (D-174).

## Rules

- Never represent a mocked response as a working integration. Unimplemented adapter behavior throws `WorkspaceError(.unsupportedCapability)` naming the milestone.
- The UI never touches processes, sockets, files, or secrets directly.
- Secrets never appear in arguments, JSON results, logs, or UI state. Use `SecretStore` references.
- Ordinary tests use fixtures and fake executables. Live provider tests are opt-in and never run in CI.
- Record material decisions as `docs/decisions/D-NNN-<slug>.md` and gate results as `docs/verification/YYYY-MM-DD-<slug>.md` ("Decisions and gate records" above), versions in `docs/compatibility.md`, and keep `docs/milestones.md` current with implemented, fixture-tested, live-tested, or blocked.
- Do not reformat `docs/roadmaps/*.md`; it is the owner's document.
