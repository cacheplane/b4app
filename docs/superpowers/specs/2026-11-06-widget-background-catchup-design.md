# Widget background catch-up

The owner observed on production build 2611060126 that a fresh approval H delivered its alert and badge with Low Power Mode off, but the widget showed H only after opening the app. After that foreground refresh, H's background approval-dot update passed. Fresh reply I's notification withdrawal after reading on the Mac also passed while the phone stayed locked. Preserve these separate results; the exact device-side cause of H's initial stale widget is not proven.

## Defect and chosen approach

`MirrorHost.backgroundRefresh` currently resumes the sync and waits for any next `AppliedBatch`. It then suspends the loop even when that batch came from a partial page or snapshot. `MirrorSync` receives `PullResponse.more` but does not expose end-of-feed completion to the host. A new thread on a later page can therefore remain absent when the wake ends.

Keep the existing App Group mirror and widget reader. Add a bounded `MirrorSync.refresh(waitingAtMost:)` operation that registers before nudging, requires a sync turn begun after its registration, drains pages while `more` is true without long polling, and returns only after applying and publishing the final page. An empty final page is successful catch-up. A pre-existing pull or snapshot alone cannot complete the operation. Cancellation, stop, authorization failure and timeout release waiters exactly once. The operation does not itself resume a parked loop; the account remains the lifecycle owner.

`MirrorHost` resumes through its existing ordered account controls, awaits this operation with the current eight-second limit, requests a final widget reload, reconciles notifications and parks sync before finishing the system callback when the app remains in the background. A small Foundation-only `MirrorRefreshCoordinator` serializes overlapping host work with a request generation. Every wake increments the generation, including a wake arriving during reconciliation or parking. Before returning, the shared task repeats the entire resume/catch-up/reload/reconcile/park cycle if a newer wake arrived, within one overall eleven-second budget (the existing three-second queued-resume plus eight-second pull budget). It reports failure rather than claiming catch-up when a late wake cannot be serviced within that budget. Clear the shared task atomically with the final generation check, so a late joiner cannot reuse an already-completed read. Log safe start/result and widget timeline counts to distinguish future device scheduling from sync failures; never log push tokens, payloads, titles or credentials.

Alternatives: waiting longer for the first batch retains the premature-completion bug. Adding a notification service extension or independent widget networking changes account/storage ownership and signing without evidence that it is necessary. The selected fix addresses a reproducible lifecycle defect within the existing architecture. iOS background execution and WidgetKit reload scheduling remain system-controlled, so this does not promise a fixed refresh deadline on a device.

## Verification and release

Use the real `MirrorSync`, a file-backed mirror, a controlled fake hub and the real `MirrorGlance` reader to reproduce a first page that does not contain the new approval thread, then a later page that does. Prove refresh completion includes the new needs-input row before suspension, including byte-limited partial pages, empty catch-up, a pull already in flight, snapshot recovery, cancellation, stop, failure/timeout and overlapping refreshes, and a host wake that arrives after the final pull during cleanup. Pending refreshes independently force nonpolling; do not rely on `nudged`, which is cleared at cycle start. Record an executable failing assertion before implementing the fix. Run package tests, strict formatting, both app builds and repository documentation checks. Review the diff, open a PR, merge only after green checks, upload a production TestFlight build from the clean merged commit and verify Apple beta readiness. The user explicitly authorized this sequence. Physical fresh-thread widget verification remains for the owner on that build.
