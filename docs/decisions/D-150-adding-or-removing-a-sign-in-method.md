## 2026-11-02 (step-up for account changes)

Closes D-113. Built on `blove/xenodochial-morse-e3bed8`. Numbered D-150: D-121 to D-140 are taken and D-141 onward is reserved for the APNs slice.

- **D-150 Adding or removing a sign-in method and deleting the account need a step-up grant: a passkey or Apple assertion of the same user, made on the same device within two minutes, used once.** Resolves D-113 (and the add-passkey case D-098 accepted).
  - **What it gates.** `POST /v1/me/passkeys/begin`, `POST /v1/me/apple` (linking an Apple ID is adding a sign-in method too: without it a thief with a token links their own Apple ID and keeps a way in after the token is revoked), `DELETE /v1/me/identities/{id}`, and `DELETE /v1/me`. An add is gated at its begin: the finish needs the begin's ceremony, which now also records the device and is refused (`ceremony_expired`) on any other. Each refusal that needs no grant comes first and spends nothing: `apple_linked` at the link begin, `not_found` for an id that is not the caller's, `last_identity`, and `shared_org`.
  - **How it is earned.** New routes behind the device token: `POST /v1/me/step-up/passkey/begin` (assertion options whose `allowCredentials` are the user's passkeys, user verification required) and `.../finish`; `POST /v1/me/step-up/apple` (the link begin's body: empty natively, the verifier hash and scheme on the web), `.../apple/native` (the identity token only: no code is exchanged, so Apple keeps no new grant), and `.../apple/handoff` (the web flow, through the same callback). Each ceremony records the user and the device that began it and finishes only for both; an Apple assertion counts only when its `sub` is the account's own Apple ID. A finish answers `{"stepUp": "<grant>", "expiresAt": "…"}`.
  - **The grant.** A 256-bit random token in a new table, `step_up_grants` (migration `0014_step_up.sql`; 0012 and 0013 are M8f's), stored as its SHA-256 with the org, user, device, method, and an expiry two minutes on. Not a ceremony row: a ceremony id is kept in clear, and the grant is a bearer secret, so it is hashed like a device token. It goes in a `B4-Step-Up` header (so `DELETE` stays bodiless) and is taken once, by one conditional `UPDATE` matching hash, user, device, unexpired, and unused. One grant covers one change, not a window: the UI asks right before each change, so a window buys nothing and would let a second change ride on the first. A change that fails after taking it (a failed Apple revoke, `500`) needs a new assertion. Pruning deletes expired grants with the ceremonies.
  - **The refusal.** A missing, unknown, expired, spent, or another device's grant is `403 step_up_required` with `details.methods`, the kinds the account can assert with (`passkey`, `apple`), so the client knows which sheet to show. The cases are indistinguishable, as for ceremonies.
  - **An account with no sign-in method** (operator-enrolled, never signed in) has nothing to assert with, so it adds its first method, and deletes itself, on the token alone, as before; D-113's risk stays accepted for that case only. Every account made by signing in has a method from its first moment.
  - **Clients.** The grant never leaves the process that earned it. On the Mac the assertion (or the Apple handoff) goes to the coordinator inside the change's own command (`account.addPasskeyBegin`, `account.appleLinkStart`, `account.removeIdentity`, `account.delete` take `stepUp`), which finishes the step-up and makes the change in one command; the verifier of a step-up's Apple web flow stays in the coordinator (`account.stepUpAppleStart`). The phone's `MirrorAccount` does the same in process. Settings → Account confirms with a passkey when the account has one, else with Apple; so an Apple-only account adds its first passkey after an Apple assertion. A closed sheet changes nothing and shows nothing; `step_up_required` (a grant the hub refused, or a method another device added meanwhile) re-reads the methods and shows one line.
