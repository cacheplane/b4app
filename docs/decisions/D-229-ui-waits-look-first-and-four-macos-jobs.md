## 2026-11-14 (CI: UI waits look first; a run asks for four macOS runners, or none)

- **D-229 The UI suites' waits look before they wait; the four app builds are steps of two jobs that already hold a macOS runner; a pull request that touches only `Hub/`, `Infra/`, `docs/` or a root Markdown file runs no macOS job.** Measured on `main` e04f5f8 (run 43612368923) and #199's run: jobs waited 1 to 8.6 minutes for a macOS runner before they started, and of the UI jobs' test time 250 s of the smoke suite's 543 s and 118 s of the layout shards' 837 s were waits.
  - **The waits.** XCTest's `waitForExistence` took at least a second for an element already on screen: 267 of the 275 waits in the two suites took 0.9 to 1.6 s. `appears(within:)` and `disappears(within:)` (`Tests/iOSLayout/UITests/Waits.swift`, and the same file in `Tests/macOSSmoke/UITests/`) look at once and then every 0.1 s, and once more after the deadline (the gate record 2026-11-14-layout-shards-hosted). Every call site keeps its condition and its timeout; no assertion changed. A second that a wait used to spend is no longer there for the app to settle in, so a check that leaned on it without saying so can now fail: the gate record holds the runs.
  - **Not changed: the launch window's 15 seconds.** In that run two of the smoke suite's 14 launches showed no window in the 15 s `launchWithWindow` allows, and the helper opened one. Shortening that wait would bring back the second window it was written against (0eda1d2), and the smoke suite drives the pointer, so it was not run on the owner's Mac to find why the window does not come.
  - **The runners.** GitHub runs 5 macOS jobs at once for the organisation on its plan (the Team plan has the same 5), and a run asked for 5: two runs at once queue. The two iOS app builds are now steps of the package job, after its tests, and the two macOS builds are steps of the smoke job; each builds in a DerivedData of its own, as before. A run asks for 4.
  - **The required check for the builds.** Branch protection requires "macOS and iOS app builds". A job of that name (`apps`, on Linux) always runs and reads the four build steps' own outcomes, not the two jobs' results: a failed test in either job does not fail it, and a build that failed, was cancelled or never ran does. The build steps run whatever the tests before them did. No branch protection setting changes.
  - **The scope.** `scope` (on Linux) lists a pull request's changed files and `Scripts/ci_scope.py` answers whether the macOS jobs are needed. It answers no only when every path, and both names of a rename, is under `Hub/`, `Infra/` or `docs/` or is a Markdown file at the root, and the list is as long as GitHub says the change is; nothing those jobs build or test reads those trees (the shared contracts are in `Tests/Fixtures/sync`, which is outside them). The macOS jobs skip only on that explicit no: a failed or missing answer runs them, and a push to `main` always does. The two required checks that combine jobs accept a skip only together with that no. 10 of the last 60 merged pull requests were such changes.
  - **Cost.** The macOS jobs start after `scope`, a Linux job of a few seconds plus its wait for a runner. The package job grows by the two iOS builds (185 s in that run) and the smoke job by the two macOS builds (237 s), so a run that finds its runners at once is no shorter and may be longer; the gain is in runs that queued. This entry claims no speedup; the gate record holds the first hosted measurement.
