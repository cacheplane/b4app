## 2026-11-04 (an instance cut off from the database)

The open question left by the Phoenix comparison (`docs/research/2026-11-03-phoenix-source-hardening/pubsub_presence.md`, M3). Numbered D-179 by `Scripts/docs-index.sh --next`.

- **D-179 An instance that cannot write its heartbeat keeps its links; it does not fence itself off.** Once the liveness window (20 s) passes without a heartbeat, the other instances count it dead and the next link of one of its users is claimed elsewhere, so that user's links are split until it can write again; then the heartbeat's `lost_claims` check closes its side (1001) and they reconnect to the owner (D-085). Phoenix.Tracker would take the opposite approach, marking itself down. The alternative here, closing every link once the instance turns stale, was rejected: a stale heartbeat usually means the database is unreachable for every instance, when no device could be served anywhere and every reconnect would fail, so self-fencing would turn a database blip into every device of the instance offline. While split, the cut-off instance cannot run commands that need the database either, so the harm is bounded to relay frames between two of one user's devices on different instances not reaching each other. `/readyz` answers `503` with `"instances": "stale"` meanwhile, so after three failed checks (about 30 s, `Infra/modules/hub/alb.tf`) the load balancer stops sending it new connections; when every target is unhealthy, as in a database-wide outage, it fails open and keeps sending to all of them. `tests/instances.rs` (`a_dead_heartbeat_lets_the_other_instance_claim_and_the_old_owner_lets_go`) now asserts the link stays up while the instance is stale.
