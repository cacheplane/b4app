## 2026-11-02 (sign-in build)

- **D-098 Pairing a signed-in phone-only account merges it into the Mac's account; a refusal says why, and the phone always tries the merge first.** `accounts::merge_in`, `devices::redeem_merging`, `routes/enroll.rs`; phone: `MirrorAccount.pair` (`Sources/WorkspaceMirror/MirrorPairing.swift`). `POST /v1/enroll` with the phone's bearer token claims the code, moves the phone-only account's identities to the code's user, deletes that account's org, user, devices, and tokens (the old device is deleted, not revoked, because its org goes; its token is `401` at once), and enrolls the phone under the code's account, in one transaction. A bad code, checked first (`invalid_code` whatever the token), or a refusal changes nothing and leaves the code redeemable. `409 merge_refused` carries `details.reason`: `same_account` (the token's org is the code's, whichever user), `shared_org`, or `has_mac` (the account has or ever had a `macos` device, revoked included); it is absent when the hub cannot say. On the phone, success is merged; `same_account` shows "This iPhone is already paired"; any other refusal asks "Switch to this Mac's account? You'll be signed out of <org>." (the code's org is unknown before redeeming, so the spec's copy is adapted). Switch redeems the code without a token first, and only then ends the old session, forgets its token, and empties the mirror, so an expired code leaves the phone as it was. A `401` on the merge (the phone's session was already dead) signs that account out and enrolls plainly. A code for another hub than the phone's asks to switch without sending the token there. Accepted: a stolen phone-only token can merge that account's identities into the thief's account, which is no worse than adding a passkey with the same stolen token; and a merge can leave an account with two Apple IDs (D-093's check is skipped).
