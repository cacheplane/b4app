## 2026-11-17 (a turn that ended with no outcome)

- **D-251 A terminal turn with no outcome draws "Turn ended." in the muted colour; only a recorded failure draws "Turn failed." in the danger colour.** The hill climb's audit read from the code that a turn which is `terminal` with no outcome was drawn as a failure (its defect 13). The transcript's note chose its words with "cancelled, or else failed", so a missing outcome fell into "failed".
  - **How a turn gets there.** Every adapter puts an outcome on the turn it finishes, so the Mac's own turns do not. A turn can still be terminal with none: its status and its outcome are separate synced columns and the status can arrive first (the hub's notification rule already allows for "a terminal turn with no outcome yet"); an outcome a newer build wrote decodes as none in an older one; and the coordinator stores whatever outcome a finished-turn event carries, including none.
  - **Every other reader already agreed.** The thread list is `failed` only when the latest outcome is `failed`, the hub notifies only for `completed` or `failed`, and the thread's detail line says "finished". The note was the one place that said otherwise.
  - **The note.** `TurnNoteRow` reads the outcome exhaustively: `failed` is "Turn failed.", `cancelled` is "Turn stopped.", and none is "Turn ended.". It still draws a note, so a turn with no recorded outcome is not read as a completed one either. An open step in such a turn is settled as unfinished, as before.
  - **Left out.** Making the coordinator refuse or repair a finished-turn event with no outcome: no adapter sends one, and the stored row would still need a reader that does not guess.
