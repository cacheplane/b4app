## 2026-11-02 (sign-in build)

- **D-110 A pairing link is the site link only for the flavour's own hub, and each iPhone flavour registers only its own scheme.** Amends D-066. `PairLink.make(siteDomain:code:)` and `parse(_:siteDomain:hubURL:legacyLoopback:)` (`Sources/WorkspaceProtocol/Relay.swift`), `HubSync.pair`. A site link is `https`, exactly the flavour's host, path `/pair`, no user, port, or query, and a fragment that is exactly `c=<code>`; its hub is the flavour's. M8c's `b4app://pair?hub=&code=` is read only by the local flavour, and only for a loopback hub. Any `https` URL with the path `/pair` counts as a pair link, so another flavour's is answered "not valid" rather than ignored. The coordinator decides the link: `HubPair.Result.link` is set only when the joined hub canonically equals the flavour's hub; otherwise the sheet shows no QR code, only "On your iPhone, tap Use an enrollment code, then enter <hub URL> and the code <code>." The system Camera, `onOpenURL`, and both scanners reach one decision (`PhoneFlavor.pairLinkDecision`); the same URL arriving again within 10 s is ignored, and an arrival waits behind a sheet or alert already shown. Each iPhone flavour registers only `b4app`, `b4app-beta`, or `b4app-local`, so a `b4app://` link opens only prod. "Connect your Mac" replaces the thread list of a signed-in phone whose device list is non-empty and has no `macos` device (a revoked Mac counts as one); a signed-out phone sees the sign-in screen, and an unread list counts as having a Mac, so a phone with one never flashes the view.
