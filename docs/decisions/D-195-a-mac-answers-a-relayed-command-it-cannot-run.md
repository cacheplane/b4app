## 2026-11-09 (relay version skew)

- **D-195 A Mac answers a relayed command whose method its build does not know, instead of dropping it.** Found in the reassessment of D-180: the owner's installed prod and Beta Mac apps predate `project.create|update|delete`, while production's hub (`hub-v0.5.1`) forwards them, so the phone's project sheet waited out the hub's 15 s reply wait and showed "Not confirmed". `RelayLink` skipped any frame it could not decode, a command included. Now `RelayFrame.decode` (`WorkspaceSync/HubLinkConnection.swift`) tells a `command` with a string `id` apart from other unreadable frames (`HubLinkError.unknownCommand(id:method:)`), and a link whose `hello` named it a host replies at once with `unsupported_capability`, "Your Mac's Agent Workspace can't do “<method>” yet. Update it on the Mac, then try again.", `details: { reason: "unknown_method", method }`; the phone shows that text where the command was made. A client link never answers commands; every other unreadable frame is still skipped and the link stays up. No hub or phone change: the hub already passes a host's reply through, and the phone already words a refusal by its message. This helps only Mac builds from now on (an installed older build still drops the command), so the owner's prod and Beta Mac apps still need repackaging from main for D-180 and D-184. `RelayLinkTests` (`aMacAnswersACommandItCannotRunAtOnce`, `aPhoneIgnoresACommandItCannotRead`), `RelayWireTests` (`aCommandWithAnUnknownMethodIsNamedNotJustSkipped`); `Hub/API.md`, "A Mac older than the command".
