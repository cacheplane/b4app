## 2026-11-14 (CI: the layout fixture builds while the Simulator boots; the shards are rebalanced; the beta iOS build moves to shard 1)

- **D-232 A layout shard builds its fixture while the Simulator boots and waits for the boot before it runs a test; `testSyncCopyJourneys` moves from shard 2 to shard 1; the beta iOS app build is a step of shard 1, not of the package job; `Scripts/ci_timings.py` reads a run's clocks from GitHub.** Measured on the four green first attempts with D-229's workflow (runs 43629968947, 43671966677, 43673503907, 43675337568): the longest macOS job ran 975, 960, 865 and 1,015 s, and it was shard 2 in three of them and the package job in one. This entry claims no speedup: no run of this workflow exists yet, and the gate record (2026-11-14-ci-boot-overlap-and-balance) says what a hosted run has to show.
  - **The boot.** `prepare_ios_layout_simulator.py` begins the boot "before app compilation", but the workflow then waited for `simctl bootstatus` before it called the script that compiles. In 15 shard logs of 8 runs that wait was 68 to 165 s in which the job did nothing else, and the fixture's build took 148 to 407 s after it. `Scripts/test-ios-layout.sh` now runs `xcodebuild build-for-testing`, then `simctl bootstatus -b` on the Simulator the workflow names (`B4APP_LAYOUT_SIMULATOR_UDID`), then `xcodebuild test-without-building` with the same arguments. A failed build or a boot that does not finish ends the script before any test, and under `CI` the script refuses to run with no Simulator to wait for. Locally the script begins its own Simulator's boot and waits the same way.
  - **What that removes.** The Simulator used to sit booted through the whole fixture build before the first test. Now the first test can start as soon as the boot has finished. D-197's failure (run 42770467156) was a run with no wait for the boot at all, which is not the case here, but the idle minutes are gone and only hosted runs show whether a first journey leaned on them.
  - **The shards.** From the four runs' result bundles, the journeys of shard 1 took 222 to 287 s and those of shard 2 291 to 533 s: D-225 split them by times from before D-229's waits. `testSyncCopyJourneys` (45 to 77 s) moves to shard 1, which makes the sums 299 to 363 s and 246 to 456 s on those same runs. The plan is still checked as a partition of the whole contract by every shard (D-225); shard 1 now owes 70 checkpoints and shard 2 owes 59. The choice and its check use the same four runs, so this shows a better balance is plausible, not its size.
  - **The beta iOS build.** With both iOS builds the package job ran 817 to 960 s. The beta build (92 to 135 s there) is now a step of layout shard 1, after its tests and whatever they did, in the fixture's DerivedData. It does not fail that job (`continue-on-error`), whose result is the layout tests' required check; the builds' check reads the step's own outcome. Shard 1's limit is 35 minutes for it. Only shard 1 sets the job's `ios-beta` output and shard 2 leaves it empty; if GitHub does not deliver it, the builds' check fails, and reverting this part alone restores D-229's arrangement.
  - **The required checks.** "macOS and iOS app builds" still passes only when all four build steps' outcomes are `success`, and accepts skipped jobs only with the scope's explicit `false`, now for three jobs. `Scripts/tests/test_ci_scope.py` runs both combining checks' own shell on 20 outcomes that must fail (a failed, cancelled, skipped or missing build; a skip without the scope's no) and each of four weakenings of that shell fails a test. No check name, scheme, destination, test or branch protection setting changes.
  - **Tried and dropped.** Building an app in the DerivedData of the UI fixture that had just built the same package, to reuse its modules: Xcode ran the same compile tasks either way (macOS 186 and 186, iOS 116 and 116), so nothing is shared between two projects' builds of one package.
  - **Not done, for the owner to decide.** The two iOS app builds compile every module for `arm64` and `x86_64`, because the destination is the generic Simulator; an `arm64`-only build would be about half the compile of both, and it would stop checking the Intel Simulator slice, which nothing ships. Larger macOS runners would cost more per minute. Neither is in this change.
  - **Expected, not measured.** Replaying the four runs with these changes: if the overlap saves the whole boot wait the longest job's median falls from 967 s to about 840 s, and if it saves nothing, to about 910 s, with one run of the four slower than before; the smoke job (816 to 842 s), which this does not touch, is then the longest. The macOS runner time of a run changes by about minus twice the saving plus the beta build's loss of the first iOS build's warm module cache (28 to 48 s in those runs).
  - **The tool.** `Scripts/ci_timings.py collect | summarize | steps` writes one row per job of each attempt and derives the run's span, the wait before the macOS jobs are created, each job's wait for a runner and run time, the wait after the last macOS job, and runner time by class. A job cancelled while it waited never started and is counted in no run time; a job a re-run did not run is in none of that attempt's clocks. The rows for 85 runs are in `docs/research/2026-11-14-ci-delivery/`, with the manifest the comparison was fixed by.
