## 2026-11-11 (runtime commands)

- **D-209 A runtime's own commands are listed from what the runtime reports, kept on the connection, and run as messages (amends D-207).** D-207 left Claude Code's and Codex's commands out for want of a contract. This is the contract. The owner asked for "all of the same codex / claude commands" in the composer, following the thread's runtime.
  - **A command is a message.** A `RuntimeCommand` (`WorkspaceProtocol/RuntimeOptions.swift`) is a name, the runtime's one-line description, an argument hint, and aliases. The app never runs one: a message that starts with `/name` goes to the thread's runtime through `turn.send` like any other, so drafts, send outcomes, the relay from the phone, and the turn's lifecycle are unchanged, and there is no new coordinator method. A token no listed command answers to is still an ordinary message.
  - **Claude Code** lists its commands (built-ins, custom commands, and skills) in the answer to the stream-json `initialize` request; the adapter kept none of it before. `ClaudeSession` now keeps the list and `ClaudeAdapter` emits `commands.changed` each time a session starts. Sent as a message, a command runs inside Claude Code; a local one such as `/context` answers with one synthetic assistant message and a zero-cost result, which the existing translation already shows (recorded live on 2.1.282, 2026-11-11). Claude Code can answer `initialize` before its plugins have loaded: the same folder reported 94 commands and then 75.
  - **Codex** has no list. Its slash commands belong to its terminal UI. The adapter names the two that have an app-server method behind them, `review` (`review/start`; alone it reviews the working tree, words after it are the reviewer's instructions) and `compact` (`thread/compact/start`), in its inspection, and `sendTurn` routes a message that is one of them to that method instead of `turn/start`. `thread/compact/start` answers `{}`, so the turn's id comes from the `turn/started` that follows. Any other slash text is a message to the model, as before.
  - **Where the list lives.** `connections.commands` (a JSON list, null for B4 and until the runtime has reported), synced like `models`: Mac migration `0013_connection_commands`, hub `0019_connection_commands`, mirror schema version 8. It is not clocked and not phone-writable; only the Mac that owns the connection writes it. Stored entries are normalized (`RuntimeCommand.normalized`): a name a composer token can spell, one line of description cut to 160 characters, at most 300 commands, so the row stays near 20 KB.
  - **When it is written.** A check that finds the runtime ready stores the list an inspection carries (Codex). For a runtime that reports only from a session (the `CommandListing` protocol; Claude Code) the coordinator asks once, while the connection has no list: it starts Claude Code in an empty temporary folder, reads the handshake, and closes it without sending a message, so there is no transcript and no inference, though the owner's session-start hooks run. After that, each `commands.changed` replaces the list only when it names a command the stored list lacks (`RuntimeCommand.replacement`), so a short early report does not flap the row or the change log. The coordinator turns the adapter's event into a `connection.changed` carrying the connection; no client sees `commands.changed`.
  - **The list is the connection's, not the thread's.** Claude Code's commands depend on the folder (a project's `.claude/commands` and skills). The stored list is the one the most recent session to name something new reported, so a project's own command can be listed on a thread in another folder, where Claude Code will read it as plain text, and a command of this thread's folder can be missing until a session starts there. A per-thread list was weighed and left out: it would be another synced column of that size on every thread, or a Mac-only answer the phone could not have. Typing the command by hand always works.
  - **Composer.** The `/` list shows the app's commands first, then the runtime's for the thread's connection (or the connection a new thread would start on): names that start with the token, then a plugin's command by the part after its colon or by an alias, then names that contain the token. A runtime command with the same name as one of the app's (`/model`) is left out. Return on one that takes no argument sends it (in a new-thread draft, as the thread's first message); on one with an argument hint it completes `/name ` in the draft for the rest to be typed. While a turn runs, or the draft cannot be sent, the command waits in the draft. The rows scroll past eight.
  - **Palette.** Commands (⇧⌘P) lists the same commands in a section named for the connection and matches them in a typed query, after an app command that matches as well. Return puts `/name ` in the draft through "Use as message", so the palette still never sends and never overwrites a draft.
  - **Not built.** Per-thread lists; argument completion; Claude Code's interactive-only commands (those it does not report over stream-json); Codex's other terminal commands (`/status`, `/diff`, `/mention`, and the rest have no app-server method); `review` against a base branch or a commit (the method takes those targets, the command does not parse them yet).
  - **Tests.** `RuntimeOptionsTests` (normalizing, replacement, parsing), `ClaudeSessionTests` (a session reports its commands, the one-time read sends no message, `/context` runs as a turn), `CodexAppServerTests` (the inspection's list, the routing, review and compact as turns), `ClaudeSessionServiceTests` (the list reaches the connection, a session with a project command replaces it and clients hear `connection.changed`, commands run as turns for both runtimes), and `PaletteTests` (the composer's order and picks, the palette's section and its draft-only rule). Fixture-tested; Codex's review and compact have not run against a live Codex.
