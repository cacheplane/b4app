## 2026-11-02 (sign-in build)

- **D-099 The hub returns the user's id, and the Mac's account registry is keyed on it.** `AuthSession.userId` and `GET /v1/me`'s `userId` (`users.id`; additive, `minClientProtocol` unchanged); `Sources/WorkspaceStorage/AccountRegistry.swift`, `Sources/Coordinator/Accounts/AccountManager.swift`. The first build keyed it on `<org slug>/<username>`, which a reset or re-seeded hub (the owner's local one) reuses, and changing the key after the registry ships would need a migration. The registry is a database of its own (`registry` beside `workspace`, `<name>_registry` beside any other) with its own migration list (`0001_registry`, `0002_account_state`), unique on `(hub_url, hub_user_id)`, with hub URLs stored and compared canonically (`HubURL.canonical`: no trailing `/`). An adopted `workspace` is registered at start from its link with no hub call, as `device:<deviceId>` until the first `/v1/me` names the user; a sign-in whose user has no row claims the placeholder row of the device the hub reused (same local id and database); a session from a hub that sends no `userId` registers a placeholder too. `needs_onboarding` and `hub_session_left_open` are stored, so a restart mid-onboarding never flashes the workspace. A late `401` or `/v1/me` answer from a closed scope is ignored (each scope has an instance id), and a `401` before any name is known signs out of "your account", never the slug. The workspace and registry migrators refuse, with `incompatible_version`, a database that records a migration newer than every bundled one, so an older build never runs against a newer store.
