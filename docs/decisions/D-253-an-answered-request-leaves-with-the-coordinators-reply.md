## 2026-11-17 (an answered request leaves with the reply)

- **D-253 On the Mac, a request that was answered leaves the thread with the coordinator's reply to the answer, not only with the resolved event that follows.** The hill climb's audit read from the code that the Mac's approval buttons could be offered again between the reply and the event (its defect 14): a second click sent an answer the coordinator refused as stale.
  - **Cause.** `WorkspaceModel.respond` and `.answer` disable the card through `busy` for as long as the call is out, and threw the reply away. The card was removed only by `runtime_request.resolved`, which reaches the model on a separate stream. The coordinator publishes that event before it returns, but nothing orders the two on the model's side, and whenever the reply was applied first the buttons were live again on a request that was already resolved.
  - **The change.** The reply is the request as it now stands (`RequestRespond.Result.request`). When it is no longer pending, the model removes it from the open thread's requests at once. The event still removes it when it arrives first, and removing it twice is harmless.
  - **What stays.** A refused answer and a reply that is still pending keep the card and its buttons. The phone is unchanged: its answer goes through the relay, its card is drawn from the mirror, and D-154 has sync resolve it; removing it early there could be undone by the next read of the mirror.
