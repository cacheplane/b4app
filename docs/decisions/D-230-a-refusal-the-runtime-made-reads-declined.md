## 2026-11-14 (a refusal the runtime made itself)

- **D-230 A tool call the runtime refused by itself reads "declined" on Claude Code and B4, where the runtime says so (amends D-227).** D-227 marked only the refusals the app made, and left a call the runtime refused without asking (a Claude Code deny rule or permission mode, a B4 route's permission policy) as `failed`, in the danger colour, because the app "cannot tell it from another error". Both runtimes do say which calls they refused, in a field or a code and not in the result's words, so the adapters now read that. The code is commits 55e4e3c6 and the one after it (B4's step, and the check against the real runtime).
  - **Claude Code.** Two signals, both keyed by tool use id. A `system` frame with subtype `permission_denied` is sent when a tool use is denied without a prompt; the turn's `result` frame lists every denial in `permission_denials`, which Claude Code's own schema calls the authoritative record and the frame a best-effort notice. `ClaudeTurnTracker` takes the frame like the app's own mark when it comes before the tool use's error result. When it comes after, or only the result names the tool use, the step was already closed as `failed`: the tracker keeps what each failed step was closed with for the length of the turn and closes it again as `declined`, with the same name, input and output. A step can therefore read "failed" until the turn ends and then "declined"; that is the price of not reading the words. An error result that neither signal names is `failed` as before.
  - **B4.** B4 stamps a step on every tool result (`additional_kwargs.b4_step` on the `ToolMessage`), whose `status` is `completed`, `failed` or `denied`; its documentation says a denied call "has `status: "denied"`". A refusal is returned to the model as an ordinary result (the message's own `status` stays `success`), so before this the app stored it as `completed` and the dense line counted a refused call as a step that ran. `B4TurnTranslator` now stores a result whose step is `denied` as `declined`, and takes a `step` event with that status as a mark for the result that follows. By B4's source this covers each of its gates: a tool named in `permissions.deny` (the one checked against the real runtime), the permission mode failing closed, an argument constraint, the workspace's path and command gates, and the app's own "Deny", which D-227 already marked.
  - **Not the error code.** The first version of this change read the `[DAWN_E3001]` prefix on the result's text, from an old checkout of B4's source. The published 0.15.8 the app pins calls it `B4_E3001`, and the step is the field B4 made for the purpose; the prefix is not read.
  - **History.** B4's checkpoint keeps the same message, so `B4Protocol.snapshotItems` marks a refused call `declined` too. Claude Code's transcript has no field for a denial (the result is an error with free text, and `permission_denials` is not written to it), so a Claude Code item read from history is still `failed`. A live row keeps its payload through a snapshot merge (D-031), so this only shows on a thread whose turns this Mac did not see.
  - **What is still not covered.** Claude Code history, as above. A Claude Code denial made by a `PreToolUse` hook is, by Claude Code's own note, not in the `permission_denied` frames; whether `permission_denials` lists it was not checked. A B4 step that says `failed` in history is still read as `completed`, as before; that is a different question from refusals and is left alone.
  - **Why not the words.** As D-227: "Permission denied" is also what a tool says when the file system refuses it. A field and a documented code are the runtime's contract; the sentence after them is not.
  - **Verification.** B4 is checked against the real runtime: `Tests/B4Runtime` (the published CLI against the fake model) has a tool the fixture project's permissions deny, and asserts that it never runs, that no prompt opens, and that its result carries a `denied` step on the stream and in `GET /threads/:id/state`, the two places the adapter reads. `B4TranslatorTests` covers the adapter (a denied step on a serialized message, the same words with a `completed` step or as a bare string, the `step` event, history). Claude Code is fixture-tested only: `ClaudeEventsTests` (the frame before the result and after it; the result's list, a failure it does not name, and nothing carried into the next turn). The frame's and the list's shapes are read from the schema inside the installed Claude Code 2.1.282; Claude Code was not run with a deny rule.
