## 2026-11-14 (a reader who scrolled back holds the view)

- **D-233 Scrolling back from the end holds the transcript where the reader is, at both densities, and a "Jump to latest" button goes back (amends D-223).** D-223's call 7 held the view only after a dense turn was opened. With nothing opened, `TranscriptView.follow` scrolled to the end on every streamed token, new item and ended turn, so reading earlier output during a turn was not possible: on the baseline the three new assertions moved the reader by 764.5, 794 and 540 pt. The code is commit 07273327.
  - **The rule.** `TranscriptEnd.intent(from:to:)` reads each change of the scroll geometry. The end in view (within 8 pt) is following. The viewport's top edge moving up over content of the same height, with the end marker out of view, is reading: a wheel, a drag, Page Up and the scroller all do that. Anything else changes nothing: a reply growing under a still viewport, the view being taken down to the end, and a layout pass that resizes the content and moves the view with it.
  - **Why the height and the end marker are in the rule.** Following rests the view with the transcript's bottom padding below it, so "the end" for this rule is anything within that padding plus 8 pt; without that, the lazy stack's small settling moves after a send read as the reader scrolling, and `sendingAMessageReleasesTheHold` failed. A step that changes the height is a layout pass, not a scroll.
  - **One hold, not two.** Reading sets the same `TranscriptFolds.holds` an opened turn sets, so everything D-223 decided for the hold applies unchanged: the bottom pin and the following stop, the size anchor is the top edge, and the hold ends when the reader reaches the end, sends, or another thread is shown.
  - **Jump to latest.** While the view is held a secondary pill at the bottom of the transcript releases the hold and scrolls to the end. It is shown whenever the hold is, which includes a turn opened at the end of the thread, where the latest output is below the opened steps.
  - **Left as it was.** A new turn releases the hold (D-223 call 7), whoever started it: the transcript cannot tell a local send from one made on another device, so a turn started from the phone still takes a Mac reader to the end. No keyboard shortcut was given to the button: Command-Down belongs to the composer's text view when it has focus.
  - **Verification.** `TranscriptScrollTests.readingBackIsNotPulledToTheEndByTheStream` (both densities) and `readingBackIsNotPulledToTheEndWhenTheTurnEnds` fail on the baseline and pass here; the ten earlier scroll tests pass unchanged; `TranscriptReadingTests` holds the rule. Not checked: the phone's scroll view, the rubber band and the keyboard there; a trackpad in the running Mac app; VoiceOver on the button.
