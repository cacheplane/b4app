## 2026-11-04 (production backup copy verification)

- **D-181 Production backup copies use a regional customer managed key, and the monthly drill compares their restored data in the production VPC through read-only queries. Amends D-071.** PR #122 gave `b4hub-prod-copy` in `us-west-2` its own rotating key, `alias/b4hub-prod-copy`; source backups remain in `us-east-2` for 35 days. The owner authorized the production apply, key verification and continued restore drill on 2026-11-04.
  - **Data path.** Runbook 8 B.3 copies a completed recovery point back to `us-east-2` under the production data key and restores it into an isolated, non-public scratch instance in the existing production VPC. The admin task reads the scratch and live databases without redirecting production's URLs or service. The monthly drill includes the test-account service recovery (A), the copy-region restore (B.1–2), and this data comparison (B.3).
  - **Comparison.** Every organization gets its own explicit tenant context inside a read-only transaction; forced row-level security makes an unscoped owner query insufficient. The restored change count and ordered content digest must match production through the restored maximum sequence. Later live writes may raise production's current sequence and row counts. Backup freshness is measured from its timestamp, not its sequence number.
  - **Cleanup and evidence.** Stop the admin task and delete the scratch instance and temporary return snapshot after comparison, retaining the vault recovery point. Record aggregate results, key identity, copy status and cleanup in a verification record; a successful on-demand copy does not by itself prove the next nightly invocation. The first comparison restored 35 changes and matched the live prefix; see `docs/verification/2026-11-04-prod-copy-vault-restore.md`.
