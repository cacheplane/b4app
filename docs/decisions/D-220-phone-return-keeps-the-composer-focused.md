## 2026-11-13 (composer keys)

- **D-220 A hardware keyboard's Return in the phone's composer sends through the field's own submit and never ends editing; the round control has no Return shortcut (amends D-219 and D-214).** At the owner's direction (after D-219's phone check found that Return with nothing to send dropped the composer's focus: no line was added, and whatever was typed next went nowhere).
  - **The cause.** On iOS 26 SwiftUI's vertical `TextField` treats a hardware keyboard's Return as a submit: `onSubmit` runs, no line is added, and the field ends editing. The on-screen Return is not a submit and adds a line. D-219 left the Send button's `.keyboardShortcut(.return)` (`returnSends()`) to take the key, which it did only while Send was on; with an empty or blank draft, a thread that cannot send, or Stop in Send's place, Return fell through to the field and the caret went with it. This is the same shape as the Mac's D-219 bug, where Return fell through to `TextEditor` and added blank lines.
  - **The keys.** The field's `onSubmit` calls the composer's `onReturn` (the thread and the new thread send when they can and otherwise do nothing) and sets the focus back, so a hardware Return sends when it can and otherwise leaves the caret where it was. The on-screen Return still adds a line, and the round button still sends. `returnSends()` is removed: a shortcut takes the key before an input method could commit a candidate with it (D-219), and with the field handling Return it would only send the draft while focus is elsewhere.
  - **The `/` completions (D-214).** The submit first offers `SlashKey.choose` to `onSlashKey`, as the Mac's text view does before `onReturn`, so while the completions show a hardware Return picks the selected row and a typed slash is never sent; otherwise it is the composer's `onReturn`. The round "choose" control loses its Return shortcut with Send's: it took Return only while its row was available, and with an unavailable row Return fell through and ended editing. The arrows and Escape still reach the completions through `onKeyPress`.
  - **What was tried.** `.onKeyPress(.return)` on the field never sees the key before the submit, so it cannot keep the field from ending editing. The submit ends editing before `onSubmit` returns focus; with the on-screen keyboard showing (only in the Simulator, where the panel's keys arrive alongside it) the keyboard drops and comes back.
  - **Checked.** In the layout harness on the iPhone 17 Pro Simulator (iOS 26.5), with the Simulator panel's Return key: an empty thread draft keeps the caret and the next letter lands; a draft sends; Return while that send is pending does nothing and keeps the caret; the on-screen Return adds a line; the new thread's empty draft keeps the caret. XCUITest's `typeKey(.return)` does not reach the field at all (it neither sent nor submitted, with or without the shortcut), so no UI test covers this. Unverified: an iPad's hardware keyboard, Shift-Return (the panel has no modifiers), and an input method's Return.
