## 2026-11-02 (sign-in build)

- **D-114 Resolved by D-140 (2026-11-02): the Apple callback scheme was the caller's choice at begin, so a hosted hub had to pin it to its flavour before Apple was enabled there.** `routes/apple.rs`: `POST /v1/auth/apple/begin` (and `POST /v1/me/apple`) takes `scheme` from the body, checked only against the allow-list `b4app`, `b4app-beta`, `b4app-local`, and the callback redirects the handoff to that scheme. On a hosted hub this is account takeover: an attacker begins a web sign-in with their own verifier and a scheme no app on the victim's Mac claims (`b4app-beta` on a Mac with only prod), phishes the victim into completing Apple's page, and a malicious app that registered that scheme receives `?handoff=`, which the attacker redeems with the verifier as the victim. It needs malware plus phishing, and Apple is off on the local flavour, so it does not block this branch. Before Sign in with Apple is enabled on any hosted hub, the hub must take its one scheme from configuration (its flavour's) and refuse any other at begin, or hand back through a domain-verified universal link instead of a custom scheme. Tracked in `docs/milestones.md` (M8d). Final review M4, 2026-11-02. *Resolved by D-140:* the hub now takes its one scheme from `B4HUB_APPLE_CALLBACK_SCHEME` and refuses any other at begin. This was done after both hosted hubs had Apple enabled (they went live with the Apple secrets set the same day), so the condition above was briefly not met; the fix still needs a hub release and the variable in each environment to take effect there.
