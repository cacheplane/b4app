## 2026-11-12 (settings belong to a user)

- **D-213 Settings belong to a user: the hub keeps one `viewSettings` row per user, stored as `view:<userId>`, and devices still send and receive `view` (amends D-208).** The owner's rule: settings are per user, separate in each organisation a user belongs to; an organisation's own settings are for things like billing. D-208 stored one row per organisation, so in an organisation with several users only the first user's row was kept. Design: `docs/superpowers/specs/2026-11-12-density-and-user-settings-design.md`, Part 1. The code is commits 48bcbd3 (the id mapping), 5cee9f5 (push and snapshot) and cf8045a, 9a2ad05 and 3715ad1 (the migration, which first went in as 0021).
  - **Where the id lives.** On the hub only. A pushed change to `view` is applied to the pusher's own row, stored as `view:<userId>`; a pull or snapshot hands that row back as `view`. The hub keeps its one keying rule, `(org, id)`, for every synced table, and the per-row clocks, which are keyed by row id, separate by user for free. The table keeps its name `viewSettings`, since it will hold more than list settings; new fields and new code call it the user's settings.
  - **Why devices keep `view`.** Five reasons, from the design. The sync layer has no rename (changes are insert, update or delete, and the change log is append-only). The Mac's store and the phone's mirror are already one per account. A device may not know its real user id yet (the Mac holds a placeholder until the hub's account call answers; the phone's is optional). An older build would keep writing `view`. Exported archives contain `view`. Translating on the hub avoids all five and needs no migration or build on either device.
  - **One refusal.** A `viewSettings` change whose row id is anything but `view`, from any device, is rejected per change with `invalid_row_id` (final, not recorded in the feed, covered by `acceptedThrough`), so no device can create or reach another user's row. This closes the deferred minor in D-208 (the hub accepted any id). The Swift fake hub (`FakeHubAPI`) refuses the same way.
  - **Migration 0020.** `0020_user_settings_rows.sql` renames each stored `view` row, and its column clocks, to `view:<its user>`, so the owner's values and clocks survive and a write after the upgrade still merges against the clock that came with the row. It deletes what no device could reach: a `viewSettings` row whose id is not `view` and the clocks of such a row, and clocks left under `view` with no row. It lifts forced row-level security on `viewSettings` and `column_clocks` for its rewrites and puts each table's flag back as it found it, so a table that was not forced stays unforced (the `environment_history_controls` tests hold every migration to that). Draft pull request 180, from another branch, also holds a `0020`; the hub's tests need the applied numbers to be consecutive, so whichever merges second takes the next number.
  - **The log keeps `view`.** Entries already in the change log, and new ones, keep the id the device pushed. Every log read is limited to the reader's own user and devices, and devices expect `view`, so a new or reinstalled device that replays the log sees the same settings.
  - **A snapshot leaves out other users' rows.** A snapshot returns the reader's own settings row, as `view`, with its clocks, and no other `viewSettings` row, so two users of one organisation never see each other's settings.
  - **Rolling deploy.** Each hub runs two tasks, so for a moment after the migration an old task can still write a row named `view`. Devices still receive that change from the log, and no snapshot returns the row, but the hub's stored row for the user misses that one edit until the setting is next changed. With one user this is the owner not touching a setting for a minute.
  - **What is not done.** The follow-ups in D-208 other than the two above are untouched. No device code changed, so no Mac or phone build is needed. A hosted hub that holds a stray settings row (an id other than `view`) loses it in the migration; whether either hosted hub holds one was not looked at. The design left new cases for the shared fixture `Tests/Fixtures/sync/changes.json` (two users in one organisation, a refused id) to the builder; the fixture is a list of changes that both languages decode and has no place for an outcome, so those cases are hub tests and the fixture is unchanged. The migration must never run twice on one database: on a migrated hub it would delete every user's settings, so it is not renumbered once any database, a local Compose hub included, has applied it; if this merges before draft pull request 180, that branch takes the next number.
