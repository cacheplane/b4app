## 2026-11-01 (distribution)

- **D-051 The Mac app stays on Developer ID outside the Mac App Store; the iOS companion goes to TestFlight; Developer ID Mac builds keep secrets in the data-protection keychain in a group the app and the coordinator share.** Research: `docs/research/reports/App Store and TestFlight signing.md`. **Mac:** TestFlight for Mac and the Mac App Store both require App Sandbox on every executable (Guideline 2.4.5(i), ITMS-90296), and three core features cannot run in it: the user's own `codex`, `claude`, and `node` (a sandboxed process may execute only inside its allowlist, and children inherit the sandbox); the bundled PostgreSQL (its System V shared memory and semaphores are denied); and the LaunchAgent the app writes into `~/Library/LaunchAgents`, with the socket in `$TMPDIR`. So the Mac app ships notarized Developer ID builds only (D-039). **iOS:** `Scripts/upload-ios.sh` archives and exports with method `app-store-connect`, destination `upload`, automatic cloud-managed signing, and a Team App Store Connect API key with the Admin role (`B4APP_ASC_KEY_ID`, `B4APP_ASC_ISSUER_ID`, the `.p8` file outside the repository). Builds are internal-only unless `B4APP_TESTFLIGHT_EXTERNAL=1`, and the build number is the UTC time (`yymmddHHMM`). Both targets now read their versions from `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION`. The iOS bundle declares `ITSAppUsesNonExemptEncryption = NO` (HTTPS through URLSession only) and a local-network usage string, and carries `PrivacyInfo.xcprivacy`: no tracking, no data collected by the developer, and no required-reason API, which was checked in the iOS-linked modules. A post-build script removes the localhost ATS exception outside Debug, since on a device `localhost` is the phone. **Team id:** `Config/Signing.xcconfig` is committed with an empty `DEVELOPMENT_TEAM` and includes the gitignored `Config/Signing.local.xcconfig`. `project.yml` sets no team, and the scripts pass `DEVELOPMENT_TEAM` (the iOS script reads it from the Developer ID certificate or `B4APP_TEAM_ID`). CI keeps building with `CODE_SIGNING_ALLOWED=NO`, and iOS Simulator builds still sign to run locally. **Mac keychain:** this supersedes D-008 for Developer ID builds. TN3137 says data-protection access groups come only from entitlements a provisioning profile authorises, and a bare tool has nowhere to embed one, so the coordinator is now a background-only app bundle, `Contents/Helpers/B4AppCoordinator.app` (`com.cacheplane.b4app.coordinator`, `LSUIElement`). The LaunchAgent, the CLI's lookup, and the app run `B4AppCoordinator.app/Contents/MacOS/b4app-coordinator` directly, and the app rewrites an existing user agent plist that points at the old path. The owner registers the App IDs `com.cacheplane.b4app` and `com.cacheplane.b4app.coordinator` with Keychain Sharing and creates a Developer ID profile for each. `Scripts/package.sh` then checks each profile (App ID, team, the group, expiry) and embeds it as `Contents/embedded.provisionprofile`. It generates the entitlements from the certificate's team id: `com.apple.application-identifier`, `com.apple.developer.team-identifier`, and `keychain-access-groups` = `<team>.com.cacheplane.b4app.shared`. It signs inside out (PostgreSQL, the CLI with the identifier `com.cacheplane.b4app.agent-workspace`, the coordinator bundle, the app) and confirms both signatures claim the group. A notarized build must also pass `syspolicy_check distribution`. `KeychainSecretStore.forCurrentProcess()` reads the process's own `keychain-access-groups` (`SecTaskCopyValueForEntitlement`): a process that claims the shared group uses the data-protection keychain in it, and anything else (`swift build`, tests, ad hoc packages, or `B4APP_SKIP_PROFILES=1`) stays in the file-based login keychain, since it has no profile. A data-protection store moves an item it lacks out of the login keychain on first read (read, add, delete), so each old item can prompt once, because the coordinator's signature changed. Every query sets `kSecUseDataProtectionKeychain` explicitly, `false` for the login keychain: with no flag, a process that claims keychain entitlements reads the data-protection copy first and deletes from both, which lost the owner's hub token on the first live move (2026-11-01, `docs/verification.md`). `doctor` names the store in use. A probe on this Mac (2026-11-01) showed why the file-based keychain alone is no longer a reason to move: a Developer ID rebuild with a new code hash read an item without a prompt, where an ad hoc rebuild returned -25293. The data-protection keychain was chosen anyway because the owner wants the full provisioning flow, it is Apple's default for new code, and the file-based keychain is on its way to deprecation. **Expiry:** a Developer ID profile lasts 18 years, but an app whose profile has expired no longer launches, so `package.sh` refuses an expired profile and prints each expiry. Renewing the Developer ID certificate means regenerating both profiles before the next release.
