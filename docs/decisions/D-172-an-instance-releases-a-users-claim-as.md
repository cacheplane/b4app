## 2026-11-03 (a claim goes with the user's last link)

Found by the two-task live check on the test hub (`docs/verification.md`, "The test hub on two tasks, live"). Numbered D-172 after D-171.

- **D-172 An instance releases a user's claim as soon as it serves no link of theirs, not only while draining; amends D-085 ("a live owner keeps its claim") and D-165.** On a rolling deploy the load balancer cuts a deregistered task's links when `deregistration_delay` (5 s) ends, but ECS sent SIGTERM about 16 s later. In between the old task was alive and heartbeating, so it kept every user's claim. Every reconnect to a new task was refused `409 relocated`, and with the clients' backoff devices were offline 17 to 35 s. D-165's release never ran, since the links ended before shutdown began. Now every link's teardown calls `instances::release_if_unlinked`: once the user has no link here, their `user_links` row is deleted before the close is written. Nothing of the user is left to keep together: holds and watches belong to links, and the pending-thread map is only a hint.
  - **The race.** A link of the same user registering here while the claim goes would otherwise be served without one. So every link, right after it registers, claims again (`instances::reclaim`, the upgrade's `claim_user`): it restores the claim, or, if another instance took the user in that moment, closes the user's links here with 1001 and they reconnect to it. `release_if_unlinked` also claims again if a link registered while it was deleting. The heartbeat's `lost_claims` check remains the backstop.
  - **Cost.** One more query per link opened (the re-claim), and a claim per user per connection lifetime instead of per instance lifetime. A user whose only device reconnects lands on whichever instance the load balancer picks, and claims it there.
  - **Tests.** `instances.rs`: a user whose Mac's link ends while the phone's remains stays claimed; once the phone's ends too the claim goes, the other instance serves the Mac at once, and the first now refuses the phone `relocated`. It failed before the change. The instance and relay suites pass.
