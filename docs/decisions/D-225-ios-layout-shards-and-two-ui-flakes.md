## 2026-11-13 (CI: the layout tests run as two shards; two UI flakes)

- **D-225 The iOS navigation and banner regression tests run as two parallel shards of a reviewed plan, and the required check passes only when both did; a dragged palette ends where the pointer is released; the layout tests ask for portrait only when the device is not in it.** From the last 80 `ci.yml` runs (2026-11-12 to 2026-11-14): a green first-attempt run took a median 27.6 minutes from push (17 runs), set by the layout job at a median 23.2 (90th percentile 25.7, 70 passes), against 11.2 for the macOS smoke job, 9.4 for the package job and 9.2 for the app builds. Outside one work-in-progress branch, 8 of 37 runs failed; four of those were UI flakes, two of them on `main`.
  - **The shards.** `Tests/iOSLayout/UITests/shards.json` places the 13 journeys in two shards by their times in run 43530508002 (785 s of tests in all): four journeys and the component bundle (400 s), and the other nine (385 s). `ci.yml`'s `ios-layout` job is a matrix of the two (`B4APP_LAYOUT_SHARD`), 30 minutes each in place of 40 for one, with `fail-fast` off so each reports.
  - **What keeps the contract whole.** A shard takes its tests, its counts and the checkpoints it owes from the plan (`Scripts/ios_layout_shards.py`, `verify_ios_layout_results.py --shard`), never from the caller, and checks the whole plan first: each journey of `coverage.json` and the component bundle is in exactly one shard, and the shards together owe all 129 IDs, none twice. The last shard skips what the others name instead of naming its own, so a test placed in no shard runs there and fails the count. The focused-coverage and partial-count refusals under `CI` (D-187) are unchanged; a shard is not a focused run and cannot be combined with one.
  - **The required check.** Branch protection requires "iOS navigation and banner regression tests". A job of that name (`ios-layout-result`, on Linux) needs both shards, always runs, and fails unless the matrix's result is `success`: a cancelled or skipped shard fails it, where a skipped required job would count as a pass. No branch protection setting changes.
  - **Cost, and what is not measured.** Each shard builds the fixture app, about 6 of the job's 23 minutes in the one run split by phase, so a run uses one more macOS runner and roughly 7 more runner-minutes for an expected layout time near 14 minutes. One run in ten already waited 11 to 12 minutes for a macOS runner; a fifth concurrent macOS job can lengthen that when several pull requests run at once. This entry claims no speedup; the gate record holds the first hosted measurement.
  - **The palette's drag.** `PaletteSmokeTests.testPalettePanelDragsSnapsAndKeepsItsShadow` failed three times. In run 43534874181 the panel's own trace shows 15 drag events and a panel 12 pt and 10 pt short of a 180 by 130 pt drag: one step of the synthesized drag. `PalettePanel` moved only on drag events, and a busy machine drops the last of them, so the release came from a place no drag event had reported. It now follows the pointer on the release as well (`FloatingPanelTests.aDragEndsWhereThePointerIsReleased`). The test and its 6 pt tolerance are unchanged. The second failure (run 43494688236, 46 pt short on one axis) left no trace and is not explained; the third (43352285210) was on a branch before the drag was reworked.
  - **The portrait reset.** `BannerLayoutTests.launch` set the orientation to portrait before every launch. On `main` acef750 that call timed out waiting for a change to be confirmed and failed `testConnectionNoticeJourney`, which never leaves portrait (run 43534874181). It now asks only when the device reports another orientation. The landscape journey still sets both orientations itself.
  - **Not done: making the UI jobs wait for a compile check.** The work-in-progress branch used 2,287 of the sample's 4,176 macOS runner-minutes over 42 failed runs, but its `swift build` step never failed: its failures were in test targets and in the smoke fixture's start, which a compile check would not catch, and its layout job passed every time. Cancelling the other jobs when the package job fails would have saved about 14% of the sample's macOS minutes with the 23-minute layout job, and close to none with 14-minute shards, since that branch's package job failed a median 15.6 minutes in. Neither is worth a delay on every healthy pull request.
  - **Not verified locally.** The macOS smoke suite drives the owner's pointer, so it was not run on the owner's Mac; the palette fix is checked by the package test and by CI's smoke job.
