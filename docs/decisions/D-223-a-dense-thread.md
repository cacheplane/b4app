## 2026-11-13 (a dense thread)

- **D-223 A dense thread shows the message, one line for the work, and the answer (amends D-218).** Part 3 of the density design: when Dense is on, a thread's turns are drawn with their steps folded behind one line, on the Mac and the phone. Design: `docs/superpowers/specs/2026-11-12-density-and-user-settings-design.md`, Part 3 and its 2026-11-13 amendment; plan: `docs/superpowers/plans/2026-11-13-dense-thread.md`. The code is commits ff6e0d51 (what a dense thread draws), eadb24c8 (drawing it), 5130e177 and 1c33b3cd (the scroll), and 8072160f (the Display page on the phone).
  - **What dense draws.** For each turn: the user's message, one muted line, the turn's system items, the answer, and the turn's note ("Turn failed.", "Turn stopped.", the unknown-outcome notice) after it. A turn that has ended shows the line as `4 steps`, `1 step`, `4 steps, 1 failed`, `4 steps, 1 declined` or `4 steps, 1 failed, 1 declined`, then `Show`; opened it ends in `Hide`. Only "N failed" is in the danger colour; the rest is muted small type. A turn with reasoning or interim messages but no counted step reads `Show working` (`Hide working` opened), so nothing the agent wrote is out of reach; a turn with only its answer has no line. Opening a turn draws its steps, reasoning and interim messages in sequence order after the line, as normal density draws them, with no animation (`withAnimation(.none)`, as `CollapsibleCard`). Whether a turn is open is `@State` in the transcript (`TranscriptFolds`), reset when another thread is shown; it is not written to `LocalPreferences`, the store or the hub. A pending approval or question is drawn by `RuntimeRequestList`, outside the transcript, and is untouched; so is the phone's pending message.
  - **Normal density is unchanged.** The `dense == false` path keeps the existing body, order and scroll behaviour, and a test pins its height against the same content. Nothing is stored and nothing on the wire changed: every rule reads `DisplayItem` and `Turn` rows only (`Sources/WorkspaceUI/DenseTranscript.swift`), so the phone draws what the Mac draws, and there is no migration and no hub deploy.
  - **Why the research changed the plan.** The first version of the plan said "3 steps so far" while a turn ran and counted every tool-role item. Research into how other tools draw an agent's progress (the owner's b4run activity design and hashbrown, threadplane, and shipping coding agents) found that the designs that work name the running step and give a count only once the turn has settled, and that a bare count while running is what users of other tools complained about: it says nothing about what the agent is doing, and it ticks up with no way to tell stuck from busy. It also found that a command the user declined is the user's refusal, not the agent's failure, and that a plan or todo update is not an action. The report itself is not committed; calls 1 to 7 are its findings, and they replace the first plan.
  - **Call 1: a running turn's line names what the agent is doing and does not count.** The name is that of the turn's newest counted step whose status is `inProgress`: B4's `payload.label` when it has one, otherwise the title its card draws (`ToolCard.title` now calls `DenseTranscript.title(of:)`, so the card and the line cannot disagree), cut at 120 characters with an ellipsis. With no step in progress, or a name that is empty or blank, the line reads `Working`. A turn whose status is `waiting_for_user` reads `Waiting for you`; that covers an approval and a question. The count appears when the turn ends. Reason: the name answers "what is it doing" and the count does not.
  - **Call 2: messages fold when the turn ends, not while it runs.** While a turn runs every `agentMessage` is drawn after the line, in order. Once it has ended the answer is the turn's last `agentMessage` with no counted step after it, and the earlier messages fold with the steps. Reason: while the turn runs there is no way to know which message will be the last, and hiding a message the reader was just watching arrive is worse than showing it.
  - **Call 3: a counted step is a tool call, by type.** Role `tool` and type `commandExecution`, `fileChange`, `mcpToolCall`, `dynamicToolCall`, `webSearch`, `imageView`, `toolCall` or `toolUse`, with `payload.name` not `TodoWrite`. Every other tool-role item (B4's `plan_update` and its other named events, Codex's `enteredReviewMode` and `functionCallOutput`, a type the list does not know) is working: folded, shown when opened, not counted, and never part of the test for the answer, so a plan update after the answer does not hide it. Reason: the number should match what the agent did, and an allow-list fails safe, since a new item type is left out of the count until someone adds it. The types `dynamicToolCall`, `imageView` and `functionCallOutput` (Codex) and `TodoWrite` (Claude Code) are inferred from the adapters' code and not from a recorded run; a recorded run may show they belong on the other side of the list.
  - **Call 4: declined is not failed.** `failed` counts steps whose status is `failed`; `declined` counts those whose status is `declined` and is drawn muted. Reason: a declined command is the user's own refusal, and showing it in the danger colour tells the reader the agent failed when it did not.
  - **Call 5: a turn that is not running never shows a running step.** In a turn that has ended, and in a group read from history, a step still `inProgress` is drawn with its status as `stopped` (the card's badge is muted) and is counted as a step. Reason: a spinner-like "in progress" on a finished turn is false, and the app lost track of that step, not the reader. A turn whose outcome is unknown (`reconciling`) is not touched by this (call 8).
  - **Call 6: items with no turn are grouped at user messages.** A turnless `user` item starts a group of its own (key `h-<item id>`); any other turnless item joins the group of the item before it, whether that is a turn or a history group. A history group is drawn as an ended turn with no note. Turnless items before the first group are drawn as they are. Reason: a thread read from history is the one most likely to be long, and leaving it at normal density would make dense look broken exactly there. Items are stably sorted by `sequence` before they are grouped.
  - **Call 7: opening a turn holds the view until the reader goes back to the end.** From a toggle until the reader scrolls to the end, sends a message, or shows another thread, the transcript neither pins its bottom edge nor follows the stream. Reason: the transcript pins its bottom edge when its height changes, which would push the line the reader just pressed off the screen, and following the stream would move the opened steps out from under the reader. A toggle in a thread short enough to fit the window does not hold, since nothing could move.
  - **Call 8: a turn whose outcome is unknown (`reconciling`) is drawn as ended.** The count, no name, its steps left as they are. The unknown-outcome notice already says what happened, and the app cannot say whether a step is running.
  - **Call 9: order within a turn.** The user's message, the line, then the messages the closed turn shows, the turn's system items, then the turn's note. Opened, everything the turn holds besides its user and system items is drawn after the line in sequence order, so each message stands where the agent wrote it. Reason: a closed turn reads as a summary followed by its answer, and an opened one reads as the turn did.
  - **Call 10: a turn's items are gathered where its first item stands**, so a turn never has two lines, even when its items are not contiguous.
  - **Call 11: the Display page's description changes.** On the Mac it reads "Tighter rows for the threads that don’t need you, and answers without the steps in a thread."; on the phone, which now has the Display page, "Answers without the steps in a thread." (`DisplaySettingsView.denseDescription`; the phone's page list is `[.account, .display, .connections, .servers, .diagnostics]`, and the Dense switch there writes through `model.setDensity`). The composer is added to the description by part 4.
  - **Scroll.** Task 3 ended on the first mechanism tried: while a turn is held open, the transcript's size-change anchor is the top (`.defaultScrollAnchor(folds.holds ? .top : .bottom, for: .sizeChanges)`), and the `ScrollPosition` fallback was not needed. A scroll geometry observer releases the hold when the reader reaches the end (within 8 pt); it watches the content height as well as the flag so a toggle in a thread that still fits does not hold. Sending a message releases the hold, and the stream is followed again. A message sent into a running turn adds no turn and no pending message, so it does not release the hold. Showing another thread while held resets the hold and scrolls the new thread to its end, in the same handler so it does not depend on the order SwiftUI runs its change handlers. A turn ending while held leaves the view where it is. The tests host the real `TranscriptView` in a window and drive the `NSScrollView` AppKit makes for it.
  - **Test seam.** `TranscriptContent` has a `lazy` parameter, true in the app. Tests pass false and measure a plain stack, because a `LazyVStack` measured outside a scroll view estimates the rows it has not laid out (389 pt against 359 pt for the same rows open). The scroll tests use the lazy stack inside a real scroll view.
  - **Left out on purpose, each a follow-up.** Elapsed time and "Worked for 1m 12s" on the line; the failed step's name and reason under the closed line; a checklist drawing of plan and todo items; a short delay before the line appears, so a fast step does not flash; and anything that needs the adapters or the store (the turn's failure reason, step durations, sub-agent grouping).
  - **The composer.** Unchanged. Dense still leaves the composer's pickers in place; part 4 removes them once the command palette's commands can change the place, the permission and the model.
  - **Not checked.** A real running turn in the app, which the spec names as the part most likely to need a look: the line naming each step, interim messages folding at the end, opening a turn while another streams. A thread read from history on each runtime. Scrolling in the running app, trackpad momentum and the elastic bounce at the end, and the phone's `UIScrollView`, since the anchor was measured only on macOS. VoiceOver on the line. The phone on a device. The phone-only assertions (the Display page's second place and its description) are in `#else` branches that `swift test` does not run; the iOS build and the iOS layout run cover them. One thing seen in the hosted test window needs a look in the real app: after the transcript had followed a stream, scrolling to the very end by hand stopped the document growing as the reply grew, and a later scroll up only partly restored it. It happened at the commit before this change too, at both densities, so it is not caused by the hold; it may come from the offscreen window or be a real SwiftUI and AppKit fault.
