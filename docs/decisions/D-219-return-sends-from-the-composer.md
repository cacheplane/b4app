## 2026-11-12 (composer keys)

- **D-219 Return sends from the Mac's composer and never adds a line; Shift-, Option- and Control-Return add one; the editor is an `NSTextView` that stops at three lines and scrolls inside (amends D-061).** At the owner's direction ("send on enter, and use shift+enter as a newline. I think this is most common for AI chat. Do deep research"; and the field, grown to its three lines, let further Returns spill out of it). The research is `docs/research/2026-11-12-composer-enter-key-conventions.md`; what it found and what this takes from it is below.
  - **The convention.** Every desktop AI chat app and coding agent checked (ChatGPT, Claude, Gemini, Perplexity, Cursor, Zed, Copilot Chat) and the messaging apps (Slack, Teams, Discord, WhatsApp, Telegram) send on Return and add a line with Shift-Return; Apple's Messages documents Option-Return too. Where a product lets Return add lines instead (Slack, Teams, Linear, the ChatGPT desktop app, Cursor, Claude Code's VS Code extension), the swap is opt-in and Command-Return sends. Users asked OpenAI and Anthropic for keys whose meaning does not change with the draft. On the phone the on-screen Return adds a line and a button sends (Messages, ChatGPT); with a hardware keyboard on an iPad, Messages sends on Return.
  - **The Mac's keys.** Return and the keypad's Enter send; Command-Return sends too; Shift-Return, Option-Return and Control-Return add a line (a plain line feed: Control-Return's `insertLineBreak:` would otherwise insert U+2028). Return means the same whatever the thread is doing: with an empty draft, while a turn runs, or while the thread cannot send, it does nothing rather than adding a line. That last case was the bug: the Send button held Return through `.keyboardShortcut(.return, modifiers: [])`, so whenever Send was off (an empty draft, or Stop in its place) Return fell through to `TextEditor` and added blank lines. No setting swaps the keys; Command-Return already sends, so one could be added without changing it.
  - **Input methods.** Return that commits a Japanese, Chinese or Korean candidate must not send; Claude, Cursor and ChatGPT have all shipped that bug. The decision is made in the text view's `textView(_:doCommandBy:)`, which runs only after the input method has had the key, and nothing is sent while `hasMarkedText()` holds. A button's keyboard shortcut takes the key before the input method, which is why the Mac's Send button no longer has one. Return and Shift-Return reach the handler as the same `insertNewline:`, so Shift is read from the key event the text view is handling (kept by its `keyDown`, not `NSApp.currentEvent`). `ComposerKey.action` is the rule, free of AppKit, and tested on its own.
  - **The editor.** `ComposerTextView` (`NSViewRepresentable`) is an `NSTextView` in an overlay-scrolling `NSScrollView`. It reports its own height from `sizeThatFits`, measured with a separate TextKit 1 stack at the proposed width (the text view uses TextKit 1 too, so the measured height is the drawn one): one line to three. The clamped frame is the scroll view's, inside the field's background, so text past the third line scrolls within the field; the caret is scrolled into view after each edit and whenever the height changes. Hanken Grotesk 15, ink text, accent caret, no inner inset or line-fragment padding, so typed text sits exactly where the placeholder does (checked in the rendered `composerEmpty` and `composerOneLine`). Undo, plain text only. The three-line cap stays; production composers go to four lines or more, which the owner can raise later.
  - **The phone.** Unchanged: its vertical `TextField` keeps the on-screen Return as a new line and the round button sends, as Messages does. Its Send button keeps the Return shortcut (`returnSends()`), for a hardware keyboard; whether that fires over the text field on an iPad, and whether an input method's Return reaches it, is unverified. The research found reports that SwiftUI's vertical field can ignore its line limit on iOS 26; the phone was not checked for the overflow here.
