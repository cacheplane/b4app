## 2026-11-19 (a turn after its request is answered)

- **D-257 Answering a turn's last pending request puts the turn back to running at once, without waiting for the runtime to say so.** A turn becomes `waiting_for_user` when a runtime request opens. It went back to `running` only on an adapter event: a `turn.state_changed` from the runtime, or a request the runtime itself resolved. `requestRespond` resolved the request and left the turn as it was. On screen in the Local build from main (99bf5ec5), a Claude Code thread's header and composer row said "Waiting for you" for several seconds after "Allow once". A live probe of Claude Code 2.1.282, launched with the adapter's environment, shows why: between the answer and the tool's result it sent nothing about the session's state (the answer at 5.4 s, the next frame at 9.5 s, the result at 12.6 s for a 6 s command), so the turn stayed waiting for as long as the allowed tool ran.
  - **The rule.** After `requestRespond` resolves a request, if its turn is `waiting_for_user` and the thread has no other pending request, the coordinator sets the turn to `running` and publishes `turn.state_changed` with the turn and `source: "answer"`. A turn with another request still pending stays waiting. The adapter paths are unchanged: a runtime that reports its own state (Codex's thread status) says the same thing a moment later.
  - **What it does not do.** A decline is an answer too: the turn runs until the runtime ends it. Nothing changes for a request that expires or that the runtime resolves.
  - **The fake.** `fake-claude.py` sent `session_state_changed: running` after every answer, which the live runtime did not; a message containing "quiet" now makes it say nothing for two seconds, as live.
  - **Tests.** `ClaudeSessionServiceTests.anAnsweredTurnIsRunningBeforeTheRuntimeSaysSo` (the turn read back as running as soon as the answer returns, and the event with the turn); it failed before the change with the turn still `waiting_for_user`.
