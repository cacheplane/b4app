## 2026-11-01 (coordinator robustness)

- **D-052 A blocking Keychain call never runs on an actor, the hub token is read once per run, and a running cluster is adopted only from this install.** The package builds with `NonisolatedNonsendingByDefault`, so `KeychainSecretStore`'s async methods ran on their caller's actor; a token read that raised a Keychain prompt (any rebuild whose signature the item's ACL does not name) held `HubSync` until someone answered, and every `hub.status` timed out behind it. Each `SecItem*` call now runs on a thread of its own (`KeychainCall`). `HubSync` keeps the device token in memory once read (`HubToken`): concurrent requests share one read, a join keeps the token it just stored, a miss or a failure is not kept, and while a read is outstanding `hub status` reports "Waiting since … for Keychain access to the hub token; answer the Keychain prompt on this Mac." in `lastError` without storing it. The token is held only by the coordinator process, never written anywhere else. `PostgresServer.start` used to adopt any postmaster serving its data directory; after a bundle swap that was the old install's server, which could not load the new install's `plpgsql` under the hardened runtime, and migration 0004 failed until the server was stopped by hand. A running cluster is now adopted only when its postmaster runs this install's `postgres` (the same file by its current path from `proc_pidpath`, so a moved bundle does not match) and started after that file was last written (so a bundle rebuilt in place does not match); otherwise it is stopped through the existing identity check (D-025) and this install's server started. Cost: one extra fast restart of the cluster after every app update, a few seconds.
