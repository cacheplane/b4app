## 2026-11-02 (step-up by enrollment code, and two live-check fixes)

Found while cleaning up after the sign-in polish live checks (`docs/verification.md`, "Sign-in polish, live").

- **D-151 An operator's enrollment code confirms it's you, for an account that can no longer assert.** Adds to D-150. At the live checks a test account's only passkey was deleted from the keychain before the account was: every change (and deleting the account) then needed a passkey assertion nobody could make, so the account could not be removed except by hand in the hub's database. The owner chose a code over an operator delete command, so the person can finish the change in the app.
  - **The hub.** `POST /v1/me/step-up/code` with `{"code"}`, behind the device token and counted with the sign-in finishes, takes once an enrollment code the operator minted (`b4hub enroll --user <name>`) for the caller's own org and user, compared as `POST /v1/enroll` compares codes, and answers the same two-minute, single-use, device-bound grant as the other step-ups, recorded as `code` (migration `0015_step_up_code.sql` widens the check; 0014 is not edited). `devices::take_operator_code` is one conditional `UPDATE`.
  - **Only an operator's code.** A pairing code (`created_by_device_id` set, minted by a Mac through `POST /v1/pairing-codes`) never counts: a stolen Mac token could otherwise mint one and step itself up, which is what D-150 exists to stop. An unknown, expired, used, pairing, or another user's code is `401 invalid_code`, indistinguishably, and changes nothing; another user's code and a pairing code stay redeemable. `details.methods` of `step_up_required` never names `code`: it is not a sign-in method, and a client may always offer it.
  - **The clients.** `AccountStepUp.enrollmentCode` crosses into the coordinator (or `MirrorAccount` on the phone) inside the change's own command, as the other confirmations do; the coordinator spends it at the hub (`HubAPI.stepUpCode`) and makes the change with the grant. A new `ErrorCode.invalidCode` carries the refusal (it fell to `auth_required` before, which reads as "sign in again"). Settings → Account: when the passkey or Apple confirmation of a change is closed or cannot open, the page remembers that change (`StepUpChange`, never the code) and offers "Can't confirm it's you here? Enter an enrollment code from your hub's operator."; Confirm runs the same change with the code, a refused code is one line and keeps the offer, Cancel ends it. Delete account offers it in its own sheet, which stays open. The typed code is cleared as it is sent, and appears in no description, log, or error.
