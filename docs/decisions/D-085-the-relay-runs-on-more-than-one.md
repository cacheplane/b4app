## 2026-11-02 (M8e Part B)

Design `docs/superpowers/specs/2026-11-02-m8e-part-b-relay-routing-design.md`, reviewed by the M8c build session; built on `blove/m8e-relay-multi-instance`. Numbered D-085 and D-086 because the open sign-in pull request claims D-081 to D-084; re-checked at merge.

- **D-085 The relay runs on more than one hub instance by serving every link of one user on one instance, never by forwarding frames between instances; amends D-057 ("One replica").** Hub: `Hub/crates/b4hub-db/src/instances.rs` (migration `0008_instances.sql`), `Hub/crates/b4hub/src/instances.rs`, `relay/link.rs`; clients: `Sources/WorkspaceSync/RelayLink.swift`; reference `Hub/API.md` "More than one instance".
  - **Claim.** Each `serve` registers a UUIDv7 in `hub_instances` and writes a heartbeat every `B4HUB_HEARTBEAT_MS` (default 5000); four heartbeats (20 s) without one is dead. `user_links` names the instance serving a user. The link upgrade claims the user after the revocation check and before the socket exists, with one upsert that keeps a live owner's claim and takes over a dead one's; another live owner means `409 relocated` (`details.instanceId`), no socket, no `hello`, nothing in presence or `watching`. The liveness window is a parameter (four heartbeats) rather than the design's literal 20 s, so the fixture tests run with a 200 ms heartbeat; every instance of one hub must run the same cadence.
  - **Cookie, amended from the design.** Every instance sets `Set-Cookie: b4hub-instance=<its id>` on `/readyz` and on an accepted upgrade, and the ALB's application-cookie stickiness (`b4hub-instance`, one hour, on only when `task_count > 1`) takes it from there. AWS documents that the ALB answers an application cookie with its own `AWSALBAPP-*` cookie encoding the target that sent it, routes only a request carrying both, and does not route by the application cookie's value. So the design's `Set-Cookie: b4hub-instance=<owner>` on the `409` would bind the device to the instance that refused it, and a `Cookie: b4hub-instance=<owner>` alone reaches nobody in particular. The `409` therefore carries no cookie; the device keeps the cookies of its last successful upgrade (both of them, behind an ALB), replays them, drops them on a `409`, and retries at once up to three times (landing by round robin), then backs off. Once it reaches the owner, the owner's `101` gives it cookies that make later reconnects sticky. The device does not read `instanceId` (`URLSessionWebSocketTask` does not expose a refused upgrade's body, and a device cannot address an instance).
  - **Drain.** On SIGTERM the instance answers every held command `device_offline` first (up to 1 s, a quarter of the wait at most), then closes its links, each writing what is queued before its 1001, and after the drain deletes its claims and its instance row so its users are claimed at once elsewhere; the whole sequence, release included, stays within `B4HUB_SHUTDOWN_WAIT_MS`. The design listed "close links" before "answer holds"; answers queued after a link closed would be lost, so the order is reversed.
  - **Rolling deploys on ECS.** The ALB deregisters an old task and waits `deregistration_delay` before ECS sends SIGTERM; meanwhile the task still heartbeats and holds its claims but gets no new connections, so a user re-linking then reaches a new task and is refused `409 relocated` with nowhere to go, and at the end of a long delay the ALB may cut the old task's WebSockets before the hub's drain runs. With `task_count > 1` the delay is therefore 5 s (60 s with one task): the real sequence is deregister, 5 s, SIGTERM, holds answered, links closed 1001, claims released, and the new task claims each user on relink. A device that re-links inside the 5 s spends its three immediate retries and backs off past the window.
  - **Split guard.** An instance whose heartbeat failed for the window may have lost users to another instance while their links stayed open here; when its heartbeat succeeds again it closes (1001) the links of every user whose claim another instance holds, so a user's links are split for at most one heartbeat after recovery.
  - **Maintenance (D-074).** While on, a client's `turn.send`, `thread.start`, and `request.respond` over the link get a `maintenance` reply with the HTTP guard's message and are not forwarded; `turn.lookup`, `turn.interrupt`, and `watch` continue.
  - **Why.** Forwarding frames would need an internal transport for 256 KiB frames and high-rate deltas and would split the in-flight map; routing by user leaves `route.rs` as it was and buys what the "next" tier needs: rolling deploys with no outage and zone redundancy. Accepted edges: per-instance rate limits, in-flight state, holds lost on a crash, and the pending-thread map (a takeover between a phone's `thread.start` and the thread row's sync answers `not_found` for seconds). A refused (`409`) upgrade still counts against the per-device upgrade limit of the instance that refused it (10 a minute): fine with two tasks, where a device rarely misses more than a few times, tighter with three or more. Outside ECS (Helm, Compose) failing readiness does not close WebSockets, so an instance whose heartbeat is stale but which is still running keeps its links until its heartbeat recovers and the split guard closes the ones it lost; only on ECS does a failed health check replace the task.
