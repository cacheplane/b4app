## 2026-11-03 (decision and verification records, one file each)

Numbered D-174: main's highest is D-172 and cacheplane/b4app#106 holds D-173. The owner chose the layout; the calls below refine it.

- **D-174 Each decision and each gate record is its own file, and the newest-first indexes are generated, never committed.** On 2026-11-02 and 2026-11-03 about seventy pull requests from parallel sessions landed, and nearly every one conflicted with the others in `docs/decisions.md` and `docs/verification.md`, where each prepended its entry; decision numbers collided at least six times (D-051/052, D-087, D-088, D-090, D-131, D-151) because every branch took "the next free number" when it started. Now a decision is `docs/decisions/D-NNN-<slug>.md`: its first line is the dated topic heading it used to sit under (`## YYYY-MM-DD (topic)`), then the entry's text as it was, one `- **D-NNN ...**` bullet with its nested lines. A gate record is `docs/verification/YYYY-MM-DD-<slug>.md`, its first line `## YYYY-MM-DD: <title>`. Two pull requests that each add a file never conflict. The 162 decisions and 70 records were split mechanically (`Scripts/split-docs.py`, run once and removed in the same pull request), and the script proved that every non-blank line of each section comes back, in order, from the files written for it. Prose a section had before its first decision went into that decision's file, and prose that followed a decision stayed with it, so D-068's file carries the hosted-hub section's design note and D-072's the implementation notes that followed it.
  - **The indexes.** `Scripts/docs-index.sh` writes `docs/decisions/index.md` and `docs/verification/index.md`, one line per entry, newest first (decisions by number, records by file name), and both are gitignored. A committed index would conflict exactly as the logs did: two branches that each add a line at the top (or the bottom) of one list edit the same hunk, and GitHub's merge honours no `.gitattributes` merge driver, so no committed form of a single list is conflict-free. On GitHub the directory listing, sorted by name, is the index; the generated one is for reading locally. `docs/decisions.md` and `docs/verification.md` stay as short pages describing the layout, so every link to them still lands, and `--check` fails if an entry is added to either.
  - **Numbering.** A branch takes its number when it opens its pull request, from `Scripts/docs-index.sh --next`, which prints the first number after the highest on `origin/main`, in the tree, and in open pull requests' `docs/decisions/` files (through `gh`, when it is signed in); if main takes the number before the branch merges, the branch renames its file. `--check` fails on a number two files share, a number `origin/main` holds under another file name, a malformed name or first line, an entry in the old logs, or a committed index; CI's "Workflow and shell lint" job runs it after fetching `origin/main`. Main's required checks do not include that job, and they are not strict, so two open pull requests with the same number can still both land; main's check is then red and the second to merge renumbers, which is one rename. Nothing on main is ever renumbered.
  - **Amendments** stay in the later decision's file ("amends D-NNN"), as before; an earlier decision's file is not edited.
  - **Left as they were.** The plans, specs, and research notes under `docs/superpowers/` and `docs/research/` still say `docs/decisions.md` and `docs/verification.md`, as they did when they were written; they are records of their time. The live documents (`AGENTS.md`, `README.md`, `Infra/README.md`, `docs/milestones.md`, `docs/compatibility.md`, `docs/deployment-architecture.md`, and the comment in migration `0007_apple_handoffs.sql`) point at the directories or at the file they meant.
