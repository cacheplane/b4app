## 2026-11-14 (declined on Claude Code and B4; a dot before Show)

- **D-226 A tool call the app refused reads "declined" on Claude Code and B4, and the dense line has a dot before its action word (amends D-223).** D-223's call 4 left a follow-up: only Codex stored `declined`, so on the other two runtimes the user's own refusal was counted as "1 failed", in the danger colour. Both adapters now mark the call they refused. The code is commits 8e2b4061 (the adapters), 55e98aa8 (the dot) and 141cd8a9 (the detail column's rule).
  - **Claude Code.** `ClaudeAdapter.respond` knows the tool use a `can_use_tool` request is about. When the answer is "Deny" or a decline (an `AskUserQuestion` that was declined too), it tells the session's `ClaudeTurnTracker` (`markDeclined(toolUseId:)`) before it sends the answer, since the result can arrive while the send is suspended, and takes the mark back if the send throws. The tracker gives that tool use's result the status `declined` in place of `failed`; `output` and `isError` are as Claude Code sent them. An error result for any other tool use is still `failed`.
  - **B4.** A B4 prompt names its `toolCallId`; `B4Adapter` keeps it with the pending prompt. A resume that denies (`deny`, or `cancelled` from a decline or from Stop on a parked turn, which B4 itself treats as a denial) calls `B4TurnTranslator.declineCall`. A call the stream has already shown is closed as `declined` at once, because B4 need not send a result for a call it did not run and the step would otherwise stay "in progress" until the turn ended; a result that does arrive for it is `declined` too. A prompt with no `toolCallId` changes nothing.
  - **Why the adapter and not the text.** The refusal is the app's own act, so the adapter knows it without reading the result. Matching the result's words ("User declined", "Permission denied") would break when a runtime rewords them, and would call a tool's own permission error a refusal.
  - **What is not covered.** A refusal the runtime made by itself (Claude Code's own deny rules or permission mode, a B4 route's policy) is still `failed`: the app did not refuse it and cannot tell it from another error. An item that comes from a snapshot of the runtime's history, not from the live stream, is `failed` (Claude Code) or `completed` (B4) as before; a live row keeps its payload through a later snapshot merge (D-031), so a refusal made on this Mac stays `declined`. A request the app declined automatically because it cannot present it is not a tool permission and is unchanged.
  - **The dot.** A running turn's line was the step's name, a space, and `Show` in the same muted type, so "swift test --filter SyncTests Show" read as one command. The line now draws a muted `·` between its words and the action word, running or ended ("3 steps, 1 failed, 1 declined · Show"). A line that is only "Show working" has no dot, and at accessibility sizes the action word is on its own line and needs none. VoiceOver's label is unchanged.
  - **The detail column's rule.** D-224 wrote the tests for "the new-thread screen is showing" twice, in `ThreadsView` and in `WorkspaceModel.newThreadViewIsShowing`, held together by comments. `WorkspaceModel.detailPane` (`environment`, `thread`, `opening`, `noConnection`, `newThread`) is now the one rule: `ThreadsView` draws it and "Choose folder…" asks it. `ComposerSummary.runtime` is nil with no connection, in place of comparing its text to "No runtime". No behaviour changes.
  - **Verification.** `ClaudeEventsTests`, `ClaudeSessionTests` (the fake Claude Code's denied tool), `B4TranslatorTests`, `B4AdapterSessionTests` (the fake B4 sends the prompt's tool call before the park when the message says "shown"), `PaletteTests` (a thread still opening). Neither runtime was run live: that Claude Code and B4 send on a denial what the fakes send (an error result for the refused tool use; the prompt's `toolCallId`) is taken from the fakes and was not checked against either.
