## 2026-11-01 (M8b)

- **D-049 Concurrent edits merge by hybrid logical clock, column by column, and the phone may write a short list of columns that the hub and the Mac both enforce.** A clock is `<12 lowercase hex digits of epoch milliseconds>-<4 hex digits of counter>-<device id>`, compared as plain strings (SQL compares them `COLLATE "C"` so no locale can reorder them). The Mac's `WorkspaceDatabase.write` takes the next value from a coordinator-wide `HybridClock` and sets it as `b4app.hlc` beside `b4app.device_id`; the change-log trigger stores it in the new `changes.hlc`, so every change in one transaction shares one clock, and falls back to `<wall>-0000-<device>` when none is set. The phone's `MirrorStore` stamps its outbox from its own clock. Every store advances its clock past each clock it receives, and clamps a received clock more than 300,000 ms ahead of its own wall clock to its own milliseconds with counter `0000` and the original device id, so a fast clock cannot win every later conflict; the clamped value is what is stored and served. **Merged columns:** `threads.title`, `pinned`, `archived`, `readTurnId`, `projects.name`, and `drafts.threadId`, `text`, `updatedAt` (the phone-writable list), plus `threads.projectId`, which only the Mac writes but rewrites when folders move. Each store keeps the clock of each such column (`columnClocks` locally and in the mirror, `column_clocks` on the hub); an incoming change to one applies only if its clock is greater, an `insert` counts as one write per such column it carries, and the Mac's own trigger keeps `columnClocks` current so a later pull of an older edit cannot overwrite a newer local one. Everything else applies as in M8a. The list is data in `b4hub-core` (`writable.rs`) and in `WorkspaceProtocol` (`SyncColumns`), kept equal by tests that read the trigger's SQL arrays back and compare hand-written lists, not by a shared fixture. **The write rule is by platform, not by row owner:** a `macos` device may write any column; an `ios` or `cli` device may `update` only the phone-writable columns, `insert` rows of `drafts`, and never `delete`, so a Mac that rejoins and re-uploads every row as inserts is not refused on its own rows. A draft is cleared by setting `text` to `''`, never by deleting the row (`SessionService` calls `clearDraft`, which keeps the row; the row goes with its thread), which makes clearing an ordinary last-writer-wins write. **Ownership:** a row's owner is the device of its latest `insert` (`owner_device_id` on the hub, `ownerDeviceId` in the mirror, `ownerDeviceName` on the thread for the header); an `update` never changes it, so `hub leave` then `hub join` makes the rejoined Mac the owner again with no rewrite, and M8c will route relayed commands with it. **A refused change never stalls the queue.** The hub applies a push change by change and answers `rejected: [{deviceSeq, code}]` with `column_not_writable`, `payload_too_large` (a `value` over 2 MiB, which M8a answered with a 413 that blocked the Mac's queue for good; the 413 now remains only for a body over 32 MiB), or `invalid_clock` (an `hlc` present but malformed; a change with none is stamped from its `wall`); `acceptedThrough` still covers every refused change and the client must not resend it. A refused change is not appended to the log and not applied; a change that loses the clock comparison is appended (the log is history) but writes nothing. `HubSync` marks rejected changes synced and records their count in `lastError` without suspending, and the phone does the same and persists the refused-upload count in `syncState`. The wire gains `hlc` on `Change` and `StoredChange` (a client without it keeps working, and the minimum client protocol stays 1). **The coordinator pulls.** `HubPull` long-polls beside the push loop and applies other devices' changes through `WorkspaceDatabase.applyRemote`, which runs with `b4app.replaying` on (nothing is re-recorded or echoed) and is a narrow merge, never a row copy: the hub holds only filtered copies of the Mac's rows, so it applies only `update`s of `threads.title`, `pinned`, `archived`, `readTurnId` and `projects.name` on rows that exist locally and inserts or updates of `drafts` rows whose thread exists, in each case by clock. It skips everything else, including every Mac-only column and every change from a `macos` device (the Mac's own rows coming back after a rejoin, a snapshot's blanked values, a pull from zero). It applies nothing until its first successful `devices()` call and counts revoked `macos` devices as Macs, so a rejoined Mac cannot re-apply its own old rows. A change whose parent row is missing is skipped under its own savepoint (`replay` gets the same savepoint, because it threw on a foreign-key violation despite its comment), only data errors (SQLSTATE class 22 and 23) are swallowed per change, any other error fails the batch, and the rows being merged are locked before their clocks are read so an older pulled value cannot overwrite a concurrent newer local edit. **Local writes and pulled batches are ordered by one transaction-scoped advisory lock:** every `WorkspaceDatabase.write` takes it shared as its first statement, before it sets `b4app.hlc`, and `applyRemote` takes it exclusive first, so a local edit that starts while a batch is in flight waits for the batch to commit and is stamped after every clock it applied (it wins, and the Mac and the hub hold the same clock), and a pull never holds a row lock a local write waits on, so the two cannot deadlock; the `FOR UPDATE` row locks stay, never wait now, and double as the existence checks. **The phone's mirror** applies a write at once and appends it to an `outbox` (`deviceSeq`, `hlc`, table, row, column, value); `MirrorSync` pushes the outbox before every pull, in requests of at most 500 rows and 8 MiB of encoded changes but always at least one (the rule of the Mac's `HubSync.batch`; a backlog over the hub's 32 MiB body limit would otherwise be refused with 413 on every retry, and the push precedes the pull), and removes rows only through `acceptedThrough`. A new local update of a column that already has an update queued and never handed to a push replaces that row's value and clock and keeps its `deviceSeq`, so offline typing queues one row per column; rows handed to a push this session, and every row present when the file was opened, are never touched, since the hub may hold them and would ignore a resend as a repeat. Mirror schema v2 (migrations keyed by `user_version`) adds `projects`, `projectFolders`, `devices`, `outbox`, `columnClocks`, `ownerDeviceId`, `threads.projectId`, and `threads.readTurnId`. A file newer than the app knows, or one whose migration fails, is rebuilt only if its outbox is empty (a failing migration with unsent edits keeps the file and reports the error instead), and **a rebuild carries the hub link and the outbox's `deviceSeq` high-water mark together or neither**: a link restored without its counter would reuse sequence numbers the hub already holds, which count as accepted and silently lose the edits. As a second guard, before its first real push the phone sends an empty batch and raises its sequence to the `acceptedThrough` the hub answers, which for an empty batch is the highest `deviceSeq` the hub has recorded for that device. Archive version 3 (`db backup`) adds the new tables; local migration `0004_organisation.sql` adds `projects`, `projectFolders`, `threads.projectId` and `readTurnId` (backfilled, see D-048), `changes.hlc` (backfilled from `wall`), `columnClocks`, an index on `runtimeRequests("threadId", "state")`, and the new triggers. Known limitations, none of them data loss in the common case: **rows written before the migration have no column clocks (the backfilled read markers aside), and a missing clock counts as oldest, so the first clocked edit after the migration wins whatever its time**; every local write waits while a pull batch is applied (one batch is at most a page of 1000 changes); the phone collapses only edits made since its last push attempt, so a phone retrying offline still queues one row per column per attempt; a clamped clock is stored by the receiver, and a receiver whose own clock is more than five minutes behind the sender clamps legitimate clocks to its own time, so clamping on receipt is not idempotent and two stores can hold different clocks for the same change; two concurrent local write transactions can leave `columnClocks` ahead of the stored value (the coordinator is the single writer); a change refused by the hub (a phone edit to a Mac-only column, an oversized value) stays applied on the phone until a snapshot or a newer write replaces it, and the count shows only in Diagnostics; a repeatable non-data error in `applyRemote` stalls the pull with backoff, a permanent push error also blocks pulling (no read-only fallback), and a successful push clears a "Pull: …" `lastError`; a second Mac's first edits can apply as a phone's for up to a minute, until `devices()` refreshes (one Mac per user is assumed); and the phone refuses `project.create`, `update`, and `delete` with `unsupportedCapability` naming "the Mac". Amends the phone-writes sentence of D-046 and the push-limit sentence of D-043.
