## 2026-11-15 (the transcript lays out every row it draws)

- **D-237 The transcript is a plain stack over the latest 150 rows of a thread, with "Show earlier" above them; it is no longer a lazy stack (amends D-223, D-087).** Running the app for the hill climb's record found that a thread whose first reply is several windows tall (120 lines) opened partway up that reply, with the messages after it never laid out and the scroller reading "at the end" (that record's defect 18, on `main` before D-233). The cause was the `LazyVStack`: it sizes rows it has not laid out by estimate, and with the bottom edge pinned on size changes (D-087) it kept the estimate after measuring the tall row, so the row ran past the content's end. The same thing made `TranscriptScrollTests.aShortThreadStillFollowsItsStream` fail on `main` whenever it ran first, by itself: the content's height fell back to 382 pt while about 1,900 pt was drawn, and the view stopped following the stream. It passed only after other tests had run.
  - **What was tried and dropped.** Scrolling to the end marker when a thread is shown left the view on blank space past the content. Dropping the size-change anchor and following from the scroll geometry opened the tall thread at its end once and 60 pt short of it the next time. Pinning the bottom edge only after the thread's first frames passed in the app and moved the collapse to the first streamed change. Each of these depends on when the lazy stack corrects an estimate, which nothing reports.
  - **The stack.** `TranscriptContent` is a `VStack`: every row it draws is laid out, so the content's height is the rows' height. The scroll rules of D-087, D-223 and D-233 are unchanged and their tests pass unchanged; `TranscriptContent`'s `lazy` switch, which existed so a test could measure it, is gone.
  - **The window.** Laying out every row of a long thread is slow: a debug build took about 160 ms for 100 rows, 510 ms for 300, 1.1 s for 600, 2.5 s for 1,200 and 6.1 s for 2,400 (rows of messages with a fenced block and command cards, three samples each, 720 pt wide; not a release build and not a device). `DenseTranscript.window` gives the last `page` (150) rows of the projection, begun at a user's message when one stands within 30 rows before the cut. `TranscriptFolds.shown` counts the rows drawn and is forgotten with the view, as the open turns are. 150 was not measured by itself; it lies between the 100 and 300 samples.
  - **Show earlier.** When rows are left out, a link at the top reads "Show earlier" (spoken with the number left out). It draws a page more, holds the view as a reader scrolling back does (D-233), and keeps the row that stood first at the top of the view. Another thread, or a change of density, goes back to one page.
  - **What it costs.** A reader cannot scroll from the end of a long thread to its start without pressing "Show earlier" once per 150 rows, and a streamed token re-evaluates up to 150 rows' views where the lazy stack evaluated the ones on screen. Dense draws about three rows a turn, so its page is about fifty turns; normal density's is 150 items.
