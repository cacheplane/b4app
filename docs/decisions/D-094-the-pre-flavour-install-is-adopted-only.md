## 2026-11-02 (sign-in build)

Built from `docs/superpowers/specs/2026-11-01-sign-in-design.md` and `docs/superpowers/plans/2026-11-01-sign-in.md` on `blove/sign-in`. These record what the build chose where the design (D-062 to D-067) was silent or was changed by review; D-062 to D-067 carry "Amended by" notes, and the hub's Sign in with Apple decisions are D-090 to D-093. The live gate passed on 2026-11-02 (`docs/verification.md`).

- **D-094 The pre-flavour install is adopted only by an explicit local flavour, inside `Coordinator.start` under the singleton lock; open the app before the CLI.** `Sources/Coordinator/Accounts/LegacyAdoption.swift`. A coordinator whose flavour is `local` by the environment or its bundle (never by default, so a `swift build` coordinator the CLI spawns never adopts), with neither `B4APP_DATA_DIR` nor `B4APP_POSTGRES_SOCKET_DIR` set, moves `b4app` to `b4app-local` after it takes the lock and before it creates its data directory, when `b4app`'s hub link is loopback and `b4app-local` holds no cluster. The old LaunchAgent is booted out and its cluster stopped through the identity checks first (refused, by D-052's rule, when the old plist is missing or names this binary). A `b4app-local` of empty directories and files is removed; one holding anything else is set aside as `b4app-local.aside-<time>-<id>`, never deleted, and put back if the move fails; a failed adoption fails the start. The packaged CLI's launcher always sets `B4APP_DATA_DIR`, so a coordinator it spawns never adopts, and if it runs before the app it creates a cluster in `b4app-local` that blocks adoption for good (the data stays in `b4app`, to be moved by hand). Hence the upgrade step: open the app first. D-063's one read of the prod keychain group is a copy, not a move (`LegacyAdoption.copySecretsOnce`, Task X2): before the first hub call of the account whose database is the adopted `workspace` (adopted from its link, or restored), `AccountManager` copies every secret that database references, its hub link's token and each connection's `secret:` `authReference`, from `<team>.com.cacheplane.b4app.shared` into the local group, only where the local group lacks it, and checks each copy reads back. The prod item is left in place, so going back to the prod build keeps working; a missing prod item is not an error. The setting `legacySecretsCopiedAt` in that database (local, never synced) records that it ran, so no later start reads the prod group again; a failed copy is logged and records nothing, so the next start tries again, and the account is restored all the same. The prod-group store reaches the coordinator only through the plan `planIfExplicitLocal` returns (`Plan.legacySecretStore`, built when the signature claims the prod group); beta, prod, a `swift build` coordinator, and every test without a fake have none, so nothing reads it. No value is logged.
  - *Amended by D-116:* the copy reads and writes each store's own copy only, its source is the prod group then the login keychain, a sign-in into the adopted row runs it too, and the old LaunchAgent's plist is deleted after a move.
  - *Limit (final review):* the pre-sign-in build and a current prod build share the app name, data directory, and LaunchAgent label, so adoption cannot tell them apart; the only guard is that `b4app`'s hub link is loopback. A prod install joined to the owner's local hub would be adopted (and its plist retired) by a local build started on the same Mac.
