## 2026-11-15 (a Claude Code reconcile finds the rows the live turn wrote)

- **D-238 Claude Code's history names an assistant block as the stream names it, the merge finds the app's own message under the id history gives it, and the adapter reads its projects folder even after an inspection (amends D-017, D-031).** The hill climb's audit listed, as a risk read from the code, that reconciling a Claude Code thread could add a second copy of each text row (its defect 12). A coordinator test over the fake runtime (`ContinuityTests.reconcilingAClaudeThreadAddsNoSecondCopyOfItsRows`: one finished turn, then `thread.reconcile`) found two defects on `main`, the first hiding the second.
  - **The thread was marked missing.** `ClaudeAdapter.inspectConnection` sets the account's scope and not `projectsDirectory`; `ensureAccount` returned as soon as a scope was set, so in a coordinator whose first act on the connection was an inspection, the projects folder was never read, `loadSession` found no transcript, and a reconcile set the thread's continuity to `missing` although its transcript was on disk. A missing thread refuses new turns. `ensureAccount` now returns early only when both are known.
  - **Every row was added again.** With the transcript read, the reconcile returned four rows for a question and its answer. The transcript named an assistant block `<line uuid>#<index in the line>` and the stream names it `<message id>#<stream index>`, so no id matched; and the user's message, which the app stores with no native id, came back under the line's `uuid`, which D-031's text match (for items with no id) did not cover.
  - **Assistant blocks.** `ClaudeTurnTracker.snapshotItems` names a block `<message id>#<n>`, n being its position among all of that message's blocks counted across lines, since the transcript writes one line a block, each carrying the message's id. That is the stream's index. A line with no message id keeps the `uuid` form. Thinking blocks are items in the snapshot as they are live; left out, their live rows matched nothing and D-031 moved them to the end of the thread.
  - **The user's message.** `mergeSnapshotItems` matches a snapshot user item that has an id and no native turn to a live user row with no native id and the same text; the row takes the id, so the next merge finds it by id. As in D-031, text is used only to recognise the app's own message: an assistant row is never matched this way.
  - **What it costs.** Snapshot rows stored under the old ids are removed and inserted again by the next reconcile, with new row ids. Two messages with the same text match in order, so in a partly cached thread a live row can take an earlier message's place; the texts and their order are the same either way (D-031's text match has the same property).
  - **Not changed.** System rows (a turn's note) are live rows no history names, and a reconcile still puts them after the snapshot's rows; both densities draw a note with its turn, not where it is stored. The reconcile of a turn still running is as D-016 left it.
  - **Verification.** The coordinator test failed on `main` with continuity `missing`, and with the first fix alone with four rows; it passes with both. `ClaudeTurnTrackerTests.transcriptBlocksAreNamedAsTheStreamNamesThem` feeds the same message to the stream translator and to the snapshot and compares ids; `SnapshotMergeTests.theAppsOwnMessageIsFoundUnderTheIdHistoryGivesIt`. One transcript written by Claude Code on the owner's Mac was read for its shape only (one block a line, a message id on every assistant line). Not checked: a live Claude Code session through the coordinator (`B4APP_LIVE_CLAUDE` was not run), whether Claude Code 2.1.282 writes the `uuid` the app sends with a message, and a transcript with sub-agent lines.
