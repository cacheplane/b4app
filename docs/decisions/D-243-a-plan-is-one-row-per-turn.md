## 2026-11-16 (a plan is one row per turn)

- **D-243 An agent's plan or task list is one `taskList` item per turn, written by each adapter and replaced in place; a live row history does not name keeps its place in its turn (amends D-031 and D-223).** The hill climb's audit found that plans had no presentation of their own (its defect 10): Codex's `turn/plan/updated` was dropped by the adapter, Claude Code's `TodoWrite` and task tools drew as generic tool rows, and B4's `plan_update` was a raw row. The owner chose a row in the transcript over a panel pinned above the composer, and adapters over a fold in the projection. The design is `docs/superpowers/specs/2026-11-16-plans-and-task-lists-design.md`.
  - **The item.** `TaskList` in `WorkspaceProtocol`: type `taskList`, role `tool`, `steps` of `{ text, status }` with status `pending`, `inProgress` or `completed`, an optional `explanation`, and its own `status` always `completed` so nothing reads the row as an open tool. An unknown status is pending: a step is never read as done or under way unless the runtime said so. The item is not called `plan` because Codex has a `plan` thread item that is prose. `SessionService` already replaces an item's payload when its native id arrives again, so the row is updated in place with no new storage, no migration and nothing new in the sync.
  - **Codex.** `turn/plan/updated` (the whole list each time: `plan` of `{ step, status }`, an optional `explanation`) becomes the item under `tasks:<turn id>`. The translator keeps no state, so an emptied plan is written as it is, and the views draw nothing for a list with no steps.
  - **B4.** A `plan_update` event with a `todos` array becomes the item under `tasks:<turn id>`. Without `todos`, and for any other named event, the generic row is unchanged.
  - **Claude Code.** `ClaudeTaskFold` holds the session's list. `TodoWrite` replaces it. `TaskCreate` adds a pending step when its result arrives, since the task's number is only there ("Task #3 created successfully"); `TaskUpdate` changes or, with `deleted`, removes the step with that number; `TaskList` and `TaskGet` change nothing; a failed result changes nothing. None of the five is a tool row any more. The list lives for the session, so a turn that changes it gets one item holding the whole list as it then stands, and a turn that does not touch it gets none.
  - **Claude Code's item id.** The live turn id is one the app makes and the transcript does not carry it, so the item is named after the tool use that first changed the list in that turn (`tasks:<tool use id>`), which the stream and the transcript both know. The history import runs the same fold (a turn begins at a user line that carries text), so a reconcile finds the row the live turn wrote and adds none.
  - **Where a turn's item ends.** The live fold starts a new item when the app begins a turn and when a turn's result arrives, so a turn Claude Code starts itself (a task notification) gets its own item and does not write on the turn before it. The history import starts one at each user line that carries text, except a compaction summary, which Claude Code writes in the middle of a turn. A sub-agent's task tools (a frame with `parent_tool_use_id`) are neither the session's list nor a row: a sub-agent keeps its own list, and its lines are not in the session's transcript. The branch's review found both; each has a test that failed first.
  - **A session started again.** The tracker is made when a session's process starts and dropped when it exits. On a resume the adapter folds the session's transcript into the new tracker before the first turn, so an update to a task an earlier process made still lands. A transcript that cannot be read leaves the list empty and updates to unknown tasks are ignored.
  - **The merge (amends D-031).** `mergeSnapshotItems` kept a live row the snapshot did not name but put it after every snapshot item. A Codex or B4 list is such a row, and so is any live row of a turn whose other rows history holds. It now stays directly after the row of its own turn that stood before it. With no such row it goes after everything history brought, as before, so a turn history has not caught up with is not moved ahead of older history.
  - **What is drawn (amends D-223).** `TaskListRow`: "Plan · 2 of 4", the explanation on one muted line, then each step with a mark (a check, the working mark, an open circle) and its text, at most two lines. Normal density draws the row where it was written. Dense draws it while the turn runs, as it draws the turn's messages, and folds it with the other working rows once the turn ends; a running turn with only a list has the list and no running line (D-239). It is never a counted step.
  - **A step left open.** Once the turn is no longer running, a step still in progress is drawn as unfinished (a dash), whatever the turn's outcome, and as unknown while the turn is reconciling, as D-234 does for tool steps. Claude Code often ends a turn with a step in progress and picks it up in the next, where the new row shows it under way again.
  - **Calls made without the owner.** The running line does not carry the count. `TaskCreate` shows nothing until its result arrives. A `TodoWrite` drops the task numbers, so a later `TaskUpdate` of an old number is ignored. Rows stored before this change are left: an old Claude Code thread keeps its raw rows, a reconcile adds the list beside them, and the dense projection still keeps the old tool names out of its step count.
  - **Not done.** `ExitPlanMode` and Codex's prose `plan` item; Codex command output while a command runs (the other half of defect 10); announcing a change to VoiceOver (defect 9); B4 history (`GET /state` is not known to return the list, so a B4 row is live-only).
  - **Verification.** `docs/verification/2026-11-16-a-plan-is-one-row-per-turn.md`. Every runtime shape was read, not observed: Codex's from the 0.166.0 schema, Claude Code's from a transcript recorded on 2.1.227, B4's from the fake server. No live session was run.
