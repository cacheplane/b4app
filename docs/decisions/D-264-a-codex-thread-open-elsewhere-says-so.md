## 2026-11-20 (a Codex thread another app holds)

- **D-264 A Codex thread that another app holds for writing says so: the send fails with a plain sentence and Check again, where it showed Codex's `thread <id> already has an active writer`.** Codex lets one process write a thread at a time, by a lock file under `~/.codex/thread-writer-locks`. The ChatGPT desktop app runs its own Codex server and holds that lock for a thread it has open, so a send to the same thread from this app was refused at `thread/resume`, and the adapter passed Codex's words through as an `internal` error with no cause and no next step. Found on 2026-11-19 with a test thread the ChatGPT app had open.
  - **The rule.** `CodexAdapter.openElsewhere` reads a JSON-RPC error whose message contains `already has an active writer` (Codex 0.166's wording, sent under `-32600` and `-32603`; Codex's own terminal client matches on the same words) and throws `protocol_invalid` with `reason: native_session_busy`, Codex's text kept in `nativeMessage`, and the message "This Codex thread is open in another app, which holds it for writing. Close the thread there, or quit that app, then choose Check again. Nothing was sent." It is applied to `thread/resume` and to `turn/start`. `Remediation` gives the reason the same Check again as an archived session (the archived-session pattern, D-190: the thread stays `available`, and its transcript and the failed message stay).
  - **Left out.** Naming the app that holds the lock (the lock file does not say); waiting for the lock and sending when it frees; the same wording for `thread/archive` and `thread/delete`, which this app does not call on Codex.
  - **Tests.** `CodexAppServerTests.aThreadOpenElsewhereIsNamedAndNotSubmitted` (`fake-codex.py`'s `thr_busy`), `ContinuityTests.aThreadOpenElsewhereStaysAvailableAndKeepsItsMessage` (through `SessionService`, a send and a re-check), `RemediationTests.aThreadOpenElsewhereOffersCheckAgain`. Not live-tested: the lock is held by another app, which this work did not drive.
