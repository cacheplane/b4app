## 2026-11-01 (M8b)

- **D-050 The hub cuts pull pages by stored value size, prunes its change log on a schedule, and restores a stale reader from one unpaged snapshot.** A pull page stops at 1000 changes or 8 MiB (8,388,608 bytes) of `value`, whichever comes first, and always holds at least one change, so a page of one 2 MiB change still moves. The size is not measured at read time: `changes.value_bytes` is the length of the value as PostgreSQL's `jsonb` text (a few bytes more than compact JSON), stored when the change is pushed, and the page is cut in SQL with a running sum over those integers, selecting `value` only for the rows inside the cut. A first version streamed 1001 rows out of PostgreSQL to find the cut, and the byte limit exists to bound work as well as memory. `changes.received_at` (`now()` at insert) is what pruning reads, not `wall`, so a device with a wrong clock cannot make its own rows look old. `serve` prunes every org when it starts and every 24 hours after; `B4HUB_RETENTION_DAYS` sets the retention (default 30; anything but a whole number of at least 1 is a configuration error and exits 2), and `b4hub prune --older-than-days N [--org slug]` does it once. Pruning takes the same per-org advisory lock a push holds, deletes every change received before the cutoff and every change with a lower `hub_seq` (the horizon is one cursor, so what remains is a contiguous tail), and raises `org_sync_horizons.horizon` to the highest `hub_seq` it deleted; the horizon never moves down and the materialised tables are not touched, because the log is history and the tables are state. A pull whose `after` is below the horizon answers `410 resync_required`; the check and the page are read in one database snapshot, so a prune that commits mid-pull cannot leave the reader a gap. The reader then calls `GET /v1/snapshot`, one `REPEATABLE READ` transaction that returns this user's rows as synthetic `insert` changes in dependency order (`hubSeq` 0, `deviceSeq` 0, `wall` 0, `deviceId` the row's owner), the per-column clocks of those rows, and `next`, the highest `hub_seq` the org's feed had at that instant (or the horizon, if pruning emptied the feed). A snapshot row's `hlc` is the greatest of its clocked columns' clocks, or `000000000000-0000-<owner device>` when none was ever set, so any later change of the row wins over it. The Mac applies the snapshot through the same narrow merge as any pull (D-049), so its rows stay and only phone-writable values are compared by clock; the phone clears its rows, keeps its outbox, applies the snapshot, re-applies the unsent outbox rows on top, and continues from `next`. **An uncut page's `next` is the highest `hub_seq` the org has recorded (at least `after`), even when that is another user's change.** Without this rule a user whose feed is idle would keep a cursor that other users' activity pushes below the horizon, and would resync every 30 days for nothing; nothing of theirs can lie in between, because pushes commit in `hub_seq` order. `GET /v1/devices` lists the user's devices (revoked ones included) for the mirror's device names. Migration `0003_organisation.sql` adds `changes.hlc`, `received_at`, and `value_bytes`, `owner_device_id` on every materialised table, `projects`, `projectFolders`, `column_clocks`, `org_sync_horizons`, and `threads."projectId"` and `"readTurnId"`. `serve` now also refuses a connection that inherits superuser, `BYPASSRLS`, or ownership of the tables through a role it is an `INHERIT` member of (`pg_has_role(current_user, oid, 'USAGE')` over the role graph), not only a role that has the attribute itself. Known limitations: the snapshot is not paged, so the hub builds the user's whole mirror in memory in one response; the first prune after a long gap deletes the whole prefix in one transaction while holding the push lock, and `received_at` has no index; the privileged-role check counts only ownership of `changes`, and a `NOINHERIT` member of a superuser can still `SET ROLE` (for a security review); the migration's backfill of `value_bytes` and `owner_device_id` is a full-table update. Amends the retention horizon and the page and value limits of D-043.
