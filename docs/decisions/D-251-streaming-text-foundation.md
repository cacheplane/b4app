## 2026-11-17 (streaming text foundation)

- **D-251 A reply is parsed as it streams by our own append-only markdown parser, owned by one stream per message outside `ThreadDetail`, revealed on a frame tick and drawn as blocks (amends D-236).** The design is `docs/superpowers/specs/2026-11-17-streaming-text-foundation-design.md`, the text half of two; the activity line (tools, sub-agents and steps as one quiet line) is the second design and is not built here. Before this, every `message.delta` appended to `ThreadDetail.liveText` and reassigned `detail`, so each token re-ran the grouping over the thread and re-evaluated up to 150 rows (D-237), and a reply was one inline-only text with fences cut out (D-236), so headings, lists, quotes and tables were literal text (defect 17 of `docs/research/2026-11-14-agent-chat-hill-climb.md`).
  - **The parser.** `Sources/StreamingMarkdown`, a Foundation-only target with its own tests, is the only markdown parser; `WorkspaceUI` depends on it and both link on iOS. `MarkdownParser` takes appended text (`push`), is told when the text is complete (`finish`), and gives a `MarkdownDocument`: paragraphs, headings, thematic breaks, fenced code, quotes, lists (ordered, bullet, task) and tables, each with an id that is its path of positions and never changes. A completed line is read once. A stack of open containers holds any blocks, so a list item holds code, quotes, tables and nested lists, a blank line between items does not end the list, and an unindented line continues a paragraph in a quote or item. A top-level block that a later line closes is frozen and returned unchanged on every later read. The open block is drawn from a projection computed on a copy and thrown away on the next push, so a wrong guess never reaches the frozen blocks: a table is a table from its first closed header cell, an open fence is code, an unclosed `**` is bold when text follows it, a half-typed list marker, thematic break or closing fence is held a character, and `[text](` draws `text` until the `)` arrives. After `finish` nothing is guessed. `MarkdownBlocks.split` and its tests are gone; its fence rules moved into the parser.
  - **Deviations from CommonMark and GFM, on purpose.** No setext headings (`Title` then `---` is a paragraph and a break, so a paragraph never turns into a heading a line later). No indented code blocks. Raw HTML, link reference definitions, footnotes and math are literal text. A soft line break inside a paragraph draws as a space and a hard break (two trailing spaces or a backslash) as a line break; before, every newline was kept. A lone `-` at the end of a reply is an empty list item, as CommonMark has it (the plan's test said a paragraph and was changed). A list marker interrupts a paragraph only when every open container matched the line, and then only with text and, if ordered, starting at 1, so `- a` followed by `2. b` is one item reading `a 2. b`. If a table's delimiter row never arrives, the header committed is a paragraph: the one block that changes kind, and only before it is frozen.
  - **What came from cacheplane's `partial-markdown` and what did not.** Taken as design, not translated: completed lines read once with the open line in a buffer, the projection rules for half-typed syntax, one tree with no second "pending" node (its 0.5.8 reversal), and flushing the buffer as a last line on finish (its 0.3.2 bug). Not taken: rebuilding and diffing the whole tree on every push, which made its cost per push grow with the reply (pushed one character at a time, a 2,140-character mixed document took 31 s against its 0.5.11 build, measured during the design), and its shallow containers, where a fence inside a list item closes the list and a blank line between items makes two lists. Where the two differ on a held marker or a link whose URL is still arriving, this parser holds or draws the text where cacheplane draws the source.
  - **One stream per message.** `MessageStream` (`Sources/WorkspaceUI/Streaming/`) owns a streaming reply's received text, its parser and how much has been shown. `MessageStreamStore`, on `WorkspaceModel` and passed to `TranscriptView`, keeps the open thread's streams by native item id. `ThreadDetail.liveText` is gone: a delta no longer reassigns the open thread's detail, so the grouping and the other rows are not run again; only the row reading that stream redraws. Deltas are appended as they arrive and never derived by comparing texts. Completion is explicit (`message.completed`, and every open stream on `turn.finished`), never inferred from quiet. A settled reply is parsed once and cached by item id and text, and a stream's last document is handed to the stored item when the texts match, so the row does not re-parse or change when the stored item replaces the live one. Blank lines at either end make no block, so a streamed reply and the same reply opened from history give equal documents.
  - **The paced reveal.** While a stream has text not yet shown, a tick at 60 a second shows `max(1, ceil(backlog / 12))` more characters, cut on a grapheme boundary, and pushes that slice to the parser: at most one parse and one redraw per frame however the deltas arrive, and the backlog stays about 200 ms from empty. On completion the step rises so the rest is shown within 9 ticks (150 ms). With Reduce Motion on, or no transcript on screen, everything received is shown at once. The ticker is injected; tests drive a `ManualTicker`. The numbers 12 and 9 are the design's first guess and have not been tuned on a live stream (step 3 of the gate, the owner's).
  - **Links and images.** `http`, `https` and `mailto` links open through the environment's `openURL`; a link with any other scheme draws as its words. `![alt](url)` draws as its alt text and nothing is loaded.
  - **The phone's relay gap: never less than was shown.** `MirrorTransport` is unchanged: after a gap it still completes the item with the text last known (often stale or empty) and may follow with a delta carrying the whole text for the same item id. Until the turn finishes, the store keeps what each item showed. A completion whose text is a prefix of what was shown leaves the row drawing the shown text, marked complete; a delta for an item whose stream completed opens a new stream whose reveal starts at the end of the prefix it shares with the shown text, so the reader's place is kept and nothing replays. When the turn finishes the stored item's text wins. Before, the same gap blanked the live text and then showed it again whole.
  - **D-236 and D-237.** This amends D-236: headings, lists, tables, quotes, breaks and links are now drawn; fenced code is still `CodeFence`, unchanged, with Copy once the fence closes or the reply ends. D-237's cost that "a streamed token re-evaluates up to 150 rows' views" no longer applies to a reply's text: a reveal re-evaluates the one row reading its stream (`aTokenDoesNotRerunTheGrouping`, at both densities). D-237's plain stack and window stand.
  - **Not done.** The activity line, the working cue, sub-agent grouping and streaming of reasoning or command output (the next design). Syntax colouring and a diff view. Selection across blocks, Copy for a whole message, and Copy for tool output. Remote images, raw HTML, math, footnotes, link reference definitions, setext headings and indented code blocks. Lazy rows. The user's own messages and reasoning text are drawn as before. Emphasis draws upright: the bundled sans has no italic face.
  - **Verification.** `docs/verification/2026-11-17-streaming-text-foundation.md`. Fixture-tested; no live runtime session, no frame-time measurement of the running app, nothing on an iPhone or with VoiceOver.
