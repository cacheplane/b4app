## 2026-11-02 (sign-in build)

- **D-096 A sign-in reuses a device of the same user, on the same platform, not revoked, named by `deviceId` or `candidateDeviceIds`; a hub without `candidateDeviceIds` refuses it, so the hub is upgraded first.** `accounts::issue_session_reusing`, `DeviceRequest`. The platform must match because it decides write rights, so a phone never takes over a Mac's device id. Reuse renames the device and deletes its earlier tokens, which also closes a session a failed log-out left open. `candidateDeviceIds` (up to 32 UUIDs; `deviceId` counts first, duplicates dropped) is for a client that cannot know which account a passkey or Apple ID belongs to: the Mac offers the device of every registry row for this hub, most recently signed in first and UUIDs only (one malformed id would make the hub refuse the sign-in), and the phone the devices it remembers for this hub (D-108). An older hub refuses the unknown field with `400 invalid_request` (`deny_unknown_fields`), so a Mac that knows several accounts cannot sign in to it; a Mac that knows one sends only `deviceId`. The upgrade order is hub, Macs, phones (`docs/compatibility.md`). *Amended by the live gate (X3):* `POST /v1/enroll` follows the same rule, with `deviceId` and `candidateDeviceIds` at the top of its body (same validation and cap, checked before the code is used up). Without it, a Mac that logged out and rejoined with `hub join` became a new device, and every row it had synced kept the old, now offline, device as `owner_device_id`, so the phone showed the Mac offline and relayed turns to it. `hub join` (`AccountManager.join`) offers the registry's devices for the hub it joins, and `MirrorAccount` the remembered devices on a typed code, a pairing scan, and the merge-first path. Candidates only ever match devices of the code's own user: on a merge, the token's account's devices are never reused (they are deleted with it). An older hub refuses the new fields as it does on sign-in, so the hub is upgraded first.
  - *Amended (final review, X3-2):* a pairing code (minted by a Mac) is redeemable only as `ios`; any other platform gets `invalid_code` and the code stays usable, so a code holder who knows the Mac's device id cannot take over that device through `candidateDeviceIds`. `devices::redeem_reusing`, test `a_pairing_code_pairs_only_a_phone`.
