# Decision log

Material implementation decisions, newest first. The spec (`docs/roadmaps/Personal_Agent_Workspace_Technical_Spec_and_Roadmap.md`) is the requirement source; this log records deviations and choices the spec left open.

## 2026-11-01 (distribution)

- **D-048 The Mac app stays on Developer ID outside the Mac App Store; the iOS companion goes to TestFlight; Developer ID Mac builds keep secrets in the data-protection keychain in a group the app and the coordinator share.** Research: `docs/research/reports/App Store and TestFlight signing.md`. **Mac:** TestFlight for Mac and the Mac App Store both require App Sandbox on every executable (Guideline 2.4.5(i), ITMS-90296), and three core features cannot run in it: the user's own `codex`, `claude`, and `node` (a sandboxed process may execute only inside its allowlist, and children inherit the sandbox); the bundled PostgreSQL (its System V shared memory and semaphores are denied); and the LaunchAgent the app writes into `~/Library/LaunchAgents`, with the socket in `$TMPDIR`. So the Mac app ships notarized Developer ID builds only (D-039). **iOS:** `Scripts/upload-ios.sh` archives and exports with method `app-store-connect`, destination `upload`, automatic cloud-managed signing, and a Team App Store Connect API key with the Admin role (`B4APP_ASC_KEY_ID`, `B4APP_ASC_ISSUER_ID`, the `.p8` file outside the repository). Builds are internal-only unless `B4APP_TESTFLIGHT_EXTERNAL=1`, and the build number is the UTC time (`yymmddHHMM`). Both targets now read their versions from `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION`. The iOS bundle declares `ITSAppUsesNonExemptEncryption = NO` (HTTPS through URLSession only) and a local-network usage string, and carries `PrivacyInfo.xcprivacy`: no tracking, no data collected by the developer, and no required-reason API, which was checked in the iOS-linked modules. A post-build script removes the localhost ATS exception outside Debug, since on a device `localhost` is the phone. **Team id:** `Config/Signing.xcconfig` is committed with an empty `DEVELOPMENT_TEAM` and includes the gitignored `Config/Signing.local.xcconfig`. `project.yml` sets no team, and the scripts pass `DEVELOPMENT_TEAM` (the iOS script reads it from the Developer ID certificate or `B4APP_TEAM_ID`). CI keeps building with `CODE_SIGNING_ALLOWED=NO`, and iOS Simulator builds still sign to run locally. **Mac keychain:** this supersedes D-008 for Developer ID builds. TN3137 says data-protection access groups come only from entitlements a provisioning profile authorises, and a bare tool has nowhere to embed one, so the coordinator is now a background-only app bundle, `Contents/Helpers/B4AppCoordinator.app` (`com.cacheplane.b4app.coordinator`, `LSUIElement`). The LaunchAgent, the CLI's lookup, and the app run `B4AppCoordinator.app/Contents/MacOS/b4app-coordinator` directly, and the app rewrites an existing user agent plist that points at the old path. The owner registers the App IDs `com.cacheplane.b4app` and `com.cacheplane.b4app.coordinator` with Keychain Sharing and creates a Developer ID profile for each. `Scripts/package.sh` then checks each profile (App ID, team, the group, expiry) and embeds it as `Contents/embedded.provisionprofile`. It generates the entitlements from the certificate's team id: `com.apple.application-identifier`, `com.apple.developer.team-identifier`, and `keychain-access-groups` = `<team>.com.cacheplane.b4app.shared`. It signs inside out (PostgreSQL, the CLI with the identifier `com.cacheplane.b4app.agent-workspace`, the coordinator bundle, the app) and confirms both signatures claim the group. A notarized build must also pass `syspolicy_check distribution`. `KeychainSecretStore.forCurrentProcess()` reads the process's own `keychain-access-groups` (`SecTaskCopyValueForEntitlement`): a process that claims the shared group uses the data-protection keychain in it, and anything else (`swift build`, tests, ad hoc packages, or `B4APP_SKIP_PROFILES=1`) stays in the file-based login keychain, since it has no profile. A data-protection store moves an item it lacks out of the login keychain on first read (read, add, delete), so each old item can prompt once, because the coordinator's signature changed. `doctor` names the store in use. A probe on this Mac (2026-11-01) showed why the file-based keychain alone is no longer a reason to move: a Developer ID rebuild with a new code hash read an item without a prompt, where an ad hoc rebuild returned -25293. The data-protection keychain was chosen anyway because the owner wants the full provisioning flow, it is Apple's default for new code, and the file-based keychain is on its way to deprecation. **Expiry:** a Developer ID profile lasts 18 years, but an app whose profile has expired no longer launches, so `package.sh` refuses an expired profile and prints each expiry. Renewing the Developer ID certificate means regenerating both profiles before the next release.

## 2026-10-31 (thread detail layout)

- **D-047 Nothing in a split-view column outside a scroll view may have a minimum height that grows with runtime text; the pending-request list scrolls past `LLA.Metrics.requestsMaxHeight`, and the detail must fit `LLA.Metrics.minimumWindow` at any content.** Opening a thread whose Claude turn waited on a `tool_permission` request blanked the whole macOS window, sidebar included, until relaunch: `NavigationSplitView` on macOS 26 measures its detail column's minimum size at an unspecified width, and the request card's command (`Text` with `fixedSize(horizontal: false, vertical: true)`) measured one character per line, 4,749 points for a 263-character command, so the split view drew nothing in either column; near the limit (a long reason, the continuity banner, the smallest window) the composer was pushed off the bottom instead, the shape of the PR #10 defect. `RuntimeRequestList` is now a scroll view capped at 240 points that sizes to its cards below the cap, so its minimum is bounded whatever a runtime sends and several requests scroll instead of displacing the composer; the continuity banner's explanation and the composer's error message drop `fixedSize` (they still wrap when there is room and truncate before the composer leaves the window); the app's window minimum is the shared `LLA.Metrics.minimumWindow`. `DetailMinimumSizeTests` pins it by measuring `ThreadsView` with `NSHostingController.sizeThatFits(in:)`, the question the split view asks, at zero width and at the detail column's minimum width, for the stored thread, a 3,000-character command and reason, two such requests, the continuity banner, and a long draft; the snapshot harness could not have caught it, since the real split view draws nothing off screen.

## 2026-10-31 (M8a)

- **D-046 The iOS app reads a SQLite mirror fed by the hub's change log through an in-process `WorkspaceTransport`, so the SwiftUI shell is unchanged across platforms; only threads created in the app sync.** Nothing is read from `~/.codex`, `~/.claude`, or a B4 server's history. Three Foundation-only modules were added. `WorkspaceSecrets` holds `SecretRef`, `SecretStore`, and `KeychainSecretStore`, moved out of `WorkspacePlatform` (which re-exports them) so the iOS target can use them without the macOS-only module; on iOS the item is in the data-protection keychain with `AfterFirstUnlockThisDeviceOnly`. `WorkspaceSync` holds the wire types, `HubAPI`, `HTTPHubAPI`, `FakeHubAPI`, and the `HubURL` rule (https anywhere; http only for `localhost`, `127.0.0.1`, `::1`), enforced by the coordinator's `hub join` and the phone's Connect screen before any request. `WorkspaceMirror` keeps STRICT SQLite tables with the Mac's column names (WAL, `synchronous` FULL, foreign keys, `busy_timeout` 5000), replays a change batch with the same semantics as `WorkspaceDatabase.replay`, blanks `authReference`, `localServerId`, and `target` again on the way in, and stores a row that does not decode through the protocol types, skips it on read, and counts it in `SyncDiagnostic.undecodableRows` rather than dropping it or failing the batch. The Mac side is `HubSync` in the coordinator, the only code that talks to the hub: it pushes the trigger-written change log in batches of 500 rows or 8 MiB, marks rows `synced` only through the hub's `acceptedThrough`, is nudged by the event log, a 30 s timer, and wake, and suspends on a 401 until the next `hub join`. `SyncFilter` keeps only the 16 known `connections` columns on an insert (an allowlist; a non-object insert is dropped), blanks `connections.authReference`, `localServerId`, and `target` for every kind, replaces a `nativeScope` (on `connections` and `threads`) that contains `/`, such as a B4 origin URL or a Claude config directory, with `scope:` plus the first 16 hex characters of its SHA-256 (stable, so the mirror's uniqueness on connection, scope, and native thread holds), never uploads `localServers`, and replaces a `displayItems.payload` or `runtimeRequests.payload` over 1 MiB with `{"truncated": true, "bytes": n}` on inserts and updates; the wire carries no device id, the hub attributes every change to the authenticated device, and the Mac's `b4app.device_id` session setting is now set per write transaction from `hubLink`, so rows written before joining, recorded as `local`, need no rewrite. `database.restore` is refused while joined (`hub leave` first), because a restore rewrites the change log and its sequence, and reused device sequence numbers would count as already accepted at the hub and never be mirrored. `DiagnosticsReport.sync` is an additive optional field, and `ConnectionsView` hides an empty target path. `Tests/Fixtures/sync/changes.json` is the cross-language contract, decoded in place by the Rust and Swift suites; edit it only with both suites. Unimplemented behaviour (phone writes, the relay) throws `unsupportedCapability` naming M8b or M8c.
- **D-045 A turn sent to a thread whose owning device is offline is refused, never queued.** The owner's decision; the refusal names the Mac's last-seen time. The relay (M8c) will route `turn.send`, `turn.interrupt`, and `request.respond` to the owning Mac; interrupts and request answers may be held for at most 60 s, and the first answer wins. Nothing of this is built in M8a, where the phone is read-only.
- **D-044 The hub owns users, organisations, devices, and credentials; no identity provider is bundled.** M8a enrolls a device with a one-time code: `b4hub enroll --user` mints eight characters from `BCDFGHJKLMNPQRSTVWXZ23456789` (no vowels, no `Y`, no `0` or `1`), valid ten minutes and single use, which a client redeems for a device token (32 random bytes, base64url). The hub stores only the token's SHA-256 and shows the token once. Revoking a device deletes its token rows and sets `devices.revoked_at`; the history it uploaded stays. The sign-in flows (PKCE for the apps, the device grant for the CLI, rotating refresh-token families, self-registration, SSO brokering) are M8d and extend these tables instead of replacing them. The enrollment code is read from the terminal with `readSecret`, never from an argument, and the phone clears its field once the request returns.
- **D-043 The hub is a Rust service in `Hub/`, one shared schema with `org_id` on every tenant table and row-level security enforced by the database.** The Cargo workspace is `b4hub-core` (pure types and rules), `b4hub-db` (sqlx), and `b4hub` (axum binary with `serve`, `migrate`, `seed`, `enroll`), edition 2021 on Rust 1.93.1, exact `=` pins, `Cargo.lock` committed, builds and tests run `--locked`, `unsafe_code` forbidden. It follows the conventions of the b4 Rust rewrite (`~/repos/b4`): B4's error envelope (`error.kind`, `error.message`, `error.details.code`; public errors never carry SQL, panics, or another tenant's data), authentication before the body is read, `deny_unknown_fields` on inbound bodies, a non-root container (uid 10001) with a `HEALTHCHECK` on `/readyz`, and a bounded drain on SIGTERM (`/readyz` fails first, new work is refused, long-polls finish, exit within `B4HUB_SHUTDOWN_WAIT_MS`, default 30000); configuration errors exit 2. Tenancy: RLS is enabled and forced on every tenant table with the policy `org_id = NULLIF(current_setting('b4hub.org_id', true), '')::uuid`, and each request transaction begins with `SELECT set_config('b4hub.org_id', $1, true)` using the org from the verified credential. The application role `b4hub_app` is provisioned by `migrate` from the password in `DATABASE_URL` (printable ASCII; the server receives only a client-computed SCRAM-SHA-256 verifier), is `NOSUPERUSER NOBYPASSRLS`, and does not own the tables, so there are two URLs: `DATABASE_ADMIN_URL` (owner; `migrate`, `seed`, `enroll`) and `DATABASE_URL` (`b4hub_app`; `serve` only). **Three tables carry no RLS.** `orgs` is the tenant directory. `device_tokens` and `enrollment_codes` are looked up by the hash of a secret the caller presents, before any org is known, so a tenant policy cannot apply; they hold only hashes, ids, and expiry, never synced content, and everything they lead to is then read under the org they name. The change log has `(org_id, device_id, device_seq)` unique for idempotent pushes and a per-org `hub_seq` bigserial as the reader's cursor; a per-org advisory lock keeps commit order equal to sequence order so a reader never skips a row that commits late. The six synced tables are materialised with the Mac's quoted camelCase columns plus `org_id`, `user_id`, `device_id`, keyed `(org_id, id)` with the client's text ids; hub-minted ids are UUIDv7. Every read and write is scoped to the token's `user_id`, and a missing resource and an inaccessible one answer the same generic 404. Limits: 2 MiB per change value (`MAX_PAYLOAD_BYTES`), 32 MiB per push body, 1000 changes per push, 1000 per pull page, and a long-poll `wait` capped at 25 s whose waiter is registered before the final emptiness check, so a push between the check and the wait is not missed. The retention horizon is 0 because M8a never prunes; `resync_required` (410) is answered only for a negative cursor until pruning exists.

## 2026-10-31 (agent)

- **D-042 The background coordinator runs from a per-user LaunchAgent plist the app writes and bootstraps, not from an `SMAppService` bundle agent.** The managed agent pins a lightweight code requirement to the registered program; with an ad hoc signature that is the binary's own hash, so every rebuild left the job loaded but unspawnable ("spawn scheduled", exit 78 EX_CONFIG, retried every ten seconds) while the previous coordinator kept serving from its deleted file, and neither `register` again nor unregister-and-register refreshed it. The same binary bootstrapped under a plain label ran at once. The app now writes `~/Library/LaunchAgents/com.cacheplane.b4app.coordinator.plist` with the bundled coordinator's absolute path, rewrites and re-bootstraps it when the path changes or launchd reports a spawn failure, unregisters a leftover managed agent once, and removes the plist on "Remove Background Agent" or `--remove-agent`; `coordinator status|restart|plist` keep the label. The bundle still carries its `Contents/Library/LaunchAgents` plist for a future Developer ID build, where the managed agent's requirement would be stable. Supersedes the hosting part of D-038.

## 2026-10-31 (storage)

- **D-041 Postgres everywhere: each Mac runs a private Postgres cluster as the coordinator's store, and a remote Postgres is the multi-device hub; GRDB and SQLite leave the package.** The owner chose one engine and one migration toolchain end to end over the recommended SQLite-on-device design. The server binaries are pinned, fetched by checksum, and bundled under `Contents/Helpers/postgres`; the cluster lives in the data directory, listens only on a Unix socket in the runtime directory, and runs under a second LaunchAgent in the packaged app or as a coordinator-owned child elsewhere. One set of versioned SQL migrations serves the local cluster and the hub; a `pg_dump` precedes every local migration; the existing SQLite file is imported once. Amended the same day: the iOS companion keeps SQLite as its own local store and syncs through the same change log (offline-capable, a limited feature subset only if necessary); the hub is multi-tenant and multi-user, so synced rows carry a tenant and a user and devices authenticate as users. Settled while building M7: PostgreSQL 17.11 from the zonky embedded build, pinned by SHA-256, thinned to arm64 and pruned to 62 MB (`Scripts/fetch-postgres.sh`), shipped under `Contents/SharedSupport/postgres` because `Contents/Helpers` admits only nested code; the coordinator starts the cluster through `pg_ctl` and stops one it started, adopting one already running after the D-025 identity check, so there is no second LaunchAgent; the store speaks libpq bound at runtime with `dlopen`, synchronously, behind the unchanged `WorkspaceDatabase` API; the pinned build has no `pg_dump`, so backups and major-version moves are the store's own JSON-lines export and restore (`db backup|restore`); the pre-0.2 `workspace.sqlite` is imported once at first start in one transaction and retired as `.imported`; the change log is written by triggers (`0002_changes.sql`) with a session setting that silences them during replay and restore. Design: `docs/superpowers/specs/2026-10-31-storage-and-sync-design.md`.

## 2026-10-31 (M6)

- **D-038 The packaged app carries the coordinator and the CLI in `Contents/Helpers` and a LaunchAgent plist in `Contents/Library/LaunchAgents`; the app registers the agent with `SMAppService` and hosts in-process only as a fallback.** Order on connect: an answering socket wins; otherwise a bundled agent is registered (`RunAtLoad`, `KeepAlive` on failure only, Aqua session) and the socket awaited for six seconds; otherwise the app hosts as before (Xcode runs, an agent awaiting Login Items approval, a failed registration). The link status says when approval is needed and opens Login Items. Restart is `launchctl kickstart -k` for the agent, a close for an in-process host, or SIGTERM for another process; the CLI exposes the same as `coordinator status|stop|restart`, and the app's Coordinator menu adds "Remove Background Agent", which unregisters. The coordinator version is the package's version (`CoordinatorVersion.current`, stamped into `MARKETING_VERSION` by `Scripts/package.sh`); a running coordinator that reports another version shows a restart note. Amends D-004 (the LaunchAgent exists) and D-032: with the agent hosting, Quit owns nothing and local work continues. Amended 2026-10-31 (M7 switch-over): launchd pins a lightweight code requirement to the registered program, and with an ad hoc signature that requirement is the binary's own hash, so a rebuilt bundle leaves the job loaded but unspawnable ("needs LWCR update", exit 78 EX_CONFIG) while the previous coordinator keeps serving from its deleted file. The app therefore calls `SMAppService.register` on every launch (idempotent; it refreshes the requirement), `Agent Workspace --register-agent` does the same for scripts, `coordinator status` prints launchd's job state and last exit code, and `coordinator restart` gives launchd 90 s for the orderly shutdown that now stops the cluster. A Developer ID signature would make the requirement stable across rebuilds.
- **D-039 Signing is ad hoc until a Developer ID certificate exists on the build Mac; the package script takes `B4APP_SIGN_IDENTITY` and then adds the hardened runtime and a timestamp.** No signing identity is installed on the target Mac (`security find-identity -v -p codesigning`: 0), so notarisation and Gatekeeper-clean distribution stay open; the ad hoc build runs where it was built. Helpers are signed before the bundle and `--deep` is never used. The Keychain stays file-based (D-008) for the same reason. **Amended 2026-10-31 (Developer ID):** the owner enrolled in the Apple Developer Program, and the build Mac now holds one identity of the form `Developer ID Application: <name> (<team id>)` in the login keychain, plus a notarytool keychain profile named `b4app` that the owner created themself with `xcrun notarytool store-credentials`, so no Apple ID or app-specific password passes through the script. When `B4APP_SIGN_IDENTITY` matches a Developer ID Application line in `security find-identity -v -p codesigning` (by name or SHA-1), `Scripts/package.sh` checks the notary profile before building; signs every Mach-O under `Contents/SharedSupport/postgres`, then both helpers, then the bundle (with `B4App.entitlements` again, since re-signing drops what Xcode embedded), all with `--options runtime --timestamp`; checks `codesign --verify --deep --strict` and that the signed `TeamIdentifier` is the certificate's; zips with `ditto -c -k --keepParent`; runs `xcrun notarytool submit --keychain-profile "${B4APP_NOTARY_PROFILE:-b4app}" --wait`, printing `notarytool log` and failing on any status but Accepted; staples and validates; re-zips the stapled app; and fails unless `spctl -a -vv --type exec` reports `source=Notarized Developer ID`. `B4APP_SKIP_NOTARIZE=1` signs without submitting; any other identity keeps the old behaviour (hardened runtime, no notarization), and no identity keeps the ad hoc path unchanged. The team id is read from the certificate at package time, so `project.yml` keeps `DEVELOPMENT_TEAM` empty and Xcode still builds ad hoc before the re-sign. **No entitlements were added**, and `B4App.entitlements` stays an empty dictionary: the first submission was accepted and the first launch ran clean under the hardened runtime. The coordinator `dlopen`s `libpq.5.dylib`, and the server loads `plpgsql.dylib` and `dict_snowball.dylib`; library validation lets each of those load because it is signed by the same team. The PostgreSQL binaries find their libraries through `LC_RPATH @loader_path/../lib`, not `DYLD_LIBRARY_PATH` (which the hardened runtime strips), and nothing JITs or maps writable code. So `com.apple.security.cs.disable-library-validation`, `allow-dyld-environment-variables`, `allow-jit`, and `allow-unsigned-executable-memory` are all unneeded. With a team-signed coordinator the `SMAppService` agent's code requirement survives a rebuild (`docs/verification.md`), but the per-user plist of D-042 stays until the owner asks to switch. D-008's file-based Keychain is unchanged by this amendment.
- **D-040 Runtime lookup without a shell also covers version managers by their on-disk layout: nvm's newest installed Node first, fnm's `default` alias, Homebrew's `opt/node`.** A Finder- or launchd-started process has `PATH=/usr/bin:/bin:/usr/sbin:/sbin`; shell hooks never run. `~/.local/bin`, Homebrew, npm-global, Volta, and Bun were already searched (M4); the CLI finds the bundled coordinator through its own resolved path, then `/Applications` and `~/Applications`.

## 2026-10-31 (M5)

- **D-031 Native history is merged into the cache by snapshot order; live rows are never deleted or duplicated.** `thread.reconcile` (and a plain `thread.read` whose cache is empty although turns were recorded) calls the adapter's `loadSession` and merges: a snapshot item whose native id is cached keeps that row (a live row keeps its payload, a snapshot row takes the new one); an id-less item that matches a cached item of the same role and text reuses that row; everything else is inserted with `snapshot` provenance in the snapshot's order; cached snapshot rows the runtime no longer reports are removed; live rows nothing matched (the turn in flight) follow at the end; sequences are renumbered in one transaction. Text matching is used only to recognise the app's own user messages, never as an exactly-once guarantee for runtime events (spec 10.1).
- **D-032 Quit offers "Quit" or "Stop local work and quit", never "keep running in the background"; threads whose native session is missing or whose connection now presents another identity stay readable and never resume.** The coordinator lives inside the app until the M6 LaunchAgent (D-004), so local turns end with the process either way; the dialog says so, names the local turns and owned servers, and states that attached and remote B4 runs continue on their server and are reconciled next launch. When another process hosts the coordinator the app owns nothing and quits at once. `connections.nativeScope` records the identity last presented; a thread created under a different scope is `identity_changed`, a runtime that lost the session is `missing`; both keep the cached transcript, refuse `turn.send` with a stable code, and offer a new thread (spec 3.3, 5.1).
- **D-033 The directory lock is derived from stored turns, not a lock table.** Before dispatch on a Codex or Claude connection the coordinator canonicalizes the thread's working directory (symlinks resolved, no trailing slash) and refuses `protocol_invalid` / `directory_locked` while any other harness thread, on any connection, has a non-terminal turn there. Because the state is the turns themselves, the lock survives restarts and holds through `waiting_for_user`, `stopping`, and `reconciling` (spec 10.1.5); `turn.abandon` releases it deliberately. B4 routes are not directories.
- **D-034 Wake is detected twice: `NSWorkspace.didWakeNotification` in the app and a clock-gap watcher in the coordinator.** `ContinuousClock` keeps counting while the Mac sleeps and `SuspendingClock` does not; a drift over 20 s between two five-second ticks means a wake and triggers `workspace.reconcile`, so a CLI-spawned coordinator with no app also reconciles. Reconciliation asks each runtime about each unresolved turn and re-checks offline connections; it never re-sends.
- **D-035 The coordinator is the redaction boundary.** Every adapter event's `message`, `stderr`, and `error.message`, every failed turn's message, and every `recentErrors` entry are passed through `LogRedactor` before they are stored or published; adapters forward runtime text as they receive it. The redactor also masks whole `Authorization:` header lines and sensitive URL query parameters (`code`, `state`, `token`, `access_token`, …). The CLI-spawned coordinator's stdout log is bounded like server logs. Redaction masks known shapes; it is not proof that arbitrary runtime output holds no secret (spec 12).

## 2026-10-31 (M4)

- **D-024 Managed servers are spawned with `posix_spawn` into their own process group, with stdout and stderr redirected to a per-server log file, not through `StreamingProcess`.** The pipe-based helper ties a child's life to the coordinator (an orphaned Node process dies on its next write to a closed pipe) and loses its output across a coordinator restart. The file keeps the server independent so an app Quit or a coordinator crash never loses a running server, and the process group lets a stop reach a runtime child that outlived `b4 dev`. The spawn also resets the child's signal mask and the dispositions of SIGTERM, SIGINT, SIGHUP, SIGPIPE, SIGQUIT, and SIGCHLD: the coordinator ignores several of those and dispositions survive exec, and a blocked SIGTERM inherited from the spawning thread left a server that only SIGKILL could stop.
- **D-025 Ownership is `(pid, process start time within one second, argv containing the CLI entry file and the port)` from `KERN_PROC_PID` and `KERN_PROCARGS2`, captured at spawn and re-verified before every signal and on every coordinator start.** A pid or a listening port alone never establishes ownership; a mismatch leaves the process alone and marks the registration stopped with a message naming the pid.
- **D-026 The project-installed CLI runs as `<node> <project>/node_modules/@b4run/cli/dist/index.js`, never through `node_modules/.bin/b4` or a shell, and is never downloaded.** The pnpm shim resolves `node` from `PATH`, which a Finder-launched app does not have. The version is read from the package's `package.json`; the minimum is 0.15.7. Inspection (`b4 routes --json --cwd <project>`) executes the project's config and route modules, so registration is the trust decision and both the CLI and the form say so.
- **D-027 A registration allocates its loopback port once (or takes `--port`) and keeps it, so route connections have a stable origin; a start whose port is taken fails with `owned_process_conflict` and stops nothing.** The port cannot change once a route connection references the server, because managed connections carry `http://127.0.0.1:<port>` as their target and threads use that origin as their native scope.
- **D-028 Source mode (`b4 start --host 127.0.0.1 --port N` with a coordinator-built environment parsed from the env file without shell evaluation) is the default; development mode (`b4 dev --port N --env-file P`) is explicit** because hot reload can replace the runtime mid-turn. The child environment is `PATH` (the Node directory plus the system directories), `HOME`, `TMPDIR`, `LANG`, `USER`, `SHELL`, and the env-file pairs; nothing else of the coordinator's environment leaks in, and env-file values exist only in the spawn call. `envFilePath` defaults to `<project>/.env` when present. `start`, `restart`, `add`, and `inspect` block until readiness (`GET /healthz` within 90 s) or discovery finishes; a concurrent start joins the one in flight.
- **D-029 Server logs are files the child writes directly; the coordinator serves redacted tails on request and bounds the file by copy-truncate (4 MiB, keep the last 1 MiB).** Bearer values, `sk-…` keys, and `key|token|secret|password|authorization` pairs are masked before the text leaves the coordinator. Log lines are never published as events, so a chatty server cannot evict conversation events from the replay buffer; `--follow` and the GUI poll `server.logs` with the last offset.
- **D-030 `server stop` and `server restart` refuse with `owned_process_conflict` (`reason: turn_active`) while a route connection has a turn in `submitting`, `running`, or `stopping`, unless forced**, because stopping loses the in-memory run. A parked prompt is durable in `.b4` and a `reconciling` turn is already lost, so neither blocks. The CLI takes `--force`; the GUI confirms. The M5 Quit dialog builds on the same check.

## 2026-10-31

- **D-019 A B4 turn's native id is its ordinal in `GET /threads/:id/turns`.** The Agent Protocol has no run id (the thread id is the run identity). Reading the turn count before `POST /runs/stream` and naming the turn `turn-<n+1>` lets reconciliation tell "the server ran it" (the nth turn exists, with its recorded status) from "the prompt never arrived" (it does not) without ever resubmitting. When the count cannot be read the id falls back to `run-<uuid>` and reconciliation relies on the thread status alone.
- **D-020 Parked versus cancelled is decided by `GET /threads/:id/pending_interrupts`, never by the `interrupted` status alone.** B4 writes `interrupted` for both. A non-empty list is a parked prompt: the turn stays `waiting_for_user` across stream loss and coordinator restart, and the prompt is re-opened from the durable `value` under a new adapter generation. An empty list is a cancellation.
- **D-021 Permission answers go through `POST /threads/:id/resume` with B4's own decisions.** `allow_once` → `once`, `allow_always` → `always` (B4 persists the pattern itself, unlike Claude in D-018; `once` when the prompt said `allowAlways: false`), `deny` → `deny`, decline → `status: cancelled`, each echoing the prompt's `grant`. The resume response is a second SSE stream that continues the same turn and item numbering. Stop on a parked turn declines the prompt, because nothing else can end it.
- **D-022 Endpoint secrets enter through the CLI's hidden prompt and the local socket into the coordinator's credential store.** `credential add <label>` reads with `readpassphrase` (or one line from a non-TTY stdin), sends `credential.add` over the 0600 socket, and prints only the `secret:<uuid>` reference. The adapter resolves the reference on first use, sends it as `Authorization: Bearer <value>` (verbatim when the value already names a scheme) to the configured origin only, and refuses every redirect. The GUI form collects the reference, never the value. Credential labels are not persisted yet; the reference is the handle.
- **D-023 Route kinds other than `agent` are stored as `incompatible` connections with an explanation.** Only `agent()` routes take the `input.messages` shape; `workflow`, `graph`, and `chain` routes are accepted at `connection add`, inspected, and reported, never run.
- **D-015 One `claude` process per native session, started on `createSession` and kept alive between turns.** The stream-json protocol has no session API: the CLI process is the session. Starting it at creation validates the executable, the `initialize` handshake, and sign-in before a thread row exists; `--session-id <uuid>` fixes the native id up front; after a coordinator restart the next turn spawns with `--resume <uuid>`.
- **D-016 A Claude process that exits mid-turn ends that turn as `failed`.** Unlike Codex, where the app-server owns the thread and a turn's final status can be read back, nothing continues once the `claude` process is gone, so the adapter emits `turn.finished failed` with the exit status, and `reconcile` after a coordinator restart reports `failed` for a turn with no live process. The disconnect is scoped to that thread; the connection and other threads are untouched.
- **D-017 Claude history is read from the transcript JSONL Claude Code writes under `projectsDirectory`, best-effort and read-only.** The app cache stays the display source; a missing file is `native_session_missing`, never a reconstructed session.
- **D-018 `allow_always` on a Claude tool permission is sent as a plain allow.** Writing per-session rules into the user's Claude settings is out of scope; the UI still offers the button so both runtimes present the same choices.

## 2026-10-30

- **D-001 Native Swift instead of Electron + React + TypeScript.** The spec chose Electron; the owner directed pure Swift with macOS and iOS targets. An Electron shell was built, verified, and discarded the same day. Consequences: no Node coordinator, no TypeScript adapters, and the Claude integration cannot use the TypeScript Agent SDK (D-002).
- **D-002 Claude Code is driven through the CLI's stream-json stdio protocol, not the TypeScript Agent SDK.** The SDK is a thin stdio client of the same CLI; its control protocol (`control_request` / `control_response`, `initialize`, `can_use_tool`, `interrupt`) was read from the SDK source and verified by a no-inference handshake against 2.1.282. The protocol is undocumented and version-coupled, so the tested CLI version is pinned and re-diffed on upgrade. See `docs/research/2026-10-30-claude-cli-stream-protocol.md`.
- **D-003 One umbrella Swift package plus XcodeGen for the app targets.** SwiftPM cannot build `.app` bundles; Tuist is heavier than needed; hand-edited `pbxproj` files are hostile to agents. The generated `.xcodeproj` is gitignored and produced by `Scripts/generate-project.sh`.
- **D-004 The macOS app hosts the coordinator in-process when none is running; the CLI spawns the standalone executable.** Both paths use the same library, lock, and socket, so GUI and CLI always share one coordinator. A LaunchAgent via `SMAppService` replaces in-process hosting in M6 when the bundle layout exists.
- **D-005 macOS 26 and iOS 26 minimum.** Personal app on current OS versions; removes availability shims for Liquid Glass APIs.
- **D-006 App Sandbox disabled.** A sandboxed app cannot spawn the user's `claude` or `codex` executables. Local builds are signed ad hoc; Developer ID and notarization are M6.
- **D-007 GRDB for SQLite, SwiftNIO for the socket, swift-subprocess for child processes, swift-argument-parser for the CLI.** See `docs/research/2026-10-30-swift-stack.md` for versions and rationale.
- **D-008 Keychain through the file-based keychain for ad-hoc builds.** The data-protection keychain needs a provisioning profile and access group; revisit at M6 with signing. **Superseded for Developer ID builds by D-048 (2026-11-01)**; ad hoc and unsigned builds still use the file-based keychain.
- **D-009 iOS ships the full shell with an unavailable transport.** The spec defers iOS; the owner wants both targets in the repo now. The iOS app builds and renders every screen but cannot reach a coordinator until the relay is designed.
- **D-010 Codex protocol types are hand-written from the generated schema, not generated code.** Resolved in M1. `codex app-server generate-json-schema` (codex-cli 0.166.0) produces 677 definitions and 4.5 MB of JSON; the app reads a few dozen fields. `Sources/CodexAdapter/CodexProtocol.swift` types exactly those fields and keeps the rest as `JSONValue`, so a newer server adds fields without breaking decoding. The generator's output is not committed; the pinned version and command are in `docs/compatibility.md`, and the schema is regenerated and re-diffed on every Codex upgrade.
- **D-011 One `codex app-server` process per Codex connection, started lazily and kept alive while the coordinator runs.** The adapter generation increments on every restart; pending runtime requests from an older generation expire and running turns become `reconciling` with an unknown outcome until the thread is reopened. A process exit is never read as a turn outcome.
- **D-012 Approval policy and sandbox come from the user's Codex configuration.** The app does not pass `approvalPolicy: never` or widen the sandbox; it answers the resulting `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, and `item/tool/requestUserInput` requests with the user's decision, and declines request kinds it cannot present (permissions, MCP elicitation, dynamic tools, token refresh, attestation) with a valid explicit response so Codex never hangs. Amended 2026-10-31: `CodexAdapter.threadPolicy` can ask `thread/start` for a stricter policy than the configuration; the app leaves it nil, and only the opt-in live approval test sets `on-request` + `workspace-write`, because the owner's configuration (`never`, full access) can never produce an approval to verify against.
- **D-013 A thread's working directory is fixed at creation and sent with every `turn/start` and `thread/resume`.** Matches spec 3.3 (a thread is bound to one native session) and keeps the Codex sandbox root stable.
- **D-014 Long-lived protocol children use Foundation `Process` (`StreamingProcess`), one-shot commands use swift-subprocess (`CommandRunner`).** swift-subprocess scopes stdin and stdout to a closure, which does not fit a server that outlives any one call. `StreamingProcess` ignores SIGPIPE process-wide so a write to a dead child is an error, not a crash.
