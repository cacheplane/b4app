# Decision log

Material implementation decisions, newest first. The spec (`docs/roadmaps/Personal_Agent_Workspace_Technical_Spec_and_Roadmap.md`) is the requirement source; this log records deviations and choices the spec left open.

## 2026-11-03 (the packaged coordinator's migrations)

- **D-171 The packaged coordinator reads its migrations from the app it ships in, not from the build tree.** Found at the step-up live check on the Mac: joining a new account failed with "The file 0001_init.sql couldn't be opened" from a path inside the scratch checkout the Local package was built in, which had been deleted. SwiftPM's generated `Bundle.module` for `WorkspaceStorage` looks only at `<main bundle>/b4app_WorkspaceStorage.bundle` (for the coordinator, the root of `B4AppCoordinator.app`, where a signed app can hold no files) and then at the absolute build path it was compiled in, and stops the process with `fatalError` when neither exists. So every packaged coordinator depended on the build tree of the checkout that made it: the owner's apps worked only because those trees were still on disk, and on any other Mac the coordinator would have stopped at its first migration (shown live: the previous Local package, started with its build tree hidden, exited 133 with "could not load resource bundle"). The app already carries the bundle in its own `Contents/Resources` (Xcode copies it), so `StorageResources.bundle` walks up from the executable through every enclosing `.app` and uses the first `Contents/Resources/b4app_WorkspaceStorage.bundle`, falling back to `Bundle.module` only outside an app (a development build or a test). The migrator, the registry, and the PostgreSQL lookup's anchor all use it. `package.sh` now fails an app whose bundle lacks `SQL/0001_init.sql` or `SQL/registry/0001_registry.sql`.

## 2026-11-03 (a paired phone hears "already paired" before it is asked)

Numbered D-170: main's highest is D-168, and cacheplane/b4app#97 holds D-169.

- **D-170 A signed-in phone checks a pairing link's code with the hub, without spending it, before it asks anything.** Amends D-098. Live on 2026-11-03, the owner's paired iPhone scanned its own Mac's code, was asked "Pair this iPhone with the hub at <host>?", and only after Pair heard "This iPhone is already paired" (the merge's `same_account` refusal): the phone cannot know a code's account without asking the hub, and until now the only question it could ask was the redemption itself. The hub now answers `POST /v1/pairing-codes/check` (`routes/pairing.rs`, `b4hub-db` `devices::code_owner`): bearer, `ios` devices only (any other is `404`, as a phone minting is), body `{code}`, answer `{sameAccount}`, where "same account" is the merge's rule (the code's org is the caller's). The lookup is a plain `SELECT` over the codes an iPhone could redeem (unused, unexpired, a pairing code or an operator's), so the code stays exactly as redeemable as it was; an unknown, expired, or used code is `401 invalid_code`, as enroll refuses it. It counts against the per-IP sign-in finish limit (10 a minute) before the token is read, like `POST /v1/me/step-up/code`, so it is no way to probe codes, whose space is far larger than any number of minutes. On the phone, `MirrorAccount.offer(for:)` checks only when it is signed in at the link's own hub (a token is never sent to another), and any failure (an older hub's `404`, a refused code, no network) falls back to the question, so `pair` still meets whatever the hub says after the tap. The enrollment sheet shows a "Checking" face while it asks rather than a question it might take back, then either the question or "This iPhone is already paired" with Done; the after-Pair `same_account` answer now shows the same face instead of an alert. Nothing about redemption changed: only `pair` and `switchAndPair`, after a tap, ever redeem a code. Considered and declined: putting the account in the link (it would name the account to anyone who sees the QR code, and a phone still could not trust it), and checking on the phone's own state (it does not know which account a code is for). Tests: hub `enroll.rs` `a_phone_checks_a_pairing_code_without_spending_it`, `only_a_signed_in_phone_checks`, `checks_are_limited_per_client`; `auth_fixture.rs` (the `pairingCodeCheck` and `pairingCodeCheckResponse` examples, decoded by `AuthWireTests.pairingCodeCheckRoundTripsAndNeverDescribesTheCode` too); `PairLinkTests` `aPairedPhoneIsToldAtOnceThatItsOwnCodeIsPaired`, `anotherAccountsCodeIsStillAsked`, `aSignedOutPhoneOrAnotherHubIsAskedWithoutAnyCheck`, `aCheckThatFailsFallsBackToTheQuestion`; `ConnectMacTests.aPairedPhoneHearsAlreadyPairedBeforeAnyQuestion`.

## 2026-11-03 (watch refusals name their thread; a catch-up for every new watcher)

The two medium-priority findings that change the relay's wire format, from the same comparison with Phoenix (whose replies carry their join's `ref`, and whose Presence sends a joiner the full state). Numbered D-167 and D-168 after D-166. `Tests/Fixtures/sync/relay.json` gains a `watching` with `refresh` and a refused `watch` (18 frames); both suites decode it.

- **D-167 Every `error` frame answering a `watch` carries `details.threadId`, and the phone acts on it.** A refused watch was an `error` frame naming no thread, so the phone ignored every `error` frame, and a watch the hub failed to look up (a database blip, `internal_error`) or could not find yet (a thread just started on the Mac, not yet synced, `not_found`) silently left that thread without live text. The hub now adds the thread to the refusal's details (`relay::route::watch_refused`); `MirrorRelay` turns a refusal of a thread it watches into a `.gap` for it (its consumers then wait for sync, as after a `stream_gap`) and, for `internal_error` and `not_found`, sends the watch again after 2, 4, then 6 s on its clock, at most three times per fresh watch (the count resets on `watch` and on every new link). `watch_limit` is final. An older phone ignores the field, as before.
- **D-168 `watching` names the threads that gained a watcher (`refresh`), and the Mac sends their catch-up again.** The Mac sent a thread's catch-up only when the thread entered its watched set, so a second watcher of an already watched thread (another phone, or the same phone after a replaced link whose drop and re-watch reached the Mac's link task as one change) got no catch-up and started mid-reply, or showed nothing until sync. The registry now keeps, per host, the threads that gained a client watch since the host was last told (`Watchers::refresh`, bounded by the watched threads); the host's link sends `watching` when the set changed *or* such a thread was already in the set it told, with those threads in `refresh`, and clears it (`Relay::take_watching`). `HubLink.watch` treats a thread in `refresh` as newly watched. Phones already apply a `catchUp` event in place, so the watchers that had the text are unaffected. An older Mac ignores `refresh` and behaves as before.
  - **Tests.** `relay.rs`: `watching_tells_the_mac_the_full_set` now expects `refresh` for a second watcher (it pinned the old "sends nothing"), and a refused watch names its thread. `HubLinkRelayTests.refreshSendsTheCatchUpAgain`, `MirrorRelayTests.aRefusedWatchIsAGapAndIsRetried`, and both fixture round-trips.

## 2026-11-03 (draining per user, commands in flight, a quiet listener)

The medium-priority findings from the same comparison with Phoenix's socket layer and Phoenix.Tracker. Numbered D-164 to D-166 after D-163.

- **D-164 A signal listener that hears nothing for the liveness window is replaced.** A half-open connection to PostgreSQL reports no error, and sqlx 0.8.6 sets no TCP keepalive, so a listener cut off that way would wait for ever: cross-instance long-polls would fall back to their full wait and links would hear of ended sessions only at their minute's check, with nothing logged. Now every successful heartbeat also sends `pg_notify('b4hub_echo', '<instance>')` (`b4hub-db/src/signals.rs`), so every listener hears at least one signal a heartbeat; `signals::listen_loop` reads with a deadline of the last signal heard plus `alive_within()` (20 s by default), and past it drops the listener and connects again, waking every long-poll and checking every link (as after any reconnect, which now includes reconnects after an error, not only sqlx's own). Phoenix.Tracker likewise infers a dead peer from silence bounded by its heartbeats. Test seam: `InstancesState::deafen_listener`. Cost: one tiny `NOTIFY` per instance per heartbeat; with every heartbeat paused (only in tests), a listener on an otherwise idle hub reconnects every window.
- **D-165 A draining instance releases each user's claim as that user's last link on it closes, and gives a device that is not reading 2 s per write.** Before, every claim was released only after the last link of any user closed (`serve::run`), and the drain's writes waited out `DEAD_LINK` (30 s): one phone that stopped reading kept every user of the instance on `409 relocated` from the other instances for most of the shutdown wait. Now a link's teardown, when shutdown has begun and the user has no other link here, deletes that user's `user_links` row (`instances::release_user`) before writing its close; a draining instance refuses upgrades, so no new link of the user can arrive meanwhile. The flush of queued frames and the close frame use `CLOSE_GRACE` while draining. The release of everything left after the drain stays as the backstop. Phoenix's socket drainer likewise tells sockets to go and moves on rather than waiting on a slow one.
- **D-166 A link may have at most 40 commands running at once.** The read loop never waits, and every command ran on a task of its own, claimed before the rate limit and able to wait 5 s to deliver even a refusal, so a device that sent faster than it read could grow tasks without bound. Each link now holds a semaphore of `COMMANDS_IN_FLIGHT` (twice `COMMAND_BURST`) permits; a command without one is answered `rate_limited` (`retryAfterMs: 1000`) inline, uncounted, unless it is a resend of one still in flight, which attaches as before. Phoenix bounds its per-transport channels the same way (`max_channels_per_transport`). Test seam: `Relay::set_commands_in_flight_max`.
  - **Tests.** `instances.rs`: a draining instance frees a user whose link closed while another user's unread link keeps the drain going, and `b` serves them at once; a deafened listener reconnects and wakes a 20 s poll within 5 s. `relay.rs`: with a cap of 2, a third command is refused at once, a resend attaches, and an answer frees room. Each failed with its change undone.

## 2026-11-03 (sessions end on every instance; the heartbeat's own connection)

Found by reading Phoenix's socket layer and Phoenix.Tracker against the hub. Numbered D-162 and D-163: D-161 is the latest on main and an open pull request holds D-154.

- **D-162 A relay link closes when the session it was opened with ends, on whichever instance serves it.** Before, a link outlived its token: `DELETE /v1/sessions/self` deleted the token and left the link up, a link never looked its token up again, and revocation, account deletion, and a merge closed links only on the instance that took the request, which with `task_count = 2` need not be the one serving the user (HTTP requests carry no instance cookie). So a stolen token, once logged out or its device revoked, could keep sending commands to the user's Mac. Phoenix's answer is a socket `id` per user and a cluster-wide `"disconnect"` broadcast (`phoenix/lib/phoenix/socket.ex`); the hub's is the same in its own terms:
  - **The link keeps its session.** The upgrade stores the SHA-256 of the bearer token on the link (`devices::SessionKey`; never the token), and `signals::check_session` resolves it again (`devices::authenticate_session`, the same lookup as every request) and closes that registration of the link (`Relay::close_generation`, so a newer link of the device is untouched) with 4001, reason "session ended", when the token is gone, its device revoked, or it now names another device, user, or org. It runs right after registration (replacing the `devices::me` look, so a log-out between the upgrade's check and the registration is caught too) and, off the link task, with the once-a-minute `last_seen_at` write. A database error leaves the link up and is logged.
  - **Every instance hears of it.** After a log-out, revocation, account deletion, or merge commits, `signals::sessions_changed` checks the user's links here and sends `pg_notify('b4hub_links', '<org> <user> <instance>')`; every other instance checks that user's links (and, serving the user's phones but not the Mac's link, sends them a fresh `presence`). One listener connection holds both channels (`b4hub-db/src/signals.rs`, renamed from `wakes.rs`); payloads carry ids only. After the listener reconnects, every link here is checked, since requests sent meanwhile are lost. The minute's check bounds any loss.
  - **The client.** 4001 already meant "stop until it joins again"; a logged-out device signs in again with a new token and a new link. No wire change beyond the close's reason text.
- **D-163 The instance heartbeat has a connection of its own, and its lease counts from when the write was sent.** It shared the service pool (10 connections, 5 s acquire wait), so a burst of slow requests could keep it from writing for the liveness window (20 s) and let the other instances take over a healthy instance's users, which it would then close on recovery. `serve::run` now registers and heartbeats over `Db::dedicated()` (one connection, never recycled, outside the pool; the `LISTEN` uses another), and `InstancesState::record_ok` takes the instant the write was sent rather than when it returned, so the instance judges itself stale no later than the others judge it dead. Phoenix.Tracker likewise keeps slow work off its heartbeat path.
  - **Tests.** `instances.rs`: a log-out and a revocation sent to the other instance close the link (4001); the heartbeat stays fresh for two liveness windows with every pool connection held. `relay.rs`: a log-out closes the link opened with that token and leaves the Mac's; a token deleted with no request closes its link at the next minute's check. Each failed against `main` before the change.

## 2026-11-03 (long-poll wake-ups across instances)

Found while weighing Phoenix and the BEAM for the hub (which concluded the hub stays on Rust). Numbered D-161: D-151 to D-153 and D-160 are on main, and an open pull request holds D-154.

- **D-161 A push wakes long-polls on every instance through PostgreSQL `LISTEN` / `NOTIFY`; the relay stays one instance per user (D-085).** Only the link upgrade is sticky: a device's `GET /v1/changes` and `POST /v1/changes` carry no instance cookie (`Hub/API.md`, *More than one instance*), so with `task_count = 2` a phone's long-poll and the Mac's push can reach different instances, and the in-process `Notifier` left that poll asleep until its `wait` ran out (up to 25 s; the new test reproduced 20 s). Now the push route, after the commit, wakes its own instance's polls and runs `pg_notify('b4hub_changes', '<org> <instance>')` (`Hub/crates/b4hub-db/src/wakes.rs`, since D-162 `signals.rs`); every `serve` runs `notify::listen_loop`, which holds a `LISTEN` on a one-connection pool of its own (outside the service pool, so the pool stays 10) and wakes the org's polls for any announcement but its own.
  - **A hint, not the data.** The change log stays the source of truth: a lost announcement (a failed `pg_notify`, which is logged and does not fail the landed push, or a dropped listener connection) costs a poll at most its `wait`. When the listener (re)connects, sqlx listens again and every waiting poll is woken once, so a poll that slept through the gap queries again; a poll woken for nothing answers an empty page and the client asks again.
  - **Why not more.** Considered: making pulls sticky too (every client HTTP request would have to carry the instance cookies, and the Mac's pushes and the phone's polls would meet on one instance only while the user's claim held), and Phoenix.PubSub, Redis, or NATS (new infrastructure for what one Postgres channel does). `NOTIFY`'s 8,000-byte limit is irrelevant to a 73-byte payload, and its commit-time lock is taken by a separate statement after the push commits, never inside the push's transaction.
  - **Tests.** `Hub/crates/b4hub/tests/instances.rs`: a push on either instance wakes a 20 s poll on the other within 5 s, and still does after both listeners' connections are terminated. Not yet `live-tested` on two ECS tasks.

## 2026-11-03 (Apple web flow through an https callback)

- **D-160 A hub can hand Sign in with Apple's web flow back to an https URL on its site instead of a custom scheme; the hosted hubs switch once a Mac build that takes it back is out.** The other half of D-114, after D-140 pinned one scheme per hub. `Hub/crates/b4hub/src/config.rs` (`AppleCallback`), `routes/apple.rs`, `Sources/Coordinator/Accounts/AccountCommands.swift` (`appleCallback`), `Sources/WorkspaceUI/SignIn/AppleCeremony.swift` (`AppleWebCallback`).
  - **Why.** A custom scheme can be registered by any app on the Mac, so D-140 left a malicious app that claims the hub's own flavour's scheme as an accepted risk. An https callback is taken back by `ASWebAuthenticationSession` (`.https(host:path:)`, macOS 14.4 and later) only for an app the site's `apple-app-site-association` names under `webcredentials`. Both Mac apps are already listed there for their sites (`b4.run`: `com.cacheplane.b4app`; `test.b4.run`: `com.cacheplane.b4app.beta`) for passkeys, and `Scripts/package.sh` already signs them with `webcredentials:<site>`, so the site needs no change. A phished browser that follows the redirect only lands on the owner's site, where nothing redeems the handoff (it also needs the verifier).
  - **The hub.** `B4HUB_APPLE_CALLBACK_URL` is an https URL with a domain host and a path, and no port, credentials, query, or fragment. With `B4HUB_APPLE_SERVICES_ID`, exactly one of it and `B4HUB_APPLE_CALLBACK_SCHEME` is required; otherwise, or with an invalid value, the hub exits 2. A begin may carry `httpsCallback: true`; a URL hub refuses a begin without it (`400 invalid_request`, "update the app"), and a scheme hub still requires the matching `scheme`. Every web begin's answer now carries `callback`, the URL the result comes back to (`<scheme>://auth` or the configured URL), and the callback redirects to `<callback>?handoff=` or `?error=`. The wire change is additive: `auth.json`, `AuthWireTests`, and `auth_fixture` carry both new fields.
  - **The Mac.** The coordinator sends `httpsCallback: true` on all three web begins (sign-in, Connect Apple ID, the step-up), takes the answer's `callback` only as its flavour's `<scheme>://auth` or an https URL with a path on its own `Flavor.siteDomain` (anything else is `protocol_invalid` and keeps no ceremony), and falls back to the scheme when a hub older than this names none. `account.appleStart`'s result (and the link's and step-up's) carries `callback` in place of `callbackScheme`; the app maps it to the session's custom-scheme or https wait.
  - **Rollout.** The hosted hubs keep `B4HUB_APPLE_CALLBACK_SCHEME`, so merging this changes nothing they do. Once a Mac build with this ships and Continue with Apple through an https callback passes on the test hub (set `B4HUB_APPLE_CALLBACK_URL=https://test.b4.run/app/auth/apple` there in place of the scheme), switch `Infra/taskdefs/hub.json.tpl` and `Infra/scripts/deploy.sh` to the URL per environment (`https://b4.run/app/auth/apple` for prod). From then on an older Mac app is refused with "update the app". Chart 0.4.0 adds `hub.apple.callbackUrl`. *Amended 2026-11-03:* the Beta Mac build from `2338c2e` was installed and the test hub switched to `B4HUB_APPLE_CALLBACK_URL=https://test.b4.run/app/auth/apple` (`deploy.sh` and `ecs.tf` now template the setting's name per environment, `apple_callback_name` and `apple_callback_value`, so neither hub carries the other's variable); prod stays on `b4app`. An older Beta Mac app is now refused at the test hub's web begin. *Amended 2026-11-03, later:* after the https callback passed live on the test hub (`docs/verification.md`), prod switched too, to `B4HUB_APPLE_CALLBACK_URL=https://b4.run/app/auth/apple`, once the prod Mac app on the owner's Mac was replaced with a notarized build from main `b8f1202` (no public `mac-v*` release yet: `cacheplane/homebrew-tap` does not exist). Both hosted hubs now hand back only through an https URL, so D-140's accepted risk (another app claiming the flavour's scheme) no longer applies to them; a prod Mac app older than D-160 is refused at Apple's web begin with "update the app".

## 2026-11-03 (a cancelled BEGIN no longer leaks a transaction)

Found by the APNs slice's iPhone gate (live gate 2) on the test hub. Numbered D-153: open pull requests hold up to D-152.

- **D-153 Every transaction on the hub's pool begins in a task of its own, so a request dropped while Postgres answers its `BEGIN` cannot leave the connection inside a transaction.** sqlx 0.8.6 counts a transaction (`transaction_depth`) only once Postgres has answered the `BEGIN`; a future dropped while it waits for that answer queues no `ROLLBACK`, because the depth is still 0, and the connection goes back to the pool inside a transaction sqlx does not know about. Every later user then runs inside it. On the test hub on 2026-11-03 a phone suspended by iOS dropped a pull while `read_tx` opened its `READ ONLY` transaction; at 05:46:37 UTC the instance heartbeat's `UPDATE` on that connection failed as read-only, and from then on the connection answered "current transaction is aborted" to whoever borrowed it (readiness, heartbeats, presence, and `/v1/changes`, which is why the phone's read retried), until the task was restarted. The new iPhone build's background wakes, which suspend mid-request, made the window reachable; prod logged none. `Db::begin` (`Hub/crates/b4hub-db/src/tenant.rs`) spawns the `BEGIN` (plain or the read transaction's custom statement) on the runtime and awaits it: a dropped caller abandons only the join handle, the task finishes the `BEGIN`, and the transaction it returns is dropped like any other, which sqlx rolls back before the connection is reused. `tenant_tx`, `read_tx`, `untenanted_tx`, and the two direct pool begins in `instances.rs` and `orgs.rs` go through it; savepoints inside an open transaction and the migration's own connection were already consistent after a cancel. A panic in the task is resumed in the caller; a cancelled task (only at runtime shutdown) is `PoolClosed`. `tests/cancel.rs` polls each begin once on a single-connection pool and drops it there, then checks the connection is outside any transaction (`now()` changes between statements, `transaction_read_only` is off); all three failed before the change. Cost: one task spawn per transaction, a few microseconds against a database round trip; a caller that has gone away no longer stops its `BEGIN`, so that one statement and its rollback still run.

## 2026-11-02 (step-up for account changes)

Closes D-113. Built on `blove/xenodochial-morse-e3bed8`. Numbered D-150: D-121 to D-140 are taken and D-141 onward is reserved for the APNs slice.

- **D-150 Adding or removing a sign-in method and deleting the account need a step-up grant: a passkey or Apple assertion of the same user, made on the same device within two minutes, used once.** Resolves D-113 (and the add-passkey case D-098 accepted).
  - **What it gates.** `POST /v1/me/passkeys/begin`, `POST /v1/me/apple` (linking an Apple ID is adding a sign-in method too: without it a thief with a token links their own Apple ID and keeps a way in after the token is revoked), `DELETE /v1/me/identities/{id}`, and `DELETE /v1/me`. An add is gated at its begin: the finish needs the begin's ceremony, which now also records the device and is refused (`ceremony_expired`) on any other. Each refusal that needs no grant comes first and spends nothing: `apple_linked` at the link begin, `not_found` for an id that is not the caller's, `last_identity`, and `shared_org`.
  - **How it is earned.** New routes behind the device token: `POST /v1/me/step-up/passkey/begin` (assertion options whose `allowCredentials` are the user's passkeys, user verification required) and `.../finish`; `POST /v1/me/step-up/apple` (the link begin's body: empty natively, the verifier hash and scheme on the web), `.../apple/native` (the identity token only: no code is exchanged, so Apple keeps no new grant), and `.../apple/handoff` (the web flow, through the same callback). Each ceremony records the user and the device that began it and finishes only for both; an Apple assertion counts only when its `sub` is the account's own Apple ID. A finish answers `{"stepUp": "<grant>", "expiresAt": "…"}`.
  - **The grant.** A 256-bit random token in a new table, `step_up_grants` (migration `0014_step_up.sql`; 0012 and 0013 are M8f's), stored as its SHA-256 with the org, user, device, method, and an expiry two minutes on. Not a ceremony row: a ceremony id is kept in clear, and the grant is a bearer secret, so it is hashed like a device token. It goes in a `B4-Step-Up` header (so `DELETE` stays bodiless) and is taken once, by one conditional `UPDATE` matching hash, user, device, unexpired, and unused. One grant covers one change, not a window: the UI asks right before each change, so a window buys nothing and would let a second change ride on the first. A change that fails after taking it (a failed Apple revoke, `500`) needs a new assertion. Pruning deletes expired grants with the ceremonies.
  - **The refusal.** A missing, unknown, expired, spent, or another device's grant is `403 step_up_required` with `details.methods`, the kinds the account can assert with (`passkey`, `apple`), so the client knows which sheet to show. The cases are indistinguishable, as for ceremonies.
  - **An account with no sign-in method** (operator-enrolled, never signed in) has nothing to assert with, so it adds its first method, and deletes itself, on the token alone, as before; D-113's risk stays accepted for that case only. Every account made by signing in has a method from its first moment.
  - **Clients.** The grant never leaves the process that earned it. On the Mac the assertion (or the Apple handoff) goes to the coordinator inside the change's own command (`account.addPasskeyBegin`, `account.appleLinkStart`, `account.removeIdentity`, `account.delete` take `stepUp`), which finishes the step-up and makes the change in one command; the verifier of a step-up's Apple web flow stays in the coordinator (`account.stepUpAppleStart`). The phone's `MirrorAccount` does the same in process. Settings → Account confirms with a passkey when the account has one, else with Apple; so an Apple-only account adds its first passkey after an Apple assertion. A closed sheet changes nothing and shows nothing; `step_up_required` (a grant the hub refused, or a method another device added meanwhile) re-reads the methods and shows one line.

## 2026-11-02 (M8f APNs, real notifications on the iPhone)

Design: `docs/superpowers/specs/2026-11-02-m8f-apns-design.md`. Plan: `docs/superpowers/plans/2026-11-02-m8f-apns.md`. Built on `blove/m8f-apns`, stacked on `blove/m8f-attention`. Numbers start at D-141 because main and the open pull requests reach D-140.

- **D-141 The `apns` sender: HTTP/2 through `reqwest`, one ES256 provider token reused for 50 minutes.** `ApnsSender` in `Hub/crates/b4hub/src/push.rs` replaces the refusing stub of D-123. Each `push_tokens` row's `environment` picks the host (`sandbox` to `api.sandbox.push.apple.com`, `production` to `api.push.apple.com`); each host has one `reqwest` client (`http2` feature, ALPN `h2`, 10 s connect and 15 s request timeouts, no redirects, HTTP/2 pings every 60 s and no pool idle timeout, so the connection stays open between sends). The provider token is an ES256 JWT (`kid` the key id, `iss` the team id, `iat`) signed with the `.p8` through the `jsonwebtoken` the sign-in already uses, minted once and reused for 50 minutes (Apple refuses one older than an hour and rate-limits minting more often than every 20 minutes); a 403 `ExpiredProviderToken` or `InvalidProviderToken` re-mints (unless another send already replaced it) and retries once. Headers: `apns-topic` is the token row's `bundle_id` (one key serves every flavour and both hubs), `apns-push-type` `alert` with `apns-priority` 10 and a 4 hour `apns-expiration` for a notification, `background` with priority 5 and 15 minutes for a withdrawal (past that the phone's own backstop, D-146, has done the work), and `apns-collapse-id` is the notification's key (D-142) on alerts, so a resend replaces rather than stacks. Apple's answers: 200 delivered; 410, 400 `BadDeviceToken`, and 400 `DeviceTokenNotForTopic` delete that device's `push_tokens` row (`b4hub_db::push::delete_token(org, device, token)`, which deletes only the token Apple refused, so a newer one the phone saved while the send was in flight survives); 429, 5xx, and a transport failure retry once after 500 ms; anything else is logged with Apple's `reason`, the `apns-id`, the device id, and the key, and dropped, so delivery stays at most once (D-121). Configuration: `B4HUB_PUSH_SENDER=apns` with `B4HUB_APNS_KEY_ID`, `B4HUB_APNS_TEAM_ID`, and `B4HUB_APNS_PRIVATE_KEY` (each also `_FILE`, the sign-in secrets' pattern); `serve` parses the key and signs once before it listens, and refuses to start on a missing or bad value, naming the variable and never echoing the key. A token, the key, or a JWT never reaches a log line, a result, or a `Debug` (the authorization header is marked sensitive; a transport error keeps only its kind, since `reqwest`'s error would name the URL, which holds the token). Compose passes `B4HUB_PUSH_SENDER` through (default `spool`), mounts `B4HUB_APNS_KEY_HOST_PATH` read-only at `/run/secrets/apns.p8`, and sets `B4HUB_APNS_PRIVATE_KEY_FILE` to it. Cost: `reqwest` gains `http2` (`h2` 0.4.20, `fnv`, `tokio-util` in `Cargo.lock`); a key that is permanently invalid after start (revoked in the portal) re-mints on every send and logs the failure, because the sender cannot tell it from a stale token; the admin container gets no sender.
- **D-142 Every notification has a key, `request:<id>` or `turn:<id>`, and the payload carries it with the badge.** `Hub/crates/b4hub-core/src/push.rs` (`key`, `payload`, `withdrawal_payload`), `Tests/Fixtures/sync/push.json` (decoded by both languages). The alert payload of D-124 gains `"key"` and `aps.badge`; the spool writes the same payload, so the Simulator path needs no APNs. The key is also the collapse id (D-141) and what a withdrawal names (D-143), and the app reads it from `userInfo` (`ThreadLink.key(fromNotification:)`), so a notification delivered before this slice (no key) can never be judged or withdrawn: it stays until the owner dismisses it. Why a key rather than the request id alone: a request and a turn can share nothing, and the phone must tell which table to ask. Cost: a key over Apple's 64-byte collapse-id limit is sent without one (UUID keys are far below it).
- **D-143 A notification is withdrawn when what it announced is over, once, in the push transaction that ends it.** Migration `0013_push_withdrawal.sql` adds `notifications_sent.withdrawn_at` (`0012_push.sql` is not edited, since databases may already hold it), a partial index on the outstanding rows of a thread, and `(org_id, user_id, "threadId")` indexes on `turns` and `runtimeRequests` for the badge. What ends a notification: a `request:` whose request is no longer `pending` (answered or expired) or was deleted; a `turn:` whose thread's `readTurnId` now names that turn or a later one (by `createdAt`, ties by id), read on the Mac or the phone; and, for either kind, a thread that was deleted (`deleted_at`, or the owner's `userDeletedAt` of D-119, which also never notifies, so a deleted thread cannot send an alert that leads nowhere). Archiving a thread ends none: its approval is still waiting (the phone's backstop and the hub's rules agree on this, a review ruling), and archiving only takes the thread out of the badge and the list. `withdrawn_at` is set whether or not any phone has a token, so each notification is withdrawn at most once; one that ended in the same push that would have sent it is neither sent nor withdrawn, which includes a turn whose `outcome` lands in a later batch than the `readTurnId` that already covers it (the read rule runs for the thread of every turn that would notify, not only for the threads the push changed). The withdrawal goes to the same phones as the alert, the phone that pushed included (its own read clears its own), as a `background` push `{"aps": {"content-available": 1}, "withdraw": ["request:<id>", ...]}` with no alert, sound, or badge, which Apple requires of a background push; the app removes the delivered notifications whose key is listed, then pulls. Cost: a withdrawal naming roughly 90 or more keys exceeds Apple's 4 KB payload, and the backstop covers it; a ledger row pruned (D-121) before it was withdrawn is judged by the backstop alone; deleting a turn does not withdraw its notification, though deleting its request does.
- **D-144 The badge is the number of threads that need the owner, computed on the hub for every alert and on the phone after every sync.** Non-archived, non-deleted threads whose band is needs input or unread (pinned threads count by their band; deleted turns and requests do not count). The hub's rule is SQL in `b4hub-db` (`bands`, `needs_you_count`), following `Attention.band(of:)` and checked by a database test against the shared `Tests/Fixtures/sync/attention.json`, so there is still one rule per language. The phone computes it from the mirror (`MirrorStore.needsYouCount()`) and sets it with `setBadgeCount`. A withdrawal carries no badge (Apple forbids one on it), so the badge changes on the phone only by the wake's refresh or the next sync. Cost: the count reads every live thread of the user with its turns and requests under the push transaction, which the two new indexes bound.
- **D-145 The push environment comes from the build, and a token belongs to one device.** `PushEnvironment.resolve(isSimulator:profile:)` in `WorkspaceMirror` (pure and unit-tested; the app passes `targetEnvironment(simulator)` and the bytes of `embedded.mobileprovision`). The Simulator is `sandbox`. On a device, an embedded profile's `aps-environment` decides (`development` is sent as `sandbox`, `production` as `production`); a device build with no profile is a TestFlight or App Store build, whose profile Apple strips, and is `production`; a profile whose entitlement cannot be read is `production` too. This replaces D-122's guess from `#if DEBUG`, which cannot tell a development build on a device (sandbox) from a TestFlight build (production) when both are Release builds, and which the Simulator always needs as sandbox. The token is saved by `save_token`, which also removes it from any other device row of the org: a phone that re-enrolled while the hub still holds its old device would otherwise be told everything twice. Cost: the profile is a CMS envelope read by finding the XML between `<?xml` and `</plist>`, not by verifying its signature; the contents only choose a host, and a wrong choice is refused by Apple as `BadDeviceToken`, which deletes the row (D-141) until the phone registers again.
- **D-146 The phone backstop removes what the hub says is over, and judges only what it has already pulled.** `MirrorStore.stillOutstanding(keys:)` (`Sources/WorkspaceMirror/MirrorNotifications.swift`; no `UserNotifications` in the library) answers from the mirror: a `request:` is outstanding while the request exists, is `pending`, and its thread is not deleted; a `turn:` while the turn exists, its thread is not deleted, and the thread's `readTurnId` is unset or names an earlier turn (a read turn the mirror does not hold leaves it up); an unknown id, another prefix, or a malformed key is not outstanding. `MirrorHost` (`Apps/iOS/B4App/MirrorHost.swift`) runs it after every successful sync turn and every published batch, at most once a second (a streaming reply is one run at the end of the interval), and removes the delivered notifications that have ended, then sets the badge (D-144). Because an unknown id reads as ended, it judges only notifications delivered before a pull that has since been applied (`judgedThrough`, advanced when a turn of the loop that began after the previous report succeeds), so a notification whose row is not pulled yet is never removed by mistake. A push wake and a foreground both reach it, so a withdrawal that was delayed, dropped (Low Power Mode, an app swiped away), or never sent (D-148) is cleared by the next sync; signing out removes every delivered notification and the badge. Parked: when more than 1000 changes are outstanding the pull spans several pages and a judged notification's row can still be on a later page, so the backstop may remove it early during that catch-up (the badge is unaffected); closing that needs `MirrorSync` to report when it has caught up. An account-to-account switch heals itself through the same judging.
- **D-147 A background wake is capped, and nothing reads the store once the sync is parked.** `didReceiveRemoteNotification` removes the keys a withdrawal names first (`MirrorHost.withdraw(keys:)`, which never touches the mirror, because it runs before the wake's background task begins), then `backgroundRefresh` resumes the sync. The resume waits for a queued suspend of the sync loop at most 3 seconds (a race, not a cancel), so the system's completion handler is always called well inside iOS's time budget, an M8f review finding; a suspend that a later resume has overtaken does nothing when its turn comes (serial numbers), so a late suspend cannot park the loop under the wake. D-127's rule gets its consequence for the backstop: the mirror lives in the App Group, and a read after the loop parked can end the app with `0xdead10cc`, so a throttled reconcile is cancelled the moment a suspend is queued, never starts while the loop is parked, and stays owed; the suspend task runs the owed reconcile inside its own background assertion before releasing it. Parked (minor): a suspend that was overtaken could, in the rare case the loop was not idle, run the owed reconcile after its assertion expired (about 30 s); skipping that tail when a later resume has overtaken it is left to a follow-up.
- **D-148 The Simulator cannot be woken by a real APNs push, so the withdrawal push is proved on a device and the Simulator relies on the backstop.** Found in the live gate: with the Compose hub sending through APNs sandbox, Apple accepted every alert and withdrawal (200), the banner and badge arrived, but SpringBoard logged "Content-available push notifications are only supported on-device for iOS, watchOS, and tvOS" for both the alert's `content-available` and the withdrawal (`pushType Background`, priority 5). `xcrun simctl push` can launch a Simulator app for a background fetch (D-128), but a push through Apple's servers cannot, so on the Simulator the approval stays in Notification Center until the app is foregrounded, when the backstop removes it (1.6 to 2.5 s later in the gate). This is a limit of the Simulator, not a defect to fix: the design's exit allows exactly this outcome, and the device gate (a withdrawal push waking the app on the iPhone) is `blocked` on D-149. Nothing in the app changed because of it.
- **D-149 The hosted hubs get the APNs secrets in two steps.** `Infra/modules/hub/secrets.tf` creates `b4hub/apns-key-id`, `b4hub/apns-team-id`, and `b4hub/apns-private-key` empty, and `Infra/taskdefs/hub.json.tpl` carries them, with `B4HUB_PUSH_SENDER=apns`, behind `INCLUDE_APNS_SECRETS` in `Infra/taskdefs/features.env` (render and deploy scripts, bats and `terraform test` coverage). ECS refuses to start a task whose secret has no value, and `features.env` drives the test and the prod deploy alike, so (1) this slice's PR ships `INCLUDE_APNS_SECRETS=0`: the secrets exist, the hub that deploys uses no sender, and nothing breaks (with the flag off the rendered task definition is byte-identical to before); (2) the owner applies the Terraform and puts the three values in both accounts (`Infra/README.md`, runbook 3a, with his AWS credentials), then a one-line follow-up sets the flag to 1, test before prod. The flag adds the secrets to the serving task only (the migrate and admin tasks send no pushes). The key is the team-scoped APNs key `34GWB4MSB5` for sandbox and production, kept in `~/.b4app/signing/`, so one key serves every flavour and both hubs. Cost: until step 2 the hosted hubs deliver nothing, and the iPhone gate waits for it.

## 2026-11-02 (M8f, attention on the phone)

Design: `docs/superpowers/specs/2026-10-31-m8b-remote-workspace-design.md` ("M8f, attention on the phone" and "Constraints"). Plan: `docs/superpowers/plans/2026-11-02-m8f-attention.md`. Built on `blove/m8f-attention`.

- **D-121 Which changes notify, and only once.** `Hub/crates/b4hub-core/src/push.rs` (the rules), `Hub/crates/b4hub-db/src/push.rs` (detection), `Tests/Fixtures/sync/push.json` (the cases).
  - **Requests.** A `runtimeRequests` row whose `state` is `pending` after a push notifies. `command_approval`, `file_change_approval`, `tool_permission`, `unknown`, and any kind this hub does not know say "Waiting for your approval"; `user_question` and `elicitation` say "Has a question for you".
  - **Turns.** A `turns` row whose `status` is `terminal` notifies when its `outcome` is `completed` ("Replied") or `failed` ("Turn failed"). `cancelled` never notifies, because Brian stopped it himself. A terminal turn whose outcome has not arrived yet waits for the push that sets it, so the two columns may land in different batches.
  - **Age.** A turn notifies only when its `updatedAt` is within 10 minutes of the hub's clock, so a Mac's first join, a rejoin, or a resync that uploads history does not send a "Replied" for every old turn. A pending request has no age limit: it is still waiting for Brian.

The row is written whether or not a sender is configured or any phone has a token, which makes delivery at most once. Ledger rows older than the retention window are pruned with the change log; a request still pending after that could notify a second time.
  - **Who.** The user's `ios` devices that are not revoked, hold a session (an unrevoked device token; a log-out under D-108 ends it and keeps the device), have a push token, and are not the device that pushed.
  - **Why.** The lock screen is public, so the body is a fixed phrase and the title is the thread's title only (cut to 100 characters; `Untitled thread` when empty), never transcript text, command text, or paths.
- **D-122 The phone's push token.** `POST /v1/devices/self/push-token` with `{"token", "environment", "bundleId"}`: `ios` devices only (403 `forbidden` otherwise), a 32 to 512 character hex token, `sandbox` or `production`, and a reverse-DNS bundle id; 204. One row per device in `push_tokens`, replaced on each call. The bundle id comes from the phone, so the hub needs no per-flavour setting and a spool file names the right app. The phone sends its token on every `didRegisterForRemoteNotifications` while signed in and after each sign-in (a passkey, Apple, an enrollment code, or a pairing), keeps it in memory only, and never logs it; `environment` is `sandbox` in Debug builds and `production` otherwise. (Superseded by D-145: the environment comes from the build's provisioning profile.) The hub never logs it either (`Notification`'s `Debug` redacts it). A log-out does not withdraw the token, but a phone without a session is not notified (D-121), and the phone also unregisters from remote notifications on log-out, so a log-out that never reached the hub does not leave thread titles arriving on its lock screen. Deleting an account, or merging a phone-only account, removes its `push_tokens` and `notifications_sent` rows.
- **D-123 The sender is swappable and never pretends.** `Hub/crates/b4hub/src/push.rs`. `B4HUB_PUSH_SENDER` is `none` (the default), `spool` (needs `B4HUB_PUSH_SPOOL_DIR`), or `apns`, which `serve` refused at start with "APNs delivery is not built yet (the deploy slice)" until D-141. Delivery runs in one spawned task after the push commits, so the response never waits on it; a failure is logged with the device id and reason only. The spool writes each payload to a hidden `.tmp` file and renames it to `<ms>-<uuid>.apns`, so a watcher never reads half a file; `Scripts/sim-push.sh` feeds those files to `xcrun simctl push` (`B4APP_SIM_DEVICE` picks the Simulator when several are booted). Compose bind-mounts `Hub/push-spool` (or `B4HUB_PUSH_SPOOL_HOST_DIR`).
- **D-124 The payload carries the thread id, not a link.** `{"aps": {"alert": {"title", "body"}, "sound": "default", "content-available": 1, "thread-id"}, "threadId", "reason"}`; the spool adds `Simulator Target Bundle`. The app builds `<its own scheme>://thread/<id>` (`ThreadLink`) and sends a notification tap and a widget row through the one path that `onOpenURL` uses (`MirrorHost.handle(url:)`), so the hub never needs to know a flavour's URL scheme. A thread link on a signed-out phone is swallowed, never handed to sign-in or pairing. A request that arrives before the model is connected (a cold launch from a tap) is held and opened once the first snapshot is in, without delaying the event stream, and the iPhone moves to the thread column even when the request predates the view. In the foreground a notification shows unless its thread is open and on screen.

## 2026-11-02 (deleting threads)

- **D-119 Deleting a thread hides it everywhere and keeps its data.** The owner deletes a thread for privacy: delete means "do not display and do not use for personal memory", not erase. Design: `docs/superpowers/specs/2026-11-02-delete-threads-design.md`.
  - **The mark.** A new synced column, `threads.userDeletedAt` (an ISO timestamp), set once and never cleared. It is phone-writable and merges by clock like the thread's other phone-writable columns (Mac migration `0008_thread_delete`, which also redefines the change trigger's clocked list; hub `0011_thread_delete`; mirror schema version 5). It is a column update, not a row delete: the Mac and the hub keep the thread, its turns, items and drafts, as the owner's rule requires (the hub never hard-deletes data unless a full delete is asked for, built later).
  - **Hidden everywhere.** `thread.list` on the Mac and the phone leaves deleted threads out, archived or not, so search, project groups and attention follow. `thread.read`, `thread.update`, `thread.reconcile` and every turn command answer `not_found` for one. Events about a deleted thread (a late turn) still update its rows but are not published. The apps drop it from the list and close it if open, discarding the unsent text, and ignore anything that arrives about it later.
  - **Naming.** `userDeletedAt`, not `deletedAt`: the soft-delete work (D-089) adds a hub-internal `deleted_at` with the opposite meaning for snapshots (left out), while a `userDeletedAt` thread is still served so devices learn it is gone.
  - **No undo.** The confirmation says so. Undo can't be honest once the runtime has deleted its side, and a restored thread could never be continued. There is no "Recently deleted" list.
  - **The confirmation.** `Delete "<title>"?` with "It's removed from this app and from Codex / Claude Code / the B4 server. You can't undo this." For a disabled connection, the runtime is not named. While a turn runs, it adds "Its running turn will be stopped." Mac: Delete… in the row's context menu and in the thread's toolbar. iPhone: a swipe and the thread's "…" menu.
- **D-120 The runtime's copy is deleted where the runtime can, and retried until it is.** The owner: "IF their api/cli supports deletion, we do it and honor it as best as we can."
  - **Per runtime.** Codex: `thread/delete { threadId }`. B4: `DELETE /threads/:id`. Claude Code has no delete command. Like the Claude desktop app, b4app removes the session's transcript `<sessionId>.jsonl` and its subagent folder `<sessionId>/` from the one project folder under `$CLAUDE_CONFIG_DIR/projects` (else `~/.claude/projects`; Claude's auth status names it when known). An id that isn't `^[A-Za-z0-9_-]+$` is refused, and nothing outside that session is touched.
  - **Outcomes.** These are recorded in a local-only table, `threadDeletes`:
    - **Done.** The runtime deleted it, or says it's gone; a B4 `404` counts.
    - **Unsupported, which is final.** Codex method-not-found, a B4 `405`, a disabled or missing connection, or a connection now signed in as another identity.
    - **Waiting.** Any thrown error. It is retried after 30 seconds, doubling to at most an hour, by a sweep at coordinator start and every 60 seconds.
  - **Running turns and the phone.** `thread.delete` answers as soon as the thread is marked and announced; the rest runs in the background, in the same step the sweep runs for a delete pulled from the phone. That step first interrupts a running turn through its adapter and waits up to 10 seconds. A turn still unresolved after that, or one already `reconciling` (say, after a restart), is ended locally as cancelled, so a deleted thread never stays in the Quit dialog or keeps its folder locked. Then the runtime's copy is deleted.
  - **Diagnostics** counts deletes waiting and not supported, by runtime, without thread titles.

- **D-094 The pre-flavour install is adopted only by an explicit local flavour, inside `Coordinator.start` under the singleton lock; open the app before the CLI.** `Sources/Coordinator/Accounts/LegacyAdoption.swift`.   - *Limit (final review):* the pre-sign-in build and a current prod build share the app name, data directory, and LaunchAgent label, so adoption cannot tell them apart; the only guard is that `b4app`'s hub link is loopback. A prod install joined to the owner's local hub would be adopted (and its plist retired) by a local build started on the same Mac.
- **D-095 Account deletion refuses a member of a shared org, and revokes at Apple before it deletes.** `Hub/crates/b4hub-db/src/accounts.rs`, `Hub/crates/b4hub/src/routes/me.rs`. `DELETE /v1/me` deletes only the owner of a personal org; anyone else (an operator-seeded user such as `blove` in `cacheplane`) gets `409 shared_org` before anything is revoked, because shared orgs are not designed yet and their devices own rows other members read. Every sealed Apple refresh token is opened first, then each is revoked; a token that does not open, a failed revoke, or a hub without Apple configured fails the request with `500` and deletes nothing, so it can be retried. The delete is one transaction that locks the user row and reads the tokens again; an Apple ID linked meanwhile is revoked and the delete retried, up to three rounds. A rotated `B4HUB_SECRET_KEY` or a corrupt row therefore leaves an account undeletable until an operator steps in. - **D-096 A sign-in reuses a device of the same user, on the same platform, not revoked, named by `deviceId` or `candidateDeviceIds`; a hub without `candidateDeviceIds` refuses it, so the hub is upgraded first.** `accounts::issue_session_reusing`, `DeviceRequest`. The platform must match because it decides write rights, so a phone never takes over a Mac's device id. Reuse renames the device and deletes its earlier tokens, which also closes a session a failed log-out left open. `candidateDeviceIds` (up to 32 UUIDs; `deviceId` counts first, duplicates dropped) is for a client that cannot know which account a passkey or Apple ID belongs to: the Mac offers the device of every registry row for this hub, most recently signed in first and UUIDs only (one malformed id would make the hub refuse the sign-in), and the phone the devices it remembers for this hub (D-108). An older hub refuses the unknown field with `400 invalid_request` (`deny_unknown_fields`), so a Mac that knows several accounts cannot sign in to it; a Mac that knows one sends only `deviceId`. Candidates only ever match devices of the code's own user: on a merge, the token's account's devices are never reused (they are deleted with it). An older hub refuses the new fields as it does on sign-in, so the hub is upgraded first.
  - *Amended (final review, X3-2):* a pairing code (minted by a Mac) is redeemable only as `ios`; any other platform gets `invalid_code` and the code stays usable, so a code holder who knows the Mac's device id cannot take over that device through `candidateDeviceIds`. `devices::redeem_reusing`, test `a_pairing_code_pairs_only_a_phone`.

A bad code, checked first (`invalid_code` whatever the token), or a refusal changes nothing and leaves the code redeemable. `409 merge_refused` carries `details.reason`: `same_account` (the token's org is the code's, whichever user), `shared_org`, or `has_mac` (the account has or ever had a `macos` device, revoked included); it is absent when the hub cannot say. ## 2026-11-02 (M8e Part B)

Design `docs/superpowers/specs/2026-11-02-m8e-part-b-relay-routing-design.md`, reviewed by the M8c build session; built on `blove/m8e-relay-multi-instance`. Numbered D-085 and D-086 because the open sign-in pull request claims D-081 to D-084; re-checked at merge.

- **D-085 The relay runs on more than one hub instance by serving every link of one user on one instance, never by forwarding frames between instances; amends D-057 ("One replica").** Hub: `Hub/crates/b4hub-db/src/instances.rs` (migration `0008_instances.sql`), `Hub/crates/b4hub/src/instances.rs`, `relay/link.rs`; clients: `Sources/WorkspaceSync/RelayLink.swift`; reference `Hub/API.md` "More than one instance".
  - **Claim.** Each `serve` registers a UUIDv7 in `hub_instances` and writes a heartbeat every `B4HUB_HEARTBEAT_MS` (default 5000); four heartbeats (20 s) without one is dead. `user_links` names the instance serving a user. The link upgrade claims the user after the revocation check and before the socket exists, with one upsert that keeps a live owner's claim and takes over a dead one's; another live owner means `409 relocated` (`details.instanceId`), no socket, no `hello`, nothing in presence or `watching`. The liveness window is a parameter (four heartbeats) rather than the design's literal 20 s, so the fixture tests run with a 200 ms heartbeat; every instance of one hub must run the same cadence.
  - **Cookie, amended from the design.** Every instance sets `Set-Cookie: b4hub-instance=<its id>` on `/readyz` and on an accepted upgrade, and the ALB's application-cookie stickiness (`b4hub-instance`, one hour, on only when `task_count > 1`) takes it from there. AWS documents that the ALB answers an application cookie with its own `AWSALBAPP-*` cookie encoding the target that sent it, routes only a request carrying both, and does not route by the application cookie's value. So the design's `Set-Cookie: b4hub-instance=<owner>` on the `409` would bind the device to the instance that refused it, and a `Cookie: b4hub-instance=<owner>` alone reaches nobody in particular. The `409` therefore carries no cookie; the device keeps the cookies of its last successful upgrade (both of them, behind an ALB), replays them, drops them on a `409`, and retries at once up to three times (landing by round robin), then backs off. Once it reaches the owner, the owner's `101` gives it cookies that make later reconnects sticky. The device does not read `instanceId` (`URLSessionWebSocketTask` does not expose a refused upgrade's body, and a device cannot address an instance).
  - **Drain.** On SIGTERM the instance answers every held command `device_offline` first (up to 1 s, a quarter of the wait at most), then closes its links, each writing what is queued before its 1001, and after the drain deletes its claims and its instance row so its users are claimed at once elsewhere; the whole sequence, release included, stays within `B4HUB_SHUTDOWN_WAIT_MS`. The design listed "close links" before "answer holds"; answers queued after a link closed would be lost, so the order is reversed.
  - **Rolling deploys on ECS.** The ALB deregisters an old task and waits `deregistration_delay` before ECS sends SIGTERM; meanwhile the task still heartbeats and holds its claims but gets no new connections, so a user re-linking then reaches a new task and is refused `409 relocated` with nowhere to go, and at the end of a long delay the ALB may cut the old task's WebSockets before the hub's drain runs. With `task_count > 1` the delay is therefore 5 s (60 s with one task): the real sequence is deregister, 5 s, SIGTERM, holds answered, links closed 1001, claims released, and the new task claims each user on relink. A device that re-links inside the 5 s spends its three immediate retries and backs off past the window.
  - **Split guard.** An instance whose heartbeat failed for the window may have lost users to another instance while their links stayed open here; when its heartbeat succeeds again it closes (1001) the links of every user whose claim another instance holds, so a user's links are split for at most one heartbeat after recovery.
  - **Maintenance (D-074).** While on, a client's `turn.send`, `thread.start`, and `request.respond` over the link get a `maintenance` reply with the HTTP guard's message and are not forwarded; `turn.lookup`, `turn.interrupt`, and `watch` continue.
  - **Why.** Forwarding frames would need an internal transport for 256 KiB frames and high-rate deltas and would split the in-flight map; routing by user leaves `route.rs` as it was and buys what the "next" tier needs: rolling deploys with no outage and zone redundancy. Accepted edges: per-instance rate limits, in-flight state, holds lost on a crash, and the pending-thread map (a takeover between a phone's `thread.start` and the thread row's sync answers `not_found` for seconds). A refused (`409`) upgrade still counts against the per-device upgrade limit of the instance that refused it (10 a minute): fine with two tasks, where a device rarely misses more than a few times, tighter with three or more. Outside ECS (Helm, Compose) failing readiness does not close WebSockets, so an instance whose heartbeat is stale but which is still running keeps its links until its heartbeat recovers and the split guard closes the ones it lost; only on ECS does a failed health check replace the task.

- **D-086 `/readyz` exercises the relay through an in-process probe principal and reports a stale heartbeat.** `Hub/crates/b4hub/src/relay/link.rs` (`probe`), `routes/health.rs`.
  - **Probe.** The link task is generic over a `LinkSocket`; the probe runs it over an in-memory socket pair as `Identity::probe()` (a client with nil ids), which `Relay::register` hands a handle without entering it in the registry, so it is never online, never in a `presence` frame, never watches, and writes no `last_seen_at`. It expects `hello`, `presence`, and a `pong` to a `ping` within 2 s. No device token is minted and no row is written. `"relay": "ok" | "failed"`; failure is `503 not_ready` with `details.relay` and a warning line. The fixture's failure case raises the relay's minimum client protocol above the hub's own, which makes the link refuse the probe.
  - **Heartbeat.** `"instances": "stale"` and `503` once the instance row has not been written for the liveness window, because the other instances already count this one dead; a hub that cannot hold its users should not receive traffic.
  - **Why.** A probe through the real upgrade would need a device and a token, and the `AuthedDevice` extractor runs before any handler code; an in-process principal tests the code that serves links without a credential.

Built from `docs/superpowers/specs/2026-11-01-m8c-relay-design.md` on the `feat/m8c-relay` branch. These record what the build chose where the design (D-054 to D-059) was silent or was changed by review; D-054 to D-059 carry "Amended by" notes. The live gate is pending (`docs/verification.md`).

- **D-075 The link's wire details: close codes, size limits, protocol header, and what `last_seen_at` means.** Hub: `Hub/crates/b4hub/src/relay/link.rs`; Mac and phone: `Sources/WorkspaceSync/RelayLink.swift`; reference `Hub/API.md` "Link".
  - **Close codes.** 4000 replaced by a newer link (after an `error` frame `link_replaced`; the device does not reconnect), 4001 revoked (stop until it joins again), 4002 `client_too_old` (stop and update), 4003 no frame for 30 s (reconnect), 1001 the hub is shutting down (reconnect). 4002 and 4003 were the builder's choice; the other three were in the design. A message past the 1 MiB socket cap ends the connection with no close frame at all.
  - **Sizes.** The socket layer reads nothing over 1 MiB (`WIRE_MAX`). On top of that the hub refuses a client frame over 64 KiB and a host frame over 256 KiB with an `invalid_request` error frame carrying `maxBytes`, unread and unlogged, and the link stays up. The design set the 64 KiB and 256 KiB limits; the 1 MiB socket cap is the build's, because the library's default message size is 64 MiB, far more than the hub will ever read.
  - **Protocol.** The `B4-Protocol` request header names the device's link protocol; a missing header is 1, a non-number is `400`, and below the hub's minimum (1 today) the device gets `client_too_old` and 4002 with no `hello`.
  - **Time.** The hub's `hubTime` and `last_seen_at` follow the system clock at the moment they are read, with the source injectable in tests; the first version captured the system time once at startup and added tokio's monotonic elapsed time to it, so a clock step after startup left the two disagreeing.
  - **Presence.** `last_seen_at` is the time of the link's last received frame, written before the device is unregistered, so anyone who sees the Mac offline finds the time already stored. If a phone's outbound queue is full when presence changes, the hub keeps the latest presence for that link and sends it once the queue drains, so presence is never silently lost to a busy phone.

- **D-076 Routing rules the design left open, and the watch rules.** `Hub/crates/b4hub/src/relay/route.rs`, `registry.rs`, `limits.rs`.
  - **Resend and wait.** A command is in flight from the moment it arrives until its answer is queued for the caller, keyed by device and id. A resend attaches to it before any limit is counted, so a send that is running is never answered `rate_limited`. Frames other than events wait up to 5 s (`QUEUE_WAIT`) for room in a full queue; events are dropped (with `stream_gap`). When the wait ends a reply is dropped (the phone settles by `turn.lookup`), and a command to a Mac whose queue stays full answers `relay_timeout`, never `device_offline`, which is reserved for "no link".
  - **Spec-silent cases.** `turn.lookup` is never held for an offline Mac. A command with a missing routing parameter is `not_found`. A `request.respond` for a request the hub holds no state for is forwarded (the Mac is the authority). A command refused by the per-user limit still counts toward the device's. An unknown method answers by id without touching the limits.
  - **Watches.** A watch of a thread the caller cannot reach is an `error` frame `not_found`, and a fifth distinct thread is `watch_limit`, neither carrying a `threadId`; the phone watches one thread at a time (the one it read last), so it can tell which is meant. Watching a thread twice is a no-op. `thread.start` starts a watch of the new thread for the caller, counted toward the 4; if the link is already at 4 the thread is simply not auto-watched. A `thread.start` the Mac refuses without `details.turnId` (so no thread exists) gives the auto-watch back. The hub does not look at event kinds; which are streamed, and the 256 KiB bound, are the Mac's (`HubLink`).
  - **Why.** Nothing here is state, so every rule fails toward "the phone asks again", which the change log and `turn.lookup` make safe; none of them can start a turn twice.

- **D-077 What the Mac does with a relayed command.** `Sources/Coordinator/HubSync/RelayExecutor.swift`, `SessionService.swift`, `Router.swift`.
  - **Errors the phone sees.** An error that is not a `WorkspaceError`, and any message that carries PostgreSQL or launch-failure text, reaches the phone as `internal_error` or its original code with the fixed text "Your Mac could not run this."; the full text goes only to the Mac's log and Diagnostics. The hub's rule that messages never carry SQL or internal text is applied on the Mac too, because the Mac is where the text is made. A refusal made before this send's turn exists (`turn_active`, `directory_locked`) names the blocking turn as `details.blockingTurnId`, never `turnId`, so the phone's rule "`details.turnId` means accepted" stays exact. Turn or thread text containing NUL is refused with `protocol_invalid` (reason `invalid_text`) before it reaches `SessionService`, which would leave such a turn stuck submitting (a predating Mac bug, still reachable from the local socket). An id reused across methods answers `operation_reused`.
  - **`thread.start`.** An existing turn for the id is answered first, then the request is validated. Before the thread is created the executor runs `SessionService.assertCanStart` (runtime outage, folder lock, readiness), so a refusal leaves no empty thread behind. The `threadId` must be a lowercase UUID, and starts of one `threadId` are serialised.
  - **Local socket.** The `Router` refuses `thread.start` and `turn.lookup` from the local socket (`unsupportedCapability`, "Only relayed from the hub."), because the design reaches `thread.start` only through the relay, and drops a `threadId` sent to a local `thread.create`.
  - **First answer wins.** `SessionService` marks a runtime request as being answered before the adapter call, so two answers reach the runtime once and the second gets `stale_runtime_request`.
  - **Catch-up.** When a thread enters the watched set, `HubLink` sends each streaming message's text so far as a `message.delta` with `payload.catchUp: true`. Live deltas never carry the field.

- **D-078 Pairing and keeping the Mac awake.** `Sources/Coordinator/HubSync/Pairing.swift`, `KeepAwake.swift`, `Sources/WorkspaceProtocol/Relay.swift`, `Hub/crates/b4hub/src/routes/pairing.rs`.
  - **Mac.** `hub.pair` mints a code and is never cached by the `Router`'s operationId cache, which would replay a spent code to a second caller. A code expires 300 s after the mint by the Mac's monotonic clock (a wall-clock change cannot extend it); the sheet polls `hub.pairStatus` once a second and closes with the new device's name. Revoking a Mac withdraws its unused pairing codes on the hub (`DELETE /v1/devices/self`). Keep-awake stays held through a 401 until `hub leave` (it means "toggled on and a hub link exists"; nothing remote can reach the Mac then, and releasing on suspension is a one-line change if the owner wants it). The Remote access page shows "Connected since…" or the last error.
  - **Phone.** The pair-link parser checks the code's length and alphabet before upper-casing (upper-casing first let a seven-character code containing `ß` pass), and refuses a hub URL with user information. `HubURL` moved from `WorkspaceSync` to `WorkspaceProtocol` so the parser reuses its https-or-localhost rule without a dependency cycle.
  - **Relation to D-066.** The link is still `b4app://pair?hub=…&code=…` in M8c. D-066 (sign-in) replaces it with `https://<site>/pair#c=<code>`; the code's handling (single use, five minutes, shown on purpose) does not change.

- **D-079 The phone: send states, presence, lookup, and what a hub refusal means.** `Sources/WorkspaceUI/SendState.swift`, `WorkspaceModel`, `Sources/WorkspaceMirror/MirrorRelay.swift`.
  - **Where state lives.** Send states belong to the shared `WorkspaceModel` and are used only when `accountSource == .host`, so the Mac's model is unchanged. `ConversationThread`, `Project`, and `Connection` gain an optional `ownerDeviceId`, filled only on the phone. Presence travels in the `events.snapshot` and each presence event carries the whole set of Macs, so a presence frame that arrives before the model subscribes is not lost.
  - **Not confirmed.** A phone asks `turn.lookup` no sooner than 30 s after the tap and 12 s after its latest attempt, backs off 5, 10, 20, then 30 s when the Mac does not answer, and asks again after 5 s on `in_flight`; only a Mac's `none` settles a send as not sent. The guard against a second start while one is unsettled is global across Macs, so an offline Mac's unsettled start also blocks starts on others (conservative; the cost is a disabled Start until it settles).
  - **Starting a thread** is not blocked while the Mac reads "reconnecting" (the hub answers `device_offline` if it is really gone), only when it is disconnected, has left the hub, or the phone's own link is down.
  - **A hub refusal** (an unauthorised or revoked phone link) leaves the link closed until the person logs out and pairs again, with "The hub no longer accepts this iPhone. Log out, then pair it again." A phone with a revoked token otherwise retried on every foreground.
  - **Resuming a stream.** When a catch-up delta arrives for an item that already has live text, the phone forwards only the suffix it has not shown, or, if its text does not begin the catch-up, resets the item and shows the whole text.

- **D-080 Shared client and storage changes.** `Sources/WorkspaceClient`, `Sources/Coordinator`, `Sources/WorkspaceMirror`.
  - **`WorkspaceClient.resetCursor`** no longer moves a cursor back within the same epoch. This also applies to the Mac, where it fixes a real bug: a snapshot refresh during streaming read the next event as a gap and re-reconciled. The model now subscribes to events before its first snapshot on both platforms.
  - **Storage.** A local B4 connection creates an automatic project for its server folder (as a thread's folder already does), so a phone has a project to start in. `connections.projectId` is backfilled on every coordinator start (a no-op once set) and rewritten when the connection's folder moves to another project. The mirror's schema is v3, adding the index `displayItems("threadId","nativeItemId")` that live deltas search by.

## 2026-11-02 (M8e operability)

Design `docs/superpowers/specs/2026-11-02-m8e-hub-operability-design.md`, Part A. The owner asked on 2026-11-02 that the hosted-hub follow-ups be completed without pausing, so these are the implementer's calls, recorded here at commit.

- **D-073 Every hub request carries a hub-minted request id and runs in a `request` span that names it, the method, the matched route pattern, the caller's own request id when it sent one, and the authenticated device id; the log is JSON when stderr is not a terminal.** The id is always a fresh UUIDv7, echoed on the response as `X-Request-Id` so a client's error can be matched to the hub's lines. An inbound `X-Request-Id` is never honoured as the hub's id, because nothing deployed in front of the hub strips or sets it (Compose and Caddy pass it through, the ALB sets only `X-Amzn-Trace-Id`, the chart does nothing), so a client could choose the id it is logged under; when it is 1 to 64 printable ASCII characters without whitespace it is recorded as the separate span field `client_request_id` for correlation with the caller's logs. `Settings::trust_proxy()` (`B4HUB_TRUST_X_FORWARDED_FOR`) exists for the sign-in branch's client-address handling and plays no part in request ids. The span's `path` is the route pattern (`/v1/changes`, or `(unmatched)`), never the raw path or query, and the device id, never the token, is recorded after authentication; one completion event per request carries `status` and `elapsed_ms`, at `warn` for a `503` (an intentional refusal: maintenance, shutting down, not ready, which must not read as failures in the log) and `error` for any other 5xx. Headers and bodies are never logged, and a test drives an authenticated request through a JSON subscriber to prove the token is absent. `B4HUB_LOG_FORMAT=text|json` overrides the terminal default. The JSON shape is `tracing-subscriber`'s (`flatten_event`, `with_current_span`, no span list), so the event's fields are top-level and the span's sit under `span`; CloudWatch Logs Insights reads both.
- **D-074 Maintenance mode is a row in a hub-wide `hub_settings` table, flipped by an operator command and polled by every instance; while on, the hub refuses writes with `503 maintenance` and `Retry-After: 30` and keeps serving reads and `/readyz`.** The alternative, an environment variable, needs a redeploy per flip and cannot reach every instance at once. `b4hub maintenance on [--message] | off | status` connects with `DATABASE_ADMIN_URL` like `seed` and `enroll` (on AWS through the `hub-admin` task, on Compose through the `migrate` service), because `migrate` lets `b4hub_app` only `SELECT` from `hub_settings`. `serve` polls before it listens and every `B4HUB_MAINTENANCE_POLL_MS` (default 5000) and keeps the last value through a failed poll, logging a warning on each failure, so a database blip flips nothing; the consequence is that an instance whose first read fails starts with maintenance off (fail-open) until a read succeeds, accepted because readiness would fail on the same unreachable database. The switch pauses client writes (the API's write routes); the hub's own `last_seen_at` touches and pruning continue. The operator's message is public (an unauthenticated enroll caller sees it). The guard is an extractor placed after authentication and before the body in the three write handlers, so a refusal is logged with the device id, a bad token still gets `401`, and a refused body is never read; `serve` reads the switch once before it listens. The load balancer still counts each refusal as a 5xx, so the `alb-5xx` alarm fires while maintenance is on with an active client; runbook 9 says so. `/readyz` stays `200` and reports `"maintenance": "read_only"`: a load balancer must keep routing, since reads still work. The table is not tenant-scoped (no `org_id`, no row-level security) and its migration is numbered `0006_settings.sql` because `0004` and `0005` are claimed by unmerged branches; a test shows sqlx 0.8 applies a lower number that lands later (`docs/compatibility.md`). `since` is stored as RFC 3339 text written by the hub rather than adding a date crate.

## 2026-11-01 (sign-in: Sign in with Apple on the hub)

Built on `blove/sign-in` (Task 13) under provisional numbers, which became D-090 to D-093 because main took D-081 to D-086 while the branch was being built.

- **D-090 The hub accepts Apple identity tokens signed `RS256` (and `ES256`), with the key's own algorithm.** The design said ES256, after Apple's documentation; Apple's key set (`https://appleid.apple.com/auth/keys`, checked 2026-11-01) publishes only RSA keys with `alg` `RS256`. The algorithm comes from the key the token's `kid` names, and a header that claims another is refused. The fake Apple in `Hub/crates/b4hub/tests/apple.rs` signs with both. The client secret stays ES256, as Apple requires for the `.p8` key.
- **D-091 The web flow's client id is a new optional `B4HUB_APPLE_SERVICES_ID`, and the native flow's is the identity token's audience.** Telling the bundle id from the Services ID by their shape would break the day either changes form. Without the variable (or `B4HUB_PUBLIC_URL`) the hub offers only the native flow. Each refresh token is sealed together with the client id it was issued to, because revoking needs that client id; the seal's associated data is the identity row's id.
- **D-092 One nonce rule; Apple's callback changes nothing, and every web outcome redirects back to the app.** Apple is always handed the lowercase hex SHA-256 of the ceremony's nonce, and the identity token must carry exactly that, in both flows. The verifier hash and the app's scheme (`b4app`, `b4app-beta`, or `b4app-local`) are fixed at `POST /v1/auth/apple/begin`, not on the start URL as the design's route table had it, so the URL the browser opens carries nothing but the ceremony id. The callback only verifies the identity token and records a handoff that carries the verified Apple ID, email, name, client id, and the unexchanged authorization code, sealed with `B4HUB_SECRET_KEY` and bound to the handoff's code hash (migration `0007`). No user, org, identity, or device is created and no code is exchanged until the app redeems the handoff with its verifier. An earlier draft linked at the callback; review showed that anyone who could get a victim's browser to complete Apple's page on an attacker's link ceremony (a forwarded start URL, a leaked ceremony id) would have linked the victim's Apple ID to the attacker's account. Once Apple's post names a known ceremony, every outcome is a redirect to that ceremony's scheme (`?handoff=` or `?error=`, `cancelled` included), so the Mac's browser session always closes.
- **D-093 Linking an Apple ID begins at `POST /v1/me/apple` and finishes from the linking account's own device: natively at `POST /v1/me/apple/native`, or on the web at `POST /v1/me/apple/handoff`.** The link ceremony records the user, and its handoff names that account; another account's device, or `POST /v1/auth/handoff`, is refused `credential_rejected` without using the handoff up (a sign-in's handoff is likewise refused by the link route). An account links at most one Apple ID, as the Settings page shows "Connect Apple ID" only when there is none: a second is `409 apple_linked`, enforced under a lock on the user row (merging a phone-only account on pairing is exempt). An Apple ID on another account, or any while sign-up is closed and the Apple ID is new, is refused before its code is exchanged, so Apple never keeps a grant the hub does not store.

## 2026-11-02 (hosted hub deployment)

Design `docs/deployment-architecture.md`, approved by the owner 2026-11-02. Research: `docs/research/reports/Managed hosting for the b4 hub.md`. Implemented on the `blove/cloud-hub-deployment-arch-4b6348` branch (see the implementation notes below); nothing is applied in an AWS account yet.

- **D-068 The hosted hubs run on AWS from day one, as ECS on Fargate behind an Application Load Balancer with RDS for PostgreSQL, one AWS account per environment under an Organization, in `us-east-2`; cacheplane operates no Kubernetes for them.** The owner's decision after research that recommended Fly.io plus Neon for about $40 a month: "I think we need to do AWS from day one." The reasons AWS won are that Neon has no cross-region path, that the "later" tier (a second region, Aurora Global Database) is then an addition rather than a migration, and that AWS is the only candidate with published failover figures. The owner excluded Google Cloud and Cloudflare, which also removed Render and DigitalOcean (both front their edge with Cloudflare); Heroku's fixed 30 s SIGTERM is under the hub's 35 s drain, AWS App Runner is closed to new customers, and Railway's October 2026 breach decrypted customer environment variables. Each environment runs one task with recreate deploys (a 45 to 90 s outage per deploy, tolerated because D-057 keeps relay routing in process memory and D-054's clients resume from their cursor) until M8e adds cross-instance routing. The "now" tier costs about $110 a month for both environments.
- **D-069 Infrastructure is Terraform in `Infra/`, applied by GitHub Actions over OIDC; test applies on merge to `main`, production on merge with the owner's approval in the `production` Environment; no long-lived cloud credential and no secret value exists in Terraform, state, or GitHub.** Three roles per account from a one-time bootstrap: a read-only plan role for pull requests, a broad infra-apply role under a permissions boundary, and a narrow application-deploy role. Secrets Manager secrets are created empty by Terraform and filled once by the owner from a terminal; the RDS master password stays RDS-managed and is used once, at bootstrap, to create `b4hub_owner`, which runs every migration from then on. The owner's direction: "Terraform".
- **D-070 Releases are tagged `hub-v<semver>`; test deploys on every merge to `main` and production on a published release, always by immutable image digest with attestation verification, after a one-off migration task that alone holds the privileged database URL.** The owner's release model: "main is latest, we build nightly artifacts using main, production is a release." The canonical registry is public GHCR (`ghcr.io/cacheplane/b4hub`), copied by digest into each account's ECR by the deploy role (an ECR pull-through cache would need a GitHub token stored in every account). A release never builds: it deploys the digest already built for its commit on `main` or fails. Migrations are forward-only; rollback redeploys the previous digest. Nightly images build from `main` and deploy nothing. Operator commands (`seed`, `enroll`, bootstrap SQL) run through a `hub-admin` task with ECS Exec, so an enrollment code reaches only the owner's terminal.
- **D-071 Edge protection is the hub's own limits plus a WAF rate rule and IP reputation list; no body-inspecting managed rule group is attached.** The AWS Common Rule Set blocks bodies over 8 KB, and `POST /v1/changes` legitimately carries up to 32 MiB; its injection rules would false-positive on `displayItems` payloads, which are agent transcripts. TLS 1.2 minimum at the load balancer; HSTS and `Cache-Control: no-store` on auth routes are set by the hub so on-prem gets them too. Backups are AWS Backup daily snapshots with a cross-region copy in production, restored in a monthly drill; external uptime probes (Better Stack) page the owner, because an alarm inside an unreachable region cannot.
- **D-072 Self-hosting ships as a Compose production profile and a `b4hub` Helm chart with an external database, a pre-upgrade hook migration Job, and file-mounted secrets; both are built in this project.** The owner: "lay it out even if they come later, I want the docs", then "Built here." The chart uses no library chart (Bitnami's catalogue was paywalled in 2025), requires `database.existingSecret` with a CloudNativePG example, defaults to one replica with `strategy: Recreate` and Restricted Pod Security Standard settings, renders a controller-agnostic Ingress or a Gateway API `HTTPRoute`, and is published as an OCI artifact on GHCR signed with cosign. Compose keeps the migrate-then-serve split (`service_completed_successfully`), reads secrets through the hub's `*_FILE` variables, and offers Caddy for TLS as an optional profile. Both tell operators their proxy must append the client address, which is what `B4HUB_TRUST_X_FORWARDED_FOR=1` assumes and what the AWS load balancer does.

## 2026-11-01 (sign-in design)

Designed 2026-11-01: `docs/superpowers/specs/2026-11-01-sign-in-design.md` and `docs/superpowers/plans/2026-11-01-sign-in.md`. Research: `docs/research/reports/Mac App Store sandbox for agents.md`. Built 2026-11-02 on `blove/sign-in` (see D-090 to D-093 and D-094 to D-112 above, which amend these entries where the build changed them); the live gate passed on 2026-11-02 (`docs/verification.md`).

- **D-062 The Mac ships only as a notarized Developer ID download and a Homebrew cask; there is no Mac App Store or TestFlight-for-Mac build.** Amends D-051. Both channels require App Sandbox on every executable. A sandboxed process can execute nothing outside its bundle and a few system locations; no file grant adds execute permission, and Apple DTS says so. Children inherit the sandbox with `HOME` moved into the container, so the user's `codex`, `claude`, and `node` cannot run, and their `~/.codex` and `~/.claude` logins are invisible. App Review rejected a home-folder exception for an agent-CLI app in April 2026. PostgreSQL needs System V IPC, which the sandbox denies, and a sandboxed app cannot write the LaunchAgent. T3 Code, ChatGPT/Codex, Claude desktop, Zed, Warp, and Conductor all ship outside the store unsandboxed; Xcode runs agents from the store only because Apple exempts it. Bundling our own agents was rejected: they could not run the user's toolchains, they would need a second login, every model update would wait on review, and Claude Code's terms forbid modifying the binary, which Apple's re-signing may count as. The iPhone app ships through the App Store and TestFlight as D-051 set up. The owner's words: "macOS is installed like codex and claude - download or homebrew."
  - *Built:* `Scripts/release-mac.sh` and the cask `Packaging/homebrew/agent-workspace.rb` (`docs/release.md`); nothing has been released, and the tap is the owner's to create.
- **D-063 Three build flavours, `prod`, `beta`, and `local`, each with its hub, site domain, and identifiers.** `prod` is the App Store iPhone app and the b4.run Mac download, against `https://hub.b4.run` with passkeys on `b4.run`. `beta` is TestFlight and a Mac beta download, against `https://hub.test.b4.run` on `test.b4.run`. `local` is built on the owner's Mac, against `http://localhost:8080` with passkeys on `local.b4.run`, Apple sign-in hidden, and its iPhone build Simulator-only. The flavour is an `Info.plist` key read at run time (`Flavor.current`), because Xcode does not pass an app's compilation conditions to package targets. Bundle ids, data directories, LaunchAgent labels, URL schemes, and keychain groups carry a `.beta`/`.local` (or `-beta`/`-local`) suffix, so flavours coexist on one Mac. Each flavour has its own relying-party id, so a test passkey never appears when signing in to prod. `local.b4.run` serves only the association file the OS requires before an app may use a passkey; the hub that verifies it can run on `localhost`, because WebAuthn checks the signed origin, not the server's address. The owner's current install becomes `local`: its data directory moves to `b4app-local`, and its hub token moves out of the prod keychain group, which the local flavour also claims for that one read.
  - *Amended by D-094, D-109, D-110:* the owner's install is adopted only by an explicit local flavour, under the coordinator's lock, so the app must be opened before the CLI; the prod keychain group is read once and the adopted install's secrets copied from it, never moved; the phone's mirror and Keychain items are per flavour, prod's unchanged; each iPhone flavour registers only its own URL scheme.
- **D-064 Accounts are created by signing in with an Apple ID or a passkey, and each gets a private org.** The hub verifies both itself: Apple identity tokens against Apple's JWKS, and passkeys with `webauthn-rs`, discoverable and with user verification required. Each sign-in ends in today's device token. One button per method signs in or signs up. A passkey sign-up asks for nothing until the OS reports no passkey, then confirms before creating an account. Onboarding asks only for the full name; the owner removed the phone number after App Review's rule against requiring unused personal data came up. The org is named "<first name>'s Org". Developer ID Mac apps cannot use the native Sign in with Apple sheet (the capability is App Store-only), so the Mac uses Apple's web flow through the hub, with a Services ID, a form-post callback, and a one-time handoff bound to a verifier. Apple refresh tokens are kept encrypted so account deletion can revoke them (App Store guideline 5.1.1(v)). Sign-up is `B4HUB_SIGNUP=open|closed`, default closed, so an on-prem hub never grows accounts by accident. Enrolled users are marked onboarded, and `b4hub enroll` stays as the operator path. ## 2026-11-01 (M8c relay design)

Design `docs/superpowers/specs/2026-11-01-m8c-relay-design.md`, approved by the owner 2026-11-01; plan `docs/superpowers/plans/2026-11-01-m8c-relay.md`. Built 2026-11-02 (see D-075 to D-080 above, which amend these entries where the build changed them).

- **D-054 The relay is one WebSocket per joined device, and it carries commands, replies, presence, and live progress, never state.**
  - **Shape.** `GET /v1/devices/self/link`, authenticated with the device token before the upgrade. A `macos` device is a host and an `ios` or `cli` device is a client. A newer link replaces an older one.
  - **Timings.** Heartbeat every 10 s; a link silent for 30 s is dead. Reconnect with backoff from 1 s to 30 s, and at once on wake and on a network change.
  - **State.** The change log stays the only source of truth: nothing from the relay is written to the mirror, so the relay needs no cursor and a lost frame costs only a moment of streaming. This replaces the M8 design's reconnect-from-a-cursor paragraph for the relay.
  - **Presence.** `last_seen_at` is the last frame heard from the device.
  - *Amended by D-075:* close codes 4000 to 4003, the 1 MiB socket cap, the `B4-Protocol` header, and `last_seen_at` written before the device reads as offline; the reconnect backoff is 1 s doubling to 30 s on the Mac and to 15 s on the phone.
- **D-055 Relayed commands are never stored, carry a deadline the Mac enforces, and are idempotent by phone-minted ids the Mac already stores.**
  - **Deadline.** The hub stamps each command with hub time + 10 s, and the Mac drops one that arrives late by its estimate of the hub's clock, so a frame buffered across a sleep never starts a turn.
  - **Idempotency.** `turn.send` uses the command id as the turn's `operationId`, which `SessionService` already deduplicates durably. `thread.start` uses a phone-minted `threadId` as well. `RelayExecutor` runs each id once at a time.
  - **Lost replies.** A reply that never came is "not confirmed". The phone resends the same id only within 30 s of the tap, and asks the Mac (`turn.lookup`) whether the turn exists, so a lost send is only ever declared by the Mac.
  - **First answer wins** is the Mac's existing `stale_runtime_request`, made true at the runtime by marking a request as being answered before the adapter call.
  - **Holds.** Interrupts and answers are held for an owner seen within 60 s (D-045); sends never are.
  - *Amended by D-076, D-077, D-079:* `turn.lookup` is never held either; a full queue answers `relay_timeout`, not `device_offline`; the Mac's errors are sanitised and a refusal before the turn exists names `blockingTurnId`; the lookup timing is 30 s after the tap, 12 s between attempts, with backoff.
- **D-056 The phone keeps every thread readable when its Mac is unreachable.**
  - **Notice.** After a 60 s grace from the Mac's last-seen time (with "Reconnecting to your Mac…" until then), a notice names the Mac and its last-seen time. The composer, Stop, approvals, and new thread are disabled for that Mac's threads, and a turn still shown as active reads "Not confirmed while your Mac is offline". The owner's direction; the same notice replaces the list-hiding "Host disconnected" screen when the Mac has left the hub.
  - **Scope.** Presence is per Mac. A thread follows its owner, and the list follows the Mac with the most recent activity.
  - *Amended by D-079:* starting a thread is disabled only when the Mac is disconnected, has left the hub, or the phone's own link is down, not during the 60 s "Reconnecting to your Mac…" grace.
- **D-057 Only `ios` and `cli` devices send relayed commands, and only to their own Macs.**
  - **Methods.** Only `turn.send`, `turn.interrupt`, `request.respond`, `thread.start`, and the read-only `turn.lookup`, allowlisted on the hub and again on the Mac.
  - **Target.** Only a non-revoked `macos` device of the same user and org that owns the thread or project. Every miss is a generic `not_found`.
  - **Folders.** `thread.start` runs only in a folder its project lists, or on a local B4 connection serving that project.
  - **Limits.** In memory on the hub: 60 commands a minute per device, 20 sends a minute per user, 4 watched threads per phone, 64 KiB client frames and 256 KiB host frames.
  - **One replica.** The hub's routing state is in memory, so cross-replica routing waits for M8e.
  - *Amended by D-085:* the hub runs on several instances by serving every link of one user on one instance (a claim per user with a heartbeat takeover, a `409 relocated` refusal at the upgrade, and ALB application-cookie stickiness); frames are never forwarded between instances.
  - *Amended by D-076, D-077:* the wire caps are 1 MiB beneath the per-role limits; a missing routing parameter is `not_found`; the Mac also refuses `thread.start` and `turn.lookup` from its local socket and requires a lowercase-UUID `threadId`.
- **D-058 A joined Mac pairs a phone by QR code.**
  - **Code.** `POST /v1/pairing-codes` mints a five-minute, single-use enrollment code for the Mac's own user (10 an hour).
  - **Mac.** The "Remote access" Settings page shows it as a `b4app://pair?hub=…&code=…` QR code, beside "Keep the Mac awake".
  - **Phone.** It scans the code (or opens the same link, which is how the Simulator is tested) and always asks before enrolling.
  - **Secret handling.** The code is a credential shown on purpose, like a typed enrollment code: it is never logged or stored, and lives only in the sheet. It is the one exception to keeping secrets out of UI state. The owner's direction, as part of M8c.
  - *Amended by D-078:* the code is withdrawn when its Mac is revoked, the parser validates the code before upper-casing it, and D-066 later replaces the `b4app://pair` link with an `https` one.
- **D-059 A local B4 connection's project syncs as `connections.projectId`, a Mac-only column, so the phone can start B4 threads in a project.** It is the owner's decision to include B4. The column holds a project id already on the hub, never a path, and needs no clock. Remote B4 threads belong to no project, so they are continued from the phone but never started there. *Amended by D-080:* a local B4 connection now creates an automatic project for its server folder, and `connections.projectId` is backfilled on every coordinator start.

- **D-050 The hub cuts pull pages by stored value size, prunes its change log on a schedule, and restores a stale reader from one unpaged snapshot.** A pull page stops at 1000 changes or 8 MiB (8,388,608 bytes) of `value`, whichever comes first, and always holds at least one change, so a page of one 2 MiB change still moves. The size is not measured at read time: `changes.value_bytes` is the length of the value as PostgreSQL's `jsonb` text (a few bytes more than compact JSON), stored when the change is pushed, and the page is cut in SQL with a running sum over those integers, selecting `value` only for the rows inside the cut. A first version streamed 1001 rows out of PostgreSQL to find the cut, and the byte limit exists to bound work as well as memory. `changes.received_at` (`now()` at insert) is what pruning reads, not `wall`, so a device with a wrong clock cannot make its own rows look old. `serve` prunes every org when it starts and every 24 hours after; `B4HUB_RETENTION_DAYS` sets the retention (default 30; anything but a whole number of at least 1 is a configuration error and exits 2), and `b4hub prune --older-than-days N [--org slug]` does it once. Pruning takes the same per-org advisory lock a push holds, deletes every change received before the cutoff and every change with a lower `hub_seq` (the horizon is one cursor, so what remains is a contiguous tail), and raises `org_sync_horizons.horizon` to the highest `hub_seq` it deleted; the horizon never moves down and the materialised tables are not touched, because the log is history and the tables are state. A pull whose `after` is below the horizon answers `410 resync_required`; the check and the page are read in one database snapshot, so a prune that commits mid-pull cannot leave the reader a gap. The reader then calls `GET /v1/snapshot`, one `REPEATABLE READ` transaction that returns this user's rows as synthetic `insert` changes in dependency order (`hubSeq` 0, `deviceSeq` 0, `wall` 0, `deviceId` the row's owner), the per-column clocks of those rows, and `next`, the highest `hub_seq` the org's feed had at that instant (or the horizon, if pruning emptied the feed). A snapshot row's `hlc` is the greatest of its clocked columns' clocks, or `000000000000-0000-<owner device>` when none was ever set, so any later change of the row wins over it. The Mac applies the snapshot through the same narrow merge as any pull (D-049), so its rows stay and only phone-writable values are compared by clock; the phone clears its rows, keeps its outbox, applies the snapshot, re-applies the unsent outbox rows on top, and continues from `next`. **An uncut page's `next` is the highest `hub_seq` the org has recorded (at least `after`), even when that is another user's change.** Without this rule a user whose feed is idle would keep a cursor that other users' activity pushes below the horizon, and would resync every 30 days for nothing; nothing of theirs can lie in between, because pushes commit in `hub_seq` order. `GET /v1/devices` lists the user's devices (revoked ones included) for the mirror's device names. Known limitations: the snapshot is not paged, so the hub builds the user's whole mirror in memory in one response; the first prune after a long gap deletes the whole prefix in one transaction while holding the push lock, and `received_at` has no index; the privileged-role check counts only ownership of `changes`, and a `NOINHERIT` member of a superuser can still `SET ROLE` (for a security review); the migration's backfill of `value_bytes` and `owner_device_id` is a full-table update. - **D-049 Concurrent edits merge by hybrid logical clock, column by column, and the phone may write a short list of columns that the hub and the Mac both enforce.** A clock is `<12 lowercase hex digits of epoch milliseconds>-<4 hex digits of counter>-<device id>`, compared as plain strings (SQL compares them `COLLATE "C"` so no locale can reorder them). - **D-038 The packaged app carries the coordinator and the CLI in `Contents/Helpers` and a LaunchAgent plist in `Contents/Library/LaunchAgents`; the app registers the agent with `SMAppService` and hosts in-process only as a fallback.** Order on connect: an answering socket wins; otherwise a bundled agent is registered (`RunAtLoad`, `KeepAlive` on failure only, Aqua session) and the socket awaited for six seconds; otherwise the app hosts as before (Xcode runs, an agent awaiting Login Items approval, a failed registration). Amends D-004 (the LaunchAgent exists) and D-032: with the agent hosting, Quit owns nothing and local work continues. The Keychain stays file-based (D-008) for the same reason. **Amended 2026-10-31 (Developer ID):** the owner enrolled in the Apple Developer Program, and the build Mac now holds one identity of the form `Developer ID Application: <name> (<team id>)` in the login keychain, plus a notarytool keychain profile named `b4app` that the owner created themself with `xcrun notarytool store-credentials`, so no Apple ID or app-specific password passes through the script. ## 2026-10-31 (M5)

- **D-031 Native history is merged into the cache by snapshot order; live rows are never deleted or duplicated.** `thread.reconcile` (and a plain `thread.read` whose cache is empty although turns were recorded) calls the adapter's `loadSession` and merges: a snapshot item whose native id is cached keeps that row (a live row keeps its payload, a snapshot row takes the new one); an id-less item that matches a cached item of the same role and text reuses that row; everything else is inserted with `snapshot` provenance in the snapshot's order; cached snapshot rows the runtime no longer reports are removed; live rows nothing matched (the turn in flight) follow at the end; sequences are renumbered in one transaction. Text matching is used only to recognise the app's own user messages, never as an exactly-once guarantee for runtime events (spec 10.1).
- **D-032 Quit offers "Quit" or "Stop local work and quit", never "keep running in the background"; threads whose native session is missing or whose connection now presents another identity stay readable and never resume.** The coordinator lives inside the app until the M6 LaunchAgent (D-004), so local turns end with the process either way; the dialog says so, names the local turns and owned servers, and states that attached and remote B4 runs continue on their server and are reconciled next launch. When another process hosts the coordinator the app owns nothing and quits at once. `connections.nativeScope` records the identity last presented; a thread created under a different scope is `identity_changed`, a runtime that lost the session is `missing`; both keep the cached transcript, refuse `turn.send` with a stable code, and offer a new thread (spec 3.3, 5.1).
- **D-033 The directory lock is derived from stored turns, not a lock table.** Before dispatch on a Codex or Claude connection the coordinator canonicalizes the thread's working directory (symlinks resolved, no trailing slash) and refuses `protocol_invalid` / `directory_locked` while any other harness thread, on any connection, has a non-terminal turn there. Because the state is the turns themselves, the lock survives restarts and holds through `waiting_for_user`, `stopping`, and `reconciling` (spec 10.1.5); `turn.abandon` releases it deliberately. B4 routes are not directories.
- **D-034 Wake is detected twice: `NSWorkspace.didWakeNotification` in the app and a clock-gap watcher in the coordinator.** `ContinuousClock` keeps counting while the Mac sleeps and `SuspendingClock` does not; a drift over 20 s between two five-second ticks means a wake and triggers `workspace.reconcile`, so a CLI-spawned coordinator with no app also reconciles. Reconciliation asks each runtime about each unresolved turn and re-checks offline connections; it never re-sends.
- **D-035 The coordinator is the redaction boundary.** Every adapter event's `message`, `stderr`, and `error.message`, every failed turn's message, and every `recentErrors` entry are passed through `LogRedactor` before they are stored or published; adapters forward runtime text as they receive it. The redactor also masks whole `Authorization:` header lines and sensitive URL query parameters (`code`, `state`, `token`, `access_token`, …). The CLI-spawned coordinator's stdout log is bounded like server logs. Redaction masks known shapes; it is not proof that arbitrary runtime output holds no secret (spec 12).

## 2026-10-31 (M4)

- **D-024 Managed servers are spawned with `posix_spawn` into their own process group, with stdout and stderr redirected to a per-server log file, not through `StreamingProcess`.** The pipe-based helper ties a child's life to the coordinator (an orphaned Node process dies on its next write to a closed pipe) and loses its output across a coordinator restart. The file keeps the server independent so an app Quit or a coordinator crash never loses a running server, and the process group lets a stop reach a runtime child that outlived `b4 dev`. The spawn also resets the child's signal mask and the dispositions of SIGTERM, SIGINT, SIGHUP, SIGPIPE, SIGQUIT, and SIGCHLD: the coordinator ignores several of those and dispositions survive exec, and a blocked SIGTERM inherited from the spawning thread left a server that only SIGKILL could stop.
- **D-025 Ownership is `(pid, process start time within one second, argv containing the CLI entry file and the port)` from `KERN_PROC_PID` and `KERN_PROCARGS2`, captured at spawn and re-verified before every signal and on every coordinator start.** A pid or a listening port alone never establishes ownership; a mismatch leaves the process alone and marks the registration stopped with a message naming the pid.
- **D-026 The project-installed CLI runs as `<node> <project>/node_modules/@b4run/cli/dist/index.js`, never through `node_modules/.bin/b4` or a shell, and is never downloaded.** The pnpm shim resolves `node` from `PATH`, which a Finder-launched app does not have. The version is read from the package's `package.json`; the minimum is 0.15.7. Inspection (`b4 routes --json --cwd <project>`) executes the project's config and route modules, so registration is the trust decision and both the CLI and the form say so.
- **D-027 A registration allocates its loopback port once (or takes `--port`) and keeps it, so route connections have a stable origin; a start whose port is taken fails with `owned_process_conflict` and stops nothing.** The port cannot change once a route connection references the server, because managed connections carry `http://127.0.0.1:<port>` as their target and threads use that origin as their native scope.
- **D-028 Source mode (`b4 start --host 127.0.0.1 --port N` with a coordinator-built environment parsed from the env file without shell evaluation) is the default; development mode (`b4 dev --port N --env-file P`) is explicit** because hot reload can replace the runtime mid-turn. The child environment is `PATH` (the Node directory plus the system directories), `HOME`, `TMPDIR`, `LANG`, `USER`, `SHELL`, and the env-file pairs; nothing else of the coordinator's environment leaks in, and env-file values exist only in the spawn call. `envFilePath` defaults to `<project>/.env` when present. `start`, `restart`, `add`, and `inspect` block until readiness (`GET /healthz` within 90 s) or discovery finishes; a concurrent start joins the one in flight.
- **D-029 Server logs are files the child writes directly; the coordinator serves redacted tails on request and bounds the file by copy-truncate (4 MiB, keep the last 1 MiB).** Bearer values, `sk-…` keys, and `key|token|secret|password|authorization` pairs are masked before the text leaves the coordinator. Log lines are never published as events, so a chatty server cannot evict conversation events from the replay buffer; `--follow` and the GUI poll `server.logs` with the last offset.
- **D-030 `server stop` and `server restart` refuse with `owned_process_conflict` (`reason: turn_active`) while a route connection has a turn in `submitting`, `running`, or `stopping`, unless forced**, because stopping loses the in-memory run. A parked prompt is durable in `.b4` and a `reconciling` turn is already lost, so neither blocks. The CLI takes `--force`; the GUI confirms. The M5 Quit dialog builds on the same check.

## 2026-10-31

- **D-019 A B4 turn's native id is its ordinal in `GET /threads/:id/turns`.** The Agent Protocol has no run id (the thread id is the run identity). Reading the turn count before `POST /runs/stream` and naming the turn `turn-<n+1>` lets reconciliation tell "the server ran it" (the nth turn exists, with its recorded status) from "the prompt never arrived" (it does not) without ever resubmitting. When the count cannot be read the id falls back to `run-<uuid>` and reconciliation relies on the thread status alone.
- **D-020 Parked versus cancelled is decided by `GET /threads/:id/pending_interrupts`, never by the `interrupted` status alone.** B4 writes `interrupted` for both. A non-empty list is a parked prompt: the turn stays `waiting_for_user` across stream loss and coordinator restart, and the prompt is re-opened from the durable `value` under a new adapter generation. An empty list is a cancellation.
- **D-021 Permission answers go through `POST /threads/:id/resume` with B4's own decisions.** `allow_once` → `once`, `allow_always` → `always` (B4 persists the pattern itself, unlike Claude in D-018; `once` when the prompt said `allowAlways: false`), `deny` → `deny`, decline → `status: cancelled`, each echoing the prompt's `grant`. The resume response is a second SSE stream that continues the same turn and item numbering. Stop on a parked turn declines the prompt, because nothing else can end it.
- **D-022 Endpoint secrets enter through the CLI's hidden prompt and the local socket into the coordinator's credential store.** `credential add <label>` reads with `readpassphrase` (or one line from a non-TTY stdin), sends `credential.add` over the 0600 socket, and prints only the `secret:<uuid>` reference. The adapter resolves the reference on first use, sends it as `Authorization: Bearer <value>` (verbatim when the value already names a scheme) to the configured origin only, and refuses every redirect. The GUI form collects the reference, never the value. Credential labels are not persisted yet; the reference is the handle.
- **D-023 Route kinds other than `agent` are stored as `incompatible` connections with an explanation.** Only `agent()` routes take the `input.messages` shape; `workflow`, `graph`, and `chain` routes are accepted at `connection add`, inspected, and reported, never run.
- **D-015 One `claude` process per native session, started on `createSession` and kept alive between turns.** The stream-json protocol has no session API: the CLI process is the session. Starting it at creation validates the executable, the `initialize` handshake, and sign-in before a thread row exists; `--session-id <uuid>` fixes the native id up front; after a coordinator restart the next turn spawns with `--resume <uuid>`.
- **D-016 A Claude process that exits mid-turn ends that turn as `failed`.** Unlike Codex, where the app-server owns the thread and a turn's final status can be read back, nothing continues once the `claude` process is gone, so the adapter emits `turn.finished failed` with the exit status, and `reconcile` after a coordinator restart reports `failed` for a turn with no live process. The disconnect is scoped to that thread; the connection and other threads are untouched.
- **D-017 Claude history is read from the transcript JSONL Claude Code writes under `projectsDirectory`, best-effort and read-only.** The app cache stays the display source; a missing file is `native_session_missing`, never a reconstructed session.
- **D-018 `allow_always` on a Claude tool permission is sent as a plain allow.** Writing per-session rules into the user's Claude settings is out of scope; the UI still offers the button so both runtimes present the same choices.
