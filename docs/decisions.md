# Decision log

Material implementation decisions, newest first. The spec (`docs/roadmaps/Personal_Agent_Workspace_Technical_Spec_and_Roadmap.md`) is the requirement source; this log records deviations and choices the spec left open.

## 2026-11-01 (distribution)

- **D-051 The Mac app stays on Developer ID outside the Mac App Store; the iOS companion goes to TestFlight; Developer ID Mac builds keep secrets in the data-protection keychain in a group the app and the coordinator share.** Research: `docs/research/reports/App Store and TestFlight signing.md`. **Mac:** TestFlight for Mac and the Mac App Store both require App Sandbox on every executable (Guideline 2.4.5(i), ITMS-90296), and three core features cannot run in it: the user's own `codex`, `claude`, and `node` (a sandboxed process may execute only inside its allowlist, and children inherit the sandbox); the bundled PostgreSQL (its System V shared memory and semaphores are denied); and the LaunchAgent the app writes into `~/Library/LaunchAgents`, with the socket in `$TMPDIR`. So the Mac app ships notarized Developer ID builds only (D-039). **iOS:** `Scripts/upload-ios.sh` archives and exports with method `app-store-connect`, destination `upload`, automatic cloud-managed signing, and a Team App Store Connect API key with the Admin role (`B4APP_ASC_KEY_ID`, `B4APP_ASC_ISSUER_ID`, the `.p8` file outside the repository). Builds are internal-only unless `B4APP_TESTFLIGHT_EXTERNAL=1`, and the build number is the UTC time (`yymmddHHMM`). Both targets now read their versions from `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION`. The iOS bundle declares `ITSAppUsesNonExemptEncryption = NO` (HTTPS through URLSession only) and a local-network usage string, and carries `PrivacyInfo.xcprivacy`: no tracking, no data collected by the developer, and no required-reason API, which was checked in the iOS-linked modules. A post-build script removes the localhost ATS exception outside Debug, since on a device `localhost` is the phone. **Team id:** `Config/Signing.xcconfig` is committed with an empty `DEVELOPMENT_TEAM` and includes the gitignored `Config/Signing.local.xcconfig`. `project.yml` sets no team, and the scripts pass `DEVELOPMENT_TEAM` (the iOS script reads it from the Developer ID certificate or `B4APP_TEAM_ID`). CI keeps building with `CODE_SIGNING_ALLOWED=NO`, and iOS Simulator builds still sign to run locally. **Mac keychain:** this supersedes D-008 for Developer ID builds. TN3137 says data-protection access groups come only from entitlements a provisioning profile authorises, and a bare tool has nowhere to embed one, so the coordinator is now a background-only app bundle, `Contents/Helpers/B4AppCoordinator.app` (`com.cacheplane.b4app.coordinator`, `LSUIElement`). The LaunchAgent, the CLI's lookup, and the app run `B4AppCoordinator.app/Contents/MacOS/b4app-coordinator` directly, and the app rewrites an existing user agent plist that points at the old path. The owner registers the App IDs `com.cacheplane.b4app` and `com.cacheplane.b4app.coordinator` with Keychain Sharing and creates a Developer ID profile for each. `Scripts/package.sh` then checks each profile (App ID, team, the group, expiry) and embeds it as `Contents/embedded.provisionprofile`. It generates the entitlements from the certificate's team id: `com.apple.application-identifier`, `com.apple.developer.team-identifier`, and `keychain-access-groups` = `<team>.com.cacheplane.b4app.shared`. It signs inside out (PostgreSQL, the CLI with the identifier `com.cacheplane.b4app.agent-workspace`, the coordinator bundle, the app) and confirms both signatures claim the group. A notarized build must also pass `syspolicy_check distribution`. `KeychainSecretStore.forCurrentProcess()` reads the process's own `keychain-access-groups` (`SecTaskCopyValueForEntitlement`): a process that claims the shared group uses the data-protection keychain in it, and anything else (`swift build`, tests, ad hoc packages, or `B4APP_SKIP_PROFILES=1`) stays in the file-based login keychain, since it has no profile. A data-protection store moves an item it lacks out of the login keychain on first read (read, add, delete), so each old item can prompt once, because the coordinator's signature changed. Every query sets `kSecUseDataProtectionKeychain` explicitly, `false` for the login keychain: with no flag, a process that claims keychain entitlements reads the data-protection copy first and deletes from both, which lost the owner's hub token on the first live move (2026-11-01, `docs/verification.md`). `doctor` names the store in use. A probe on this Mac (2026-11-01) showed why the file-based keychain alone is no longer a reason to move: a Developer ID rebuild with a new code hash read an item without a prompt, where an ad hoc rebuild returned -25293. The data-protection keychain was chosen anyway because the owner wants the full provisioning flow, it is Apple's default for new code, and the file-based keychain is on its way to deprecation. **Expiry:** a Developer ID profile lasts 18 years, but an app whose profile has expired no longer launches, so `package.sh` refuses an expired profile and prints each expiry. Renewing the Developer ID certificate means regenerating both profiles before the next release.

## 2026-11-01 (M8b)

- **D-050 The hub cuts pull pages by stored value size, prunes its change log on a schedule, and restores a stale reader from one unpaged snapshot.** A pull page stops at 1000 changes or 8 MiB (8,388,608 bytes) of `value`, whichever comes first, and always holds at least one change, so a page of one 2 MiB change still moves. The size is not measured at read time: `changes.value_bytes` is the length of the value as PostgreSQL's `jsonb` text (a few bytes more than compact JSON), stored when the change is pushed, and the page is cut in SQL with a running sum over those integers, selecting `value` only for the rows inside the cut. A first version streamed 1001 rows out of PostgreSQL to find the cut, and the byte limit exists to bound work as well as memory. `changes.received_at` (`now()` at insert) is what pruning reads, not `wall`, so a device with a wrong clock cannot make its own rows look old. `serve` prunes every org when it starts and every 24 hours after; `B4HUB_RETENTION_DAYS` sets the retention (default 30; anything but a whole number of at least 1 is a configuration error and exits 2), and `b4hub prune --older-than-days N [--org slug]` does it once. Pruning takes the same per-org advisory lock a push holds, deletes every change received before the cutoff and every change with a lower `hub_seq` (the horizon is one cursor, so what remains is a contiguous tail), and raises `org_sync_horizons.horizon` to the highest `hub_seq` it deleted; the horizon never moves down and the materialised tables are not touched, because the log is history and the tables are state. A pull whose `after` is below the horizon answers `410 resync_required`; the check and the page are read in one database snapshot, so a prune that commits mid-pull cannot leave the reader a gap. The reader then calls `GET /v1/snapshot`, one `REPEATABLE READ` transaction that returns this user's rows as synthetic `insert` changes in dependency order (`hubSeq` 0, `deviceSeq` 0, `wall` 0, `deviceId` the row's owner), the per-column clocks of those rows, and `next`, the highest `hub_seq` the org's feed had at that instant (or the horizon, if pruning emptied the feed). A snapshot row's `hlc` is the greatest of its clocked columns' clocks, or `000000000000-0000-<owner device>` when none was ever set, so any later change of the row wins over it. The Mac applies the snapshot through the same narrow merge as any pull (D-049), so its rows stay and only phone-writable values are compared by clock; the phone clears its rows, keeps its outbox, applies the snapshot, re-applies the unsent outbox rows on top, and continues from `next`. **An uncut page's `next` is the highest `hub_seq` the org has recorded (at least `after`), even when that is another user's change.** Without this rule a user whose feed is idle would keep a cursor that other users' activity pushes below the horizon, and would resync every 30 days for nothing; nothing of theirs can lie in between, because pushes commit in `hub_seq` order. `GET /v1/devices` lists the user's devices (revoked ones included) for the mirror's device names. Migration `0003_organisation.sql` adds `changes.hlc`, `received_at`, and `value_bytes`, `owner_device_id` on every materialised table, `projects`, `projectFolders`, `column_clocks`, `org_sync_horizons`, and `threads."projectId"` and `"readTurnId"`. `serve` now also refuses a connection that inherits superuser, `BYPASSRLS`, or ownership of the tables through a role it is an `INHERIT` member of (`pg_has_role(current_user, oid, 'USAGE')` over the role graph), not only a role that has the attribute itself. Known limitations: the snapshot is not paged, so the hub builds the user's whole mirror in memory in one response; the first prune after a long gap deletes the whole prefix in one transaction while holding the push lock, and `received_at` has no index; the privileged-role check counts only ownership of `changes`, and a `NOINHERIT` member of a superuser can still `SET ROLE` (for a security review); the migration's backfill of `value_bytes` and `owner_device_id` is a full-table update. Amends the retention horizon and the page and value limits of D-043.
- **D-049 Concurrent edits merge by hybrid logical clock, column by column, and the phone may write a short list of columns that the hub and the Mac both enforce.** A clock is `<12 lowercase hex digits of epoch milliseconds>-<4 hex digits of counter>-<device id>`, compared as plain strings (SQL compares them `COLLATE "C"` so no locale can reorder them). The Mac's `WorkspaceDatabase.write` takes the next value from a coordinator-wide `HybridClock` and sets it as `b4app.hlc` beside `b4app.device_id`; the change-log trigger stores it in the new `changes.hlc`, so every change in one transaction shares one clock, and falls back to `<wall>-0000-<device>` when none is set. The phone's `MirrorStore` stamps its outbox from its own clock. Every store advances its clock past each clock it receives, and clamps a received clock more than 300,000 ms ahead of its own wall clock to its own milliseconds with counter `0000` and the original device id, so a fast clock cannot win every later conflict; the clamped value is what is stored and served. **Merged columns:** `threads.title`, `pinned`, `archived`, `readTurnId`, `projects.name`, and `drafts.threadId`, `text`, `updatedAt` (the phone-writable list), plus `threads.projectId`, which only the Mac writes but rewrites when folders move. Each store keeps the clock of each such column (`columnClocks` locally and in the mirror, `column_clocks` on the hub); an incoming change to one applies only if its clock is greater, an `insert` counts as one write per such column it carries, and the Mac's own trigger keeps `columnClocks` current so a later pull of an older edit cannot overwrite a newer local one. Everything else applies as in M8a. The list is data in `b4hub-core` (`writable.rs`) and in `WorkspaceProtocol` (`SyncColumns`), kept equal by tests that read the trigger's SQL arrays back and compare hand-written lists, not by a shared fixture. **The write rule is by platform, not by row owner:** a `macos` device may write any column; an `ios` or `cli` device may `update` only the phone-writable columns, `insert` rows of `drafts`, and never `delete`, so a Mac that rejoins and re-uploads every row as inserts is not refused on its own rows. A draft is cleared by setting `text` to `''`, never by deleting the row (`SessionService` calls `clearDraft`, which keeps the row; the row goes with its thread), which makes clearing an ordinary last-writer-wins write. **Ownership:** a row's owner is the device of its latest `insert` (`owner_device_id` on the hub, `ownerDeviceId` in the mirror, `ownerDeviceName` on the thread for the header); an `update` never changes it, so `hub leave` then `hub join` makes the rejoined Mac the owner again with no rewrite, and M8c will route relayed commands with it. **A refused change never stalls the queue.** The hub applies a push change by change and answers `rejected: [{deviceSeq, code}]` with `column_not_writable`, `payload_too_large` (a `value` over 2 MiB, which M8a answered with a 413 that blocked the Mac's queue for good; the 413 now remains only for a body over 32 MiB), or `invalid_clock` (an `hlc` present but malformed; a change with none is stamped from its `wall`); `acceptedThrough` still covers every refused change and the client must not resend it. A refused change is not appended to the log and not applied; a change that loses the clock comparison is appended (the log is history) but writes nothing. `HubSync` marks rejected changes synced and records their count in `lastError` without suspending, and the phone does the same and persists the refused-upload count in `syncState`. The wire gains `hlc` on `Change` and `StoredChange` (a client without it keeps working, and the minimum client protocol stays 1). **The coordinator pulls.** `HubPull` long-polls beside the push loop and applies other devices' changes through `WorkspaceDatabase.applyRemote`, which runs with `b4app.replaying` on (nothing is re-recorded or echoed) and is a narrow merge, never a row copy: the hub holds only filtered copies of the Mac's rows, so it applies only `update`s of `threads.title`, `pinned`, `archived`, `readTurnId` and `projects.name` on rows that exist locally and inserts or updates of `drafts` rows whose thread exists, in each case by clock. It skips everything else, including every Mac-only column and every change from a `macos` device (the Mac's own rows coming back after a rejoin, a snapshot's blanked values, a pull from zero). It applies nothing until its first successful `devices()` call and counts revoked `macos` devices as Macs, so a rejoined Mac cannot re-apply its own old rows. A change whose parent row is missing is skipped under its own savepoint (`replay` gets the same savepoint, because it threw on a foreign-key violation despite its comment), only data errors (SQLSTATE class 22 and 23) are swallowed per change, any other error fails the batch, and the rows being merged are locked before their clocks are read so an older pulled value cannot overwrite a concurrent newer local edit. **Local writes and pulled batches are ordered by one transaction-scoped advisory lock:** every `WorkspaceDatabase.write` takes it shared as its first statement, before it sets `b4app.hlc`, and `applyRemote` takes it exclusive first, so a local edit that starts while a batch is in flight waits for the batch to commit and is stamped after every clock it applied (it wins, and the Mac and the hub hold the same clock), and a pull never holds a row lock a local write waits on, so the two cannot deadlock; the `FOR UPDATE` row locks stay, never wait now, and double as the existence checks. **The phone's mirror** applies a write at once and appends it to an `outbox` (`deviceSeq`, `hlc`, table, row, column, value); `MirrorSync` pushes the outbox before every pull, in requests of at most 500 rows and 8 MiB of encoded changes but always at least one (the rule of the Mac's `HubSync.batch`; a backlog over the hub's 32 MiB body limit would otherwise be refused with 413 on every retry, and the push precedes the pull), and removes rows only through `acceptedThrough`. A new local update of a column that already has an update queued and never handed to a push replaces that row's value and clock and keeps its `deviceSeq`, so offline typing queues one row per column; rows handed to a push this session, and every row present when the file was opened, are never touched, since the hub may hold them and would ignore a resend as a repeat. Mirror schema v2 (migrations keyed by `user_version`) adds `projects`, `projectFolders`, `devices`, `outbox`, `columnClocks`, `ownerDeviceId`, `threads.projectId`, and `threads.readTurnId`. A file newer than the app knows, or one whose migration fails, is rebuilt only if its outbox is empty (a failing migration with unsent edits keeps the file and reports the error instead), and **a rebuild carries the hub link and the outbox's `deviceSeq` high-water mark together or neither**: a link restored without its counter would reuse sequence numbers the hub already holds, which count as accepted and silently lose the edits. As a second guard, before its first real push the phone sends an empty batch and raises its sequence to the `acceptedThrough` the hub answers, which for an empty batch is the highest `deviceSeq` the hub has recorded for that device. Archive version 3 (`db backup`) adds the new tables; local migration `0004_organisation.sql` adds `projects`, `projectFolders`, `threads.projectId` and `readTurnId` (backfilled, see D-048), `changes.hlc` (backfilled from `wall`), `columnClocks`, an index on `runtimeRequests("threadId", "state")`, and the new triggers. Known limitations, none of them data loss in the common case: **rows written before the migration have no column clocks (the backfilled read markers aside), and a missing clock counts as oldest, so the first clocked edit after the migration wins whatever its time**; every local write waits while a pull batch is applied (one batch is at most a page of 1000 changes); the phone collapses only edits made since its last push attempt, so a phone retrying offline still queues one row per column per attempt; a clamped clock is stored by the receiver, and a receiver whose own clock is more than five minutes behind the sender clamps legitimate clocks to its own time, so clamping on receipt is not idempotent and two stores can hold different clocks for the same change; two concurrent local write transactions can leave `columnClocks` ahead of the stored value (the coordinator is the single writer); a change refused by the hub (a phone edit to a Mac-only column, an oversized value) stays applied on the phone until a snapshot or a newer write replaces it, and the count shows only in Diagnostics; a repeatable non-data error in `applyRemote` stalls the pull with backoff, a permanent push error also blocks pulling (no read-only fallback), and a successful push clears a "Pull: …" `lastError`; a second Mac's first edits can apply as a phone's for up to a minute, until `devices()` refreshes (one Mac per user is assumed); and the phone refuses `project.create`, `update`, and `delete` with `unsupportedCapability` naming "the Mac". Amends the phone-writes sentence of D-046 and the push-limit sentence of D-043.
- **D-048 Threads belong to projects, and every list shows them in one attention order computed by the same code on both devices.** A project is a named set of folders on one Mac; a thread belongs to the project that owns its working directory exactly, so a subfolder is its own project. Paths are matched in the coordinator's canonical form (tilde expanded, symlinks resolved, no trailing slash), `projectFolders.path` stores that form, and `threads.context` is never rewritten, because Codex and Claude receive it as the working directory. The coordinator creates an automatic project (empty name, shown as the folder's last path component) when a thread's folder has none, resolving the project and inserting the thread in one actor section so a concurrent create cannot split them. A thread on a local B4 connection belongs to the project of its managed server's directory; a thread on a remote B4 connection has none and appears under "Other". A folder belongs to at most one project: adding one to a manual project moves it out of its automatic project, an automatic project left with no folders is deleted, and adding a folder that already belongs to another manual project is refused (`protocolInvalid`) rather than moved, as is an unknown path in `project.update`. Deleting a manual project returns its folders to automatic projects; renaming one to the empty string restores the folder-name display. `project.list|create|update|rename|delete` and the `project.changed` event are coordinator commands (the mirror answers `project.list` and `project.rename`); local migration `0004` backfills automatic projects from existing threads' canonical folders and local servers' directories, with the log recording it so it syncs, and marks every existing thread read at its latest turn when that turn is terminal (latest by `createdAt`, then greatest `id`, `COLLATE "C"`; a thread still working keeps a null marker), also through the logging trigger, so the upgrade turns no old reply unread and the markers reach the phone. Each thread falls in one band, tested in this order: needs input (a runtime request in state `pending`, on any turn), working (the latest turn, by `createdAt` then greatest `id`, is not terminal), unread reply (the latest turn is terminal, a failure included, and its id is not `threads.readTurnId`), and quiet. Display order is pinned first, then needs input, unread, working, quiet; inside a band, `lastActivityAt` descending, ties by thread id. `lastActivityAt` is the latest of the thread's `createdAt`, its latest turn's `updatedAt`, and its latest request's `updatedAt`, never `threads.updatedAt`, so pinning, renaming, or reading a thread cannot reshuffle the list. `ConversationThread.activity` carries these facts; the coordinator computes them in SQL and `MirrorStore` in SQLite, both against `Tests/Fixtures/sync/attention.json`, and `Attention` in `WorkspaceProtocol` computes bands and order on both platforms; nothing about bands is stored or synced. `readTurnId` is Brian's, not a device's, so reading on the Mac clears unread on the phone. `thread.markRead` is sent when a thread is open and its latest terminal turn is on screen, once per (thread, turn); "on screen" is `WorkspaceModel.isDetailOnScreen`, which the views set only while the scene is active, the Mac's window is active, and on a compact width the detail column is the one showing, because the open thread stays loaded behind the iPhone's list and the Mac's inactive window, so a reply arriving there stays unread until the thread comes back on screen, and the store accepts a terminal turn not earlier than the current marker and never touches `threads.updatedAt`; "Mark as Unread" (set to null) is offered only for quiet threads. The Mac sidebar has "Pinned", then one collapsible section per project ordered by its best band and then its most recent activity, then "Other" always last; collapsed state is `@SceneStorage` and never syncs. The iPhone has one flat list whose filter menu replaces the connection picker (All projects, each project, Other, Archived, then the connections). Each row shows a status dot, title, project, connection kind, and a reason line ("Waiting for your approval", "Has a question for you", "Replied 3m ago", "Failed", "Working"). **The status dots follow D-036's one accent, not the per-state colours the plan first named:** needs input is a filled accent dot, unread a filled ink dot, working an ink ring that pulses gently only when Reduce Motion is off (never paler than the quiet dot), and quiet a small muted hollow ring, each with an accessibility label naming its band. Known limitations: projects and their folders are created and changed only on the Mac; the iPhone still shows the Mac's working directory (D-046); rows are three lines tall (a design call to revisit on the owner's word); every `thread.updated` makes the model refetch the whole thread, so a large pull is many reads (debounced about 200 ms per thread); the "New Project" and rename sheets compile on iOS but are unreachable there (the phone renames the project selected in its filter menu, through an alert, added in the live run); a folder whose symlink target changes can keep a thread out of its project until the next backfill; and the live gate for this decision passed on 2026-11-01 (`docs/verification.md`).

## 2026-10-31 (thread detail layout)

- **D-047 Nothing in a split-view column outside a scroll view may have a minimum height that grows with runtime text; the pending-request list scrolls past `LLA.Metrics.requestsMaxHeight`, and the detail must fit `LLA.Metrics.minimumWindow` at any content.** Opening a thread whose Claude turn waited on a `tool_permission` request blanked the whole macOS window, sidebar included, until relaunch: `NavigationSplitView` on macOS 26 measures its detail column's minimum size at an unspecified width, and the request card's command (`Text` with `fixedSize(horizontal: false, vertical: true)`) measured one character per line, 4,749 points for a 263-character command, so the split view drew nothing in either column; near the limit (a long reason, the continuity banner, the smallest window) the composer was pushed off the bottom instead, the shape of the PR #10 defect. `RuntimeRequestList` is now a scroll view capped at 240 points that sizes to its cards below the cap, so its minimum is bounded whatever a runtime sends and several requests scroll instead of displacing the composer; the continuity banner's explanation and the composer's error message drop `fixedSize` (they still wrap when there is room and truncate before the composer leaves the window); the app's window minimum is the shared `LLA.Metrics.minimumWindow`. `DetailMinimumSizeTests` pins it by measuring `ThreadsView` with `NSHostingController.sizeThatFits(in:)`, the question the split view asks, at zero width and at the detail column's minimum width, for the stored thread, a 3,000-character command and reason, two such requests, the continuity banner, and a long draft; the snapshot harness could not have caught it, since the real split view draws nothing off screen.

## 2026-10-31 (M8a)

- **D-046 The iOS app reads a SQLite mirror fed by the hub's change log through an in-process `WorkspaceTransport`, so the SwiftUI shell is unchanged across platforms; only threads created in the app sync.** Nothing is read from `~/.codex`, `~/.claude`, or a B4 server's history. Three Foundation-only modules were added. `WorkspaceSecrets` holds `SecretRef`, `SecretStore`, and `KeychainSecretStore`, moved out of `WorkspacePlatform` (which re-exports them) so the iOS target can use them without the macOS-only module; on iOS the item is in the data-protection keychain with `AfterFirstUnlockThisDeviceOnly`. `WorkspaceSync` holds the wire types, `HubAPI`, `HTTPHubAPI`, `FakeHubAPI`, and the `HubURL` rule (https anywhere; http only for `localhost`, `127.0.0.1`, `::1`), enforced by the coordinator's `hub join` and the phone's Connect screen before any request. `WorkspaceMirror` keeps STRICT SQLite tables with the Mac's column names (WAL, `synchronous` FULL, foreign keys, `busy_timeout` 5000), replays a change batch with the same semantics as `WorkspaceDatabase.replay`, blanks `authReference`, `localServerId`, and `target` again on the way in, and stores a row that does not decode through the protocol types, skips it on read, and counts it in `SyncDiagnostic.undecodableRows` rather than dropping it or failing the batch. The Mac side is `HubSync` in the coordinator, the only code that talks to the hub: it pushes the trigger-written change log in batches of 500 rows or 8 MiB, marks rows `synced` only through the hub's `acceptedThrough`, is nudged by the event log, a 30 s timer, and wake, and suspends on a 401 until the next `hub join`. `SyncFilter` keeps only the 16 known `connections` columns on an insert (an allowlist; a non-object insert is dropped), blanks `connections.authReference`, `localServerId`, and `target` for every kind, replaces a `nativeScope` (on `connections` and `threads`) that contains `/`, such as a B4 origin URL or a Claude config directory, with `scope:` plus the first 16 hex characters of its SHA-256 (stable, so the mirror's uniqueness on connection, scope, and native thread holds), never uploads `localServers`, and replaces a `displayItems.payload` or `runtimeRequests.payload` over 1 MiB with `{"truncated": true, "bytes": n}` on inserts and updates; the wire carries no device id, the hub attributes every change to the authenticated device, and the Mac's `b4app.device_id` session setting is now set per write transaction from `hubLink`, so rows written before joining, recorded as `local`, need no rewrite. `database.restore` is refused while joined (`hub leave` first), because a restore rewrites the change log and its sequence, and reused device sequence numbers would count as already accepted at the hub and never be mirrored. `DiagnosticsReport.sync` is an additive optional field, and `ConnectionsView` hides an empty target path. `Tests/Fixtures/sync/changes.json` is the cross-language contract, decoded in place by the Rust and Swift suites; edit it only with both suites. Unimplemented behaviour (phone writes, the relay) throws `unsupportedCapability` naming M8b or M8c. `threads.context` (a harness thread's working directory, a B4 thread's route) syncs unchanged, by the owner's decision on 2026-11-01: transcripts already carry the same paths (a command item's `cwd`, file changes, output), so hashing this one column would only cost the phone its project label; keeping local paths off the hub altogether is a separate, larger decision (end-to-end encryption or transcript scrubbing), not taken in M8. *Amended by D-049 (2026-11-01): phone writes (titles, pins, archive, read markers, project names, drafts) exist as of M8b; the relay, turns, and thread creation from the phone still throw `unsupportedCapability` naming M8c, and project create, update, and delete name the Mac.*
- **D-045 A turn sent to a thread whose owning device is offline is refused, never queued.** The owner's decision; the refusal names the Mac's last-seen time. The relay (M8c) will route `turn.send`, `turn.interrupt`, and `request.respond` to the owning Mac; interrupts and request answers may be held for at most 60 s, and the first answer wins. Nothing of this is built in M8a, where the phone is read-only.
- **D-044 The hub owns users, organisations, devices, and credentials; no identity provider is bundled.** M8a enrolls a device with a one-time code: `b4hub enroll --user` mints eight characters from `BCDFGHJKLMNPQRSTVWXZ23456789` (no vowels, no `Y`, no `0` or `1`), valid ten minutes and single use, which a client redeems for a device token (32 random bytes, base64url). The hub stores only the token's SHA-256 and shows the token once. Revoking a device deletes its token rows and sets `devices.revoked_at`; the history it uploaded stays. The sign-in flows (PKCE for the apps, the device grant for the CLI, rotating refresh-token families, self-registration, SSO brokering) are M8d and extend these tables instead of replacing them. The enrollment code is read from the terminal with `readSecret`, never from an argument, and the phone clears its field once the request returns.
- **D-043 The hub is a Rust service in `Hub/`, one shared schema with `org_id` on every tenant table and row-level security enforced by the database.** The Cargo workspace is `b4hub-core` (pure types and rules), `b4hub-db` (sqlx), and `b4hub` (axum binary with `serve`, `migrate`, `seed`, `enroll`), edition 2021 on Rust 1.93.1, exact `=` pins, `Cargo.lock` committed, builds and tests run `--locked`, `unsafe_code` forbidden. It follows the conventions of the b4 Rust rewrite (`~/repos/b4`): B4's error envelope (`error.kind`, `error.message`, `error.details.code`; public errors never carry SQL, panics, or another tenant's data), authentication before the body is read, `deny_unknown_fields` on inbound bodies, a non-root container (uid 10001) with a `HEALTHCHECK` on `/readyz`, and a bounded drain on SIGTERM (`/readyz` fails first, new work is refused, long-polls finish, exit within `B4HUB_SHUTDOWN_WAIT_MS`, default 30000); configuration errors exit 2. Tenancy: RLS is enabled and forced on every tenant table with the policy `org_id = NULLIF(current_setting('b4hub.org_id', true), '')::uuid`, and each request transaction begins with `SELECT set_config('b4hub.org_id', $1, true)` using the org from the verified credential. The application role `b4hub_app` is provisioned by `migrate` from the password in `DATABASE_URL` (printable ASCII; the server receives only a client-computed SCRAM-SHA-256 verifier), is `NOSUPERUSER NOBYPASSRLS`, and does not own the tables, so there are two URLs: `DATABASE_ADMIN_URL` (owner; `migrate`, `seed`, `enroll`) and `DATABASE_URL` (`b4hub_app`; `serve` only). **Three tables carry no RLS.** `orgs` is the tenant directory. `device_tokens` and `enrollment_codes` are looked up by the hash of a secret the caller presents, before any org is known, so a tenant policy cannot apply; they hold only hashes, ids, and expiry, never synced content, and everything they lead to is then read under the org they name. The change log has `(org_id, device_id, device_seq)` unique for idempotent pushes and a per-org `hub_seq` bigserial as the reader's cursor; a per-org advisory lock keeps commit order equal to sequence order so a reader never skips a row that commits late. The six synced tables are materialised with the Mac's quoted camelCase columns plus `org_id`, `user_id`, `device_id`, keyed `(org_id, id)` with the client's text ids; hub-minted ids are UUIDv7. Every read and write is scoped to the token's `user_id`, and a missing resource and an inaccessible one answer the same generic 404. Limits: 2 MiB per change value (`MAX_PAYLOAD_BYTES`), 32 MiB per push body, 1000 changes per push, 1000 per pull page, and a long-poll `wait` capped at 25 s whose waiter is registered before the final emptiness check, so a push between the check and the wait is not missed. The retention horizon is 0 because M8a never prunes; `resync_required` (410) is answered only for a negative cursor until pruning exists. *Amended by D-049/D-050 (2026-11-01): a value over 2 MiB is rejected per change (`payload_too_large`) and no longer 413s the push (only a body over 32 MiB does); a pull page also stops at 8 MiB of stored value sizes; the hub prunes every 24 hours (`B4HUB_RETENTION_DAYS`, default 30), so the horizon moves and `resync_required` is answered for any cursor below it, restored from `GET /v1/snapshot`.*

## 2026-10-31 (M5)

- **D-031 Native history is merged into the cache by snapshot order; live rows are never deleted or duplicated.** `thread.reconcile` (and a plain `thread.read` whose cache is empty although turns were recorded) calls the adapter's `loadSession` and merges: a snapshot item whose native id is cached keeps that row (a live row keeps its payload, a snapshot row takes the new one); an id-less item that matches a cached item of the same role and text reuses that row; everything else is inserted with `snapshot` provenance in the snapshot's order; cached snapshot rows the runtime no longer reports are removed; live rows nothing matched (the turn in flight) follow at the end; sequences are renumbered in one transaction. Text matching is used only to recognise the app's own user messages, never as an exactly-once guarantee for runtime events (spec 10.1).
- **D-032 Quit offers "Quit" or "Stop local work and quit", never "keep running in the background"; threads whose native session is missing or whose connection now presents another identity stay readable and never resume.** The coordinator lives inside the app until the M6 LaunchAgent (D-004), so local turns end with the process either way; the dialog says so, names the local turns and owned servers, and states that attached and remote B4 runs continue on their server and are reconciled next launch. When another process hosts the coordinator the app owns nothing and quits at once. `connections.nativeScope` records the identity last presented; a thread created under a different scope is `identity_changed`, a runtime that lost the session is `missing`; both keep the cached transcript, refuse `turn.send` with a stable code, and offer a new thread (spec 3.3, 5.1).

Because the state is the turns themselves, the lock survives restarts and holds through `waiting_for_user`, `stopping`, and `reconciling` (spec 10.1.5); `turn.abandon` releases it deliberately. B4 routes are not directories.
- **D-034 Wake is detected twice: `NSWorkspace.didWakeNotification` in the app and a clock-gap watcher in the coordinator.** `ContinuousClock` keeps counting while the Mac sleeps and `SuspendingClock` does not; a drift over 20 s between two five-second ticks means a wake and triggers `workspace.reconcile`, so a CLI-spawned coordinator with no app also reconciles. ## 2026-10-31 (M4)

- **D-024 Managed servers are spawned with `posix_spawn` into their own process group, with stdout and stderr redirected to a per-server log file, not through `StreamingProcess`.** The pipe-based helper ties a child's life to the coordinator (an orphaned Node process dies on its next write to a closed pipe) and loses its output across a coordinator restart. The file keeps the server independent so an app Quit or a coordinator crash never loses a running server, and the process group lets a stop reach a runtime child that outlived `b4 dev`. The spawn also resets the child's signal mask and the dispositions of SIGTERM, SIGINT, SIGHUP, SIGPIPE, SIGQUIT, and SIGCHLD: the coordinator ignores several of those and dispositions survive exec, and a blocked SIGTERM inherited from the spawning thread left a server that only SIGKILL could stop.
- **D-025 Ownership is `(pid, process start time within one second, argv containing the CLI entry file and the port)` from `KERN_PROC_PID` and `KERN_PROCARGS2`, captured at spawn and re-verified before every signal and on every coordinator start.** A pid or a listening port alone never establishes ownership; a mismatch leaves the process alone and marks the registration stopped with a message naming the pid.
- **D-026 The project-installed CLI runs as `<node> <project>/node_modules/@b4run/cli/dist/index.js`, never through `node_modules/.bin/b4` or a shell, and is never downloaded.** The pnpm shim resolves `node` from `PATH`, which a Finder-launched app does not have. The version is read from the package's `package.json`; the minimum is 0.15.7. Inspection (`b4 routes --json --cwd <project>`) executes the project's config and route modules, so registration is the trust decision and both the CLI and the form say so.
- **D-027 A registration allocates its loopback port once (or takes `--port`) and keeps it, so route connections have a stable origin; a start whose port is taken fails with `owned_process_conflict` and stops nothing.** The port cannot change once a route connection references the server, because managed connections carry `http://127.0.0.1:<port>` as their target and threads use that origin as their native scope.
- **D-028 Source mode (`b4 start --host 127.0.0.1 --port N` with a coordinator-built environment parsed from the env file without shell evaluation) is the default; development mode (`b4 dev --port N --env-file P`) is explicit** because hot reload can replace the runtime mid-turn. The child environment is `PATH` (the Node directory plus the system directories), `HOME`, `TMPDIR`, `LANG`, `USER`, `SHELL`, and the env-file pairs; nothing else of the coordinator's environment leaks in, and env-file values exist only in the spawn call. `envFilePath` defaults to `<project>/.env` when present. `start`, `restart`, `add`, and `inspect` block until readiness (`GET /healthz` within 90 s) or discovery finishes; a concurrent start joins the one in flight.

Log lines are never published as events, so a chatty server cannot evict conversation events from the replay buffer; `--follow` and the GUI poll `server.logs` with the last offset.
- **D-030 `server stop` and `server restart` refuse with `owned_process_conflict` (`reason: turn_active`) while a route connection has a turn in `submitting`, `running`, or `stopping`, unless forced**, because stopping loses the in-memory run. A parked prompt is durable in `.b4` and a `reconciling` turn is already lost, so neither blocks. The CLI takes `--force`; the GUI confirms. The M5 Quit dialog builds on the same check.

## 2026-10-31

- **D-019 A B4 turn's native id is its ordinal in `GET /threads/:id/turns`.** The Agent Protocol has no run id (the thread id is the run identity). Reading the turn count before `POST /runs/stream` and naming the turn `turn-<n+1>` lets reconciliation tell "the server ran it" (the nth turn exists, with its recorded status) from "the prompt never arrived" (it does not) without ever resubmitting. When the count cannot be read the id falls back to `run-<uuid>` and reconciliation relies on the thread status alone.
- **D-020 Parked versus cancelled is decided by `GET /threads/:id/pending_interrupts`, never by the `interrupted` status alone.** B4 writes `interrupted` for both. A non-empty list is a parked prompt: the turn stays `waiting_for_user` across stream loss and coordinator restart, and the prompt is re-opened from the durable `value` under a new adapter generation. An empty list is a cancellation.
- **D-021 Permission answers go through `POST /threads/:id/resume` with B4's own decisions.** `allow_once` → `once`, `allow_always` → `always` (B4 persists the pattern itself, unlike Claude in D-018; `once` when the prompt said `allowAlways: false`), `deny` → `deny`, decline → `status: cancelled`, each echoing the prompt's `grant`.
