# Decision log

Material implementation decisions, newest first. The spec (`docs/roadmaps/Personal_Agent_Workspace_Technical_Spec_and_Roadmap.md`) is the requirement source; this log records deviations and choices the spec left open.

## 2026-11-02 (hosted hub deployment)

Design `docs/deployment-architecture.md`, approved by the owner 2026-11-02. Research: `docs/research/reports/Managed hosting for the b4 hub.md`. Not built yet: these record what the hosted-hub project will build.

- **D-068 The hosted hubs run on AWS from day one, as ECS on Fargate behind an Application Load Balancer with RDS for PostgreSQL, one AWS account per environment under an Organization, in `us-east-2`; cacheplane operates no Kubernetes for them.** The owner's decision after research that recommended Fly.io plus Neon for about $40 a month: "I think we need to do AWS from day one." The reasons AWS won are that Neon has no cross-region path, that the "later" tier (a second region, Aurora Global Database) is then an addition rather than a migration, and that AWS is the only candidate with published failover figures. The owner excluded Google Cloud and Cloudflare, which also removed Render and DigitalOcean (both front their edge with Cloudflare); Heroku's fixed 30 s SIGTERM is under the hub's 35 s drain, AWS App Runner is closed to new customers, and Railway's October 2026 breach decrypted customer environment variables. Each environment runs one task with recreate deploys (a 45 to 90 s outage per deploy, tolerated because D-057 keeps relay routing in process memory and D-054's clients resume from their cursor) until M8e adds cross-instance routing. The "now" tier costs about $110 a month for both environments.
- **D-069 Infrastructure is Terraform in `Infra/`, applied by GitHub Actions over OIDC; test applies on merge to `main`, production on merge with the owner's approval in the `production` Environment; no long-lived cloud credential and no secret value exists in Terraform, state, or GitHub.** Three roles per account from a one-time bootstrap: a read-only plan role for pull requests, a broad infra-apply role under a permissions boundary, and a narrow application-deploy role. Secrets Manager secrets are created empty by Terraform and filled once by the owner from a terminal; the RDS master password stays RDS-managed and is used once, at bootstrap, to create `b4hub_owner`, which runs every migration from then on. The owner's direction: "Terraform".
- **D-070 Releases are tagged `hub-v<semver>`; test deploys on every merge to `main` and production on a published release, always by immutable image digest with attestation verification, after a one-off migration task that alone holds the privileged database URL.** The owner's release model: "main is latest, we build nightly artifacts using main, production is a release." The canonical registry is public GHCR (`ghcr.io/cacheplane/b4hub`), copied by digest into each account's ECR by the deploy role (an ECR pull-through cache would need a GitHub token stored in every account). A release never builds: it deploys the digest already built for its commit on `main` or fails. Migrations are forward-only; rollback redeploys the previous digest. Nightly images build from `main` and deploy nothing. Operator commands (`seed`, `enroll`, bootstrap SQL) run through a `hub-admin` task with ECS Exec, so an enrollment code reaches only the owner's terminal.
- **D-071 Edge protection is the hub's own limits plus a WAF rate rule and IP reputation list; no body-inspecting managed rule group is attached.** The AWS Common Rule Set blocks bodies over 8 KB, and `POST /v1/changes` legitimately carries up to 32 MiB; its injection rules would false-positive on `displayItems` payloads, which are agent transcripts. TLS 1.2 minimum at the load balancer; HSTS and `Cache-Control: no-store` on auth routes are set by the hub so on-prem gets them too. Backups are AWS Backup daily snapshots with a cross-region copy in production, restored in a monthly drill; external uptime probes (Better Stack) page the owner, because an alarm inside an unreachable region cannot.
- **D-072 Self-hosting ships as a Compose production profile and a `b4hub` Helm chart with an external database, a pre-upgrade hook migration Job, and file-mounted secrets; both are built in this project.** The owner: "lay it out even if they come later, I want the docs", then "Built here." The chart uses no library chart (Bitnami's catalogue was paywalled in 2025), requires `database.existingSecret` with a CloudNativePG example, defaults to one replica with `strategy: Recreate` and Restricted Pod Security Standard settings, renders a controller-agnostic Ingress or a Gateway API `HTTPRoute`, and is published as an OCI artifact on GHCR signed with cosign. Compose keeps the migrate-then-serve split (`service_completed_successfully`), reads secrets through the hub's `*_FILE` variables, and offers Caddy for TLS as an optional profile. Both tell operators their proxy must append the client address, which is what `B4HUB_TRUST_X_FORWARDED_FOR=1` assumes and what the AWS load balancer does.

## 2026-11-01 (sign-in design)

Designed, not built: `docs/superpowers/specs/2026-11-01-sign-in-design.md` and `docs/superpowers/plans/2026-11-01-sign-in.md`. Research: `docs/research/reports/Mac App Store sandbox for agents.md`.

- **D-062 The Mac ships only as a notarized Developer ID download and a Homebrew cask; there is no Mac App Store or TestFlight-for-Mac build.** Amends D-051. Both channels require App Sandbox on every executable. A sandboxed process can execute nothing outside its bundle and a few system locations; no file grant adds execute permission, and Apple DTS says so. Children inherit the sandbox with `HOME` moved into the container, so the user's `codex`, `claude`, and `node` cannot run, and their `~/.codex` and `~/.claude` logins are invisible. App Review rejected a home-folder exception for an agent-CLI app in April 2026. PostgreSQL needs System V IPC, which the sandbox denies, and a sandboxed app cannot write the LaunchAgent. T3 Code, ChatGPT/Codex, Claude desktop, Zed, Warp, and Conductor all ship outside the store unsandboxed; Xcode runs agents from the store only because Apple exempts it. Bundling our own agents was rejected: they could not run the user's toolchains, they would need a second login, every model update would wait on review, and Claude Code's terms forbid modifying the binary, which Apple's re-signing may count as. The iPhone app ships through the App Store and TestFlight as D-051 set up. The owner's words: "macOS is installed like codex and claude - download or homebrew."
- **D-063 Three build flavours, `prod`, `beta`, and `local`, each with its hub, site domain, and identifiers.** `prod` is the App Store iPhone app and the b4.run Mac download, against `https://hub.b4.run` with passkeys on `b4.run`. `beta` is TestFlight and a Mac beta download, against `https://hub.test.b4.run` on `test.b4.run`. `local` is built on the owner's Mac, against `http://localhost:8080` with passkeys on `local.b4.run`, Apple sign-in hidden, and its iPhone build Simulator-only. The flavour is an `Info.plist` key read at run time (`Flavor.current`), because Xcode does not pass an app's compilation conditions to package targets. Bundle ids, data directories, LaunchAgent labels, URL schemes, and keychain groups carry a `.beta`/`.local` (or `-beta`/`-local`) suffix, so flavours coexist on one Mac. Each flavour has its own relying-party id, so a test passkey never appears when signing in to prod. `local.b4.run` serves only the association file the OS requires before an app may use a passkey; the hub that verifies it can run on `localhost`, because WebAuthn checks the signed origin, not the server's address. The owner's current install becomes `local`: its data directory moves to `b4app-local`, and its hub token moves out of the prod keychain group, which the local flavour also claims for that one read.
- **D-064 Accounts are created by signing in with an Apple ID or a passkey, and each gets a private org.** The hub verifies both itself: Apple identity tokens against Apple's JWKS, and passkeys with `webauthn-rs`, discoverable and with user verification required. Each sign-in ends in today's device token. One button per method signs in or signs up. A passkey sign-up asks for nothing until the OS reports no passkey, then confirms before creating an account. Onboarding asks only for the full name; the owner removed the phone number after App Review's rule against requiring unused personal data came up. The org is named "<first name>'s Org". Developer ID Mac apps cannot use the native Sign in with Apple sheet (the capability is App Store-only), so the Mac uses Apple's web flow through the hub, with a Services ID, a form-post callback, and a one-time handoff bound to a verifier. Apple refresh tokens are kept encrypted so account deletion can revoke them (App Store guideline 5.1.1(v)). Sign-up is `B4HUB_SIGNUP=open|closed`, default closed, so an on-prem hub never grows accounts by accident. Enrolled users are marked onboarded, and `b4hub enroll` stays as the operator path. Narrows the M8 design's M8d: no email or password, no CLI device grant, no shared orgs.
- **D-065 The Mac keeps one database per account and adopts the existing one; Log out ends the session and keeps the device.** A `registry` database lists the accounts that have signed in on this Mac. Each account has its own `workspace_<16 hex>` database in the same cluster (the existing `workspace` database is adopted as the first account's), and the coordinator runs one `AccountScope` (database, sessions, servers, projects, sync, link) for the active account. Signing in as the same or another account resumes exactly where that account left off. Store commands answer `signed_out` while nobody is signed in. Log out confirms when work is running, stops turns and owned servers, pushes what is unsynced (each step bounded at 10 s), then deletes this session's token on the hub but not the device, so signing back in reuses the device id and the sync cursor. A hub 401 signs the account out with a reason the sign-in screen shows. The iPhone keeps D-053's Log out, which empties the mirror, and returns to the sign-in screen.
- **D-066 Pairing links are `https://<site>/pair#c=<code>` universal links, and a scan signs the phone in.** Amends D-058. The site domain implies the hub, and the code after `#` never reaches a web server's log. The iPhone app claims `/pair`, so the system Camera opens it; without the app the page points to the App Store. A scan signs a signed-out phone in. It merges a phone-only account into the Mac's: its identities move and the empty user and org are deleted, so the person never lands in an empty account again. On an account that has its own Mac, it asks before switching. A new Mac account sees "Add your iPhone" once after onboarding. A phone whose account has no Mac sees "Connect your Mac", with Scan the code, Copy download link, and Help.
- **D-067 The hosted hubs are a separate project; the b4.run site serves the app's association files and pages under `/app/`.** The owner moved deploying `hub.b4.run` and `hub.test.b4.run` to a separate thread. This design states only what it needs from them. `/privacy` and `/docs` on b4.run already belong to B4, so the app's pages are `/app/download`, `/app/terms`, `/app/privacy`, and `/app/help/iphone`; `/pair` stays at the root to keep the QR link short. Mac zips go to GitHub Releases on `cacheplane/b4app`, and a `cacheplane/homebrew-tap` cask installs the prod build.

## 2026-11-01 (composer)

- **D-061 The composer is one rounded field in two shapes, with a round send button, and grows to three lines.** At the owner's direction ("behave like the input for iMessage, or ChatGPT"; chose the ChatGPT-style box from three mockups, "responsive to a single line on larger devices"; "be diligent and precise" about spacing and alignment). It replaces D-036's composer card with its hint row and Send/Stop pills.
  - Shapes: the box (every iPhone, and an iPad or Mac once the draft wraps or has a line break) holds the text on top and a tool row underneath with send at its trailing end; the line (iPad and Mac while the draft fits beside the button, and never at an accessibility text size) is a 44 pt capsule with send inline. `ComposerView.shape` decides from the field's width and the draft's natural width, so the shape cannot oscillate; one `AnyLayout` holds the same children in both shapes, so the text keeps focus when the shape changes.
  - Metrics: a 44 pt line and a 32 pt button, which sits 6 pt from every edge it touches, so it is concentric with the field's 22 pt corner. Corners are circular, not continuous: a continuous corner at half the height flattens the capsule's ends, and only a circular arc is concentric with the button. Text starts 16 pt in, and its first line is centred in the top 44 pt in both shapes, so nothing jumps when the shape changes; 4 pt between the text and the tool row. The line, the button, and the gaps grow with Dynamic Type up to 1.5 times (a 48 pt button at AX3). Measured in the Simulator and the Mac snapshots (`docs/verification.md`).
  - Text: Hanken Grotesk 16 pt relative to `.callout` on the phone (a step under the 17 pt replies, at the owner's "too large and strong"), the Mac's 15 pt body there; ink text, muted "Message <connection>" prompt, cobalt caret. It grows a line at a time to three, then scrolls inside. The phone uses a vertical `TextField` (no inner inset, so the text sits exactly on the grid; Return adds a line, the button sends); the Mac keeps `TextEditor`, whose Return the send button's shortcut takes and whose Shift-Return adds a line.
  - Send and stop: one round button in the same place, ink with the background-coloured arrow; while a turn runs it is a stop square, as in ChatGPT. Disabled, it is a raised-surface circle with a ghost glyph rather than faded ink. A round icon button departs from D-036's worded pills; the arrow and the square are the controls' meaning, not decoration, and each keeps its accessible name ("Send", "Stop") and a 44 pt target. The turn's state and, when its outcome is unknown, Check again and Abandon turn sit above the field, the words aligned with the text inside it (two lines at most on the Mac, whose smallest window must fit the detail).
  - On the phone the transcript scrolls on under the composer (`safeAreaBar`, with the system's soft scroll edge) instead of being cut off above a rule; the Mac keeps the rule.
  - Room for attachments: a turn carries text only today (Codex accepts images, Claude Code images and documents, B4 text). When it can carry more, a row of attachment previews goes between the text and the tool row, a non-empty row forces the box, and attach takes the tool row's leading end. Neither is drawn until something can be sent, so no control does nothing.

## 2026-11-01 (M8c relay design)

Design `docs/superpowers/specs/2026-11-01-m8c-relay-design.md`, approved by the owner 2026-11-01; plan `docs/superpowers/plans/2026-11-01-m8c-relay.md`. Not built yet: these record what M8c will build.

- **D-054 The relay is one WebSocket per joined device, and it carries commands, replies, presence, and live progress, never state.**
  - **Shape.** `GET /v1/devices/self/link`, authenticated with the device token before the upgrade. A `macos` device is a host and an `ios` or `cli` device is a client. A newer link replaces an older one.
  - **Timings.** Heartbeat every 10 s; a link silent for 30 s is dead. Reconnect with backoff from 1 s to 30 s, and at once on wake and on a network change.
  - **State.** The change log stays the only source of truth: nothing from the relay is written to the mirror, so the relay needs no cursor and a lost frame costs only a moment of streaming. This replaces the M8 design's reconnect-from-a-cursor paragraph for the relay.
  - **Presence.** `last_seen_at` is the last frame heard from the device.
- **D-055 Relayed commands are never stored, carry a deadline the Mac enforces, and are idempotent by phone-minted ids the Mac already stores.**
  - **Deadline.** The hub stamps each command with hub time + 10 s, and the Mac drops one that arrives late by its estimate of the hub's clock, so a frame buffered across a sleep never starts a turn.
  - **Idempotency.** `turn.send` uses the command id as the turn's `operationId`, which `SessionService` already deduplicates durably. `thread.start` uses a phone-minted `threadId` as well. `RelayExecutor` runs each id once at a time.
  - **Lost replies.** A reply that never came is "not confirmed". The phone resends the same id only within 30 s of the tap, and asks the Mac (`turn.lookup`) whether the turn exists, so a lost send is only ever declared by the Mac.
  - **First answer wins** is the Mac's existing `stale_runtime_request`, made true at the runtime by marking a request as being answered before the adapter call.
  - **Holds.** Interrupts and answers are held for an owner seen within 60 s (D-045); sends never are.
- **D-056 The phone keeps every thread readable when its Mac is unreachable.**
  - **Notice.** After a 60 s grace from the Mac's last-seen time (with "Reconnecting to your Mac…" until then), a notice names the Mac and its last-seen time. The composer, Stop, approvals, and new thread are disabled for that Mac's threads, and a turn still shown as active reads "Not confirmed while your Mac is offline". The owner's direction; the same notice replaces the list-hiding "Host disconnected" screen when the Mac has left the hub.
  - **Scope.** Presence is per Mac. A thread follows its owner, and the list follows the Mac with the most recent activity.
- **D-057 Only `ios` and `cli` devices send relayed commands, and only to their own Macs.**
  - **Methods.** Only `turn.send`, `turn.interrupt`, `request.respond`, `thread.start`, and the read-only `turn.lookup`, allowlisted on the hub and again on the Mac.
  - **Target.** Only a non-revoked `macos` device of the same user and org that owns the thread or project. Every miss is a generic `not_found`.
  - **Folders.** `thread.start` runs only in a folder its project lists, or on a local B4 connection serving that project.
  - **Limits.** In memory on the hub: 60 commands a minute per device, 20 sends a minute per user, 4 watched threads per phone, 64 KiB client frames and 256 KiB host frames.
  - **One replica.** The hub's routing state is in memory, so cross-replica routing waits for M8e.
- **D-058 A joined Mac pairs a phone by QR code.**
  - **Code.** `POST /v1/pairing-codes` mints a five-minute, single-use enrollment code for the Mac's own user (10 an hour).
  - **Mac.** The "Remote access" Settings page shows it as a `b4app://pair?hub=…&code=…` QR code, beside "Keep the Mac awake".
  - **Phone.** It scans the code (or opens the same link, which is how the Simulator is tested) and always asks before enrolling.
  - **Secret handling.** The code is a credential shown on purpose, like a typed enrollment code: it is never logged or stored, and lives only in the sheet. It is the one exception to keeping secrets out of UI state. The owner's direction, as part of M8c.
- **D-059 A local B4 connection's project syncs as `connections.projectId`, a Mac-only column, so the phone can start B4 threads in a project.** It is the owner's decision to include B4. The column holds a project id already on the hub, never a path, and needs no clock. Remote B4 threads belong to no project, so they are continued from the phone but never started there.

## 2026-11-01 (sidebar redesign)

- **D-053 The sidebar becomes a chat-app sidebar; Connections, Local servers, and Diagnostics move to a Settings window reached from a profile menu.** At the owner's direction (design `docs/superpowers/specs/2026-11-01-sidebar-profile-settings-design.md`, approved 2026-11-01). The sidebar holds, top to bottom: New thread (⌘N, also a `CommandGroup` in the Mac's File menu), Search (⌘K, a palette over the window on the Mac and a sheet on the iPhone, matching shown titles, so "untitled" finds an untitled thread), and More (on the Mac the "Show archived" switch that replaces M8b's inline one, and the connection filter; on the iPhone the project filter that used to sit in the toolbar), then M8b's thread list with no "Threads" label, then the profile button. There is no mark or title at the top and no surface rows; `Surface` is gone and the model has `SettingsPage` and a `settingsRequest` counter that the root view turns into `openSettings()` (Mac) or the Settings sheet (iPhone), so a remediation such as "Open Connections" now opens Settings at that page.

  Thread rows are one line: the attention dot, the title, and the runtime's mark in a ghosted grey (`LLA.Color.ghost`, light `#B8B8BC`, dark `#5A5A5E`). The reason line and the connection moved into the row's accessibility label, with "Pinned" and the connection's trouble when it is offline; the iPhone keeps a pin glyph, since its flat list has no Pinned group. The marks are real: the Anthropic mark from Simple Icons 16.36.0 and the OpenAI mark from Simple Icons 15.22.0, the last release that has it (16.0.0 removed it); both are CC0 path data, vendored in `Resources/Brand/` with a comment saying so, and the trademarks are their owners'. B4 has a "B4" monogram. The ghost colour is exempt from the 3:1 graphics floor because the marks are supplementary. The brand SVG reader gained arcs and run-together decimals, which those files use.

  The profile button shows initials (or a person glyph), the hub user's name (or "Not signed in"), and the coordinator state in a few words. The coordinator's error, the host's note, and a version mismatch appear as a notice above the button, three lines at most, because the footer sits outside the scroll view (D-047). The menu is the app's own panel rather than SwiftUI's `Menu`: a `Menu` opens downward from its label on the Mac and as a context menu on the iPhone, and the design needs it to open upward at the button's width on both. It holds Settings (⌘,), GitHub (https://github.com/cacheplane/b4app in the default browser), and Log out. The panel is lifted by the button's measured height; an alignment guide on the overlay was ignored and the panel drew over the button.

  Settings on the Mac is a `Settings` scene: a 200 pt sidenav in the sidebar's style beside the page, in a plain `HStack` (a nested split view would give the window a second collapsible sidebar), with a 760 × 500 minimum. A page's one action (Re-check runtimes, Refresh) sits in the page heading there, since the scene has no navigation toolbar; on the iPhone the pages push from a list in a sheet and keep the action in the toolbar.

  Log out on the Mac is `hub leave` after a confirmation: the device is revoked, its token forgotten, and the threads stay. Joining again is `agent-workspace hub join` with a new code; there is no join screen in the app. On the iPhone, Log out (`MirrorLogOut`) revokes the device (best effort), forgets the token and the link, empties the mirror (rows, the outbox of unsent edits, and the devices list), and returns to the Connect screen; unsent edits are discarded rather than uploaded under a later link. The iPhone shows "Host disconnected" in place of the list when the mirror's `devices` table, which M8b refreshes each sync cycle, is non-empty and has no unrevoked macOS device; an empty table (before the first fetch) is not a lost host, and a joined Mac that is asleep still counts (telling those apart is M8c presence). The menu still works there, so the phone can log out.

  The hub user's display name reaches the Mac through `HubStatus.Result.displayName` (optional, so an older coordinator decodes as absent). `HubSync` keeps it in memory, from the enrollment or from `GET /v1/me` when it starts on an existing link, so the link table needed no migration; while the name is unknown it asks again after each successful push or pull, and the Mac's window refreshes the account when it becomes active. The phone fetches `/v1/me` once per sync start. A sign-in screen (Apple ID or a passkey, gating the whole app) is a separate project that needs identity-provider work on the hub (M8d); until then the app stays usable after Log out and shows "Not signed in".

## 2026-11-01 (coordinator robustness)

- **D-052 A blocking Keychain call never runs on an actor, the hub token is read once per run, and a running cluster is adopted only from this install.** The package builds with `NonisolatedNonsendingByDefault`, so `KeychainSecretStore`'s async methods ran on their caller's actor; a token read that raised a Keychain prompt (any rebuild whose signature the item's ACL does not name) held `HubSync` until someone answered, and every `hub.status` timed out behind it. Each `SecItem*` call now runs on a thread of its own (`KeychainCall`). `HubSync` keeps the device token in memory once read (`HubToken`): concurrent requests share one read, a join keeps the token it just stored, a miss or a failure is not kept, and while a read is outstanding `hub status` reports "Waiting since … for Keychain access to the hub token; answer the Keychain prompt on this Mac." in `lastError` without storing it. The token is held only by the coordinator process, never written anywhere else. `PostgresServer.start` used to adopt any postmaster serving its data directory; after a bundle swap that was the old install's server, which could not load the new install's `plpgsql` under the hardened runtime, and migration 0004 failed until the server was stopped by hand. A running cluster is now adopted only when its postmaster runs this install's `postgres` (the same file by its current path from `proc_pidpath`, so a moved bundle does not match) and started after that file was last written (so a bundle rebuilt in place does not match); otherwise it is stopped through the existing identity check (D-025) and this install's server started. Cost: one extra fast restart of the cluster after every app update, a few seconds.

- **D-050 The hub cuts pull pages by stored value size, prunes its change log on a schedule, and restores a stale reader from one unpaged snapshot.** A pull page stops at 1000 changes or 8 MiB (8,388,608 bytes) of `value`, whichever comes first, and always holds at least one change, so a page of one 2 MiB change still moves. The size is not measured at read time: `changes.value_bytes` is the length of the value as PostgreSQL's `jsonb` text (a few bytes more than compact JSON), stored when the change is pushed, and the page is cut in SQL with a running sum over those integers, selecting `value` only for the rows inside the cut. A first version streamed 1001 rows out of PostgreSQL to find the cut, and the byte limit exists to bound work as well as memory. `changes.received_at` (`now()` at insert) is what pruning reads, not `wall`, so a device with a wrong clock cannot make its own rows look old. `serve` prunes every org when it starts and every 24 hours after; `B4HUB_RETENTION_DAYS` sets the retention (default 30; anything but a whole number of at least 1 is a configuration error and exits 2), and `b4hub prune --older-than-days N [--org slug]` does it once. Pruning takes the same per-org advisory lock a push holds, deletes every change received before the cutoff and every change with a lower `hub_seq` (the horizon is one cursor, so what remains is a contiguous tail), and raises `org_sync_horizons.horizon` to the highest `hub_seq` it deleted; the horizon never moves down and the materialised tables are not touched, because the log is history and the tables are state. A pull whose `after` is below the horizon answers `410 resync_required`; the check and the page are read in one database snapshot, so a prune that commits mid-pull cannot leave the reader a gap. The reader then calls `GET /v1/snapshot`, one `REPEATABLE READ` transaction that returns this user's rows as synthetic `insert` changes in dependency order (`hubSeq` 0, `deviceSeq` 0, `wall` 0, `deviceId` the row's owner), the per-column clocks of those rows, and `next`, the highest `hub_seq` the org's feed had at that instant (or the horizon, if pruning emptied the feed). A snapshot row's `hlc` is the greatest of its clocked columns' clocks, or `000000000000-0000-<owner device>` when none was ever set, so any later change of the row wins over it. The Mac applies the snapshot through the same narrow merge as any pull (D-049), so its rows stay and only phone-writable values are compared by clock; the phone clears its rows, keeps its outbox, applies the snapshot, re-applies the unsent outbox rows on top, and continues from `next`. **An uncut page's `next` is the highest `hub_seq` the org has recorded (at least `after`), even when that is another user's change.** Without this rule a user whose feed is idle would keep a cursor that other users' activity pushes below the horizon, and would resync every 30 days for nothing; nothing of theirs can lie in between, because pushes commit in `hub_seq` order. `GET /v1/devices` lists the user's devices (revoked ones included) for the mirror's device names. Known limitations: the snapshot is not paged, so the hub builds the user's whole mirror in memory in one response; the first prune after a long gap deletes the whole prefix in one transaction while holding the push lock, and `received_at` has no index; the privileged-role check counts only ownership of `changes`, and a `NOINHERIT` member of a superuser can still `SET ROLE` (for a security review); the migration's backfill of `value_bytes` and `owner_device_id` is a full-table update. The application role `b4hub_app` is provisioned by `migrate` from the password in `DATABASE_URL` (printable ASCII; the server receives only a client-computed SCRAM-SHA-256 verifier), is `NOSUPERUSER NOBYPASSRLS`, and does not own the tables, so there are two URLs: `DATABASE_ADMIN_URL` (owner; `migrate`, `seed`, `enroll`) and `DATABASE_URL` (`b4hub_app`; `serve` only). **Three tables carry no RLS.** `orgs` is the tenant directory. `device_tokens` and `enrollment_codes` are looked up by the hash of a secret the caller presents, before any org is known, so a tenant policy cannot apply; they hold only hashes, ids, and expiry, never synced content, and everything they lead to is then read under the org they name. The change log has `(org_id, device_id, device_seq)` unique for idempotent pushes and a per-org `hub_seq` bigserial as the reader's cursor; a per-org advisory lock keeps commit order equal to sequence order so a reader never skips a row that commits late. The six synced tables are materialised with the Mac's quoted camelCase columns plus `org_id`, `user_id`, `device_id`, keyed `(org_id, id)` with the client's text ids; hub-minted ids are UUIDv7. Every read and write is scoped to the token's `user_id`, and a missing resource and an inaccessible one answer the same generic 404. Limits: 2 MiB per change value (`MAX_PAYLOAD_BYTES`), 32 MiB per push body, 1000 changes per push, 1000 per pull page, and a long-poll `wait` capped at 25 s whose waiter is registered before the final emptiness check, so a push between the check and the wait is not missed. The retention horizon is 0 because M8a never prunes; `resync_required` (410) is answered only for a negative cursor until pruning exists. *Amended by D-049/D-050 (2026-11-01): a value over 2 MiB is rejected per change (`payload_too_large`) and no longer 413s the push (only a body over 32 MiB does); a pull page also stops at 8 MiB of stored value sizes; the hub prunes every 24 hours (`B4HUB_RETENTION_DAYS`, default 30), so the horizon moves and `resync_required` is answered for any cursor below it, restored from `GET /v1/snapshot`.*

## 2026-10-31 (M5)

- **D-031 Native history is merged into the cache by snapshot order; live rows are never deleted or duplicated.** `thread.reconcile` (and a plain `thread.read` whose cache is empty although turns were recorded) calls the adapter's `loadSession` and merges: a snapshot item whose native id is cached keeps that row (a live row keeps its payload, a snapshot row takes the new one); an id-less item that matches a cached item of the same role and text reuses that row; everything else is inserted with `snapshot` provenance in the snapshot's order; cached snapshot rows the runtime no longer reports are removed; live rows nothing matched (the turn in flight) follow at the end; sequences are renumbered in one transaction. Text matching is used only to recognise the app's own user messages, never as an exactly-once guarantee for runtime events (spec 10.1).

## 2026-10-31 (M4)

- **D-024 Managed servers are spawned with `posix_spawn` into their own process group, with stdout and stderr redirected to a per-server log file, not through `StreamingProcess`.** The pipe-based helper ties a child's life to the coordinator (an orphaned Node process dies on its next write to a closed pipe) and loses its output across a coordinator restart. The file keeps the server independent so an app Quit or a coordinator crash never loses a running server, and the process group lets a stop reach a runtime child that outlived `b4 dev`. The spawn also resets the child's signal mask and the dispositions of SIGTERM, SIGINT, SIGHUP, SIGPIPE, SIGQUIT, and SIGCHLD: the coordinator ignores several of those and dispositions survive exec, and a blocked SIGTERM inherited from the spawning thread left a server that only SIGKILL could stop.
- **D-025 Ownership is `(pid, process start time within one second, argv containing the CLI entry file and the port)` from `KERN_PROC_PID` and `KERN_PROCARGS2`, captured at spawn and re-verified before every signal and on every coordinator start.** A pid or a listening port alone never establishes ownership; a mismatch leaves the process alone and marks the registration stopped with a message naming the pid.
- **D-026 The project-installed CLI runs as `<node> <project>/node_modules/@b4run/cli/dist/index.js`, never through `node_modules/.bin/b4` or a shell, and is never downloaded.** The pnpm shim resolves `node` from `PATH`, which a Finder-launched app does not have. The version is read from the package's `package.json`; the minimum is 0.15.7. - **D-027 A registration allocates its loopback port once (or takes `--port`) and keeps it, so route connections have a stable origin; a start whose port is taken fails with `owned_process_conflict` and stops nothing.** The port cannot change once a route connection references the server, because managed connections carry `http://127.0.0.1:<port>` as their target and threads use that origin as their native scope.
- **D-028 Source mode (`b4 start --host 127.0.0.1 --port N` with a coordinator-built environment parsed from the env file without shell evaluation) is the default; development mode (`b4 dev --port N --env-file P`) is explicit** because hot reload can replace the runtime mid-turn. The child environment is `PATH` (the Node directory plus the system directories), `HOME`, `TMPDIR`, `LANG`, `USER`, `SHELL`, and the env-file pairs; nothing else of the coordinator's environment leaks in, and env-file values exist only in the spawn call. `envFilePath` defaults to `<project>/.env` when present. `start`, `restart`, `add`, and `inspect` block until readiness (`GET /healthz` within 90 s) or discovery finishes; a concurrent start joins the one in flight.

Log lines are never published as events, so a chatty server cannot evict conversation events from the replay buffer; `--follow` and the GUI poll `server.logs` with the last offset.

A parked prompt is durable in `.b4` and a `reconciling` turn is already lost, so neither blocks. The CLI takes `--force`; the GUI confirms. The M5 Quit dialog builds on the same check.

## 2026-10-31

- **D-019 A B4 turn's native id is its ordinal in `GET /threads/:id/turns`.** The Agent Protocol has no run id (the thread id is the run identity). Reading the turn count before `POST /runs/stream` and naming the turn `turn-<n+1>` lets reconciliation tell "the server ran it" (the nth turn exists, with its recorded status) from "the prompt never arrived" (it does not) without ever resubmitting. A non-empty list is a parked prompt: the turn stays `waiting_for_user` across stream loss and coordinator restart, and the prompt is re-opened from the durable `value` under a new adapter generation.
