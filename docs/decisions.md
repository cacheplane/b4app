# Decision log

Material implementation decisions, newest first. The spec (`docs/roadmaps/Personal_Agent_Workspace_Technical_Spec_and_Roadmap.md`) is the requirement source; this log records deviations and choices the spec left open.

## 2026-10-31 (M4)

- **D-024 Managed servers are spawned with `posix_spawn` into their own process group, with stdout and stderr redirected to a per-server log file, not through `StreamingProcess`.** The pipe-based helper ties a child's life to the coordinator (an orphaned Node process dies on its next write to a closed pipe) and loses its output across a coordinator restart. The file keeps the server independent so an app Quit or a coordinator crash never loses a running server, and the process group lets a stop reach a runtime child that outlived `b4 dev`. The spawn also resets the child's signal mask and the dispositions of SIGTERM, SIGINT, SIGHUP, SIGPIPE, SIGQUIT, and SIGCHLD: the coordinator ignores several of those and dispositions survive exec, and a blocked SIGTERM inherited from the spawning thread left a server that only SIGKILL could stop.
- **D-025 Ownership is `(pid, process start time within one second, argv containing the CLI entry file and the port)` from `KERN_PROC_PID` and `KERN_PROCARGS2`, captured at spawn and re-verified before every signal and on every coordinator start.** A pid or a listening port alone never establishes ownership; a mismatch leaves the process alone and marks the registration stopped with a message naming the pid.
- **D-026 The project-installed CLI runs as `<node> <project>/node_modules/@b4run/cli/dist/index.js`, never through `node_modules/.bin/b4` or a shell, and is never downloaded.** The pnpm shim resolves `node` from `PATH`, which a Finder-launched app does not have. The version is read from the package's `package.json`; the minimum is 0.15.7. Inspection (`b4 routes --json --cwd <project>`) executes the project's config and route modules, so registration is the trust decision and both the CLI and the form say so.
- **D-027 A registration allocates its loopback port once (or takes `--port`) and keeps it, so route connections have a stable origin; a start whose port is taken fails with `owned_process_conflict` and stops nothing.** The port cannot change once a route connection references the server, because managed connections carry `http://127.0.0.1:<port>` as their target and threads use that origin as their native scope.
- **D-028 Source mode (`b4 start --host 127.0.0.1 --port N` with a coordinator-built environment parsed from the env file without shell evaluation) is the default; development mode (`b4 dev --port N --env-file P`) is explicit** because hot reload can replace the runtime mid-turn. The child environment is `PATH` (the Node directory plus the system directories), `HOME`, `TMPDIR`, `LANG`, `USER`, `SHELL`, and the env-file pairs; nothing else of the coordinator's environment leaks in, and env-file values exist only in the spawn call. `envFilePath` defaults to `<project>/.env` when present. `start`, `restart`, `add`, and `inspect` block until readiness (`GET /healthz` within 90 s) or discovery finishes; a concurrent start joins the one in flight.
- **D-029 Server logs are files the child writes directly; the coordinator serves redacted tails on request and bounds the file by copy-truncate (4 MiB, keep the last 1 MiB).** Bearer values, `sk-…` keys, and `key|token|secret|password|authorization` pairs are masked before the text leaves the coordinator. Log lines are never published as events, so a chatty server cannot evict conversation events from the replay buffer; `--follow` and the GUI poll `server.logs` with the last offset.
- **D-030 `server stop` and `server restart` refuse with `owned_process_conflict` (`reason: turn_active`) while a route connection has a turn in `submitting`, `running`, or `stopping`, unless forced**, because stopping loses the in-memory run. A parked prompt is durable in `.b4` and a `reconciling` turn is already lost, so neither blocks. The CLI takes `--force`; the GUI confirms. The M5 Quit dialog builds on the same check.

## 2026-10-31

- **D-019 A B4 turn's native id is its ordinal in `GET /threads/:id/turns`.** The Agent Protocol has no run id (the thread id is the run identity). Reading the turn count before `POST /runs/stream` and naming the turn `turn-<n+1>` lets reconciliation tell "the server ran it" (the nth turn exists, with its recorded status) from "the prompt never arrived" (it does not) without ever resubmitting. When the count cannot be read the id falls back to `run-<uuid>` and reconciliation relies on the thread status alone.
- **D-020 Parked versus cancelled is decided by `GET /threads/:id/pending_interrupts`, never by the `interrupted` status alone.** B4 writes `interrupted` for both. A non-empty list is a parked prompt: the turn stays `waiting_for_user` across stream loss and coordinator restart, and the prompt is re-opened from the durable `value` under a new adapter generation. An empty list is a cancellation.
- **D-021 Permission answers go through `POST /threads/:id/resume` with B4's own decisions.** `allow_once` → `once`, `allow_always` → `always` (B4 persists the pattern itself, unlike Claude in D-018; `once` when the prompt said `allowAlways: false`), `deny` → `deny`, decline → `status: cancelled`, each echoing the prompt's `grant`. The resume response is a second SSE stream that continues the same turn and item numbering. Stop on a parked turn declines the prompt, because nothing else can end it.
- **D-022 Endpoint secrets enter through the CLI's hidden prompt and the local socket into the coordinator's credential store.** `credential add <label>` reads with `readpassphrase` (or one line from a non-TTY stdin), sends `credential.add` over the 0600 socket, and prints only the `secret:<uuid>` reference. The adapter resolves the reference on first use, sends it as `Authorization: Bearer <value>` (verbatim when the value already names a scheme) to the configured origin only, and refuses every redirect. The GUI form collects the reference, never the value. Credential labels are not persisted yet; the reference is the handle.
- **D-023 Route kinds other than `agent` are stored as `incompatible` connections with an explanation.** Only `agent()` routes take the `input.messages` shape; `workflow`, `graph`, and `chain` routes are accepted at `connection add`, inspected, and reported, never run.
- **D-015 One `claude` process per native session, started on `createSession` and kept alive between turns.** The stream-json protocol has no session API: the CLI process is the session. Starting it at creation validates the executable, the `initialize` handshake, and sign-in before a thread row exists; `--session-id <uuid>` fixes the native id up front; after a coordinator restart the next turn spawns with `--resume <uuid>`.
- **D-016 A Claude process that exits mid-turn ends that turn as `failed`.** Unlike Codex, where the app-server owns the thread and a turn's final status can be read back, nothing continues once the `claude` process is gone, so the adapter emits `turn.finished failed` with the exit status, and `reconcile` after a coordinator restart reports `failed` for a turn with no live process. The disconnect is scoped to that thread; the connection and other threads are untouched.
- **D-017 Claude history is read from the transcript JSONL Claude Code writes under `projectsDirectory`, best-effort and read-only.** The app cache stays the display source; a missing file is `native_session_missing`, never a reconstructed session.
- **D-018 `allow_always` on a Claude tool permission is sent as a plain allow.** Writing per-session rules into the user's Claude settings is out of scope; the UI still offers the button so both runtimes present the same choices.

## 2026-10-30

- **D-001 Native Swift instead of Electron + React + TypeScript.** The spec chose Electron; the owner directed pure Swift with macOS and iOS targets. An Electron shell was built, verified, and discarded the same day. Consequences: no Node coordinator, no TypeScript adapters, and the Claude integration cannot use the TypeScript Agent SDK (D-002).
- **D-002 Claude Code is driven through the CLI's stream-json stdio protocol, not the TypeScript Agent SDK.** The SDK is a thin stdio client of the same CLI; its control protocol (`control_request` / `control_response`, `initialize`, `can_use_tool`, `interrupt`) was read from the SDK source and verified by a no-inference handshake against 2.1.282. The protocol is undocumented and version-coupled, so the tested CLI version is pinned and re-diffed on upgrade. See `docs/research/2026-10-30-claude-cli-stream-protocol.md`.
- **D-003 One umbrella Swift package plus XcodeGen for the app targets.** SwiftPM cannot build `.app` bundles; Tuist is heavier than needed; hand-edited `pbxproj` files are hostile to agents. The generated `.xcodeproj` is gitignored and produced by `Scripts/generate-project.sh`.
- **D-004 The macOS app hosts the coordinator in-process when none is running; the CLI spawns the standalone executable.** Both paths use the same library, lock, and socket, so GUI and CLI always share one coordinator. A LaunchAgent via `SMAppService` replaces in-process hosting in M6 when the bundle layout exists.
- **D-005 macOS 26 and iOS 26 minimum.** Personal app on current OS versions; removes availability shims for Liquid Glass APIs.
- **D-006 App Sandbox disabled.** A sandboxed app cannot spawn the user's `claude` or `codex` executables. Local builds are signed ad hoc; Developer ID and notarization are M6.
- **D-007 GRDB for SQLite, SwiftNIO for the socket, swift-subprocess for child processes, swift-argument-parser for the CLI.** See `docs/research/2026-10-30-swift-stack.md` for versions and rationale.
- **D-008 Keychain through the file-based keychain for ad-hoc builds.** The data-protection keychain needs a provisioning profile and access group; revisit at M6 with signing.
- **D-009 iOS ships the full shell with an unavailable transport.** The spec defers iOS; the owner wants both targets in the repo now. The iOS app builds and renders every screen but cannot reach a coordinator until the relay is designed.
- **D-010 Codex protocol types are hand-written from the generated schema, not generated code.** Resolved in M1. `codex app-server generate-json-schema` (codex-cli 0.166.0) produces 677 definitions and 4.5 MB of JSON; the app reads a few dozen fields. `Sources/CodexAdapter/CodexProtocol.swift` types exactly those fields and keeps the rest as `JSONValue`, so a newer server adds fields without breaking decoding. The generator's output is not committed; the pinned version and command are in `docs/compatibility.md`, and the schema is regenerated and re-diffed on every Codex upgrade.
- **D-011 One `codex app-server` process per Codex connection, started lazily and kept alive while the coordinator runs.** The adapter generation increments on every restart; pending runtime requests from an older generation expire and running turns become `reconciling` with an unknown outcome until the thread is reopened. A process exit is never read as a turn outcome.
- **D-012 Approval policy and sandbox come from the user's Codex configuration.** The app does not pass `approvalPolicy: never` or widen the sandbox; it answers the resulting `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, and `item/tool/requestUserInput` requests with the user's decision, and declines request kinds it cannot present (permissions, MCP elicitation, dynamic tools, token refresh, attestation) with a valid explicit response so Codex never hangs. Amended 2026-10-31: `CodexAdapter.threadPolicy` can ask `thread/start` for a stricter policy than the configuration; the app leaves it nil, and only the opt-in live approval test sets `on-request` + `workspace-write`, because the owner's configuration (`never`, full access) can never produce an approval to verify against.
- **D-013 A thread's working directory is fixed at creation and sent with every `turn/start` and `thread/resume`.** Matches spec 3.3 (a thread is bound to one native session) and keeps the Codex sandbox root stable.
- **D-014 Long-lived protocol children use Foundation `Process` (`StreamingProcess`), one-shot commands use swift-subprocess (`CommandRunner`).** swift-subprocess scopes stdin and stdout to a closure, which does not fit a server that outlives any one call. `StreamingProcess` ignores SIGPIPE process-wide so a write to a dead child is an error, not a crash.
