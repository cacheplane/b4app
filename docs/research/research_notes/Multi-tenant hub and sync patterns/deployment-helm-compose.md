# Deployment patterns for a PostgreSQL-backed multi-tenant service: Helm chart and Docker Compose, on-prem and vendor cloud (state as of 2025–2026)

Scope: how well-run open-source and commercial products package a Postgres-backed service as a Helm chart and a Compose stack, covering bundled vs external Postgres, migrations, secrets, IdP bundling, upgrades, air-gap, and client/server version compatibility. Sources are primary docs and chart READMEs where possible; practitioner blog material is flagged as such. Research date: 2026-10-31.

## Key Question 1: Chart structure — umbrella/subcharts, Bitnami vs CloudNativePG vs bring-your-own, values conventions for external databases, PDBs, probes, resource defaults, ingress/TLS, NetworkPolicies

### Takeaway
The 2025–2026 consensus is "bundled Postgres is for quickstart only; production is bring-your-own via a Secret." The Bitnami PostgreSQL subchart, which most umbrella charts used for the bundled case, became a liability in August 2025 when Broadcom moved public Bitnami images to an unmaintained `bitnamilegacy` registry; CloudNativePG (an operator with a `Cluster` CRD that generates its own connection Secrets) is the replacement direction for in-cluster Postgres, while every mature product chart (Coder, Zitadel, Keycloak Operator, Mattermost Operator, Sourcegraph, GitLab) treats the external database as the default production path and references credentials via an existing Secret.

### Cited Findings

**Bitnami licence/distribution change (affects every chart that bundles `bitnami/postgresql`)**
- Effective August 28, 2025, Bitnami stopped publishing new images and Helm charts to Docker Hub in OCI format; existing images were moved to `docker.io/bitnamilegacy`, which "will receive no further updates or support and should only be used for temporary migration purposes." — [bitnami/charts issue #35164](https://github.com/bitnami/charts/issues/35164)
- A small set of hardened images stays free at `bitnamisecure`, but "These free images are intended for development and are only available on the 'latest' tag." Everything else is behind the commercial Bitnami Secure Images (BSI) subscription. — [bitnami/charts issue #35164](https://github.com/bitnami/charts/issues/35164)
- Chart source on GitHub is unchanged and remains Apache 2.0 ("No changes are being made to the helm chart source code"); already-published OCI charts at `docker.io/bitnamicharts` remain but are no longer updated and may not deploy without overriding bundled image references. — [bitnami/charts issue #35164](https://github.com/bitnami/charts/issues/35164)
- Documented stopgap: keep the chart version and set e.g. `--set image.repository=bitnamilegacy/postgresql` plus `global.security.allowInsecureImages=true`; alternatives are subscribing to BSI or building images from the Apache-2.0 `bitnami/containers` source. Deletion of the public catalog was postponed to September 29, 2025. Sealed Secrets, charts-syncer, and minideb are stated to be unaffected. — [bitnami/charts issue #35164](https://github.com/bitnami/charts/issues/35164)
- Real-world downstream effect: Coder's own Kubernetes install docs now show the proof-of-concept Bitnami Postgres install with `image.repository=bitnamilegacy/postgresql`, while recommending a managed database and stating "Coder does not manage a database server for you." — [Coder: Install on Kubernetes](https://coder.com/docs/install/kubernetes)
- Third-party summaries report conflicting dates (Aug 28 vs Sep 29 deletion) and a different legacy path (`docker.io/legacybitnami`) in a Broadcom VMware Cloud Director KB; the GitHub issue is the authoritative statement. — [Broadcom KB 408744](https://knowledge.broadcom.com/external/article/408744); [MOSIP advisory](https://community.mosip.io/t/advisory-bitnami-catalog-changes-and-impact-on-mosip-deployments/2311)

**Bitnami PostgreSQL chart conventions (still the de-facto values vocabulary many umbrella charts copy)**
- `auth.existingSecret` (default `""`): when set, "`auth.postgresPassword`, `auth.password`, and `auth.replicationPassword` will be ignored and picked up from this secret"; secret keys default to `postgres-password`, `password`, `replication-password`; `global.postgresql.auth.*` overrides the per-chart `auth.*` values so an umbrella chart can set credentials once. — [bitnami/postgresql README](https://raw.githubusercontent.com/bitnami/charts/main/bitnami/postgresql/README.md)
- Production-hardening defaults in the chart: `primary.pdb.create` defaults to `true` (minAvailable defaults to 1 when both unset); `primary.networkPolicy.enabled` defaults to `true` with `allowExternal: true`; `primary.resourcesPreset` defaults to `nano` with `primary.resources` empty, and the README warns "in production workloads using `resourcesPreset` is discouraged." — [bitnami/postgresql README](https://raw.githubusercontent.com/bitnami/charts/main/bitnami/postgresql/README.md)
- Probe defaults: liveness enabled (initialDelay 30s, period 10s, timeout 5s, failureThreshold 6), readiness enabled (initialDelay 5s, period 10s, timeout 5s, failureThreshold 6), startup probe disabled by default (30s/10s/1s, failureThreshold 15). Persistence defaults to an 8Gi RWO PVC at `/bitnami/postgresql`. — [bitnami/postgresql README](https://raw.githubusercontent.com/bitnami/charts/main/bitnami/postgresql/README.md)
- The chart carries a `passwordUpdateJob` for in-place password rotation; with `auth.existingSecret` or `helm template` you must supply `passwordUpdateJob.previousPasswords.*` yourself. — [bitnami/postgresql README](https://raw.githubusercontent.com/bitnami/charts/main/bitnami/postgresql/README.md)

**CloudNativePG as the in-cluster alternative**
- `initdb` is the default bootstrap; with no database name supplied CNPG creates an `app` database and "The user that owns the database defaults to the database name instead." The operator will "randomly generate a secure password for both the superuser and the application user." — [CNPG bootstrap docs](https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/main/docs/src/bootstrap.md)
- To bring your own credential, reference a `kubernetes.io/basic-auth` Secret under `bootstrap.initdb.secret`; "the `username` in the secret must match the one of the `owner`." Post-init SQL hooks run as superuser against `postgres`, `template1`, and the app database (`postInitSQL`, `postInitTemplateSQL`, `postInitApplicationSQL`, plus `*SQLRefs` to Secrets/ConfigMaps). — [CNPG bootstrap docs](https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/main/docs/src/bootstrap.md)
- Migrating an existing database into CNPG: `pg_basebackup` bootstrap requires same major version and architecture, and "The CloudNativePG community does not endorse this approach" for sources outside Kubernetes; the recommended path is the logical `initdb` import, which can "import one or more databases from an existing PostgreSQL cluster, even if it's outside Kubernetes." — [CNPG bootstrap docs](https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/main/docs/src/bootstrap.md)
- Declarative roles: roles in `.spec.managed.roles` get full lifecycle management and "If a user modifies role attributes directly in the database, the CloudNativePG operator will revert those changes during the next reconciliation cycle"; passwords come from a `kubernetes.io/basic-auth` Secret referenced by `passwordSecret`, labelled `cnpg.io/reload: "true"`. Newer docs add a `DatabaseRole` CRD that is "the recommended approach for modern environments and GitOps workflows." — [CNPG declarative role management](https://cloudnative-pg.io/docs/devel/declarative_role_management)

**Product charts: how they handle the database**
- Coder: install docs recommend a managed PostgreSQL; the chart reads `CODER_PG_CONNECTION_URL` from a user-created Secret `coder-db-url` key `url` via `secretKeyRef`; the chart already sets `CODER_HTTP_ADDRESS`, `CODER_TLS_ENABLE`, `CODER_TLS_CERT_FILE`, `CODER_TLS_KEY_FILE` from `tls.secretNames`, and setting them yourself "will cause conflicts." — [Coder: Install on Kubernetes](https://coder.com/docs/install/kubernetes)
- Zitadel: "The ZITADEL chart ships with an optional PostgreSQL subchart" for quickstart only; production sets `postgresql.enabled: false` and `ZITADEL_DATABASE_POSTGRES_DSN`, connecting through the `postgres` maintenance database so Zitadel can create its own database during init. Supported PostgreSQL 14–18 (18 needs Zitadel v4.11.0+). — [Zitadel: Deploy on Kubernetes](https://zitadel.com/docs/self-hosting/deploy/kubernetes)
- Keycloak Operator: "The Keycloak Operator does not manage the database and you need to provision it yourself." The docs' PostgreSQL StatefulSet is `emptyDir`-backed and labelled development-only; DB credentials come from a Secret with `username`/`password` keys referenced by `usernameSecret`/`passwordSecret`; a TLS Secret is referenced as `http.tlsSecret`; "For a production ready installation, you need a hostname." — [Keycloak Operator basic deployment](https://www.keycloak.org/operator/basic-deployment)
- Mattermost: the `mattermost-team-edition` Helm chart README opens with "This helm chart is no longer supported" and recommends the Mattermost Operator; that chart bundled MySQL (`mysql.enabled: true`) and offered `externalDB.enabled`, `externalDB.externalDriverType` (`postgres`|`mysql`) and `externalDB.externalConnectionString` with no `existingSecret` parameter documented. — [mattermost-team-edition README](https://raw.githubusercontent.com/mattermost/mattermost-helm/master/charts/mattermost-team-edition/README.md)
- Mattermost Operator: the installation manifest points at an external database via `database.external.secret: <database-secret-name>`; the operator's DB readiness check has a "legacy" default mode that "will be deprecated in a future operator release." — [Mattermost: Deploy on Kubernetes](https://docs.mattermost.com/deployment-guide/server/kubernetes/deploy-k8s.html)
- Sourcegraph Helm: disable the bundled DB with `pgsql.enabled: false` and supply `auth.host/user/password/port/pgsslmode` in the override file; Sourcegraph recommends keeping DB credentials in Secrets created outside the chart, one Secret per database. Sourcegraph 6.0+ requires PostgreSQL 16+. — [Sourcegraph Helm docs](https://docs-legacy.sourcegraph.com/admin/deploy/kubernetes/helm); [Sourcegraph external Postgres](https://sourcegraph.com/docs/admin/external_services/postgres)
- Sourcegraph runs three databases (frontend `pgsql` via `PG*`, `codeintel-db` via `CODEINTEL_PG*`, code insights via `CODEINSIGHTS_PG*`); if the first two share identical settings "the Sourcegraph instance will refuse to start." Migrations "expect `SUPERUSER` permissions" by default; on RDS use `rds_superuser`; a DBA must pre-create extensions (citext, hstore, pg_stat_statements, pg_trgm, pgcrypto, intarray). — [Sourcegraph external Postgres](https://sourcegraph.com/docs/admin/external_services/postgres)
- GitLab chart: PostgreSQL can be "provided as external services reachable from the Kubernetes cluster"; the external example uses host, port, database, username and `psql.password.secret`/`psql.password.key` (defaults `gitlab-postgres` / `psql-password`). — [GitLab migrations chart](https://docs.gitlab.com/charts/charts/gitlab/migrations/)
- Camunda (as a comparison point for the Bitnami-style convention): external DB is selected with `postgresql.enabled: false` and a Secret for the password. — [Camunda: Use external PostgreSQL](https://docs.camunda.io/docs/self-managed/deployment/helm/configure/database/using-existing-postgres)

**Helm 4 (relevant to chart authors in 2026)**
- Helm 4.0 reached GA on 12 November 2025. New releases default to server-side apply while releases migrated from Helm 3 keep client-side apply; `--wait` now uses kstatus and requires the `watch` verb in addition to `list` on chart resources, otherwise waits fail immediately. — [wz-it: Migrate Helm 3 to Helm 4](https://wz-it.com/en/knowledge/kubernetes/migrate-helm-3-to-helm-4/); [DEV: Helm v4 key changes](https://dev.to/ilya-lesikov/helm-v4-key-changes-from-v3-2i26) (secondary sources; the official Helm registries page itself notes it "has not yet been updated for Helm 4" — [helm.sh registries](https://helm.sh/docs/topics/registries/))

### Inferences
- A 2026 chart should expose three database modes, in this priority: (1) `database.existingSecret` + key names (the Bitnami vocabulary `auth.existingSecret`/`secretKeys.*` is the most widely recognised), (2) an opt-in CNPG `Cluster` rendered by the chart (or documented alongside it) whose auto-generated `<cluster>-app` Secret is consumed directly, (3) a legacy Bitnami subchart only if you can supply your own image repository, since the public images are frozen.
- Umbrella charts that still declare `bitnami/postgresql` as a dependency now ship with a time bomb: a fresh install pulls a frozen `bitnamilegacy` image or fails verification unless `global.security.allowInsecureImages` is set. Expect customers to ask about this explicitly.
- Bitnami's own defaults (PDB on, NetworkPolicy on, probes on, `resourcesPreset` on but discouraged) are a reasonable checklist for the app chart too; the `resourcesPreset` idea (named T-shirt sizes with an explicit override) is a good way to give a working default without pretending to know production sizing.
- Every serious product documents TLS as "bring a `kubernetes.io/tls` Secret; the chart wires it," not "the chart generates certificates," except GitLab's shared-secrets self-signed certs for first boot.

### Gaps
- I could not retrieve the CNPG "connecting applications" page listing the exact keys of the generated `<cluster>-app` Secret (the fetch returned empty). From memory the keys include `username`, `password`, `dbname`, `host`, `port`, `uri`, `jdbc-uri`, `pgpass` and `fqdn-uri`, but this is unverified here and should be checked against https://cloudnative-pg.io/docs/current/applications.
- The top-level `networkPolicy.enabled` default in the Bitnami PostgreSQL README was truncated in the fetch; only the `primary.networkPolicy.enabled: true` default was confirmed.

- The Grafana Helm chart's external-database values were not fetched; Grafana's DB configuration is via `grafana.ini` `[database]` (see KQ2 findings) rather than a dedicated `externalDatabase` block.

## Key Question 2: Database migrations — Helm hooks vs init containers vs app-start vs separate migrate command; avoiding double-runs with multiple replicas; rollback

### Takeaway
Two camps dominate: Rails/Django products (GitLab, PostHog, Sourcegraph's `migrator`) run migrations as a separate Job/service before the app rolls out, while Go products (Grafana, Mattermost, Coder) run migrations at process start and serialise concurrent replicas with a database lock. Helm `pre-install`/`pre-upgrade` hook Jobs are the standard chart mechanism (GitLab shared-secrets and Zitadel use them), with the known pitfalls that hook resources are not tracked by the release and `post-*` hooks can deadlock against pods waiting on the schema. Nobody relies on Helm rollback to undo schema changes; the rollback story is expand/contract (forward-only, additive migrations) plus a pre-upgrade backup, with Sourcegraph's explicit `downgrade` command as the notable exception.

### Cited Findings

**Helm hook mechanics**
- Hook types: `pre-install`, `post-install`, `pre-delete`, `post-delete`, `pre-upgrade`, `post-upgrade`, `pre-rollback`, `post-rollback`, `test`. Ordering within a kind is by `helm.sh/hook-weight` (string, may be negative, ascending). For Job or Pod hooks "Helm waits until the resource runs to completion. If the hook fails, the release fails." — [Helm chart hooks](https://helm.sh/docs/topics/charts_hooks/)
- Deletion policies: `before-hook-creation` (default), `hook-succeeded`, `hook-failed`. "Helm doesn't track hook resources after they reach ready state, so `helm uninstall` won't remove them." Subchart hooks are evaluated and a parent chart cannot disable them. — [Helm chart hooks](https://helm.sh/docs/topics/charts_hooks/)
- Pitfall: an Airflow discussion reports a `post-install,post-upgrade` migration hook deadlocking upgrades because pods waited for the migration while the hook waited for the pods; the fix was moving to `pre-install`/`pre-upgrade`. An Ory Kratos thread reports the opposite failure (pre-upgrade migration blocking rollout) and suggests an init container as the alternative. — [apache/airflow discussion #33888](https://redirect.github.com/apache/airflow/discussions/33888); [Ory community archive](https://archive.ory.sh/t/538350/hey-all-i-d-like-to-discuss-an-issue-with-a-helm-chart-we-ha)
- Practitioner guidance (blog): init containers "run every time a new pod is created" and can run concurrently when several pods start, so they are "a good first solution for when scaling is not a problem yet"; the hybrid pattern is a migration Job plus init containers in app pods that "block the execution of new deployments until after the job has completed successfully." — [freeCodeCamp: migrations in Kubernetes](https://www.freecodecamp.org/news/how-to-run-database-migrations-in-kubernetes/); [Andrew Lock: Jobs and init containers](https://andrewlock.net/deploying-asp-net-core-applications-to-kubernetes-part-8-running-database-migrations-using-jobs-and-init-containers)

**Product implementations — separate Job/service**
- GitLab: the migrations sub-chart "creates a new migrations Job each time the chart is installed" and on any upgrade that changes chart version, appVersion, or any value. Completed Jobs "remain as objects in the cluster until the next chart upgrade" deliberately so logs stay observable; with `helm template` + `kubectl apply` old Jobs are not removed. A skip-if-up-to-date optimisation is not used because migration status is not persisted. An experimental `batchedBackgroundMigrationsCheck` Job (set by the GitLab Operator during upgrades, `activeDeadlineSeconds: 21600`) waits for unfinished batched background migrations. The Job also flips an application setting after migrating. — [GitLab migrations chart](https://docs.gitlab.com/charts/charts/gitlab/migrations/)
- Sourcegraph: a dedicated `migrator` image/service. `up` (the default, used at startup) "should always be run using the `migrator` image version corresponding with the Sourcegraph version being deployed"; `upgrade` performs multi-version upgrades including out-of-band migrations; `downgrade` "performs database schema migrations and (reverse-applied) out-of-band migrations"; `drift` diffs live schema against expected and "if schema drift is detected it must be resolved before completing the upgrade"; `add-log` records a manually applied migration in `migration_logs` when repairing a dirty database. In Compose the migrator is a container whose `command:` you edit; in Kubernetes it is a Job (`migrator.Job.yaml`); in Helm you pass `--set "migrator.args={...}"`. — [Sourcegraph migrator operations](https://sourcegraph.com/docs/admin/updates/migrator/migrator-operations)
- Sourcegraph Compose: external DB env vars must be set on all `sourcegraph-frontend-*` services and on the `migrator` service (3.37+); "After the database is configured, Sourcegraph will attempt to run migrations." Failed migrations go through a "dirty database" repair procedure. — [Sourcegraph external Postgres](https://sourcegraph.com/docs/admin/external_services/postgres)
- Zitadel: the chart runs a `zitadel-init` Job (schema) then a `zitadel-setup` Job (first instance and admin), ordered by Helm hooks on install and upgrade; the chart's `initjob.yaml` template is public. — [Zitadel: Deploy on Kubernetes](https://zitadel.com/docs/self-hosting/deploy/kubernetes); [zitadel-charts initjob.yaml](https://github.com/zitadel/zitadel-charts/blob/main/charts/zitadel/templates/initjob.yaml)
- PostHog Compose: `docker-compose.base.yml` defines a `migrate` service (`python manage.py migrate && python manage.py migrate_clickhouse && python manage.py run_async_migrations`) with `restart: 'no'` and `deploy.replicas: 0`, plus an `asyncmigrationscheck` service; `web` has no `depends_on` on it, so ordering is driven by the `deploy-hobby`/`upgrade-hobby` scripts rather than by Compose. — [PostHog docker-compose.base.yml](https://raw.githubusercontent.com/PostHog/posthog/master/docker-compose.base.yml); [PostHog self-host docs](https://posthog.com/docs/self-host)

**Product implementations — migrate at app start with a DB lock**
- Grafana: `[database] migration_locking` — "Set to `false` to disable database locking during the migrations. Default is true"; `locking_attempt_timeout_sec` — "the time, in seconds, to wait before failing to lock the database for the migrations," default 0, MySQL and Postgres only. Default DB is SQLite; "SQLite isn't recommended for production." — [Grafana configuration reference](https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/)
- Grafana HA reports: with two instances starting against Postgres (Grafana 11.4.0) the second "tries 5 times within 1-2 seconds and then fails the systemd service startup"; a manual restart after the lock released succeeded. Kolla-Ansible's 2020 fix was to "only start additional Grafana instances after the DB has been configured." — [Grafana community: locking_attempt_timeout_sec](https://community.grafana.com/t/database-locking-attempt-timeout-sec-purpose/142001); [Kolla-Ansible grafana role](https://opendev.org/openstack/kolla-ansible/src/commit/56a07702bcea02cf3793d6c830acc687b68244be/ansible/roles/grafana)
- Mattermost: the server imports the `morph` migration library; "In high availability environments, multiple instances try to run migrations, and a lock table is used to prevent this." Morph release notes include a change titled "drivers: remove advisory locks," and a stack trace from a hung startup points at `drivers/postgres/lock.go` (v1.1.0), so Postgres locking still exists but the exact mechanism after that change is not documented. — [Mattermost schema migration guide](https://developers.mattermost.com/contribute/more-info/server/schema-migration-guide); [mattermost/morph releases](https://github.com/mattermost/morph/releases); [Cloudron forum trace](https://forum.cloudron.io/topic/9707/mattermost-v8-0-and-postgresql/1)
- Coder uses golang-migrate; a Coder commit raised the migrate `LockTimeout` from golang-migrate's 15-second `DefaultLockTimeout` to two minutes because a long migration batch exceeded it. — [Coder commit 8cc6473 (mirror)](https://git.dragonfruit.dev/mirror/coder/commit/8cc64737362f67af0bf31cedd9f1dc44afea070e)
- golang-migrate issue #960 reports replicas running `CREATE INDEX CONCURRENTLY` during parallel `m.Up()` deadlocking on Postgres and proposes `pg_try_advisory_lock` with retry instead of `pg_advisory_lock`. The Postgres driver README documents `x-migrations-table`, `x-statement-timeout`, `x-multi-statement` (default false, 10MB max), and that statements such as `CREATE INDEX CONCURRENTLY` must live in their own migration file because multi-statement execution runs "inside a transaction." — [golang-migrate issue #960](https://github.com/golang-migrate/migrate/issues/960); [golang-migrate postgres README](https://raw.githubusercontent.com/golang-migrate/migrate/master/database/postgres/README.md)

**Rollback**
- Practitioner consensus (blogs, 2025–2026): a Helm rollback "reverts the chart and its images, not the database schema"; "if your migrations never destroy anything the previous version needs, a code rollback is always safe"; expand/contract = add new structure, dual-write and backfill, remove old structure once nothing uses it; never ship a destructive change in the same deploy that introduces it. Renames are "the classic breaker in rolling deploys" because old and new pods coexist. — [DEV: expand and contract](https://dev.to/jp_fontenele4321/the-expand-and-contract-pattern-for-zero-downtime-migrations-445m); [pandastack: rollback failed deployment](https://pandastack.io/blog/rollback-failed-deployment); [oneuptime: ArgoCD rollback and migrations](https://oneuptime.com/blog/post/2026-02-26-argocd-rollback-database-migrations/view)
- Vendor example: Upbound's Helm upgrade docs state migrations are forward-only, Helm has no awareness of the schema, and a non-compatible rollback requires a database restore from a pre-upgrade backup followed by the Helm rollback. — [Upbound upgrades](https://docs.upbound.io/hub/howtos/upgrades/)
- Grafana community guidance on blue/green: "some DB schema changes are not backwards compatible," so check release notes before running two versions against one database. — [Grafana community: HA and blue-green](https://community.grafana.com/t/grafana-db-changes-with-ha-and-blue-green-deployment/11527)

### Inferences
- The cleanest pattern that works for both Helm and Compose is a single image with a `migrate` subcommand: Helm runs it as a `pre-install,pre-upgrade` hook Job with `hook-delete-policy: before-hook-creation` (so logs survive until the next run, as GitLab chose) and the Deployment's init container or startup probe gates on schema version; Compose runs the same subcommand as a `migrate` service that the app `depends_on` with `condition: service_completed_successfully`. Sourcegraph's `migrator` is the most complete worked example of one binary used across Compose, raw Kubernetes and Helm.
- Migrate-at-start is acceptable only with a real DB lock and a lock timeout that waits rather than fails (Grafana's default `locking_attempt_timeout_sec = 0` combined with the 11.4 reports shows the failure mode when replicas race). If migrations run at start, set the Deployment strategy so a single replica starts first (e.g. `maxSurge: 1`, `maxUnavailable: 0`) or keep a separate Job.
- Dropping the `post-install`/`post-upgrade` hook for migrations is a hard rule: with `--wait` it deadlocks against pods that cannot become ready without the schema.
- For multi-tenant hubs, Sourcegraph's `drift` command is a model worth copying: a schema fingerprint check that blocks upgrades is cheaper than supporting repairs of hand-edited customer databases.

### Gaps
- The golang-migrate Postgres README fetched does not document its advisory-lock key derivation; the lock behaviour was only confirmed indirectly via issue #960 and the Coder commit. Whether #960's `pg_try_advisory_lock` proposal was merged was not confirmed.
- Morph's current Postgres lock implementation (post "remove advisory locks") was not read; the Mattermost docs only say "a lock table."
- Coder's docs pages fetched do not state whether `coder server` migrations are safe with multiple replicas starting simultaneously; only the lock-timeout commit was found.
- No primary source was found for Django/Rails lock semantics specifically (Rails' advisory lock on `db:migrate`, Liquibase's `DATABASECHANGELOGLOCK`, Flyway's history-table lock); these are well known but were outside the fetched sources, so they are not cited here.

## Key Question 3: Secrets — generated at install, External Secrets Operator, Sealed Secrets, rotation of DB passwords and JWT signing keys

### Takeaway
Mature charts generate first-boot secrets with an idempotent hook Job (GitLab's shared-secrets: "It never rotates a value") or Helm's `lookup`-with-fallback pattern (which breaks under ArgoCD client-side rendering), while telling production users to bring secrets from an external manager; External Secrets Operator has absorbed both roles via `refreshPolicy: CreatedOnce` + Password generators and `refreshInterval`-driven sync, with Reloader to restart pods. DB password rotation is converging on operator-managed roles (CNPG `passwordSecret`/`DatabaseRole`) plus dual-credential overlap; JWT signing-key rotation follows the JWKS state machine Supabase documents (standby → current → previously used → revoked) so that cached verifiers never see an unknown `kid`.

### Cited Findings

**Generated at install**
- GitLab shared-secrets: "A `pre-install` and `pre-upgrade` hook job then generates the secrets" — initial root password, self-signed TLS certs for GitLab/Registry/KAS/Pages, registry auth certs, Registry/Shell/Gitaly secrets, SSH host keys, Rails secret, AI Gateway keys, OpenBao unseal key. "The job runs on every install and upgrade. It never rotates a value." Existing Secrets keep their values; missing keys are added only for literal values; "Generated secrets are not owned by the Helm release, so `helm uninstall` does not remove them." Disable with `shared-secrets.enabled: false`, after which "you must manually create all secrets." — [GitLab shared-secrets chart](https://docs.gitlab.com/charts/charts/shared-secrets/)
- Helm `lookup` pattern: a Secret template reads the existing value via `lookup` and falls back to `randAlphaNum` only on first install; `lookup` requires a live cluster (`--dry-run=server`), and under ArgoCD "Helm's lookup function always returns an empty result in client-side rendering, so every ArgoCD sync generates new random values" — workaround is to render once and pin the values. Replicated also reports `lookup` is unsupported in its pipeline. — [helm-www issue #1259](https://github.com/helm/helm-www/issues/1259); [CrewAI ArgoCD notes](https://enterprise-docs.crewai.com/configuration/argocd); [Replicated community](https://community.replicated.com/t/helm-release-isinstall-and-isupgrade-are-inaccurate/1189/2); [Magnolia chart fix MR](https://gitlab.com/mironet/magnolia-helm/-/merge_requests/40)
- Zitadel masterkey: "encrypts sensitive data at rest"; production stores it in Secret `zitadel-masterkey` (key `masterkey`) referenced by `masterkeySecretName` (setting both inline and secret is rejected); "Once ZITADEL has been initialized with a masterkey, it cannot be changed without losing access to encrypted data." — [Zitadel: Deploy on Kubernetes](https://zitadel.com/docs/self-hosting/deploy/kubernetes); [zitadel-charts values.yaml](https://github.com/zitadel/zitadel-charts/blob/a8abf2d4ac6d0601bf8b81fbc3db16ff7a68249d/charts/zitadel/values.yaml)
- Supabase Compose: `setup.sh` / `utils/generate-keys.sh` generate `POSTGRES_PASSWORD` (random; "use only letters and numbers to avoid URL encoding issues"), dashboard basic-auth password, `SECRET_KEY_BASE`, `REALTIME_DB_ENC_KEY`, `VAULT_ENC_KEY`, `PG_META_CRYPTO_KEY`, Logflare tokens, S3 keys; `utils/add-new-auth-keys.sh` adds the API keys and the asymmetric JWT signing key pair. "we strongly recommend using a secrets manager when deploying to production"; by default everything is in `.env`. — [Supabase self-hosting with Docker](https://supabase.com/docs/guides/self-hosting/docker)

**External Secrets Operator / Sealed Secrets**
- ESO `refreshPolicy`: `Periodic` (default; updates on `refreshInterval`, and `refreshInterval: 0` "will only create the secret once"), `CreatedOnce` ("syncs the Kind=Secret once per ExternalSecret object and then stops"; pair with `immutable: true` so recreation does not overwrite), `OnChange`. `creationPolicy`: Owner (default), Orphan, Merge, None. `deletionPolicy`: Retain (default), Delete, Merge. Templates build derived values, e.g. `postgres://{{ .username }}:{{ .password }}@{{ .database_host }}:5432/payments`. Generators (including a Password generator) are referenced through `dataFrom.sourceRef.generatorRef`; the Keycloak example combines Password generator + `CreatedOnce` + `immutable: true`. — [ESO ExternalSecret API](https://external-secrets.io/latest/api/externalsecret/)
- Bitnami's Sealed Secrets is explicitly unaffected by the August 2025 Bitnami catalogue changes. — [bitnami/charts issue #35164](https://github.com/bitnami/charts/issues/35164)

**DB password rotation**
- CNPG: managed roles reference a `kubernetes.io/basic-auth` Secret (`passwordSecret`, label `cnpg.io/reload: "true"`), the username in the Secret must match the role, and `DatabaseRole` "is applied when its specification or its password Secret changes." Pre-hashed passwords pass through with annotation `cnpg.io/passwordPassthrough: "enabled"`. — [CNPG declarative role management](https://cloudnative-pg.io/docs/devel/declarative_role_management)
- Bitnami PostgreSQL chart ships a `passwordUpdateJob`; previous passwords are read from the deployed Secret unless `auth.existingSecret`/`helm template` is used, in which case `passwordUpdateJob.previousPasswords.*` must be set. — [bitnami/postgresql README](https://raw.githubusercontent.com/bitnami/charts/main/bitnami/postgresql/README.md)
- Practitioner pattern (2026 blogs, not authoritative): ESO syncs on `refreshInterval`; pods reading env vars need a restart, done by Stakater Reloader via `secret.reloader.stakater.com/reload: "<secret>"`; `subPath` mounts do not pick up updates; "Dual-Credential Rotation" creates the new user/password alongside the old, rolls pods, then retires the old one; Vault dynamic credentials with short TTL are the alternative. — [oneuptime: ESO refresh intervals](https://oneuptime.com/blog/post/2026-02-09-secret-rotation-external-secrets-refresh/view); [oneuptime: ESO rotation with Flux](https://oneuptime.com/blog/post/2026-03-13-handle-external-secrets-rotation-with-flux/view)
- A CNPG-specific 2026 post recommends alternating login roles (`app_login_a`/`app_login_b`) for zero-downtime rotation because pooled sessions do not reauthenticate and can hide a failed rotation. — [oneuptime: CNPG password and TLS rotation](https://oneuptime.com/blog/post/2026-09-18-cloudnativepg-password-tls-rotation/view) (blog)
- Supabase Compose rotation runbook: API keys via `utils/rotate-new-api-keys.sh --update-env` then `sh run.sh recreate` ("Rotating these keys does not invalidate existing user session tokens"); DB password via `utils/db-passwd.sh` then recreate; regenerating the asymmetric key pair affects active sessions. — [Supabase self-hosting with Docker](https://supabase.com/docs/guides/self-hosting/docker)

**JWT signing key rotation**
- Supabase signing keys: asymmetric (ES256 recommended over RS256; shared secrets "Not recommended for production applications"), published at a JWKS endpoint. States: standby ("A newly created key starts off as standby, before being rotated into in use"), current, previously used, revoked; "Each action on a key is reversible (except permanent deletion)." — [Supabase: JWT signing keys](https://supabase.com/docs/guides/auth/signing-keys)
- Rotation: create standby → confirm verifiers use JWKS (`getClaims()`) → rotate ("Rotating the keys immediately causes the Auth server to issue new JWT access tokens"; "Non-expired access tokens will remain to be accepted") → revoke the previous key after all regular JWTs expire. Standby exists because the discovery endpoint "is cached by Supabase's edge servers for 10 minutes" plus up to 10 more minutes in clients. For a 1-hour token expiry, wait "at least 1 hour and 15 minutes" before revoking the legacy secret. Cadence: "rotate signing keys at least once a year" and immediately on suspected compromise. — [Supabase: JWT signing keys](https://supabase.com/docs/guides/auth/signing-keys)

### Inferences
- For a product that must ship both Helm and Compose, the lowest-drift approach is: the application binary can generate its own missing secrets on first boot into a persisted location (Compose) *and* the chart can create them via a `pre-install` hook Job that is a no-op when the Secret exists (GitLab's exact semantics). Avoid `lookup` if customers deploy with ArgoCD or Flux.
- Separate "install-time generated" from "externally managed" in values: `secrets.create: true|false` plus `secrets.existingSecret`, and document the ESO `CreatedOnce` + Password generator recipe as the GitOps-friendly way to get install-time generation.
- Multi-key JWKS with `kid` and a standby period is the only rotation scheme that works when the verifiers are third parties (customer IdP integrations, mobile clients that cache keys); a single shared `JWT_SECRET` env var cannot be rotated without a logout storm.

### Gaps
- No primary Sealed Secrets or Stakater Reloader docs were fetched; their behaviour is cited only via the Bitnami notice and 2026 blog posts.
- No product chart was found that documents DB password rotation end-to-end for an external (non-operator) database; GitLab, Coder, Sourcegraph all defer to "update the Secret and restart."
- Keycloak's own key-rotation docs were not fetched; Supabase is used as the representative JWKS rotation design.

## Key Question 4: Bundling an identity provider (Keycloak, Zitadel, Dex) as a subchart vs expecting the customer's IdP; what Sourcegraph, GitLab, Mattermost, Grafana, Supabase, PostHog and Coder do

### Takeaway
None of the surveyed products bundles a third-party IdP in its chart or Compose stack; each ships its own user store plus OIDC/SAML/OAuth federation to the customer's IdP (Coder: GitHub OAuth default with "configure your own" advice; GitLab: its own Rails auth plus shared-secrets-generated root password; Supabase: its own GoTrue auth; Keycloak and Zitadel are themselves IdPs that require an external Postgres). Bundling Keycloak as a subchart is seen in platform products such as Camunda, which nonetheless recommends an external Keycloak for production.

### Cited Findings
- Coder: the Kubernetes install page covers only GitHub OAuth2 and recommends production deployments "configure your own GitHub OAuth2 provider and disabling the default one" (`CODER_OAUTH2_GITHUB_DEFAULT_PROVIDER_ENABLE: "false"`); no IdP subchart is mentioned. — [Coder: Install on Kubernetes](https://coder.com/docs/install/kubernetes)
- GitLab: the shared-secrets job generates the "Initial root password" and Rails secrets; GitLab is its own identity store, with no IdP subchart in the umbrella. — [GitLab shared-secrets chart](https://docs.gitlab.com/charts/charts/shared-secrets/)
- Supabase: the Compose stack includes its own Auth service (GoTrue) alongside Studio, Envoy/Kong, PostgREST, Realtime, Storage, imgproxy, postgres-meta, Postgres, Edge Runtime and Supavisor; no third-party IdP container. — [Supabase self-hosting with Docker](https://supabase.com/docs/guides/self-hosting/docker)
- Keycloak Operator: requires an externally provisioned database and a TLS Secret; "Change the default admin credentials and enable MFA in Keycloak before going to production"; proxy headers must match the ingress and with edge/reencrypt termination the HTTP port should be restricted with network policies to prevent header spoofing. — [Keycloak Operator basic deployment](https://www.keycloak.org/operator/basic-deployment)
- Zitadel: chart with optional Postgres subchart for quickstart, `zitadel-init`/`zitadel-setup` Jobs, masterkey Secret; PostgreSQL 14–18. — [Zitadel: Deploy on Kubernetes](https://zitadel.com/docs/self-hosting/deploy/kubernetes)
- Dex: official chart at `charts.dexidp.io`; connector secrets (GitHub `clientSecret`, LDAP `bindPW`, Google service-account file) are expected to be pre-created Kubernetes Secrets injected as env vars or mounted volumes; a maintainer on the chart repo said users should create the Secret before installing the chart. After updating the Secret, "the Dex pods need a restart so environment-based secret values reload." — [dexidp/helm-charts issue #23](https://github.com/dexidp/helm-charts/issues/23); [oneuptime: Dex with Flux](https://oneuptime.com/blog/post/2026-03-06-deploy-dex-identity-provider-flux-cd/view) (blog)
- Camunda (platform chart that does bundle Keycloak): uses a Keycloak subchart for an internal instance and recommends an external Keycloak for production. — [Camunda: internal Keycloak](https://docs.camunda.io/docs/self-managed/deployment/helm/configure/authentication-and-authorization/internal-keycloak/); [Camunda: external Keycloak](https://docs.camunda.io/docs/self-managed/deployment/helm/configure/authentication-and-authorization/using-external-keycloak)
- Mattermost: the operator-based deployment manifests reference an external database and object storage; IdP integration is not part of the chart. — [Mattermost: Deploy on Kubernetes](https://docs.mattermost.com/deployment-guide/server/kubernetes/deploy-k8s.html)
- PostHog: self-hosted hobby stack is Compose-only with PostHog's own auth; Kubernetes deployments are "no longer supported." — [PostHog self-host docs](https://posthog.com/docs/self-host)

### Inferences
- For a single-org on-prem install, the expected shape is: built-in local accounts for break-glass and first boot, OIDC (and optionally SAML) against the customer's IdP, with the OIDC client secret supplied as a Secret reference. Bundling Keycloak/Zitadel adds a second Postgres-backed stateful system with its own masterkey/backup/upgrade lifecycle, which is why only platform suites (Camunda) do it and even they say "external for production."
- If an embedded IdP is wanted for the vendor cloud (multi-tenant), Zitadel's model (multi-instance, PostgreSQL only, masterkey Secret) maps better than Keycloak's realm-per-tenant model, but this is a design inference, not something the fetched docs state.

### Gaps
- Grafana's and Sourcegraph's auth-provider docs were not fetched; both are known to support OAuth/OIDC/SAML but no citation was gathered here.
- No source was found describing a product that ships Dex as a subchart in 2025–2026 (Argo CD historically did; not verified in this research).

## Key Question 5: Docker Compose for development and small on-prem — healthchecks, ordering, volume layout, backups, keeping Compose and Helm from drifting

### Takeaway
Official Compose guidance is explicit that `depends_on` alone only waits for "running," so production-grade stacks (PostHog, Supabase) put `pg_isready -h 127.0.0.1` healthchecks on Postgres and use `condition: service_healthy` / `service_completed_successfully`; Mattermost's official Compose instead keeps things minimal (no healthchecks) but hardens containers (`read_only`, `no-new-privileges`, tmpfs). Backups are mostly left to the operator ("make sure you have created back-ups" before `upgrade-hobby`). The anti-drift pattern that works is the same image with a `migrate` entry point used by both Compose and the Helm Job (Sourcegraph's migrator), plus scripted updates that three-way-merge upstream Compose files (Supabase `update.sh`).

### Cited Findings
- Compose semantics: "Compose does not wait until a container is 'ready', only until it's running." Long-syntax conditions: `service_started`; `service_healthy` ("a dependency is expected to be 'healthy', which is defined with `healthcheck`"); `service_completed_successfully` ("expected to run to successful completion before starting a dependent service"). `restart: true` restarts dependents when the dependency is restarted by an explicit Compose operation; Compose "also removes services in dependency order." — [Docker: Control startup order](https://docs.docker.com/compose/how-tos/startup-order/)
- `pg_isready` gotcha (blog): without `-h`, it probes the Unix socket, which can answer during the Postgres image's init phase while TCP 5432 is still closed; use `pg_isready -h 127.0.0.1`. A healthy database also does not mean tables exist, which is why a migration gate matters. — [DEV: depends_on doesn't wait, neither does pg_isready](https://dev.to/ji_ai/docker-compose-dependson-doesnt-wait-neither-does-pgisready-179b)
- PostHog base Compose: `db` healthcheck `pg_isready -U posthog -h 127.0.0.1` (interval 5s, timeout 30s, retries 30, start_period 10s); Redis `redis-cli ping`; ClickHouse `wget --spider http://localhost:8123/ping`; Kafka (Redpanda) `curl -f http://localhost:9644/v1/status/ready`; several services use `condition: service_healthy`; images pinned (`postgres:15.12-alpine`, `redis:7.2-alpine`, `redpandadata/redpanda:v25.1.9`, a PostHog-built ClickHouse). — [PostHog docker-compose.base.yml](https://raw.githubusercontent.com/PostHog/posthog/master/docker-compose.base.yml)
- PostHog hobby: `deploy-hobby` asks for a Docker Hub tag and domain; "We will need to wait ~5-10 minutes for things to settle down, migrations to finish, and TLS certs to be issued" (Caddy issues Let's Encrypt certs). Upgrades via `upgrade-hobby`; "Before upgrading, make sure you have created back-ups of all your data!" Sizing: ~4 vCPU, 16 GB RAM, >30 GB disk. Self-hosted is "officially unsupported," MIT-licensed, no CVEs published; "New deployments of PostHog's paid open source product using Kubernetes are no longer supported." PostHog builds an image per commit rather than numbered releases. — [PostHog self-host docs](https://posthog.com/docs/self-host); [PostHog: Sunsetting Kubernetes support](https://posthog.com/blog/sunsetting-helm-support-posthog)
- Supabase Compose: data in `volumes/db/data` and `volumes/storage` plus Docker-managed volumes; `reset.sh` deletes all of them; `update.sh` "pulls the latest `self-hosted/v*` configuration and merges it into your files with a three-way merge"; stable snapshots ship roughly monthly and "The images are tested together"; changing a single image tag means "compatibility is not guaranteed." HTTPS via a reverse proxy is required for production/OAuth. Kubernetes is a community project (`supabase-community/supabase-kubernetes`). — [Supabase self-hosting with Docker](https://supabase.com/docs/guides/self-hosting/docker); [Supabase self-hosting overview](https://supabase.com/docs/guides/self-hosting)
- Mattermost official Compose: two services, `postgres:${POSTGRES_IMAGE_TAG}` and `mattermost/${MATTERMOST_IMAGE}:${MATTERMOST_IMAGE_TAG}`; both `security_opt: no-new-privileges:true`, postgres `read_only: true` with tmpfs `/tmp` and `/var/run/postgresql`; `mem_limit` 16G/4G; bind-mounted host paths for config, data, logs, plugins, client plugins; DB via `MM_SQLSETTINGS_DRIVERNAME`/`MM_SQLSETTINGS_DATASOURCE`; short-form `depends_on` with no healthcheck; an optional commented-out Watchtower auto-updater. — [mattermost/docker compose file](https://github.com/mattermost/docker/blob/main/docker-compose.yml)
- Sourcegraph: the same `migrator` image is used as a Compose container, a Kubernetes Job, and a Helm value (`migrator.args`); Compose users edit `command:` and must reset it to `up` afterwards. — [Sourcegraph migrator operations](https://sourcegraph.com/docs/admin/updates/migrator/migrator-operations)
- Coder offline Compose: Docker users can add `./plugins:/opt/terraform/plugins` in `compose.yaml` instead of rebuilding the image. — [Coder: Offline deployments](https://coder.com/docs/install/offline)

### Inferences
- A minimal production-grade Compose for a Postgres-backed service in 2026: pinned `postgres:<major>.<minor>-alpine`, `pg_isready -h 127.0.0.1 -U <user>` healthcheck with a `start_period`, a `migrate` one-shot service (`restart: "no"`) that `depends_on: db: condition: service_healthy`, the app `depends_on: migrate: condition: service_completed_successfully`, named volumes for data, and `read_only` + `no-new-privileges` + tmpfs as Mattermost does.
- Drift control: (a) one image, one entrypoint with `serve` and `migrate` subcommands; (b) the Helm chart's Job and the Compose `migrate` service both call the same subcommand; (c) env-var-only configuration so values.yaml and `.env` map 1:1; (d) a CI job that renders both and diffs the image references. PostHog's per-commit images and Supabase's "tested together" monthly snapshots are two different answers to "which combination of tags is supported."
- Compose backups are universally left to the operator; shipping a documented `pg_dump` sidecar/cron (or pointing at CNPG/managed backups on Kubernetes) is a differentiator rather than table stakes.

### Gaps
- Compose `required: false` and healthcheck `start_interval` were not covered by the fetched official page.
- No surveyed vendor documents a built-in Compose backup service; this appears to be a genuine gap in the ecosystem, not just in this research.
- GitLab's Docker (Omnibus) single-container path was not researched; it is a different packaging from the chart and is a known drift source but no citation was gathered.

## Key Question 6: Air-gapped installs — image mirrors, chart museums, offline licence checks

### Takeaway
Air-gap practice in 2025–2026 is: mirror every image a release references into a customer registry (vendor-published image list preferred, `helm template | grep image:` as fallback), ship charts as OCI artifacts (Helm's recommended distribution; digest pinning advised) or tarballs, and validate licences with locally verifiable signed keys (Coder: "No outbound connection to Coder is required"; GitLab: approval-only Offline Cloud License with monthly manual usage export; Replicated: licence fields gate air-gap and bundle the installer, k0s and Helm extensions into a `.airgap` file).

### Cited Findings
- Helm: "It is recommended to use container registries with OCI support to store and share chart packages." `helm push` accepts only `helm package` tarballs and the `oci://` reference "must not contain the basename or tag"; `helm pull/show/template/install/upgrade` accept `oci://`; dependencies use `repository: oci://host/repo`; `.prov` provenance files upload automatically; `helm-sigstore` is the alternative to GPG provenance; "Installing a chart with a digest is more secure than a tag because digests are immutable." — [helm.sh: Registries](https://helm.sh/docs/topics/registries/)
- Coder offline: build a custom image extending the official one with Terraform provider mirrors (`/opt/terraform/plugins`); set `CODER_TELEMETRY_ENABLE=false`, `CODER_UPDATE_CHECK=false`, `CODER_BLOCK_DIRECT=true`, `CODER_DERP_SERVER_STUN_ADDRESSES=disable`, and `CODER_PG_CONNECTION_URL` to an external database. "License keys are validated locally using cryptographic signatures. No outbound connection to Coder is required." — [Coder: Offline deployments](https://coder.com/docs/install/offline)
- GitLab: an Offline Cloud License is available "on an approval-only basis" for air-gapped instances on 15.0+; after-sale requests need Sales VP approval for a Cloud Licensing Exemption; the licence file arrives by email/Customers Portal; usage data must be exported and sent manually each month or renewals get complicated; a Cloud License activation code cannot be applied during installation whereas an offline licence file can. — [GitLab Cloud Licensing FAQ](https://about.gitlab.com/pricing/licensing-faq/cloud-licensing/); [GitLab handbook: cloud licensing exemptions](https://handbook.gitlab.com/handbook/support/license-and-renewals/workflows/self-managed/cloud-licensing/); [gitlab-org issue 407471](https://gitlab.com/gitlab-org/gitlab/-/issues/407471)
- Replicated: "By default, licenses support online installations only"; air-gap access is a built-in licence field; Embedded Cluster air-gap bundles include the installer, k0s, and Helm extensions, installed with `./my-app install --license license.yaml --airgap-bundle myapp.airgap`; the Replicated SDK must be a chart dependency; Embedded Cluster v3 is Beta. A third-party doc (Dreadnode) states Replicated does not build air-gap bundles for Helm CLI installs and that Helm air-gap means mirroring images yourself; Replicated's onboarding page claims Helm CLI coverage — unresolved conflict. — [Replicated: air gap onboarding](https://docs.replicated.com/vendor/replicated-onboarding-air-gap); [Replicated: Embedded Cluster air gap](https://docs.replicated.com/embedded-cluster/v3/installing-embedded-air-gap); [Dreadnode air-gap docs](https://docs.dreadnode.io/self-hosting/air-gap/)
- Vendor runbook examples: Stacklok authenticates `skopeo` and `helm registry login` to the Replicated proxy registry with the License ID and says to use the portal's image list as the source of truth; Fish Audio warns the licence bundle "must also cross the air gap, and that it expires," that a Helm release is many images, and that copying an image into another registry drops a digest pin. — [Stacklok air-gap install](https://docs.stacklok.com/platform/enterprise-platform/airgap-install); [Fish Audio air-gapped](https://docs.fish.audio/developer-guide/self-hosting/air-gapped)
- Community approach to building the mirror list: render with `helm template` and grep `image:`; OpenFaaS ships an `airfaas` tool to mirror images and bundle charts; Kubeapps documents download chart → mirror images → install from local chart directory. — [oneuptime: mirror images for offline clusters](https://oneuptime.com/blog/post/2026-01-19-kubernetes-mirror-images-offline/markdown); [OpenFaaS airgap](https://docs.openfaas.com/openfaas-pro/airgap); [Kubeapps offline installation](https://sap.github.io/kubeapps/docs/howto/offline-installation)
- Bitnami impact on air-gap: because public Bitnami images are frozen, any bundled-Postgres subchart in an air-gap bundle must be re-pointed to a mirrored `bitnamilegacy`/BSI/self-built image. — [bitnami/charts issue #35164](https://github.com/bitnami/charts/issues/35164)

### Inferences
- Ship, per release: (1) a machine-readable image list with digests, (2) the chart as an OCI artifact plus `.tgz`, (3) a `global.imageRegistry` override that rewrites every image including subcharts, (4) a licence format that is an offline-verifiable signed token with an expiry and an explicit renewal workflow, and (5) disabled-by-default outbound calls (telemetry, update checks) when the licence is marked air-gapped. Coder's env-var list is a compact checklist of outbound paths to turn off.
- GitLab's monthly manual usage export is the model for seat-based billing without connectivity; Coder's locally signed key is the model for feature gating.

### Gaps
- ChartMuseum specifically was not researched; Helm's own docs now steer toward OCI registries (Harbor, ECR, GHCR) rather than ChartMuseum.
- Whether Replicated supports `.airgap` bundles for pure Helm CLI installs in 2026 is contradicted between sources.

## Key Question 7: Versioning and upgrade compatibility between clients that sync (older app versions against a newer hub, schema version negotiation)

### Takeaway
Shipping products handle client/server skew with an explicit, published window rather than open-ended compatibility: GitLab's agent supports the same minor ±1 with a UI warning; Mattermost's mobile app pins its minimum server to the most recently end-of-lifed ESR and signs users out below it; Immich enforces matching major versions and users hit hard errors on mismatch; Replicache sends a `schemaVersion` on every push/pull so the server can serve old and new clients concurrently and new clients re-download rather than migrate local data.

### Cited Findings
- GitLab agent for Kubernetes: "the version of the agent installed in your cluster should match the GitLab major and minor version. The previous and next minor versions are also supported" (example: GitLab 14.9.x supports agent 14.8.x–14.10.x); "GitLab warns you on the agent's list page to update the agent version"; do not use `--reuse-values` on upgrade; "The Helm chart is updated separately from the agent." — [GitLab: Install the agent](https://docs.gitlab.com/user/clusters/agent/install/)
- Mattermost mobile: minimum server version "tracks the most recent Extended Support Release (ESR) to reach End of Support"; from October 2026 the app requires server v10.11+; below that "users won't be able to sign in from the mobile app, and anyone already signed in will be signed out"; next step is v11.7 after May 2027. The changelog states "Upgrade to server version v10.11.0 or later is required." — [Mattermost forum announcement](https://forum.mattermost.com/t/starting-in-october-2026-the-mattermost-mobile-app-will-require-mattermost-server-v10-11-or-later/26039); [Mattermost mobile changelog](https://docs.mattermost.com/product-overview/mobile-app-changelog.html)
- Immich: users report "Your App Major version is not compatible with this server" errors and a 2024 case where app 1.98.1 failed against server 1.98.0 until the server was upgraded; packaged servers (TrueNAS, Umbrel) lag releases; iOS users may be told to update before the App Store build is live. No official compatibility matrix was found. — [immich discussion #29051](https://github.com/immich-app/immich/discussions/29051); [immich discussion #7776](https://www.github.com/immich-app/immich/discussions/7776); [immich issue #9457](https://www.Github.com/immich-app/immich/issues/9457)
- Replicache: "Replicache forks the storage from some previous instance with the same name and schemaVersion; clients will have to download a new copy of the data. But this is much more robust than trying to migrate data"; "Other clients that haven't yet upgraded proceed happily using the old schema"; "Replicache also includes the schemaVersion in replicache-push and replicache-pull so that the server can respond appropriately"; pull requests are themselves versioned (`pullVersion`); mutators are not versioned, so a changed signature needs a new mutator name; newer releases include the schemaVersion in the IndexedDB name. — [Replicache: launch checklist](https://doc.replicache.dev/howto/launch); [replicache PR #741](https://github.com/rocicorp/replicache/pull/741)
- Server-side schema versioning examples that interact with clients: Sourcegraph's `migration_logs` table and `drift` check gate upgrades; GitLab's batched background migrations must finish before the next upgrade (the chart's `batchedBackgroundMigrationsCheck` Job waits up to `activeDeadlineSeconds: 21600`). — [Sourcegraph migrator operations](https://sourcegraph.com/docs/admin/updates/migrator/migrator-operations); [GitLab migrations chart](https://docs.gitlab.com/charts/charts/gitlab/migrations/)
- Supabase's "tested together" monthly snapshots and PostHog's per-commit images are the two server-side answers to "which component versions are compatible"; Supabase states per-service tag changes have "compatibility not guaranteed." — [Supabase self-hosting with Docker](https://supabase.com/docs/guides/self-hosting/docker); [PostHog: Sunsetting Kubernetes support](https://posthog.com/blog/sunsetting-helm-support-posthog)

### Inferences
- For a hub that on-prem customers upgrade on their own schedule while the vendor cloud auto-upgrades, the combination that the evidence supports is: (1) clients send a protocol/schema version with every sync request (Replicache), (2) the hub advertises `minClientVersion`/`maxClientVersion` and the client shows an upgrade prompt or hard-stops (Mattermost/Immich behaviour), (3) a published skew window such as "same minor ±1" (GitLab agent), (4) additive-only wire/schema changes within the window and expand/contract on the server, and (5) local client data keyed by schema version so a client upgrade re-syncs rather than migrates (Replicache).
- The vendor cloud differs from single-org on-prem mainly in that the cloud hub will usually be *newer* than on-prem clients, while on-prem hubs may be *older* than app-store clients; the compatibility window therefore has to be symmetric, which is exactly what GitLab's ±1 minor rule provides and what Immich's "match the major" rule does not.

### Gaps
- No vendor doc was found that formally describes "schema version negotiation" between a mobile client and a self-hosted server beyond Replicache's `schemaVersion`/`pullVersion`; Mattermost and GitLab express it as version windows, not negotiated schemas.
- GitLab agent-vs-KAS (server component) skew separate from the GitLab release version was not documented on the fetched page.
- Grafana, Sourcegraph, Coder and Supabase client-compatibility policies were not researched; Coder's CLI/agent skew policy and Supabase's client-library-vs-server policy are plausible additional data points.

## Cross-cutting: single-org on-prem vs the vendor's own cloud (synthesis of the above)

### Takeaway
The products surveyed run the same images in both places but differ in (a) who owns Postgres (customer-supplied vs vendor-managed/operator-managed), (b) who holds secrets (install-time generated or customer ESO vs vendor secret manager), (c) licence verification (offline signed keys vs online), (d) who drives upgrades (customer runs `helm upgrade`/`upgrade-hobby` with a pre-upgrade backup vs continuous deploys with expand/contract), and (e) support posture (PostHog and Sourcegraph have withdrawn or narrowed self-hosted support entirely; Mattermost has retired its Helm chart for the operator).

### Cited Findings
- PostHog "no longer supports paid, self-hosted deployments and no longer sells self-hosted licenses," recommends PostHog Cloud, keeps the MIT Docker Compose path "without guarantee," and builds an image per commit so users "can pin a version or roll back where necessary." — [PostHog: Sunsetting Kubernetes support](https://posthog.com/blog/sunsetting-helm-support-posthog)
- Sourcegraph moved its core repository to a private repo on August 22, 2024 (no longer source-available) after moving to the Enterprise licence in 2023; Docker Compose remains a supported deployment (the "deprecated" wording in 2024 docs refers only to the `docker-compose` CLI being replaced by `docker compose`). — [Wikipedia: Sourcegraph](https://en.wikipedia.org/wiki/Sourcegraph); [sourcegraph/docs PR #583](https://github.com/sourcegraph/docs/pull/583.patch); [Sourcegraph Compose upgrade notes](https://sourcegraph.com/changelog/self-hosted/docker-compose)
- Mattermost's Team Edition Helm chart "is no longer supported"; the Mattermost Operator is the maintained Kubernetes path. — [mattermost-team-edition README](https://raw.githubusercontent.com/mattermost/mattermost-helm/master/charts/mattermost-team-edition/README.md)
- Coder: "Coder does not manage a database server for you"; licences validate offline; telemetry and update checks are on by default and can be disabled. — [Coder: Install on Kubernetes](https://coder.com/docs/install/kubernetes); [Coder: Offline deployments](https://coder.com/docs/install/offline)
- Supabase: self-hosting means "you are responsible for monitoring and uptime," the Compose setup "does not collect telemetry," and Kubernetes support is community-maintained. — [Supabase self-hosting overview](https://supabase.com/docs/guides/self-hosting)

### Inferences
- The surviving pattern for a small vendor is: one chart and one Compose file, both consuming the same image and the same `migrate`/`serve` entrypoint; a hard split between "quickstart" (bundled Postgres, generated secrets, self-signed TLS) and "production" (external Postgres or CNPG, ESO/Sealed Secrets, customer TLS and IdP) expressed as values presets; offline-verifiable licences; and a published client skew window. The vendor cloud is then a Helm install of the same chart with vendor-managed Postgres (or CNPG), vendor secret manager, continuous deploys, and the compatibility window enforced at the API edge.

### Gaps
- No single source compares a vendor's own cloud deployment with its on-prem chart; the cloud-side details above are inferred from the on-prem docs and the products' public statements.
