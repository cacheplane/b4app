# Reference repository survey: multi-tenant, on-prem-deployable hub service patterns

Scope: a read-only survey of one vendor's monorepo (the "reference product"), conducted 2026-10-31 against a checkout whose last commit is dated 2026-03-16. The product is an enterprise "agent interaction" hub: a REST API, a browser SPA, a realtime WebSocket gateway, PostgreSQL, Redis, and an external OIDC identity provider. All citations are file paths relative to the reference repository root; no web sources were used. Identifiers (product, vendor, customers, people, hosts, registries, ticket prefixes) are redacted. The product's short code prefix appears in the source as a schema name, a package scope, a cookie prefix, an API-key prefix, and image/secret names; it is written here as `<prefix>` or `app.` (schema).

Discrepancies between the repository's own documents and its code are called out explicitly, because several of them are the most instructive findings.

## What is the stack and repository shape?

### Takeaway
An Nx 22 / pnpm 9 TypeScript monorepo with an Express 4 API, an Angular 20 + NgRx SPA (the docs still say React), shared `libs/` for auth and threads, a separate Elixir/Phoenix realtime gateway, raw SQL migrations via graphile-migrate, a single Helm chart, Terraform for the vendor's own cloud, and docker-compose for local development.

## How is a tenant identified on each request and enforced in the data layer?

### Takeaway
Tenant identity is a request-scoped string: in hosted mode it must arrive as an `x-tenant-id` header (400 otherwise); in self-hosted mode it is a configured `DEFAULT_TENANT_ID`. Enforcement is purely application-level: every table carries a `tenant_id TEXT REFERENCES app.tenants(id)` column and every query adds `AND tenant_id = $n`; there is no PostgreSQL row-level security, no `SET LOCAL` session variable, and no per-tenant database role.

### Cited Findings
- Deployment mode is a zod enum `['hosted','self-hosted']` defaulting to `self-hosted`; `DEFAULT_TENANT_ID` defaults to `'default'` — [libs/auth-server/src/env/authEnv.schema.ts](libs/auth-server/src/env/authEnv.schema.ts)
- Tenant middleware (shape, from `main.ts`):
  ```ts
  if (authEnv.deploymentMode === 'hosted') {
    const tenantHeader = req.headers['x-tenant-id'];
    if (typeof tenantHeader !== 'string' || tenantHeader.length === 0) {
      next(createAppError('TENANT_CONTEXT_REQUIRED')); return;
    }
    req.tenantId = tenantHeader; res.locals.tenantId = tenantHeader; next(); return;
  }
  req.tenantId = authEnv.defaultTenantId; ...
  ```
  — [apps/app-api/src/main.ts](apps/app-api/src/main.ts)
- `TENANT_CONTEXT_REQUIRED` is HTTP 400, category `validation`; `TENANT_OIDC_CONFIG_NOT_FOUND` is HTTP 500, category `dependency` — [apps/app-api/src/errors/registry.ts](apps/app-api/src/errors/registry.ts)
- The tenant header is not authenticated: middleware order is request-id → tenant header → Auth.js routes → session → user resolution; nothing checks that the session's user belongs to the header's tenant — [apps/app-api/src/main.ts](apps/app-api/src/main.ts)
- Tenants table: `id TEXT NOT NULL DEFAULT gen_random_uuid()::text PRIMARY KEY, name TEXT NOT NULL` plus timestamps and soft-delete columns; child tables (`tenant_email_domains`, `tenant_oidc_connections`, `users`, `user_identities`, `projects`, `api_keys`, `threads`, `agent_runs`, `run_events`, `run_state`) all have `tenant_id TEXT NOT NULL REFERENCES app.tenants(id)` and a partial index `CREATE INDEX ... ON app.<table> (tenant_id) WHERE deleted_at IS NULL` — [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql)
- Thread data access is tenant-scoped in every query, for example `WHERE thread_id = $1 AND tenant_id = $2 AND deleted_at IS NULL` for reads and the same predicate inside the `UPDATE` and the soft-delete CTE — [libs/threads/src/threads.ts](libs/threads/src/threads.ts)
- API-key list/delete queries add `tenant_id = $n` and (in code) `organization_id = $n` — [apps/app-api/src/api-keys.ts](apps/app-api/src/api-keys.ts)
- Event uniqueness is tenant-scoped: `CREATE UNIQUE INDEX ... ON app.run_events (tenant_id, event_id) WHERE deleted_at IS NULL`, and the gateway inserts with `ON CONFLICT (tenant_id, event_id) WHERE deleted_at IS NULL DO NOTHING` — [db-migrations/migrations/current/005-run-event-ordering.sql](db-migrations/migrations/current/005-run-event-ordering.sql), [apps/realtime-gateway/lib/realtime_gateway/consumers/postgres_writer.ex](apps/realtime-gateway/lib/realtime_gateway/consumers/postgres_writer.ex)
- The gateway stamps `tenant_id` onto every ingested event from the authenticated API key, not from the payload — [apps/realtime-gateway/lib/realtime_gateway/events/enricher.ex](apps/realtime-gateway/lib/realtime_gateway/events/enricher.ex), [apps/realtime-gateway/lib/realtime_gateway/sources/runner_channel.ex](apps/realtime-gateway/lib/realtime_gateway/sources/runner_channel.ex)
- A grep for `ROW LEVEL`, `CREATE POLICY`, `SET LOCAL`, `current_setting` across `apps`, `libs`, `db-migrations` returns nothing — repository search
- Current state defect: the thread routes ignore the middleware and hard-code the tenant: `// const getTenantId = (req) => req.tenantId ?? 'default';` is commented out and replaced with a constant seed tenant id, with "TODO: Replace this local testing override with tenant resolution before shipping" — [apps/app-api/src/routes/threads-routes.ts](apps/app-api/src/routes/threads-routes.ts)
- Current state defect: the API-key routes take `tenant_id`, `organization_id`, and `user_id` from the request body/query (zod-validated but caller-supplied), not from the resolved principal — [apps/app-api/src/routes/api-keys-routes.ts](apps/app-api/src/routes/api-keys-routes.ts)
- Current state defect: the WebSocket thread channel assigns the tenant from the join token but has `# TODO: Validate thread belongs to socket.assigns.tenant_id`; the broadcaster fans out by `thread:{thread_id}` alone — [apps/realtime-gateway/lib/realtime_gateway/client/thread_channel.ex](apps/realtime-gateway/lib/realtime_gateway/client/thread_channel.ex), [apps/realtime-gateway/lib/realtime_gateway/consumers/client_broadcaster.ex](apps/realtime-gateway/lib/realtime_gateway/consumers/client_broadcaster.ex)

### Inferences
- The intended design is "tenant is a column, every repository function takes `tenantId` as an explicit parameter, and tenant-scoped unique indexes make cross-tenant id collisions impossible." That part is sound and portable. What is missing is a binding between the authenticated principal and the tenant claimed on the request; in hosted mode a client can currently name any tenant.
- Using `TEXT` tenant ids with a uuid default (rather than integer identity) lets the seed and self-hosted deployments use readable ids like `default`, which simplifies single-tenant installs.
- Partial indexes `WHERE deleted_at IS NULL` on every FK/tenant column are a consistent convention; they keep soft-deleted rows out of the hot index.

### Gaps
- No evidence of how hosted-mode tenant resolution is meant to work end to end (subdomain? header set by an edge proxy? claim in the OIDC token?). The header is the only mechanism in code.

## How do users belong to orgs, and how are roles assigned and checked?

### Takeaway
Users belong to exactly one tenant via `users.tenant_id`; OIDC identities are linked to users through a `user_identities(issuer, subject)` table, with a first-login fallback that matches the email domain against verified tenant domains. There are no roles, no permissions, no memberships, no invites, and no SCIM anywhere in the repo; the only authorization distinction is "authenticated" (401) versus "authenticated but not a registered user" (403).

### Cited Findings
- Committed schema: `app.users (id NON_EMPTY_TEXT PRIMARY KEY, tenant_id TEXT NOT NULL REFERENCES app.tenants(id), created_at, deleted_at, deleted_by, deleted_reason)`; `app.user_identities (id identity, tenant_id, user_id REFERENCES app.users(id), issuer TEXT, subject TEXT, ...)` with `UNIQUE (issuer, subject) WHERE deleted_at IS NULL`; `app.tenant_email_domains (tenant_id, domain, verified BOOLEAN, verified_at)` with a global `UNIQUE (domain) WHERE deleted_at IS NULL` — [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql)
- Resolution order documented in code: "1. Fast path: lookup by (issuer, subject) in user_identities. 2. First-login: match email domain to a verified org domain, find user by email, then create user_identity link. 3. Not found: req.user remains undefined." — [libs/auth-server/src/express/userResolutionMiddleware.ts](libs/auth-server/src/express/userResolutionMiddleware.ts)
- Middleware is dependency-injected (`findUserByIdentity`, `findUserByEmailDomain`, `createUserIdentity`) so it is unit-testable without pg — [libs/auth-server/src/express/userResolutionMiddleware.ts](libs/auth-server/src/express/userResolutionMiddleware.ts), [libs/auth-server/src/express/userResolutionMiddleware.spec.ts](libs/auth-server/src/express/userResolutionMiddleware.spec.ts)
- `requireAuth` returns 401 `AUTH_UNAUTHENTICATED` when `res.locals.principal` is absent; `requireUser` returns 403 `USER_NOT_REGISTERED` ("Returns 403, not 401, because the caller IS authenticated — they just have no user record") — [libs/auth-server/src/express/requireAuth.ts](libs/auth-server/src/express/requireAuth.ts), [libs/auth-server/src/express/requireUser.ts](libs/auth-server/src/express/requireUser.ts)
- `GET /api/me` returns `{ principal, tenantId, user, organizationId }` behind `requireAuth` only — [apps/app-api/src/main.ts](apps/app-api/src/main.ts)
- Code/schema mismatch: `resolveUser.ts` selects `u.organization_id, u.name, u.email` from `app.users` and joins `app.organization_email_domains`; the committed schema has no `organization_id`, `name`, or `email` on `users` and names the domains table `tenant_email_domains`. `api-keys.ts` inserts an `organization_id` column that `app.api_keys` does not have. `ResolvedUser.id` is typed `number` while `users.id` is `TEXT` — [libs/auth-server/src/user/resolveUser.ts](libs/auth-server/src/user/resolveUser.ts), [libs/auth-server/src/user/types.ts](libs/auth-server/src/user/types.ts), [apps/app-api/src/api-keys.ts](apps/app-api/src/api-keys.ts), [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql)
- The seed treats tenant and organization as the same thing: "ensures at least one organization (tenant), user, project, and a pair of API keys" — [db-migrations/seed.sql](db-migrations/seed.sql)
- A repository-wide grep for `role`, `roles`, `permission`, `rbac`, `membership`, `invite`, `invitation`, `scim`, `saml` finds only message roles (`user`/`assistant`/`tool`), the error category `permission`, and Kubernetes RBAC manifests — repository search
- `requireUser` is exported but not applied to any route; `requireAuth` is applied only to `/api/me` and `/api/tenant`; `/api/keys/*` and `/api/threads/*` are registered with no auth guard — [apps/app-api/src/main.ts](apps/app-api/src/main.ts), [apps/app-api/src/routes/index.ts](apps/app-api/src/routes/index.ts)
- Thread routes accept an `x-user-id` header as a fallback identity when no session user is present — [apps/app-api/src/routes/threads-routes.ts](apps/app-api/src/routes/threads-routes.ts)

### Inferences
- The code is mid-migration from a `tenant`-only model to a `tenant -> organization -> user` model (hence `organizationId` on the request and `organization_email_domains` in queries) but the migration that adds organizations is not in the repo. A reader should take the *intended* three-level model from the code and the *implemented* two-level model from the SQL.
- The "verified email domain -> auto-link identity on first login" pattern is a lightweight substitute for invites and JIT provisioning: a tenant admin verifies a domain once and any IdP user with that email domain who already has a `users` row gets linked. It does not create users, so some out-of-band provisioning (seed, SCIM, admin UI) is still required.
- Authorization is "coming later": the error category list already includes `permission` and `requireUser` exists, but nothing distinguishes admins from members.

### Gaps
- No invite flow, no org admin UI, no role table, no SCIM endpoint. The report writer should not imply the reference product has any of these.
- How the `projects` table (`created_by_user_id`, per-tenant) relates to authorization is unspecified; API keys are per project.

## What exactly does the Keycloak/OIDC integration do, and what would change for SAML or SCIM?

### Takeaway
Keycloak is only a development IdP; the product speaks generic OIDC Authorization Code + PKCE through Auth.js (`@auth/express`), mounted at `/auth/*` on the API, with a stateless encrypted-JWT cookie session and a normalized principal `userId = "${issuer}:${subject}"`. Per-tenant IdP config is resolved from a JSON env var in hosted mode or static env in self-hosted mode. Moving to SAML would mean adding a second Auth.js-compatible provider or a different library behind the same `createAuthConfig` seam; SCIM would be a new inbound API writing to `users`/`user_identities`, which the current resolver would then pick up unchanged.

### Cited Findings
- Dev IdP is Keycloak 26.0.2 run with `start-dev --import-realm`, importing a realm export that defines two confidential clients (control-plane and data-plane, each with a single redirect URI `.../auth/callback/enterprise-sso`, `standardFlowEnabled: true`, `directAccessGrantsEnabled: false`) and one seeded user — [docker-compose.yml](docker-compose.yml), [tools/dev/oidc/keycloak/realm-export.json](tools/dev/oidc/keycloak/realm-export.json), [tools/dev/oidc/README.md](tools/dev/oidc/README.md)
- Provider definition (shape):
  ```ts
  { id, name, type: 'oidc', clientId, clientSecret, issuer,
    checks: ['pkce', 'state'],
    authorization: { params: { scope: 'openid profile email' } },
    profile(p) { return { id: `${iss}:${sub}`, name, email, subject: sub, issuer: iss,
                          displayName: p.preferred_username } } }
  ```
  — [libs/auth-server/src/oidc/provider.ts](libs/auth-server/src/oidc/provider.ts)
- Auth config: `session: { strategy: 'jwt' }`, `trustHost` from env, per-plane cookie names `<plane-prefix>.session-token`, `.csrf-token`, `.callback-url` with `httpOnly`, `sameSite: 'lax'`, `secure` = `NODE_ENV === 'production'` — [libs/auth-server/src/oidc/createAuthConfig.ts](libs/auth-server/src/oidc/createAuthConfig.ts), [libs/auth-server/src/oidc/cookies.ts](libs/auth-server/src/oidc/cookies.ts), [apps/app-api/src/main.ts](apps/app-api/src/main.ts)
- JWT and session callbacks copy `sub`/`iss`/`email`/`displayName` from the IdP profile into the token and then into `session.user`; no access/refresh token from the IdP is retained — [libs/auth-server/src/oidc/callbacks.ts](libs/auth-server/src/oidc/callbacks.ts)
- Principal v1: required `subject`, `issuer`; optional `email`, `displayName`; derived `userId = ${issuer}:${subject}` — [libs/auth-shared/src/principal/principalFromSession.ts](libs/auth-shared/src/principal/principalFromSession.ts), [AGENTS.md](AGENTS.md)
- Mount shape: `app.use('/auth/*', (req,res,next) => ExpressAuth(resolveConfig(resolveTenantId(req.headers['x-tenant-id'])))(req,res,next))` — a fresh Auth.js config per request keyed by tenant — [libs/auth-server/src/express/mountAuth.ts](libs/auth-server/src/express/mountAuth.ts)
- Session middleware calls Auth.js `getSession(req, resolveConfig(tenantId))` on every request and sets `res.locals.principal` — [libs/auth-server/src/express/sessionMiddleware.ts](libs/auth-server/src/express/sessionMiddleware.ts)
- Hosted-mode tenant IdP map is `HOSTED_TENANT_OIDC_CONFIG_JSON`, a zod `record(tenantId -> { clientId, clientSecret, issuer, providerId?, providerName? })`; self-hosted uses `AUTH_ISSUER`, `AUTH_CLIENT_ID`, `AUTH_CLIENT_SECRET`; `AUTH_SECRET` must be >= 32 chars — [libs/auth-server/src/env/authEnv.schema.ts](libs/auth-server/src/env/authEnv.schema.ts), [libs/auth-server/src/env/authEnv.load.ts](libs/auth-server/src/env/authEnv.load.ts), [.env.example](.env.example)
- A DB table `app.tenant_oidc_connections (tenant_id UNIQUE, issuer, client_id, client_secret TEXT)` exists but no code reads it; client secrets would be stored in plaintext — [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql)
- Browser client: calls Auth.js REST endpoints `GET /auth/providers`, `GET /auth/session`, `GET /auth/csrf`, and submits hidden HTML forms to `POST /auth/signin/:providerId` and `POST /auth/signout` with the CSRF token; `fetch(..., { credentials: 'include' })` — [libs/auth-client/src/browser/auth-client.ts](libs/auth-client/src/browser/auth-client.ts), [libs/auth-client/src/browser/auth-navigation.ts](libs/auth-client/src/browser/auth-navigation.ts)
- Frontend state: NgRx actions `Session Check Requested/Succeeded/Failed`, `Sign Out Completed`, `Unauthorized Response Observed`; the root route re-dispatches a session check on every `NavigationEnd`; home route redirects to `/login?redirectTo=` when anonymous; login shows a single "Continue with SSO" button for the first provider — [apps/app-frontend/auth-actions/src/index.ts](apps/app-frontend/auth-actions/src/index.ts), [apps/app-frontend/auth/src/routes/root-route.component.ts](apps/app-frontend/auth/src/routes/root-route.component.ts), [apps/app-frontend/auth/src/routes/login-route.component.ts](apps/app-frontend/auth/src/routes/login-route.component.ts), [apps/app-frontend/store-auth/src/session/session.reducer.ts](apps/app-frontend/store-auth/src/session/session.reducer.ts)
- Same-origin is preserved by proxying `/api` and `/auth` to the API in Vite dev, and by routing `/api` and `/auth` to the API service and `/` to the SPA on each ingress host in production — [apps/app-frontend/entrypoint/vite.config.mts](apps/app-frontend/entrypoint/vite.config.mts), [charts/<product>/templates/ingress.yaml](charts/<product>/templates/ingress.yaml)
- Machine clients (agent runners / customer BFFs) do not use OIDC: they present a prefixed API key as the WebSocket `authToken` (sent via the `Sec-WebSocket-Protocol` bearer entry) to the gateway, which validates it against `app.api_keys` — [apps/realtime-gateway/lib/realtime_gateway/sources/runner_auth.ex](apps/realtime-gateway/lib/realtime_gateway/sources/runner_auth.ex), [apps/realtime-gateway/lib/realtime_gateway/endpoint.ex](apps/realtime-gateway/lib/realtime_gateway/endpoint.ex)
- API key format: `<prefix>_<shortToken 8 chars>_<longToken 24 chars>` base58; only `sha256(longToken)` hex is stored (`long_token_hash`), `short_token` is the lookup key, comparison uses `timingSafeEqual` in Node and `Plug.Crypto.secure_compare` in Elixir; keys have `visibility` enum `public|private`, `expires_at NOT NULL`, and a collision-retry loop on unique violation; list responses never include the hash — [apps/app-api/src/api-keys.ts](apps/app-api/src/api-keys.ts), [apps/realtime-gateway/lib/realtime_gateway/sources/runner_auth.ex](apps/realtime-gateway/lib/realtime_gateway/sources/runner_auth.ex), [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql)
- Only `private` keys may open a runner socket; `public` keys are rejected — [apps/realtime-gateway/lib/realtime_gateway/sources/runner_auth.ex](apps/realtime-gateway/lib/realtime_gateway/sources/runner_auth.ex)
- The demo BFF constructs the vendor SDK client with the seeded private API key, a hard-coded tenant id, and sets an `x-user-id` header per request — [demos/simple-agent/bff/src/main.ts](demos/simple-agent/bff/src/main.ts)
- The REST API has no API-key authentication middleware; `api-keys.ts` only manages keys — [apps/app-api/src/main.ts](apps/app-api/src/main.ts)
- Session revocation for sockets: the gateway polls Redis `EXISTS user_expired:{user_id}` every 15 s per channel and pushes `expired` then disconnects — [apps/realtime-gateway/lib/realtime_gateway/client/expiry_checker.ex](apps/realtime-gateway/lib/realtime_gateway/client/expiry_checker.ex)

### Inferences
- "Keycloak integration" is really "any OIDC issuer with discovery"; the chart README lists Keycloak, Okta, Azure AD, and Auth0 as interchangeable. Nothing Keycloak-specific (admin API, realm roles, groups claim) is consumed.
- SAML: Auth.js has no SAML provider, so the realistic path is either (a) front SAML with the customer's IdP federating into an OIDC broker (Keycloak can do this; the product would then be unchanged), or (b) replace `createOidcProvider` with a SAML SP library behind the same `createAuthConfig`/`principalFromSession` seam. Because the principal is reduced to `(issuer, subject, email, displayName)` and sessions are the product's own JWT cookie, the rest of the stack would not change. The repo documents none of this; it is a design inference.
- SCIM: the data model already separates `users` (tenant-owned) from `user_identities` (IdP-owned link). A SCIM 2.0 `/Users` endpoint would create/deactivate `users` rows (soft delete) and could pre-create `user_identities` when the IdP supplies the subject; the first-login domain matcher would keep working for IdPs that do not. There is no SCIM code.
- Per-request `ExpressAuth(resolveConfig(tenantId))` construction means hosted-mode tenant isolation of *auth* is config-driven and in-process; a wrong `x-tenant-id` selects a different IdP but the session cookie is still signed with one shared `AUTH_SECRET`, so a cookie minted under tenant A validates under tenant B. The missing principal-to-tenant binding noted above applies here too.
- Writing IdP client secrets into `tenant_oidc_connections` as plain `TEXT` conflicts with the usual "secrets never in the DB in clear" rule; the env-JSON approach is what actually ships.

### Gaps
- No token refresh, no IdP logout (RP-initiated logout) and no back-channel logout are implemented; session lifetime is whatever Auth.js JWT defaults give.
- E2E tests are tagged `auth:keycloak` and `auth:client-id:*` in CI's dynamic matrix, but the e2e sources were not reviewed in depth.

## How are database schema and migrations done, and how are they run in production?

### Takeaway
Raw SQL migrations managed by graphile-migrate (with a shadow database) in a single `db-migrations/` project; committed migrations are hash-chained files `000001.sql`, `000002.sql`, each split into named sections. Conventions are strong: one schema, identity PKs, `tenant_id` everywhere, `updated_at` triggers, a uniform soft-delete triple (`deleted_at/deleted_by/deleted_reason`) with a CHECK and a trigger that forbids hard `DELETE`, partial indexes, `pg_trgm` search, and PG `NOTIFY` triggers. In production the intended path is a Helm `pre-install,pre-upgrade` hook Job running a dedicated migrations image, but it is disabled by default and the image build is stale.

### Cited Findings
- graphile-migrate config: `connectionString`, `shadowConnectionString`, `rootConnectionString`, `pgSettings.search_path = public`; npm scripts `migrate:migrate`, `migrate:watch`, `migrate:commit` (renames `1-current.sql` back to `001-current.sql`), `migrate:uncommit`, `migrate:reset --erase`, `migrate:status`; `db:seed` pipes `seed.sql` through `psql` — [db-migrations/.gmrc](db-migrations/.gmrc), [package.json](package.json), [scripts/db-seed.sh](scripts/db-seed.sh)
- Committed files carry `--! Previous: sha1:...` / `--! Hash: sha1:...` headers and `--! split: NNN-name.sql` markers — [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql)
- Shared primitives in migration 1 and 2: `CREATE SCHEMA app`; `app.update_updated_at()` trigger function; `CREATE DOMAIN app.non_empty_text AS TEXT CHECK (btrim(VALUE) <> '')`; `CREATE EXTENSION pg_trgm` — [db-migrations/migrations/committed/000001.sql](db-migrations/migrations/committed/000001.sql), [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql)
- Soft-delete pattern (verbatim shape):
  ```sql
  deleted_at TIMESTAMPTZ,
  deleted_by app.non_empty_text,
  deleted_reason app.non_empty_text,
  CHECK (num_nulls(deleted_at, deleted_by, deleted_reason) IN (0, 3))
  ```
  plus `CREATE TRIGGER <t>_enforce_soft_delete BEFORE DELETE ... EXECUTE PROCEDURE app.enforce_soft_delete()` which `RAISE EXCEPTION`s, and `app.soft_delete(deleting_table regclass, deleting_id TEXT, user, reason)` which performs the UPDATE via `EXECUTE format(...)` and raises if zero rows matched — [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql)
- Application code calls the function inside a CTE so tenant scoping and deletion are one statement: `WITH target AS (SELECT id FROM app.threads WHERE thread_id=$1 AND tenant_id=$2 AND deleted_at IS NULL LIMIT 1) SELECT id, app.soft_delete('app.threads'::regclass, id::text, $3, $4) FROM target` — [libs/threads/src/threads.ts](libs/threads/src/threads.ts)
- Table naming: snake_case plural tables, `<table>_<col>_idx` indexes, `<table>_update_updated_at` / `<table>_enforce_soft_delete` triggers, `INTEGER GENERATED ALWAYS AS IDENTITY` or `BIGINT ... IDENTITY` PKs (TEXT uuid for tenants and, in the current migration, threads) — [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql), [db-migrations/migrations/current/004-threads.sql](db-migrations/migrations/current/004-threads.sql)
- Event log tables: `agent_runs (tenant_id, thread_id REFERENCES threads(thread_id), run_id TEXT UNIQUE, parent_run_id self-FK)`, `run_events (BIGINT id, tenant_id, run_id -> agent_runs.id, raw JSONB, event_id TEXT NOT NULL, event_seq BIGINT)`, `run_state (thread_id UNIQUE, running_state enum, current_run_id, server_id)` — [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql), [db-migrations/migrations/current/005-run-event-ordering.sql](db-migrations/migrations/current/005-run-event-ordering.sql)
- Keyset pagination index `(created_at DESC, id DESC) WHERE deleted_at IS NULL` and `gin (name gin_trgm_ops)` for `%` similarity search — [db-migrations/migrations/current/004-threads.sql](db-migrations/migrations/current/004-threads.sql), [libs/threads/src/threads.ts](libs/threads/src/threads.ts)
- `NOTIFY` trigger: `AFTER INSERT OR UPDATE ON app.threads` builds a JSONB payload with semantic `operation` (`created|deleted|archived|unarchived|renamed|updated`), `threadId`, `userId`, `tenantId`, and either a full `thread` snapshot or a `deleted` tombstone, then `pg_notify('thread_metadata', payload::text)` — [db-migrations/migrations/current/006-thread-metadata-notify.sql](db-migrations/migrations/current/006-thread-metadata-notify.sql)
- Idempotent style throughout: `CREATE TABLE IF NOT EXISTS`, `CREATE OR REPLACE TRIGGER`, `DO $$ IF NOT EXISTS (SELECT 1 FROM pg_type ...)` for enums/domains, `ADD COLUMN IF NOT EXISTS` followed by backfill `UPDATE` then `SET NOT NULL` — [db-migrations/migrations/current/004-threads.sql](db-migrations/migrations/current/004-threads.sql), [db-migrations/migrations/current/005-run-event-ordering.sql](db-migrations/migrations/current/005-run-event-ordering.sql)
- Seed is a single idempotent `DO $$` block using `ON CONFLICT DO NOTHING` / `WHERE NOT EXISTS`, printing the dev API keys via `RAISE NOTICE` — [db-migrations/seed.sql](db-migrations/seed.sql)
- Local Postgres init creates the app DB and a shadow DB from `infra/postgres/init/01-create-databases.sql`, mounted into `/docker-entrypoint-initdb.d` — [infra/postgres/init/01-create-databases.sql](infra/postgres/init/01-create-databases.sql), [docker-compose.yml](docker-compose.yml)
- Production path: Helm Job named `<release>-migrations-<revision>` with `helm.sh/hook: pre-install,pre-upgrade`, `hook-weight: -5`, `hook-delete-policy: before-hook-creation,hook-succeeded`, `activeDeadlineSeconds: 300`, `backoffLimit: 3`, `restartPolicy: Never`, non-root + read-only FS + drop ALL caps, `DATABASE_URL` from the DB secret — [charts/<product>/templates/migrations/job.yaml](charts/<product>/templates/migrations/job.yaml)
- The job is opt-in: `migrations.enabled: false` with its own image repository; "Requires a pre-built migrations image containing the migration files" — [charts/<product>/values.yaml](charts/<product>/values.yaml)
- The migrations image is stale relative to the repo: it installs `graphile-migrate@2`, copies `control-plane-migrations/` and `data-plane-migrations/` (directories that do not exist) and runs two migrate passes against `CONTROL_PLANE_DATABASE_URL` / `DATA_PLANE_DATABASE_URL` — [infra/docker/migrations.Dockerfile](infra/docker/migrations.Dockerfile), [infra/docker/run-migrations.sh](infra/docker/run-migrations.sh)
- Working-tree drift: `migrations/current/` contains `004-threads.sql`, `005-run-event-ordering.sql`, `006-thread-metadata-notify.sql` which supersede sections already inside committed `000002.sql` (e.g. threads `id` changes from identity INTEGER to TEXT uuid, and the notify function is rewritten) — [db-migrations/migrations/current/004-threads.sql](db-migrations/migrations/current/004-threads.sql), [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql)
- Database name drift: compose and `.env.example` use `<product>_app` (plus a `<product>_app_shadow` DB); chart defaults and `scripts/requirements.md` use a different, shorter single database name; the legacy chart composes `DATABASE_URL` from an RDS-managed secret — [.env.example](.env.example), [charts/<product>/values.yaml](charts/<product>/values.yaml), [scripts/requirements.md](scripts/requirements.md), [infra/helm/app-api/templates/externalsecret.yaml](infra/helm/app-api/templates/externalsecret.yaml)
- The API does not run migrations at start; `main.ts` only opens a `pg.Pool` — [apps/app-api/src/main.ts](apps/app-api/src/main.ts)

### Inferences
- The "migration as Helm hook Job" choice is the standard answer for on-prem Helm installs because it works without an operator and runs with the customer's own DB credentials; the "image contains the SQL" requirement is what makes it awkward (a second image to build and version-align). An init container on the API Deployment would avoid the extra image at the cost of running on every pod start.
- graphile-migrate's "one forward-only SQL file, no down migrations, shadow DB for validation" fits a team writing hand-tuned SQL with triggers and domains; an ORM-driven migration tool would struggle with `soft_delete(regclass)` and `pg_notify` triggers.
- Everything in the data layer is plain PostgreSQL (no extension beyond `pg_trgm`); this is the most directly reusable part for a Swift/Postgres service.

### Gaps
- No rollback story, no migration lock/advisory-lock behaviour documented for multi-replica upgrades (graphile-migrate handles its own `graphile_migrate.migrations` table but the repo does not discuss concurrent runs).
- No evidence the migrations Job has ever been exercised; the stale Dockerfile suggests not.

## What does the API layer look like (style, versioning, error shape)?

### Takeaway
Plain Express REST under `/api/*` with zod validation at every boundary and a single typed error registry that yields one response shape `{ error: { code, message, category, retryable }, requestId, traceId }`. There is no URL or header versioning, no OpenAPI, no GraphQL or tRPC.

### Cited Findings
- Error registry entries are `{ code, httpStatus, message, category, retryable, docsPath }` with `category` in `validation|auth|permission|not_found|conflict|rate_limit|internal|dependency`, declared `as const satisfies Record<string, ErrorRegistryEntry>` so `ErrorCode` is a union type — [apps/app-api/src/errors/registry.ts](apps/app-api/src/errors/registry.ts)
- Terminal error handler maps any thrown value to a registry entry (`toAppError`: known `code` or `INTERNAL_SERVER_ERROR`), logs at a level chosen by category (`not_found` info, `validation|conflict` warn, else error), and responds with the uniform shape — [apps/app-api/src/main.ts](apps/app-api/src/main.ts)
- Route handlers never throw typed exceptions; they `next(createAppError('CODE'))`, where `createAppError` just returns the registry entry object — [apps/app-api/src/routes/threads-routes.ts](apps/app-api/src/routes/threads-routes.ts), [apps/app-api/src/routes/api-keys-routes.ts](apps/app-api/src/routes/api-keys-routes.ts)
- Every error code is mirrored in a Markdown doc with the same fields — [docs/errors/app-api.md](docs/errors/app-api.md)
- Request correlation: `pino-http` with `genReqId` honouring inbound `x-request-id`, `traceId` parsed from the W3C `traceparent` header (second segment) or random; both copied onto `req` — [apps/app-api/src/main.ts](apps/app-api/src/main.ts)
- `app.set('trust proxy', true)` and `AUTH_TRUST_HOST` are both on, i.e. the API expects to sit behind an ingress — [apps/app-api/src/main.ts](apps/app-api/src/main.ts)
- Pagination: threads use fixed `PAGE_SIZE = 50` keyset pagination with an opaque base64url cursor of `created_at|id` and `(created_at, id) < ($a, $b)`; API keys use offset pagination with `page_size` restricted to 25 or 100 and a parallel `COUNT(*)` — [libs/threads/src/types.ts](libs/threads/src/types.ts), [libs/threads/src/threads.ts](libs/threads/src/threads.ts), [apps/app-api/src/api-keys.ts](apps/app-api/src/api-keys.ts)
- Input schemas accept both snake_case and camelCase aliases and normalise via `.transform()` — [libs/threads/src/schemas.ts](libs/threads/src/schemas.ts)
- Mutations that soft-delete require a `reason` in the body (`z.string().trim().min(1).max(1000)`) which is persisted in `deleted_reason` — [apps/app-api/src/routes/threads-routes.ts](apps/app-api/src/routes/threads-routes.ts)
- Health: `GET /api/health` returns `{ status: 'ok', service: 'app-api' }` and is used for both liveness and readiness probes — [apps/app-api/src/main.ts](apps/app-api/src/main.ts), [charts/<product>/templates/app-api/deployment.yaml](charts/<product>/templates/app-api/deployment.yaml)
- A legacy chart's Argo Rollouts analysis also hits `/api/health` on the preview service before promotion — [infra/helm/app-api/templates/rollout.yaml](infra/helm/app-api/templates/rollout.yaml)
- Data-shape convention: DB rows are snake_case `ThreadRow`, API resources are camelCase `Thread`, converted by a single `toThread()`; `SELECT_COLUMNS` is a constant so no `SELECT *` — [libs/threads/src/types.ts](libs/threads/src/types.ts), [libs/threads/src/threads.ts](libs/threads/src/threads.ts)

### Inferences
- The registry-plus-doc pattern gives stable machine-readable codes without an exception hierarchy; it is language-agnostic and maps cleanly onto a Swift `enum` with associated HTTP status and category.
- Absence of versioning is acceptable at 0.1.0 but a hub that ships to on-prem customers will need at least an additive-only policy or `/api/v1`.

### Gaps
- No rate limiting, no idempotency keys, no OpenAPI document, no request body size limits beyond Express defaults.

## How is the Helm chart structured (subcharts, Postgres, secrets, ingress, probes)?

### Takeaway
One umbrella-free chart with per-component template folders (`app-api/`, `app-frontend/`, `realtime-gateway/`, `migrations/`, `external-secrets/`), no subcharts and no bundled PostgreSQL or Redis: the customer must supply hosts and either pre-created Kubernetes Secrets (`existingSecret`) or External Secrets Operator mappings. Ingress is one resource with two or three hosts (control plane, data plane, realtime), each routing `/api` and `/auth` to the API and `/` to the SPA. Pods run non-root with read-only root FS, HTTP probes on a shared `healthCheck` block, optional HPA, PDB, pod anti-affinity, and a NetworkPolicy.

- "External Postgres only" is a deliberate on-prem stance: the chart neither runs nor backs up a database, so customer DBAs keep ownership. The trade-off is that first install requires the DB and database name to pre-exist (the chart says so) and migrations are a separate opt-in.
- The `existingSecret` + `secretKeys` pair per dependency is the key reusable values idiom: it lets the same chart work with manually created Secrets, ESO, Vault, or sealed-secrets without template changes.
- Keeping live values outside git because they contain hostnames/account ids is a pragmatic answer to "we want to open-source the chart but not our environment"; it does, however, break the ArgoCD examples, which the vendor admits.

### Gaps
- No PodSecurityAdmission labels, no PriorityClass, no topology spread beyond hostname anti-affinity, no resource quotas; no backup/restore guidance.
- No chart tests (`templates/tests/`) beyond lint/template/kubeconform.

## What resembles client sync, realtime, or offline support?

### Takeaway
There is no offline-first or CRDT-style sync. There is a well-thought-out *reconnect/catch-up* design: PostgreSQL is the durable, tenant-scoped event log; Redis holds a 4-hour replay list per thread plus short-lived join tokens and a per-thread run lock; the gateway replays from Redis or falls back to Postgres by cursor, buffers live events during replay to avoid gaps, and PG `LISTEN/NOTIFY` drives a per-user metadata channel so clients fetch lists via REST and apply incremental WebSocket updates.

### Cited Findings
- Contract doc: "PostgreSQL (`agent_runs` + `run_events`) is the source of truth for durable thread history"; "Redis `thread_events:${threadId}` is a replay cache for websocket reconnects, not the authoritative REST read model"; "`thread_metadata` is a live-only ownership-scoped feed. Clients should fetch their initial thread list via REST and apply incremental updates from websocket events." — [docs/thread-realtime-contract.md](docs/thread-realtime-contract.md)
- Keys: lock `thread:${threadId}:lock` (value = active run id, `SET NX`, released by the gateway on `RUN_FINISHED`/`RUN_ERROR`), join code `thread:${threadId}:join-code` (300 s TTL), client join token `join_token:${token}` (Redis hash `{user_id, tenant_id}`, 300 s TTL), replay list `thread_events:${threadId}` (`RPUSH` + `EXPIRE 14400`), stop signal `stop:${threadId}` (300 s), revocation flag `user_expired:${userId}` — [apps/app-api/src/routes/threads-routes.ts](apps/app-api/src/routes/threads-routes.ts), [apps/realtime-gateway/lib/realtime_gateway/consumers/redis_writer.ex](apps/realtime-gateway/lib/realtime_gateway/consumers/redis_writer.ex), [apps/realtime-gateway/lib/realtime_gateway/client/thread_channel.ex](apps/realtime-gateway/lib/realtime_gateway/client/thread_channel.ex), [apps/realtime-gateway/lib/realtime_gateway/client/expiry_checker.ex](apps/realtime-gateway/lib/realtime_gateway/client/expiry_checker.ex)
- Reconnect endpoint `POST /api/threads/:threadId/connect { lastSeenEventId? }`: if no active run and the cursor equals the latest durable event -> `204`; if no active run otherwise -> `{ mode: 'bootstrap', latestEventId, events: [MESSAGES_SNAPSHOT] }`; if a run is active -> `{ mode: 'live', joinToken, joinFromEventId, events: [] | [MESSAGES_SNAPSHOT] }`, choosing to reuse the client cursor only when it is present in the Redis window at or beyond the durable boundary — [apps/app-api/src/routes/threads-routes.ts](apps/app-api/src/routes/threads-routes.ts)
- Event identity and ordering: producers stamp `metadata.<prefix>_event_id` and optional `metadata.<prefix>_event_seq`; the gateway adds `metadata.<prefix>_ingested` (UUIDv7); Postgres orders by `ar.created_at, COALESCE(re.event_seq, re.id), re.id` and deduplicates on `(tenant_id, event_id)` — [apps/realtime-gateway/lib/realtime_gateway/events/enricher.ex](apps/realtime-gateway/lib/realtime_gateway/events/enricher.ex), [apps/realtime-gateway/lib/realtime_gateway/consumers/postgres_writer.ex](apps/realtime-gateway/lib/realtime_gateway/consumers/postgres_writer.ex), [libs/threads/src/threads.ts](libs/threads/src/threads.ts)
- Gateway replay: on join, capture a high-watermark cursor (Redis tail, else Postgres latest), send the window `(last_seen, high_watermark]` from Redis if Redis contains both ends, else from Postgres via a `row_number()` window bounded by the two event ids; meanwhile buffer live broadcasts and flush only those after the watermark once replay completes; replay lookups run in a `Task` with a 1 s timeout — [apps/realtime-gateway/lib/realtime_gateway/client/replay.ex](apps/realtime-gateway/lib/realtime_gateway/client/replay.ex), [apps/realtime-gateway/lib/realtime_gateway/client/thread_channel.ex](apps/realtime-gateway/lib/realtime_gateway/client/thread_channel.ex)
- Transcript compaction from the event log is implemented twice, once in TypeScript for REST and once in Elixir for snapshots, with identical semantics (`MESSAGES_SNAPSHOT` resets, text deltas concatenate, tool calls attach to parent messages) — [libs/threads/src/threads.ts](libs/threads/src/threads.ts), [apps/realtime-gateway/lib/realtime_gateway/client/replay.ex](apps/realtime-gateway/lib/realtime_gateway/client/replay.ex)
- Fan-out pipeline: runner socket -> `Phoenix.PubSub` topic `thread_events` -> independent consumers (`PostgresWriter`, `RedisWriter`, `ClientBroadcaster`, plus blob and search writers) each with a dead-letter queue on failure; `PostgresWriter` auto-creates the `agent_runs` row with `ON CONFLICT (run_id) DO NOTHING` and caches run PKs — [apps/realtime-gateway/lib/realtime_gateway/consumers/postgres_writer.ex](apps/realtime-gateway/lib/realtime_gateway/consumers/postgres_writer.ex), [apps/realtime-gateway/lib/realtime_gateway/application.ex](apps/realtime-gateway/lib/realtime_gateway/application.ex)
- Metadata feed: PG trigger -> `pg_notify('thread_metadata', ...)` -> `Postgrex.Notifications` listener -> PubSub `user_meta_events` -> `Endpoint.broadcast("user_meta:#{user_id}", "thread_metadata", data)`; the `user_meta:*` channel join is rejected unless the topic user id equals the socket's authenticated user id — [apps/realtime-gateway/lib/realtime_gateway/sources/postgres_listener.ex](apps/realtime-gateway/lib/realtime_gateway/sources/postgres_listener.ex), [apps/realtime-gateway/lib/realtime_gateway/consumers/metadata_broadcaster.ex](apps/realtime-gateway/lib/realtime_gateway/consumers/metadata_broadcaster.ex), [apps/realtime-gateway/lib/realtime_gateway/client/user_meta_channel.ex](apps/realtime-gateway/lib/realtime_gateway/client/user_meta_channel.ex)
- Runner disconnect without a terminal event synthesises a `RUN_ERROR` with code `RUNNER_CONNECTION_DROPPED`; a `stop_run` from a client is written to Redis and relayed to the runner socket, and the channel suppresses further non-terminal events for that run — [apps/realtime-gateway/lib/realtime_gateway/sources/runner_channel.ex](apps/realtime-gateway/lib/realtime_gateway/sources/runner_channel.ex), [apps/realtime-gateway/lib/realtime_gateway/client/thread_channel.ex](apps/realtime-gateway/lib/realtime_gateway/client/thread_channel.ex)
- Browser never talks to the gateway without first obtaining a short-lived join token from the cookie-authenticated REST API — [apps/app-api/src/routes/threads-routes.ts](apps/app-api/src/routes/threads-routes.ts), [apps/realtime-gateway/lib/realtime_gateway/client/socket.ex](apps/realtime-gateway/lib/realtime_gateway/client/socket.ex)

### Inferences
- The split "REST for authoritative reads + opaque cursor; WebSocket for live tail; short-lived token minted by the REST tier to bridge the two auth domains" is a reusable shape for any hub with a separate realtime process. It avoids sharing session cookies or JWT secrets with the realtime service: the only shared state is Redis.
- `(tenant_id, event_id)` uniqueness plus `ON CONFLICT DO NOTHING` makes ingestion idempotent, which is what makes replay-after-reconnect safe.
- Nothing here helps a client that was offline for longer than the Redis TTL beyond "re-bootstrap from the durable snapshot", which is the correct minimal answer for a hub whose clients are mostly online.

### Gaps
- No client-side persistence or conflict handling exists; the SPA holds state only in NgRx memory.
- The `run_state` table (`running_state`, `current_run_id`, `server_id`) is defined but not written by any code reviewed; the Redis lock is the live mechanism.

## What is well-designed and what is fragile?

### Takeaway
Well-designed: the data-layer conventions (uniform soft-delete with DB-enforced invariants, tenant column + tenant-scoped unique indexes, partial indexes, keyset cursors, NOTIFY triggers), the typed error registry with a single response shape, the clean separation of `auth-server` / `auth-client` / `auth-shared` behind a tiny principal type, the reconnect protocol with durable log + replay cache + buffered live tail, and the Helm chart's `existingSecret`/ESO dual path with non-root hardened pods and CI schema validation. Fragile: authorization is effectively absent (tenant and user ids are caller-supplied on key and thread routes, no `requireAuth` on them, a trusted `x-user-id` header, a hard-coded tenant, an unchecked tenant on WebSocket thread joins), the auth library queries columns and tables that the committed schema does not have, the migrations image and several docs describe a different repository than the one checked out, and live deployment config lives outside git so the GitOps examples cannot be applied as-is.

### Cited Findings
- Well-designed evidence is cited in the sections above; the clearest single artefacts are the soft-delete block and `soft_delete()` function — [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql); the error registry — [apps/app-api/src/errors/registry.ts](apps/app-api/src/errors/registry.ts); the replay module — [apps/realtime-gateway/lib/realtime_gateway/client/replay.ex](apps/realtime-gateway/lib/realtime_gateway/client/replay.ex); the chart helpers — [charts/<product>/templates/_helpers.tpl](charts/<product>/templates/_helpers.tpl)
- Fragile evidence: unguarded routes and hard-coded tenant — [apps/app-api/src/main.ts](apps/app-api/src/main.ts), [apps/app-api/src/routes/threads-routes.ts](apps/app-api/src/routes/threads-routes.ts); caller-supplied tenant/org/user — [apps/app-api/src/routes/api-keys-routes.ts](apps/app-api/src/routes/api-keys-routes.ts); schema/code mismatch — [libs/auth-server/src/user/resolveUser.ts](libs/auth-server/src/user/resolveUser.ts) vs [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql); stale migrations image — [infra/docker/migrations.Dockerfile](infra/docker/migrations.Dockerfile); unchecked WebSocket tenant — [apps/realtime-gateway/lib/realtime_gateway/client/thread_channel.ex](apps/realtime-gateway/lib/realtime_gateway/client/thread_channel.ex); docs drift — [AGENTS.md](AGENTS.md), [README.md](README.md); GitOps examples are not live — [docs/deployment-from-secrets-manager.md](docs/deployment-from-secrets-manager.md)
- Dependencies on an unreleased preview build of the vendor's own packages at a pinned commit — [package.json](package.json)
- Postgres SSL is configured with `verify: :verify_none` in the gateway when `sslmode=require` is present — [apps/realtime-gateway/config/runtime.exs](apps/realtime-gateway/config/runtime.exs), [apps/realtime-gateway/lib/realtime_gateway/sources/postgres_listener.ex](apps/realtime-gateway/lib/realtime_gateway/sources/postgres_listener.ex)

### Inferences
- The repository is strongest where a single engineer could enforce a convention in one place (SQL migrations, chart helpers, error registry) and weakest where a convention has to be applied at every call site (tenant scoping and auth guards per route). A hub service should push tenant binding into one mandatory layer (middleware that derives tenant from the principal, or RLS with `SET LOCAL app.tenant_id`) rather than relying on each handler.
- Documentation that describes the intended architecture (two planes, published packages, org model) rather than the implemented one is itself a risk for an on-prem product, because customers install from the docs.

### Gaps
- No performance or load data; no security review artefacts; no test coverage numbers were collected.

## What is reusable as a pattern for a Swift/Postgres hub, and what is specific to this web stack?

### Takeaway
Nearly all of the database and deployment design transfers directly to a Swift service talking to PostgreSQL; the OIDC flow transfers as a design (authorization code + PKCE, principal = issuer:subject, identity-link table, domain-based first login) but needs a Swift OIDC client instead of Auth.js; the realtime gateway's *protocol* transfers while its Phoenix/BEAM implementation does not.

### Cited Findings
- Reusable SQL primitives: schema-level `update_updated_at()` trigger, `non_empty_text` domain, soft-delete triple with `num_nulls` CHECK and `BEFORE DELETE` trigger, `soft_delete(regclass, id, user, reason)` function, tenant-scoped partial unique indexes, `(created_at DESC, id DESC)` keyset index, `pg_trgm` GIN for search, `pg_notify` trigger with semantic operation payloads — [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql), [db-migrations/migrations/current/004-threads.sql](db-migrations/migrations/current/004-threads.sql), [db-migrations/migrations/current/006-thread-metadata-notify.sql](db-migrations/migrations/current/006-thread-metadata-notify.sql)
- Reusable identity model: `tenants`, `users(tenant_id)`, `user_identities(issuer, subject) UNIQUE`, `tenant_email_domains(domain UNIQUE, verified)`, `api_keys(short_token UNIQUE, long_token_hash UNIQUE, visibility, expires_at, project_id)` — [db-migrations/migrations/committed/000002.sql](db-migrations/migrations/committed/000002.sql)
- Reusable API-key scheme: prefix + short lookup token + long secret, store only `sha256(long)`, constant-time compare, collision retry, never return the hash — [apps/app-api/src/api-keys.ts](apps/app-api/src/api-keys.ts), [apps/realtime-gateway/lib/realtime_gateway/sources/runner_auth.ex](apps/realtime-gateway/lib/realtime_gateway/sources/runner_auth.ex)
- Reusable request conventions: `x-request-id` passthrough, `traceparent` parsing, tenant header only in hosted mode, uniform error envelope with stable codes and `retryable`, `reason` required on destructive calls, opaque base64url cursors — [apps/app-api/src/main.ts](apps/app-api/src/main.ts), [apps/app-api/src/errors/registry.ts](apps/app-api/src/errors/registry.ts), [libs/threads/src/types.ts](libs/threads/src/types.ts)
- Reusable deployment conventions: external-Postgres-only chart; `database.existingSecret` + `secretKeys.url`; one ConfigMap for non-secrets with a checksum annotation; ESO mapping table in values; `required`/`fail` guards; hardened pod security context; HTTP probes on a configurable `healthCheck` block; HPA/PDB/anti-affinity toggles per component; opt-in NetworkPolicy; opt-in migrations hook Job; `values-onprem-example.yaml` and `values-<cloud>-example.yaml` overlays; `ci/test-values.yaml` + `helm lint` + `kubeconform` in CI; chart published to an OCI registry on tags; a preflight script that checks cluster, secrets, DB version, Redis, and object storage — [charts/<product>/values.yaml](charts/<product>/values.yaml), [charts/<product>/templates/_helpers.tpl](charts/<product>/templates/_helpers.tpl), [charts/<product>/templates/migrations/job.yaml](charts/<product>/templates/migrations/job.yaml), [.github/workflows/helm-lint.yml](.github/workflows/helm-lint.yml), [scripts/preflight.sh](scripts/preflight.sh)
- Reusable realtime protocol: REST-minted short-lived join token stored in Redis as `{user_id, tenant_id}`; per-thread lock with `SET NX`; replay list with TTL; `connect` negotiation returning `204 | bootstrap | live` with a cursor; event dedupe on `(tenant_id, event_id)`; user-scoped metadata channel fed by PG NOTIFY — [apps/app-api/src/routes/threads-routes.ts](apps/app-api/src/routes/threads-routes.ts), [docs/thread-realtime-contract.md](docs/thread-realtime-contract.md)
- Web-stack-specific: Auth.js (`@auth/express`) providing `/auth/providers|session|csrf|signin|signout` and the JWT cookie session; NgRx action hygiene and store-per-feature libraries; Nx tag-based module boundaries; Vite dev proxy; esbuild single-file ESM bundle for the API image; Phoenix Channels / `Phoenix.PubSub` / `Postgrex.Notifications` / BEAM clustering (headless Service, epmd and distribution ports, release cookie Secret) — [libs/auth-server/src/express/mountAuth.ts](libs/auth-server/src/express/mountAuth.ts), [AGENTS.md](AGENTS.md), [apps/app-frontend/entrypoint/vite.config.mts](apps/app-frontend/entrypoint/vite.config.mts), [apps/app-api/Dockerfile](apps/app-api/Dockerfile), [charts/<product>/templates/realtime-gateway/deployment.yaml](charts/<product>/templates/realtime-gateway/deployment.yaml)

### Inferences
- For a Swift hub, the equivalent of `libs/auth-server` is a small module that (1) performs OIDC discovery + authorization code + PKCE, (2) issues its own signed session (cookie for browsers, bearer for native clients), (3) reduces the IdP profile to `(issuer, subject, email, displayName)`, and (4) resolves `user_identities` -> `users` with the domain-matching fallback. Keycloak remains only a compose-based test IdP with a committed realm export.
- The strongest improvement over the reference for a new hub is to bind tenant to principal centrally: look up the user's `tenant_id` from `users`, reject or ignore any client-supplied tenant that disagrees, and consider PostgreSQL RLS with a per-transaction `SET LOCAL` as a second line of defence, which the reference lacks.
- A single-process Swift hub can replace the Phoenix gateway with the same Redis keys and the same `connect` negotiation; PG `LISTEN/NOTIFY` is available from any Postgres client, so the metadata feed design survives the language change.
- The decision to make migrations a Helm hook Job with a dedicated image is the piece most worth re-deciding: with a compiled Swift binary, shipping the SQL files inside the API image and exposing a `migrate` subcommand (run by the hook Job or an init container) avoids a second image.

### Gaps
- The repo offers no guidance on multi-region, backup, or upgrade compatibility windows between chart versions and schema versions; a hub team must design those independently.
