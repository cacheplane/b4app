# Multi-tenant data isolation in PostgreSQL: shared schema + RLS vs schema-per-tenant vs database-per-tenant (as of late 2026)

Scope note: tenants are organizations containing users; rows are small (conversation index and transcripts, thousands of rows per user); the same product ships as a single bundled Docker/Helm deployment on-prem (one org) and as a shared public cloud (many orgs). Research date: 2026-10-31. Source ages are flagged inline; several canonical pieces (AWS blog 2020, Microsoft Azure SQL patterns 2017–2018) are old but still what the vendors link to today.

## Key question 1: How do mature products and the literature choose between the three models, and what operational costs follow each?

### Takeaway
The vendor literature converges: a pooled shared schema with a `tenant_id` column plus RLS is the default for many small tenants and the cheapest to operate; schema-per-tenant is a middle ground whose costs (migrations × N, catalog growth, per-schema `pg_dump` overhead, autovacuum pressure) climb with tenant count; database-per-tenant gives the strongest isolation, the simplest per-tenant restore/delete, and the largest fleet-management and connection cost. The 2025–2026 practitioner material adds that teams most often migrate *from* RLS *to* schema/database-per-tenant for enterprise contracts, and that the hyperscale answer is a hybrid ("pods of tenants": shared schema inside a pod, many pods).

### Cited Findings
- AWS Prescriptive Guidance names three PostgreSQL partitioning models (silo, bridge, pool), says RDS and Aurora support all three, and that "Row-level security (RLS) is required to maintain tenant data isolation in a pool model with PostgreSQL. This is because there is no logical separation between infrastructure, PostgreSQL databases, or schemas on a per-tenant basis in a pool model." — [AWS Prescriptive Guidance: Best practices](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/best-practices.html)
- AWS on pool-model drawbacks: "The noisy neighbor phenomenon cannot be completely eliminated in a pool model"; some customers "might not find the logical separation provided by RLS to be sufficient"; and "PostgreSQL by default isn't aware of which tenant is consuming resources," so per-tenant metering needs application instrumentation. — [AWS Prescriptive Guidance: Pool model](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/pool.html)
- AWS's older tenant-isolation whitepaper (now marked "historical reference") notes that with Aurora PostgreSQL "you cannot use IAM to scope access to data at the row level. Instead, you'll need to use the row level security (RLS) feature of PostgreSQL to isolate your tenant data." — [AWS SaaS Tenant Isolation Strategies: pooled storage](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/pooled-storage-isolation-strategies.html)
- Citus (Microsoft) makes the shared-tables case: "each tenant's data can be stored together in a single database instance," which uses hardware efficiently and lets application improvements reach every client at once. Citus requires `tenant_id` in every primary and foreign key, and offers `isolate_tenant_to_new_shard` plus `citus_move_shard_placement` to move a noisy large tenant to a dedicated node ("it is worthwhile to move large tenants to dedicated nodes"). — [Citus docs: Multi-tenant Applications](https://docs.citusdata.com/en/stable/use_cases/multi_tenant.html)
- Citus distribution-column guidance: "A distribution column that we've found to work well in practice is tenant ID in multi-tenant applications"; "Do not choose a timestamp as the distribution column"; test each query by asking "would it work if it had additional WHERE clauses to restrict all tables involved to rows with the same tenant id?" — [Citus docs: Choosing Distribution Column](https://docs.citusdata.com/en/latest/sharding/colocation.html)
- Microsoft's Azure SQL Database SaaS tenancy patterns (2017–2018 era, SQL Server not PostgreSQL, but the taxonomy is widely reused) define standalone single-tenant, database-per-tenant, and sharded multi-tenant; note that a 1,000-tenant database with 20 indexes becomes 20,000 indexes if split into 1,000 databases; and state the tenancy model "generally doesn't change application behavior, but it does affect restore, disaster recovery, and customization, and switching models later can be costly." The choice can be made per tenant at provisioning time. — [Microsoft Learn: Multitenant SaaS database tenancy patterns](https://learn.microsoft.com/en-us/azure/sql-database/saas-tenancy-app-design-patterns); [Azure blog](https://azure.microsoft.com/en-us/blog/new-multi-tenant-patterns-for-building-saas-applications-on-sql-database/)
- Neon's database-per-tenant pitch (2025–2026 marketing page): "Every customer runs on a separate Neon project"; projects are created "programmatically, in milliseconds" via API/Terraform; idle tenants scale to zero ("Neon pauses compute and you pay nothing until they return"); and you "can restore just one customer's database (project) to any point in time—within seconds." The page does not discuss RLS/shared-schema nor how to run schema migrations across a fleet of projects. Only one named customer (Opusflow). — [Neon: Database per tenant](https://neon.com/use-cases/database-per-tenant)
- PGConf.PL 2026 talk (HexaCluster, scheduled 2026-11-24; abstract only, talk not yet given): schema-per-tenant problems grow "as tenant count climbs" in the catalog, planning time, `pg_dump`, and autovacuum pressure; database-per-tenant has the strongest isolation but costs in connections, backups, and operational sprawl; RLS has ergonomics and planner surprises; large platforms converge on a hybrid "pods of tenants" pattern. No numeric thresholds given. — [PGConf.PL 2026 session](https://www.postgresql.eu/events/pgconfpl2026/schedule/session/8462-multi-tenant-postgres-where-each-design-hits-a-wall/)
- Evidence that per-schema `pg_dump` cost tracks the whole catalog, not the schema dumped: a 2026 bug report (BUG #19688, PostgreSQL 18.6) describes `pg_dump --schema` calling `pg_get_sequence_data()` "for every sequence in the database, even when pg_dump is restricted to a single schema," with ~142,000 sequences across hundreds of tenant schemas and daily per-schema backups; the reporter's patch is unreviewed. Older threads: >20,000 schemas, dumping one near-empty schema took 12 minutes (PG 9.0, 2012); 2,600 schemas, ~30–40 s overhead per schema dump regardless of data size; 557 schemas, a `pg_depend` query dominated. — [BUG #19688](https://www.postgresql.org/message-id/19688-e90025dc375a22a3@postgresql.org); [pgsql-performance 2012](https://postgrespro.com/list/id/1337843209018-5709766.post@n5.nabble.com); [pgsql-hackers 2012](https://www.postgresql.org/message-id/1352216421913-5730877.post%40n5.nabble.com); [pgsql-general](https://www.postgresql.org/message-id/CAE7ByhiroJbXUzAJMFE0mVhOOcyYLGONAj83dkrXFkG5-H-rZg%40mail.gmail.com)
- Practitioner anecdotes (2026, single pseudonymous author, treat as weak evidence): one post reports a team's bill climbing after ~1,200 schema-based tenants because "Connection pooling, vacuuming, and backups all started duplicating work per schema," after which they moved to RLS; a sibling post by the same author says schema-per-tenant worked well. Rules of thumb quoted: RLS for many small tenants; schema-per-tenant for dozens-to-hundreds of mid-size tenants needing per-tenant restore; database-per-tenant for a handful of large, compliance-separated customers; "You must run every migration against every tenant. Sequentially is safe but slow. In parallel, you risk partial failures"; "Track migration state per tenant. A global schema_migrations table won't cut it when tenants can be at different versions." — [kubaik: schema per tenant cost us 170% more than RLS](https://kubaik.github.io/schema-per-tenant-cost-us-170-more-than-rls/); [kubaik: 2026 trade-offs](https://kubaik.github.io/schema-per-tenant-the-2026-trade-offs-nobody-talks/); [Bytebase: Multi-Tenant Database Architecture Patterns](https://www.bytebase.com/blog/multi-tenant-database-architecture-patterns-explained.md)
- Database-per-tenant trade-off summary from a practitioner guide: "strongest isolation (no query can cross it), independent extensions and collations. Cost: connection-pool fragmentation, migrations × tenants, cross-tenant analytics requires FDW gymnastics or ETL." — [Bytebase](https://www.bytebase.com/blog/multi-tenant-database-architecture-patterns-explained.md)
- Neon's PG 18 guide on UUIDv7 uses a single-column `id UUID PRIMARY KEY DEFAULT uuidv7()` plus a separate `tenant_id` column and a composite index on `(tenant_id, id)` so tenant-scoped scans stay time-ordered. — [Neon: PostgreSQL 18 UUIDv7 support](https://neon.com/postgresql/postgresql-18/uuidv7-support)

### Inferences
- For organizations-with-users tenants whose per-user data is thousands of small rows, the per-tenant data volume is tiny; the vendor literature's own rules of thumb (AWS pool model, Citus shared tables, Bytebase/kubaik heuristics) all land on shared schema + RLS for this profile. Schema- or database-per-tenant would pay the N× migration and catalog costs for no data-volume reason.
- The costs that actually bite each model, from the sources: shared schema = noisy neighbours and a single blast radius for a missing filter; schema-per-tenant = migrations × N, catalog/planning/autovacuum growth, per-schema `pg_dump` overhead proportional to the whole catalog; database-per-tenant = connections × N, backups × N, cross-tenant reporting via ETL/FDW, fleet migrations.
- The migration direction in the literature is RLS → more isolation when an enterprise customer demands it; Microsoft's per-tenant choice at provisioning time and Citus's `isolate_tenant_to_new_shard` are both ways to keep the shared schema and carve out the few tenants that need it. A design that keeps `tenant_id` on every row preserves that option; schema-per-tenant does not convert back as easily.

### Gaps
- No controlled benchmark compares the three models on the same workload; all cost figures found are anecdotal (single-author blog) or vendor marketing (Neon).
- The PGConf.PL 2026 talk promises "roughly when" schema-per-tenant degrades, but the abstract has no numbers and the talk has not happened yet (Nov 2026).
- Crunchy Data's and Supabase's opinion on *model choice* (as opposed to RLS mechanics) was not found in primary sources; Crunchy's post links to a sibling "multi-tenancy design" article that was not fetched.

## Key question 2: How is row-level security done well (session-setting policies, SECURITY DEFINER, BYPASSRLS, indexing, testing)?

### Takeaway
The settled pattern is one application role that is *not* the table owner, `FORCE ROW LEVEL SECURITY` anyway, a policy of the form `tenant_id = current_setting('app.current_tenant')::uuid` (optionally `NULLIF(current_setting(..., true), '')` to fail closed as "zero rows" rather than an error), a `WITH CHECK` that matches `USING`, an index leading with `tenant_id`, policies that compare only columns of the current row, and `(SELECT ...)` wrapping of per-query-constant function calls so the planner evaluates them once. Test with pgTAP by seeding two tenants and asserting each sees only its own rows; distinguish "zero rows" (filtered) from "permission denied" (missing grant).

### Cited Findings
- PostgreSQL docs: "Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system when accessing a table." "Table owners normally bypass row security as well, though a table owner can choose to be subject to row security with ALTER TABLE ... FORCE ROW LEVEL SECURITY." — [PostgreSQL docs: Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- PostgreSQL docs on SECURITY DEFINER: "Policy expressions are run as part of the query and with the privileges of the user running the query, although security-definer functions can be used to access data not available to the calling user." Also: sub-selects in policies "can create race conditions that could allow information leakage if care is not taken," and "the sub-SELECT could be embedded into a security definer function." — [PostgreSQL docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- PostgreSQL docs on covert channels: "Referential integrity checks, such as unique or primary key constraints and foreign key references, always bypass row security to ensure that data integrity is maintained. Care must be taken when developing schemas and row level policies to avoid 'covert channel' leaks of information through such referential integrity checks." — [PostgreSQL docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- PostgreSQL docs on LEAKPROOF and evaluation order: the policy expression "will be evaluated for each row prior to any conditions or functions coming from the user's query," with the only exception being "leakproof functions, which are guaranteed to not leak information; the optimizer may choose to apply such functions ahead of the row-security check." — [PostgreSQL docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- PostgreSQL docs on `row_security = off` for backups: "when taking a backup, it could be disastrous if row security silently caused some rows to be omitted from the backup. In such a situation, you can set the row_security configuration parameter to off. This does not in itself bypass row security; what it does is throw an error if any query's results would get filtered by a policy." — [PostgreSQL docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- PostgreSQL docs on performance: policies that "consider only the current values in the row to be accessed or updated" are "the simplest and best-performing case; when possible, it's best to design row security applications to work this way." — [PostgreSQL docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- AWS recommends the runtime-variable method over a Postgres user per tenant ("The second option is preferred, because the first option requires the creation of a new PostgreSQL user for each tenant"), enabling RLS "on all tables that contain tenant data," with the sample policy `CREATE POLICY tenant_isolation_policy ON tenant USING (tenant_id = current_setting('app.current_tenant')::UUID);` and the comment "This policy implies a WITH CHECK that matches the USING clause." Sample code: [aws-saas-factory-postgresql-rls](https://github.com/aws-samples/aws-saas-factory-postgresql-rls). — [AWS Prescriptive Guidance: RLS recommendations](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/rls.html)
- AWS blog (May 2020, Michael Beardsley; old but still the linked reference): "you should have your application connect to the database as a user *other than* the owner of the database objects"; the per-tenant-role approach "is hard to maintain and does not scale well"; a filtered SELECT/UPDATE/DELETE behaves as if rows don't exist while a failing INSERT returns an error; "Be sure to thoroughly test functions, procedures, views and complex nested queries"; and "Consider using numeric sequences for your primary key instead of random UUID values." The post sets the GUC with session-level `SET` on every `getConnection()` and warns "Using session variables may be incompatible with server-side connection pooling such as pgBouncer." — [AWS Database Blog: Multi-tenant data isolation with PostgreSQL RLS](https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/)
- Crunchy Data (Craig Kerstiens, April 2024) recommends a session variable over a user per tenant because per-request users are "a lot of overhead and takes away many of the tools that exist for managing and scaling Postgres connections," with the policy `CREATE POLICY event_session_user ON events TO application USING (org_id = NULLIF(current_setting('rls.org_id', TRUE), '')::uuid);` (the `TO application` clause binds the policy to the app role; `NULLIF(..., '')` turns an unset/empty GUC into NULL so the cast does not error and no rows match). The post has typos (variable name differs between SQL and Python snippets). — [Crunchy Data: Row Level Security for Tenants in Postgres](https://www.crunchydata.com/blog/row-level-security-for-tenants-in-postgres)
- Fail-closed semantics: `current_setting('app.tenant_id')` with the missing_ok flag false raises an error when unset; with `true` it returns NULL "and therefore matches no rows." — [Chat2DB RLS guide (secondary)](https://chat2db.ai/resources/blog/postgres-row-level-security-guide)
- Supabase's RLS performance guide (benchmarks on 100K and 1M rows): indexing the policy column took a policy from 171 ms to <0.1 ms; wrapping a per-query-constant function in `(select ...)` took `auth.uid() = user_id` from 179 ms to 9 ms, `has_role() = role` from 178,000 ms to 12 ms, and `team_id = any(user_teams())` from 173,000 ms to 16 ms; adding an explicit `WHERE user_id = ...` filter on top of RLS took 171 ms to 9 ms; restricting the policy `TO authenticated` instead of public took anonymous access from 170 ms to <0.1 ms. Recommendations: "put an index on columns used in the RLS that are not primary keys or unique already"; "wrap your RLS queries and functions in select statements" (only when the result does not vary per row); "Do not rely on RLS for filtering but only for security"; "Use security definer functions to do queries on other tables to bypass their RLS when possible"; "Always add 'authenticated' to the approved roles instead of nothing or public." The guide links discussions titled "current_setting can lead to bad performance when used on RLS" and "Stable functions do not seem to be honored in RLS in basic form." — [Supabase: RLS Performance and Best Practices](https://supabase.com/docs/guides/troubleshooting/rls-performance-and-best-practices-Z5Jjwv); benchmark repo [GaryAustin1/RLS-Performance](https://www.github.com/GaryAustin1/RLS-Performance)
- Testing: Supabase's pgTAP guide covers "RLS testing utilities such as checking whether RLS is enabled and simulating different user contexts" with a cross-organization isolation example; `basejump/supabase-test-helpers` provides `tests.authenticate_as`, `tests.rls_enabled`; `rlsautotest` generates pgTAP suites from the policy catalog, seeds two tenants, and distinguishes "row-level filtering is verified as zero rows visible; a missing grant is verified as a permission error"; `rlsgrid` generates a role × table × operation allow/deny matrix for `pg_prove` plus a cross-tenant leak fuzzer; a practitioner guide recommends `FORCE ROW LEVEL SECURITY` so the owner is not exempt in tests. — [Supabase: Advanced pgTAP Testing](https://supabase.com/docs/guides/local-development/testing/pgtap-extended.md); [rlsautotest](https://pypi.org/project/rlsautotest/); [rlsgrid](https://pypi.org/project/rlsgrid/0.1.0/); [helpmetest: RLS testing](https://helpmetest.com/blog/row-level-security-testing/)
- A Rust multi-tenant Axum library warns that without `FORCE ROW LEVEL SECURITY` "the owner connection bypasses the policy and your isolation is silently broken." — [tenaxum source](https://docs.rs/crate/tenaxum/0.2.0/source/src/tx.rs)

### Inferences
- The combination that avoids the three documented footguns: (1) migrations run as the owner role; the app connects as a non-owner, non-superuser, non-BYPASSRLS role; (2) `FORCE ROW LEVEL SECURITY` on every tenant table anyway, so a mis-wired connection string does not silently bypass; (3) policies restricted `TO app_role`, with `USING` and `WITH CHECK` both equal to `tenant_id = (SELECT NULLIF(current_setting('app.current_tenant', true), '')::uuid)`. The `(SELECT ...)` wrap is Supabase's measured fix for `current_setting` being re-evaluated per row; PostgreSQL's own docs only say row-local policies are the "best-performing case."
- "Do not rely on RLS for filtering but only for security" (Supabase) matches Citus's "every query carries a tenant filter" rule: keep the `WHERE tenant_id = $1` in application queries so the planner uses the `(tenant_id, ...)` index directly and RLS is a backstop.
- Because referential-integrity checks bypass RLS, a cross-tenant foreign key or unique constraint on a tenant-visible value (e.g. a globally unique slug) is a covert channel; keep uniqueness tenant-scoped (`UNIQUE (tenant_id, slug)`).
- Any admin/export/backup path should run with `row_security = off` as a tripwire, so an accidentally-scoped dump errors instead of silently omitting rows.

### Gaps
- No primary source quantifies the planner cost of `current_setting()` in a policy on PostgreSQL 17/18 specifically; Supabase's numbers are on its own stack (PG 15-era) and reference `auth.uid()` which itself wraps `current_setting`.
- The PostgreSQL docs do not discuss views and RLS; whether a view's owner or caller's policies apply (security_invoker views since PG 15) was not checked here.

## Key question 3: How do pooled connections (PgBouncer, pgcat) interact with SET LOCAL tenant settings, and what are the safe patterns?

### Takeaway
PgBouncer's own feature matrix says session-level `SET/RESET` is "Never" supported in transaction pooling, so a session-level tenant GUC can leak to the next client that reuses the server connection. The safe pattern is an explicit transaction per request with `SET LOCAL app.current_tenant = ...` (or `set_config(name, value, true)`) as its first statement; the value is discarded at COMMIT/ROLLBACK. Watch the PostgreSQL quirk that after a custom GUC has once been set locally, `current_setting(name, true)` returns `''` rather than NULL on that backend, which is why policies should use `NULLIF(..., '')`.

### Cited Findings
- PgBouncer features page: in transaction pooling, `SET/RESET`: "Never"; `LISTEN`: "Never"; `PREPARE/DEALLOCATE`: "Never"; `PRESERVE/DELETE ROWS temp tables`: "Never"; `Session-level advisory locks`: "Never"; `ON COMMIT DROP temp tables`: Yes; protocol-level prepared plans: Yes once `max_prepared_statements` is non-zero. Transaction pooling "breaks a few session-based features of PostgreSQL" and "breaks client expectations of the server by design." Startup parameters are tracked ("PgBouncer detects their changes and so it can guarantee they remain consistent for the client"); for more, see `track_extra_parameters` and `ignore_startup_parameters`. `SET LOCAL` is not mentioned on the page. — [PgBouncer: Features](https://www.pgbouncer.org/features.html)
- A django-rls-tenants guide: use `SET LOCAL` or `set_config(..., true)` in transaction mode because "session-level state from the previous transaction can leak to the next client"; its `USE_LOCAL_SET` option "requires ATOMIC_REQUESTS=True," which wraps each view in a transaction so the setting lasts the whole request. — [django-rls-tenants: connection pooling](https://dvoraj75.github.io/django-rls-tenants/guides/connection-pooling)
- A DZone article applies the same pattern to schema-per-tenant: `SET LOCAL search_path` in middleware, "the SET LOCAL is crucial. It scopes the search_path change to the current transaction only." — [DZone: PgBouncer multi-tenant pooling](https://dzone.com/articles/database-connection-pooling-at-scale-pgbouncer-mul)
- A pgsql-jdbc reply: transaction mode is "compatible with any SET statements which don't leave a persistent state beyond the end of the transaction." — [pgsql-jdbc thread](https://postgrespro.com/list/id/155582596.4848118.1418225874525.JavaMail.yahoo@jws100188.mail.ne1.yahoo.com)
- PostgreSQL mailing list, "set_config with is_local parameter true escapes transaction boundaries": after a custom GUC is first set with `is_local = true`, `current_setting(name, true)` returns an empty string rather than NULL once the transaction ends; Tom Lane treats this as a consequence of how GUCs work rather than a bug; the poster flags pooled-connection reuse as the concern; workaround discussed is `RESET ALL` / `DISCARD ALL`. — [pgsql thread](https://postgrespro.com/list/thread-id/2631762)
- In transaction mode `server_reset_query` is not executed, so session-level `SET` (search_path, statement_timeout, custom GUCs) is lost between transactions. — [StackHarbor PgBouncer transaction pool guide (secondary)](https://stackharbor.com/fr/base-de-connaissances/pgbouncer-transaction-pool-advanced/)
- A pgcat vs PgBouncer vs Supavisor comparison: session-only features (session temp tables, LISTEN/NOTIFY) do not work under transaction pooling in any of them. — [Chat2DB comparison (secondary)](https://chat2db.ai/resources/blog/pgcat-vs-pgbouncer-vs-supavisor)
- AWS's 2020 blog set the tenant GUC with session-level `SET` on every connection checkout and explicitly warned it "may be incompatible with server-side connection pooling such as pgBouncer." — [AWS Database Blog](https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/)

### Inferences
- Pattern that is safe under PgBouncer/pgcat transaction pooling: `BEGIN; SELECT set_config('app.current_tenant', $1, true); ...queries...; COMMIT;` with the tenant value bound as a parameter (never string-concatenated). Statements outside a transaction have no tenant and, with `NULLIF(current_setting(..., true), '')`, see zero rows.
- Because the empty-string quirk means an "unset" GUC on a reused backend is `''` not NULL, a policy written as `tenant_id = current_setting('app.current_tenant', true)::uuid` would throw a cast error on `''`; the Crunchy `NULLIF` form is the robust one.
- If the service uses LISTEN/NOTIFY for sync fan-out, that needs a session-mode pool or a direct connection; it cannot share the transaction-mode pool with tenant-scoped request traffic.
- The coordinator-style single-process architecture of this repo (one owner of DB access) makes "one transaction per request, `SET LOCAL` first" straightforward to enforce centrally and test once.

### Gaps
- Neither PgBouncer nor pgcat documentation found explicitly documents `SET LOCAL` behaviour; the guidance that it is safe rests on PostgreSQL semantics (transaction-scoped GUC) plus practitioner write-ups.
- pgcat-specific documentation on GUC handling was not found; only a third-party comparison.

## Key question 4: Recommended primary-key and tenant-scoping convention (composite keys with tenant_id, UUIDv7, ULID), and effects on sync engines

### Takeaway
Two conventions coexist: Citus-style composite keys `PRIMARY KEY (tenant_id, id)` (required when the tenant id is a sharding key, and enforces per-tenant uniqueness) versus a single-column globally unique `id` (UUIDv7, native in PostgreSQL 18) with a `NOT NULL tenant_id` column and a composite index `(tenant_id, id)`. Sync engines (PowerSync, ElectricSQL) want client-generated, globally unique, single-column UUID ids and single-table filters, which favours the second convention with `tenant_id` denormalized onto every synced table.

### Cited Findings
- Citus: "Citus requires that primary and foreign key constraints include the distribution column," producing composite keys such as `PRIMARY KEY (company_id, id)`; "This is compatible with the multi-tenant case because what we really need there is to ensure uniqueness on a per-tenant basis." ORMs `activerecord-multi-tenant` and `django-multitenant` "will automatically add these filters to all your queries, even the complicated ones." — [Citus docs: Multi-tenant Applications](https://docs.citusdata.com/en/stable/use_cases/multi_tenant.html)
- PostgreSQL 18 adds a native `uuidv7()` function per RFC 9562, time-ordered, with `uuid_extract_timestamp()` extended to v7. Neon's pattern: `id UUID PRIMARY KEY DEFAULT uuidv7()`, a separate `tenant_id`, and a composite index on `(tenant_id, id)`: "you can efficiently query records by tenant while maintaining chronological order." — [Neon: PostgreSQL 18 UUIDv7 support](https://neon.com/postgresql/postgresql-18/uuidv7-support)
- AWS (2020) advised "Consider using numeric sequences for your primary key instead of random UUID values" for large tables; this predates UUIDv7 and targets random v4 index locality. — [AWS Database Blog](https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/)
- GitLab's sharding guidelines (the rule set for a product that ships the same schema self-managed and SaaS): each row should have exactly one sharding key, as specific as possible; keys "must be immutable"; avoid multi-column keys unless necessary; `organization_id` is an allowed key; every new model that stores customer data must define a sharding key so each row is attributable to a single organization; existing tables can declare a `desired_sharding_key` backfilled from a parent table. — [GitLab: Sharding guidelines](https://docs.gitlab.com/development/organization/sharding/); [GitLab: Cells development](https://docs.gitlab.com/ee/development/cells.html); [GitLab isolation blueprint](https://docs.GitLab.com/ee/architecture/blueprints/organization/isolation.html)
- PowerSync: "Each model used with PowerSync needs to have a UUID id column. Since clients can also create rows locally, using randomized ids reduces the chance of collisions"; "For tables where the client will create new rows, we recommend using a UUID for the ID" (client helper generates v4); "PowerSync does not perform any validation that IDs are unique. Duplicates can occur if a non-unique column is used as the ID, or if Postgres table partitions contain the same ID"; if the server uses sequential keys, a client-UUID-to-server-id mapping "must be performed wherever the UUIDs are referenced, including for every foreign key column." — [PowerSync: Serverpod integration](https://docs.powersync.com/integrations/serverpod); [PowerSync: Client ID](https://docs.powersync.com/usage/sync-rules/client-id)
- PowerSync replication caveats: a table is not replicated unless it is in the `powersync` publication; publication row-filter changes "are not automatically picked up by PowerSync during replication, and can cause PowerSync to miss changes." A community guide recommends denormalizing the owner/tenant column onto each synced table so sync rules can filter on it, and notes PowerSync does not enforce foreign keys client-side. — [PowerSync: Implementing schema changes](https://docs.powersync.com/usage/lifecycle-maintenance/implementing-schema-changes); [community PowerSync skill (secondary)](https://www.claudepluginhub.com/skills/ichabodcole-recipes-plugins-recipes/powersync-local-first-sync)
- ElectricSQL shapes: "A shape contains all of the rows in the table that match the where clause"; "Shapes are currently single table only"; equality filters are cheap because "shapes are indexed by their constant, allowing a single lookup to retrieve all shapes for that constant"; use positional `$1` params; non-deterministic functions such as `now()` are not supported in where clauses; scoping through a relation uses `id IN (SELECT user_id FROM memberships WHERE org_id = $1)`. A third-party auth-proxy pattern appends the tenant filter server-side from the token so clients cannot choose their tenant. — [ElectricSQL: Shapes guide](https://electric-sql.com/docs/guides/shapes); [ElectricSQL: Shapes usage](https://electric-sql.com/docs/usage/data-access/shapes); [Scope3 Electric auth proxy (third party)](https://docs.agentic.scope3.com/docs/electric/ELECTRIC_AUTH_PROXY)
- A secondary skills page states the generic rule that in a composite key the leading column should match the dominant access or partition pattern (i.e. `tenant_id` first). — [skills.sh db-keys (secondary)](https://www.skills.sh/hainrixz/claude-db/db-keys)

### Inferences
- For a service whose rows originate on devices and sync, the sync-engine constraints dominate: single-column, client-generatable, globally unique ids (UUIDv7 on the server default, UUIDv4 or v7 on clients) with `tenant_id uuid NOT NULL` on every synced table, including leaf tables (transcript lines) that could otherwise derive the tenant through a parent. This also satisfies "every query can carry `WHERE tenant_id = $1`" and lets RLS and sync-shape filters use the same column.
- Keep `(tenant_id, id)` as the leading index even with a single-column PK; add `(tenant_id, user_id, updated_at)` or similar for the conversation index. Composite *primary* keys are only required if a sharding layer (Citus) demands them; they complicate ORMs and sync engines that assume one `id`.
- Make `tenant_id` immutable (GitLab rule); moving a conversation between organizations should be a copy-plus-delete, not an UPDATE of `tenant_id`, which would otherwise require `WITH CHECK` re-evaluation and confuse replication filters.
- Because PowerSync does not validate uniqueness and PG partitions can repeat ids, do not partition by tenant with per-partition sequences; UUIDs avoid this entirely.

### Gaps
- No source benchmarks `PRIMARY KEY (tenant_id, id)` versus `PRIMARY KEY (id)` + index `(tenant_id, id)` on PostgreSQL 17/18.
- ULID-specific guidance for PostgreSQL multi-tenancy was not found in primary sources; UUIDv7 has displaced it in the 2025–2026 material.
- Official PowerSync or ElectricSQL documentation for a `tenant_id` multi-tenant pattern was not found; the tenant scoping advice above is inferred from their single-table filter and client-id rules.

## Key question 5: How do products run a single-tenant on-prem deployment with the same schema as the cloud without special-casing?

### Takeaway
The only well-documented product-scale example found is GitLab: self-managed and Dedicated run inside a "default organization," every customer-data table carries an `organization_id`-derived sharding key, and `Current.organization` is always set (falling back to the default), so the same code and schema serve one-org instances and GitLab.com. The general pattern is "always multi-tenant in the schema; the single-tenant deployment is a tenant count of one, created at install time."

### Cited Findings
- GitLab: "GitLab Self-Managed and GitLab Dedicated legitimately run inside the default organization"; "`Current.organization` is always set, falling back to the default organization when none applies"; building features at the organization level avoids rebuilding instance-level features for GitLab.com top-level groups ("Organizations remove this duplication"), and the organization-level default "serves both." — [GitLab: Organization development](https://docs.gitlab.com/development/organization/)
- GitLab's Cells rule that every new model storing customer data must define a sharding key attributable to a single organization, with schemas defaulting to requiring one; organization-level tables declare `sharding_key` in `db/docs/`. — [GitLab: Cells](https://docs.gitlab.com/ee/development/cells.html); [GitLab: Sharding guidelines](https://docs.gitlab.com/development/organization/sharding/)
- SingleStore's multi-tenant guide (vendor, not PostgreSQL) states its `tenant_id` approach "also work[s] well with a self-hosted environment," and that compliance customers who need their own database push toward database-per-tenant. — [SingleStore: Designing for Multi-Tenant Applications](https://docs.singlestore.com/db/v9.1/developer-resources/designing-for-multi-tenant-applications)
- Microsoft: the tenancy model "generally doesn't change application behavior" and can be chosen per tenant at provisioning or later. — [Microsoft Learn](https://learn.microsoft.com/en-us/azure/sql-database/saas-tenancy-app-design-patterns)
- A general comparison recommends defaulting to multi-tenant and siloing hot or regulated customers later; single-tenant instances are "patched and upgraded separately." — [designgurus (secondary)](https://www.designgurus.io/answers/detail/what-is-multitenancy-in-software-architecture-and-how-do-you-design-a-multi-tenant-system)

### Inferences
- Treat the on-prem bundle as a one-tenant instance of the multi-tenant schema: the installer/first boot creates the single organization row and all `tenant_id` columns, RLS policies, and `SET LOCAL` plumbing stay identical. The only deployment-specific code is "which tenant does this request belong to" (on-prem: the sole org; cloud: from the auth token), which is exactly GitLab's `Current.organization` fallback.
- This also makes the on-prem build a free RLS test bed: a single org with RLS enforced catches a missing tenant context as "zero rows" locally before it becomes a cross-tenant leak in the cloud.
- Keeping the schema identical means on-prem backups (`pg_dump` of the whole database) are already a per-tenant backup, and a cloud tenant export can reuse the on-prem import path (see Q6).

### Gaps
- No engineering blog post was found that narrates the "single-tenant on-prem + multi-tenant SaaS, one schema" decision explicitly for a PostgreSQL product other than GitLab; Sentry, Mattermost, and similar self-hostable products were not researched.

## Key question 6: Per-tenant data export, deletion (GDPR), and backup granularity under each model

### Takeaway
Database-per-tenant makes export, restore, and deletion single commands (`pg_dump`, `pg_restore`, `DROP DATABASE`; Neon adds per-project PITR). Schema-per-tenant gets `pg_dump -n` and `DROP SCHEMA ... CASCADE`, but per-schema dump cost scales with the total catalog. Shared schema makes whole-system backup trivial and per-tenant restore the hard case; export and deletion become application-level jobs that rely on every table carrying `tenant_id` (with `ON DELETE` cascades or an explicit per-table delete order), and PostgreSQL warns that a dump taken under RLS could silently omit rows unless `row_security = off` is used as a tripwire.

### Cited Findings
- PostgreSQL docs: when taking a backup "it could be disastrous if row security silently caused some rows to be omitted from the backup"; set `row_security = off` so any query that would be filtered throws an error instead. — [PostgreSQL docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- Neon: "restore just one customer's database (project) to any point in time—within seconds"; provisioning, restore, and deletion are available through the public API; no backups need pre-configuring. — [Neon: Database per tenant](https://neon.com/use-cases/database-per-tenant)
- Microsoft: the tenancy model "does affect restore, disaster recovery, and customization." — [Microsoft Learn](https://learn.microsoft.com/en-us/azure/sql-database/saas-tenancy-app-design-patterns)
- Per-schema `pg_dump` overhead evidence (PG 18.6 BUG #19688: every sequence in the database scanned when dumping one schema; 2012 threads: 12 minutes for a near-empty schema in a 20,000-schema DB, ~30–40 s fixed overhead per schema at 2,600 schemas). — [BUG #19688](https://www.postgresql.org/message-id/19688-e90025dc375a22a3@postgresql.org); [pgsql-performance 2012](https://postgrespro.com/list/id/1337843209018-5709766.post@n5.nabble.com); [pgsql-hackers 2012](https://www.postgresql.org/message-id/1352216421913-5730877.post%40n5.nabble.com)
- Practitioner summaries (secondary): shared schema makes whole-system backup trivial but per-tenant restore hard; schema-per-tenant deletion is `DROP SCHEMA tenant_acme CASCADE` and export is `pg_dump --schema`; database-per-tenant "GDPR deletion is a single DROP DATABASE" and per-tenant restore is "restore that DB," at the cost of "managing a fleet"; recommendation to "decide which restore story you need before choosing." — [devsaran: choosing a multi-tenant data model](https://devsaran.com/writing/choosing-a-multi-tenant-data-model); [Bytebase](https://www.bytebase.com/blog/multi-tenant-database-architecture-patterns-explained.md); [kolonell 2026 (secondary)](https://kolonell.com/en/blog/saas-multi-tenant-postgres-architecture-2026-en)
- AWS sample schema uses `tenant_id UUID NOT NULL REFERENCES tenant (tenant_id) ON DELETE RESTRICT` on child tables, i.e. deletion is deliberately not cascaded from the tenant row. — [AWS Prescriptive Guidance: RLS recommendations](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/rls.html)
- Citus's `isolate_tenant_to_new_shard ... CASCADE` moves one tenant's rows across all co-located tables into a dedicated shard, which is also the unit for moving a tenant between nodes. — [Citus docs](https://docs.citusdata.com/en/stable/use_cases/multi_tenant.html)

### Inferences
- In the shared-schema model, per-tenant export is "run every table's `SELECT ... WHERE tenant_id = $1` inside one `SET LOCAL` transaction (REPEATABLE READ for a consistent snapshot) and emit a portable format"; per-tenant deletion is the same traversal with DELETE, or `DELETE FROM tenant WHERE id = $1` if children use `ON DELETE CASCADE` (AWS chooses RESTRICT, so deletion is explicit). Because every synced table already carries `tenant_id` (Q4), this traversal needs no joins.
- Per-tenant *restore* in shared schema is the genuinely weak spot: the practical answer is to restore the full backup to a scratch instance and re-import one tenant's rows via the same export/import path used for on-prem migration; keeping that path first-class (it is also the on-prem ↔ cloud migration tool) is the mitigation.
- With tiny per-tenant volumes, the simplest high-value investment is a tested logical "tenant bundle" export/import, not a change of tenancy model.

### Gaps
- No source addressed whether GDPR erasure must also purge deleted-tenant rows from existing backups or how long backups may retain them; this is a legal/DPA question not covered by the engineering sources found.
- No measured data on how long per-tenant logical export takes at scale in a shared schema.

## Key question 7: Concrete guidance for this service (synthesis)

### Takeaway
Use one shared schema with `tenant_id uuid NOT NULL` on every tenant-owned table (including transcript lines), RLS with `FORCE`, a non-owner application role, policies `USING/WITH CHECK (tenant_id = (SELECT NULLIF(current_setting('app.current_tenant', true), '')::uuid))`, `SET LOCAL`/`set_config(..., true)` as the first statement of every request transaction, UUIDv7 single-column ids with `(tenant_id, ...)` leading indexes, and the on-prem bundle as a one-organization instance of the same schema. Reserve schema/database-per-tenant for a future enterprise tier, which the `tenant_id`-everywhere design keeps open.

### Cited Findings
- Shared schema + RLS as the pooled-model requirement and the AWS `app.current_tenant` convention — [AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/rls.html)
- Non-owner app role, `FORCE ROW LEVEL SECURITY`, `BYPASSRLS` — [PostgreSQL docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html); [AWS Database Blog 2020](https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/)
- `NULLIF(current_setting(..., true), '')` form and policy bound `TO application` — [Crunchy Data 2024](https://www.crunchydata.com/blog/row-level-security-for-tenants-in-postgres)
- `SET/RESET` "Never" in transaction pooling; use transaction-scoped settings — [PgBouncer features](https://www.pgbouncer.org/features.html); [django-rls-tenants](https://dvoraj75.github.io/django-rls-tenants/guides/connection-pooling)
- Index policy columns, wrap constants in `(select ...)`, keep explicit tenant filters, restrict policy roles — [Supabase RLS performance](https://supabase.com/docs/guides/troubleshooting/rls-performance-and-best-practices-Z5Jjwv)
- UUIDv7 single-column PK with `(tenant_id, id)` index — [Neon PG 18 UUIDv7](https://neon.com/postgresql/postgresql-18/uuidv7-support); client-generated UUID ids for synced tables — [PowerSync Client ID](https://docs.powersync.com/usage/sync-rules/client-id); single-table tenant-filtered shapes — [ElectricSQL shapes](https://electric-sql.com/docs/guides/shapes)
- Default organization for single-tenant installs and immutable sharding key on every customer-data table — [GitLab Organization development](https://docs.gitlab.com/development/organization/); [GitLab Sharding guidelines](https://docs.gitlab.com/development/organization/sharding/)
- Per-tenant isolation escape hatch within a shared schema (Citus tenant isolation) and per-tenant-database option (Neon) for a future enterprise tier — [Citus docs](https://docs.citusdata.com/en/stable/use_cases/multi_tenant.html); [Neon database per tenant](https://neon.com/use-cases/database-per-tenant)

### Inferences
- A minimal DDL/runtime checklist consistent with all sources above:
  1. `CREATE ROLE app NOLOGIN NOBYPASSRLS; CREATE ROLE migrator;` tables owned by `migrator`; the service connects as `app` (on-prem and cloud alike).
  2. Every tenant table: `tenant_id uuid NOT NULL REFERENCES organization(id)`, `id uuid PRIMARY KEY DEFAULT uuidv7()` (PG 18; `gen_random_uuid()` fallback for PG ≤17 on-prem), `ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL SECURITY`, policy `tenant_isolation ON t TO app USING (...) WITH CHECK (...)` with the `(SELECT NULLIF(current_setting('app.current_tenant', true), '')::uuid)` expression, index `(tenant_id, <access columns>)`, tenant-scoped uniques `UNIQUE (tenant_id, ...)`.
  3. Request path: `BEGIN; SELECT set_config('app.current_tenant', $1, true); ...; COMMIT;` with the tenant id from the auth token (cloud) or the sole org (on-prem). Never session-level `SET`.
  4. Admin/export/backup connections: `migrator` or a dedicated role with `SET row_security = off` so filtered results error instead of silently truncating.
  5. Tests: pgTAP (or the repo's fixture tests) seed two orgs, run every query path under each tenant context and under no context, assert zero rows for the other tenant and for no-context, and assert `FORCE` + policy presence for every table with a `tenant_id` column (catalog query), so a new table cannot ship unprotected.
- The on-prem Docker/Helm bundle differs from cloud only in tenant resolution and in running PgBouncer (if at all) in transaction mode with the same `SET LOCAL` discipline; it should not disable RLS "because there is only one org", since the single-org deployment is the cheapest place to catch a missing tenant context.
- Export/import of a "tenant bundle" (all tables filtered by `tenant_id`, consistent snapshot) is the one feature that serves four needs at once: GDPR export, GDPR delete verification, on-prem ↔ cloud migration, and per-tenant restore from a scratch instance.

### Gaps
- Whether the project's deployment targets will run PostgreSQL 18 on-prem (for native `uuidv7()`) is a project decision, not a research finding; older on-prem Postgres would need application-side UUIDv7 generation.
- No source was found that measures RLS overhead for the specific access pattern "thousands of small rows per user, read-mostly, synced to devices"; expect it to be negligible given Supabase's sub-10 ms numbers once the policy column is indexed and constants are wrapped, but this should be verified with `EXPLAIN (ANALYZE)` on the actual schema.
