# Enterprise authentication and org/user management for a multi-tenant service with native macOS, iOS, and CLI clients (on-prem and public cloud), 2025–2026

Scope note: these notes cover OIDC/SAML SSO, SCIM provisioning, organizations/roles/invitations, native and CLI client authentication, service-side authorization, and a bundled-IdP versus build-in-house evaluation. Research date: 2026-10-31. Where a finding is from my own direct check (container registry manifests) rather than a published page, it is labelled as such. "On-prem" below means a single-organization installation run by a customer; "cloud" means the vendor-run multi-tenant service.

## Key question 1: How native desktop/mobile apps and CLIs authenticate as a user and keep per-device credentials (PKCE via system browser, device grant, refresh rotation, token binding, Keychain), and what gh, gcloud, 1Password CLI, Tailscale, Linear/Notion actually do

### Takeaway
The 2025–2026 consensus is: authorization code + PKCE (S256) through an external user agent (ASWebAuthenticationSession on Apple platforms, loopback 127.0.0.1 redirect for CLIs), device authorization grant (RFC 8628) as the headless/remote fallback, refresh-token rotation or DPoP sender-constraining for public clients, and tokens stored in the data-protection Keychain with a "ThisDeviceOnly" accessibility class. The well-known products differ mainly in the fallback order and in whether they rely on a separate local trusted process (1Password) or a per-device key pair bound to a human login (Tailscale).

### Cited Findings

Standards baseline
- RFC 8252 (OAuth for Native Apps): "native apps MUST use an external user-agent to perform OAuth authorization requests" and "native apps MUST NOT use embedded user-agents to perform authorization requests"; the stated reason is that an embedding app "can access the user's full authentication credential, not just the OAuth authorization grant" — [RFC 8252 §5, §8.12](https://www.rfc-editor.org/rfc/rfc8252.html)
- RFC 8252 requires authorization servers to support three redirect options for native apps: private-use URI scheme (reverse-domain, e.g. `com.example.app:/oauth2redirect/example-provider`), claimed `https` scheme (which "native apps SHOULD use ... over the other options where possible"), and loopback `http://127.0.0.1:{port}/{path}` or `http://[::1]:{port}/{path}`; "The authorization server MUST allow any port to be specified at the time of the request", clients are RECOMMENDED to try both IPv4 and IPv6 loopback, and "the use of localhost is NOT RECOMMENDED" to avoid listening on non-loopback interfaces — [RFC 8252 §7.1–7.3, §8.3](https://www.rfc-editor.org/rfc/rfc8252.html)
- RFC 8252: "Public native app clients MUST implement the Proof Key for Code Exchange" and "authorization servers MUST support PKCE for such clients"; client secrets shipped in an app "should not be treated as confidential secrets" and servers are "NOT RECOMMENDED" to require them; in-app browser tabs are "RECOMMENDED, for usability reasons" because they retain the browser's security properties and authentication state — [RFC 8252 §6, §8.1, §8.5, §8.7](https://www.rfc-editor.org/rfc/rfc8252.html)
- RFC 9700 (OAuth 2.0 Security BCP, 2025): "Public clients MUST use PKCE"; `S256` is "the only such method" that does not expose the verifier; "the authorization server MUST enforce the correct usage of `code_verifier`"; "Authorization servers MUST mitigate PKCE downgrade attacks" — [RFC 9700 §2.1.1, §4.8.2](https://www.rfc-editor.org/rfc/rfc9700.html)
- RFC 9700: "Refresh tokens for public clients MUST be sender-constrained or use refresh token rotation"; under rotation "the authorization server issues a new refresh token with every access token refresh response" and on reuse of a stale token revokes the active token and forces re-authorization; "Refresh tokens SHOULD expire if the client has been inactive for some time"; servers "MAY revoke refresh tokens automatically in case of a security event" (password change, logout) — [RFC 9700 §2.2.2, §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html)
- RFC 9700: "Authorization and resource servers SHOULD use mechanisms for sender-constraining access tokens" (mTLS RFC 8705 or DPoP RFC 9449); "DPoP can be used with public clients"; access tokens "SHOULD be audience-restricted to a specific resource server" and "the resource server MUST refuse to serve the respective request" otherwise; the ROPC (password) grant "MUST NOT be used"; the implicit grant "SHOULD NOT" be used; redirect URIs "MUST utilize exact string matching except for port numbers" of native-app loopback URIs — [RFC 9700 §2.1, §2.1.2, §2.2.1, §2.3, §2.4, §4.1.3, §4.10](https://www.rfc-editor.org/rfc/rfc9700.html)
- RFC 8628 (device grant): the device gets `device_code`, `user_code`, `verification_uri` ("should be short and easy to remember"), optional `verification_uri_complete` (for QR/NFC; clients "MUST still display the user_code"), `expires_in`, and `interval` (default 5 s); it polls the token endpoint handling `authorization_pending`, `slow_down` (add 5 s), `access_denied`, `expired_token`, and "MUST stop polling" on any other error — [RFC 8628 §3.2–3.5](https://www.rfc-editor.org/rfc/rfc8628.html)
- RFC 8628 security: user codes are low entropy so servers must rate-limit guesses (example: 8-char base-20 code ≈ 34.5 bits needs ≈ 5 allowed attempts per window to reach 2^-32); recommended alphabet is the 20 consonants `BCDFGHJKLMNPQRSTVWXZ`; remote phishing (attacker emails a victim a code) is mitigated by telling the user they are authorizing a device and confirming it is in their possession, which matters most when `verification_uri_complete` is used — [RFC 8628 §5.1, §5.2, §5.4, §6.1](https://www.rfc-editor.org/rfc/rfc8628.html)
- DPoP: the draft explicitly names native apps "installed and run on a user's device" as well positioned to benefit from DPoP-bound tokens; DPoP "MUST always be used in conjunction with HTTPS" — [draft-ietf-oauth-dpop-07 (became RFC 9449)](https://datatracker.ietf.org/doc/draft-ietf-oauth-dpop/07/)
- A commercial mobile SDK vendor (Curity) documents the practical device-binding pattern: generate the DPoP key in the Secure Enclave ("private key never leaves the enclave"), bind authorization codes and refresh tokens to that key, fall back to a software P-256 key where the enclave is unavailable (App Extensions, simulators), and expect `invalid_dpop_proof` when the proof is missing — [Curity: Configure Token Binding](https://curity.io/docs/identity-server/developer-guide/haapi-sdks/mobile-sdks/how-to/configure-token-binding); [Curity: Token Binding SDK layer](https://curity.io/docs/identity-server/developer-guide/haapi-sdks/mobile-sdks/sdk-layer/token-binding)

Apple platform mechanics
- `ASWebAuthenticationSession.Callback.https(host:path:)` "Creates a callback object that matches against HTTPS URLs with the given host and path"; "The host must be a member of a domain associated with the app"; availability iOS 17.4+, macOS 14.4+, visionOS 1.1+ — [Apple: https(host:path:)](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession/callback/https(host:path:).md)
- Before iOS 17.4 / macOS 14.4 apps had to use a custom URL scheme; any app could claim `myapp://`, which is the motivation for HTTPS callbacks. Sources disagree whether the Associated Domains entitlement needs `applinks:` (Auth0 guide) or `webcredentials:` (Apple forum error message); verify against Apple docs — [Auth0 support article](https://support.auth0.com/center/s/article/auth0-https-scheme-does-not-work-for-ios-universal-link); [Apple Developer Forums thread 750051](https://developer.apple.com/forums/thread/750051); [Apple Developer Forums thread 769749](https://developer.apple.com/forums/thread/769749)
- An HTTPS callback that works on device can fail on the Simulator with a "not associated with domain" error — [Apple Developer Forums thread 763621](https://developer.apple.com/forums/thread/763621)
- `kSecUseDataProtectionKeychain` (macOS 10.15+): "A key whose value indicates whether to treat macOS keychain items like iOS keychain items"; Apple says "It's highly recommended that you set the value of this key to `true` for all keychain operations"; it is what makes `kSecAttrAccessible` and `kSecAttrAccessGroup` apply on macOS, and gives "the iOS behavior without synchronization" (unlike `kSecAttrSynchronizable`, which also syncs via iCloud) — [Apple: kSecUseDataProtectionKeychain](https://developer.apple.com/documentation/security/ksecusedataprotectionkeychain.md)
- `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`: readable after first unlock until restart, recommended for background access; "Items with this attribute do not migrate to a new device. Thus, after restoring from a backup of a different device, these items will not be present." — [Apple: kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly](https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlockthisdeviceonly.md)
- Third-party guide (secondary source): on macOS the keychain access group list is built from the `keychain-access-groups` entitlement plus the application identifier; app-group identifiers do not work as keychain access groups on macOS; Team-ID prefixes prevent cross-team access — [tessl.io keychain-sharing reference](https://tessl.io/registry/dpearson2699/swift-ios-skills/files/skills/swift-security/references/keychain-sharing.md)

What real products do
- GitHub CLI (`cli/oauth` library): "First, Device flow is attempted, and the localhost server is used as fallback"; the fallback is the web application flow with a receiver at `http://127.0.0.1:<port>/` so it works on GHES hosts without device flow; "GitHub rotates refresh tokens on every refresh, so always persist the refresh token returned by `Refresh`" — [github.com/cli/oauth](https://github.com/cli/oauth)
- `gh auth login`: default is "a web-based browser flow"; `--web --clipboard` copies the one-time code; the token "will be stored securely in the system credential store" with a plain-text file fallback; `--with-token` and `GH_TOKEN` cover headless use — [gh auth login manual](https://cli.github.com/manual/gh_auth_login)
- `gcloud auth login`: "Obtains access credentials for your user account via a web-based authorization flow"; reuses valid stored credentials unless `--force`; `--no-launch-browser` prints a URL and accepts a pasted code; `--no-browser` prints a `gcloud auth login --remote-bootstrap="..."` command to run on a second trusted machine (gcloud ≥ 372.0) and paste the resulting URL back; `--update-adc` writes to the Application Default Credentials location. The page does not mention PKCE or loopback ports — [gcloud auth login reference](https://docs.cloud.google.com/sdk/gcloud/reference/auth/login)
- Third-party descriptions say gcloud binds a local HTTP server on 127.0.0.1 and relies on the browser hitting the callback, which breaks behind proxies and in containers/CI; one blog opines that gcloud, wrangler and Anthropic's `claude` "still don't default to" the device flow — [dev.to: Stop spawning localhost servers from your CLI](https://dev.to/abgeo/stop-spawning-localhost-servers-from-your-cli-3l9a); [nhimg.org loopback redirect glossary](https://nhimg.org/glossary/loopback-redirect/)
- 1Password CLI (app integration): the CLI does no biometric check itself; the desktop app authorizes it using Touch ID / Apple Watch / Windows Hello / device password; enabled under Developer > "Integrate with 1Password CLI"; `OP_BIOMETRIC_UNLOCK_ENABLED` toggles it — [1Password: about biometric unlock](https://www.1password.dev/cli/about-biometric-unlock); [1Password: app integration](https://www.1password.dev/cli/app-integration)
- 1Password CLI security model: on macOS the CLI and app both connect to the `1Password Browser Helper` XPC service and "Authenticity of both is confirmed by verifying the code signature"; on Linux a Unix socket plus setgid `onepassword-cli` group check ("If the GID doesn't match, the connection is reset"); on Windows a named pipe with Authenticode checks; per-terminal session credentials are tty+start-time (macOS/Linux) or PID+start-time (Windows) and "don't consist of any sensitive or secret information"; authorization lasts 10 minutes of inactivity with a 12-hour hard cap and is revoked when the app locks; accepted risks include root/admin bypass while unlocked and macOS accessibility-permission apps defeating the prompt — [1Password CLI security model](https://www.1password.dev/cli/biometric-security)
- 1Password CLI with SSO accounts: if biometric unlock is not allowed, the user is prompted to allow CLI access to the app at sign-in — [1Password: Unlock CLI with SSO](https://developer.1password.com/docs/cli/sign-in-sso)
- Tailscale: each machine generates a curve25519 machine key; "On login, clients generate a node private key"; the control server replies with "a unique authentication URL for a node key" that requires an interactive browser flow, which "typically results in an OAuth2 or SAML flow with an organization's identity provider, and can include a multi-factor authentication (MFA) step"; the server "ties a node key to a human identity, and can apply policy"; it "can also require that a key be regenerated at a regular interval" and "Revocation messages are delivered the moment the key is automatically rotated or manually disabled" — [Tailscale: key management](https://tailscale.com/blog/tailscale-key-management)
- Tailscale practical flow: `tailscale up` prints a login URL and returns once approved in a browser; pre-authorized auth keys skip the browser step; persisted state reconnects without a new login — [novita.ai Tailscale guide](https://docs.novita.ai/guides/sandbox-vpn-tailscale); [tailscale-web (Go) docs](https://pkg.go.dev/github.com/adrianosela/tailscale-web)
- Electron desktop pattern (generic, used as the proxy for Linear/Notion): open the system browser and receive a custom-scheme deep link; on macOS the running app gets `open-url`, while on Windows/Linux the deep link launches a second instance that must forward args via a single-instance lock; `electron .` dev builds are not registered for the scheme — [Clerk: OAuth deep links for Electron](https://clerk.com/docs/guides/configure/auth-strategies/oauth-deep-links); [OpenReplay: add authentication to an Electron app](https://blog.openreplay.com/add-authentication-electron-app/)
- A `notion://` protocol exists (a Chrome extension changelog notes replacing a `/native` redirect with "support for new notion:// protocol"), confirming Notion registers a custom scheme for opening the desktop app, but not documenting the login hand-off — [open-in-notion changelog](https://github.com/creold/open-in-notion)

### Inferences
- For this project's three clients, one authorization server configuration serves all: a single public OAuth client per platform (or one shared public client) with PKCE S256 required, redirect URIs = claimed `https` callback (macOS 14.4+/iOS 17.4+) with a reverse-domain custom scheme fallback for older OS, plus `http://127.0.0.1:*` and `http://[::1]:*` for the CLI; and the device grant enabled for the CLI's headless/SSH case. This mirrors the gh pattern (device first, loopback fallback) in reverse for a desktop-first CLI.
- Refresh-token rotation is the practical minimum for a public client; DPoP with a Secure Enclave key is the only widely specified way to actually bind a token to a device, and Keycloak, Zitadel, Ory Hydra and Authentik support vary (not verified here, see Gaps). A cheaper "device binding" for a small team is a server-side device record (per-device refresh token family, revocable from an admin UI), which RFC 9700's rotation plus "revoke on security event" already implies.
- On Apple platforms the storage decision is: data-protection keychain (`kSecUseDataProtectionKeychain = true`), `AfterFirstUnlockThisDeviceOnly` for refresh tokens so they never leave the device via backup/iCloud, a keychain access group shared between the macOS app and the CLI only if both are signed by the same team (which is the 1Password-style trust boundary); otherwise the CLI keeps its own item.
- 1Password's model (CLI never holds the secret; a code-signed desktop app brokers access over XPC with biometric consent) is the strongest desktop pattern for a CLI that ships beside a GUI app, and this repository already has a coordinator process in that position; the trade-off is that it only works when the app is installed and running.
- Tailscale's model (per-device key pair registered to a human identity, with policy-driven expiry and rotation) is the right mental model for "per-device credentials" in a sync hub: the device, not the token, is the first-class object.

### Gaps
- No primary source describes Linear's or Notion's desktop login implementation (scheme, magic link vs OAuth, token storage). Searches returned only generic Electron guidance and a third-party scheme mention.
- gcloud's exact PKCE and port-selection behaviour is not documented on the reference page; only third-party descriptions of the loopback server were found.
- Apple's ASWebAuthenticationSession overview page did not render in the fetch tool, so statements about cookie sharing and `prefersEphemeralWebBrowserSession` are not quoted from Apple here; only the `Callback.https` symbol page was verified.
- Which bundled IdPs (Keycloak, Zitadel, Hydra, Authentik) support DPoP for public clients was not verified in this pass.

## Key question 2: How products expose "sign in with your company's IdP" per organization (home realm discovery by email domain, per-org OIDC/SAML), and what Keycloak, Zitadel, Ory, WorkOS and Auth0 offer

### Takeaway
Every current product converges on the same shape: an organization owns one or more verified email domains, each domain (or the org) is linked to an OIDC or SAML connection, and an identifier-first login screen routes by the email's domain; invitations are the explicit override for guests. Keycloak 26.x Organizations (fully supported since 26.0, routing reworked in 26.8) and Zitadel organizations with domain discovery both provide this self-hosted; Ory provides it only on Ory Network or under its paid Enterprise License; WorkOS and Auth0 are SaaS references for the same model.

### Cited Findings

Keycloak Organizations
- Organizations shipped as technology preview in Keycloak 25 with "the introduction of an identity-first login flow whenever you are authenticating to a realm that has the Organizations setting enabled"; "Starting with Keycloak 26, the Organizations feature is fully supported" — [Keycloak: CIAM and multi-tenancy announcement](https://www.keycloak.org/2024/06/announcement-keycloak-organizations); [Keycloak 26.0.0 released](https://www.keycloak.org/2024/10/keycloak-2600-released)
- Domain rules: "A domain cannot be shared by different organizations within a realm"; org names must be unique in a realm; aliases are URL-friendly and immutable — [Red Hat build of Keycloak 26.4: Managing organizations](https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/managing_organizations)
- IdP linking (26.4 behaviour): "An identity provider can only be linked to a single organization"; options are **Hide on login page** and **Redirect when email domain matches** (a domain of `Any` lets any org domain trigger the redirect; an exact domain match takes priority over `Any`) — [Red Hat build of Keycloak 26.4: Managing organizations](https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/managing_organizations)
- 26.8 (released 2026-10-01) changed this: "Identity providers can now be linked to multiple organizations", "Domain routing has been moved from the identity provider to the domain entity" so each domain sets its own IdP and auto-redirect, "The domain gate ensures cross-organization isolation", and new links default to Unmanaged membership — [Keycloak 26.8.0 released](https://www.keycloak.org/2026/10/keycloak-2680-released); [Keycloak release notes](https://www.keycloak.org/docs/latest/release_notes/index.html)
- Identity-first login: "the user is asked first for a username or email to continue authenticating to a realm"; a non-existent user whose domain matches an organization "sees the login page again with an error and is not asked for credentials"; membership is granted "once they authenticate through the identity provider associated with an organization and successfully complete the flow" (first broker login) — [Red Hat build of Keycloak 26.4: Managing organizations](https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/managing_organizations)
- Matching detail (third-party write-up of 26.8): domain is lower-cased and matched exactly or by wildcard (`*.example.com`), most specific wins; "a user with a local password is asked for it rather than redirected"; the domain `verified` field "is not checked or enforced by Keycloak" — [Skycloak: home realm discovery with Keycloak Organizations](https://skycloak.io/blog/home-realm-discovery-keycloak-organizations/)
- Members: "Managed members are those managed by the organization, and they cannot exist outside of their organization" (typically created via the org's IdP; deleted with the org); "unmanaged members are those that can exist without the organization" and "the realm is the single-source of truth for the identity" — [Red Hat build of Keycloak 26.4: Managing organizations](https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/managing_organizations)
- Invitations: "An invitation is basically an email sent with a link"; existing users confirm; new users go through self-registration and "the user is forced to provide the same email address used to send the invitation"; 26.5 added "Organization invitation management" and 26.8 added an "Invite-user workflow step" that sends an action-token invitation automatically when a user is created — [Red Hat build of Keycloak 26.4: Managing organizations](https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/managing_organizations); [Keycloak 26.5.0 released](https://www.keycloak.org/2026/01/keycloak-2650-released); [Keycloak 26.8.0 released](https://www.keycloak.org/2026/10/keycloak-2680-released)
- Token claim: request scope `organization` → claim `organization` keyed by alias; `organization:<alias>` maps one named org; `organization:*` "Maps to all organizations the user is a member of"; org id and attributes are omitted unless the mapper's **Add organization id** / **Add organization attributes** are enabled; 26.7 added support for multiple organization scopes in one request; 26.6/26.8 added org groups and group roles inside the `organization` claim — [Red Hat build of Keycloak 26.4: Managing organizations](https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/managing_organizations); [Keycloak 26.7.0 released](https://www.keycloak.org/2026/07/keycloak-2670-released); [Keycloak release notes](https://www.keycloak.org/docs/latest/release_notes/index.html)
- Org admin: 26.7 added `manage-organizations` and Fine-Grained Admin Permissions for organizations; 26.6 added organization groups — [Keycloak: FGAP for organizations](https://www.keycloak.org/2026/05/org-fgap); [Keycloak: Organization groups](https://www.keycloak.org/2026/04/org-groups)
- Before core Organizations, the Phase Two extension provided this with a `home.idp.discovery.domains` IdP config key; it is a separate add-on — [Phase Two: automatic IdP redirection](https://phasetwo.io/docs/organizations/automatic-idp-redirection/)

Zitadel organizations
- An organization is a tenant-like container; "Users cannot select their organization manually"; the org is derived from the login name; unmatched users go to the default organization; orgs override instance defaults for login behaviour, MFA, password rules, branding and texts, and "Settings configured at the Organization level take priority over Default settings"; org branding on a login requires scope `urn:zitadel:iam:org:id:{id}` — [Zitadel: Organizations](https://zitadel.com/docs/guides/manage/console/organizations)
- Domain discovery: enable "Domain discovery allowed" in Login Behavior and Security Settings, allow login by email, verify each org's domain under Organization Domains (DNS verification can be disabled instance-wide), then set per-org login policy — an org with username/password disabled and one external IdP means "the user will be automatically redirected to the external identity provider", several IdPs mean "the user will be prompted to select an identity provider"; "The default organization will hold all unmatched users" — [Zitadel: Domain discovery](https://zitadel.com/docs/guides/solution-scenarios/domain-discovery)
- Scopes: `urn:zitadel:iam:org:id:{id}` restricts login to one org ("ZITADEL will enforce that the user is a member of the selected organization"); `urn:zitadel:iam:org:domain:primary:{domain}` does the same via domain — [Zitadel: scopes](https://zitadel.com/docs/apis/openidoauth/scopes)

Ory
- Ory organizations: "An organization always belongs to one Ory project"; an org lists multiple email domains and "All members of an organization must use one of the organization's OIDC or SAML SSO connections to log in"; requires identifier-first authentication; "SAML is available exclusively on select Enterprise plans"; the page also covers SCIM provisioning, break-glass recovery and a customer-admin onboarding portal; warns that some IdPs do not verify domain ownership — [Ory: Organizations and B2B SSO](https://www.ory.com/docs/kratos/organizations)
- Self-hosted availability: the Kratos README says the Ory Enterprise License "layers on top of self-hosted Kratos" and adds "enterprise features that are not available in the open source version such as SCIM, SAML, organization login" plus CAPTCHAs, security SLAs, multi-tenancy support and a private registry — [ory/kratos README](https://raw.githubusercontent.com/ory/kratos/master/README.md); summarised also by [Ory: Network or self-hosted?](https://www.ory.com/ory-network-or-self-hosting-explained-use-cases/)

WorkOS and Auth0 (SaaS reference patterns)
- WorkOS: "Only one organization can hold a given verified domain per environment"; "Domain verification by itself does not grant access to anything"; a domain policy applies to anyone on that domain "regardless of whether they already have an account or which organization they picked at sign-in"; once SSO is configured "other authentication methods for that organization are typically disabled by default"; guests on unverified domains "have to be invited first"; "Domain policies aren't an allowlist that invitations have to check against"; corporate-domain invites can be accepted by anyone on that domain, consumer-domain invites only by the exact address — [WorkOS: how WorkOS decides organization access](https://workos.com/blog/how-workos-decides-organization-access)
- WorkOS rejects consumer domains like gmail.com for domain claims and warns against using email domain as the tenant boundary (guests), recommending validation on organization ID; a team with ~200 organizations built their own email-to-connection discovery step rather than showing 200 buttons — [WorkOS: add SSO to B2B SaaS with AuthKit](https://workos.com/blog/add-sso-b2b-saas-authkit); [ory/kratos PR 3831 discussion](https://github.com/ory/kratos/pull/3831)
- Auth0 Identifier First + Home Realm Discovery: "Auth0 checks if the domain matches one from a registered Enterprise connection"; up to 1,000 domains per enterprise connection; on match the user is redirected to the IdP, otherwise prompted for a password — [Auth0: Identifier First](https://auth0.com/docs/authenticate/login/auth0-universal-login/identifier-first)

### Inferences
- The data model to copy is: Organization → verified Domains (unique per deployment) → each Domain optionally bound to an SSO Connection (OIDC or SAML) with an "auto-redirect" flag; plus Invitations as the out-of-band override. Keycloak 26.8's move of routing onto the domain entity and Zitadel's per-org login policy both landed on this; a hand-built hub should start there rather than at "one IdP per org".
- Identifier-first UI is now a hard requirement, not a nicety: Keycloak, Zitadel, Ory and Auth0 all gate per-org IdP routing on it. For native clients this means the app collects the email first (or hands the whole thing to the hosted login page) before opening the browser session; a device-grant CLI gets it for free because the browser page is the IdP's.
- On-prem single-org installs can skip discovery entirely (one org, one domain list, one connection, auto-redirect on); the same code path with N orgs is what the cloud needs. Keep the single-org install as "the default organization" (Zitadel's term) so no second code path exists.
- Among bundled IdPs, only Keycloak and Zitadel give per-org SSO in the free self-hosted build; Ory and (per Key question 5) Authentik require commercial terms or lack the concept; Dex has no org model at all.

### Gaps
- Keycloak invitation link expiry and the exact "membership determined during broker login" rules were not readable from the official single-page guide (truncated); the Red Hat 26.4 copy was used for the quoted sentences.
- WorkOS's behaviour when one organization has several SSO connections, and Auth0's behaviour when several enterprise connections claim the same domain, were not found.
- Whether Ory's Enterprise License exposes the same organizations API as Ory Network when self-hosted was not confirmed by a primary source.

## Key question 3: SCIM 2.0 for user and group provisioning — minimum viable server and which IdPs push to it

### Takeaway
A minimum viable SCIM 2.0 server is `/Users` (POST, GET by id, GET with `filter=userName eq`, PATCH, PUT), `/Groups` (same plus `members` add/remove via PATCH and `excludedAttributes=members`), `/ServiceProviderConfig`, `/ResourceTypes`, `/Schemas`, `startIndex`/`count` pagination with stable ordering, soft-delete via `active=false`, a long-lived bearer token, and SCIM error bodies; Entra ID and Okta both push to it on their own schedules, Google Workspace does not push SCIM, and Keycloak 26.8 / Zitadel (preview, users only) can themselves act as SCIM servers if you bundle them.

### Cited Findings

Minimum viable server (as defined by the two dominant pushers)
- Entra ID requires: create users (and optionally groups) per RFC 7644 §3.3; "Modify users or groups with PATCH requests" (§3.5.2); query users by `userName` and `externalId`, groups by `displayName` (§3.4.2); "The filter excludedAttributes=members when querying the group resource"; soft-delete with `active=false` and restore with `active=true` ("The user object should be returned in a request whether or not the user is active"); "Support the /Schemas endpoint"; "Accept a single bearer token for authentication and authorization" — [Microsoft Learn: Develop a SCIM endpoint](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups)
- Entra detail rules: `id` is required on every resource; PATCH responses need not include the whole resource; `op` values are emitted as `Add`, `Replace`, `Remove` so matching must be case-insensitive; filter responses are always a `ListResponse`; "Any attributes that are considered for user uniqueness must be usable as part of a filtered query"; groups "are optional, but only supported if the SCIM implementation supports PATCH requests" and need unique `displayName`; `/Bulk` is not used today; `/Schemas` is called when the provisioning config is saved — [Microsoft Learn: Develop a SCIM endpoint](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups)
- Entra describes `/Schemas`, `/ServiceProviderConfig` ("details about the features of the SCIM standard that are supported") and `/ResourceTypes` as the discovery endpoints — [Microsoft Learn: Develop a SCIM endpoint](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups)
- Entra provisioning lifecycle: an initial cycle queries all in-scope users/groups and matches against the target by the matching attribute (e.g. `userPrincipalName` → `userName`), caching the target `id`; incremental cycles then run "back-to-back ... indefinitely"; out-of-scope or disabled users get `active=false`; hard-deleted users (30 days after soft delete) get DELETE; repeated failures put the job in quarantine (reduced to daily, disabled after four weeks); nested groups are not provisioned; the TLS channel is TLS 1.2 — [Microsoft Learn: How provisioning works](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/how-provisioning-works)
- Okta minimum: TLS; "Your SCIM API must be secured against anonymous access" with OAuth 2.0 authorization code, Basic, or header token; base path such as `/scim/v2/` without underscores; required attributes `userName`, `name.givenName`, `name.familyName`, `emails`; "Keep your user ID value distinct from the user's email address"; `id` "Must be a stable identifier", unique, case-sensitive, read-only, never reassigned; `active` is required; new work should target 2.0 — [Okta: prepare a SCIM integration](https://developer.okta.com/docs/guides/scim-provisioning-integration-prepare/main/)
- Okta operations: before create it sends `GET /Users?filter=userName eq "{userName}"` and "Your SCIM server must support this query parameter"; duplicates return `409 Conflict` with the SCIM error schema; paging uses `startIndex` and `count=100` and "The SCIM server must consistently return the same ordering of results"; `itemsPerPage`/`startIndex`/`totalResults` are integers; updates are PUT (full object) for new OIN integrations except activation/deactivation/password sync which are PATCH; deactivate is PATCH `replace active=false` (200 with body or 204); "Okta doesn't perform DELETE operations on user objects"; groups use POST, `filter=displayName eq`, PATCH `add`/`remove`/`replace` on `members`, DELETE on unlink; "You must return the members list payload when GET /Groups/{groupID} is requested without any query parameters" — [Okta: SCIM 2.0 protocol guide](https://developer.okta.com/docs/api/openapi/okta-scim/guides/scim-20/)

Who pushes
- WorkOS Directory Sync lists directory types "azure scim v2.0", "okta scim v2.0", "jump cloud scim v2.0", "generic scim v2.0" and "gsuite directory"; WorkOS states Google's Directory API "does not push SCIM events" so Google Workspace is handled with a pull model — [WorkOS: Directory Sync beyond SCIM](https://workos.com/blog/directory-sync-beyond-scim); [WorkOS Node SDK directory types](https://mintlify.com/workos/workos-node/api/directory-sync); [WorkOS Directory Sync docs](https://workos.com/docs/directory-sync/index.md)

Bundled IdPs as SCIM servers/clients
- Keycloak 26.7 added a SCIM server behind the `scim-api` feature flag ("In the default profile it is disabled by default"); 26.8: "the SCIM API is promoted from preview to supported" with multivalued user attributes, User Profile permissions and FGAP in search filters — [Keycloak release notes](https://www.keycloak.org/docs/latest/release_notes/index.html); [Keycloak 26.8.0 released](https://www.keycloak.org/2026/10/keycloak-2680-released)
- Zitadel's SCIM server shipped for testing at v2.69+ (window to 2025-03-31) with "all requests for the user resource and the discovery endpoints"; the guide is still titled "SCIM v2.0 (Preview)" and "only the users schema urn:ietf:params:scim:schemas:core:2.0:User is supported"; endpoints live under `https://${ZITADEL_DOMAIN}/scim/v2/{orgId}` — [Zitadel community announcement](https://questions.zitadel.com/m/1335916973070090413); [Zitadel: SCIM v2.0 (Preview)](https://zitadel.com/docs/guides/manage/user/scim2); [Zitadel SCIM API](https://docs-gkfqter4p-zitadel.vercel.app/docs/apis/scim2)
- Authentik's SCIM provider "can be used to provision and sync users from authentik into other applications" (outbound client); no inbound SCIM server is described — [authentik: SCIM provider](https://docs.goauthentik.io/docs/add-secure-apps/providers/scim/)
- Ory: SCIM is an Enterprise License / Ory Network feature ("SCIM, SAML, organization login") — [ory/kratos README](https://raw.githubusercontent.com/ory/kratos/master/README.md)
- Dex: no SCIM is mentioned anywhere in its README or docs; "Dex acts as a shim between a client app and the upstream identity provider" — [dexidp/dex README](https://raw.githubusercontent.com/dexidp/dex/master/README.md)

### Inferences
- The on-prem single-org install needs SCIM only if the customer's IdP will push; implement it once in the hub (not in the bundled IdP) so the hub owns the user/org tables and can run without an IdP. The surface is small: two resource types, four discovery/meta endpoints, `eq` filter on two attributes, PATCH with case-insensitive ops, integer pagination, `active` soft delete, per-org bearer token (Okta also wants OAuth code grant as an option; Entra wants a long-lived token).
- Tenant isolation at the SCIM layer must come from the token, not the URL: Zitadel puts `{orgId}` in the path, Okta recommends per-tenant subdomains; either works, but the token must be scoped to one organization and SCIM-created users must land as that org's managed members (Keycloak's term) so deprovisioning is bounded.
- "Who pushes" in practice: Entra, Okta, OneLogin, JumpCloud, Rippling via SCIM; Google Workspace needs a pull adapter (or you accept JIT provisioning from SAML/OIDC only). For a small team, SCIM + JIT-on-first-login covers everything except Google group sync.
- If Keycloak 26.8 is bundled, its now-supported SCIM server could be the inbound endpoint, but that puts user truth in Keycloak rather than the hub; only sensible if Keycloak is also the user store for the cloud.

### Gaps
- The Entra incremental-cycle interval (commonly cited as 40 minutes) is not stated on either Microsoft page fetched; the "How provisioning works" page defers to per-app tutorials.
- No source enumerates every IdP that pushes SCIM; the WorkOS list is the closest proxy.
- Whether Keycloak's SCIM API supports Groups PATCH with `members` was not confirmed from the release notes text.

## Key question 4: Service-side authorization for org-scoped data (RBAC with org roles, resource ownership, per-device scopes) and how tokens carry org and user identity (claims, audience, multiple orgs)

### Takeaway
Shipping products put exactly one active organization in a token (`org_id`, plus role/permissions for that org) and switch orgs by re-issuing the token; Keycloak and Zitadel can instead list all memberships in one token. Audience must name the hub's API, and the API must segment every query by the org claim and re-check membership against its own tables rather than trusting token contents alone.

### Cited Findings
- Auth0: ID and access tokens include `org_id`; "By default, ID and access tokens only include organization IDs" (`org_name` is opt-in); a token for a specific org is requested with the `organization` parameter on `/authorize` (or on client-credentials `/oauth/token`); when Organization Roles are used the `permissions` claim reflects "only the roles held within the active Organization for that session"; "Your API servers must also segment access to data and resources based on the `org_id`"; APIs should check `iss` and that `org_id` "is expected", and reject otherwise; org IDs are "the preferred method for validating tokens" over names — [Auth0: Organizations and tokens](https://auth0.com/docs/manage-users/organizations/using-tokens)
- WorkOS AuthKit session JWT claims: `sub`, `sid`, `iss`, `org_id`, `role`, `permissions`; `org_id` is the organization selected at sign-in and `role`/`permissions` apply only when an org is selected; to switch orgs, refresh with `organization_id` and the claims change accordingly; role changes do not appear until refresh; rendered JWT templates are limited to 3072 bytes; for API/M2M tokens WorkOS recommends resolving permissions via API from `sub` and `org_id` rather than trusting claims — [WorkOS: sessions](https://workos.com/docs/authkit/sessions.md); [WorkOS: Connect token claims](https://workos.com/docs/authkit/connect/token-claims.md); [WorkOS: FGA + AuthKit](https://workos.com/docs/fga/authkit-integration.md)
- Zitadel: `urn:zitadel:iam:org:project:roles` is keyed by role then by org id with the org's primary domain as value (e.g. `{"user": {"id1": "acme.zitade.ch", "id2": "caos.ch"}}`), so one token can carry roles across several orgs; `urn:zitadel:iam:user:resourceowner:id/name/primary_domain` identify the user's home org; `aud` "by default all client id's and the project id are included"; scope `urn:zitadel:iam:org:project:id:{projectid}:aud` adds a project to the audience; `urn:zitadel:iam:org:projects:roles` asserts roles for each project in the audience; user metadata is base64 in `urn:zitadel:iam:user:metadata` — [Zitadel: claims](https://zitadel.com/docs/apis/openidoauth/claims); [Zitadel: scopes](https://zitadel.com/docs/apis/openidoauth/scopes)
- Zitadel delegation: an org can grant a project to a partner org, which "can assign roles from a project grant to its own users" — [Zitadel: Organizations](https://zitadel.com/docs/guides/manage/console/organizations)
- Keycloak: `organization` claim keyed by alias; `organization:*` lists all memberships; org groups' realm/client roles can be included in the claim (26.8); org id/attributes are optional mapper switches — [Red Hat build of Keycloak 26.4: Managing organizations](https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/managing_organizations); [Keycloak release notes](https://www.keycloak.org/docs/latest/release_notes/index.html)
- Keycloak 26.8 adds an `act` claim for token-exchange delegation and impersonation ("tokens from impersonation sessions now carry the `act` claim"), and client secret rotation with two active secrets — [Keycloak 26.8.0 released](https://www.keycloak.org/2026/10/keycloak-2680-released)
- RFC 9700: access tokens "SHOULD be audience-restricted to a specific resource server", clients may use RFC 8707 resource indicators, and refresh tokens "MUST be bound to the scope and resource servers as consented" — [RFC 9700 §2.3, §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html)
- WorkOS guidance: do not use email domain as the tenant boundary (guests); validate on organization ID — [WorkOS: add SSO to B2B SaaS with AuthKit](https://workos.com/blog/add-sso-b2b-saas-authkit)
- Tailscale's authorization model binds a per-device node key to a human identity and compiles admin-defined tags and user groups into per-machine packet filters, i.e. authorization is evaluated per device, not only per user — [Tailscale: key management](https://tailscale.com/blog/tailscale-key-management)

### Inferences
- Recommended token contract for the hub: `iss` = the deployment's issuer, `aud` = the hub API identifier, `sub` = stable user id, `org_id` = the single active org, `roles`/`permissions` for that org, `sid` for session revocation, and (if device binding is wanted) a `cnf` (DPoP) or a hub-issued `device_id` claim. Switching org = refresh with an org parameter (WorkOS/Auth0 pattern). This keeps authorization checks O(1) and avoids the Keycloak/Zitadel "all memberships" blob growing with large users.
- Service-side model that matches all three reference products: tables `users`, `organizations`, `memberships(user, org, role)`, `devices(user, org?, public_key/refresh_family, last_seen)`, `resources(org_id owner, created_by)`; every repository query is prefixed by `org_id` from the verified token, and membership is re-read from the DB on sensitive writes (WorkOS's advice for M2M tokens generalises). Resource ownership (creator) is an attribute inside the org, not a parallel authorization axis.
- Per-device scopes: issue each device its own refresh-token family (RFC 9700 rotation already produces one) and record it in `devices`; "sign out device X" = revoke that family; a CLI token can carry narrower scopes than the desktop app (e.g. `sync:read sync:write` but not `org:admin`), which RFC 9700's scope binding of refresh tokens supports.
- On-prem single-org deployments still carry `org_id`; it is just constant. That is cheaper than special-casing.

### Gaps
- No source quantified real-world token size limits beyond WorkOS's 3072-byte template cap; Keycloak `organization:*` size behaviour for users in many orgs is not documented in the material found.
- No engineering write-up from a desktop/CLI product described per-device scopes explicitly; the per-device model is inferred from Tailscale and RFC 9700.

## Key question 5: Operational comparison of bundled IdPs (Keycloak, Zitadel, Ory Kratos+Hydra, Authentik, Dex): footprint, Helm, database, Apple Silicon, licensing, upgrade pain, single-org on-prem vs public cloud

### Takeaway
Keycloak is the most complete (orgs, per-domain SSO, SCIM server, SAML and OIDC both ways) but the heaviest (Java, ~1.25 GB sizing baseline, fails to start under ~768 MB) and its Helm story fractured when Bitnami moved versioned images behind a paywall in 2025; Zitadel is a single Go binary on PostgreSQL only, has orgs and domain discovery, but relicensed to AGPL-3.0 at v3 (2025) and its SCIM is users-only preview; Ory's open-source Kratos/Hydra lack organizations, SAML and SCIM (Enterprise License / Ory Network only); Authentik is MIT-core plus an enterprise directory, Python, PostgreSQL-only since 2025.10, with outbound-only SCIM and no org/tenant concept comparable to Keycloak's; Dex is a stateless Apache-2.0 OIDC broker with no user store, no orgs and no SCIM. All five publish linux/arm64 images.

### Cited Findings

Footprint and sizing
- Single-VPS idle measurement (one source, all containers per stack): Keycloak 539 MiB, authentik 715 MiB, Zitadel 214 MiB, Authelia+LLDAP 70 MiB; "Keycloak's JVM refused to start at 768 MiB", Zitadel and Authelia ran in 768 MiB; authentik was the only one OOM-killed after initially working — [SSD Nodes: Keycloak vs Authentik vs Zitadel on one VPS](https://www.ssdnodes.com/learn/keycloak-vs-authentik-vs-zitadel)
- Other third-party numbers disagree by 2x+ (e.g. ~350 MB Authentik / ~600 MB Keycloak / ~150 MB Zitadel / ~80 MB Kratos alone; elsewhere ~1.5 GB Keycloak) and methodology is unclear — [computingforgeeks comparison](https://computingforgeeks.com/keycloak-vs-authentik-vs-zitadel-vs-authelia/); [devhandbook self-hosted auth showdown](https://devhandbook.io/blog/2026-08-08-self-hosted-auth-sso-showdown/)
- Keycloak official sizing: "The base memory usage for a Pod including caches of Realm data and 10,000 cached sessions is 1250 MB of RAM"; limit ≈ 1360 MB (heap = 70% of limit, ~300 MB non-heap); 1 vCPU per 15 password logins/s, per 120 client-credential grants/s, per 120 refresh requests/s; "Leave 150% extra head-room for CPU"; database: 1400 write IOPS and 0.35–0.7 vCPU per 100 login/logout/refresh requests/s; tests ran on ARM `c7g` and x86 may deliver up to 2x ops per core; example uses 3 pods — [Keycloak: memory and CPU sizing](https://www.keycloak.org/high-availability/multi-cluster/concepts-memory-and-cpu-sizing)
- Zitadel process "needing approximately 512MB of RAM" (vendor guidance cited by a comparison); authentik Docker Compose asks for "at least 2 CPU cores and 2 GB of RAM" and is "intended for test setups and small-scale production setups" — [SSD Nodes comparison](https://www.ssdnodes.com/learn/keycloak-vs-authentik-vs-zitadel); [authentik: Docker Compose install](https://docs.goauthentik.io/docs/install-config/install/docker-compose)

Databases and runtime
- Keycloak: container images moved to OpenJDK 21 in 26.0; 26.6 added Java 25 support; 26.0 made user sessions persisted by default; 26.1 made `jdbc-ping` the default cluster transport; 26.8's multi-cluster v2 (`--features=stateless`) stores "Session data ... in the database" and needs no external Infinispan; login failures now stored in the DB by default — [Red Hat build of Keycloak 26.0 release notes](https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.0/html-single/release_notes); [Keycloak release notes](https://www.keycloak.org/docs/latest/release_notes/index.html); [Keycloak 26.8.0 released](https://www.keycloak.org/2026/10/keycloak-2680-released)
- Zitadel: "PostgreSQL is the default database" and "versions 14 to 18 are supported"; `zitadel init` must run before `start`; CockroachDB support ended with v2 (end of support 2025-09-30), "v3 won't start if CockroachDB is configured", with a `mirror` CLI for migration; Zitadel Cloud itself moved to PostgreSQL citing cost (~3x) and latency — [Zitadel: database](https://zitadel.com/docs/self-hosting/manage/database); [zitadel/zitadel issue 9414](https://github.com/zitadel/zitadel/issues/9414); [Zitadel advisory a10015](https://zitadel.com/docs/support/advisory/a10015); [Zitadel: why we moved from CockroachDB](https://zitadel.com/blog/move-to-postgresql)
- authentik: "in our 2025.10 release, we removed Redis as a required database"; caching, embedded outpost and WebSocket moved to PostgreSQL; TLS to PostgreSQL now requires TLS 1.3 or Extended Master Secret; the blog concedes "PostgreSQL was not built for this; Redis PubSub was purpose built for it" — [authentik blog: We removed Redis](https://goauthentik.io/blog/2025-11-13-we-removed-redis/)
- Dex storage: etcd v3; Kubernetes CRDs ("may not be appropriate for a large number of users"); SQLite3 "is **not** appropriate for real workloads"; Postgres and MySQL (≥5.7) need a dedicated DB because "Dex requires privileged access to its database because it performs migrations" and migrations "do not support rolling back" — [Dex: storage](https://dexidp.io/docs/configuration/storage/)
- Dex capabilities: "an identity service that uses OpenID Connect to drive authentication for other apps"; connectors LDAP, GitHub, SAML 2.0 (stable but "unmaintained and likely vulnerable to auth bypasses"), GitLab, OIDC, Microsoft, Gitea, Google, etc.; refresh tokens and groups depend on the connector (SAML cannot refresh); device flow is a configurable grant type — [dexidp/dex README](https://raw.githubusercontent.com/dexidp/dex/master/README.md); [Dex: OAuth2 configuration](https://dexidp.io/docs/configuration/oauth2/)

Helm and Kubernetes
- Keycloak ships an official Kubernetes Operator but "no separate chart for classic installations"; most people used the Bitnami chart; from 2025-08-28 Bitnami moved most versioned image tags to `docker.io/bitnamilegacy` with no updates, keeping only "latest" free, with a final cutoff of 2025-09-29; alternatives are forking the Bitnami chart or using the Codecentric chart — [bare.id: Bitnami change for Keycloak users](https://www.bare.id/en/blog/bitnami-umstellung-was-keycloak-nutzer-jetzt-wissen-und-tun-mussen); [MOSIP advisory on Bitnami catalog changes](https://community.mosip.io/t/advisory-bitnami-catalog-changes-and-impact-on-mosip-deployments/2311)

### Inferences
- Single-org on-prem: the bundled IdP's job is "accept the customer's existing IdP (OIDC/SAML), optionally accept SCIM, issue tokens to three native clients". Dex does exactly the first and third at the smallest footprint and with an Apache license, but has no users, orgs, invitations or SCIM, so the hub must own all of that anyway. Zitadel and Keycloak do all four but each costs a database and (for Keycloak) >1 GB RAM in a deployment that may otherwise be one small binary and SQLite.
- Public cloud: Keycloak Organizations (26.8) and Zitadel organizations both model N orgs with per-domain SSO natively; Keycloak additionally has a supported SCIM server with Groups while Zitadel's is users-only preview; Keycloak's AGPL-free license is an advantage over Zitadel for a product that embeds and redistributes it on-prem, where AGPL's network clause and "modified code" questions land on the vendor, not the customer.
- Operational risk ranking for a small team: Dex (lowest; stateless, but you build everything) < Zitadel (single Go binary, Postgres only, but AGPL and a v3 break) < Authentik (Python, enterprise split, no inbound SCIM, no org concept) < Keycloak (heaviest, Java, Helm chart churn after the Bitnami paywall, but most features and the broadest enterprise familiarity) ≈ Ory (clean APIs but the needed features are paid).
- Apple Silicon is not a differentiator in 2026: all five publish arm64 images (checked directly). Local dev on M-series Macs via Docker/OrbStack/colima is fine for each.

### Gaps
- No apples-to-apples benchmark includes Ory; Ory stack footprint numbers are single-source and unmeasured.
- Keycloak's and Ory's license texts were not re-fetched in this pass (both are widely documented as Apache 2.0; cite the repositories before publishing).
- Authentik's own documented memory numbers beyond the 2 GB Compose minimum, and whether Authentik has any tenant/organization construct comparable to Keycloak Organizations, were not found.
- The Keycloak SCIM server's Group PATCH semantics and the Zitadel SCIM GA status were not confirmed.

## Key question 6: What a public cloud needs that on-prem does not (self-serve signup, email verification, billing hooks, abuse controls)

### Takeaway
On-prem single-org installs need none of signup, verification, billing or abuse controls because the customer's IdP (or an admin) creates every user; the cloud adds identifier-first self-registration with email verification, a default "catch-all" organization for unmatched domains, event hooks (user/org created, membership changed) feeding billing and provisioning, and layered signup abuse controls (rate limits by IP/device/email domain, disposable-email and MX checks, bot detection, progressive verification).

### Cited Findings
- Keycloak invitation flow for new users "uses self-registration" and binds the registration to the invited email; Keycloak 26.8 added an "Invite-user workflow step" that emails an action-token invitation when a user is created — [Red Hat build of Keycloak 26.4: Managing organizations](https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/managing_organizations); [Keycloak 26.8.0 released](https://www.keycloak.org/2026/10/keycloak-2680-released)
- Zitadel's domain-discovery scenario keeps a default org (named CIAM in the example) with its own login policy where "The default organization will hold all unmatched users"; per-org policies control whether self-registration and username/password are enabled — [Zitadel: Domain discovery](https://zitadel.com/docs/guides/solution-scenarios/domain-discovery)
- WorkOS treats guests (unverified domains) as invite-only and rejects consumer domains for domain claims, so self-serve users on gmail.com-style addresses cannot be routed to an org by domain — [WorkOS: how WorkOS decides organization access](https://workos.com/blog/how-workos-decides-organization-access); [WorkOS: add SSO to B2B SaaS with AuthKit](https://workos.com/blog/add-sso-b2b-saas-authkit)
- Event hooks: Keycloak's Event Listener SPI fires `REGISTER` for self-service registration but not for API-created users (those produce admin events `CREATE`/`USER`), listeners are synchronous, and community webhook extensions post on a background thread — [Keycloak Discourse: REST-created users and REGISTER events](https://keycloak.discourse.group/t/user-creation-through-keycloak-rest-api-doesnt-produce-register-event-for-spi/12333); [dev.to: Keycloak knows, why doesn't the rest of your stack](https://dev.to/mr_buch/keycloak-knows-why-doesnt-the-rest-of-your-stack-4ikj)
- Zitadel Actions v2: "you can modify ZITADEL's behavior on specific API calls, events, or functions"; an Endpoint "can be anything, as long as it can receive an HTTP POST request"; Executions bind to Request, Response, Function or Event conditions (examples: enrich newly created users, "provisioning new users to other systems", notify when a user is locked) — [Zitadel: Actions v2](https://zitadel.com/docs/concepts/features/actions_v2)
- Keycloak 26.8 Shared Signals Framework (experimental) emits `account-disabled` / `account-enabled` events — [Keycloak 26.8.0 released](https://www.keycloak.org/2026/10/keycloak-2680-released)
- Abuse controls: "Layered defences that combine rate limiting, bot management, device signals and adaptive verification are more effective than any single control"; "Per-IP limits are the bare minimum. You also need rate limits by account, device fingerprint, email domain and behavioural session"; check "email age, domain registration recency, and mail exchange (MX) record patterns"; roll out "bot detection, then disposable email blocking, device fingerprinting, and only then progressive verification and payment method requirements" — [Stripe: prevent free-trial abuse](https://stripe.com/de-li/resources/more/how-to-prevent-free-trial-abuse-in-saas-and-ai-products)
- Arcjet's signup protection reference blocks "emails with invalid syntax, that are from disposable email providers, or do not have valid MX records" and uses a 5-per-10-minutes-per-IP rate limit as an example — [Arcjet: signup protection reference](https://docs.arcjet.com/signup-protection/reference); [Arcjet: signup protection concepts](https://docs.arcjet.com/signup-protection/concepts)
- "Rate limiting slows down signups ... but it doesn't catch a bot that signs up with a real, valid email", so pair it with email verification — [emaillistvalidation: stop fake accounts](https://emaillistvalidation.com/blog/stop-fake-accounts-rate-limiting-email-signup-endpoints/)
- RFC 8628 device-flow user codes need rate limiting against brute force and UI copy warning the user they are authorizing a device (remote phishing), which is a cloud-scale concern because anyone can start a device flow against a public issuer — [RFC 8628 §5.1, §5.4](https://www.rfc-editor.org/rfc/rfc8628.html)
- Ory's enterprise feature list names CAPTCHAs as a paid add-on, indicating bot protection on registration is treated as a cloud/commercial feature — [ory/kratos README](https://raw.githubusercontent.com/ory/kratos/master/README.md)

### Inferences
- Cloud-only components to add on top of the shared core: (1) a public registration endpoint behind identifier-first, with email verification and a personal/default org for consumer domains; (2) an outbox of domain events (`user.created`, `org.created`, `membership.changed`, `device.registered`) consumed by billing and audit — whether the IdP is bundled or not, emit these from the hub, since Keycloak's SPI misses API-created users and Zitadel's Actions v2 require per-deployment configuration; (3) signup abuse middleware (IP/device/email-domain rate limits, disposable/MX checks, bot detection) in front of registration and the device-code verification page; (4) org-level quotas and seat counts that billing reads from `memberships`.
- On-prem single-org: disable public registration, treat SCIM/JIT as the only user sources, and ship no billing or abuse middleware; keep the same event outbox so the customer can wire audit/SIEM to it.
- Email verification in the cloud should be enforced before a user can be auto-joined to any org by domain; WorkOS and Keycloak both key access on the email, and an unverified address would otherwise let anyone claim membership in an org whose domain matches.

### Gaps
- No Auth0 Attack Protection documentation was retrieved; its brute-force, suspicious-IP, breached-password and bot-detection feature specifics are not cited here.
- No primary source describes a concrete billing-webhook design (e.g. Stripe seat sync) for a multi-tenant hub; the inference is from the event-hook capabilities of Keycloak and Zitadel.

## Key question 7 (synthesis): Bundle an open-source IdP on-prem versus build in-house — recommendation for a small team

### Takeaway
Build the organization/membership/invitation/device/SCIM layer in the hub (it is small, it must exist for the cloud anyway, and every bundled IdP would otherwise force the hub to mirror it), and bundle a thin standards-only authorization server for the protocol surface. For a small team shipping three native clients, the lowest-risk 2026 choice is: own the user/org model and token issuance contract in the hub; delegate OIDC/SAML brokering to Dex (on-prem default, zero state beyond a Postgres/SQLite table) or to Keycloak 26.8 when a customer needs Keycloak-grade SAML, SCIM-into-the-IdP, or admin UI; avoid Zitadel for redistribution unless AGPL is acceptable; treat Ory and Authentik as non-starters for per-org SSO without paid terms.

### Cited Findings
- Dex is an OIDC "shim between a client app and the upstream identity provider" with connectors for LDAP, SAML, OIDC, GitHub, Microsoft, Google etc., Apache 2.0, device flow configurable, no user store — [dexidp/dex README](https://raw.githubusercontent.com/dexidp/dex/master/README.md); [Dex: OAuth2 configuration](https://dexidp.io/docs/configuration/oauth2/)
- Dex's SAML connector is flagged "unmaintained and likely vulnerable to auth bypasses" and SAML logins get no refresh tokens — [dexidp/dex README](https://raw.githubusercontent.com/dexidp/dex/master/README.md)
- Keycloak 26.8 is the only free self-hosted option in this set with supported Organizations (per-domain IdP routing, invitations, managed members, org claim), a supported SCIM server, multi-cluster without Infinispan, and arm64 images — [Keycloak 26.8.0 released](https://www.keycloak.org/2026/10/keycloak-2680-released); [quay.io keycloak/keycloak](https://quay.io/repository/keycloak/keycloak)
- Keycloak's baseline is 1250 MB RAM per pod and it would not start at 768 MB in a third-party test — [Keycloak: memory and CPU sizing](https://www.keycloak.org/high-availability/multi-cluster/concepts-memory-and-cpu-sizing); [SSD Nodes comparison](https://www.ssdnodes.com/learn/keycloak-vs-authentik-vs-zitadel)
- Zitadel: organizations and domain discovery in the free build, ~214 MiB idle, PostgreSQL-only, AGPL-3.0 since v3 with a commercial license offered for AGPL-incompatible projects — [Zitadel: Domain discovery](https://zitadel.com/docs/guides/solution-scenarios/domain-discovery); [SSD Nodes comparison](https://www.ssdnodes.com/learn/keycloak-vs-authentik-vs-zitadel); [Zitadel license FAQ](https://zitadel.com/license-faq)
- Ory: organizations, SAML, SCIM are Enterprise License / Ory Network features — [ory/kratos README](https://raw.githubusercontent.com/ory/kratos/master/README.md); [Ory: Organizations](https://www.ory.com/docs/kratos/organizations)
- Authentik: enterprise directory under a separate license, outbound-only SCIM, 2 GB RAM minimum for Compose — [goauthentik/authentik LICENSE](https://github.com/goauthentik/authentik/blob/main/LICENSE); [authentik: SCIM provider](https://docs.goauthentik.io/docs/add-secure-apps/providers/scim/); [authentik: Docker Compose install](https://docs.goauthentik.io/docs/install-config/install/docker-compose)
- WorkOS, Auth0 and Ory all put the tenant model (orgs, domains, invitations, roles) in their own product and expose SSO connections as a per-org attribute; none delegate the org model to the customer's IdP — [WorkOS: how WorkOS decides organization access](https://workos.com/blog/how-workos-decides-organization-access); [Auth0: Organizations and tokens](https://auth0.com/docs/manage-users/organizations/using-tokens); [Ory: Organizations](https://www.ory.com/docs/kratos/organizations)

### Inferences
- What must be in-house regardless: organizations, domains, memberships/roles, invitations, devices and refresh-token families, SCIM endpoint, event outbox, and the token contract (`org_id`, `aud`, `sid`). Every product surveyed keeps this in the product, and the hub's authorization model (Key question 4) needs these tables locally for every query.
- What is worth bundling: the protocol-facing authorization server (OIDC provider with PKCE, device grant, refresh rotation, JWKS; OIDC and SAML brokering to the customer's IdP). Writing a correct SAML SP and an OIDC AS with device flow and rotation is the part where a small team loses months and takes on security review burden.
- Decision rule: default on-prem bundle = the smallest component that brokers OIDC/SAML and issues tokens (Dex, or Hydra+a tiny login UI if SAML is not needed) with the hub as its "connector" of record; offer Keycloak as the alternative image for customers who already standardise on it or need SCIM-into-Keycloak. For the public cloud, run the same hub with either Keycloak Organizations or a hub-native broker; do not expose the bundled IdP's admin UI to tenants.
- Avoid: Zitadel for redistribution unless legal clears AGPL or buys the commercial license; Authentik for per-org SSO (no org model, inbound SCIM absent); Ory open source for B2B (features paid).
- Risk to the Dex-default path: Dex's SAML connector maintenance status; if SAML matters at launch, bundle Keycloak instead or put a maintained SAML library in the hub.

### Gaps
- No source compares total engineering effort of "build the AS in-house" against bundling; the recommendation is a judgement from the feature/licensing/footprint facts above.
- Hydra+Kratos as a composed open-source AS without organizations was not evaluated in depth (only licensing and feature gating were verified).
- No vendor publishes a Swift-native OIDC AS; a hub-native authorization server would be custom code.
