# How comparable developer tools sync sessions, conversations, and settings across devices (2025–2026 state)

Scope: Cursor, Zed, Warp, Linear, Obsidian Sync, Raycast, JetBrains (Backup and Sync / Toolbox), VS Code Settings Sync, GitHub Copilot (VS Code + CLI), Codex, Claude Code, Ghostty, Tailscale. Researched 2026-10-31. Everything below is from public documentation, changelogs, issue trackers, and forums; third-party or community sources are labelled as such. Items marked "(older)" predate 2025 and may have changed.

## Key question 1: Which products sync conversation/session content versus only metadata, and how they treat large tool outputs and secrets

### Takeaway
As of late 2026 there are three distinct tiers: (a) tools that upload full transcripts (Claude Code Remote Control, Warp cloud conversations and session sharing, Cursor cloud agents, Raycast AI chat history, GitHub Copilot session sync); (b) tools that sync settings/config only and keep conversations machine-local (VS Code Settings Sync, JetBrains Backup and Sync, Raycast non-AI categories, Warp Settings Sync); and (c) tools with no first-party sync at all (Cursor IDE settings and chat history, Zed settings and agent threads, Ghostty, Codex CLI local sessions). Secret handling is explicit only in a few places: Raycast ("never synced"), Copilot (pattern-based filtering that "might not detect every secret"), Cursor cloud agents (runtime secrets stripped from transcripts), Claude Code cloud bundles (credential-like files left out), and Warp (secret redaction explicitly *not* applied to session sharing).

### Cited Findings

**Claude Code (Anthropic)**
- Local CLI sessions are stored as JSONL at `~/.claude/projects/<project>/<session-id>.jsonl`; "Each line is a JSON object: a message, a tool use or result, a record of a request Claude Code sent the model, or a metadata entry." Default retention is 30 days (`cleanupPeriodDays`); the desktop app, claude.ai/code, and the VS Code extension "each keep their own session list." — [Claude Code: Manage sessions](https://code.claude.com/docs/en/sessions.md)
- Local sessions are not uploaded by default. Only while Remote Control is connected is "the session transcript, including your messages, Claude's responses, and tool activity, ... stored on Anthropic servers. The stored transcript keeps the conversation in sync across your devices and lets the session reconnect after a network drop." — [Claude Code: Remote Control](https://code.claude.com/docs/en/remote-control)
- Remote Control is unavailable to orgs with Zero Data Retention or the HIPAA configuration; `disableRemoteControl` turns it off entirely. — [Claude Code: Remote Control](https://code.claude.com/docs/en/remote-control)
- When `claude --cloud` must upload a local repo bundle (no GitHub remote), on macOS/Linux/WSL it "leaves uncommitted changes to files named like credentials or keys out of the upload. This includes `.env` files, Terraform `*.tfvars` files, and key files such as `id_rsa` and `*.pem`"; on native Windows "uncommitted changes to tracked files upload as they are." Bundles are capped at 100 MB. — [Claude Code: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web.md)
- In cloud sessions, "your GitHub credentials stay encrypted on Anthropic's servers and never enter a session's VM"; git operations go through a server-side proxy. — [Claude Code: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web.md)

**Warp**
- Agent conversations sync to the cloud only when Settings > Privacy > "Store AI conversations in the cloud" is on; with it off they are "stored locally on your machine only." "Your conversations are always preserved locally on your machine." Each sync "stores a snapshot of conversation state." Cloud-agent conversations are always cloud-stored regardless. Free-plan users hitting storage limits have oldest cloud conversations removed automatically. The page does not say whether terminal/tool output is included. — [Warp: Cloud conversations](https://docs.warp.dev/agents/local-agents/cloud-conversations.md)
- Settings Sync (Beta) syncs "the state of most of your Warp settings to our cloud servers" (themes, most features, privacy settings, AI settings) but not custom keybindings, custom themes, or device-specific settings such as preferred editor or startup shell; platform-specific settings sync only among same-platform devices; non-synced settings show a cloud-strikethrough icon. — [Warp: Settings Sync](https://docs.warp.dev/terminal/more-features/settings-sync)
- Session sharing uploads "the session's scrollback and live output to Warp's servers"; agent activity shared can include "prompts, responses, thinking states, tool use, planning steps, terminal output, and follow-up messages." "Secret Redaction isn't applied to Session Sharing." Shared data expires about one week after creation. — [Warp: Agent session sharing](https://docs.warp.dev/agent-platform/local-agents/session-sharing/)
- Warp's configurable Secret Redaction "is disabled by default"; when enabled it masks matching content before AI requests. Telemetry payloads are redacted with built-in patterns regardless. "Telemetry must be enabled to use AI features on the Free plan." — [Warp: Privacy](https://docs.warp.dev/privacy/privacy)

**Cursor**
- The IDE has no first-party settings sync or chat-history sync. The forum thread "Sync of keybindings and settings" (141 replies, still active June 2026) and "We need ability to sync settings between devices" (March 4, 2026) are open feature requests with no staff reply on the latter; related threads from Aug 2026 ask the same. — [Cursor forum: We need ability to sync settings between devices](https://forum.cursor.com/t/we-need-ability-to-sync-settings-between-devices/153503); [Cursor forum: Sync of keybindings and settings](https://forum.cursor.com/t/sync-of-keybindings-and-settings/31)
- Cloud Agents store conversation state (prompts, responses, tool calls, diffs) "in Cursor's backend, encrypted with per-agent keys," "Kept indefinitely by default," deletable via the Delete Agent API; VM snapshots are encrypted and retained on a "Rolling 30 days of inactivity." "Runtime Secrets" are "stripped from the transcript, tool output, and commits, and never reach the model." — [Cursor: Cloud agent security overview](https://cursor.com/docs/cloud-agent/security)
- "Move to Cloud" from a local agent "does not snapshot your local uncommitted changes"; it transfers conversation history and context only. — [Cursor help: Cloud Agents](https://cursor.com/help/ai-features/cloud-agents)
- Cursor "temporarily caches file contents on its servers to reduce latency and network usage. The files are encrypted using unique client-generated keys," which exist on servers only for the request duration. — [Cursor: Data use & privacy overview](https://cursor.com/data-use)
- Third-party CLIs exist to copy Cursor chat history between machines (community, March 2026). — [Neura Market / dev.to repost](https://www.neura.market/directories/cursor/blog/devto-3308580)

**Zed**
- No built-in settings sync; the long-standing community request "Inbuilt synchronisation support" remains the reference issue. Workarounds: keep `~/.config/zed/settings.json` and `keymap.json` in git plus `auto_install_extensions`; or the community `zed-settings-sync` extension that pushes user config to a GitHub Gist. — [zed-industries/community issue 952](https://github.com/zed-industries/community/issues/952); [vittorius/zed-settings-sync](https://awesome.ecosyste.ms/projects/github.com%2Fvittorius%2Fzed-settings-sync); [roboin.io guide (Nov 2025)](https://roboin.io/article/2025/11/13/how-to-sync-settings-and-extensions-in-zed-editor)
- Agent threads are stored locally in a SQLite file `threads.db` (`~/.local/share/zed/threads/threads.db` on Linux; under Application Support on macOS), each thread as a compressed JSON blob (third-party tool description). — [zed-context-manipulator (PyPI)](https://pypi.org/project/zed-context-manipulator/)
- "Zed does not retain your prompts or code context by default"; AI data is retained only on explicit feedback or opt-in to training data. Rated feedback "can send a conversation thread to Zed for review and improvement." — [Zed: AI privacy and security](https://zed.dev/docs/ai/privacy-and-security.md)
- Zed's commit history shows thread history previously did not even sync between two open windows on the same machine (each Agent panel had its own `ThreadStore`); fixed for the native agent's history list only. — [Zed commit 081bb237 (mirror)](https://git.secluded.site/zed/commit/081bb237f432a02bcfb24a2b6a5ba2d81fdcee82)

**VS Code Settings Sync**
- Syncs Settings (excluding `machine` / `machine-overridable` scope), Keyboard Shortcuts (per-OS by default), Snippets, user Tasks, MCP Servers (user-profile configs), UI State, Extensions (and global enable/disable state), up to 20 Profiles, and "Prompts and Instructions." Not synced: workspace tasks and extensions in remote windows (SSH, devcontainers, WSL). Size limits: settings, keybindings, and tasks each ≤100 KB; exceeding a limit disables that category. — [VS Code: Settings Sync](https://code.visualstudio.com/docs/configure/settings-sync.md)

**GitHub Copilot (VS Code + CLI)**
- Session sync (VS Code 1.123-era docs) syncs "Session metadata: repository, branch, working directory, timestamps, and the agent or participant," conversation turns, file paths touched, and PR/issue/commit references to the user's personal GitHub account; stored locally in SQLite. Before syncing, VS Code filters detected secrets by "known patterns and secret values" but "might not detect every secret." `chat.sessionSync.excludeRepositories` blocks sessions by `owner/repo` glob. The page does not state whether full tool outputs are synced. — [VS Code: Sync and query session history](https://code.visualstudio.com/docs/agents/run/sessions/session-history.md)
- Copilot CLI stores sessions under `~/.copilot/session-state/` with index `~/.copilot/session-store.db`, and "by default syncs sessions to your GitHub account"; `/chronicle reindex` rebuilds the store and re-pushes. Deleting local files does not delete synced copies, and synced data cannot be deleted locally. — [GitHub Docs: Using Copilot CLI session data](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/chronicle)
- Before this shipped, Copilot CLI issue #1947 (opened March 10, 2026) described sessions as "stored locally in `~/.copilot/` and tied to the machine that created them"; `/resume` worked only on the same machine. Closed as completed August 4, 2026 citing v1.0.24: sessions "can now be exported privately to GitHub, resumed from a fresh install, shared with controlled visibility, and deleted remotely." — [github/copilot-cli issue 1947](https://github.com/github/copilot-cli/issues/1947)
- Older (pre-2026) Copilot Chat history "is stored locally on each device"; community discussion requesting export/sync. — [GitHub community discussion 159535](https://github.com/orgs/community/discussions/159535)

**Codex (OpenAI)**
- Local CLI state: JSONL rollout files under `~/.codex/sessions/YYYY/MM/DD/` (`.jsonl.zst`) as "the source of truth for replay," plus a SQLite index `state_5.sqlite`; all surfaces attach to one local App Server that owns thread lifecycle. The article does not establish any cloud upload of local sessions (third-party knowledge base, April 2026, updated Oct 2026). — [Daniel Vaughan: Cross-surface session sync](https://codex.danielvaughan.com/2026/04/08/cross-surface-session-sync/)
- A community discussion (June 14, 2026) states "an official cross-device/session-sync story does not exist yet" and offers a `.codexbundle` export/import tool, warning bundles "may contain prompts, code, terminal output, absolute paths, and secrets." No OpenAI reply. — [openai/codex discussion 28140](https://github.com/openai/codex/discussions/28140)
- Official help: "Codex desktop tasks do not appear on web; use the Remote tab in the ChatGPT mobile app to access supported remote tasks," and remote tasks "don't get added to web or mobile chat history." — [OpenAI Help: ChatGPT Work and Codex](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex)
- Newer official docs describe an opt-in sync for local-computer tasks: "Syncing a conversation doesn't upload the entire local folder or make it available to another computer"; "Existing tasks, including those in projects, stay local only or in the cloud without access to local files"; "ChatGPT chats don't appear in the Codex sidebar." — [learn.chatgpt.com: Projects and chats](https://learn.chatgpt.com/docs/projects)

**Raycast**
- Cloud Sync (Pro feature; public beta July 16, 2026 for Mac/Windows, v2 on iOS Oct 12, 2026) syncs AI Commands & Agents, AI Chat History (separately toggleable), MCP Servers, Quicklinks, Notes, Snippets, Themes, Transcription Styles, Window Management Layouts, extensions (must be enabled per device), and some General Settings; "Root Search Ranking" and some General Settings are always synced. Not synced: Clipboard History, Script Command scripts, Screenshots, Search History, device-specific settings. "Credentials and passwords are never synced." — [Raycast Manual: Cloud Sync](https://manual.raycast.com/cloud-sync.md); [Raycast changelog v0.69](https://www.raycast.com/changelog/macos/0-69); [Raycast changelog iOS 1.4.0](https://www.raycast.com/changelog/ios/1-4-0)
- (older) Clipboard History excluded by design "to ensure sensitive information stays on your Mac." — [Raycast blog: Introducing Raycast Pro](https://raycast.com/blog/introducing-raycast-pro)

**JetBrains Backup and Sync**
- Syncs UI (appearance, menus, fonts, color scheme), Code (editor, code style, live templates, inlay hints), Tools (VCS, debugger, database, shared indexes), System (date formats, server certificates, registry keys) categories; plugin enable/disable state and installation are propagated across IDEs with specific rules (a plugin uninstalled on one IDE is disabled, not uninstalled, on the other). Data "is stored under JetBrains Account." — [JetBrains Help: IDE settings backup and sync](https://www.jetbrains.com/help/idea/sharing-your-ide-settings.html)
- JetBrains AI chat history sync was not found in official docs (gap below).

**Obsidian Sync**
- Syncs vault files plus optional "Vault configuration" categories: "Main settings," "Appearance," "Themes and snippets," "Hotkeys," "Active core plugin list," "Core plugin settings," and (off by default) "Active community plugin list" and "Installed community plugin list." Image/audio/video/PDF are selectively synced by default; hidden dot-items are excluded except `.obsidian`. File size limits: 5 MB (Standard) / 200 MB (Plus). — [Obsidian Help: Sync settings and selective syncing](https://obsidian.md/help/sync/settings)

**Linear**
- Linear is a server-authoritative sync engine, not a settings-sync tool: the client holds "a subset of the server database" in IndexedDB per workspace; local edits are applied in memory, queued as transactions, and local tables change only after server delta packets arrive. (Community reverse engineering, endorsed by Linear's CTO: "This is a pretty awesome (and correct) write-up of our sync engine.") — [wzhudev/reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine)

**Ghostty**
- Configuration is file-based only ("Presently, the text-based configuration is the only way to configure Ghostty"); `config-file` includes with a `?` prefix are "particularly useful for platform-specific or machine-specific configuration files." No sync, cloud, or account feature is documented. — [Ghostty docs: Configuration](https://ghostty.org/docs/config)

### Inferences
- The products that sync conversations all do so because the conversation must live on a server for a secondary device to render it; none of them describe a peer-to-peer or E2EE transcript channel. The common pattern is "server holds the transcript as the hub; the executing machine is a client" (Claude Code Remote Control, Copilot remote control, Warp remote control).
- Large tool output handling is almost never documented. Only Warp (scrollback upload, one-week expiry), Claude Code (compaction summaries do not carry original messages to a teleported terminal), and VS Code size caps for *settings* give any hint. Treat per-item size limits as an unaddressed design space.
- Secret handling splits into "prevent upload" (Raycast, Claude Code bundles, Cursor runtime secrets) versus "best-effort pattern scrubbing" (Copilot) versus "explicitly not protected" (Warp session sharing). A design that stores secrets by reference only, as this project's `SecretStore` does, is stricter than any surveyed product.

### Gaps
- No official source states whether Warp cloud conversations include terminal/tool output bodies, or any per-conversation size cap.
- Cursor's local chat-history storage format and whether Privacy Mode (Legacy) still exists as a selectable option in 2026 were not confirmed from official docs; the Legacy description comes from a support email quoted on the forum (~2025). — [Cursor forum: Privacy Mode with storage vs legacy](https://forum.cursor.com/t/details-on-privacy-mode-with-storage-how-its-different-than-privacy-mode-legacy/108044)
- Whether JetBrains AI Assistant chat history syncs through Backup and Sync was not found.
- Whether Codex's newer "sync local-computer tasks" option uploads transcripts to OpenAI servers, and its retention, is not stated on the pages retrieved.

## Key question 2: How devices appear to the user (device list, naming, revoking a device, per-device keys)

### Takeaway
Only Raycast, VS Code, Tailscale, Linear (sessions), and Claude Code (Trusted Devices) expose a first-class device list with rename and revoke. Obsidian has device *names* for logs but no server-side device list beyond "Log out everywhere." Most sync services identify devices implicitly through the account session, and only Tailscale and Claude Code Trusted Devices use per-device cryptographic keys.

### Cited Findings
- **Raycast**: the Synced Devices screen "lists each device with its platform, app version, and last sync time"; devices can be renamed; "Removing a device stops its syncing and revokes access. It clears that device's synced state, but its local data remains." The current device is marked "This Device," listed first, and cannot be removed; all v1 and iOS devices appear as one "Legacy Raycast & iOS Devices" entry that cannot be managed individually. A Danger Zone action "Delete Cloud Sync Data & Devices" removes all server data and disconnects devices. — [Raycast Manual: Cloud Sync](https://manual.raycast.com/cloud-sync.md)
- **VS Code**: Settings Sync: Show Synced Data > Synced Machines lists machines; default names combine OS with Stable/Insiders; machines can be renamed; removal is done via a per-machine action that turns off Settings Sync remotely. Remote backups keep "the latest 20 versions of each data category"; local backups are deleted after 30 days. — [VS Code: Settings Sync](https://code.visualstudio.com/docs/configure/settings-sync.md)
- **Claude Code**: Remote Control session names default to `<hostname>-<adjective>-<animal>` (e.g. `myhost-graceful-unicorn`), overridable with `--name` or `--remote-control-session-name-prefix`; renaming from claude.ai also renames the CLI session. Trusted Devices (beta) ties access to "a known device and a recent authentication, not just a signed-in account"; "Only the device's public key and basic metadata such as display name, platform, and enrollment time are stored"; the account page lists "every enrolled device with its name, platform, and enrollment date. Removing a device revokes its credential immediately"; credentials expire on their own if unused; re-auth prompt after 18 hours. Transport uses "multiple short-lived credentials, each scoped to a single purpose and expiring independently." — [Claude Code: Remote Control](https://code.claude.com/docs/en/remote-control)
- **Tailscale**: machine names are generated from the OS hostname, uniqueness is enforced per tailnet with `-1` suffixes, and renaming is done in the admin console ("Edit machine name") or `tailscale set --hostname=`; while "Auto-generate from OS hostname" is checked the name follows hostname changes; renaming also changes the MagicDNS name. — [Tailscale KB: Machine names](https://tailscale.com/kb/1098/machine-names)
- **Tailscale** node keys: "a public/private key pair generated on a node by a Tailscale client"; keys expire by default after 180 days (admin-configurable 1–180 days), per-device "Disable Key Expiry," tagged devices default to no expiry, "Temporarily extend key" gives 30 minutes; when expired, "Connections to and from the endpoint stop working." — [Tailscale KB: Key expiry](https://tailscale.com/kb/1028/key-expiry)
- **Tailscale** device approval: new devices show "Needs approval" at the top of the Machines page and "cannot send or receive traffic" until approved; pre-approved auth keys skip this; revoke via API `{"authorized": false}`; webhook `nodeNeedsApproval` enables posture-check automation. — [Tailscale KB: Device approval](https://tailscale.com/kb/1099/device-approval)
- **Tailscale** Tailnet Lock: "All new node keys must be signed by an existing Tailnet Lock key"; protects "even if Tailscale were malicious or Tailscale infrastructure hacked"; max 20 signing nodes; disablement secrets issued once at init; mutually exclusive with device approval. — [Tailscale KB: Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock)
- **Linear**: Security & Access shows "your current session along with a list of other active sessions, with the location and date last seen for each"; individual revoke or "Revoke all"; "Inactive sessions will be automatically expired after 30 days." — [Linear Docs: Security & Access](https://linear.app/docs/security-and-access)
- **Obsidian**: a device name is set per device "to make reading your Sync logs easier"; device name, conflict resolution, and selective sync are device-specific and "Sync settings do not sync across devices." — [Obsidian Help: Set up Obsidian Sync](https://obsidian.md/help/sync/setup); [Obsidian Help: Sync settings](https://obsidian.md/help/sync/settings)
- **Obsidian** lost device: there is no per-device revoke; forum guidance is the account's "Log out everywhere," noting files stay on the lost device and "there is no way to wipe them from our end." (Community.) — [Obsidian forum: remove sync from lost device](https://forum.obsidian.md/t/how-to-remove-sync-from-lost-device/107764)
- **Warp**: no device list is documented; Settings Sync's "last device you enabled it on" semantics are the only device-aware behaviour. — [Warp: Settings Sync](https://docs.warp.dev/terminal/more-features/settings-sync)
- **JetBrains**: no device list; sync is per JetBrains Account, with "Remove data from JB account and disable for all IDEs" as the global reset. — [JetBrains Help: IDE settings backup and sync](https://www.jetbrains.com/help/idea/sharing-your-ide-settings.html)
- **GitHub Copilot**: no device list for session sync; the October 2026 cloud experience lets you "register a local device as an environment through GitHub Mission Control" (and `--environment-host` for self-hosted). — [GitHub Changelog 2026-10-28](https://github.blog/changelog/2026-10-28-work-from-anywhere-with-a-new-connected-copilot-cloud-experience/)

### Inferences
- Hostname-derived default names with a uniqueness suffix (Tailscale) or a hostname prefix plus random words (Claude Code) are the two de facto conventions; both let the user rename later and both treat rename as cosmetic except where the name is also an address (MagicDNS).
- Per-device keys only appear where the device is a security principal (Tailscale nodes, Claude Trusted Devices). Pure settings-sync products treat the account token as the only credential, which is why their "revoke" is really "sign that machine out."

### Gaps
- Cursor, Zed, Ghostty, and Codex have no documented device list at all; nothing to report.
- Raycast's docs do not say what identifier a device is keyed on (hardware ID vs. install ID), so behaviour after an OS reinstall is unknown.

## Key question 3: How a thread bound to one machine (local shell, local repo) is represented on other devices

### Takeaway
The 2026 consensus for agent sessions is "window into the running process": the originating machine must stay online, remote surfaces can steer it live, and if the process dies the remote view becomes a stale transcript until the same machine resumes it (Claude Code Remote Control, Copilot remote control, Warp remote control/session sharing, Codex Remote tab). Hand-over to a different machine exists only via git: Claude Code `--teleport` and Cursor "Move to Cloud" copy the conversation and check out the branch, leaving the original and the copy as independent forks. No surveyed product transparently migrates a live shell.

### Cited Findings
- **Claude Code Remote Control**: "The web and mobile interfaces are a window into that local session, so your computer has to stay on and the `claude` process has to keep running." Sessions "show a computer icon with a green status dot when online." If the process stops, "the session goes offline until you bring it back"; `claude remote-control --continue` / `--session-id` work "for about four hours after the server stopped." Resuming the same conversation in a second terminal prints "Remote Control not started here" rather than stealing the session; `/remote-control` in the second terminal moves it. Switching conversations with `/resume` means "the connected device doesn't receive the switched-to conversation's title or earlier history." Local-only commands (`/plugin`, `/resume`) do not work from the phone. — [Claude Code: Remote Control](https://code.claude.com/docs/en/remote-control)
- **Claude Code cloud ↔ terminal**: "From the CLI, session handoff is one-way: you can pull cloud sessions into your terminal with `--teleport`, but you can't push an existing terminal session to the cloud." Teleport requires clean git state, the same repository (not a fork), the branch pushed, and the same account; "The terminal gets its own copy of the session: new work there stays local and doesn't appear in the cloud session." Compacted messages are not copied. The Desktop app can send a local Code-tab session to the cloud via "Open in." — [Claude Code: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web.md)
- **GitHub Copilot CLI**: "Synced sessions are read-only on GitHub.com and GitHub Mobile. To steer a session remotely, you must enable remote control." "The CLI session must be actively running in a terminal on a machine with an internet connection"; if the machine sleeps, "remote control is unavailable until the machine is back online"; `/keep-alive` prevents sleep. Both local and remote stay active and "the first response to a prompt or permission request is the one Copilot uses." Session events are sent to GitHub and the CLI polls for commands. — [GitHub Docs: About remote control](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-remote-control); [GitHub Docs: Steering a Copilot CLI session from another device](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/steer-remotely)
- **GitHub Copilot cloud (Oct 28, 2026)**: cloud sandboxes save a snapshot on shutdown "so a session can resume later from any surface"; "every surface shows the same session list." — [GitHub Changelog 2026-10-28](https://github.blog/changelog/2026-10-28-work-from-anywhere-with-a-new-connected-copilot-cloud-experience/)
- **Warp**: opening the same cloud conversation on two machines "creates independent branches. Changes don't sync between them in real time"; continuing someone else's shared conversation forks it. — [Warp: Cloud conversations](https://docs.warp.dev/agents/local-agents/cloud-conversations.md). Remote Control for third-party agents (Claude Code, Codex, OpenCode) "uploads the session state to the cloud"; viewers get view or edit access (send input, approve commands); "Syncing stops when you close the session or stop publishing it." — [Warp: Remote Control](https://docs.warp.dev/agent-platform/cli-agents/remote-control/)
- **Cursor**: "Move to Cloud" transfers conversation and context but "does not snapshot your local uncommitted changes." — [Cursor help: Cloud Agents](https://cursor.com/help/ai-features/cloud-agents)
- **Codex**: on mobile, the Remote tab reaches "supported desktop Codex tasks"; "Desktop Work threads and local files stay on that computer." — [OpenAI Help: ChatGPT Work and Codex](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex). The May 2026 mobile preview says "the machine's files and credentials stay local, while updates flow back to your phone in real time, including screenshots, terminal output, diffs, test results, and approvals." — [OpenAI blog: Work with Codex from anywhere](https://openai.com/blog/work-with-codex-from-anywhere). If the computer is unavailable, an eligible task "can continue in a cloud container" that "can't reach your files or tools," and "Work can't switch from local to cloud execution during a turn." — [learn.chatgpt.com: Projects and chats](https://learn.chatgpt.com/docs/projects). User reports: mobile thread lists lag the desktop sidebar, and CLI sessions are "not surfaced in Codex desktop history the same way" (community). — [openai/codex issue 23152](https://github.com/openai/codex/issues/23152); [openai/codex issue 10547](https://github.com/openai/codex/issues/10547)
- **Zed**: remote projects run a headless server over SSH; the local UI persists unsaved changes locally and reconnects to the existing daemon; "The original remote mode that routed traffic through Zed's servers is no longer available as of v0.157." Remote hosts are declared in `ssh_connections` with `nickname`. Collaboration channels share a *project*, and "Sharing a project gives collaborators access to your local file system within that project." — [Zed: Remote development](https://zed.dev/docs/remote-development.md); [Zed: Collaboration overview](https://zed.dev/docs/collaboration/overview.md)
- **Linear** has no machine-bound threads; every client is a replica of the server. — [wzhudev/reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine)

### Inferences
- Three representations recur and are worth naming for a design doc: (1) *live window* (process online, remote can steer; offline → greyed/stale), (2) *read-only mirror* (Copilot default, Claude archived sessions), (3) *fork-on-handover* (teleport, Move to Cloud, Warp branches). None offers true migration of a running shell; all require either git as the carrier of state or a cloud VM as the new host.
- Status indication is binary (online dot vs. offline) in every product; none shows "last seen on host X" richer than that except Linear's session list.

### Gaps
- No product documents what happens to pending permission prompts when the originating machine disconnects mid-prompt (Copilot says first responder wins while both are online; nothing on disconnect).
- How Warp represents a cloud conversation whose originating machine is offline (beyond "branches") is not documented.

## Key question 4: Encryption choices (Obsidian E2EE, Warp and Cursor privacy modes, Linear's model)

### Takeaway
Obsidian Sync is the only surveyed service offering true end-to-end encryption (default, scrypt + AES-256-GCM, server sees only routing metadata); everyone else encrypts in transit and at rest with provider-held keys and offers "privacy" as a policy (no training, zero-data-retention with model vendors, admin lockdown) rather than cryptography. Cursor and Claude Code add per-object or client-generated keys for specific artifacts; Tailscale Tailnet Lock is the only control-plane-distrust mechanism.

### Cited Findings
- **Obsidian**: E2EE is the default; standard encryption lets Obsidian hold the key. Key derivation "scrypt with salt," cipher "AES-256 in Galois/Counter Mode (GCM)." Not E2EE: "Which device uploaded or deleted a file, and when" and "the mapping between encrypted file paths and encrypted content," used "to route changes, track per-file version history, and keep devices in sync." Deterministic hashing enables dedup but lets a compromised server test whether a chosen file matches a prior upload. Lost password = data "encrypted and unusable forever." Servers on DigitalOcean in Singapore, Frankfurt, San Francisco, Sydney. "Obsidian doesn't encrypt your local vault." — [Obsidian Help: Security and privacy](https://obsidian.md/help/sync/security)
- Obsidian publishes a self-verification procedure for E2EE. — [Obsidian blog: Verify Sync encryption](https://obsidian.md/blog/verify-obsidian-sync-encryption/). A forum post argues the published procedure verifies only part of the scheme because account-auth hashing is undocumented (community, unverified). — [Obsidian forum: Incomplete E2E verification](https://forum.obsidian.md/t/security-issue-incomplete-e2e-encryption-verification/102387)
- Headless Sync (CLI, open beta) uses the same encryption; "Don't use both the desktop app Sync and Headless Sync on the same device, as it can cause data conflicts." — [Obsidian Help: Headless Sync](https://obsidian.md/help/sync/headless)
- **Warp**: no E2EE; "you own your data that is securely stored on Google Cloud Platform servers by Warp." Privacy is tiered: telemetry must be on for Free-plan AI; paid plans can disable telemetry; "Business and Enterprise plans are covered by our Zero Data Retention (ZDR) agreement" ("No AI interaction or console data is ever collected"). Requests carry an `X-Warp-Telemetry-Enabled` header. Client is AGPL v3. — [Warp: Secure by design](https://www.warp.dev/legal/security); [Warp: Privacy](https://docs.warp.dev/privacy/privacy)
- **Cursor**: Privacy Mode = no training on customer data plus ZDR with all model providers (abuse-detection exceptions); off = Cursor may store "codebase data, prompts, editor actions, code snippets." Even BYO API key requests "will still go through our backend." Cloud agents: TLS 1.2+, AES-256 at rest "with per-agent keys," CMEK/BYOK for enterprise; "Cloud Agents run in Privacy Mode" and "Legacy Privacy Mode is not supported." — [Cursor: Data use](https://cursor.com/data-use); [Cursor: Cloud agent security](https://cursor.com/docs/cloud-agent/security). Legacy mode described (via a support email quoted by a user, ~2025) as "No code storage whatsoever," versus current Privacy Mode allowing temporary code storage for features. — [Cursor forum thread 108044](https://forum.cursor.com/t/details-on-privacy-mode-with-storage-how-its-different-than-privacy-mode-legacy/108044)
- **Linear**: "Linear forces HTTPS on all connections and encrypts data in-transit with TLS 1.2. All data at-rest is secured using AES 256-bit encryption." No E2EE or self-hosting is offered. — [Linear: Security](https://linear.app/security). A March 24, 2026 incident exposed private-team data to other workspace members for about an hour; mobile sessions were logged out and web/desktop caches force-cleared. — [Linear: Post mortem March 24, 2026](https://linear.app/now/linear-incident-on-mar-24th-2026)
- **Claude Code**: Remote Control traffic "travels through the Anthropic API over TLS"; transcripts stored server-side under the Data usage policy; cloud GitHub credentials "never enter a session's VM." No E2EE. Trusted Devices stores only device public keys and biometric checks stay on-device. — [Claude Code: Remote Control](https://code.claude.com/docs/en/remote-control); [Claude Code: Cloud](https://code.claude.com/docs/en/claude-code-on-the-web.md)
- **Raycast**: synced data "is encrypted locally, in transit, and on the server" (provider-held keys, not E2EE as described). — [Raycast Manual: Cloud Sync](https://manual.raycast.com/cloud-sync.md)
- **Zed**: provider ZDR for Zed-hosted models, with the exception that "Anthropic retains prompts and outputs for models it designates as Covered Models" for at least 30 days; Zed "can't opt out," and BYO key does not avoid it. — [Zed: AI privacy and security](https://zed.dev/docs/ai/privacy-and-security.md)
- **Tailscale**: data plane is WireGuard between nodes; the coordination server distributes public keys and is proprietary; Tailnet Lock removes the need to "trust the Tailscale coordination server for distributing public node keys." — [Tailscale: Open source](https://tailscale.com/opensource); [Tailscale KB: Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock)
- **VS Code / JetBrains**: no E2EE statements; VS Code uses the OS credential store for the sync token (Linux keyring issues documented). — [VS Code: Settings Sync](https://code.visualstudio.com/docs/configure/settings-sync.md)

### Inferences
- E2EE is viable for Obsidian because the server never needs to interpret content; it only needs per-file routing metadata. Any product that renders transcripts in a web UI, runs server-side search, or lets a server-side model read the content (every agent tool here) has chosen provider-held keys. Obsidian's "server sees who changed which path when" is the minimal metadata leak a hub-and-spoke design should expect to accept.
- Per-object keys (Cursor per-agent keys, Cursor client-generated cache keys, Claude Trusted Device public keys) are the intermediate step several vendors have taken between plaintext-at-rest and E2EE.

### Gaps
- Warp's docs do not describe encryption of cloud conversations beyond "encrypted at rest."
- Linear's security page is JavaScript-rendered; quotes above come from search snippets and should be re-verified against the live page.

## Key question 5: Self-hosting and enterprise (on-prem sync, SSO, org admin control over sync)

### Takeaway
No surveyed product offers a self-hostable *settings or conversation sync* backend: VS Code explicitly says "Custom backends are not supported," JetBrains and Raycast are account-bound, Obsidian is hosted-only (self-hosting is left to community plugins), and Tailscale's control plane is proprietary with the independent Headscale project as the only alternative. What enterprises get instead is an admin kill-switch (Raycast, Warp, Copilot policy "Store local sessions in the Cloud," Claude Code org toggles and custom roles, Zed Business admin controls) plus SSO/SCIM for identity and, in Claude Code's case, self-hosted *execution* environments while the transcript store stays with Anthropic.

### Cited Findings
- **VS Code**: supported accounts are Microsoft and GitHub; "Not supported: GitHub Enterprise Server accounts and Microsoft Sovereign Cloud accounts. Custom backends are not supported. Settings Sync uses a dedicated service." No enterprise policy documented on that page. — [VS Code: Settings Sync](https://code.visualstudio.com/docs/configure/settings-sync.md)
- **GitHub Copilot**: session sync is governed by the GitHub.com policy "Store local sessions in the Cloud" with values "View from cloud" (sync only) and "View and control" (sync + remote control); unconfigured/disabled means neither is available; enterprises can enforce or "Let organizations decide." VS Code group policy `CopilotSessionSync` forces `chat.sessionSync.enabled` to false and shows "Disabled by policy." "Enabling the policy doesn't give administrators access to session data." Enterprise `remoteControl` managed setting can require SSO for specific orgs or disable remote control per device. — [GitHub Docs: About remote control](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-remote-control); [VS Code: Session history](https://code.visualstudio.com/docs/agents/run/sessions/session-history.md). Oct 2026: "Organization members need single sign-on to access session data from organization repositories"; Gists unavailable to Enterprise Managed Users. — [GitHub Changelog 2026-10-28](https://github.blog/changelog/2026-10-28-work-from-anywhere-with-a-new-connected-copilot-cloud-experience/); [GitHub Docs: chronicle](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/chronicle)
- **Claude Code**: Remote Control needs an Owner-enabled toggle on Team/Enterprise and, under custom roles, both "cloud sessions" and "Claude Code remote control" permissions; unavailable via Bedrock, Vertex/Agent Platform, Foundry, LLM gateways, or the enterprise Claude apps gateway; ZDR and HIPAA orgs cannot enable it; Trusted Devices can be required org-wide. Cloud sessions can run "on your organization's self-hosted environment when routed there," but the transcript and session list remain on claude.ai; CMEK orgs "can't start cloud sessions"; IP-allowlisted orgs break Anthropic-hosted sessions. — [Claude Code: Remote Control](https://code.claude.com/docs/en/remote-control); [Claude Code: Cloud](https://code.claude.com/docs/en/claude-code-on-the-web.md)
- **Warp**: "Admins can disable cloud storage through the Admin Panel"; when disabled, conversations are local only and cannot be shared or accessed across devices. Workspace admins can disable invites and link sharing. Share links default to "Anyone on your team." — [Warp: Cloud conversations](https://docs.warp.dev/agents/local-agents/cloud-conversations.md); [Warp: Agent session sharing](https://docs.warp.dev/agent-platform/local-agents/session-sharing/)
- **Raycast**: Enterprise admins toggle Cloud Sync for the organization at Account Settings → Organization → Admin Controls; "Enterprise Exclusive," enabled by default; when off, members cannot enable it in the client; Enterprise features "aren't yet supported in Raycast for Windows." No per-category or SSO/SCIM linkage documented. — [Raycast Manual: Cloud Sync Control](https://manual.raycast.com/enterprise/cloud-sync-control.md)
- **Cursor**: enterprise cloud-agent controls include customer-managed KMS keys, retention policies capping conversation retention, org-wide network egress lockdown, "Protected Git Scopes," and audit logs streaming to SIEM/webhook/S3; the docs recommend "enforcing standard Privacy Mode org-wide." — [Cursor: Cloud agent security](https://cursor.com/docs/cloud-agent/security)
- **Linear**: SAML "via most identity providers (Okta, OneLogin, LastPass, Auth0, Bitium, and more)"; "SAML authentication and IP restrictions are only available to workspaces on our Enterprise plan"; SCIM provisions/deprovisions via the IdP; enabling SAML does not log out existing sessions. — [Linear: Security](https://linear.app/security); [Linear Docs: Login methods](https://linear.app/docs/login-methods); [Linear Docs: SAML](https://linear.app/docs/saml-and-access-control)
- **Zed**: "Zed Business enforces privacy settings across an organization"; owners/admins control Zed-hosted models, Edit Prediction, and feedback sharing via Admin Controls. Zed's collab server is not documented as self-hostable on the pages retrieved. — [Zed: AI privacy and security](https://zed.dev/docs/ai/privacy-and-security.md)
- **JetBrains**: sign-in via JetBrains Account including when using an activation code or license server ("Backup and Sync | Log in with JetBrains account"); no on-prem sync server documented; the Toolbox App's offline mode covers IDE feeds, not settings sync. — [JetBrains Help: IDE settings backup and sync](https://www.jetbrains.com/help/idea/sharing-your-ide-settings.html); [JetBrains Help: Offline remote development in Toolbox](https://www.jetbrains.com/help/toolbox-app/offline-remote-development-in-the-toolbox-app.html)
- **Obsidian**: hosted only, with four regions and a "Collaborate on a shared vault" model; community plugins (Osync, Syncian, Vault Syncryption) provide self-hosted or alternative E2EE sync. — [Obsidian Help: Set up Obsidian Sync](https://obsidian.md/help/sync/setup); [Obsidian plugin: Osync](https://community.obsidian.md/plugins/osync)
- **Tailscale**: "A closed source coordination server ... remains proprietary as part of our managed service"; Headscale "is developed independently and separately from Tailscale," is "a community-maintained project, not Tailscale-managed or part of the supported Tailscale product," though Tailscale "employs the head maintainer of Headscale, but does not direct or steer the project." — [Tailscale: Open source](https://tailscale.com/opensource)

### Inferences
- The industry pattern is "identity from the IdP, policy from the vendor console, data in the vendor cloud." Self-hosting is offered for *compute* (Claude Code self-hosted environments, Copilot `--environment-host`, Zed SSH servers) but not for the *hub that holds the transcript index*. A product that self-hosts the hub itself would be differentiated against every tool here except Headscale-style community projects.
- Admin controls are coarse (one toggle) everywhere except Copilot (two-level policy) and Cursor (retention caps, CMEK). Fine-grained per-category admin control over what syncs was not found in any product.

### Gaps
- Raycast's docs do not say whether disabling Cloud Sync org-wide deletes already-synced data or how quickly it propagates.
- Warp's Admin Panel documentation for disabling Settings Sync (as opposed to conversations) was not located.
- Linear's offering for on-prem or EU data residency was not confirmed from the pages retrieved.

## Key question 6: Conflict and offline handling as described publicly, and known failure modes from user reports

### Takeaway
Three conflict strategies dominate: last-writer-wins without timestamps (Linear offline, Warp Settings Sync "last device enabled wins," Obsidian non-Markdown files), automatic content merge (Obsidian diff-match-patch for Markdown, Obsidian JSON key merge for settings, JetBrains "merged using the most recent configuration," VS Code automatic merge with a manual diff fallback), and fork-instead-of-merge (Warp cloud conversations, Claude Code teleport). The dominant user complaint across every settings-sync product is the same: a stale device coming online overwrote the good copy (JetBrains IJPL-200976, VS Code #183485, Raycast known issue, Obsidian iPhone thread), followed by "a toggle that shouldn't have synced did" (Warp #6692) and silent merges that duplicated text (Obsidian).

### Cited Findings
- **Linear**: offline mode "is designed as a failsafe and not a full-fledged feature"; the app does not check each change's creation date, so heavy offline editing "could overwrite a teammate's recent changes"; queued changes survive restart and a "Syncing" label shows the count. — [Linear Docs: Download Linear](https://linear.app/docs/get-the-app). Engine detail: a central server assigns a total order via `lastSyncId`; rejected mutations roll back; cached transactions are replayed on reconnect and, because some are not idempotent, "a resend can produce errors, such as an attempt to delete a model that no longer exists" (author's reading). — [wzhudev/reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine). (older) Jan 2024 incident: "changes that weren't syncing" with a syncing/offline spinner. — [Linear status incident](https://linearstatus.com/incidents/01HKWZHY2CSQJ5WYVWHNQQ8DE7)
- **Obsidian**: Markdown conflicts are merged with Google's diff-match-patch; other files use "last modified wins"; settings JSON is merged "applying local keys on top of remote ones." Since 1.9.7 a per-device setting offers "Automatically merge" (default; "can produce duplicate text or formatting problems") or "Create conflict file" named `original-note-name (Conflicted copy device-name YYYYMMDDHHMM).md`, where the conflict file holds the local changes and the original keeps the remote version. Known edge: a newly created local note is replaced without merge if a remote copy arrives within a couple of minutes. — [Obsidian Help: Troubleshoot Obsidian Sync](https://obsidian.md/help/sync/troubleshoot)
- Obsidian user reports: "Obsidian Sync on iPhone Overwrites Newer Data, Causing Data Loss" (bug report, tracked; poster counted "6-8 more instances," Aug 2024). — [Obsidian forum 85214](https://forum.obsidian.md/t/obsidian-sync-on-iphone-overwrites-newer-data-causing-data-loss/85214). "Obsidian Sync incorrectly duplicates sections of files" (multi-page bug thread) and requests for a manual diff-style resolver. — [Obsidian forum 94732](https://forum.obsidian.md/t/obsidian-sync-incorrectly-duplicates-sections-of-files/94732); [Obsidian forum 94468](https://forum.obsidian.md/t/option-to-let-user-manually-resolve-sync-conflicts/94468). June 2026 report of duplications and lost content after "ages" of stable use; moderator suspected a competing sync service. — [Obsidian forum 114896](https://forum.obsidian.md/t/sync-issues-occuring-latetly/114896)
- **VS Code**: conflicts arise "when you first enable sync on a device or when you change data while offline"; sync pauses until resolved via Accept Local / Accept Remote / Show Conflicts (diff editor, Complete Merge). Local backups (30 days) and remote backups (20 versions per category) exist. Insiders data can turn sync off in Stable due to incompatibility. — [VS Code: Settings Sync](https://code.visualstudio.com/docs/configure/settings-sync.md). Failure reports: second computer overwriting cloud settings on launch (#183485, closed not planned); conflict notification whose "Show Conflict" does nothing (#123514); stuck "Turning on Setting Sync..." (#141393); constant conflicts in Codespaces (#107363); whole-file keybinding conflicts because the array is compared as a unit (third-party explanation). — [microsoft/vscode #183485](https://github.com/microsoft/vscode/issues/183485); [microsoft/vscode #123514](https://github.com/microsoft/vscode/issues/123514); [microsoft/vscode #141393](https://github.com/microsoft/vscode/issues/141393); [microsoft/vscode #107363](https://github.com/microsoft/vscode/issues/107363); [syncintosh PR 20](https://github.com/devgyurak/syncintosh/pull/20)
- **JetBrains**: on enable, "Push Settings to Account" overrides the server copy; "Get Settings from Account" pulls. (older, 2022) Simultaneous edits on two machines are "merged using the most recent configuration." — [JetBrains Help: IDE settings backup and sync](https://www.jetbrains.com/help/idea/sharing-your-ide-settings.html); [JetBrains blog: 2022.3 EAP 3](https://blog.jetbrains.com/idea/2022/10/intellij-idea-2022-3-eap-3/). YouTrack IJPL-200976 (created 2025-08-07, resolved 2025-12-23 as Incomplete): choosing "Get settings from account" on a home machine overwrote the account's stored settings with defaults; reporter noted "There's no way to roll back settings if the wrong option is chosen" and confusion about the scope of "all JetBrains IDEs" vs. "WebStorm instances only." — [YouTrack IJPL-200976](https://youtrack.jetbrains.com/issue/IJPL-200976). Recovery is via Backup and Sync History (a diff per "commit"). — [YouTrack article SUPPORT-A-390](https://youtrack.jetbrains.com/articles/SUPPORT-A-390). Cross-IDE sync disables plugins specific to one IDE (IJPL-13103). — [YouTrack IJPL-13103](https://youtrack.jetbrains.com/issue/IJPL-13103). Support-forum reports of settings lost after a Toolbox-driven major upgrade. — [JetBrains support: Lost my settings](https://intellij-support.jetbrains.com/hc/en-us/community/posts/10980327141650-Lost-my-settings)
- **Warp**: Settings Sync is last-enabled-device-wins: "If you turn it off and back on, the synced settings come from the last device where you enabled it." Warp Drive "will continue to work in read only mode" offline. — [Warp: Settings Sync](https://docs.warp.dev/terminal/more-features/settings-sync); [Warp: Warp Drive](https://docs.warp.dev/features/warp-drive). Issue #6692 (June 2025, reproduced May 2026 on macOS and Windows): the Warp Agent on/off toggle and the Settings Sync toggle itself propagate across devices even with Settings Sync off; closed "not planned" by a bot, reopened by the CEO ("makes sense to fix"); still open with `needs-info`. — [warpdotdev/warp #6692](https://github.com/warpdotdev/warp/issues/6692)
- **Raycast**: no general merge policy documented. Re-enabling sync "starts a fresh sync" where "Settings may revert to cloud values, deleted items may reappear, and local edits may be replaced by newer cloud versions"; "Don't toggle sync off and on to force a sync." Known issues: hotkeys/settings may revert to default on a new install during alpha/beta; "opening an unchanged note on iOS can overwrite newer edits from another device" (fix planned); the v1→v2 de-duplicator is conservative so duplicates may remain. — [Raycast Manual: Cloud Sync](https://manual.raycast.com/cloud-sync.md). July 2026 fixes: TLS-inspecting proxy support, very long AI chats losing history, "changes made right before a restart occasionally not being synced," and disable failing while the DB was busy. — [Raycast changelog Windows v0.70](https://www.raycast.com/changelog/windows/0-70)
- **Claude Code**: resuming the same session in two terminals without forking means "messages from both interleave into one transcript"; `/branch` is the fork primitive and Remote Control follows the branch. Reconnect after failure archives the server session if compaction rewrote the conversation. Cloud "Environment expired" restores conversation history but not running shell commands, subagents, or session-scoped scheduled tasks. — [Claude Code: Manage sessions](https://code.claude.com/docs/en/sessions.md); [Claude Code: Remote Control](https://code.claude.com/docs/en/remote-control); [Claude Code: Cloud](https://code.claude.com/docs/en/claude-code-on-the-web.md)
- **Codex**: Desktop may not list CLI sessions created while the app-server was not running (#10547); a session ID can be printed with no resumable artefacts after early transport failure (#15870); `--ephemeral` sessions cannot be resumed (third-party summary of official issues). — [Daniel Vaughan: Cross-surface session sync](https://codex.danielvaughan.com/2026/04/08/cross-surface-session-sync/); [openai/codex #10547](https://github.com/openai/codex/issues/10547); [openai/codex #15870](https://github.com/openai/codex/issues/15870)
- **Copilot CLI**: when the machine sleeps, "remote control is unavailable until the machine is back online"; with both surfaces active, "the first response to a prompt or permission request is the one Copilot uses." — [GitHub Docs: About remote control](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-remote-control)
- **Tailscale**: key expiry causes hard loss of connectivity ("Connections to and from the endpoint stop working") and the docs warn against `tailscale up --force-reauth` over SSH/RDP without a backup path. — [Tailscale KB: Key expiry](https://tailscale.com/kb/1028/key-expiry)

### Inferences
- Every settings-sync product that lacks per-field vector clocks eventually ships an "overwrote my settings" bug; the mitigations that vendors actually shipped are (a) server-side version history with restore (VS Code 20 versions, JetBrains history), (b) a visible "last synced" per device (Raycast), and (c) refusing to overwrite on first enable without an explicit Push/Get choice (JetBrains, VS Code merge prompt). A new design should assume it needs all three.
- For conversations, vendors avoid merging altogether: branches/forks (Warp, Claude Code) or single-writer (Copilot first-responder). Append-only turn logs with one owner per session sidestep the merge problem that bites settings sync.
- "Toggle state itself syncing" (Warp #6692) and "sync preferences are device-local" (Obsidian) are opposite answers to the same question; Obsidian's explicit per-device sync preferences avoided the class of bug Warp hit.

### Gaps
- Linear's description-field conflict handling (CRDT vs. last-write) is asserted in community posts but not confirmed in the reverse-engineering README's visible portion or official docs.
- Raycast's internal conflict policy (timestamp vs. revision) is not documented.
- The Reddit report of Raycast iOS overwriting AI chat history on toggle could not be fetched (mirror unavailable) and is unverified.
- JetBrains' current (2025–2026) merge policy text was not retrievable from the live help page; the "most recent configuration" wording is from the 2022.3 announcement.
