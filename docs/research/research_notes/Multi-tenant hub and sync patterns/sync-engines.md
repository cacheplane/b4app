# Local-first sync engines and protocols for Postgres-backed services (state as of 2026)

Scope: ElectricSQL, PowerSync, Replicache and Zero (Rocicorp), Ditto, Automerge and Yjs, Turso/libSQL embedded replicas, and hand-rolled change-log replication, evaluated for a product whose macOS client keeps data in a local PostgreSQL, whose iOS client keeps it in SQLite, with server Postgres as source of truth and organizations (tenants) containing users.

Research method: official docs, GitHub repositories and licence files fetched directly (October 2026); vendor blog posts; the HLC paper's author's write-up; first-party engineering posts from Figma, Linear and Notion; one reverse-engineering study of Linear; a small number of secondary comparisons flagged as such. Every renamed or deprecated item encountered is called out inline.

Renames and deprecations encountered during this research (summary):
- `electric-sql.com` now 301-redirects to `electric.ax`; Electric's HTTP API is at version 1.7.4 and the docs refer to "Electric 2.0" deprecating `GET` subset queries. — observed redirect; [Electric OpenAPI](https://electric.ax/openapi); [Electric auth guide](https://electric.ax/docs/guides/auth)
- PowerSync "Sync Rules" are legacy; "Sync Streams" are the replacement (GA announced 2026). — [PowerSync Sync Rules](https://docs.powersync.com/usage/sync-rules); [Sync Streams GA](https://releases.powersync.com/announcements/sync-streams-are-now-generally-available)
- The PowerSync Swift SDK was re-implemented natively in Swift at v1.14 (previously wrapped a Kotlin XCFramework). — [PowerSync Swift SDK](https://docs.powersync.com/client-sdk-references/swift)
- The `rocicorp/replicache` GitHub repository was archived (read-only) on 10 June 2026; Rocicorp's Reflect product was retired in 2024; Zero is "generally available" as of March 2026. — [rocicorp/replicache](https://github.com/rocicorp/replicache); [Retiring Reflect](https://rocicorp.dev/blog/retiring-reflect); [Zero status](https://zero.rocicorp.dev/docs/status)
- Ditto renamed "Big Peer" to "Ditto Server". — [Ditto glossary](https://docs.ditto.live/home/glossary)
- Turso's libSQL sync APIs are being deprecated in favour of the Rust "Turso Database" (`turso` crate) and "Turso Sync"; the embedded-replicas page itself now recommends Turso Sync for new projects. — [Turso embedded replicas](https://docs.turso.tech/features/embedded-replicas); [search summary of libSQL commit, April 2026](https://github.com/tursodatabase/libsql-swift)

## Key question 1: Per-engine architecture, Swift/iOS support, client store, write path, conflicts, partial sync, auth, offline, licensing, hosting, pricing, limits

### Takeaway
No off-the-shelf engine in this set offers a supported Swift client that writes into a local PostgreSQL on macOS; the only engines with production-grade Swift SDKs are PowerSync (SQLite client store, writes through your API) and Ditto (its own CRDT document store, no Postgres connector). ElectricSQL is the only engine whose protocol is plain HTTP and whose official tooling already syncs into client-side Postgres, but only via TypeScript/Node; a Swift consumer of the shape protocol would be hand-written (one small community package exists). Zero, Replicache, Turso Sync, and the CRDT libraries are either web/JS-only, in technical preview, or unsuited to relational multi-tenant data.

### Cited Findings

#### ElectricSQL (Electric)

- Architecture: Electric reads Postgres logical replication and serves subsets of rows as "shapes" over HTTP that CDNs can cache; shapes are defined by table plus a SQL `where` clause. — [Electric Postgres Sync](https://electric.ax/sync/postgres-sync); [Electric installation guide](https://electric.ax/docs/sync/guides/installation)
- Setup requires logical replication enabled and a database user with the `REPLICATION` role; Electric can manage publications automatically or a DBA can pre-configure a publication and set `REPLICA IDENTITY FULL` on synced tables. — [Electric installation guide](https://electric.ax/docs/sync/guides/installation)
- Write path: "Electric does not do write-path sync." Four documented write patterns: online writes (REST, UI waits), optimistic state (React `useOptimistic`, not persisted), shared persistent optimistic state (e.g. valtio + localStorage), and "through-the-DB sync" where the app reads/writes a local embedded database (PGlite in the example), synced rows land in an immutable table, local changes go to a shadow table, a view merges them, triggers log changes, and a sync utility sends them to your server. — [Electric writes guide](https://electric.ax/docs/guides/writes)
- Offline: the online-writes pattern "won't work offline"; optimistic-state patterns accept writes offline; through-the-DB sync gives "full offline support". — [Electric writes guide](https://electric.ax/docs/guides/writes)
- Conflicts: Electric leaves merge/rollback to the app; the baseline is to "clear all local state if any write is rejected", with finer options (mark for manual resolution, clear only causally dependent writes). The guide argues "conflicts are extremely rare and can be mitigated well by strategies like presence." — [Electric writes guide](https://electric.ax/docs/guides/writes)
- Client stores: the official client is TypeScript (`@electric-sql/client` with `ShapeStream`/`Shape`); an Elixir client exists. Since v0.11 Electric can sync into PGlite and, under Node, into any Postgres via node-postgres. The TypeScript client page lists no Swift, Dart, Kotlin, Rust or Python client. — [Electric TypeScript client](https://electric.ax/docs/api/clients/typescript); [Electric v0.11 Postgres client support](https://electric.ax/blog/2024/05/14/electricsql-postgres-client-support)
- Swift: no official Swift client. Community `ElectricSync` (paulharter) subscribes to shapes from SwiftUI, persists with SwiftData, targets iOS 18+/macOS 15+, has 20 stars, MIT licence, and its README says the persistent publisher "is a bit slow during initial sync and needs a bit of attention!" — [ElectricSync](https://github.com/paulharter/ElectricSync)
- Shape protocol (what a Swift port would implement): `offset` is a position in the shape log; `handle` identifies the shape and must accompany an offset; live mode long-polls with `liveRequestTimeoutMs` defaulting to 45 s; `liveSse` switches to Server-Sent Events with fallback to long-poll; `cursor` is a reserved parameter. — [Electric TypeScript client](https://electric.ax/docs/api/clients/typescript)
- Partial sync and auth: Electric is "all just HTTP"; the proxy pattern has your API set `table`, `where`, `queryable_columns` and `secret` server-side (example sets `org_id = $1` unless the user is an admin); the gatekeeper pattern issues a shape-scoped token whose claim contains the shape definition, which a proxy validates on each request; client subset queries are `AND`ed with the shape `where`, so they "can only narrow results, never widen them"; `GET` subset requests are deprecated in Electric 2.0 in favour of `POST`. — [Electric auth guide](https://electric.ax/docs/guides/auth)
- Licensing and hosting: "Released under the Apache 2.0 License"; the sync service is self-hostable (it is the Docker service you run against `DATABASE_URL`). Electric 1.1 (August 2025) shipped a new storage engine with "100x faster writes". — [Electric pricing](https://electric.ax/pricing); [Electric installation guide](https://electric.ax/docs/sync/guides/installation); [Electric 1.1 release](https://electric.ax/blog/2025/08/13/electricsql-v1.1-released)
- Electric Cloud pricing: PAYG $0/month (fees under $5 waived), Pro $249/month, Scale $1,999/month (6-month commitment), Enterprise custom; writes billed at $1 / $0.90 / $0.80 per 1M; retention $0.10 / $0.09 / $0.08 per GB-month; "Postgres Sync add-on" +$2 / +$1.8 / +$1.6 per 1M; reads, egress and fan-out free; max 10 / 50 / 200 databases. — [Electric pricing](https://electric.ax/pricing)
- A 2026 practitioner (font-editor author) abandoned Electric + TanStack DB after about two months citing long polling and DIY write endpoints, and chose Zero; this is opinion without benchmarks. — [Choosing a Sync Engine for Local-First in 2026](https://johnny-sh.pages.dev/blog/choosing-a-sync-engine-in-2026)

#### PowerSync

- Architecture: the PowerSync Service replicates from the source database (Postgres 11+, MongoDB 6.0+, MySQL 5.7+ supported) into buckets; clients hold a local SQLite database and stream bucket operations. The service monorepo lists replication modules for MongoDB, MySQL, Convex and Postgres and a "MongoDB bucket storage module"; its description also claims Azure DocumentDB and SQL Server support. — [PowerSync supported platforms](https://docs.powersync.com/resources/supported-platforms); [powersync-service](https://github.com/powersync-ja/powersync-service)
- Client store is SQLite only; the schema is applied as SQLite views over JSON data, "so schema migrations are generally not needed"; column types are `text`, `integer`, `real`. No Postgres client store exists. — [PowerSync Swift SDK](https://docs.powersync.com/client-sdk-references/swift)
- Swift SDK: listed as "Supported" for iOS 15.0, macOS 12.0, iPadOS 15.0, tvOS 15.0, watchOS 9.0; Mac Catalyst and visionOS not supported; "HTTP only, no WebSocket." From v1.14 the SDK is "implemented natively in Swift" using the Rust core for the sync protocol and SQLite extension; up to v1.13 it wrapped a Kotlin XCFramework. App-group/extension sharing is "experimental" and only one process may call `connect()`. The checkpoint-request API is alpha and needs Service v1.24.0+. — [PowerSync supported platforms](https://docs.powersync.com/resources/supported-platforms); [PowerSync Swift SDK](https://docs.powersync.com/client-sdk-references/swift)
- Write path: the app writes to local SQLite; the SDK "places every write to the SQLite database in an upload queue"; your `BackendConnector` implements `fetchCredentials` and `uploadData`, which sends the queued CRUD entries to your own API, which applies them to Postgres. After the queue drains, the client requests a write checkpoint so it receives its own mutations back before applying further downloads. — [PowerSync Swift SDK](https://docs.powersync.com/client-sdk-references/swift); [PowerSync protocol](https://docs.powersync.com/architecture/powersync-protocol)
- Conflict handling is therefore entirely in your `uploadData` backend endpoint (PowerSync ships no merge policy; the local write is optimistic until the server's version replicates back). — [PowerSync Swift SDK](https://docs.powersync.com/client-sdk-references/swift)
- Partial sync: legacy Sync Rules define buckets with parameter queries drawing on JWT claims (`sub` always included, custom claims selectable), client parameters, or table lookups, and data queries such as `WHERE owner_id = bucket.user_id`; a definition with no parameter query is a global bucket synced to everyone; "Client Parameters should always be treated with care, and should not be used for access control purposes." Sync Rules "keep working and stay supported while you migrate." — [PowerSync Sync Rules](https://docs.powersync.com/usage/sync-rules)
- Sync Streams (replacement): named server-side SQL-like stream definitions; clients subscribe with parameters from the JWT, the connection, or the subscription; a stream creates one bucket per distinct filter value (e.g. per `auth.user_id()`); `auto_subscribe: true` for offline-first; data from unsubscribed streams is retained for a TTL (24 h default). Status: beta then GA in 2026 (the GA announcement is dated 14 May 2026; a roadmap post gives March beta / June GA, which could not be reconciled). — [PowerSync Sync Streams](https://docs.powersync.com/sync/streams/overview); [Sync Streams GA](https://releases.powersync.com/announcements/sync-streams-are-now-generally-available); [2025 roadmap update](https://powersync.com/blog/2025-powersync-roadmap-update)
- Protocol: client opens a session with a JWT plus its current buckets and last op_id per bucket; server streams checkpoint id with per-bucket checksums, `PUT`/`REMOVE` operations after the client's op_id, then "checkpoint complete"; a row is deleted locally only when removed from all containing buckets; checksum mismatch causes the client to drop and resync the bucket; compaction replaces stale updates with markers while keeping checksums valid; each checkpoint is a point-in-time consistent snapshot. — [PowerSync protocol](https://docs.powersync.com/architecture/powersync-protocol)
- Auth: clients authenticate to the service with JWTs returned by `fetchCredentials()`; you can reuse your provider's JWT (JWKS URLs listed for Firebase, Auth0, Clerk, Cognito; Supabase uses its JWT secret) or mint custom ones; development tokens exist for Cloud and self-hosted. — [PowerSync authentication setup](https://docs.powersync.com/installation/authentication-setup)
- Licensing: the PowerSync Service is under the Functional Source License 1.1 with Apache 2.0 future licence (FSL-1.1-ALv2); each release converts to Apache 2.0 "on the second anniversary of the date we make the Software available"; "Competing Use" (offering a substitute product/service) is prohibited before then. — [powersync-service LICENSE](https://raw.githubusercontent.com/powersync-ja/powersync-service/main/LICENSE)
- Hosting and pricing: Cloud Free $0 (2 GB synced/month, 500 MB hosted, 50 peak concurrent clients, 2 instances, deactivated after a week idle); Pro from $49/month (30 GB synced then $1/GB, 10 GB hosted then $1/GB, 1,000 concurrent then $30 per 1,000, max 3,000 by default); Team from $599/month (same unit prices, higher caps, up to 50,000+ concurrent on request); Enterprise custom. Self-hosted "Open Edition" is free and source-available with all backends, all SDKs, Sync Streams and Prometheus metrics; Enterprise Self-Hosted adds custom checkpoints, hardened images, SOC 2 report, 24x7 support. — [PowerSync pricing](https://www.powersync.com/pricing)
- Noted limits: no WebSocket in Swift/.NET/Flutter SDKs; Swift `CrudBatch`/`CrudEntry`/`CrudTransaction` are structs you cannot construct in tests since v1.14; MongoDB bucket storage is the only storage module listed in the service repo. — [PowerSync supported platforms](https://docs.powersync.com/resources/supported-platforms); [PowerSync Swift SDK](https://docs.powersync.com/client-sdk-references/swift); [powersync-service](https://github.com/powersync-ja/powersync-service)

#### Replicache (Rocicorp)

- Status: the GitHub repository "was archived by the owner on Jun 10, 2026. It is now read-only." Rocicorp's 2024 statement was that it would keep maintaining Replicache while building Zero and then encourage migration; secondary directories describe it as "in maintenance mode". — [rocicorp/replicache](https://github.com/rocicorp/replicache); [Retiring Reflect](https://rocicorp.dev/blog/retiring-reflect); [toolradar Replicache](https://toolradar.com/tools/replicache)
- Licensing: official docs (v12) say the Terms of Service require every user to acquire a license key, free for non-commercial or pre-revenue use; several third-party sites claim it later became free/open source, but no primary Rocicorp announcement was found. Treat the licence as unverified. — [Replicache v12 licensing](https://v12.doc.replicache.dev/howto/licensing); [search summary](https://rocicorp.dev/terms)
- Architecture: client-side key-value store (IndexedDB in browsers); each instance is a client with a random `clientID`, clients sharing a `name` form a client group with one on-disk cache; docs advise a different `name` per user. Mutations get sequential mutation IDs; the server stores `lastMutationID` per client; on pull "Replicache therefore discards any pending mutations it has for each client with id ≤ lastMutationID" so a change is never applied twice. Push sends mutator name, args, clientID and order; "the server is authoritative" and re-runs mutators. Pull takes a cookie (opaque, identifies the canonical server state the client has) and returns a new cookie, a patch and `lastMutationIDChanges`. Rebase: Replicache "rewinds the state of the Client View to the last version it got from the server", applies the patch, replays pending mutations; replays may produce different results, which the app must handle. Pokes are contentless hints over SSE, WebSockets or Pusher that trigger a pull. — [Replicache how it works](https://doc.replicache.dev/concepts/how-it-works)
- Backend strategies: Reset (retransmit whole client view each pull), Global Version ("Limited to about 50 pushes/second across entire app", read auth and partial sync difficult), Per-Space Version (about 50 pushes/second/space, all-or-nothing per space), Row Version (per-row versions, "Each individual data item can be authorized based on arbitrary code", "Sync any arbitrary subset of the database", hardest to implement). — [Replicache strategies](https://doc.replicache.dev/strategies/overview)
- Swift/iOS: Replicache is a JavaScript library; no Swift client exists (none referenced anywhere in the docs fetched). — [Replicache how it works](https://doc.replicache.dev/concepts/how-it-works)

#### Zero (Rocicorp)

- Status: "As of March 2026, Zero is generally available and fully-supported." 2026 plans: Cloud Zero to public availability, column permissions, "Terabugs"; considered but uncommitted: aggregates, SSR, JSON filters, text search. — [Zero status](https://zero.rocicorp.dev/docs/status)
- Architecture: "It replicates Postgres into a SQLite replica inside `zero-cache`, then syncs subsets of rows to clients"; clients are kept current via logical replication; apps choose what syncs by writing queries (ZQL), not static sync rules; client store is e.g. IndexedDB on web. — [Zero llms.txt](https://zero.rocicorp.dev/llms.txt); [Zero introduction](https://zero.rocicorp.dev/docs/introduction)
- Postgres requirements: "Postgres v15.0 or higher, and support for logical replication"; `wal_level = logical`; Zero creates its publication if privileged; separate `ZERO_CVR_DB` and `ZERO_CHANGE_DB` connections; without event triggers "any schema change triggers a full reset of all server-side and client-side state". — [Zero connecting to Postgres](https://zero.rocicorp.dev/docs/connecting-to-postgres)
- Platforms: docs cover React, SolidJS, React Native (requires a `kvStore`: `expoSQLiteStoreProvider` or `opSQLiteStoreProvider`; op-sqlite "does not work with Expo Go") and community integrations. No Swift/iOS or Kotlin client is documented anywhere; a web search for a Zero Swift SDK found nothing. — [Zero React Native](https://zero.rocicorp.dev/docs/react-native); [Zero llms.txt](https://zero.rocicorp.dev/llms.txt)
- Writes: mutators run optimistically on the client, then `zero-cache` calls your `ZERO_MUTATE_URL` endpoint which runs the write against Postgres; "Do not generate IDs inside mutators, since mutators run multiple times." — [Zero llms.txt](https://zero.rocicorp.dev/llms.txt)
- Auth/permissions: client passes `userID` (used to "segregate the client-side storage for each user") and an opaque `auth` token forwarded as `Authorization: Bearer`, or cookies via `ZERO_QUERY_FORWARD_COOKIES`/`ZERO_MUTATE_FORWARD_COOKIES`; your endpoints verify credentials, build a `Context`, and filter in queries (`zql.post.where('authorID', ctx.id)`) and check ownership in mutators; Zero "does not have (or need) a first-class permission system"; denied reads return no rows. `clientGroupID` "could be stolen with XSS or leaked in logs"; "Never use SameSite=None for auth cookies" because of Cross-Site WebSocket Hijacking. — [Zero auth](https://zero.rocicorp.dev/docs/auth)
- Offline: Zero does not support offline writes; "the cost to support offline is extremely high"; reads work from local data in `disconnected`/`error`/`needs-auth`; writes are queued only during `initializing`/`connecting` and rejected otherwise; `disconnectTimeoutMs` defaults to one minute and raising it "has caveats and is not recommended"; docs recommend blocking input while offline. Reasons given: unresolvable concurrent edits ("no way that any software algorithm can automatically resolve their conflict"), constraints/business logic/authorization that pass offline but fail on reconnect, schema changes while offline, week-long offline sessions. — [Zero offline](https://zero.rocicorp.dev/docs/offline)
- Licensing/hosting: "the Zero client and server are Apache-2 licensed"; "You can use, modify, host, and distribute them freely"; Rocicorp earns revenue "running Zero as a service" plus paid support; "we have no plans to ever change the licensing of the core product." Cloud Zero is the managed option; no prices were published on the pages fetched. — [Zero open source](https://zero.rocicorp.dev/docs/open-source); [Cloud Zero](https://zero.rocicorp.dev/docs/cloud-zero)

#### Ditto

- Architecture: embedded SDK ("Small Peer") instances sync with each other over mesh transports (Bluetooth LE, local network/Bonjour) and with "Ditto Server" (formerly "Big Peer"), "a cluster of servers that can run on-premises or in the cloud". Applications write to the local database first; sync is identical whether the peer is a device or the server. Each peer keeps a metadata database of sync state. — [Ditto glossary](https://docs.ditto.live/home/glossary); [Ditto syncing data](https://docs.ditto.live/key-concepts/syncing-data)
- Data model: JSON-like documents stored as CRDTs; field CRDT types are `REGISTER` (last-write-wins by HLC timestamp), `MAP` (add-wins per key), `ATTACHMENT` (binary by token, fetched explicitly). Documents have a soft limit of 256 KiB and hard limit of 5 MiB. Arrays are discouraged because concurrent offline edits conflict. `_id` is immutable and "feeds into authorization rules". — [Ditto document model](https://docs.ditto.live/key-concepts/document-model); [Ditto glossary](https://docs.ditto.live/home/glossary)
- HLC: "A Ditto HLC combines a physical clock portion" (Unix ms) with a per-peer logical counter; concurrent REGISTER writes resolve to "the most recent write (by HLC timestamp)". — [Ditto glossary](https://docs.ditto.live/home/glossary)
- Partial sync: subscriptions are DQL queries; "the device only receives what its queries describe"; delta sync sends field-level changes. Causal consistency holds within a database ID. — [Ditto syncing data](https://docs.ditto.live/key-concepts/syncing-data)
- Deletes/tombstones: `DELETE` is permanent and leaves a tombstone; `EVICT` only frees local storage; Edge SDK tombstone TTL defaults to 7 days (`TOMBSTONE_TTL_HOURS = 168`), Ditto Cloud to 30 days; reaping runs daily on edge, hourly in cloud; "Never set the Edge SDK TTL to a number larger than the Ditto Server TTL"; a device offline past the TTL "will not be aware of the deletion"; concurrent DELETE and UPDATE can produce a "husked" document; `DELETE` requires SDK 4.10.1+. — [Ditto delete](https://docs.ditto.live/crud/delete)
- Swift SDK: supports iOS 15.0+, Mac Catalyst 15.0+, macOS (AppKit) 12.0+, installed from `github.com/getditto/DittoSwiftPackage`; needs Bluetooth and local-network Info.plist entries; "you must connect to the internet at least once before you can sync offline with other peers". — [Ditto Swift install guide](https://docs.ditto.live/sdk/latest/install-guides/swift)
- Postgres integration: none found. Ditto offers a MongoDB Connector (bidirectional with conflict resolution), Kafka Change Data Capture via "Data Bridges", and webhooks; the platform page says "Kafka, webhooks, and SQL" integrations exist, but no Postgres connector documentation was located. — [Ditto CDC](https://docs.ditto.live/cloud/cdc); [Ditto MongoDB connector](https://docs.ditto.live/cloud/mongodb-connector); [Ditto platform](https://ditto.live/platform); [Ditto cloud overview](https://docs.ditto.live/cloud/overview)
- Pricing/hosting: Free (10 concurrent cloud connections, 2 GB storage, 5 GB transfer, no SLA), Pro (1,000+ connections with add-ons to 10,000, 50 GB storage, 250 GB transfer, 99% SLA, MongoDB connector), Enterprise (custom, 99.95% SLA, AWS/Azure/GCP, "Ditto-Hosted, BYOC, Self-Managed"). Self-managed deployment appears only at Enterprise. — [Ditto pricing](https://ditto.com/pricing)

#### Automerge and Yjs (CRDT libraries)

- automerge-swift: MIT; quickstart pins `from: "0.5.2"`; 330 stars, 21 open issues; provides `Document` with `putObject`/`insert`/`delete`/`fork`/`merge`; the README calls it low-level with "few concessions to ergonomics". Full integration with the automerge-repo sync server was described as future work on the Swift Forums thread. — [automerge-swift](https://github.com/automerge/automerge-swift); [Swift Forums: Introducing Automerge](https://forums.swift.org/t/introducing-automerge-enable-collaborative-asynchronous-syncing-for-your-data-structures/67985)
- automerge-repo-swift: "the API is far from stable"; "This package does NOT yet have a release tagged"; some classes not Swift 6-compatible; a "functional port/replica" of the JS automerge-repo. — [automerge-repo-swift](https://github.com/automerge/automerge-repo-swift)
- YSwift: Swift bindings to Yrs via UniFFI (`yniffiFFI` XCFramework + `YSwift` overlay); README says it is a work in progress and "Not all features and capabilities from Yrs or Yjs are exposed at this time"; 92 stars, 10 open issues; MIT. — [y-crdt/yswift](https://github.com/y-crdt/yswift)
- Positioning: both are document CRDTs (JSON/text trees), not relational row stores; there is no Postgres-backed server for them in this role (an automerge-repo sync server stores documents as blobs). A 2026 secondary comparison calls Yjs "the production default with the largest ecosystem" and Automerge strongest at Git-like history; download figures in that piece are unverified. — [PkgPulse CRDT comparison 2026](https://www.pkgpulse.com/guides/yjs-vs-automerge-vs-loro-crdt-libraries-2026)

#### Turso / libSQL embedded replicas and Turso Sync

- Embedded replicas: reads are served from the local file; "Writes are sent to the remote primary database" at `syncUrl` and reflected back to the writing replica; other replicas see changes after `sync()` or the periodic `syncInterval`; local writes are possible with `offline: true`; a 4 kB frame is the sync unit; opening the local DB while syncing "can lead to data corruption". The page now recommends Turso Sync for new projects. — [Turso embedded replicas](https://docs.turso.tech/features/embedded-replicas)
- Turso Sync: explicit `push()` (sends committed transactions as logical statements) and `pull()`; conflicts follow "last push wins"; a pull after a push can still report changes due to server-side conflict resolution; bootstrap requires the remote to be reachable unless `bootstrap_if_empty` is false; documented SDKs are TypeScript, Python and Go only; no partial sync is described. — [Turso Sync](https://docs.turso.tech/sync)
- Offline writes were announced as a private beta, and the Expo guide describes Turso's Offline Sync as "public beta" with "conflict detection" but no automatic resolution; this is inconsistent with the Sync docs' "last push wins" statement, so treat conflict semantics as in flux. — [Introducing Offline Writes](https://turso.tech/blog/introducing-offline-writes-for-turso); [Expo local-first guide](https://docs.expo.dev/guides/local-first/)
- Swift: `libsql-swift` "is currently in technical preview", supports macOS/iOS/iPadOS/tvOS/watchOS, example pins `from: "0.1.1"`, 26 commits; it covers embedded replicas (read sync on a timer) and says nothing about offline writes; the Turso Database (Rust rewrite) packages cover Rust, JS, Python, Go, Java and .NET with no Swift listed. — [libsql-swift](https://github.com/tursodatabase/libsql-swift); [search summary](https://turso.tech/blog/upcoming-changes-to-the-turso-platform-and-roadmap)
- Auth: a database token created with `turso db tokens create <db>`; no row filtering or per-user partial sync is documented (the unit of sync is a whole database). — [Turso Sync](https://docs.turso.tech/sync)
- Pricing: Free $0 (100 databases, 5 GB, 500M rows read, 10M rows written, 3 GB syncs/month); Developer $4.99/month; Scaler $24.92/month; Pro $416.58/month (100 GB syncs then $0.15/GB); Enterprise custom with a "BYOC Deployment" row. — [Turso pricing](https://turso.tech/pricing)

#### Hand-rolled change-log replication (precedents that match the proposed design)

- cr-sqlite's `crsql_changes` exposes `table, pk, cid, val, col_version, db_version, site_id, cl`: `col_version` is a per-column Lamport clock for merging, `db_version` tracks what a site has seen, `site_id` identifies the writer, and `cl` (causal length) marks row deletion/re-insertion; columns can be counter, fractional-index or last-write-wins CRDTs. As of cr-sqlite 0.15 the winner is the largest `col_version`, ties broken by the larger value. — [crsql_changes](https://vlcn.io/docs/cr-sqlite/api-methods/crsql_changes); [Corrosion CRDT notes](https://superfly.github.io/corrosion/crdts.html); [cr-sqlite](https://github.com/vlcn-io/cr-sqlite)
- Rust `baukit-sync` combines an HLC with per-owner revision counters and tombstone purging behind a per-owner horizon; a pull cursor below the horizon receives `resync_required`; it deliberately "does not choose which record wins". `crdt-lite` is a column-level LWW CRDT with tombstones where tombstones get the highest possible column version. — [baukit-sync](https://docs.rs/crate/baukit-sync/latest); [crdt-lite source](https://docs.rs/crdt-lite/0.5.0/src/crdt_lite/lib.rs.html)

### Inferences
- For the stated product (macOS client on local Postgres, iOS on SQLite, server Postgres, org/user tenancy), the realistic engine choices are: PowerSync (accepting SQLite on macOS too, writes via your API, FSL licence for the service), or ElectricSQL as a read-path only piece with a Swift shape consumer you write yourself (the protocol is small: `GET /v1/shape` with `offset`+`handle`, long-poll or SSE) plus your own write API. Everything else fails a hard constraint: Zero and Replicache have no Swift client and Zero rejects offline writes; Ditto cannot source from Postgres; Turso's Swift SDK is a technical preview and its sync unit is a whole database; Automerge/Yjs are document CRDTs.
- Electric's "through-the-DB sync" pattern (immutable synced table + shadow table + merging view + change-log triggers) is essentially the hand-rolled design described in the brief, with Electric replacing only the download half. This makes an Electric-read / custom-write hybrid a credible middle path, and the local Postgres on macOS is a natural fit because Electric already ships Postgres-target sync for Node.
- PowerSync's architecture (buckets keyed by JWT claims, op_id cursors, write checkpoints) is the closest packaged equivalent of a per-tenant change log with per-device cursors; its FSL licence permits self-hosting for your own product but not reselling a sync service.

### Gaps

## Key question 2: What teams who built their own sync report (Linear, Figma, Notion, Replicache's design, cr-sqlite) about effort and pitfalls

### Takeaway
First-party accounts converge on the same architecture (server-ordered append-only change log, per-client cursor, optimistic local apply with rebase) and the same pitfalls: non-idempotent resend after crashes, catch-up queries that degrade as the log and permission sets grow, per-property LWW silently dropping concurrent edits, and reconciliation of structural changes after reconnect; Linear's numbers show the read path of the log becomes the scaling problem long before the write path does.

### Cited Findings
- Figma: a custom system because OTs were "unnecessarily complex"; CRDT-inspired but with the server as central authority; the server keeps the latest value per property per object, so edits to different properties never conflict and "changes are atomic at the property value boundary" (concurrent text edits resolve to one client's full value); clients discard incoming server changes that conflict with their own unacknowledged edits to avoid flicker; object IDs embed a client ID so creation works offline; deleted objects are removed from the server and kept only in the deleter's undo buffer; parent links plus fractional-index position are stored as one property; the server rejects cycle-creating moves while clients may briefly see a cycle; on reconnect clients download a fresh copy and reapply offline edits over a new WebSocket. — [How Figma's multiplayer technology works](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)
- Linear (first-party, 2026): each workspace has an immutable ordered log of sync actions (ordered id, model, change type, routing metadata, payload) that sits above the Postgres WAL and describes changes in client terms; a returning client sends a checkpoint with the last applied id; "sync groups" encode access and "sync subscriptions" narrow to needed models; the old read path was a second Postgres table queried by id range plus array-overlap predicates, which produced volatile tail latency as checkpoints grew to thousands of actions, read replicas did not help, and a GIN index was rejected because "the cost at write for our scale didn't make sense"; they rebuilt the read path on turbopuffer posting lists with payloads late-enriched from Postgres, Postgres serving the authoritative head of the log, and fallback to Postgres. Scale: "close to one million sync actions per day" for the largest workspaces, clients offline a few hours return "hundreds of thousands of actions behind", the store exceeds 20 TB, replication lag about 1 s p50. Lesson: "storing a change log and serving a change log are different problems." — [Rebuilding delta sync's read path](https://linear.app/blog/rebuilding-delta-sync-read-path)
- Linear (reverse-engineered client, unofficial): IndexedDB per workspace with a table per model; "client-side operations will never directly modify the tables in the local database!" (changes flow through transactions); transactions are cached in a `__transactions` table and resent after reconnect; `lastSyncId` is "a monotonically increasing number that ensures the correct order of operations" and is database-wide; the server broadcasts delta packets to all clients "including the client that initiated the transaction"; on WebSocket handshake the client compares `lastSyncId` and requests missing packets; full/partial/local bootstraps; rejected mutations call `rollback`; a known edge case is resending after a crash because "some transactions are not idempotent" (e.g. deleting an already deleted model); a `__schemaHash` over model metadata bumps the IndexedDB version to trigger migrations. — [reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine)
- Notion (first-party, December 2025): SQLite had been a best-effort record cache; offline mode turned it into a persistent layer with `offline_page` and `offline_action` tables ("one row per reason a page is offline"); "We should only remove a page from the offline set when the **last** reason disappears"; periodic polling "wouldn't scale to millions of users and devices", so updates are pushed on per-page channels and clients refetch pages whose `lastUpdatedTime` exceeds `lastDownloadedTimestamp`; partially available pages were judged worse than unavailable pages; structural moves require reconciling the offline forest and "always treat `offline_action` as the source of truth"; databases auto-download up to 50 rows of the current view; rich-text conflict resolution required migrating offline pages to a new CRDT model. — [How we made Notion available offline](https://www.notion.com/blog/how-we-made-notion-available-offline)
- Replicache's generic design (the "sync problem" framing): clients and server mutate the same key space independently; each change must be applied exactly once; the solution is per-client sequential mutation IDs with server-stored `lastMutationID`, opaque server cookies, and rebase by rewinding to the last server state and replaying pending mutations, with conflict handling delegated to re-running app mutators; the Row Version strategy (per-row version numbers, per-client view records) is required for fine-grained auth and partial sync and is "the hardest to implement". — [Replicache how it works](https://doc.replicache.dev/concepts/how-it-works); [Replicache strategies](https://doc.replicache.dev/strategies/overview)
- Electric's write guide lists the same rebase/rollback problems for hand-rolled through-the-DB sync and notes rollbacks are harder there because the write context is no longer available. — [Electric writes guide](https://electric.ax/docs/guides/writes)
- Zero's team, having built Replicache, states that supporting offline requires either disallowing destructive operations offline, custom fork-and-merge UX, restricting offline writes to one device, or accepting data loss; schema changes during offline periods and constraints that fail on reconnect are named pitfalls. — [Zero offline](https://zero.rocicorp.dev/docs/offline)
- Large blobs: Ditto keeps binaries out of documents as attachments fetched explicitly; Linear keeps large payloads in Postgres and indexes only filter fields. — [Ditto syncing data](https://docs.ditto.live/key-concepts/syncing-data); [Rebuilding delta sync's read path](https://linear.app/blog/rebuilding-delta-sync-read-path)

### Inferences
- The design in the brief (append-only log, per-device cursor, HLC + per-column LWW) matches Figma's and cr-sqlite's merge rule and Linear's log/cursor model; the documented pitfalls to design for up front are idempotent mutation IDs per device (Replicache's `lastMutationID`, Linear's non-idempotent resend bug), an index for "actions after cursor X visible to tenant/user Y" (Linear's reconnect query shape), and a resync path when a device's cursor is older than retained history (baukit-sync's `resync_required`, Figma's fresh download then reapply).
- Teams that succeeded kept the server authoritative and used CRDT ideas selectively (per-property LWW, add-wins maps) rather than adopting full CRDT libraries for relational data.

### Gaps
- No primary source for Tuomas Artman's "Scaling the Linear Sync Engine" talk content was fetched; the client-side details come from an unofficial reverse-engineering study.
- No first-party effort estimates (engineer-months) were published by any of these teams in the sources found.
- A Rocicorp essay specifically titled around "generic sync" was not located; the Rocicorp blog index shows no 2025–2026 essays (latest post June 2024).

## Key question 3: Hybrid logical clocks (algorithm, encodings), per-column LWW and when it is wrong, tombstone compaction

### Takeaway
HLC (Kulkarni et al.) gives a 64-bit timestamp that respects happened-before and stays within clock-uncertainty of wall time (48 bits physical, 16 bits counter), which is why cr-sqlite, Ditto and most hand-rolled designs use it for per-column LWW; LWW is wrong for anything whose merge is not "keep one value" (counters, ordered lists, text, structural parent/child moves), and tombstones can only be dropped after every replica has either seen them or been forced to resync, which every system implements as a retention window plus a resync-from-zero rule.

### Cited Findings
- HLC algorithm: timestamp has `l` (largest physical time seen, locally or from messages) and `c` (counter ordering events with equal `l`); `l` advances when a larger `l` arrives or when physical time catches up, and `c` resets in both cases; goals are preserving happened-before, O(1) integer size, and staying close to physical time. — [Murat Demirbas, Hybrid Logical Clocks](https://muratbuffalo.blogspot.com/2014/07/hybrid-logical-clocks.html)
- Bounds: "l-pt is trivially bounded by ε" (clock uncertainty); with each node's clock advancing between events, `c < N*(ε+1)`; if message transit lets every clock advance by at least d, `c < ε/d+1`; experiments saw `c` in single digits. — [Murat Demirbas, Hybrid Logical Clocks](https://muratbuffalo.blogspot.com/2014/07/hybrid-logical-clocks.html)
- Encoding: keep the most significant 48 bits of the 64-bit NTP timestamp for `l` (microsecond granularity) and 16 bits for `c` (up to 65,536); on out-of-bound `l-pt` or `c`, reset to `(pt, 0)` and ignore out-of-bound messages; "HLC is being used in CockroachDB". — [Murat Demirbas, Hybrid Logical Clocks](https://muratbuffalo.blogspot.com/2014/07/hybrid-logical-clocks.html)
- Practical string encoding (Jared Forsyth, following James Long's "CRDTs for Mortals"): tuple `(ts, count, node)`; pack as zero-padded 15-digit ms timestamp, base-36 counter padded to 5, node id, joined by colons so plain string comparison orders them; `inc`: if wall clock is ahead adopt it with count 0, else keep ts and increment; `recv`: adopt the max of wall/local/remote ts, counter = max+1 when timestamps tie; advice to check client timestamps server-side and "raise a red flag if their too out of sync". — [Jared Forsyth, Hybrid Logical Clocks](https://jaredforsyth.com/posts/hybrid-logical-clocks/)
- Ditto encodes HLC as Unix-millisecond physical part plus per-peer logical counter and resolves REGISTER conflicts by latest HLC. — [Ditto glossary](https://docs.ditto.live/home/glossary)
- Why wall clocks alone fail: if replica B's clock is behind A's, a later write can receive a smaller timestamp; HLC fixes this by raising the counter when physical parts tie under happened-before. — [arXiv 1808.05698](https://arxiv.org/pdf/1808.05698)
- Per-column LWW mechanics in practice: cr-sqlite stores one `col_version` per column per row and merges by greatest version, tie-broken by greater value; crdt-lite assigns tombstones the highest possible column version so deletion beats any concurrent update; Talon resolves per field with HLC and optional drift limits that reject extreme skew; Figma applies LWW per property with the server deciding "last". — [crsql_changes](https://vlcn.io/docs/cr-sqlite/api-methods/crsql_changes); [Corrosion CRDT notes](https://superfly.github.io/corrosion/crdts.html); [crdt-lite source](https://docs.rs/crdt-lite/0.5.0/src/crdt_lite/lib.rs.html); [Talon conflict resolution](https://docs.page/jaaco/talon/concepts/conflict-resolution); [Figma multiplayer](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)
- When LWW is wrong: by definition the LWW register keeps only one value and a concurrent write "may have never been observed", so LWW silently drops updates; Figma's text fields lose one side's edit; Ditto advises against arrays because concurrent offline edits conflict and recommends MAPs (add-wins) instead; cr-sqlite offers counter and fractional-index column CRDTs precisely for counters and ordered lists; Ditto documents "husked" documents when DELETE and UPDATE race; Figma handles tree moves with parent-link plus fractional index in one property and server cycle rejection. — [arXiv 2602.19231](https://arxiv.org/pdf/2602.19231); [arXiv 1806.10254](https://arxiv.org/pdf/1806.10254); [Figma multiplayer](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/); [Ditto document model](https://docs.ditto.live/key-concepts/document-model); [cr-sqlite](https://github.com/vlcn-io/cr-sqlite); [Ditto delete](https://docs.ditto.live/crud/delete)
- Tombstone retention and resurrection: Cassandra "treats a deletion as an insertion" of a tombstone; `gc_grace_seconds` defaults to 864,000 s (ten days); a replica down longer than that may miss the delete and, once tombstones are gone, "Cassandra treats the object on the recovered node as new data, and propagates it to the rest of the cluster"; tombstones drop only at compaction, only when older than the grace period, and only when all older data for the partition is in the compaction. — [Cassandra tombstones](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/compaction/tombstones.html)
- Ditto: edge tombstone TTL 7 days, server 30 days, daily/hourly reaping, edge TTL must not exceed server TTL, offline-past-TTL devices miss deletes; batch deletes under 30,000 rows to avoid slowing sync. — [Ditto delete](https://docs.ditto.live/crud/delete)
- PowerSync compacts bucket history by replacing stale updates with markers while keeping checksums valid; clients whose bucket checksum mismatches drop and resync that bucket. — [PowerSync protocol](https://docs.powersync.com/architecture/powersync-protocol)
- baukit-sync purges tombstones behind a per-owner horizon and tells any client whose cursor is below the horizon to resync from zero. — [baukit-sync](https://docs.rs/crate/baukit-sync/latest)
- Figma deletes object data from the server entirely and keeps it only in the deleting client's undo buffer so documents do not grow. — [Figma multiplayer](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)

### Inferences
- A per-column LWW log needs an HLC per change row plus a deterministic tie-break (device id) so two devices never disagree; cr-sqlite's "greater value wins on tie" and Forsyth's node-id suffix are the two common choices. The server should validate incoming HLCs against its own clock and reject or clamp timestamps far in the future (Talon's drift limit, Forsyth's red flag), otherwise one skewed device's writes beat everyone's forever.
- Tombstones must outlive the longest acceptable device absence; the server can record a "horizon" (oldest retained log position per tenant) and any device presenting a cursor older than it must re-bootstrap rather than incrementally sync. Retention windows of 7–30 days are the observed defaults.
- Columns that are counters, orderings, or rich text should not be LWW columns; model them as increments in the log, fractional indices, or a CRDT document column respectively.

### Gaps
- The original HLC paper PDF could not be text-extracted via the fetch tool; the algorithm details are cited from the co-author's own blog summary rather than the paper body. The 2014 tech report URL is https://cse.buffalo.edu/tech-reports/2014-04.pdf.
- James Long's "Using CRDTs in the wild" (Actual's per-column LWW with HLC and a merkle trie) returned 404 at the fetched URL, so its specifics are not cited.

## Key question 4: Schema evolution with multiple device versions syncing the same log

### Takeaway
No engine in the set solves mixed-version sync; the mitigations in use are server-side schema hooks that force a full client reset (Zero), schema-as-views over schemaless JSON on the client so most migrations never touch the client (PowerSync), client-pulled migrations keyed on a reported schema version (Turso, Linear's schema hash), and, as a research direction, Cambria's bidirectional lenses that translate writes tagged with the writer's schema on read.

### Cited Findings
- Zero: with Postgres event triggers Zero "handles schema migration efficiently"; without them "any schema change triggers a full reset of all server-side and client-side state"; providers lacking event triggers must call `update_schemas()` after DDL. Offline clients may hold data that "may not work with the new schema". — [Zero connecting to Postgres](https://zero.rocicorp.dev/docs/connecting-to-postgres); [Zero offline](https://zero.rocicorp.dev/docs/offline)
- PowerSync applies the client schema as SQLite views over synced JSON "so schema migrations are generally not needed" on the client; column types are text/integer/real. — [PowerSync Swift SDK](https://docs.powersync.com/client-sdk-references/swift)
- Linear computes `__schemaHash` from all model/property metadata; a changed hash increments `schemaVersion`, which is passed to `IndexedDB.open` to trigger migration, and a full bootstrap is triggered when models are outdated. — [reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine)
- Turso's recommendation for offline-first fleets: clients report their schema version to a registry and pull the SQL they need, since a device offline for weeks may be several versions behind. — [Turso: schema changes to a million databases](https://turso.tech/blog/how-to-deploy-schema-changes-to-a-million-databases)
- Cambria (Ink & Switch): software cannot be upgraded everywhere at once, so both backward and forward compatibility are needed; lenses are bidirectional specs per schema change, versions form a graph, data moves along the shortest path; translation is "performed on read, not on write" and writes are tagged with the writer's schema; limitations: "Interoperability requires trading off between irreconcilable design goals", some lenses are not reversible (name splitting), `convert` weakens guarantees, some changes need outside data (inline object to ID). — [Cambria](https://www.inkandswitch.com/cambria/)
- Yjs forum: a migration that sets a new field can conflict with the same migration run by another client, with the winner determined by client-id priority; proposed mitigation is using the document version as the client id for migration writes (a suggestion, not a confirmed fix). — [Yjs: applying document migrations](https://discuss.yjs.dev/t/what-is-the-correct-way-to-apply-document-migrations/2321)
- An Apple patent describes keeping separate per-schema-version transaction logs on the server and rewriting an old log under the new schema when a device upgrades. — [US9244914B2](https://patents.google.com/patent/US9244914)
- Electric is schema-agnostic on the wire (shapes carry Postgres column values) and the auth guide notes it does not clear client data on logout; no migration guidance beyond this was found. — [Electric auth guide](https://electric.ax/docs/guides/auth)

### Inferences
- For a hand-rolled per-column log, the minimum is: (a) a schema version stamped on every log entry or batch; (b) additive-only changes (new nullable columns, new tables) tolerated by old clients, which ignore unknown columns; (c) a server minimum-supported-client-version that forces re-bootstrap for older clients; (d) destructive changes (renames, type changes, splits) staged as add-new, dual-write, backfill, then drop after the oldest supported client version has moved on. Cambria-style lenses are an option only if writes are stored with their schema tag.
- PowerSync's "views over JSON" trick is reproducible in SQLite on iOS; on a macOS Postgres client the equivalent is a raw JSONB row store with generated columns or views, at the cost of losing native Postgres typing on the client.

### Gaps
- No published production account of a per-column-LWW log surviving a column rename or type change across mixed client versions was found; the 2023 academic paper referenced in search results calling schema change an unsolved local-first problem was not fetched.

## Key question 5: Transport choices (HTTP long-poll, SSE, WebSocket), push vs pull, backoff, resuming from a per-device cursor

### Takeaway
The surveyed engines split between HTTP streaming/long-poll with a per-shape or per-bucket cursor (Electric, PowerSync, Replicache pull) and WebSocket with a monotonically increasing sync id (Zero, Linear, Figma); all of them pair a durable pull cursor with a contentless push hint, and none rely on push alone.

### Cited Findings
- Electric: `GET /v1/shape` with `offset` and `handle`; live mode long-polls with a 45 s default timeout (`liveRequestTimeoutMs`) and reconnects; `liveSse: true` uses Server-Sent Events, falling back to long-poll if SSE fails; `offset: 'now'` skips history; the design is explicitly CDN-cacheable HTTP. — [Electric TypeScript client](https://electric.ax/docs/api/clients/typescript); [Electric Postgres Sync](https://electric.ax/sync/postgres-sync)
- PowerSync: a session carries the JWT, current buckets and last op_id per bucket; the server streams checkpoint, ops, "checkpoint complete", then waits for the next checkpoint; "The stream can be interrupted at any time" and the client restarts from its last position; Swift, .NET and Flutter SDKs are "HTTP only, no WebSocket" (the service includes an `rsocket-router` package for the WebSocket variant used by other SDKs). — [PowerSync protocol](https://docs.powersync.com/architecture/powersync-protocol); [PowerSync supported platforms](https://docs.powersync.com/resources/supported-platforms); [powersync-service](https://github.com/powersync-ja/powersync-service)
- Replicache: pull on `pullInterval` is for development; production uses pokes, "contentless" hints over SSE, WebSockets or Pusher, after which the client pulls with its cookie. — [Replicache how it works](https://doc.replicache.dev/concepts/how-it-works)
- Zero: uses a WebSocket between client and zero-cache (the auth guide warns about Cross-Site WebSocket Hijacking); `disconnectTimeoutMs` defaults to one minute before the client enters `disconnected`; a 2026 user reports not yet having tested WebSocket scaling. — [Zero auth](https://zero.rocicorp.dev/docs/auth); [Zero offline](https://zero.rocicorp.dev/docs/offline); [Choosing a Sync Engine in 2026](https://johnny-sh.pages.dev/blog/choosing-a-sync-engine-in-2026)
- Linear: WebSocket handshake compares client and server `lastSyncId` and the client requests missing delta packets; the server broadcasts delta packets to all clients including the originator; the catch-up request is "an ID range intersected with very large permission and subscription sets". — [reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine); [Rebuilding delta sync's read path](https://linear.app/blog/rebuilding-delta-sync-read-path)
- Figma: reconnect downloads a fresh document copy, reapplies offline edits, then resumes over a new WebSocket. — [Figma multiplayer](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)
- Notion: moved from periodic polling (which "wouldn't scale to millions of users and devices") to server-emitted messages on per-page channels, with clients comparing `lastDownloadedTimestamp` to `lastUpdatedTime` on reconnect. — [How we made Notion available offline](https://www.notion.com/blog/how-we-made-notion-available-offline)
- Turso Sync is pull/push on demand only ("Sync happens only when you call `push()` or `pull()`"). — [Turso Sync](https://docs.turso.tech/sync)
- Ditto uses Bluetooth LE and local network (Bonjour) between peers plus a server URL; Bluetooth background modes are needed for sync while locked. — [Ditto Swift install guide](https://docs.ditto.live/sdk/latest/install-guides/swift)

### Inferences
- For an iOS client, Electric's and PowerSync's HTTP-only designs are notable: both vendors chose plain HTTP streaming/long-poll for Apple platforms, which survives proxies, CDNs and URLSession background behaviour better than WebSockets; a hand-rolled design can follow the same shape (a `GET /changes?cursor=…` long-poll with a 30–45 s timeout, optional SSE, and an opaque per-device cursor) and add a push notification or SSE "poke" only as an accelerator.
- The per-device cursor should be a server-assigned monotonic position (Linear's sync id, PowerSync's op_id, Electric's offset), not an HLC, because HLCs are device-generated and not gap-free; the HLC belongs on the change rows for merge ordering.

### Gaps
- None of the fetched docs publish their reconnect backoff schedules (Electric mentions reconnect after timeout; Zero mentions a one-minute disconnect threshold); jitter/backoff values would need to be read from SDK source.

## Key question 6: Security: per-device credentials, row filters by tenant and user, preventing one device from writing another user's rows

### Takeaway
Every engine with multi-user support enforces reads by deriving row filters from server-verified identity (JWT claims or a server-side context) and enforces writes exclusively in your own server endpoint; client-supplied parameters are explicitly untrusted, and the two engines with Swift SDKs (PowerSync, Ditto) differ in that PowerSync's write authorization is entirely yours while Ditto evaluates document-level permissions in its server.

### Cited Findings
- PowerSync: bucket parameters come from JWT claims (`sub` always, custom claims optional); "A client can pass any value for a Client Parameter" and client parameters "should not be used for access control purposes"; global buckets go to everyone; writes reach Postgres only through your `uploadData` endpoint, so write authorization is your backend's job; clients fetch JWTs through `fetchCredentials()` and the service validates them against your provider's JWKS or secret. — [PowerSync Sync Rules](https://docs.powersync.com/usage/sync-rules); [PowerSync Swift SDK](https://docs.powersync.com/client-sdk-references/swift); [PowerSync authentication setup](https://docs.powersync.com/installation/authentication-setup)
- Electric: your proxy sets `table`, `where`, `queryable_columns` and `secret` server-side from the authenticated user (example adds `org_id = $1` unless admin); gatekeeper tokens carry the shape definition as a claim and the proxy rejects mismatching requests; client subset queries can "only narrow results, never widen them"; "You _don't_ have to codify your auth logic into a database rule system"; Electric does not clear client-side data on logout. — [Electric auth guide](https://electric.ax/docs/guides/auth)
- Zero: `userID` segregates client storage per user; your query and mutate endpoints verify the token/cookie, build `ctx`, filter reads (`where('authorID', ctx.id)`) and check ownership in mutators; passing the server-verified `userID` to `handleQueryRequest`/`handleMutateRequest` "lets Zero enforce that only tabs belonging to the same user can be in the same client group"; `clientGroupID` can be stolen via XSS or logs; 401/403 disconnects the client into `needs-auth`; never `SameSite=None` on auth cookies. — [Zero auth](https://zero.rocicorp.dev/docs/auth)
- Replicache: the server is authoritative and re-runs mutators with its own logic; a different store `name` per user keeps data separate; Row Version strategy authorizes each data item "based on arbitrary code". — [Replicache how it works](https://doc.replicache.dev/concepts/how-it-works); [Replicache strategies](https://doc.replicache.dev/strategies/overview)
- Ditto: the sample app logs in with an authentication expiration handler and provider; `_id` "feeds into authorization rules"; permissions are evaluated against the Ditto Server identity service (the "Ditto Server" adds "identity, monitoring, and data integration"). — [Ditto Swift install guide](https://docs.ditto.live/sdk/latest/install-guides/swift); [Ditto document model](https://docs.ditto.live/key-concepts/document-model); [Ditto glossary](https://docs.ditto.live/home/glossary)
- Turso: a single database auth token (`turso db tokens create`) scopes access to a whole database; no row-level filtering is documented for sync. — [Turso Sync](https://docs.turso.tech/sync)
- Linear: access is encoded in per-user "sync groups" and clients cannot receive delta packets from workspaces or teams they lack permission to view; filtering is applied server-side before packets are returned. — [Rebuilding delta sync's read path](https://linear.app/blog/rebuilding-delta-sync-read-path)
- Figma: object IDs embed a client ID so offline creation is collision-free; the server validates structural operations (rejects cycles). — [Figma multiplayer](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)
- Device identity in Replicache/Zero: a random per-instance `clientID` with server-stored `lastMutationID` per client doubles as a per-device idempotency key; Zero binds client groups to the server-verified user. — [Replicache how it works](https://doc.replicache.dev/concepts/how-it-works); [Zero auth](https://zero.rocicorp.dev/docs/auth)

### Inferences
- A hand-rolled design should mirror these: issue a per-device credential (device id registered under a user and org, token with `sub`, `org_id`, `device_id` claims), derive every read filter server-side from those claims (never from request parameters), and have the write endpoint stamp or verify `org_id`/`user_id`/`device_id` on every change row from the token rather than trusting the payload. Per-device `lastMutationID`-style sequence numbers both deduplicate retries and let the server detect a device replaying another device's log.
- Because PowerSync and Electric both defer write authorization to your API, choosing either does not reduce the security work for writes; it only packages the read-path filtering.

### Gaps
- None of the vendor docs fetched describe per-device (as opposed to per-user) credentials or device revocation; the closest are Replicache/Zero client IDs and Ditto's device monitoring tier. Device-level revocation would be a custom addition in every option.
