# Path from one instance to multi-region for a small stateful Postgres-backed hub (managed hosts, no Kubernetes, no GCP/Cloudflare), as of late 2026

Scope note: research was done 2026-11-01. Items marked **(older)** predate 2024 or are undated; items marked **(archived)** are vendor pages the vendor itself has retired. Everything else was published or last updated 2024-2026 as far as the page states. Vendor pricing is quoted as shown on the vendor page on the research date and will drift.

## Step 1: two instances in one region, cross-instance command routing and live-event fan-out

### Takeaway
For a hub with small, infrequent writes and one WebSocket per device, PostgreSQL LISTEN/NOTIFY is a legitimate first fan-out bus *provided* the listener holds a dedicated session-mode connection (never a transaction-pooled one) and the payload carries only an id/cursor, not the change itself; the well-publicised 2025 scaling failure happened under tens of thousands of concurrent writers, not this workload. Device-affinity via `fly-replay` (Fly only) avoids a bus entirely but is lightly documented for WebSockets; Redis Pub/Sub and NATS Core are the same at-most-once semantics as NOTIFY, so none of the three is a durable queue and the change-log table must remain the source of truth with the bus acting as a wake-up signal.

### Cited Findings

**PostgreSQL LISTEN/NOTIFY semantics (official docs)**
- Payload: "In the default configuration it must be shorter than 8000 bytes. (If binary data or large amounts of information need to be communicated, it's best to put it in a database table and send the key of the record.)" — [PostgreSQL docs: NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)
- Delivery only to connected listeners that have executed `LISTEN`; notifications sent inside a transaction "are not delivered until and unless the transaction is committed", and a listening session inside a transaction receives them "just after the transaction is completed", so "notification events are only delivered between transactions." — [PostgreSQL docs: NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)
- Ordering: "NOTIFY guarantees that notifications from the same transaction get delivered in the order they were sent. It is also guaranteed that messages from different transactions are delivered in the order in which the transactions committed." — [PostgreSQL docs: NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)
- Duplicate folding: identical channel+payload within one transaction is delivered once; distinct payloads and different transactions are never folded. — [PostgreSQL docs: NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)
- Queue: "If this queue becomes full, transactions calling NOTIFY will fail at commit. The queue is quite large (8GB in a standard installation)"; a listener stuck in a long transaction blocks cleanup; monitor with `pg_notification_queue_usage`. — [PostgreSQL docs: NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)
- The docs do not promise durability: a disconnected listener misses everything sent while it was away (follows from "sends ... to each client application that has previously executed LISTEN"). — [PostgreSQL docs: NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)

**The 2025 "does not scale" incident and the global commit lock**
- Recall.ai had three downtime periods 19-22 March 2025; the lock seen was `AccessExclusiveLock on object 0 of class 1262 of database 0`, taken in `PreCommit_Notify` at COMMIT for any transaction that issued NOTIFY; "This lock effectively ensures that only a single COMMIT query can be handled at a time." Workload was "tens of thousands of simultaneous writers." They removed NOTIFY from that path in under a day. Their post has an update saying the bottleneck was later "Fixed in Postgres core." — [Recall.ai: Postgres LISTEN/NOTIFY does not scale](https://recall.ai/blog/postgres-listen-notify-does-not-scale)
- DBOS's counter-post argues NOTIFY scales if you buffer/batch so the lock is taken on flush, which only works when notifications are not the source of truth. — [DBOS: Postgres LISTEN/NOTIFY Actually Scales](https://dbos.dev/blog/postgres-listen-notify-scalability)
- Hackers-list work in 2025: a proposed docs patch describing the global lock and O(N²) duplicate checking; Joel Jacobson's partitioned-channel-lock proposal (July 2025) and his statement that the heavyweight lock in `PreCommit_Notify()` remained a separate problem; a race-condition fix ("Fix LISTEN startup race with direct advancement") is listed as committed for the PG20 cycle. — [pgsql-hackers thread: docs LISTEN/NOTIFY performance considerations](https://postgrespro.com/list/thread-id/2743933); [Optimize LISTEN/NOTIFY thread](https://www.postgresql.org/message-id/02a7cd37-e2fc-4212-8b19-f8c239c95fb8@app.fastmail.com); [CommitFest patch 6787](https://commitfest.postgresql.org/patch/6787/)
- Conflict: Recall.ai's update says the lock is "Fixed in Postgres core"; the hackers-list material I found confirms committed race fixes but I did not find the specific commit that removes the global lock or the release it ships in. Treat "fixed" as unverified for a specific PG version.

**Connection poolers**
- PgBouncer feature table: `LISTEN` is supported in session pooling, "Never" in transaction pooling; `NOTIFY` works in both, which is why the failure is silent (the LISTEN lands on a backend that is returned to the pool). Workarounds: a dedicated direct connection for the listener, or a second PgBouncer in session mode. — [Netdata guide: PgBouncer LISTEN/NOTIFY in transaction mode](https://www.netdata.cloud/guides/pgbouncer/pgbouncer-listen-notify-transaction-mode/); [PgBouncer issue #655](https://github.com/pgbouncer/pgbouncer/issues/655)
- Oban (Elixir job queue) documents the same: transaction pooling "disables all of PostgreSQL's LISTEN and NOTIFY activity". — [Oban troubleshooting](https://hexdocs.pm/oban/2.14.2/troubleshooting.html)
- Relevance: Fly Managed Postgres bundles PgBouncer on all plans ("All plans include high availability, backups, and connection pooling"), so a hub on MPG must route its LISTEN connection around the pooler. — [Fly.io docs: Managed Postgres](https://docs.fly.io/mpg/)

**Redis Pub/Sub and NATS as alternatives**
- Redis Pub/Sub is fire-and-forget: messages reach only clients connected at that moment; slow subscribers are disconnected under load. NATS Core is "at-most-once"; NATS JetStream adds persistence and "at-least-once" (NATS Server 2.2+), with redelivery limits and replay by time or sequence. — [dev.to: Redis 8 Pub/Sub vs NATS 2.11 JetStream](https://dev.to/johalputt/deep-dive-into-redis-8-pubsub-and-nats-211-jetstream-for-real-time-messaging-4pke); [dev.to: Pub/Sub patterns Redis vs NATS](https://dev.to/young_gao/pubsub-messaging-patterns-redis-nats-and-when-to-use-what-2el2)
- Centrifugo (Go realtime server) scales nodes via Redis as broker; a single Redis is bound by one CPU core and Redis Cluster can make Pub/Sub throughput worse, so Centrifugo shards channels across standalone Redis instances with Jump consistent hashing, or (PRO) uses Redis 7 sharded Pub/Sub. — [Centrifugo blog, June 2026: Scaling Redis Pub/Sub](https://centrifugal.dev/blog/2026/06/29/scaling-redis-pub-sub); [Centrifugo PRO scalability docs](https://centrifugal.dev/docs/pro/scalability)
- Soketi (Pusher-protocol server) uses a Redis adapter "to enable node-to-node or process-to-process communication when scaling horizontally". — [Soketi docs: Redis configuration](https://sweetsunnyflower.gitbook.io/soketi/advanced-usage/horizontal-scaling/redis-configuration)

**Phoenix Channels: the "which bus" decision made by a mature framework**
- `phoenix_pubsub_postgresql` runs Phoenix.PubSub over LISTEN/NOTIFY so "multiple nodes of a Phoenix application talk through a shared database" with no extra service; payloads are term-encoded, compressed, Base85'd to fit the NOTIFY limit. — [hex.pm: phoenix_pubsub_postgresql 0.7.0](https://preview.hex.pm/preview/phoenix_pubsub_postgresql/0.7.0)
- The PushEx guide ranks the options: native distributed Erlang first ("removing a single networking bottleneck"), Redis as the fallback when nodes cannot reach each other but can reach a central Redis, which "adds a single networked point of failure." — [PushEx: Phoenix PubSub](https://push-ex.hexdocs.pm/pub_sub.html)

**Device affinity via the proxy (Fly only)**
- `fly-replay` fields: `region`, `instance` (a specific Machine ID), `app`, `state` (echoed back in `fly-replay-src`), `elsewhere`, `prefer_instance`, `timeout`, `fallback`. "Requests larger than 1MB cannot be replayed." For WebSockets, the app returning `fly-replay` "should not negotiate a web socket upgrade itself"; the target Machine handles the upgrade. Replay caching "is an optimization, not a guarantee." — [Fly.io docs: Dynamic Request Routing with fly-replay](https://docs.fly.io/reference/fly-replay)
- `fly-force-instance-id` request header: "Forces routing to a specific Machine", retried if unhealthy, "No fallback if Machine is ultimately unavailable." Browser/JS WebSocket clients cannot set custom headers, hence server-side replay before upgrade is the workable pattern; native Mac/iOS clients *can* set headers. — [Fly.io docs: fly-replay](https://docs.fly.io/reference/fly-replay); [Fly community: force WebSocket to a specific machine](https://community.fly.io/t/request-force-websockets-requests-to-a-specific-machine-from-client/21713)
- Community reports of `instance=` replays failing silently or hanging; one reply attributes it to crossing an app boundary without `app=`. — [Fly community: fly-replay to specific instance failing](https://community.fly.io/t/fly-replay-to-specific-instance-failing-despite-machine-being-started-and-responsive/26928)
- Render and Railway do not offer sticky sessions: Railway "does not support sticky sessions"; with replicas it routes "randomly" within the nearest region, and Socket.IO users report connections bounced between replicas; the official guide says "any replica can receive any request" and to keep session state in Redis or a DB. — [Railway docs: Scaling](https://docs.railway.com/deployments/scaling); [Railway guide: Multi-region API with failover](https://railway.com/guides/multi-region-api-failover); [Railway Station: WebSockets](https://station.railway.com/questions/websockets-1bda16bd); [Railway Station: Sticky sessions feature request](https://station.railway.com/feedback/sticky-sessions-fa65efc4)
- AWS App Runner is not a WebSocket host: AWS re:Post describes it as for "standard HTTPS based apps" and points to ALB+ECS or API Gateway for WebSockets; multiple users report hangs. **(older, 2021-2024 sources)** — [AWS re:Post: WebSockets on App Runner](https://www.repost.aws/ko/questions/QU0jOAcOoTQqigUj6B9oGDxg/websockets-on-apprunner); [xlwings docs: App Runner](https://server.xlwings.org/en/latest/aws_app_runner/)

**Comparable products**
- Figma: "The server spawns a separate process per multiplayer document to which every concurrent editor of that document connects", one authoritative reconciler per doc; rewritten from TypeScript to Rust. **(older, 2019 blog as summarised)** — [sysdesign-wiki summary of Figma multiplayer post](https://sysdesign-wiki.pages.dev/sources/2019-figma-how-figmas-multiplayer-technology-works/)
- Linear: mutations apply locally, push to server, server "broadcasts deltas back to other clients via WebSocket"; stack "React, TypeScript, MobX, Postgres, a CDN". Reverse-engineering notes say each delta action carries a sync id so clients can detect missed packets. Linear's own "Scaling the Linear sync engine" page (June 2023) is a talk announcement with no server-topology detail. — [HN discussion: How's Linear so fast](https://hackernews-dynamic.seasondane.workers.dev/news/48437609); [skcript: reverse-linear-sync-engine](https://github.com/skcript/reverse-linear-sync-engine); [Linear blog: Scaling the Linear sync engine](https://linear.app/blog/scaling-the-linear-sync-engine)
- Ably: clusters span 2-10 AWS regions, each region runs its own connections and channel management, cross-region flow is peer-to-peer, unhealthy regions have traffic sent to the nearest healthy one. — [Ably docs: What is Ably](https://ably.com/docs/basics/ably)

### Inferences
- The hub's writes are "small and infrequent" and per-tenant; the NOTIFY global commit lock is a many-concurrent-writers problem and will not bite at this scale. The two real hazards are the pooler (silent loss of LISTEN) and durability (missed notifications while a node is reconnecting). Both are solved by: dedicated non-pooled LISTEN connection per instance; payload = `{tenant_id, seq}` only; receivers treat NOTIFY as a hint and re-query the change log from their cursor, so the per-tenant sequence, not the bus, is the correctness mechanism.
- For command routing (device A's command to device B on another instance), NOTIFY with a channel per instance or per tenant is sufficient at this scale; the same "hint + table" pattern (write command row, NOTIFY, holder of B's socket delivers and acks) gives at-least-once with idempotency by command id. Redis/NATS add a second stateful service and do not improve semantics unless JetStream/Streams are used.
- Device affinity with `fly-replay instance=` is attractive because the hub already keeps routing in process memory, but it locks the design to Fly and is reported flaky; it also does not survive the pinned Machine being replaced in a deploy. A bus (NOTIFY first, Redis/NATS later) is portable across all four hosts; affinity is not.
- Choosing a host now: Render, Railway and Fly can all run two instances; App Runner cannot host the WebSocket. ECS Fargate behind an ALB can (ALB supports WebSockets and sticky sessions) but adds the most ops.

### Gaps
- I did not find a confirmed PostgreSQL release that removes the NOTIFY global commit lock; the Recall.ai "fixed in core" note is unverified against release notes.
- No primary-source Linear or Figma document describing their cross-server fan-out bus (Redis vs other) was found; only secondary summaries.
- No Fly documentation stating how `fly-replay instance=` behaves when the target Machine is mid-replacement during a rolling deploy.

## Step 2: zero-downtime deploys with WebSockets

### Takeaway
No managed host keeps an existing WebSocket alive across a deploy; all of them overlap old and new instances for the HTTP handshake and then terminate the old one after a grace window (Render: 60 s then SIGTERM, 30 s default up to 300 s to SIGKILL; Fly: SIGINT, 5 s default up to 300 s `kill_timeout`, best-effort). The client therefore carries the correctness: reconnect with jittered backoff and resume from its per-tenant cursor, and the server should close sockets deliberately (code 1001) on SIGTERM rather than let the host kill them.

### Cited Findings
- Render (article dated 1 April 2026): a new instance starts while the old serves; traffic switches once health passes; "The old instance keeps running for 60 seconds after traffic switches, and Render then sends it SIGTERM"; default shutdown delay 30 s, raisable to 300 s with `maxShutdownDelaySeconds`, then SIGKILL. "For long-lived connections like WebSockets or Server-Sent Events (SSE), zero-downtime routing applies only to the initial HTTP handshake. When the old instance eventually terminates, active WebSocket connections break." A persistent disk disables zero-downtime deploys. A health endpoint that returns 200 on boot before dependencies are ready is called out as a common mistake. — [Render: How Render handles zero-downtime deploys](https://render.com/articles/how-render-handles-zero-downtime-deploys)
- Railway: "Railway will wait for this endpoint to serve a 200 status code before switching traffic to your new deployment"; health check times out after 300 s and the deploy fails. No Railway documentation on WebSocket draining was found; a community template recommends sending close code 1001 on shutdown so clients reconnect quickly. — [Railway docs: Healthchecks](https://docs.railway.app/deploy/healthchecks); [Railway template: WebSocket + HTTP on one port](https://railway.com/deploy/websocket-node-server-sharing-one-port-with-http--websocket-or-node--1)
- Fly: default stop signal is SIGINT; `kill_timeout` "default is 5 seconds. You can set it up to a maximum of 300 seconds (5 minutes)", "should be considered best-effort", then SIGTERM. Strategies: `rolling` (default; "One by one, each running Machine is taken down and replaced"), `immediate`, `canary`, `bluegreen` ("For every running Machine, a new one is booted alongside it in the same region", requires a health check, not for volumes). `max_unavailable` default 0.33. The config reference says nothing about how Fly Proxy treats existing WebSocket connections when a Machine stops. — [Fly.io docs: fly.toml configuration reference](https://docs.fly.io/reference/configuration/)
- Fly's archived Postgres page states the general point: apps "with long-lived connections such as WebSockets, are poor fits" for the replay-to-primary model. **(archived)** — [Fly.io docs (archived): HA and global replication](https://docs.fly.io/postgres/high-availability-and-global-replication)
- The `websockets` library's Render guide pattern: `/healthz` endpoint plus "closes connections and exits cleanly when it receives a SIGTERM signal." **(library v12 docs)** — [websockets: Deploy to Render](https://websockets.readthedocs.io/en/12.0/howto/render.html)

### Inferences
- The hub already has the right primitive: a monotonic per-tenant cursor. Reconnect-and-resume-from-cursor makes deploy-induced disconnects invisible to the sync result; only latency suffers. The 25 s long-poll is naturally deploy-safe if the server returns early (empty) on SIGTERM and clients retry.
- Set the host's grace window (Render `maxShutdownDelaySeconds`, Fly `kill_timeout`) to at least the long-poll duration plus a few seconds so in-flight polls complete, and have the hub stop accepting upgrades and fail its health check as soon as SIGTERM arrives so the proxy stops routing new handshakes to it.
- On a two-instance deploy, fan-out via NOTIFY (Step 1) means a device whose socket moved from instance A to B during a deploy still receives events, because B listens on the same channels; with device affinity instead, the pinned Machine ID changes on every deploy and the routing table must be rebuilt.

### Gaps
- No official Fly statement found on whether Fly Proxy drains (stops routing new connections to) a Machine between SIGINT and kill; the connection-draining blueprint URL returned 404.
- No published measurements of client reconnection storms on these hosts for small fleets.

## Step 3: database high availability in one region

### Takeaway
Every managed Postgres candidate offers in-region HA with automatic failover and dropped connections, but they differ sharply in what they publish: RDS Multi-AZ two-readable-standby is the only one with a quoted failover figure ("typically under 35 seconds") and synchronous replication; Crunchy Bridge HA is a hidden hot standby with no published timing or sync/async statement; Neon has no standby at all (multi-AZ storage, compute rescheduled in "1-10 minutes" on AZ loss); Fly MPG says "high availability with automatic failover" and nothing more. True RPO=0 requires synchronous commit, which the PostgreSQL docs warn can block commits forever if the sync standby dies.

### Cited Findings
- PostgreSQL synchronous replication: each commit "will wait until confirmation is received that the commit has been written to the write-ahead log on disk of both the primary and standby server"; "The minimum wait time is the round-trip time between primary and standby"; `remote_apply` "allows for load balancing with causal consistency"; quorum via `synchronous_standby_names = 'ANY 2 (s1, s2, s3)'`; "Such transaction commits may never be completed if any one of the synchronous standbys should crash." — [PostgreSQL docs: High Availability, Load Balancing, and Replication](https://www.postgresql.org/docs/current/warm-standby.html)
- RDS Multi-AZ with two readable standbys (PostgreSQL and MySQL): failover "typically under 35 seconds"; the AWS engineering blog cites "typically 20 seconds" and attributes time to standby apply lag plus DNS propagation. Third-party tables put classic single-standby Multi-AZ at 60-120 s. — [AWS: RDS Multi-AZ](https://aws.amazon.com/rds/features/multi-az); [AWS Database Blog: Multi-AZ with two readable standbys under the hood](https://aws.amazon.com/blogs/database/amazon-rds-multi-az-with-two-readable-standbys-under-the-hood); [barkingiguana: Designing RDS for AZ failover](https://barkingiguana.com/writing/designing-rds-for-az-failover-and-cross-region-recovery/)
- Crunchy Bridge HA: "the control plane creates a hidden hot standby which receives the same writes as your primary database cluster"; on failure it will "promote the standby to replace the impacted cluster in an instant"; "all existing connections will be dropped"; "your connection string does not change"; "HA standby instances are always the same size as the instance they back up"; not on Hobby plans. Sync vs async and measured failover time are not stated. — [Crunchy Bridge docs: High availability](https://docs.crunchybridge.com/concepts/high-availability)
- Neon: "Safekeepers are distributed across multiple Availability Zones (AZs)" for WAL; secondary Pageservers; compute runs in one AZ at a time; Postgres crash restarts in "a few seconds", node failure "1-2 minutes", AZ failure "1-10 minutes"; temporary tables, prepared statements and cache "will not persist across a failover"; "we currently do not support real-time replication across different cloud regions." Neon's pricing page: "multi-AZ storage (high availability without standbys)" on all plans; uptime SLA only on Scale. — [Neon docs: High availability](https://neon.com/docs/introduction/high-availability); [Neon pricing](https://neon.com/pricing)
- Fly Managed Postgres: "A highly-available Postgres cluster"; "Storage is replicated across all nodes in your cluster"; HA, backups and PgBouncer on all plans; Postgres 16/17 chosen at creation, "you can't upgrade a cluster in place"; alerting limited to maintenance emails. Node count, failover mechanism and PITR window are not documented on the overview. — [Fly.io docs: Managed Postgres overview](https://docs.fly.io/mpg/overview/); [Fly.io docs: Managed Postgres](https://docs.fly.io/mpg/)
- Fly unmanaged Postgres (Flex) is retired: "This page is archived. Fly Postgres (unmanaged) is no longer maintained." A June 2026 community incident on a 3-node Flex cluster split 2×`sin` + 1×`nrt`: automatic failover at 06:53 UTC, the old primary restarted at 09:12 as a "zombie" with a `zombie.lock`, failed its health check yet "kept receiving connections through `.flycast`", causing about three hours of intermittent write failures until the operator ran `fly machine stop`. No Fly staff replied; a community member noted clustering is designed for all members in one region. — [Fly.io docs (archived): HA and global replication](https://docs.fly.io/postgres/high-availability-and-global-replication); [Fly community: Postgres Flex zombie primary](https://community.fly.io/t/postgres-flex-a-former-primary-db-machine-came-back-as-a-zombie-and-kept-serving-read-only-writes/28167)
- Aurora Global Database (also relevant in-region): RTO "in the order of minutes", RPO "typically measured in seconds". — [AWS docs: Aurora Global Database switchover/failover](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database-disaster-recovery.html)
- Client pool recovery: sqlx `PgPoolOptions::test_before_acquire` defaults to true (checks a connection before handing it out) in the 0.5.x source I could verify; no sqlx-specific failover report was found. A Go pgx report describes an app hanging during an RDS Multi-AZ failover and failing afterward until restart, the failure mode to test for. **(sqlx source is old version)** — [sqlx-core 0.5.5 pool options source](https://docs.rs/crate/sqlx-core/0.5.5/source/src/pool/options.rs); [golang-nuts: pgx during RDS failover](https://groups.google.com/g/golang-nuts/c/SScngL0SiOQ/m/sjvdK6DiAwAJ)
- A payments post-mortem (undated): a 300 s DNS TTL left "half our fleet ... still hammering the dead primary", and one service's pool "cached the resolved IP at startup and never re-resolved." — [jaykoh: The incident that changed everything](https://jaykoh.pages.dev/blog/disaster-recovery-payment-systems)

### Inferences
- For "a reader never misses a change it was told exists", in-region HA with async standby is acceptable only if the hub treats a post-failover sequence regression as a hard error rather than silently continuing: after reconnect, compare the max sequence per tenant with what was last acknowledged to clients; if the new primary is behind, the lost tail must be re-requested from devices (which still hold their local copies). Sync replication (RDS two-standby, or a self-configured `synchronous_standby_names`) removes this case at the cost of commit latency and availability coupling.
- Among the managed options only RDS documents sync replication to standbys; Crunchy Bridge's "receives the same writes" is ambiguous and should be confirmed with their support before relying on RPO=0.
- Pool configuration matters as much as the database: short DNS TTL honouring, `test_before_acquire`, bounded `max_lifetime`, and a reconnect loop on the dedicated LISTEN connection.

### Gaps
- No published failover time for Crunchy Bridge, Fly MPG or Neon compute beyond the ranges above; no statement whether Crunchy Bridge or Fly MPG replication is synchronous.
- No current (0.7/0.8) sqlx documentation on behaviour across a primary failover was retrieved; needs a local test (restart Postgres under load, observe `acquire()`).

## Step 4: multi-region, single-writer

### Takeaway
Every realistic multi-region design for this hub keeps one writer region and forwards writes to it; the cross-region options are Aurora Global Database (switchover RPO 0 and "typically under 30 seconds" on recent engine versions; unplanned managed failover RPO in seconds with explicit split-brain warnings), Crunchy Bridge cross-region/cross-provider replicas that can be detached into a standalone primary, RDS cross-region read replicas promoted manually, and Fly `fly-replay region=` for the app layer. Neon and Supabase do not offer cross-region replication of a single project (Supabase replicas are async and geo-routed for GET only). Monotonic reads from a lagging replica need an LSN or sequence fence: PostgreSQL 19's `WAIT FOR LSN` (or polling `pg_last_wal_replay_lsn()`) or, simpler for this hub, compare the replica's max per-tenant sequence with the client's cursor and replay to the primary when behind.

### Cited Findings

**Aurora Global Database**
- RTO "can be in the order of minutes"; RPO "typically measured in seconds". Switchover (planned): waits for sync, "RPO is 0 (no data loss)", and "On qualifying engine versions (... Aurora PostgreSQL 16.8, 15.12, 14.17, 13.20, or higher), switchover recovery time for read/write operations is typically under 30 seconds." Managed failover (unplanned): "doesn't wait for data to synchronize"; "Typically, the chosen secondary cluster assumes the primary role within a few minutes"; Aurora attempts "write fencing" but "Because fencing writes is a best-effort attempt, it's possible that writes might be momentarily accepted in the old primary Region, causing split-brain issues"; old primary is rebuilt as a secondary and a snapshot `rds:unplanned-global-failover-...` is taken for recovering lost writes. Recommendation: use the global writer endpoint and reduce DNS TTL "to a low value such as 5 seconds". `rds.global_db_rpo` (20 s minimum) blocks commits on the primary when all secondaries exceed the RPO. Requires matching engine versions. — [AWS docs: Aurora Global Database switchover/failover](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database-disaster-recovery.html)
- Billing: "you pay for replicated write I/Os between the primary region and each secondary region"; AWS re:Post confirms it applies under both Standard and I/O-Optimized. A third-party blog quotes roughly $0.20 per million replicated write I/Os (unverified). Each secondary region also needs its own instances and storage. — [AWS: Aurora Global Database](https://aws.amazon.com/rds/aurora/global-database); [AWS re:Post: cost for replicated IOPS](https://repost.aws/questions/QUWhW5EG0ERi258BUs5IqHFA/cost-for-replicated-iops-in-aurora-global-database); [Bytebase: Aurora pricing explained](https://www.bytebase.com/blog/understanding-aws-aurora-pricing)
- Headless secondary clusters (storage only, no instance) exist but "you must add a DB instance" before failing over to one. — [AWS docs: Aurora Global Database switchover/failover](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database-disaster-recovery.html)

**RDS cross-region read replica**
- Replicas are promoted via console, `promote-read-replica`, or `PromoteReadReplica`; replication is asynchronous so RPO is the observed `ReplicaLag`; a smaller DR replica "may result in increased replication lag"; scaling it up before promotion adds to RTO. — [AWS Database Blog: migrate Aurora/RDS to a new region](https://aws.amazon.com/blogs/database/migrate-amazon-aurora-and-amazon-rds-to-a-new-aws-region); [AWS re:Post: lower instance size cross-region replica for DR](https://repost.aws/questions/QU-gKy7b7mRWuM2TZKLYGwqA/aws-rds-postgres-lower-instance-size-cross-region-read-replica-for-dr-site)

**Crunchy Bridge**
- "provision read replicas across regions and infrastructure provider"; replica must match storage size; "Detach Replica ... will create a standalone instance holding the data at the time of the detach action"; each replica billed as a full cluster. Sync/async and lag not stated. — [Crunchy Bridge docs: Replicas](https://docs.crunchybridge.com/how-to/replicas)

**Neon and Supabase**
- Neon: "In the event of a region-wide outage, your data is not automatically replicated to another region"; cross-region replication unsupported; read replicas are same-region computes that "count toward CU-hours". — [Neon docs: High availability](https://neon.com/docs/introduction/high-availability); [Neon pricing](https://neon.com/pricing); [Neon community: multi-region deployments](https://community.neon.tech/t/multiregion-deployments/1022)
- Supabase read replicas: "Replication is asynchronous"; load balancer does "geo-routing for Data API requests to automatically route GET requests to the database closest to your user"; non-GET and all Auth go to the primary; replication lag acknowledged; promotion of a replica on primary failure is not documented. — [Supabase docs: Read Replicas](https://supabase.com/docs/guides/platform/read-replicas)

**Fly.io app-layer routing**
- Anycast: "We announce global IP blocks from all of our datacenters over BGP"; Fly Proxy terminates TLS at the edge and forwards "to the nearest available Machine" over WireGuard backhaul; `Fly-Prefer-Region` request header and `fly-replay` response header steer placement. — [Fly.io docs: Fly Proxy](https://fly.io/docs/reference/fly-proxy/); [Fly.io docs: Public network services](https://fly.io/docs/networking/services/)
- Archived pattern for writes from a replica region: app catches the read-only error and responds with `fly-replay: region=<primary>` (Rails example used HTTP 409); replicas "usually eventually consistent, and can fall behind the leader"; the page suggests session version counters or timestamps to detect stale reads and replay to the primary. Inter-region private network traffic is billed from February 2026. **(archived)** — [Fly.io docs (archived): HA and global replication](https://docs.fly.io/postgres/high-availability-and-global-replication); [Fly.io docs: Managed Postgres](https://docs.fly.io/mpg/)
- Fly staff view on cross-region DB failover: "Automatic failover between regions is risky, and not something Postgres is designed for" and the "cost and UX complexity ... is not worth it for full stack app developers." **(undated forum post)** — [Fly community: Postgres HA single vs multi region](https://community.fly.io/t/postgres-high-availability-single-vs-multi-region-leader-replica/4601/2)

**Read-your-writes and monotonic reads on a replica**
- PostgreSQL 19 adds `WAIT FOR LSN`: capture `pg_current_wal_insert_lsn()` *after* commit on the primary, pass it to the replica session, which blocks until replay passes it; must run with no snapshot held; errors by default on timeout (`NO_THROW` returns status); "WAIT FOR compares LSN positions without understanding timelines," so after a promotion a success may refer to a different timeline. The earlier `pg_wal_replay_wait()` procedure commit is the precursor. Polling `pg_last_wal_replay_lsn()` is the pre-19 approach. — [rednafi: Reading your own writes with WAIT FOR LSN in Postgres 19](https://rednafi.com/system/wait-for-lsn/); [ClickHouse blog: PostgreSQL 19 WAIT FOR](https://clickhouse.com/blog/postgresql-19-wait-for-read-your-writes); [PostgreSQL commit: Implement WAIT FOR command](https://forger.sitiv.fr/open-dsi/postgres/commit/447aae13b0305780e87cac7b0dd669db6fab3d9d)
- `synchronous_commit = remote_apply` "allows for load balancing with causal consistency" at the cost of commit latency equal to the round-trip. — [PostgreSQL docs: warm standby](https://www.postgresql.org/docs/current/warm-standby.html)

**Routing without Cloudflare**
- Route 53 health checks monitor endpoints, other health checks, or CloudWatch alarms; DNS failover routes "from an unhealthy resource to a healthy resource"; Application Recovery Controller adds routing-control health checks. A health check is healthy when at least 18% of global checkers report healthy; DNS-based failover is subject to client TTL caching. — [AWS docs: Route 53 health checks](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/dns-failover.html); [AWS Networking blog: DR mechanisms with Route 53](https://aws.amazon.com/blogs/networking-and-content-delivery/creating-disaster-recovery-mechanisms-using-amazon-route-53)
- Global Accelerator: two static anycast IPv4 addresses (four with dual-stack); "instantly begins directing traffic for all new connections to another available endpoint when it determines that an active endpoint is unhealthy"; endpoints are NLB, ALB, EC2 or EIP; TCP idle timeout 340 s and "You cannot use TCP keep-alive packets to maintain an open connection" (a WebSocket must send at least one byte within 340 s); established connections keep going to the old endpoint until idle timeout even if it is unhealthy; if no endpoint is healthy it routes to all. — [AWS docs: How Global Accelerator works](https://docs.aws.amazon.com/global-accelerator/latest/dg/introduction-how-it-works.html)
- A DAZN WebSocket failover test noted that a service "could be performing badly and still respond to the health check requests." **(older)** — [Medium (DAZN): failover strategy with Route 53](https://medium.com/dazn-tech/how-to-implement-the-perfect-failover-strategy-using-amazon-route53-1cc4b19fa9c7)
- Railway: "automatically route public traffic to the nearest region"; guide for multi-region API with failover exists. — [Railway guide: Multi-region API with failover](https://railway.com/guides/multi-region-api-failover)

### Inferences
- Because the hub's correctness anchor is the server-assigned per-tenant sequence, a replica-region hub can answer a long-poll or WebSocket subscription only if `max(seq) for tenant on replica >= client cursor`; otherwise it must `fly-replay region=primary` (Fly) or proxy the request to the primary region itself (any host). This is a cheaper, timeline-safe fence than WAIT FOR LSN because the sequence is already in the data model. Writes always go to the primary region; sequence assignment therefore never needs cross-region coordination.
- "Fail-safe" at each tier realistically means: Step 1-2, survive an instance crash and deploys (seconds of reconnect); Step 3, survive an AZ or DB node loss (20 s to minutes, connections dropped, possible lost tail unless sync); Step 4, survive a region loss with a *human-initiated* promotion (minutes to hours, seconds of data loss unless planned switchover) plus DNS/anycast re-steering. Automatic cross-region DB failover is explicitly discouraged by Fly staff and comes with split-brain caveats from AWS; a documented runbook (pre-created secondary, tested promotion, low TTL, app fencing of writes to the old region) is the realistic target.
- Host/database choices that do not block later stages: Crunchy Bridge (cross-region, cross-provider replica + detach) and AWS Aurora/RDS (Global Database or cross-region replica) keep Step 4 open; Neon and Supabase cap out at same-region HA/replicas for a single project; Fly MPG today documents no cross-region replica. On the app side Fly (anycast + replay) and AWS (Route 53 / Global Accelerator) are the two routing stories without Cloudflare; Railway has nearest-region routing but no sticky sessions; Render has no documented multi-region routing in the sources found.

### Gaps
- No Fly MPG documentation on cross-region replicas, PITR window, node count or failover timing.
- No Supabase statement on promoting a read replica after primary-region loss.
- No published Route 53 end-to-end failover timing including resolver TTLs for a WebSocket client population; Global Accelerator health-check interval defaults were not extracted.
- Crunchy Bridge replica replication mode (async assumed) and detach duration not documented.

## Active-active multi-writer Postgres (pgEdge/Spock, EDB PGD) and why it is the wrong fit

### Takeaway
Multi-master logical replication products solve ID collisions with node-partitioned or Snowflake-style sequences and resolve row conflicts after the fact; a server-assigned, gapless, per-tenant monotonic sequence is exactly the property they cannot provide without "only ever write to one node" (which is single-writer again) or eager/synchronous commit across regions (which gives up the latency they exist for).

### Cited Findings
- pgEdge Spock provides multi-master replication for PostgreSQL 14+ (README) or 15+ (docs page); its sequence answer is Snowflake Sequences, "an int8 and sequence based unique ID solution to optionally replace the PostgreSQL built-in bigserial"; conflict handling is "conflict-free delta-apply for running totals" plus ACE (Active Consistency Engine) for reconciliation. Material is vendor-authored. — [pgEdge/spock on GitHub](https://Www.github.com/pgEdge/spock); [pgEdge: What is multi-master distributed Postgres](https://pgedge.com/solutions/benefit/multi-master); [pgEdge blog: Navigating distributed PostgreSQL options](https://www.pgedge.com/blog/navigating-distributed-postgresql-options-pglogical-and-beyond)
- EDB PGD: "For INSERT/INSERT conflicts, use global sequences to prevent this type of conflict"; conflicts are resolved at row level and logged to `bdr.conflict_history`; conflict avoidance options include "only ever write to one node"; for cases where conflicts are unacceptable (double-booking) use Eager Replication, which trades latency for consistency; asynchronous mechanisms "can't support geographically distributed applications where very low latency is critical". — [EDB PGD docs: Conflicts overview](https://www.enterprisedb.com/docs/pgd/latest/conflict-management/conflicts/00_conflicts_overview/)

### Inferences
- Global/Snowflake sequences are unique but not dense or ordered across nodes; a cursor-based reader relying on "seq N+1 exists iff written" would see gaps and reorderings, breaking the "never miss a change it was told exists" invariant. The hub would have to re-sequence on read, which is the single-writer design again.
- Users sync their own two devices; there is no write contention between tenants and no need for local-write latency. Multi-writer buys nothing here and adds a conflict surface.

### Gaps
- No independent (non-vendor) 2024-2026 evaluation of Spock or PGD for append-only logs was found.

## Backups as the last line: cross-region copies, restore drills, PITR verification

### Takeaway
Managed providers include continuous WAL archiving and PITR with retention windows from 6 hours (Neon Free) to 30 days (Neon Scale, Supabase Enterprise), but none of the pages I read commits to cross-region backup storage, and all practitioner sources agree that only a scheduled, data-verified restore into a separate target proves PITR works.

### Cited Findings
- Supabase: daily backups retained 7 days (Pro), 14 (Team), up to 30 (Enterprise); PITR add-on at about $100/$200/$400 per month for 7/14/28 days; "WAL files are backed up every two minutes by default", so "in the worst case scenario, PITR achieves a Recovery Point Objective (RPO) of two minutes"; "The project is inaccessible during this process"; replication slots must be dropped and recreated around a restore; no cross-region storage mentioned. — [Supabase docs: Backups](https://supabase.com/docs/guides/platform/backups)
- Neon: history (restore) window 6 h on Free, up to 7 days on Launch, up to 30 days on Scale; instant restore $0.20/GB-month; scheduled snapshots $0.09/GB-month; object storage durability quoted at 99.999999999%. — [Neon pricing](https://neon.com/pricing); [Neon docs: High availability](https://neon.com/docs/introduction/high-availability)
- Crunchy Bridge: "Daily and WAL backups included", "Restore to any point in time with continuous WAL archiving"; retention window not stated on the pricing page; the HA page notes that without HA, recovery from backup "may take many hours" for larger clusters. — [Crunchy Data pricing](https://www.crunchydata.com/pricing); [Crunchy Bridge docs: High availability](https://docs.crunchybridge.com/concepts/high-availability)
- Aurora: after an unplanned failover Aurora tries to snapshot the old primary volume "so that you can use it to recover any of the missing data"; that snapshot is subject to the old cluster's retention and must be copied to a manual snapshot to keep it. — [AWS docs: Aurora Global Database switchover/failover](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database-disaster-recovery.html)
- Drill practice: check `pgbackrest info` shows a usable backup and that archived WAL covers the target before restoring; a PITR drill overwrites the target data directory so do it in a sandbox or separate host; teams hit a `--delta` gotcha on populated PGDATA; "nothing alerts on a failing archive and nothing runs verify" is a typical gap; verify at the data level, record duration, test quarterly at minimum; a `pg_dump`-level check does not exercise WAL replay. — [Pigsty docs: Manual PITR drill](https://doc.pigsty.io/docs/pgsql/tutorial/pitr/); [CORA PR #582: pgBackRest drill notes](https://github.com/xmap/cora/pull/582); [dev.to: PostgreSQL PITR with pgBackRest](https://dev.to/philip_mcclarence_2ef9475/postgresql-point-in-time-recovery-with-pgbackrest-1cg6); [Bring: the value of fire drills](https://developer.bring.com/blog/the-value-of-firedrills/) **(2017)**
- A fintech-startup retrospective: "Your backup strategy is only as good as your last tested restore." **(2021)** — [lawzava: Database reliability engineering](https://lawzava-com.pages.dev/blog/2021-08-09-database-reliability-engineering)

### Inferences
- Because the hub's data is a per-tenant append-only log and every user's devices hold full local copies, the hub's backup RPO can be looser than a typical SaaS: after a restore the hub can detect its max sequence is behind a device's and re-ingest. This makes a nightly `pg_dump` to a bucket in a second region (owner-controlled, provider-independent) a cheap and sufficient cross-region "last line" at Step 1-3, with the provider's PITR covering operator error.
- A restore drill for this service should assert: restored max seq per tenant, a device reconnect that re-pushes the missing tail, and the time taken.

### Gaps
- No provider page I read states where backups are stored relative to the primary region or whether copies exist in another region; this must be asked of each vendor.
- Fly MPG backup retention/PITR window not documented on the pages fetched.

## Rough monthly cost and operational burden at each step

### Takeaway
A single small instance plus the cheapest HA-capable managed Postgres is roughly $50-150/month; adding a second instance and HA roughly doubles the database line (Crunchy HA standby is same-size; RDS Multi-AZ adds standbys; Neon charges per replica compute); a second region with a full replica cluster and its own hub instances roughly doubles again, into the low hundreds to around $1,000/month depending on provider, before cross-region data transfer. Burden grows from "redeploy" to "own a runbook and drill it."

### Cited Findings
- Fly Managed Postgres plans: Basic (shared-2x, 1 GB) $38/mo; Starter (2 GB) $72; Launch (performance-2x, 8 GB) $282; Scale (32 GB) $962; storage $0.28/GB-month; HA, backups and pooling included on all plans. — [Fly.io docs: Managed Postgres overview](https://docs.fly.io/mpg/overview/)
- Crunchy Bridge (AWS): Hobby-0 $9, Hobby-1 $18, Hobby-2 $35, Hobby-4 $70, Standard-4 $70, Standard-8 $140, Standard-16 $280; storage $0.10/GB-month; prices "include infrastructure, backups, and data transfer"; HA is not on Hobby and the standby is same-size (so HA on Standard-4 implies two $70 instances, inferred). — [Crunchy Data pricing](https://www.crunchydata.com/pricing); [Crunchy Bridge docs: High availability](https://docs.crunchybridge.com/concepts/high-availability)
- Neon: Free $0 (100 CU-hours, 1 GB); Launch $0.106/CU-hour and $0.35/GB-month storage, example small workload about $15/mo; Scale $0.222/CU-hour, example about $31/mo, SLA only on Scale; read replicas count toward CU-hours. — [Neon pricing](https://neon.com/pricing)
- Supabase add-ons: PITR about $100/$200/$400 per month for 7/14/28 days and requires at least a Small compute add-on. — [Supabase docs: Backups](https://supabase.com/docs/guides/platform/backups)
- Aurora Global: secondary region needs its own instances and storage plus replicated write I/O (third-party quote around $0.20 per million) and inter-region transfer. — [AWS: Aurora Global Database](https://aws.amazon.com/rds/aurora/global-database); [Bytebase: Aurora pricing explained](https://www.bytebase.com/blog/understanding-aws-aurora-pricing)
- Fly bills inter-region private network traffic from February 2026 "at the same rate as Machines" data transfer. — [Fly.io docs: Managed Postgres](https://docs.fly.io/mpg/)
- Operational burden signals: Fly MPG has "no alerts for CPU or storage"; Aurora failover requires reconciling parameter groups, alarms, Secrets Manager and IAM across regions and checking engine patch parity; the Fly Flex zombie incident required the operator to diagnose from logs and stop the Machine by hand. — [Fly.io docs: Managed Postgres overview](https://docs.fly.io/mpg/overview/); [AWS docs: Aurora Global Database switchover/failover](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database-disaster-recovery.html); [Fly community: Postgres Flex zombie primary](https://community.fly.io/t/postgres-flex-a-former-primary-db-machine-came-back-as-a-zombie-and-kept-serving-read-only-writes/28167)

### Inferences (USD/month, order-of-magnitude, compute for the hub itself excluded unless noted)
- Now (1 instance, 1 region, managed PG without HA): $10-40 DB (Crunchy Hobby, Neon Launch, Fly MPG Basic) + one small host instance ($5-25). Burden: deploys, backups verified by a dump.
- Next (2 instances + in-region HA): DB $70-150 (Crunchy Standard-4 with HA, Fly MPG Starter/Launch, RDS Multi-AZ small) + 2 instances; optional PITR add-on $100 on Supabase. Burden: NOTIFY listener on a non-pooled connection, SIGTERM handling, pool recovery test, restore drill.
- Later (second region, single writer): add a same-size replica cluster in region 2 ($70-300), hub instances in region 2, cross-region transfer, and either Fly anycast (included) or Route 53 health checks / Global Accelerator (hourly fee + transfer premium; exact rates not fetched). Total likely $300-1,000+. Burden: promotion runbook, fencing writes to the old primary, DNS TTL discipline, quarterly failover and restore drills.
