# CI/CD and release model for a single Rust service image (GitHub Actions to managed container hosts)

Research date: 2026-11-01. Scope: building one Docker image of the Rust hub (`Hub/Dockerfile`, linux/amd64 + linux/arm64, digest-pinned bases) in GitHub Actions on the public repo `cacheplane/b4app`, publishing to GHCR, and deploying it to Fly.io, Render, Railway, AWS App Runner, or ECS Fargate under the release model: merge to `main` deploys test; GitHub Release deploys production; nightly from `main` produces artifacts; PRs may get previews. Facts older than 2025 are marked "(older)".

Repo facts that shape the findings (read from the worktree, not web sources): `Hub/Dockerfile` is a two-stage build (`rust@sha256:…` 1.93.1-slim-bookworm builder, `debian@sha256:…` bookworm-slim runtime) with `cargo fetch --locked` then `cargo build --release --locked --offline --bin b4hub` and no cache mounts or cargo-chef; the runtime image has `ENTRYPOINT ["/usr/local/bin/b4hub"]`, `CMD ["serve"]`, and a `HEALTHCHECK` against `/readyz`. Migrations use `sqlx` 0.8.6 (`Hub/crates/b4hub-db/src/migrate.rs`), invoked as a separate `migrate` subcommand (`Hub/crates/b4hub/src/cli.rs`). The only existing workflow is `.github/workflows/ci.yml`; Mac releases are tagged `mac-v<version>` (per the user's brief; no web source).

## Key question 1: GitHub Actions — Buildx multi-arch builds, caching, GHCR push, Rust build caching

### Takeaway
The current stack is `docker/setup-buildx-action` + `docker/login-action` (to `ghcr.io` with `GITHUB_TOKEN`, `packages: write`) + `docker/metadata-action@v6` + `docker/build-push-action@v7` with `cache-from: type=gha` / `cache-to: type=gha,mode=max` (or a registry cache ref in GHCR). For Rust, the biggest win is layer-caching dependencies (cargo-chef), optionally with BuildKit cache mounts for the cargo registry and an sccache dir; cache mounts are not exported to the `gha` cache without a workaround. For arm64, avoid QEMU: either cross-compile from the amd64 builder or build natively on GitHub's free `ubuntu-24.04-arm` runners and merge the two digests into one index.

### Cited Findings
- GitHub's reference GHCR workflow uses job permissions `contents: read`, `packages: write`, `attestations: write`, `id-token: write`; logs in with `docker/login-action` (`registry: ghcr.io`, `username: ${{ github.actor }}`, `password: ${{ secrets.GITHUB_TOKEN }}`); then `docker/metadata-action` → `docker/build-push-action` (`push: true`, `tags`/`labels` from metadata) → `actions/attest@v4` with `subject-name`, `subject-digest: ${{ steps.push.outputs.digest }}`, `push-to-registry: true`. It uses `actions/checkout@v6` and pins the Docker actions to commit SHAs ("GitHub recommends pinning actions to a commit SHA"). — [GitHub Docs: Publishing Docker images](https://docs.github.com/en/actions/use-cases-and-examples/publishing-packages/publishing-docker-images)
- `docker/build-push-action` README examples use `@v7`; inputs include `cache-from`/`cache-to` (lists of cache sources/destinations), `platforms` (list), `provenance`, `sbom`, and `attests`. `setup-buildx-action` is "not required but recommended" for multi-platform; `setup-qemu-action` adds emulation. — [docker/build-push-action](https://github.com/docker/build-push-action)
- GitHub cache backend: `cache-from: type=gha` / `cache-to: type=gha,mode=max`. Only GitHub Cache API v2 is supported (v1 shut down April 15, 2025); needs Buildx ≥ v0.21.0 and BuildKit ≥ v0.20.0. Events like `pull_request_target` get read-only cache access, so `cache-to` can fail with "failed to reserve cache"; `cache-to: type=gha,mode=max,ignore-error=true` makes export failures non-fatal. Registry cache: `cache-from: type=registry,ref=user/app:buildcache` / `cache-to: type=registry,ref=user/app:buildcache,mode=max`. Inline cache "only supports `min` cache mode". — [Docker Docs: GitHub Actions cache](https://docs.docker.com/build/ci/github-actions/cache/)
- Actions cache limits: "By default, the limit is 10 GB per repository"; "GitHub will remove any cache entries that have not been accessed in over 7 days"; runs "can restore caches created in either the current branch or the default branch", and PR runs can also restore base-branch caches. — [GitHub Docs: Caching dependencies](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/caching-dependencies-to-speed-up-workflows)
- BuildKit `RUN --mount=type=cache` mounts are "cumulative across builds", but "BuildKit doesn't preserve cache mounts in the GitHub Actions cache by default"; the documented workaround is `reproducible-containers/buildkit-cache-dance` (example pinned to `4b2444fec0c0fb9dbf175a96c094720a692ef810 # v2.1.4`) which extracts/injects cache-mount data around the build step, saved with `actions/cache@v5`. — [Docker Docs: GitHub Actions cache](https://docs.docker.com/build/ci/github-actions/cache/); [Docker Docs: Optimize cache usage](https://docs.docker.com/build/cache/optimize/)
- cargo-chef: `cargo chef prepare` writes `recipe.json` describing dependency inputs; `cargo chef cook` builds only dependencies into a cacheable layer; claimed speed-up "up to 5x measured on some commercial projects". Caveats: `cook` and `cargo build` must run from the same working directory; "You must use the same Rust version in all stages"; the recipe only stays identical "as long as your dependencies do not change"; it picks up all workspace crates automatically; musl targets need an explicit `--target`. — [LukeMathWalker/cargo-chef](https://github.com/LukeMathWalker/cargo-chef)
- Depot's measured example (older, Rust 1.75 era): unoptimized incremental rebuild "around 34s"; with cargo-chef "around 15 seconds" ("more than a 50% reduction"); with cargo-chef + sccache + cache mounts (`--mount=type=cache,target=/usr/local/cargo/registry` and `--mount=type=cache,target=$SCCACHE_DIR,sharing=locked`) "around 7 seconds" ("more than a 75% reduction"); the article notes cache mounts only help "if they persist between builds", which is harder on ephemeral CI runners. — [Depot: Rust Dockerfile best practices](https://depot.dev/blog/rust-dockerfile-best-practices)
- sccache's GitHub Actions backend: set `SCCACHE_GHA_ENABLED=on`; it needs `ACTIONS_RESULTS_URL` and `ACTIONS_RUNTIME_TOKEN` (exported via `actions/github-script`); `SCCACHE_GHA_VERSION` purges; `SCCACHE_GHA_RW_MODE=READ_ONLY` available; on rate limit "the build will continue, but the storage might not be performed." The page does not cover use inside Docker builds. — [sccache GHA docs](https://github.com/mozilla/sccache/blob/main/docs/GHA.md)
- No head-to-head benchmark of cargo-chef vs sccache vs cache mounts was found; a Feb 2026 guide recommends starting with cargo-chef plus BuildKit cache mounts and warns that a `target/` cache mount is not visible in later layers, so the binary must be copied out in the same `RUN`. — [OneUptime (2026-02-08)](https://oneuptime.com/blog/post/2026-02-08-how-to-speed-up-docker-build-for-rust-projects/view); [Earthly: Incremental Rust builds in CI](https://earthly.dev/blog/incremental-rust-builds/)
- Multi-platform strategies: QEMU emulation ("can be much slower than native builds"), multiple native nodes, or cross-compilation with `--platform=$BUILDPLATFORM` plus `TARGETPLATFORM`/`TARGETARCH` build args. Multi-platform images "contain a manifest list, pointing to multiple manifests." — [Docker Docs: Multi-platform builds](https://docs.docker.com/build/building/multi-platform/)
- GitHub's arm64 Linux hosted runners (`ubuntu-24.04-arm`, `ubuntu-22.04-arm`, 4 vCPU) are generally available "at no cost" in public repositories since August 7, 2025 (public preview since January 2025). A Jan 2026 changelog reportedly extends them to private repos at 2 vCPU (secondhand, via a developer blog). — [GitHub Changelog 2025-08-07](https://github.blog/changelog/2025-08-07-arm64-hosted-runners-for-public-repositories-are-now-generally-available/); [GitHub Changelog 2025-01-16](https://github.blog/changelog/2025-01-16-linux-arm64-hosted-runners-now-available-for-free-in-public-repositories-public-preview/); [Classmethod blog on private-repo arm64 (secondhand)](https://dev.classmethod.jp/articles/github-actions-arm64-private-repos/)

### Inferences
- For the hub, the cheapest first step is cargo-chef layers inside the existing Dockerfile (planner → cook → build), which works with `cache-to: type=gha,mode=max` without any cache-dance; cache mounts (cargo registry, sccache) are a second step that needs `buildkit-cache-dance` or a persistent builder to pay off in Actions.
- Because the repo is public, a native-arm64 job on `ubuntu-24.04-arm` plus an amd64 job, each pushing by digest, then `docker buildx imagetools create` to assemble the index, avoids QEMU for a Rust release build (Rust under QEMU is typically many times slower; no measured figure was found for this project).
- The 10 GB/7-day Actions cache is adequate for one Rust service with two platforms, but a `mode=max` multi-arch cache can approach it; a registry cache ref in GHCR (e.g. `ghcr.io/cacheplane/b4hub:buildcache`) avoids the limit at the cost of GHCR storage.
- `docker/build-push-action` is at v7 and the GitHub docs page pins SHAs; the hub workflow should pin SHAs with a version comment, as the repo's CI already does for other actions (not verified).

### Gaps
- No source quantified QEMU slowdown for Rust specifically, nor a measured cargo-chef vs sccache vs cache-mount comparison on comparable hardware.
- The `build-push-action` README fetch did not surface explicit defaults for `cache-to` modes; the Docker docs page was used instead.

## Key question 2: Image tagging conventions and release-tag naming when one repo ships several artifacts

### Takeaway
Tag every push by long SHA (`sha-<40 hex>`), add `main`/`edge` for branch heads, `nightly` for schedule builds, and semver tags from the Git tag for releases, but deploy by immutable digest (`steps.build.outputs.digest`). `docker/metadata-action` can strip an artifact prefix such as `hub-v1.2.3` with `type=match` (regex + capture group) or `type=semver` with `match=`, so a `hub-v<version>` tag scheme alongside the existing `mac-v<version>` is directly supportable; it is also the default format release-please uses for monorepo components (`<component>-v<version>`).

### Cited Findings
- `type=sha`: "Output Git short commit (or long if specified) as Docker tag like `sha-860c190`"; defaults `prefix=sha-`, `format=short` (7 chars, configurable via `DOCKER_METADATA_SHORT_SHA_LENGTH`); `type=sha,format=long` for the full SHA. `type=schedule,pattern=nightly` outputs `nightly` on `schedule` events. `type=edge` "reflects the last commit of the active branch". `type=ref,event=tag` outputs the Git tag as-is (e.g. `v1.2.3`). `type=raw,value=foo` emits custom tags. — [docker/metadata-action](https://github.com/docker/metadata-action)
- `type=semver` "requires a valid semver Git tag"; patterns `{{version}}`, `{{major}}.{{minor}}`, `v{{major}}`; prefix stripping example: `type=semver,pattern={{version}},value=p1/v1.0.0,match=v(\d.\d.\d)$` maps Git tag `p1/v1.2.3` to `1.2.3`. `type=match` "Can create a regular expression for matching Git tag with a pattern and capturing group" (example `pattern=v(.*)`, `group=1`). — [docker/metadata-action](https://github.com/docker/metadata-action); [metadata-action README (master)](https://github.com/docker/metadata-action/blob/master/README.md)
- `latest` flavor: generated by default (`latest=auto`) for `type=ref,event=tag`, `type=semver`, `type=pep440`, `type=match`; can be forced with `latest=true|false`. For `type=semver`, "Pre-release (rc, beta, alpha) will only extend `{{version}}` (or `{{raw}}` if specified) as tag"; the semver example output for `refs/tags/v2.0.8-beta.67` is only `2.0.8-beta.67` (no `latest`), whereas the basic example using `type=ref,event=tag` lists `v2.0.8-beta.67, latest`. — [metadata-action README (master)](https://github.com/docker/metadata-action/blob/master/README.md); [docker/metadata-action](https://github.com/docker/metadata-action)
- The metadata-action README documents triggers `schedule`, `push` (branch/tag), `pull_request`, `workflow_dispatch`; it does not document the `release` event. On a `release` event GitHub sets `GITHUB_REF` to "Tag ref of release `refs/tags/<tag_name>`" and `GITHUB_SHA` to "Last commit in the tagged release", so tag-based types still resolve. — [docker/metadata-action](https://github.com/docker/metadata-action); [GitHub Docs: events that trigger workflows](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#release)
- Release-please (manifest/monorepo mode) default tag format is `<component-name>-v<release-version>`; setting `include-component-in-tag: false` changes it to `v<release-version>`; it creates GitHub Releases per package, and draft releases do not get Git tags until published unless `force-tag-creation` is set. — [release-please manifest releaser docs](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md)
- Render explicitly supports digest references: "You can specify an image _digest_ instead of a tag", and its rollback reuses the target deploy's tag or digest, noting "A digest always refers to the same image, while a tag may now point to a different one." — [Render: Deploy an image](https://render.com/docs/deploy-an-image); [Render: Rollbacks](https://render.com/docs/rollbacks)
- Sigstore guidance in CI: sign and deploy by digest (`${tag}@${DIGEST}`), using the `digest` output of `build-push-action`. — [sigstore/cosign-installer](https://github.com/sigstore/cosign-installer)

### Inferences
- Recommended scheme for this repo: Git tag `hub-v1.4.0` → image tags `1.4.0`, `1.4`, `1`, `latest` (via `type=match,pattern=hub-v(.*),group=1` or `type=semver,...,match=hub-v(\d+\.\d+\.\d+)`), plus `sha-<long sha>` on every build, `main` on branch pushes, and `nightly` + `nightly-<date>` on schedule. Mac releases keep `mac-v*`; workflows filter on the prefix (`on: push: tags: ['hub-v*']` or an `if: startsWith(github.event.release.tag_name, 'hub-v')` guard on `release`).
- Pre-release hub tags (`hub-v1.4.0-rc.1`) should use `type=semver`-style handling so they do not move `latest`; with `type=match`, set `flavor: latest=false` for pre-releases explicitly.
- Deploy jobs should consume `digest` (`ghcr.io/cacheplane/b4hub@sha256:…`), never a mutable tag, so the test, production and rollback paths refer to the identical artifact.

### Gaps
- The metadata-action README does not state explicitly how `latest=auto` treats pre-releases under `type=match`; the semver table implies `latest` is suppressed only for `type=semver`.
- No authoritative GitHub doc on recommended Release tag naming for multi-artifact repos was found; the release-please convention is the strongest tooling precedent.

## Key question 3: Supply chain — SBOM/provenance attestations, cosign keyless, and deploy-time verification

### Takeaway
Two complementary layers exist: BuildKit attestations attached to the image index (`provenance`, `sbom` on build-push-action; public repos get `mode=max` provenance automatically) and GitHub artifact attestations (`actions/attest@v4`, Sigstore-signed, verifiable with `gh attestation verify oci://…`, SLSA Build L2; L3 with a reusable workflow). Cosign keyless signing from Actions is a one-step add-on (`cosign sign --yes image@digest` with `id-token: write`). None of the target hosts (Fly, Render, Railway, ECS) verifies signatures at deploy time; verification is done as a gate in the deploy job.

### Cited Findings
- `docker/build-push-action`: "If the GitHub repository is public, provenance attestations with `mode=max` are automatically added to the image"; private repos get `mode=min` by default (set `provenance: mode=max` to upgrade). SBOMs are not automatic: set `sbom: true`. No attestations are added with the `docker` exporter or `load: true`; attestations require pushing to a registry. Provenance "contains the values of build arguments", so secrets must go through secret mounts. — [Docker Docs: Build attestations in GitHub Actions](https://docs.docker.com/build/ci/github-actions/attestations/)
- Attestation storage: "Attestation manifests are attached to the root image index object" after the runnable manifests, with `platform` set to `unknown/unknown` "To prevent container runtimes from accidentally pulling or running the image", annotated `vnd.docker.reference.type=attestation-manifest` and `vnd.docker.reference.digest`. — [Docker Docs: Attestation storage](https://docs.docker.com/build/metadata/attestations/attestation-storage/)
- GitHub artifact attestations for containers: use `actions/attest@v4` with `subject-name` (fully qualified image name, "Do not include a tag as part of the image name"), `subject-digest` (`sha256:HEX_DIGEST`, e.g. from build-push-action's `digest` output), `push-to-registry: true`; permissions `id-token: write`, `contents: read`, `attestations: write`, `packages: write`. SBOM attestation adds `sbom-path` (SPDX or CycloneDX, generated e.g. with `anchore/sbom-action`). Verify: `docker login ghcr.io` then `gh attestation verify oci://ghcr.io/ORG/IMAGE:tag -R ORG/REPO` (`--predicate-type https://spdx.dev/Document/v2.3` for SBOMs). — [GitHub Docs: Using artifact attestations](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds)
- Artifact attestations give "SLSA v1.0 Build Level 2"; Build L3 when builds run in a reusable workflow that isolates the build from the calling workflow. Public repositories use the Sigstore Public Good Instance ("written to an immutable transparency log that is publicly readable"); private repositories use GitHub's Sigstore instance that "does not have a transparency log". "A copy of the generated Sigstore bundle is stored with GitHub." — [GitHub Docs: Artifact attestations concept](https://docs.github.com/en/actions/concepts/security/artifact-attestations)
- Cosign keyless: "Fulcio issues short-lived certificates binding an ephemeral key to an OpenID Connect identity"; signing events are logged in Rekor; cosign can mint the token itself in GitHub Actions (ambient credentials). — [Sigstore: Cosign signing overview](https://docs.sigstore.dev/cosign/signing/overview/)
- `sigstore/cosign-installer@v4.1.0` (latest release shown v4.1.0); keyless example needs `permissions: id-token: write # needed for signing the images with GitHub OIDC Token`, then `cosign sign --yes ${tag}@${DIGEST}` for each tag using `steps.build-and-push.outputs.digest`. — [sigstore/cosign-installer](https://github.com/sigstore/cosign-installer)
- Deploy-time verification on hosts: searches found no Fly.io, Render, or Railway feature for signature verification; for ECS, sources describe running `cosign verify` in the pipeline before updating the task definition because ECS does not verify signatures at deploy time; admission-controller enforcement (Sigstore Policy Controller, Kyverno, Connaisseur) applies to Kubernetes/EKS, not ECS. — [Cubepath: Cosign signing and verification](https://cubepath.com/docs/container-security/cosign-container-image-signing); [LiteLLM docker image security guide (example of CI-gate pattern)](https://docs.litellm.ai/docs/proxy/docker_image_security)
- `dataaxiom/ghcr-cleanup-action` "safely handles multi-architecture images, attestation and Sigstore cosign referrers", which matters because attestation and cosign artifacts appear as extra (untagged or `sha256-…`-tagged) package versions in GHCR. — [dataaxiom/ghcr-cleanup-action](https://github.com/dataaxiom/ghcr-cleanup-action)

### Inferences
- For a public repo, the minimal credible setup is: build-push-action with `sbom: true` (provenance max is automatic), `actions/attest@v4` with `push-to-registry: true`, and optionally cosign keyless; the deploy job then runs `gh attestation verify oci://ghcr.io/cacheplane/b4hub@<digest> -R cacheplane/b4app` (and/or `cosign verify --certificate-identity-regexp … --certificate-oidc-issuer https://token.actions.githubusercontent.com`) before invoking the host's deploy, which is the only enforcement point available on these hosts.
- Because the repo is public, every attestation is in the public Rekor log; nothing secret can be in build args or SBOM content.
- Any GHCR cleanup must be attestation-aware or it will strand or orphan the attestation manifests (see Q7).

### Gaps
- Exact `cosign verify` flags for GitHub OIDC identity were not confirmed from Sigstore's own CI page (the fetched Sigstore pages did not include them); the cosign-installer README and secondary sources were used.
- No primary statement from Fly, Render, or Railway about signature verification (absence of a feature is inferred from absence in docs and search results).

## Key question 4: Deploying a prebuilt GHCR image to Fly.io, Render, Railway, App Runner, ECS Fargate from Actions

### Takeaway
Fly: `flyctl deploy --image <ref>` with a scoped deploy token (`fly tokens create deploy`); public GHCR works, private GHCR does not (Fly's documented path is its own `registry.fly.io`). Render: image-backed service pulls from GHCR (public, or private with a PAT having `read:packages`), redeploy via deploy-hook URL with `imgURL=<tag or digest>`. Railway: image-sourced services need a GraphQL `serviceInstanceUpdate` + redeploy from CI (CLI cannot set the image tag; private registries require Pro). App Runner is closed to new customers (ECR/ECR Public sources only) and AWS recommends ECS Express Mode. ECS Fargate: OIDC via `aws-actions/configure-aws-credentials@v6`, task definition with `repositoryCredentials` (Secrets Manager) for private GHCR, deploy with `amazon-ecs-deploy-task-definition@v2`.

### Cited Findings
- Fly GitHub Actions guide: workflow uses `superfly/flyctl-actions/setup-flyctl@master`, `run: flyctl deploy --remote-only`, `FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}`, and "concurrency: deploy-group    # optional: ensure only one action runs at a time". Create the token with `fly tokens create deploy -x 999999h` (copy including the `FlyV1 ` prefix); `fly tokens create org` for an org-wide token; environment secrets require an `environment:` key on the job. — [Fly Docs: Continuous deployment with GitHub Actions](https://docs.fly.io/launch/continuous-deployment-with-github-actions)
- `fly deploy` flags: `-i, --image` "The Docker image to deploy"; `--strategy` (canary, rolling, bluegreen, immediate; default rolling); `--wait-timeout` (default 5m0s); `--release-command-timeout` (default 5m0s, or `none`); `--build-only`, `--push`, `--local-only`/`--remote-only`, `-e/--env`, `-y/--yes`. If an image is specified, Fly uses "that image, regardless of the presence of a Dockerfile". — [Fly Docs: fly deploy](https://docs.fly.io/flyctl/deploy/); [Fly Docs: Deploy an app](https://docs.fly.io/launch/deploy/)
- Fly registry: "You can deploy images from the Fly.io registry or public registries"; push to `registry.fly.io/<app>:<tag>` after `fly auth docker`; the blueprint "does not address deploying from private external registries". A Nov 2023 (older) community post reports `fly launch --image ghcr.io/...` on a private package failing with "Authentication required to access image" with no resolution. — [Fly Docs: Using the Fly Docker registry](https://docs.fly.io/blueprints/using-the-fly-docker-registry); [Fly community thread 16461 (older)](https://community.fly.io/t/deploy-from-private-package-with-github-actions/16461)
- Render image-backed services: GHCR supported for private images; credentials are per-workspace "Container Registry Credentials" (username + PAT with `read:packages`). "Image-backed services do _not_ automatically redeploy"; trigger via Dashboard, or GET/POST to the deploy hook URL, optionally "specify a tag or digest by appending an `imgURL` query parameter" (other URL components must match the service's image). The image must target `linux/amd64`, compressed size ≤ 10 GB; Render pulls from the registry on every deploy/restart/scale-out and keeps no local cache. — [Render: Deploy an image](https://render.com/docs/deploy-an-image)
- Railway image sources: public images from Docker Hub, GHCR, Quay, GitLab, MCR; "Private Docker registry deployments require the Pro plan"; GHCR credentials are "a personal access token (classic)". Railway monitors for new versions and stages an update you must deploy; auto-update schedules can be configured; CLI docs do not document setting a tag. — [Railway: Services guide](https://docs.railway.com/guides/services#deploying-a-public-docker-image)
- Railway CLI in CI: "Set `RAILWAY_TOKEN` for project-level actions", "Set `RAILWAY_API_TOKEN` for account-level actions"; install via `npm i -g @railway/cli` or `bash <(curl -fsSL railway.com/install.sh)`; `railway up` has `--service`, `--environment`, `--ci` ("Stream build logs only, then exit"), `--detach`; exit code 0 means deployment SUCCESS; `railway redeploy` = "Redeploy latest deployment". — [Railway: CLI guide](https://docs.railway.com/guides/cli); [Railway: railway up](https://docs.railway.com/cli/up)
- Railway image updates from CI (community/staff answers, not an official doc): call the GraphQL `serviceInstanceUpdate` mutation with `source.image` set to the new tag, then a redeploy mutation (`serviceInstanceRedeploy` / `serviceInstanceDeploy` / `serviceInstanceDeployV2` across threads); "The CLI can't set the image tag". — [Railway Station: deploy docker tag from CI](https://station.railway.com/questions/deploy-docker-tag-from-ci-cf2cd5dc); [Railway Station: Redeploy from GitActions](https://station.railway.com/questions/redeploy-from-git-actions-e2e06590)
- App Runner: "AWS App Runner is no longer open to new customers. Existing customers can continue to use the service as normal"; AWS "recommend[s] Amazon ECS Express Mode". Source-image providers are only Amazon ECR and ECR Public (no GHCR); no automatic deployment for ECR Public or cross-account ECR images. ECS Express Mode provisions "an ECS service on Fargate, an Application Load Balancer, auto scaling, and networking" with one API call; GitHub Action `aws-actions/amazon-ecs-deploy-express-service@v1`. — [AWS: App Runner availability change](https://docs.aws.amazon.com/apprunner/latest/dg/apprunner-availability-change.html); [AWS: App Runner source image](https://docs.aws.amazon.com/apprunner/latest/dg/service-source-image.html)
- `aws-actions/configure-aws-credentials@v6` (examples pin `v6.3.0`): OIDC needs `permissions: id-token: write`, inputs `role-to-assume`, `aws-region`; trust policy `StringEquals` on `token.actions.githubusercontent.com:aud = sts.amazonaws.com` and `:sub`; repos created on/after 15 July 2026 emit the immutable subject form `repo:octo-org@123456/octo-repo@789012:ref:refs/heads/main` and name-only trust policies fail with "Not authorized to perform sts:AssumeRoleWithWebIdentity"; "Avoid `ForAllValues:` in `Allow` statements"; `role-duration-seconds` default 3600 (900–43200). — [aws-actions/configure-aws-credentials](https://github.com/aws-actions/configure-aws-credentials)
- OIDC subject for environment-scoped jobs: `repo:octo-org/octo-repo:environment:prod`; branch form `repo:my-org/my-repo:ref:refs/heads/main`; "Repositories created after July 15, 2026 use an immutable default subject format that includes owner and repository IDs". — [GitHub Docs: OIDC hardening](https://docs.github.com/en/actions/security-for-github-actions/security-hardening-your-deployments/about-security-hardening-with-openid-connect)
- ECS pulling from non-ECR registries: container definition `repositoryCredentials.credentialsParameter` = Secrets Manager secret ARN with `{"username": ..., "password": ...}`; task execution role needs `secretsmanager:GetSecretValue` (and `kms:Decrypt` for custom keys); Fargate platform version ≥ 1.2.0. — [AWS: Using non-AWS container images in ECS](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/private-auth.html)
- `aws-actions/amazon-ecs-deploy-task-definition@v2`: inputs `task-definition`, `service`, `cluster`, `wait-for-service-stability`, `run-task`, `wait-for-task-stopped`, `run-task-launch-type`; "Overrides and VPC networking options are available as well" (see `action.yml`). — [aws-actions/amazon-ecs-deploy-task-definition](https://github.com/aws-actions/amazon-ecs-deploy-task-definition)

### Inferences
- Since `cacheplane/b4app` is public, the GHCR package can be public, which removes the private-registry friction on all four hosts (Fly `--image ghcr.io/...` works for public images; Render/Railway/ECS need no pull credentials). If the package must be private, Fly requires re-pushing to `registry.fly.io`, Railway requires Pro, and ECS requires a Secrets Manager secret holding a GitHub PAT.
- App Runner should be treated as unavailable for a new deployment; ECS Express Mode (or plain ECS Fargate) is the AWS option.
- Railway is the weakest fit for an "Actions pushes a prebuilt image" model: the officially documented image path is pull-and-stage in the UI; CI control needs undocumented GraphQL mutations.

### Gaps
- Fly's current official docs do not state whether `fly deploy --image` accepts private external-registry credentials; the only evidence is a 2023 unanswered thread.
- Railway's GraphQL mutation names for redeploying an image-sourced service are inconsistent across community threads; no official doc page was found.
- Whether Render's API (as opposed to deploy hook) can trigger an image deploy with a specific digest was not confirmed from the fetched page.

## Key question 5: Running the migration before traffic switches on each host; behaviour on failure

### Takeaway
Fly `release_command`, Render pre-deploy command, and Railway pre-deploy command all run the new image's command in a temporary container after build and before the new version takes traffic, and all three abort the deploy on non-zero exit while the previous version keeps serving. App Runner has no pre-deploy hook (and is closed to new customers). On ECS, `amazon-ecs-deploy-task-definition` with `run-task: true` + `wait-for-task-stopped: true` runs a one-off migration task and only updates the service if it exits successfully; the deployment circuit breaker handles rollout failures.

### Cited Findings
- Fly: `release_command` runs "in a temporary Machine using the newly built image, once per deploy attempt"; "A non-zero exit status from this command will stop the deployment"; the Machine has "full access to the network, environment variables and secrets" but no volumes; `release_command` replaces `CMD` and "the Docker image's `ENTRYPOINT` is not overridden" (so with the hub's `ENTRYPOINT ["/usr/local/bin/b4hub"]`, `release_command = "migrate"` is the natural form); default timeout 5 minutes (`release_command_timeout` or `--release-command-timeout`); `RELEASE_COMMAND=1` is set in the environment; `[deploy.release_command_vm]` sizes the temporary Machine. Strategies: rolling (default), immediate, canary, bluegreen (bluegreen needs ≥1 health check and no volumes). — [Fly Docs: fly.toml reference](https://docs.fly.io/reference/configuration)
- Fly zero-downtime page: release command "Fails the deploy if the command fails"; "we don't send users to your new code until it passes a health check. If it fails, the old version keeps running." — [Fly: Zero-downtime deploys](https://fly.io/zero-downtime-deploys.md)
- Fly secrets and the privileged DB URL: the release Machine sees the app's full secret set, so a separate privileged URL would be visible to the serving Machines too unless kept out of app secrets (see Inferences). — [Fly Docs: fly.toml reference](https://docs.fly.io/reference/configuration)
- Render: "The pre-deploy command runs _after_ your service's build finishes, but _before_ that build is deployed"; "executes on a separate instance from your running service"; filesystem changes not reflected; no persistent disk access; 30-minute timeout; "If any command fails or times out, the entire deploy fails" and the last successful deploy keeps running; "available for paid web services, private services, and background workers"; consumes pipeline minutes. Zero-downtime: "All service types redeploy with zero downtime, unless they attach a persistent disk"; for multi-instance services, any failing new instance cancels the deploy and reverts. — [Render: Deploys](https://render.com/docs/deploys)
- Railway: pre-deploy command executes "between building and deploying your application", has the service's environment variables and runs "within your private network"; "If your command fails, it will not be retried and the deployment will not proceed"; separate container, no volumes; no time limit by default (configurable 1–3600 s). The doc implies it runs from the application image but does not state image-based deploy support explicitly. Railway's Wait-for-CI doc advises running migrations "as a pre-deploy command" rather than relying on CI ordering. — [Railway: Pre-deploy command](https://docs.railway.com/deployments/pre-deploy-command); [Railway: GitHub autodeploys](https://docs.railway.com/guides/github-autodeploys)
- Railway deployment lifecycle: a healthcheck gates Deploying → Active, and the old deployment is "stopped and removed with a slight overlap for zero downtime" (`RAILWAY_DEPLOYMENT_OVERLAP_SECONDS`). — [Railway: Deployments reference](https://docs.railway.com/reference/deployments)
- App Runner: documentation for image sources describes no pre-deploy or migration hook; service is closed to new customers. — [AWS: App Runner source image](https://docs.aws.amazon.com/apprunner/latest/dg/service-source-image.html)
- ECS: with `run-task: true` and `wait-for-task-stopped: true`, "the service would not be updated until the ad-hoc task exits successfully", suited to "database migrations"; Fargate requires `awsvpc` network mode and a network configuration. — [aws-actions/amazon-ecs-deploy-task-definition](https://github.com/aws-actions/amazon-ecs-deploy-task-definition)
- ECS deployment circuit breaker: rolls back a failed deployment "to the deployment that is in the `COMPLETED` state"; two stages (tasks reaching RUNNING, then ELB/Cloud Map/container health checks); threshold default `BOUNDED_PERCENT` 50% clamped to [3, 200] (so 3 failures for a 1-task service); `resetOnHealthyTask` default true; only for the rolling-update (`ECS`) controller; emits `SERVICE_DEPLOYMENT_FAILED` EventBridge events. — [AWS: ECS deployment circuit breaker](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-circuit-breaker.html)
- Repo fact: the hub image's `HEALTHCHECK` already targets `/readyz` and `ENTRYPOINT` is the binary, so `migrate` can be passed as the command on every host without a wrapper script. — `Hub/Dockerfile` in the worktree

### Inferences
- Privileged-vs-serving credentials: on Fly, Render and Railway the pre-deploy step inherits the same environment/secrets as the service, so the privileged `MIGRATE_DATABASE_URL` would also be present (though unused) in the serving process unless the platform supports per-command env. The cleanest separation is on ECS: the one-off migration task can use a different task definition whose secrets (from Secrets Manager) include only the privileged URL, and the service task definition only the restricted URL. On the PaaS hosts, the practical mitigation is for `serve` to refuse to start if the privileged variable is present, or to run the migration from the GitHub Actions job itself (the runner has the GHCR image and can `docker run ghcr.io/…@digest migrate` against the database over a public/allow-listed endpoint) before calling the host deploy, which keeps the privileged URL in an environment secret in GitHub only.
- On all three PaaS hosts, "migration failed" leaves the previous version serving and the deploy marked failed; the Actions job should surface that as a failed deployment in the GitHub Environment (no manual rollback required). On ECS, a failed `run-task` fails the Actions step before `update-service`, so the old task set is untouched.
- Running migrations in a one-off container before the rolling restart means old `serve` instances briefly run against the new schema; migrations must therefore be backward-compatible (expand/contract), which matches the forward-only stance in Q9.

### Gaps
- Not confirmed whether Render's pre-deploy command can see a different environment than the service (docs do not describe per-command env), or whether Railway's pre-deploy works for image-sourced services (docs silent).
- No ECS Express Mode doc fetched for how a pre-deploy task fits Express services; the standard ECS action pattern is assumed.

## Key question 6: GitHub Environments and release-triggered production deploys

### Takeaway
Create `test`, `production` (and per-PR `pr-<n>`) Environments; `production` gets required reviewers (up to 6, one approval suffices), optional wait timer, "Prevent self-review", and a deployment tag rule (e.g. `hub-v*`) so only release tags can deploy there; secrets/variables scoped to the environment are released only after protection rules pass. Trigger production with `on: release: types: [published]` (fires for stable and pre-release, and for drafts when published) and guard on the tag prefix; `on: push: tags: ['hub-v*']` is the alternative when releases are created by tag push.

### Cited Findings
- Required reviewers: "Enter up to 6 people or teams. Only one of the required reviewers needs to approve the job for it to proceed."; "Prevent self-review" option; wait timer; "Deployment branches and tags" ("Name patterns must be configured for branches or tags individually"); environment secrets "are only available to workflow jobs that use the environment"; custom protection rules via GitHub Apps; each run "creates a deployment object with the `environment` property set to the name of your environment" with `environment_url`. Plans: "Users with GitHub Free plans can only configure environments for public repositories"; Pro/Team for private repos. — [GitHub Docs: Managing environments](https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-deployments/managing-environments-for-deployment)
- Workflow syntax: `environment: staging_environment` or `environment: { name: production_environment, url: https://… }`; `url` may reference `steps` outputs (`url: ${{ steps.step_id.outputs.url_output }}`) and "maps to `environment_url` in the deployments API"; "All deployment protection rules must pass before a job referencing the environment is sent to a runner." — [GitHub Docs: Workflow syntax](https://docs.github.com/en/actions/writing-workflows/workflow-syntax-for-github-actions)
- `release` event types: `published`, `unpublished`, `created`, `edited`, `deleted`, `prereleased`, `released`. "If you want a workflow to run when stable *and* pre-releases publish, subscribe to `published` instead of `released` and `prereleased`"; "The `prereleased` type will not trigger for pre-releases published from draft releases"; drafts do not fire `created`/`edited`/`deleted`. On `release`, `GITHUB_REF` is `refs/tags/<tag_name>` and `GITHUB_SHA` the last commit of the tagged release. `push` supports `tags`/`tags-ignore` filters; no events are created when more than three tags are pushed at once. — [GitHub Docs: Events that trigger workflows](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows)
- `on.push.tags` example: `tags: [v2, 'v1.*']`; `permissions` can be set at workflow or job level and "If you specify the access for any of these permissions, all of those that are not specified are set to `none`." — [GitHub Docs: Workflow syntax](https://docs.github.com/en/actions/writing-workflows/workflow-syntax-for-github-actions)
- OIDC subject for an environment-scoped job is `repo:ORG/REPO:environment:NAME`, so an AWS role trust policy can be restricted to the `production` environment rather than a branch. — [GitHub Docs: OIDC hardening](https://docs.github.com/en/actions/security-for-github-actions/security-hardening-your-deployments/about-security-hardening-with-openid-connect)
- Fly's guide notes environment secrets "requires an `environment:` key in the deploy job". — [Fly Docs: Continuous deployment with GitHub Actions](https://docs.fly.io/launch/continuous-deployment-with-github-actions)
- `superfly/fly-pr-review-apps` creates "a GitHub deployment environment per PR" and "will destroy the Fly app, but it will not destroy the GitHub environment"; the README's optional cleanup uses `strumwolf/delete-deployment-environment@v2` on `closed`. — [superfly/fly-pr-review-apps](https://github.com/superfly/fly-pr-review-apps)

### Inferences
- A Release-triggered production job: `on: release: types: [published]`, job `if: startsWith(github.event.release.tag_name, 'hub-v')`, `environment: { name: production, url: https://hub.example }`, with the production environment's tag rule `hub-v*` as a second guard. The `mac-v*` releases will fire the same event and be filtered out by the `if`.
- Because the repo is public, Environments with required reviewers are available on the Free plan (private would need Pro/Team).
- Required reviewers are the "deployment approval" primitive; the deploy token / AWS role trust should be bound to the environment so that approval, secrets and credentials align.

### Gaps
- GitHub docs fetched do not state how deployment tag rules behave when the workflow is triggered by `release` (the job ref is the tag, so tag rules should apply; not explicitly documented in the fetched text).

## Key question 7: Nightly builds — cron, skipping when unchanged, GHCR retention and cleanup, prereleases

### Takeaway
Use `schedule:` cron (UTC, offset from the top of the hour; runs only from the default branch; auto-disabled after 60 days without activity in public repos) and short-circuit when `HEAD` equals the last nightly's commit. Tag nightlies `nightly` plus a dated tag via `metadata-action`'s `type=schedule`, and prune GHCR with an attestation-aware cleanup action (`dataaxiom/ghcr-cleanup-action`) since GitHub Packages has no built-in retention policy; deleted versions are restorable for 30 days.

### Cited Findings
- `schedule`: "By default, scheduled workflows run in UTC" (IANA time zone optional); runs on "the latest commit on the default branch and only on the default branch"; minimum interval 5 minutes; "can be delayed during periods of high loads" (offset from the top of the hour); in public repositories "scheduled workflows are automatically disabled when no repository activity has occurred in 60 days". — [GitHub Docs: Events that trigger workflows](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows)
- Skip-when-unchanged patterns in the wild: compare the previous nightly tag's SHA to `HEAD` and exit early; or count commits in the last 24 h as a gating job. A Flatcar PR reversed its skip logic because a rerun "doesn't fix any failure because the rerun became a no-op", so they rebuild if the previous run failed. `polytech-com/release-changes-action` compares commits since the latest tag and outputs a boolean. — [gh-aw-firewall PR 673](https://github.com/github/gh-aw-firewall/pull/673); [flatcar/scripts PR 509](https://github.com/flatcar/scripts/pull/509); [polytech-com/release-changes-action](https://github.com/polytech-com/release-changes-action)
- `metadata-action`: `type=schedule,pattern=nightly` outputs `nightly`; patterns can embed dates (README documents `{{date 'YYYYMMDD'}}` style handlebars for schedule). — [docker/metadata-action](https://github.com/docker/metadata-action)
- GitHub Packages deletion/retention: version deletion requires admin on the package or repo; "You restore the package within 30 days of its deletion" (namespace must be free); public packages with >5,000 downloads on any version cannot be deleted without GitHub Support; workflows can delete with a `GITHUB_TOKEN` that has `admin` on the package (repo must be granted the admin role); "GitHub Packages only supports authentication using a personal access token (classic)" for the GraphQL path; the page "doesn't mention retention policies or automated cleanup". — [GitHub Docs: Deleting and restoring a package](https://docs.github.com/en/packages/learn-github-packages/deleting-and-restoring-a-package)
- `actions/delete-package-versions@v5`: `package-type: container`, `min-versions-to-keep`, `delete-only-untagged-versions`, `ignore-versions`, `num-old-versions-to-delete`; token defaults to `github.token`; README does not mention multi-arch or attestation manifests. — [actions/delete-package-versions](https://github.com/actions/delete-package-versions)
- `dataaxiom/ghcr-cleanup-action@v1`: deletes untagged images by default; `keep-n-tagged`, `older-than`, `exclude-tags`, `delete-tags`, `delete-orphaned-images` (stranded referrer/cosign artifacts), `delete-ghost-images`/`delete-partial-images` (broken multi-arch), `validate`; removes child platform/referrer manifests before parents; needs `packages: write` and the package granting the repo Admin; `dry-run: true` recommended first; nested indices unsupported. — [dataaxiom/ghcr-cleanup-action](https://github.com/dataaxiom/ghcr-cleanup-action)
- Prereleases: GitHub's `release` event distinguishes `prereleased`/`released`, and `metadata-action`'s `type=semver` withholds `latest` for pre-release versions (see Q2). — [GitHub Docs: Events that trigger workflows](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows); [metadata-action README](https://github.com/docker/metadata-action/blob/master/README.md)

### Inferences
- A nightly job for the hub: `schedule: cron '17 3 * * *'` (offset) + `workflow_dispatch`; first step reads the `nightly` tag's `org.opencontainers.image.revision` label (or a stored SHA) and skips unless `HEAD` differs or the last nightly run failed; build pushes `nightly` and `nightly-YYYYMMDD` plus `sha-<sha>`.
- Nightly artifacts can also be attached to a rolling prerelease GitHub Release (`gh release create --prerelease`), but since the production workflow listens to `release: published`, nightly releases must use a non-`hub-v` tag (e.g. `nightly`) or the production job must guard on `github.event.release.prerelease == false`; this is an inference from the event semantics above, not a documented recipe.
- Prefer `dataaxiom/ghcr-cleanup-action` over `actions/delete-package-versions` because the image is multi-arch with attestation manifests (untagged children) that naive "delete untagged" rules would break.

### Gaps
- No GitHub source for a GHCR retention policy feature (none appears to exist; only manual/API deletion).
- The 60-day auto-disable applies to inactivity in the repo as a whole; whether bot commits count as activity was not verified.

## Key question 8: Preview environments per PR with database branching, teardown, cost

### Takeaway
Fly's `superfly/fly-pr-review-apps` creates/updates/destroys a `pr-<n>-<org>-<repo>` app on `opened/reopened/synchronize/closed` and accepts a prebuilt `image` and `secrets`; Neon's official example pairs it with `neondatabase/create-branch-action` (branch per PR, `db_url`/`db_url_with_pooler` outputs) and `delete-branch-action` on close. Render previews are Blueprint-based copies of production (Pro workspace; datastores copied without data; expiry setting) and Railway PR environments are created on PR open and deleted on merge/close; neither doc confirms image-backed service support. Cost control is per-second billing on Render, Fly's small per-PR Machines, Neon branch deletion on close, and `concurrency` per PR.

### Cited Findings
- `superfly/fly-pr-review-apps@1.5.0`: "This action will create, deploy, and destroy Fly apps"; default app name `pr-{number}-{repo_org}-{repo_name}`; inputs `name` ("must include the PR number"), `region` (default `iad`), `org` (default `personal`), `image` ("Optional pre-existing Docker image to use"), `config`, `postgres` (existing cluster to attach), `secrets` (space-separated), `path`; workflow `on: pull_request: types: [opened, reopened, synchronize, closed]`; requires `FLY_API_TOKEN` (org token recommended); creates a GitHub deployment environment per PR but does not delete it. — [superfly/fly-pr-review-apps](https://github.com/superfly/fly-pr-review-apps)
- Neon GitHub integration: installs a GitHub App that adds `NEON_API_KEY` (secret) and `NEON_PROJECT_ID` (variable); sample workflow on `pull_request` types `opened, reopened, synchronize, closed`; `neondatabase/create-branch-action@v5` with `branch_name: preview/pr-${{ github.event.number }}-…`; connection string via `steps.create_neon_branch.outputs.db_url_with_pooler` (do not log it; step outputs are job-scoped so run migrations in the same job); `neondatabase/delete-branch-action@v3` on close. — [Neon: GitHub integration](https://neon.com/docs/guides/neon-github-integration)
- Neon + Fly example repo (`neondatabase/preview-branches-with-fly`): `create-branch-action@v4` (text says v5), `branch_name: preview/${{ steps.branch-name.outputs.current_branch }}`; passes the DB to Fly via `secrets: DATABASE_URL=${{ steps.create-branch.outputs.db_url }}?sslmode=require` on `superfly/fly-pr-review-apps@1.2.1`; runs migrations with `db_url_with_pooler`; `concurrency: group: pr-${{ github.event.number }}`; separate `delete-neon-branch.yml` on `closed` with `delete-branch-action@v3.1.3`. — [neondatabase/preview-branches-with-fly](https://github.com/neondatabase/preview-branches-with-fly)
- Render preview environments: "automatically creating a fresh copy of your production environment" from the Blueprint per PR; manual mode requires `[render preview]` in the PR title, automatic mode previews every PR; Render "automatically destroys them when the original pull request is merged or closed"; `previews.expireAfterDays` deletes after N days without commits (default none); "Preview environments require a Pro workspace plan or higher"; billed prorated per second; "Copies of datastores and persistent disks do not include data from their corresponding" base resource (seed via `initialDeployHook`, downsize via `previewPlan`, or share one DB via `previewValue`); the page does not say whether image-backed services support previews. — [Render: Preview environments](https://render.com/docs/preview-environments)
- Railway PR environments: enabled in Project Settings → Environments; "are created when a Pull Request is opened on a branch" and "deleted as soon as the PR is merged or closed"; "Focused PR Environments" toggle "speeds up PR environments and reduces resource usage"; Bot PR environments toggle; Railway will not deploy a PR branch from a user "not in your workspace"; the page does not address database forking or image-sourced services. — [Railway: Environments](https://docs.railway.com/guides/environments)
- Fork PRs: "secrets are not passed to the runner when a workflow is triggered from a forked repository" (only `GITHUB_TOKEN`, read-only); Dependabot PRs are treated as forks. — [GitHub Docs: Events that trigger workflows](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows)

### Inferences
- For a public repo, preview deploys must be restricted to same-repo PRs (`if: github.event.pull_request.head.repo.full_name == github.repository`) because fork PRs cannot read `FLY_API_TOKEN`/`NEON_API_KEY`; previews are therefore a maintainer-only convenience, consistent with "pull requests may get preview environments".
- The hub's `migrate` subcommand should run in the preview job against the Neon branch URL (privileged) before `fly-pr-review-apps` deploys with a restricted URL as `secrets:`, mirroring production's split; Neon branches are cheap and deleted on close.
- Fly + Neon is the only combination with an official, end-to-end image-based example; Render and Railway previews are source/Blueprint-oriented and unconfirmed for image-backed services.

### Gaps
- Neither Render nor Railway documentation fetched states whether image-backed services participate in previews/PR environments.
- Fly review-app cost figures and Neon branch pricing were not fetched.

## Key question 9: Rollback — redeploying the previous image on each host; migration rollback stance

### Takeaway
Rollback on every host means redeploying a previous immutable image reference: Fly `fly deploy --image <previous digest>`, Render Dashboard/API rollback (re-pulls the recorded tag/digest, fails if gone), Railway "Rollback" on a prior deployment (within plan retention), ECS circuit-breaker automatic rollback or re-registering the previous task definition. Database migrations are treated as forward-only: sqlx supports reversible `.up/.down` files only when opted in from the first migration, and the hosts' pre-deploy hooks give no "un-migrate" step.

### Cited Findings
- Render rollback: "Render kicks off a _new_ deploy using the target deploy's build artifact"; reuses start command, health check path, Docker command, "registry-hosted image", instance count and env vars; "If the specified image is no longer available or reachable in the registry, the rollback fails"; "Render retains a fixed number of recent build artifacts for each service, based on your workspace plan"; API rollback endpoint exists and "does _not_ disable automatic deploys" (Dashboard rollback does). — [Render: Rollbacks](https://render.com/docs/rollbacks)
- Railway rollback: deployment menu "Rollback" → "Redeploys the selected deployment"; "will use the source code from the selected deployment"; not available for deployments older than the plan's retention policy. — [Railway: Deployments reference](https://docs.railway.com/reference/deployments)
- Fly: `fly deploy --image` deploys any image reference; bluegreen/canary/rolling strategies and health checks gate traffic ("If it fails, the old version keeps running"); the fetched pages do not document a dedicated rollback command. — [Fly Docs: fly deploy](https://docs.fly.io/flyctl/deploy/); [Fly: Zero-downtime deploys](https://fly.io/zero-downtime-deploys.md)
- ECS: circuit breaker with `rollback=true` reverts to the last `COMPLETED` deployment; if none exists the deployment stalls; `DescribeServices` exposes `rolloutState`/`rolloutStateReason`. — [AWS: ECS deployment circuit breaker](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-circuit-breaker.html)
- sqlx-cli migrations: `sqlx migrate add <name>` creates `migrations/<timestamp>_<name>.sql`; `sqlx migrate run` "runs any scripts that are still pending"; reversible migrations require `-r` on the first migration ("All the subsequent migrations will be reversible as well"), producing `.up.sql`/`.down.sql` and enabling `sqlx migrate revert`. The `migrate!()` macro embeds migrations; checksums are hashed (LF/CRLF differences break reproducibility; `sqlx.toml` can ignore whitespace and rename `_sqlx_migrations`). — [sqlx-cli README](https://github.com/launchbadge/sqlx/blob/main/sqlx-cli/README.md); [sqlx `migrate!` docs](https://docs.rs/sqlx/latest/sqlx/macro.migrate.html)
- Repo fact: the hub uses sqlx 0.8.6 with the `migrate` feature and a `migrate` CLI subcommand (`Hub/crates/b4hub/src/cli.rs`, `Hub/crates/b4hub-db/src/migrate.rs`); whether the existing migrations are reversible was not inspected.

### Inferences
- Record the deployed digest in the GitHub deployment (`environment.url` or a job summary) so rollback is "re-run the deploy job with the previous digest" (`workflow_dispatch` input) rather than a host-specific UI action; this works uniformly on Fly, Render (via `imgURL` deploy hook) and ECS, and keeps GHCR as the source of truth (retention policy must keep release digests; see Q7).
- Forward-only stance: since migrations run before the rolling restart and old code may still be serving, every migration must be backward-compatible with the previous release; an application rollback then needs no schema rollback. Hosts offer no "revert migration" hook, so down-migrations would have to be a manual `b4hub migrate revert`-style operation if ever added.

### Gaps
- No source fetched on Fly's `fly releases`/`fly deploy --image` rollback workflow specifically, nor Railway's rollback behaviour for image-sourced services (it describes "source code" redeploys).
- Industry survey evidence for "forward-only migrations" as current practice was not collected; the stance is inferred from tooling and host mechanics.

## Key question 10: Concurrency control and deployment locking

### Takeaway
Use a job-level `concurrency: { group: deploy-<environment>, cancel-in-progress: false }` so at most one deploy runs per environment; by default only one further run waits (newer pending runs cancel older pending ones), and `queue: max` queues up to 100 in FIFO order. Per-PR previews use `group: pr-<number>`; hosts add their own serialisation (Fly deploys are per-app; Railway's Wait-for-CI warns against concurrency groups that cancel queued migration runs).

### Cited Findings
- "there can be at most one running job or workflow in a concurrency group at any time"; default queue behaviour: "any existing `pending` job or workflow in the same concurrency group will be canceled" when a new run arrives; `cancel-in-progress: true` also cancels the running one; `queue: max` allows up to 100 waiting runs processed "in first-in-first-out (FIFO) order" (not guaranteed), and combining it with `cancel-in-progress: true` "is not allowed and will result in a workflow validation error"; group names are case-insensitive and may be expressions; `concurrency` works at job or workflow level; the page's `production-deploy` example uses `queue: max`. — [GitHub Docs: Concurrency](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/control-the-concurrency-of-workflows-and-jobs)
- Fly's CI guide: "concurrency: deploy-group    # optional: ensure only one action runs at a time". — [Fly Docs: Continuous deployment with GitHub Actions](https://docs.fly.io/launch/continuous-deployment-with-github-actions)
- Neon/Fly preview example: `concurrency: group: pr-${{ github.event.number }}` so only one deployment runs per PR. — [neondatabase/preview-branches-with-fly](https://github.com/neondatabase/preview-branches-with-fly)
- Railway Wait-for-CI: deployments sit `WAITING` until all GitHub check suites finish (2-hour timeout); for migrations, keep that workflow "out of any concurrency group that cancels queued runs, or running the step as a pre-deploy command". — [Railway: GitHub autodeploys](https://docs.railway.com/guides/github-autodeploys)
- Environment protection: "All deployment protection rules must pass before a job referencing the environment is sent to a runner", which serialises production behind reviewer approval. — [GitHub Docs: Workflow syntax](https://docs.github.com/en/actions/writing-workflows/workflow-syntax-for-github-actions)

### Inferences
- Use `group: deploy-test` with default queueing (skipping intermediate merges is fine for test) and `group: deploy-production` with `queue: max` so every published release deploys in order; never set `cancel-in-progress: true` on a job that runs migrations.
- Combining `concurrency` with Environment required reviewers gives a deployment lock plus approval gate without extra tooling; the hosts' own deploy serialisation (Fly per-app, ECS per-service deployment) is the second layer.

### Gaps
- The GitHub page fetched does not explicitly state the default value of `cancel-in-progress` (behaviour described implies false).
- No source on dedicated deployment-locking tools beyond Actions `concurrency`; none appears necessary for a single-service repo.
