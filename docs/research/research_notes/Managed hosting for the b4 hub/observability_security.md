# Observability, alerting, and edge security for a small internet-facing Rust (axum/tokio/tracing/sqlx) API on a managed container host

Research date: 2026-11-01. Scope: logging, metrics, tracing, uptime/alerting, status page, edge protections, secret hygiene, dependency/image hygiene, solo-operator incident basics. Google Cloud and Cloudflare excluded as vendors the owner would buy from (note: two of the candidate hosts, Render and Railway, themselves sit behind Cloudflare/Fastly networks; see the edge section). Prices are as read from vendor pages on 2026-11-01 unless flagged; several pages carry no date.

## Key question 1: Structured logging from `tracing` to stdout, and what each host does with stdout logs (retention, search, export, cost)

### Takeaway
Every candidate host captures stdout/stderr, parses single-line JSON, and keeps it for only 3–30 days depending on plan; none charges separately for the built-in log viewer, but long retention requires shipping to a vendor (Fly: NATS log shipper app; Render: log streams to syslog/HTTPS vendors; Railway: no log drain, run Vector/Fluent Bit or push via OTLP from the app; AWS: CloudWatch Logs at $0.50/GB ingested after 5 GB free). Emit one JSON object per line from `tracing_subscriber::fmt().json()`, with `level`, `message`, `target`, and span fields flattened.

### Cited Findings
- Fly.io: "We have an app log search feature in Grafana that retains logs for 7 days." App output flows from the Machine's init to Vector on the host and then to an internal NATS cluster; a proxy in front of NATS limits you to your own logs, and Vector can read NATS and forward elsewhere — the Fly Log Shipper app is the packaged example. `fly logs` and the dashboard only live-tail. The page states no log pricing. — [Fly.io docs: Logs](https://docs.fly.io/metrics-and-logs/logs)
- Fly Log Shipper: deployed with `fly launch --image ghcr.io/superfly/fly-log-shipper:latest`; it runs Vector reading Fly's NATS stream, scoped to the whole organization (collects logs from all apps); `ACCESS_TOKEN` is a Fly personal access token; `SUBJECT` defaults to `logs.>`; bundled sinks include AWS S3, Uptrace, and a generic HTTP endpoint. — [superfly/fly-log-shipper README](https://github.com/superfly/fly-log-shipper/blob/5d78784996afc3f905bee7139b73118d3d64afcd/README.md); background in [Fly blog: Shipping Logs](https://fly.io/blog/shipping-logs/) (undated blog post, likely 2022; flag as older)
- Fly.io community: Fly "doesn't keep your logs around forever"; a community answer describes the built-in window as short; one search result referenced 30-day Grafana retention on an undated page, which conflicts with the current docs' 7 days — treat 7 days as current. — [Fly community: How long does Fly store logs?](https://community.fly.io/t/how-long-does-fly-io-store-logs/12789); [Fly docs](https://docs.fly.io/metrics-and-logs/logs)
- Render dashboard retention by workspace plan: Hobby 7 days, Pro 14 days, Scale/Enterprise 30 days; "Logs older than the current retention period are no longer available, even after a plan upgrade." Render processes a maximum of 6,000 application log lines per minute per running instance; excess lines are dropped and dropped lines do not appear in the log explorer or in log streams. — [Render docs: Logging](https://render.com/docs/logging)
- Render log streams: HTTPS providers are Datadog and Loggly; syslog providers are Better Stack, Coralogix, LaunchDarkly (formerly highlight.io), Mezmo, New Relic, Papertrail, SolarWinds, Sumo Logic. Syslog transport is TLS-encrypted TCP with RFC 5424 lines; HTTPS streams "encrypted logs over HTTPS as JSON payloads." Grafana Loki and Axiom are not listed; an unmatched HTTPS endpoint is treated as syslog. Per-service overrides: Pro+ can omit services, only Scale/Enterprise can route a service to a different destination; Hobby cannot override. "Log streaming traffic does not count against your workspace's outbound bandwidth usage." The page does not state which plans can set a default destination or any fee. — [Render docs: Log Streams](https://render.com/docs/log-streams)
- Railway retention by plan: Free 3 days, Trial 7 days, Hobby 7 days, Pro 30 days, Enterprise up to 90 days; upgrading "will immediately restore logs that were previously outside of the retention period." JSON is parsed only when "The entire JSON log must be emitted on a single line"; stderr lines become `level.error`, stdout `level.info`; `log.msg` normalizes to `log.message`, `log.level` to `log.severity`; levels lowercased and matched to debug/info/warn/error; attributes queryable as `@name:value`. Rate limit: "500 log lines per second per replica" on all plans, excess dropped with a warning. "Railway does not have a log drain setting"; to retain longer, forward stdout with Vector or Fluent Bit, or send from the app via a vendor SDK or OpenTelemetry. — [Railway docs: Logging](https://docs.railway.com/reference/logging)
- AWS CloudWatch Logs (us-east-1, from the pricing page's worked examples): first 5 GB/month free (ingestion, archive storage, and Logs Insights scans), plus 1,800 Live Tail minutes/month; Standard ingestion $0.50/GB in the 5–30 GB band; Infrequent Access class $0.25/GB; archive storage $0.03/GB-month; custom metrics $0.30/metric for the first 10,000; standard alarms $0.10/alarm-metric/month; composite alarms $0.50/month each. The page labels these as examples; verify the tables. — [AWS CloudWatch pricing](https://aws.amazon.com/cloudwatch/pricing/)
- AWS App Runner "is no longer open to new customers. Existing customers can continue to use the service as normal... AWS recommends Amazon ECS Express Mode." — [AWS App Runner docs: Managing AWS WAF web ACLs (banner)](https://docs.aws.amazon.com/apprunner/latest/dg/waf-manage.html)

### Inferences
- For this hub, the host's built-in viewer is adequate for live debugging, but any compliance-ish need (auth audit trail beyond 7 days) forces a shipper or direct OTLP export from the app. Direct OTLP export from the Rust process (opentelemetry-appender-tracing to Honeycomb/Grafana/Axiom) is the only path that works identically on all four hosts, because Railway has no drain and Fly's shipper is a separate app to run.
- Railway's 500 lines/s/replica and Render's 6,000 lines/min/instance (100/s) caps mean debug-level request logging on a busy WebSocket service can silently drop lines; keep stdout at INFO and send DEBUG spans via OTLP sampling instead.
- Because stderr becomes `error` on Railway regardless of content, write all `tracing` output to stdout.

### Gaps
- Fly's current log-search retention appears only as a one-line statement (7 days) and conflicts with an older community figure (30 days); no official changelog found.
- Render does not publish whether log streams are available on Hobby workspaces or any per-GB fee for them.
- Railway's third-party observability guide URL (`/guides/connect-third-party-observability-tool`) returned 404; the logging page links to it but the canonical location was not found.
- CloudWatch Logs Insights per-GB-scanned rate was not in the fetched portion of the pricing page.

## Key question 2: OpenTelemetry in Rust in 2026 — crate state, axum/tower-http instrumentation, sqlx spans, minimal setup, overhead

### Takeaway
As of October 2026 the opentelemetry-rust crates are at 0.33.x: Logs and Metrics API/SDK are stable and the OTLP exporters for logs and metrics became stable in 0.33.1, but "Distributed Tracing remains pre-stable"; `tracing-opentelemetry` 0.34 bridges `tracing` spans to OTel and depends on `opentelemetry ^0.33`. The minimal production setup is `tracing_subscriber::registry()` + JSON `fmt` layer (stdout) + `tracing_opentelemetry::layer()` with an OTLP `SdkTracerProvider` using batch export, + tower-http `TraceLayer` with a custom `make_span_with`; sqlx has no built-in OTel spans, so wrap repository calls in `#[tracing::instrument]`. No authoritative benchmark exists; overhead is dominated by the subscriber layer, so sample at the SDK (sampler runs before span creation).

### Cited Findings
- opentelemetry-rust releases: `opentelemetry 0.33.1` (09 Oct, marked Latest); 0.33.0 notes say "Distributed Tracing remains pre-stable" and "The Logs and Metrics API and SDK remain stable"; 0.33.1 notes: "The OTLP exporters for Logs and Metrics are now stable" (they were release candidates in 0.33.0). Metrics SDK was declared stable in 0.30.0; Logs SDK and Logs-Appender-Tracing stable in 0.29.0; Logs API stable in 0.28.0. The releases page shows `opentelemetry-otlp 0.31.1` dated 19 Mar as the most recent separately-listed otlp tag; years are not shown on the page. — [opentelemetry-rust releases](https://github.com/open-telemetry/opentelemetry-rust/releases)
- `tracing-opentelemetry` 0.34.0 depends on `opentelemetry ^0.33.0` (dev-deps `opentelemetry_sdk`, `opentelemetry-otlp`, `opentelemetry-stdout` ^0.33). Minimal setup: build `SdkTracerProvider::builder().with_simple_exporter(...).build()`, `provider.tracer("name")`, `tracing_opentelemetry::layer().with_tracer(tracer)`, add to `Registry::default().with(telemetry)`. The `metrics` feature (default on) adds `MetricsLayer` exporting metrics from specially named events. "The crate does not export logs to OpenTelemetry collectors" — use `opentelemetry-appender-tracing`. The docs warn breaking changes may occur because `opentelemetry` is not yet stable; no performance discussion. — [docs.rs: tracing-opentelemetry](https://docs.rs/tracing-opentelemetry/latest/tracing_opentelemetry/)
- 2026 third-party guides pair `tracing-opentelemetry 0.33` with `opentelemetry 0.32` and `opentelemetry-otlp 0.32` (`grpc-tonic`, `trace` features), build the exporter with `.with_tonic()`, attach to `SdkTracerProvider` with batch export, and use tower-http `TraceLayer` per request plus custom Tower middleware for W3C context propagation; a January 7, 2026 guide still uses `opentelemetry_sdk 0.24`/`opentelemetry-otlp 0.17` with the removed `new_exporter()` API and should not be copied. — [OneUptime: Instrument Rust Axum with OpenTelemetry (2026-02-06)](https://oneuptime.com/blog/post/2026-02-06-instrument-rust-axum-opentelemetry/view); [OneUptime: trace context propagation (2026-01-25)](https://oneuptime.com/blog/post/2026-01-25-opentelemetry-trace-context-propagation-rust/markdown); outdated: [OneUptime 2026-01-07](https://oneuptime.com/blog/post/2026-01-07-rust-opentelemetry-instrumentation/view)
- `tracing-otel` 0.33.2 is a convenience crate (successor to `tracing-otel-extra`) that wires the standard `OTEL_EXPORTER_OTLP_*` env vars, gRPC on 4317 by default. — [docs.rs: tracing-otel](https://docs.rs/crate/tracing-otel/latest)
- tower-http 0.7.1 `TraceLayer`: sample output `request{method=GET path="/foo"}: started processing request` and `finished processing request latency=1 ms status=200` at DEBUG; headers are opt-in via `DefaultMakeSpan::new().include_headers(true)`; levels adjustable with `DefaultOnRequest::new().level(Level::INFO)`; latency unit via `.latency_unit(LatencyUnit::Micros)`; the pattern for late-bound fields is `tracing::debug_span!("http-request", request_id = tracing::field::Empty)` then `span.record(...)`. — [docs.rs: tower_http::trace](https://docs.rs/tower-http/latest/tower_http/trace/index.html)
- sqlx 0.9.0 `ConnectOptions` exposes `log_statements(level)` ("Log executed statements with the specified `level`"), `log_slow_statements(level, duration)`, and `disable_statement_logging()`; no span/OTel API is documented on the trait. — [docs.rs: sqlx ConnectOptions](https://docs.rs/sqlx/latest/sqlx/trait.ConnectOptions.html)
- Overhead: the OpenTelemetry spec's performance-benchmark doc exists but no tracing-opentelemetry number is published; a Reddit commenter attributes cost to many `Instant::now()` calls; the fastrace author reported "~12.5x faster than tracing-opentelemetry" with a no-op exporter, acknowledged as not equivalent work; another commenter: "tracing itself doesn't really have much overhead; the overall performance really depends on the layer/subscriber." Datadog's engineering post notes the SDK "calls the sampler before a span is created, and the resulting decision is immutable", which "minimizes overhead by dropping unsampled spans as early as possible." — [r/rust fastrace thread](https://redlib.hbubli.cc/r/rust/comments/1jh2fzg/fastrace_a_modern_approach_to_distributed_tracing/mjdoo1l/?context=3); [Datadog engineering: Rust tracing + OpenTelemetry](https://datadoghq.com/blog/engineering/rust-tracing-opentelemetry); [OTel spec performance benchmark](https://opentelemetry.io/docs/specs/otel/performance-benchmark/index.md)

### Inferences
- Pin `opentelemetry*` 0.33 and `tracing-opentelemetry` 0.34 together; the ecosystem moves in lockstep and mixing minor versions fails to compile. Expect one breaking upgrade per quarter until tracing is declared stable.
- For a tiny service, send traces with a head-based sampler (for example 10–20% of requests, 100% of errors via a `tracing` filter) and emit logs to stdout only; this keeps the vendor free tiers (next section) comfortably under limits.
- sqlx query spans must be added by hand (`#[instrument(skip(pool), fields(db.system="postgresql", db.operation=...))]`) and must not include bind parameters, which can carry tokens.

### Gaps
- No peer-reviewed or vendor-neutral benchmark of `tracing-opentelemetry` per-span cost in 2026 was found; only competitor-authored comparisons.
- The exact `opentelemetry_sdk`/`opentelemetry-otlp` 0.33.x release dates were not confirmed from the releases page (years omitted).

## Key question 3: Vendors with generous free/cheap tiers; OTLP acceptance; prices

### Takeaway
For a one-person service, Grafana Cloud Free (10k series, 50 GB logs, 50 GB traces, 14-day retention, 3 users, IRM for 3 users, synthetics included) and Honeycomb Free (20M events/month, native OTLP) cover logs/metrics/traces at $0; Sentry Developer (5k errors, 5M spans, 5 GB logs, 1 user, free forever) covers error tracking with a `tracing` layer; Axiom Personal ($0, 500 GB/month, 30 days) and New Relic Free (100 GB/month, 1 full user, 8-day retention) are alternatives; Better Stack Telemetry is 3 GB/3 days free. Datadog has no durable free tier for this use and costs roughly $15–36/host/month plus $0.10/GB logs ingested and $1.70–2.55 per million indexed events.

## Key question 5: Status page options and whether a one-person product needs one at launch

### Takeaway
Free status pages exist at every uptime vendor (Better Stack Free: 1 page; UptimeRobot Free: 1 basic page; Instatus Starter: free with 200 subscribers; Atlassian Statuspage Free: 100 subscribers, 2 team members), so the cost of having one is $0; the realistic launch choice is a monitor-driven page at the uptime vendor rather than a separate product.

### Cited Findings

## Key question 6: Metrics that matter; Postgres metrics from providers; `/metrics` Prometheus vs OTLP push

### Takeaway

### Cited Findings

- `tracing-opentelemetry` `metrics` feature exports metrics from specially named `tracing` events (`MetricsLayer`). — [docs.rs: tracing-opentelemetry](https://docs.rs/tracing-opentelemetry/latest/tracing_opentelemetry/)

## Key question 7: Secret hygiene in logs — `tracing` field redaction, header scrubbing in tower-http, sqlx statement logging defaults, testing

### Takeaway
sqlx logs every executed statement at DEBUG by default (and statements slower than 1 s at WARN), so a `RUST_LOG=debug` deployment prints SQL (not bind values, but statement text); set `log_statements(LevelFilter::Trace)` or `disable_statement_logging()` in production. tower-http `TraceLayer` does not log headers unless `include_headers(true)`; wrap `Authorization`/`Cookie`/`Sec-WebSocket-Key` with `SetSensitiveRequestHeadersLayer` placed before `TraceLayer` so `HeaderValue::set_sensitive` redacts Debug output. Wrap tokens in a newtype whose `Debug` prints a fixed marker (secrecy-style), never derive `Debug` on structs holding them, and `#[instrument(skip(...))]` arguments. Test by running the subscriber into an in-memory writer and asserting the token string is absent.

### Cited Findings
- sqlx `LogSettings` defaults: `statements_level: LevelFilter::Debug`, `slow_statements_level: LevelFilter::Warn`, `slow_statements_duration: Duration::from_secs(1)`; `ConnectOptions::log_statements(level)`, `log_slow_statements(level, duration)`, and `disable_statement_logging()` ("Entirely disables statement logging (both slow and regular)"). — [sqlx-core/src/connection.rs (main)](https://raw.githubusercontent.com/launchbadge/sqlx/main/sqlx-core/src/connection.rs); [docs.rs sqlx 0.9.0 ConnectOptions](https://docs.rs/sqlx/latest/sqlx/trait.ConnectOptions.html)
- sqlx issue #942 records that statement logs were originally at INFO and were lowered to DEBUG because users found them too noisy in production. — [launchbadge/sqlx#942](https://github.com/launchbadge/sqlx/issues/942)
- tower-http 0.7.1 `sensitive_headers` (feature `sensitive-headers`): `SetSensitiveHeadersLayer` ("Mark headers as sensitive on both requests and responses"), `SetSensitiveRequestHeadersLayer` ("Mark request headers as sensitive"), `SetSensitiveResponseHeadersLayer`; example marks `Authorization` "so it doesn't show in logs"; "to hide headers on both requests and responses with TraceLayer, you have to apply SetSensitiveRequestHeadersLayer before TraceLayer" and the response layer after it. — [docs.rs: tower_http::sensitive_headers](https://docs.rs/tower-http/latest/tower_http/sensitive_headers/index.html)
- tower-http `TraceLayer` default span records method and path; headers are opt-in with `include_headers(true)`. — [docs.rs: tower_http::trace](https://docs.rs/tower-http/latest/tower_http/trace/index.html)
- Newtype pattern: a `Secret<T>` with a hand-written `Debug` that always writes a fixed redaction marker, inner value exposed only via `expose()`, unit-tested by asserting the formatted output does not contain the secret (litchee crate example). Derive-macro alternative: `redactable` crate (`#[sensitive(Secret)]`, `#[sensitive(skip_debug)]`, generated `tracing`/`slog` integrations; its docs warn never to enable the `testing` feature in production because it prints real values; 0.11 requires Rust 1.97). — [litchee secret module](https://docs.rs/crate/litchee/latest/source/src/secret/mod.rs); [redactable 0.11.0](https://docs.rs/crate/redactable/0.11.0); [redactable 0.6.2](https://docs.rs/crate/redactable/0.6.2)
- Sentry's docs warn that with `#[instrument]`, function arguments become span fields by default, which can leak sensitive data (Sentry's Python/Rust bridge docs, `include_tracing_fields`). — [Sentry docs: Rust Tracing integration](https://docs.sentry.io/platforms/python/integrations/rust_tracing/)
- Railway: stderr lines are tagged `level.error` and JSON must be single-line to be parsed; multi-line pretty `Debug` output would be stored as separate raw lines. — [Railway docs: Logging](https://docs.railway.com/reference/logging)

### Inferences
- Production `RUST_LOG` should be `info,sqlx=warn` (keeps slow-statement warnings, drops statement text) and the code should additionally call `disable_statement_logging()` or `log_statements(Trace)` on `PgConnectOptions`, so a misconfigured env var cannot re-enable SQL logging.
- Apple identity tokens, WebAuthn challenges/attestations, and device bearer tokens should be `Secret<String>`-typed from extraction (`TypedHeader<Authorization<Bearer>>` → newtype) through to verification; log only a stable fingerprint (e.g. first 8 hex of SHA-256) when correlation is needed.
- Test harness: initialize `tracing_subscriber::fmt().json().with_writer(shared Vec<u8>)` in integration tests, exercise a login/WebSocket path with a known token, then assert `!output.contains(token)` and `!output.contains("Bearer ")`; also run with `RUST_LOG=trace` to prove redaction does not rely on filtering.

### Gaps
- No official `tracing` documentation on field redaction was found; the ecosystem relies on `Debug` impls and third-party crates (`secrecy`, `redactable`). The `secrecy` crate page was not fetched this session.
- sqlx does not document whether bind parameters are ever logged; from the code structure (`SqlStr` logged with elapsed time) only statement text is logged, but this was not verified line-by-line.

## Key question 8: Edge security without Cloudflare — TLS policy per host, HSTS, body limits, rate limiting, bot/abuse protection for auth endpoints, AWS WAF, Fly/Render/Railway DDoS posture, what is reasonable for launch

### Takeaway
None of Fly, Render, or Railway offers an always-on, user-configurable L7 WAF or rate limiter as of late 2026: Fly terminates TLS at Fly Proxy (TLS versions/ALPN configurable via `tls_options`, response headers addable via `http_options.response.headers`, infra-level DDoS protection only), Render provides free DDoS protection "built on Cloudflare's network" (no user controls, TLS 1.2+ per staff), Railway provides an incident-only "Under Attack Mode" that blocks all non-browser traffic (so it would block an API/WebSocket service) and, since February 2026, a Fastly WAF layer. ## Key question 9: Security headers and CORS for an API that receives Apple's browser form POST, plus `Referrer-Policy`/`Cache-Control` for the custom-scheme handoff redirect

### Takeaway
Apple's `form_post` response mode delivers the authorization result as a cross-site `POST` from `https://appleid.apple.com` to the registered HTTPS `redirect_uri`, so the callback must accept a top-level cross-site form POST (no CORS preflight is involved for a navigation POST, but any state cookie must be `SameSite=None; Secure`, scoped to the callback path, short-lived). The handoff response that redirects to the app's custom URL scheme should carry `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and the code/token should travel in the redirect fragment or a one-time code rather than a query string that could be logged.

### Cited Findings
- Apple: for `response_mode=form_post`, "an HTTP POST request containing the results of the authorization is sent to the redirectURI"; an `id_token` response type requires `response_mode` to be `fragment` or `form_post` (Apple forum answer). — [Apple: Request an authorization to the Sign in with Apple server](https://developer.apple.com/documentation/signinwithapplerestapi/request-an-authorization-to-the-sign-in-with-apple-server.); [Apple Developer Forums thread 660531](https://developer.apple.com/forums/thread/660531)
- Apple `redirect_uri` must be HTTPS — no localhost, no IPs. — [ActingWeb guide: Sign in with Apple](https://actingweb.readthedocs.io/en/latest/docs/guides/apple-sign-in.html)
- State/CSRF cookie: "Apple specifically requires SameSite=None on the bound cookie because the form-post callback is a cross-site POST — SameSite=Lax cookies are not sent." Arctic docs: "Make sure to set the state cookie with the SameSite=None attribute." — [cheers-providers Apple redirect source](https://docs.rs/crate/cheers-providers/latest/source/src/providers/apple/redirect.rs); [Arctic: Apple provider](https://v1.arcticjs.dev/providers/apple)
- Mitigation for not loosening SameSite site-wide: use "an additional, SameSite-free, path-scoped (just to the callback URL), short-lived cookie only during Apple login"; the same post says you may need CORS rules allowing `https://appleid.apple.com`, ideally only for POSTs to the SIWA redirect URL. — [bscotch: Sign in with Apple implementation hurdles](https://blog.bscotch.net/post/sign-in-with-apple-implementation-hurdles/)
- OWASP API8:2023 Security Misconfiguration covers missing security headers and permissive CORS. — [OWASP API Security Top 10 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10)
- Fly can add/remove response headers at the proxy via `http_options.response.headers`. — [Fly docs: configuration reference](https://docs.fly.io/reference/configuration)

### Inferences
- A browser form navigation POST is not subject to CORS (it is a simple request/navigation), so a strict CORS policy (no `Access-Control-Allow-Origin` for `appleid.apple.com`) still works for the callback; the bscotch advice to allow the Apple origin applies only if the callback is fetched via XHR/fetch, which Apple does not do. Keep CORS closed for the API (apps are native, not browsers) and exempt only the callback route from CSRF checks by validating `state` against the path-scoped `SameSite=None; Secure; HttpOnly; Max-Age=600` cookie.
- The handoff: respond to the callback with `303 See Other` to `b4app://auth?code=<one-time code>` plus `Cache-Control: no-store`, `Pragma: no-cache`, `Referrer-Policy: no-referrer`, and a minimal HTML fallback with a button (for browsers that block automatic custom-scheme redirects). Exchange the one-time code for the device bearer token over the API so the identity token never sits in a URL or log; log the callback with `code` redacted.
- Apply `X-Frame-Options: DENY`/`Content-Security-Policy: frame-ancestors 'none'` to the callback HTML to prevent clickjacking of the handoff page.

### Gaps
- Apple's documentation page could not be fetched (returned only a title); wording of `form_post` requirements with `name`/`email` scope is from secondary sources and training knowledge.
- No authoritative source found on `Referrer-Policy` specifically for custom-scheme redirects; the recommendation follows general OAuth redirect hygiene.

### Inferences
- Because Dependabot's Docker ecosystem does not do security updates, pin the base image by digest (`FROM debian:bookworm-slim@sha256:...`) and rely on Dependabot `docker` version updates (which bump digests) plus Trivy image scans to catch OS CVEs; Renovate can do the same with `pinDigests`, but Renovate docs were not fetched.
- For a Rust static or `distroless`/`scratch` final image, Trivy's `library` scan of the binary is limited; the `cargo-deny` advisories check is the primary Rust CVE gate, and Trivy mainly covers the OS layer.
- Weekly scheduled runs matter more than PR runs for a solo project with sparse commits, since advisories land between commits.

### Gaps

- Grype/Syft documentation not fetched; Trivy covers the same need.
- No 2026 primary source confirming GHCR scanning status beyond the absence of any mention in GitHub's docs.

## Key question 11: Incident basics for a solo operator — on-call via phone push, runbook location, backups verified, vendor incident notification

### Takeaway
A solo operator should route monitor alerts through one paging tool that can escalate from push to phone call (Better Stack voice/SMS/push, Grafana IRM phone/SMS for up to 3 users free, or UptimeRobot credits), subscribe to the host's and DB vendor's status pages (Fly, Render, Railway, and AWS all publish incident reports/status pages; RSS/email availability per page not verified this session), keep the runbook in the repo (`docs/`), and treat backup verification as a scheduled restore test rather than a vendor promise.

### Cited Findings
- Better Stack: "Unlimited voice call alerts", SMS, email, Slack, Teams, push; escalation rules by time, team availability, incident origin. — [Better Stack Uptime](https://betterstack.com/uptime)
- Grafana IRM Free: 3 active IRM users; no fixed limits on outgoing phone/SMS notifications, subject to throttling at abnormal volume. — [Grafana OnCall](https://grafana.com/products/cloud/oncall/); [Grafana IRM rate limits](https://grafana.com/docs/grafana-cloud/observe-and-act/respond-to-incidents/irm/reference/rate-limits/)
- UptimeRobot: SMS/voice credits are one-time grants; Solo includes 10–20, Team 30. — [UptimeRobot pricing](https://uptimerobot.com/pricing/)
- Sentry Developer includes 1 uptime monitor and 1 cron monitor free. — [Sentry pricing](https://sentry.io/pricing/)
- Vendor incident communication exists and is detailed: Railway publishes post-incident reports (Feb 2026 multi-day DDoS and Cloudflare BGP outage; Jan 2024 report). — [Railway incident report Feb 2026](https://blog.railway.com/p/incident-report-february-19-2026); [Railway incident report Jan 2024](https://blog.railway.com/p/2024-01-31-incident-report)
- Instatus Starter and Atlassian Statuspage Free both let you subscribe users to incident updates (200 and 100 subscribers respectively), the same mechanism by which vendors' own Statuspage-hosted pages notify customers. — [Instatus pricing](https://instatus.com/pricing); [Atlassian Statuspage pricing](https://www.atlassian.com/software/statuspage/pricing)
- OWASP API9:2023 Improper Inventory Management: "incomplete documentation, outdated API versions, and exposed debug endpoints create hidden risk" — supports keeping an inventory/runbook. — [OWASP API Security Top 10 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10)

### Inferences
- Recommended solo setup: (1) uptime monitor → Better Stack (push + call) or Grafana IRM; (2) Sentry alerts for new error classes → email/push; (3) vendor status subscriptions via email to a dedicated folder plus the vendors' status feeds in a reader; (4) a `docs/runbook.md` in the repo covering deploy/rollback, DB restore, token-rotation, and "host down" steps, mirrored to the status page's internal notes; (5) a monthly calendar reminder to restore the latest managed-Postgres backup into a scratch database and run the hub's own migration/health check.
- Because all four hosts and the auth dependency (Apple) are single points of failure the operator cannot fix, the runbook's most valuable section is "communicate and wait" templates for the status page.

### Gaps
- RSS/Atom and email-subscription availability on status.flyio.net, Render's status page, Railway's status page, and the AWS Health Dashboard were not verified (search returned unrelated results). The report writer should state that these pages exist and recommend checking each for a subscribe link.
