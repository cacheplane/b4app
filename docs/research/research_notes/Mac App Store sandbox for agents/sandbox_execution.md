# Mac App Store (App Sandbox) process-execution and file-access rules for running coding-agent CLIs

Scope: what a sandboxed Mac App Store or TestFlight-for-Mac build of b4app could and could not do when it runs `codex app-server`, `claude`, `node` and the tools those agents invoke. Researched 2026-11-01. Labels: **[Apple doc]** is Apple's documentation, an SDK header, or the App Review Guidelines. **[DTS]** is a post by Quinn "The Eskimo!" (Apple Developer Technical Support), who says he does not speak for App Review. **[Report]** is a third-party developer account. **[Local]** was checked on the owner's Mac (macOS 26 / Darwin 25.5, Xcode 26.6). Older items carry their date.

This deepens `docs/research/research_notes/App Store and TestFlight signing/mac_app_store_sandbox.md` (Q2/Q3). Its central claim holds up: a sandboxed process may execute only inside its static allowlist, children inherit the sandbox, and no user consent flow grants execute permission. The single sanctioned exception is `NSUserUnixTask` with the Application Scripts folder (Q5).

## Q1. Can a sandboxed app execute a binary outside its bundle (e.g. /opt/homebrew/bin/codex, ~/.local/bin/claude), including one the user picks with NSOpenPanel? What does `com.apple.security.files.user-selected.executable` allow?

### Takeaway
No. Execution is limited to the static sandbox: the app's bundle, system locations, and `/Applications`. The user granting a file or folder (open panel, security-scoped bookmark) extends read and write access, never execute access. `user-selected.executable` lets the app *write* files that keep their execute bit (shell scripts and the like). It does not let the app run a user-chosen binary. DTS's only recommendation for running developer tools is to not sandbox.

### Cited Findings
- **[DTS, Feb 2024]** "Running `otool` from `/Applications/Xcode.app/...` works because `/Applications` is in the sandbox's built-in allowlist. This is part of your static sandbox, so you can run executables from there." A copy of Xcode in `~/XcodeZone` "might not be part of your static sandbox so, by default, you won't be able to run tools from it." — [Running Developer Tools from a Sandboxed App](https://developer.apple.com/forums/thread/746478)
- **[DTS, Feb 2024]** "For normal files you can dynamically extend your sandbox to allow this, for example, by presenting a standard open panel. However, this doesn't work for executable access. There is currently no way to get a dynamic sandbox extension that grants executable access." — [thread 746478](https://developer.apple.com/forums/thread/746478)
- **[DTS, Feb 2024]** `/usr/bin` developer tools such as `otool` are `xcrun` trampolines, and they fail with "`xcrun: error: cannot be used within an App Sandbox.`" Tool locations inside the Developer directory are not API. — [thread 746478](https://developer.apple.com/forums/thread/746478)
- **[DTS, Feb 2024]** "The only approach I'm prepared to actively recommend is to not sandbox your app." If you must sandbox, the alternatives are (1) using only tools inside the static sandbox, accepting that complex tools may break, or (2) embedding the tool, which works only for compatibly licensed open-source tools, makes the app bigger, and pins one version. — [thread 746478](https://developer.apple.com/forums/thread/746478)
- **[DTS, Mar 2021]** "Sandboxed apps cannot run arbitrary shell scripts. If you want to support script attachment, you should look at NSUserScriptTask." A script embedded in the bundle "is definitely possible". — [thread 677025](https://developer.apple.com/forums/thread/677025)
- **[Report, Mar 2021]** A developer added `com.apple.security.files.user-selected.executable`, `user-selected.read-write` and `scripting-targets`, picked the binary with NSOpenPanel, and still could not run it. DTS's reply only redirected to thread 677025 and did not confirm that this combination grants execution. — [thread 677172](https://developer.apple.com/forums/thread/677172)
- **[Apple doc, archived, ~2016]** The entitlement key reference describes `com.apple.security.files.user-selected.executable` as letting the app *write* executable files. An app that creates executables run other than through Launch Services (e.g. shell scripts) should also specify it. Apple's current per-entitlement page returned 404 when fetched. — [Enabling App Sandbox (archive)](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html) (summarised by search; not fetched directly)
- **[Report/search summary]** Files a sandboxed app writes are quarantined by default, and Gatekeeper blocks quarantined executables unless the user opens them from Finder. So writing a downloaded agent binary into the container and running it is also blocked. — [Enabling App Sandbox (archive)](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html); [ITMS-90885 thread](https://developer.apple.com/forums/thread/730398) (search summary)

### Inferences
- `/opt/homebrew/bin/codex`, `~/.local/bin/claude`, `~/.nvm/.../node` and `~/.bun/bin/*` cannot be executed by a sandboxed b4app or its children, whatever entitlements or user picks are involved. `/usr/bin/git` is an `xcrun` trampoline (it is when only CLT or Xcode supplies git), so it would hit the same `xcrun ... App Sandbox` error. I inferred this from the otool example. It was not tested for git.
- Codex is a native Rust binary. A **bundled** copy (inside `Contents/MacOS` or `Contents/Helpers`) is executable, because the bundle is in the static sandbox.

### Gaps
- Apple publishes no list of the macOS 26 static execute allowlist. `/Applications` comes from DTS. `/usr/bin` and `/bin` system binaries are allowed in practice, but I found no current doc that says so.
- I found no first-hand test, after 2024, showing whether a binary inside a user-granted folder fails at `posix_spawn` (EPERM) or at a later check. DTS's "no dynamic extension grants executable access" is the most authoritative statement found.

## Q2. Children inherit the sandbox: what can a sandboxed `git`/`bash`/`node` child read and write? Bookmarked project folders? ~/.codex and ~/.claude? Will App Review accept temporary-exception entitlements?

### Takeaway
Any child (bundled with `app-sandbox` + `inherit`, or an unsigned or third-party binary from an allowed location) runs inside the parent's sandbox. It gets the parent's container, entitlements and (by DTS's description) its IPC rules. `HOME` is remapped to the container, so `~/.codex` and `~/.claude` resolve to empty container paths. Reaching the real ones needs `temporary-exception.files.home-relative-path.*`. App Review now rejects those for new submissions; one was rejected in April 2026 on an agent-CLI app.

### Cited Findings
- **[DTS, 2021]** "A child process inherits the sandbox from its parent, and thus is subject to the same rules concerning IPC and so on." An XPC service has its own sandbox, and its children inherit that one. — [thread 677025](https://developer.apple.com/forums/thread/677025)
- **[DTS, Feb 2024]** "when a sandboxed app runs a command-line tool like this, the tool inherits the app's sandbox." — [thread 746478](https://developer.apple.com/forums/thread/746478) (as quoted in the prior notes)
- **[Apple doc]** An embedded helper must be signed with exactly `com.apple.security.app-sandbox` and `com.apple.security.inherit`. Other entitlements on the tool "can cause problems", and `get-task-allow` is incompatible with `inherit`. — [Embedding a command-line tool in a sandboxed app](https://developer.apple.com/documentation/xcode/embedding-a-helper-tool-in-a-sandboxed-app)
- **[Report, Apr 2026]** PolyPilot, a Mac Catalyst app with a "copilot helper process" that uses `~/.copilot/`, was rejected under **Guideline 2.4.5(i)**: "Entitlement `com.apple.security.temporary-exception.files.home-relative-path.read-only` value "/" is not permitted." The PR says "Temporary exception entitlements are not approved for new Mac App Store submissions". That is the developer's reading, not Apple's text. The fix was to drop the exceptions, rely on the sandbox remapping `HOME` to `~/Library/Containers/<bundle-id>/Data/` (the helper inherits that), and do a one-time best-effort copy of `.copilot/` into the container. — [PureWeen/PolyPilot PR #578](https://github.com/PureWeen/PolyPilot/pull/578) (opened 2026-04-09, merged 2026-04-13)
- **[Report]** An App Review Resolution Center message (quoted in a Japanese developer's post) said a home-relative-path read-write exception "will not be granted" and pointed the developer to DTS for sandbox-compliant alternatives. — [zenn.dev/kyome](https://zenn.dev/kyome/articles/f5a7b9224c7fda) (search summary; not fetched)
- **[Apple engineer, forums]** Temporary exceptions were allowed in the MAS while sandbox infrastructure such as security-scoped bookmarks was being built. They remain public API, App Review "typically" rejects them, and they are fine outside the MAS. — [Access dot folder file from macOS app with App Sandbox, thread 709333](https://developer.apple.com/forums/thread/709333) (search summary)
- **[Report, Dec 2024]** Cascable dropped a read-write temporary exception it had used for exporting outside the container in order to pass review. — [Journey to Cascable Studio pt 1: App Review](https://ikennd.ac/blog/2024/12/journey-to-cascable-studio-pt-1-app-review/) (search summary)

### Inferences
- **Project folders.** A repo the user picks with NSOpenPanel (persisted as a security-scoped bookmark and started with `startAccessingSecurityScopedResource`) gives the parent read and write access. Inherited children should share that access, because they run in the same sandbox instance. DTS's "same rules" statement supports this, but no source tested it explicitly for bookmark extensions. Even then, nothing under the repo is *executable* (Q1), so `./gradlew`, `node_modules/.bin/*`, `.venv/bin/python`, and repo-local scripts would all fail to exec.
- **Agent login state.** With `HOME` remapped, a bundled Codex would read `$CODEX_HOME` / `~/.codex` from the container and a bundled Claude Code would read `~/.claude` from the container. The user's existing CLI logins, config, MCP servers, skills, and session history would be invisible. The user would have to log in again inside the app, as PolyPilot's migration approach implies. A one-time copy needs read access to the real `~/.codex`, which needs either an exception (rejected) or the user picking `~/.codex` in an open panel. Dot-folders are hidden by default, but the panel can show them.
- **Keychain.** Claude Code on macOS stores its OAuth credential in the login keychain. A sandboxed child signs as the app (or inherits the app's identity) and could not read an item the user's unsandboxed `claude` created, because of the item's ACL and access group. This is an inference; I did not test it.

### Gaps
- No primary Apple statement that inherited children receive the parent's *dynamic* (bookmark) extensions. It is widely assumed and consistent with DTS, but untested here.
- No Apple-published policy text listing which temporary exceptions App Review still grants. The evidence is reports and one forum engineer.

## Q3. Bundling the agents: would a bundled `codex` (Rust) and a bundled Node + Claude Code, signed with sandbox + inherit, work?

### Takeaway
They would launch and could talk to the network if the app has `network.client`. They would be crippled agents: their own config and login live in the container, and every tool they spawn must come from the static allowlist. That rules out Homebrew, nvm, pyenv, cargo, repo-local binaries, and Xcode toolchain trampolines. Write access is limited to the container and user-granted folders.

### Cited Findings
- **[Apple doc]** Bundled helpers are allowed and must carry exactly app-sandbox + inherit. App Store Connect rejects any unsandboxed executable in the bundle (ITMS-90296). — [Embedding a command-line tool in a sandboxed app](https://developer.apple.com/documentation/xcode/embedding-a-helper-tool-in-a-sandboxed-app); [thread 41400](https://developer.apple.com/forums/thread/41400)
- **[DTS, Feb 2024]** Embedding is viable only for compatibly licensed open-source tools, makes the app larger, and pins the version, so you "can only ship the version you build". — [thread 746478](https://developer.apple.com/forums/thread/746478)
- **[DTS, Feb 2024]** Tools reached through `xcrun` trampolines fail inside the sandbox. — [thread 746478](https://developer.apple.com/forums/thread/746478)
- **[Apple doc]** 2.4.5(iv): MAS apps "may not download or install standalone apps, kexts, additional code, or resources to add functionality or significantly change the app". 2.5.2 bars executing code "which introduces or changes features or functionality of the app". — [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- **[Report, Apr 2026]** PolyPilot ships an agent CLI helper in the sandbox that inherits the app's sandbox and remapped `HOME`. That shows the bundled-helper pattern for an agent CLI got to review. — [PolyPilot PR #578](https://github.com/PureWeen/PolyPilot/pull/578)

### Inferences
- **Codex.** Codex is Apache-2.0 open source, so embedding fits DTS's licensing condition. Codex auto-updates (`codex` self-update and npm distribution), which would have to be disabled under 2.4.5(vii) and (iv). Codex's own macOS sandbox runs commands under Seatbelt (`/usr/bin/sandbox-exec`). Whether a process already in App Sandbox can apply a further Seatbelt profile is unverified. It may fail, which would force `danger-full-access` mode inside the app's sandbox.
- **Claude Code.** Claude Code is proprietary (Anthropic's commercial terms), so embedding needs Anthropic's permission. It also auto-updates and downloads native builds, which conflicts with 2.4.5(iv) and (vii). Its Bash tool would run `/bin/bash` and `/bin/zsh`, which are system locations and likely in the allowlist. Anything those shells exec from `/opt/homebrew` or `~/` would fail.
- **Node.** A bundled Node can run, but `npm install` writes into the project folder (allowed if granted) and runs package lifecycle scripts and native builds that need compilers. Those need `/usr/bin/clang` and `make`, which are `xcrun` trampolines, and Homebrew Python. The JIT needs no special entitlement under App Sandbox. `allow-jit` is a Hardened Runtime entitlement, and its interaction with inherit (where only two entitlements are allowed) is unverified.
- **Network.** Inherited from the parent's `com.apple.security.network.client`. `codex app-server` speaks stdio, so no listener is needed, but the hub link and any local MCP servers that listen would need `network.server`.
- **Net effect.** A MAS b4app with bundled agents is technically buildable. Its agents could edit files in granted repos and run system binaries only, which breaks most real coding-agent workflows (builds, tests, package managers).

### Gaps
- No public report found of a MAS app shipping Claude Code or Codex bundled and sandboxed. PolyPilot is the closest analogue, but its PR does not say which CLI binary it bundles.
- Nested Seatbelt inside App Sandbox (Codex's sandbox) is untested and unsourced.

## Q4. Do Guidelines 2.5.2 and 2.4.5 bar running agents that execute arbitrary shell commands, or interpreters? MAS precedents (CodeRunner, BBEdit, terminals) and how they do it

### Takeaway
The guidelines don't name agents or interpreters. The bar comes from the sandbox (2.4.5(i)) together with 2.5.2/2.4.5(iv) on downloaded or executed code that changes the app's functionality. MAS developer tools that run code (CodeRunner 4, BBEdit since 12.6 in 2019) live inside these limits and report toolchain breakage, such as the `xcrun ... App Sandbox` error in CodeRunner. Apple's own Xcode is distributed through the MAS but is **not** sandboxed (Q6), so it is no precedent for third parties.

### Cited Findings
- **[Apple doc]** 2.4.5(i): "They must be appropriately sandboxed, and follow macOS File System Documentation." (iii): no code running at login without consent, and no spawned processes that "continue to run without consent after a user has quit the app". (iv): no downloading or installing "additional code, or resources to add functionality". (v): no root escalation. (vii): updates only through the MAS. — [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- **[Apple doc]** 2.5.2: apps "may not read or write data outside the designated container area, nor may they download, install, or execute code which introduces or changes features or functionality of the app, including other apps". Educational code-teaching apps are the only carve-out, and they must keep code "completely viewable and editable by the user". — [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- **[Apple doc]** 4.7 allows "chatbots" and "plug-ins" not embedded in the binary. 4.7.2: "Your app may not extend or expose native platform APIs or technologies to the software without prior permission from Apple." — [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- **[Report]** CodeRunner 4 is on the MAS ("run code in 25 languages"). A user review reports "xcrun: error: cannot be used within an App Sandbox" running Python 3, and a release note mentions improved PATH resolution "eliminating run issues with certain third-party tools". — [CodeRunner 4 on the App Store](https://apps.apple.com/cl/app/id955297617) (search summary)
- **[Report, 2019]** BBEdit 12.6 became sandboxed to return to the MAS. Its release notes describe reworking the AppleScript runner "for sandbox compatibility" and modernizing "the #! script and Unix executable runner ... and shell worksheets". — [BBEdit 12.6 release notes](https://barebones.com/support/bbedit/notes-12.6.html); [MacRumors, 2019-04-04](https://www.macrumors.com/2019/04/04/bbedit-returns-to-mac-app-store) (search summary)
- **[Bare Bones]** Without broad file access, "many of BBEdit's most useful features, from the basic to the most powerful, won't work at all." Editing `#!` scripts with execute permission draws extra macOS security restrictions. — [BBEdit and App Sandboxing](https://www.barebones.com/support/bbedit/AppSandboxing.html)
- **[Report, unverified]** A forum poster claims BBEdit sandboxes only the main app, not its embedded command-line tools, and is still in the MAS. No reply confirmed it. — [thread 771117](https://developer.apple.com/forums/thread/771117) (Dec 2024, 0 replies)
- **[Forum reports, older]** Scripting Terminal from a MAS app is not allowed because it is an easy sandbox escape. A review rejected an app that ran a shell command (a fastlane build) through Terminal. — [thread 10011](https://developer.apple.com/forums/thread/10011); [thread 663311](https://developer.apple.com/forums/thread/663311) (search summary; not fetched)

### Inferences
- An AI agent that runs commands the model chooses is arguably "executing code" chosen at runtime. The guideline's test is whether that code "introduces or changes features or functionality of the app". The text gives App Review room either way. The practical blocker is the sandbox, not 2.5.2.
- Local-shell terminal emulators (iTerm2, Warp, Ghostty) are distributed outside the MAS. I found no sandboxed MAS app that offers a general local shell with the user's PATH tools. Not verified exhaustively.

### Gaps
- I did not find how CodeRunner 4 (MAS) actually invokes compilers: Application Scripts, `/usr/bin` only, or something else. Its documentation was not retrieved.
- No App Review statement specific to AI coding agents found.

## Q5. The NSUserUnixTask / Application Scripts route: can the user place a script in `~/Library/Application Scripts/<bundle id>/` that execs `codex app-server` unsandboxed, with stdin/stdout pipes? Is it App Review-acceptable?

### Takeaway
Mechanically, yes. `NSUserUnixTask` runs a user-installed script from that folder **outside the app's sandbox**, with arguments and `NSFileHandle` stdin, stdout and stderr, so a user-installed shim `#!/bin/zsh -l` → `exec codex app-server` would give an unsandboxed, pipe-connected Codex (or `claude --output-format stream-json`). The app can read the folder but not write it, so the user has to install the script by hand. DTS (July 2025) warns that the API "is intended to be used to implement script attachment, not as a general-purpose sandbox bypass mechanism". An app whose core function depends on it would be at real risk under 2.4.5(i) and 2.5.2. I found no app that does this for an agent.

### Cited Findings
- **[Apple doc, SDK header, Xcode 26.6]** "These classes are intended to execute user-supplied scripts, and will execute them outside of the application's sandbox, if any. (They are *not* intended to execute scripts built into an application; for that, use NSTask, NSAppleScript, or AMWorkflow.) If the application is sandboxed, then the script must be in the "application scripts" folder ... A sandboxed application may read from, but not write to, this folder." — `Foundation.framework/Headers/NSUserScriptTask.h` [Local]; same wording in [NSUserScriptTask docs](https://developer.apple.com/documentation/foundation/nsuserscripttask)
- **[Apple doc, SDK header]** `NSUserUnixTask` has `standardInput`, `standardOutput` and `standardError` (`NSFileHandle`, nil binds to `/dev/null`). It runs with `executeWithArguments:completionHandler:`. "The arguments do not undergo shell expansion ... shell variables are not resolved." — `NSUserScriptTask.h` [Local]; [NSUserUnixTask docs](https://developer.apple.com/documentation/foundation/nsuserunixtask)
- **[Apple doc, SDK header]** `NSApplicationScriptsDirectory` = "the user scripts folder for the calling application (~/Library/Application Scripts/code-signing-id)". It is keyed by code-signing identifier, macOS 10.8+. — `NSPathUtilities.h` [Local]
- **[DTS, Jul 2025]** "Because these scripts were specifically installed by the user, their presence indicates user intent and the system runs them outside of your app's sandbox." Use `NSUserUnixTask` to "Supply command-line arguments. Connect pipes to stdin, stdout, and stderr. Get the termination status." The app can reveal the folder in Finder with `NSWorkspace.shared.activateFileViewerSelecting([scriptsDir])` so the user can add scripts. — [Implementing Script Attachment in a Sandboxed App](https://developer.apple.com/forums/thread/794355)
- **[DTS, Jul 2025]** "**IMPORTANT** ... While I don't work for App Review, and thus can't make definitive statements on their behalf, I want to be clear that `NSUserScriptTask` is intended to be used to implement script attachment, not as a general-purpose sandbox bypass mechanism." — [thread 794355](https://developer.apple.com/forums/thread/794355)
- **[Report, 2012–2013, old]** cocoa-dev threads report output-handling quirks: a `readabilityHandler` on stdout never fired, and the interpreter had to be explicit. Also, creating a task from a URL outside the folder should fail. — [cocoa-dev Nov 2012](https://lists.apple.com/archives/cocoa-dev/2012/Nov/msg00533.html); [Dec 2012](https://lists.apple.com/archives/cocoa-dev/2012/Dec/msg00019.html) (search summary; may not reflect macOS 26)
- **[Report]** User-facing requirements: the script needs a shebang and the execute bit, and the user must place it manually. — [Xojo forum](https://forum.xojo.com/t/lsof-shell-command-not-running-in-macos-sandbox/68264/10) (search summary)
- **[Apple doc, archived]** Technical Q&A QA1888, "Sandboxing and Automation in OS X", covers the sandboxed-automation story. Not fetched in this pass. — [QA1888](https://developer.apple.com/library/archive/qa/qa1888/_index.html)
- **[Local]** On this Mac, `~/Library/Application Scripts/` contains folders for many sandboxed apps (e.g. `2BBY89MBSN.dev.warp`, `BQR82RBBHL.com.tinyspeck.slackmacgap`, `UBF8T346G9.com.microsoft.teams`, `59GAB85EFG.com.apple.dt.XcodeCloud`). They show that the folder exists per code-signing id, mostly for app groups and extensions, not that these apps run user scripts.

### Inferences
- **How it would work.** The user installs `b4app-codex.sh` (`#!/bin/zsh -l` to get PATH, then `exec codex app-server "$@"`) into `~/Library/Application Scripts/<team>.com.cacheplane.b4app/` or the plain bundle-id folder (whichever `URLForDirectory:NSApplicationScriptsDirectory` returns). The app creates `NSUserUnixTask(url:)`, sets `standardInput` and `standardOutput` to `Pipe` file handles, and calls `execute(withArguments:)`. The completion handler fires at exit. The script and everything it spawns run unsandboxed as the user, so git, Homebrew, `~/.codex`, `~/.claude` and the login keychain all work.
- **Gaps against b4app's current model.** There is no PID, and therefore no SIGTERM, process-group signalling, or identity verification. `LocalServerService`'s "never signal a process whose identity it has not verified" cannot be met directly; the script could write its PID to a file in the container's readable area, but that is a hand-rolled channel. There is no environment control (no `env` parameter, so the script must set its own) and no cwd parameter (pass it as an argument and `cd` in the script). Each long-lived app-server is a script invocation. The coordinator, PostgreSQL and the LaunchAgent would all need the same treatment or a redesign, since they hit separate sandbox walls (prior notes Q4).
- **Review risk.** The feature is "script attachment". An app that cannot do its primary job until the user installs an exec shim is using the API as the "general-purpose sandbox bypass" DTS warns against. Reviewers test the app as submitted. If the core feature does nothing without a manually installed script, that also risks rejection under 2.1 (app completeness) or as a demo that fails review. This is an inference, not documented policy.
- A scripted or one-click installer for the shim cannot come from the sandboxed app, because the folder is read-only to it. Asking the user to save a file there with an NSSavePanel aimed at the folder could work technically (user-selected write). Whether the sandbox allows a user-selected write into that specific folder is unverified.

### Gaps
- No app was found, in the MAS or out, that uses Application Scripts to host an AI agent or another long-lived stdio server. No App Review decision on such a design was found.
- Behaviour of `NSUserUnixTask` pipes with long-lived bidirectional JSON-RPC (buffering, child lifetime when the app quits, whether the child is killed with the app) is unverified on macOS 26. 2.4.5(iii) forbids processes that keep running after quit without consent.

## Q6. Xcode 26 (a MAS app) runs coding agents. Is Xcode sandboxed?

### Takeaway
No. Xcode 26.6 on this Mac carries no `com.apple.security.app-sandbox` entitlement. It is signed by Apple (team `59GAB85EFG`) with dozens of private `com.apple.private.*` entitlements. Its ability to host coding agents is an Apple-only privilege, not a precedent a third-party MAS app can cite.

### Cited Findings
- **[Local]** `codesign -d --entitlements - /Applications/Xcode.app` (Xcode 26.6): `app-sandbox` appears 0 times. The entitlements include `com.apple.private.security.cryptex.mount`, `com.apple.private.security.storage.CoreSimulator`, `com.apple.private.security.restricted-application-groups`, `com.apple.corespotlight.privateindex.unsandboxed`, `com.apple.modelmanager.inference`, and the application identifier `59GAB85EFG.com.apple.dt.Xcode`. The bundle contains `SharedFrameworks/CodeGenerationIntelligence.framework` and `IDECodeGenerationIntelligence.framework`.
- **[DTS, Feb 2024]** DTS's guidance for third-party apps that run developer tools is to not sandbox, because Xcode tools (`xcrun` trampolines, selected-Xcode paths) don't work from the sandbox. — [thread 746478](https://developer.apple.com/forums/thread/746478)

### Inferences
- Third-party apps must meet 2.4.5(i) sandboxing. Apple's own apps are not bound by App Review in the same way and can hold private entitlements no third party can get. So "Xcode runs Claude/Codex agents from the MAS" does not imply b4app could.

### Gaps
- I did not research where Xcode 26's agent integration (Claude Agent / Codex, added in the Xcode 26.x line) stores or runs its agent binaries. No `CodingAssistant` directory was found under `~/Library/Developer/Xcode` on this Mac. That detail is unsourced here.
