# iOS HIG mobile layout guidance: hit targets, buttons, lists, layout, text fields (iOS 26, SwiftUI)

Method note: the HIG pages were read from Apple's own JSON (`https://developer.apple.com/tutorials/data/design/human-interface-guidelines/<page>.json`) on 2026-11-01, and API pages from `https://developer.apple.com/tutorials/data/documentation/<path>.json`. Citations use the human-readable URLs of the same pages. Change-log dates are quoted from each page so the writer can tell current guidance from older guidance. An archived copy of the Layout page (Wayback, 2025-12-01, alert date 2025-09-09) was used to recover iOS-specific guidance that the September 2026 revision removed.

## Minimum hit target and spacing between targets

### Takeaway
Apple's number for iOS/iPadOS is a 44x44 pt hit region (the "default control size"), with 28x28 pt as the absolute minimum. Spacing gets its own guidance: about 12 pt of padding around bezeled elements and about 24 pt around unbezeled ones (bare icons, text). What counts is the hit region, not the visible glyph. In SwiftUI the hit region is set with `contentShape`.

### Cited Findings
- Buttons page, verbatim rule: "As a general rule, a button needs a hit region of at least 44x44 pt — in visionOS, 60x60 pt — to ensure that people can select it easily, whether they use a fingertip, a pointer, their eyes, or a remote." — [HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)
- The same page: "It's essential to include enough space around a button so that people can visually distinguish it from surrounding components and content." It also says "Always include a press state for a custom button." — [HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)
- Accessibility > Mobility table, "Default control size / Minimum control size": iOS, iPadOS 44x44 pt / 28x28 pt; macOS 28x28 pt / 20x20 pt; tvOS 66x66 pt / 56x56 pt; visionOS 60x60 pt / 28x28 pt; watchOS 44x44 pt / 28x28 pt. The text: "Strive to meet the recommended minimum control size for each platform." — [HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- Spacing between targets: "Consider spacing between controls as important as size. … In general, it works well to add about 12 points of padding around elements that include a bezel. For elements without a bezel, about 24 points of padding works well around the element's visible edges." — [HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- Accessibility page change log: March 7, 2025 "Expanded and refined all guidance" (the table with the 28x28 minimum belongs to this revision); June 9, 2025 added Assistive Access, Switch Control, and Nutrition Labels. — [HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- visionOS comparison: buttons should have "centers … at least 60 pts apart", and buttons of 60 pt or larger get 4 pt of padding so the hover effect doesn't overlap. visionOS button sizes: Mini 28 pt, Small 32 pt, Regular 44 pt, Large 52 pt, Extra large 64 pt. — [HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons); repeated in [HIG Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- Invisible hit area (macOS image buttons): "An image button's edges define its clickable area even when they aren't visible." The page recommends "about 10 pixels of padding between the edges of the image and the button edges." — [HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)
- Accessibility also says to use simple gestures and to offer onscreen alternatives to gestures, for example a button as well as swipe-to-dismiss. — [HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- SwiftUI: `contentShape(_:eoFill:)` "Defines the content shape for hit testing" and returns "A view that uses the given shape for hit testing." — [contentShape(_:eoFill:)](https://developer.apple.com/documentation/swiftui/view/contentshape(_:eofill:))
- `contentShape(_:_:eoFill:)` (iOS 15+) takes a `ContentShapeKinds`, so the hit-testing shape (`.interaction`) can be set separately from `.focusEffect`, `.contextMenuPreview`, and `.dragPreview` shapes. — [contentShape(_:_:eoFill:)](https://developer.apple.com/documentation/swiftui/view/contentshape(_:_:eofill:))

### Inferences
- For a chat app: give every icon-only control a hit region of at least 44x44 pt. That covers the send button, the attach and runtime pickers, and the small runtime icons if they are tappable. A 16 to 20 pt glyph needs padding or `.frame(minWidth: 44, minHeight: 44)` plus `.contentShape(Rectangle())`. Without a content shape, SwiftUI hit-tests only the drawn content, so transparent padding around a custom-styled label is not tappable. That last point is common SwiftUI behavior; the doc pages above don't state it outright.
- Treat 28x28 pt as an exception for dense secondary controls only, never for the send button.
- An unbezeled icon next to another unbezeled icon wants about 24 pt of space around its visible edges. One way to meet that with 44 pt boxes is to place the boxes edge to edge, since a 20 pt glyph in a 44 pt box leaves 12 pt on each side.

### Gaps
- The current Layout page has no hit-target number. The 44 pt figure lives only on the Buttons and Accessibility pages.
- No Apple page gives a minimum spacing between list rows or between toolbar items as a number. Toolbar spacing is left to the system (see the buttons section).

## Buttons on iOS 26: styles, sizes, icon-only buttons, Liquid Glass

### Takeaway
iOS 26 adds the `.glass` and `.glassProminent` SwiftUI button styles. Bordered buttons default to a capsule shape. There is a new extra-large control size for the most important actions. Toolbar items sit on a floating Liquid Glass surface and group automatically. Apple's advice is to use system styles and not hard-code metrics. The HIG publishes no iOS button heights or padding values; those numbers exist only for visionOS.

### Cited Findings
- Prominence: "use a button that has a prominent visual style for the most likely action in a view … Keep the number of prominent buttons to one or two per view." Also "Use style — not size — to visually distinguish the preferred choice among multiple options." — [HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)
- Liquid Glass color: "Avoid applying a similar color to button labels and content layer backgrounds … prefer using the default monochromatic appearance of button labels." — [HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)
- Roles: Normal, Primary, Cancel, Destructive. A primary button uses the accent color and a destructive button uses system red. "Don't assign the primary role to a button that performs a destructive action." — [HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)
- iOS-specific: a button can show an activity indicator, with an optional alternate label such as "Checking out…", for actions that don't complete instantly. — [HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)
- Buttons page change log: December 16, 2025 "Updated guidance for Liquid Glass"; June 9, 2025 "Updated guidance for button styles and content." — [HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)
- `PrimitiveButtonStyle.glass` (iOS 26.0+): "A button style that applies a Liquid Glass effect based on the button's context." — [glass](https://developer.apple.com/documentation/swiftui/primitivebuttonstyle/glass)
- `PrimitiveButtonStyle.glassProminent` (iOS 26.0+): "applies a prominent Liquid Glass effect … This style is similar to the borderedProminent style." — [glassProminent](https://developer.apple.com/documentation/swiftui/primitivebuttonstyle/glassprominent)
- WWDC25 session 323: "Bordered buttons now have a capsule shape by default", and "the existing button border shape modifier enables you to specify the shape for any size" (`.buttonBorderShape(.capsule)`). The session also says "for your most important, prominent actions there is now support for extra large sized buttons." Example: `.buttonStyle(.glassProminent)` / `.buttonStyle(.glass)`. — [WWDC25 Build a SwiftUI app with the new design](https://developer.apple.com/videos/play/wwdc2025/323/)
- `buttonBorderShape(_:)` (iOS 15+) affects buttons of the `bordered` and `borderedProminent` styles. — [buttonBorderShape(_:)](https://developer.apple.com/documentation/swiftui/view/buttonbordershape(_:))
- `ControlSize` cases: `mini`, `small`, `regular` (the default), `large`, `extraLarge`. `extraLarge` (iOS 17.0+) is documented as "Resolves to large on platforms other than visionOS." — [ControlSize](https://developer.apple.com/documentation/swiftui/controlsize); [ControlSize.extraLarge](https://developer.apple.com/documentation/swiftui/controlsize/extralarge)
- Conflict to flag: the API doc says `extraLarge` resolves to `large` outside visionOS. Apple's Liquid Glass overview says "Controls also feature an option for an extra-large size, allowing more space for labels and accents". WWDC25 sessions 356 and 323 describe a new X-Large size on macOS and for prominent buttons. The writer should not assume `.controlSize(.extraLarge)` looks different from `.large` on iPhone without testing. — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass); [WWDC25 Get to know the new design system](https://developer.apple.com/videos/play/wwdc2025/356/)
- `controlSize(_:)` (iOS 15+) "override[s] the system default size for controls in this view" and can be applied to one control or a container. — [controlSize(_:)](https://developer.apple.com/documentation/swiftui/view/controlsize(_:))
- `buttonSizing(_:)` (iOS 26.0+) is "The preferred sizing behavior of buttons". `.flexible` makes a button span its container; `.fitted` sizes it to its content. — [buttonSizing(_:)](https://developer.apple.com/documentation/swiftui/view/buttonsizing(_:))
- Liquid Glass overview: "If you use standard controls from system frameworks and don't hard-code their layout metrics, your app adopts changes to shapes and sizes automatically." It also says "Prefer to use standard spacing metrics instead of overriding them, and avoid overcrowding or layering Liquid Glass elements on top of each other," and advises "Avoid overusing Liquid Glass effects" on custom controls. — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)
- Shapes (WWDC25 356): "Capsules use a radius that's half the height of the container. And concentric shapes calculate their radius by subtracting padding from the parent's." For phones: "use a capsule with extra margin to create space near the screen edge." On macOS, "Large controls will now use capsule shapes, alongside with the new X-Large size", while Mini, Small, and Medium keep rounded rectangles. — [WWDC25 Get to know the new design system](https://developer.apple.com/videos/play/wwdc2025/356/)
- Concentric shapes in SwiftUI: `.background(.tint, in: .rect(corner: .containerConcentric))` makes a shape "automatically match its container". — [WWDC25 323](https://developer.apple.com/videos/play/wwdc2025/323/)
- Icon-only toolbar items (Toolbars page): "Prefer simple, recognizable symbols for items instead of text, except for actions like edit." The page also says "Prefer system-provided symbols without borders … Borders (like outlined circle symbols) aren't necessary because the section provides a visible container." and "Use the standard Back and Close buttons … don't use a text label that says Back or Close." — [HIG Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)
- Toolbar grouping: "Minimize the number of groups … aim for a maximum of three." Also "Keep actions with text labels separate," inserting fixed space between them. On iOS, "Prioritize only the most important items … Create a More menu to include additional items." Change log: Dec 16, 2025 Liquid Glass; June 9, 2025 grouping and symbols, with navigation bar guidance folded in. — [HIG Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)
- SwiftUI toolbar APIs (WWDC25 323): "Toolbar items are automatically grouped". `ToolbarSpacer(.fixed)` splits groups and `ToolbarSpacer(.flexible, placement: .bottomBar)` adds flexible space. `.sharedBackgroundVisibility(.hidden)` separates an item without a background, and `.badge(_:)` works on toolbar items. A primary action like Done "appears tinted, often as a blue checkmark on iOS" (WWDC25 356). — [WWDC25 323](https://developer.apple.com/videos/play/wwdc2025/323/); [WWDC25 356](https://developer.apple.com/videos/play/wwdc2025/356/)
- "Provide an accessibility label for every icon." Also: "don't mix text and icons across items that share a background." — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)

### Inferences
- Composer send button: an SF Symbol such as `arrow.up` in a circular `.glassProminent` or `.borderedProminent` button, shaped with `.buttonBorderShape(.circle)`, framed at 44 pt or more, and given an accessibility label "Send". That follows the guidance on prominent primary actions, circle/capsule shapes, and accessibility labels. The HIG doesn't prescribe a composer button specifically.
- Make the send button the only prominent button in the thread view, per "one or two per view".
- Keep `.glass` on controls and navigation, never on transcript bubbles or thread rows. The Liquid Glass overview says the material "forms a distinct functional layer for controls and navigation elements."

### Gaps
- Apple publishes no point heights for iOS `ControlSize` values or for bordered or glass buttons on iPhone, and no recommended horizontal padding inside them. Only visionOS sizes are tabulated. Measure in the simulator if exact numbers are needed.
- No source confirms whether `.extraLarge` renders differently from `.large` on iOS 26.

## Lists and tables: row heights, insets, separators, swipe and context actions

### Takeaway
The HIG Lists page has no row-height number. In SwiftUI the floor is `defaultMinListRowHeight`, which is an environment value with no published default; the familiar 44 pt is legacy knowledge, not a documented iOS 26 value. iOS 26 officially gives lists "a larger row height and padding" and rounder section corners. Row padding is changed with `listRowInsets`, spacing with `listRowSpacing` and `listSectionSpacing`, and separators per row with `listRowSeparator`.

### Cited Findings
- Liquid Glass overview: "To give content room to breathe, organizational components like lists, tables, and forms have a larger row height and padding. Sections have an increased corner radius to match the curvature of controls across the system." — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)
- HIG Lists and tables: "Prefer displaying text in a list or table." Also "Keep item text succinct so row content is comfortable to read." For long items: "you could list item titles only, letting people choose an item to reveal its content in a detail view." A middle ellipsis "can make an item easier to distinguish". — [HIG Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables)
- Row styles: "you might need to display a small image in the leading end of a row, followed by a brief explanatory label." The page points to `UIListContentConfiguration` for built-in row layouts. Styles: the iOS grouped style "uses headers, footers, and additional space to separate groups of data." — [HIG Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables)
- Selection feedback: navigation tables "persistently highlight[] the selected row"; option lists highlight briefly and then show a checkmark. "In iOS and iPadOS, people must enter an edit mode before they can select table items." — [HIG Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables)
- iOS accessories: use a disclosure indicator to drill into a row. The info button (detail disclosure) is "only to reveal more information about a row's content". Avoid an index on a list whose rows have trailing controls. — [HIG Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables)
- The Lists page was last changed June 21, 2023. It has no Liquid Glass revision, so the iOS 26 row changes are documented only in the Liquid Glass overview. — [HIG Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables)
- `defaultMinListRowHeight` (iOS 13+): "The height of list rows is bounded below by this default value, and is otherwise determined by the height of the row's content and the row insets." The doc gives no default number. `defaultMinListHeaderHeight` defaults to `nil` ("the system chooses the appropriate height"). — [defaultMinListRowHeight](https://developer.apple.com/documentation/swiftui/environmentvalues/defaultminlistrowheight); [defaultMinListHeaderHeight](https://developer.apple.com/documentation/swiftui/environmentvalues/defaultminlistheaderheight)
- `listRowInsets(_:)` changes "the default padding of the content of list items" by taking `EdgeInsets?`. Version note: "On iOS 18 and earlier … the content of list rows can grow slightly into the row insets. The effective vertical insets can then be smaller than expected." This implies iOS 26 honors insets more strictly. — [listRowInsets(_:)](https://developer.apple.com/documentation/swiftui/view/listrowinsets(_:))
- `listRowSpacing(_:)` (iOS 15+) sets vertical spacing between adjacent rows (`nil` keeps the default). `listSectionSpacing(_:)` (iOS 17+) sets spacing between sections; when adjacent sections differ, each applies half its spacing. — [listRowSpacing(_:)](https://developer.apple.com/documentation/swiftui/view/listrowspacing(_:)); [listSectionSpacing(_:)](https://developer.apple.com/documentation/swiftui/view/listsectionspacing(_:))
- `listRowSeparator(_:edges:)` (iOS 15+) expresses a preference; "The list style is the final arbiter of the separator visibility." Related modifiers: `listRowSeparatorTint`, `listSectionSeparator`. — [listRowSeparator(_:edges:)](https://developer.apple.com/documentation/swiftui/view/listrowseparator(_:edges:))
- `InsetGroupedListStyle` (iOS 14+), also available as `.insetGrouped`. — [InsetGroupedListStyle](https://developer.apple.com/documentation/swiftui/insetgroupedliststyle)
- `swipeActions(edge:allowsFullSwipe:content:)` (iOS 15+): the default edge is trailing and `allowsFullSwipe` defaults to true, so a full swipe performs the first action. Apple's example is a messages list with unread toggled from the leading edge and delete or flag on the trailing edge. — [swipeActions](https://developer.apple.com/documentation/swiftui/view/swipeactions(edge:allowsfullswipe:content:))
- Reachability and swipe: "it tends to be easier and more comfortable for people to reach a control when it's located in the middle or bottom area of the display, so it's especially important to let people swipe to navigate back or initiate actions in a list row." — [HIG Designing for iOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-ios)
- Context menu previews can get their own shape via `.contentShape(.contextMenuPreview, RoundedRectangle(cornerRadius: 10))`. — [contentShape(_:_:eoFill:)](https://developer.apple.com/documentation/swiftui/view/contentshape(_:_:eofill:))
- Accessibility (via Layout): rows "may need to grow in height so that text isn't cropped," and single-line rows "might need to grow vertically to accommodate multiple lines of text" under Dynamic Type. — [HIG Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- UIKit: inset grouped cells are inset on the leading and trailing edges by the table view's `directionalLayoutMargins` (Apple developer forums, not official docs). — [Apple Developer Forums thread 712026](https://developer.apple.com/forums/thread/712026)

### Inferences
- For the thread list, use the default `List` with a title, a one-line subtitle (`.lineLimit(1)` with `.truncationMode(.middle)` where ids matter), and a small leading runtime icon. Leave row height to the system and don't hard-code 44 pt. iOS 26 rows are already taller, and Dynamic Type must be able to grow them.
- Avoid setting `defaultMinListRowHeight` or `listRowInsets` below the system values unless the design calls for density. Overriding them opts out of the iOS 26 spacing changes the overview says apps pick up for free.
- Leading icon size: the HIG gives none. Matching the row's text style with SF Symbols and `Label`, rather than a fixed pixel size, scales with Dynamic Type. This is a reasonable choice; Apple doesn't mandate it.

### Gaps
- No Apple source gives the iOS 26 default row height in points. The pre-iOS 26 44 pt minimum and any 52 pt figure for iOS 26 are unverified; searches found no primary source. Measure in the iOS 26 simulator.
- No Apple doc gives the default leading text inset of a list row (commonly cited as 16 pt or 20 pt). The separator's leading inset to the text is also undocumented.
- The HIG has no explicit guidance on title-plus-subtitle typography for rows, beyond pointing to `UIListContentConfiguration`.

## Layout: margins, readable width, safe areas, Dynamic Island, bottom edge

### Takeaway
On iPhone, system layout margins run from 16 to 20 pt, per Apple's own API doc. Apple says to read the guide rather than hard-code it. Safe areas cover the Dynamic Island, the home indicator, and bars. The September 2026 Layout revision dropped the iOS-specific section, including "Avoid full-width buttons", and the device-dimension tables that the 2025 revision had. Apple uses no 8 pt grid.

### Cited Findings
- `ContentMarginGuide.container`: "This guide vends the system layout margins, which range from 16 to 20 points on iPhone and are larger on platforms like tvOS. On iPhone Duo, the margin can also be asymmetric … Apply or read the guide instead of writing these values into your layout." The availability is listed as iOS 27.1, so this API is newer than iOS 26, though the 16 to 20 pt fact describes the system margins generally. — [ContentMarginGuide.container](https://developer.apple.com/documentation/swiftui/contentmarginguide/container)
- UIKit: for a view controller's root view, `layoutMargins` and `directionalLayoutMargins` default to values that reflect "the system minimum margins and safe area insets." `systemMinimumLayoutMargins` holds those minimums, and a custom margin smaller than the minimum is raised to it. Apple's example: a minimum of `20` beats a requested `10`. You can opt out with `viewRespectsSystemMinimumLayoutMargins = false`. — [directionalLayoutMargins](https://developer.apple.com/documentation/uikit/uiview/directionallayoutmargins); [systemMinimumLayoutMargins](https://developer.apple.com/documentation/uikit/uiviewcontroller/systemminimumlayoutmargins); [Positioning content within layout margins](https://developer.apple.com/documentation/uikit/positioning-content-within-layout-margins)
- `readableContentGuide`: "never extends beyond the view's layout margin guide," and its width "is equal to or less than the readable width defined for the current dynamic text size." Apple says to use it "to lay out a single column of text." — [readableContentGuide](https://developer.apple.com/documentation/uikit/uiview/readablecontentguide)
- HIG Layout, current revision: a layout guide defines "a rectangular region that helps you position, align, and space your content," including "standard margins around content and restrict[ing] the width of text for optimal readability." A safe area is "the area within a window that isn't covered on the edge by a hardware feature or another view within the window, like a toolbar, tab bar, or status bar. Respecting the safe area is essential to make sure system UI and hardware features like the Dynamic Island don't obstruct content and controls." — [HIG Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- HIG Layout, current revision, on Liquid Glass: "Instead of applying a solid or semi-opaque background color beneath controls, use a scroll edge effect to visually elevate controls above content." Adaptability items listed include "System features like the Dynamic Island" and text-size changes. — [HIG Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- The current Layout page says "No additional considerations for iOS or iPadOS." Change log: "September 9, 2026 | Updated guidance to reflect current best practices"; Sept 9, 2025 added iPhone 17 and iPhone Air specs; June 9, 2025 added Liquid Glass guidance. — [HIG Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- Older revision (2025, flagged as superseded), iOS section: "Avoid full-width buttons. Buttons feel at home in iOS when they respect system-defined margins and are inset from the edges of the screen. If you need to include a full-width button, make sure it harmonizes with the curvature of the hardware and aligns with adjacent safe areas." Also: "Hide the status bar only when it adds value." Same revision: "ensure that scrollable layouts continue all the way to the bottom and the sides of the device screen. Controls and navigation components like sidebars and tab bars appear on top of content." — [HIG Layout, Wayback 2025-12-01](https://web.archive.org/web/20251201140322/https://developer.apple.com/design/human-interface-guidelines/layout)
- Older revision device points (portrait), useful for widths: iPhone 17 Pro Max and 16 Pro Max 440x956 pt; iPhone Air 420x912; iPhone 17, 17 Pro, and 16 Pro 402x874; iPhone 16 Plus and 15 Pro Max 430x932; iPhone 16 and 15 Pro 393x852; iPhone 16e 390x844. Size classes: all iPhones are compact width, regular height in portrait. In landscape, Pro Max, Plus, and Air models are regular width, compact height; the others are compact/compact. — [HIG Layout, Wayback 2025-12-01](https://web.archive.org/web/20251201140322/https://developer.apple.com/design/human-interface-guidelines/layout)
- Current revision on size classes: "Determine layout based on size classes, not device type or orientation." — [HIG Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- WWDC25 356, on iPhone shapes near edges: "For phone layouts, use a capsule with extra margin to create space near the screen edge." — [WWDC25 Get to know the new design system](https://developer.apple.com/videos/play/wwdc2025/356/)
- SwiftUI safe-area APIs:
  - `safeAreaInset(edge:alignment:spacing:content:)` (iOS 15+) anchors content to an edge. "The modified view is inset by the width of content … with its safe area increased by the same amount." `spacing: nil` uses the default. — [safeAreaInset](https://developer.apple.com/documentation/swiftui/view/safeareainset(edge:alignment:spacing:content:))
  - `safeAreaBar(edge:alignment:spacing:content:)` (iOS 26.0+) works like `safeAreaInset`, but "Additionally, it extends the edge effect of any scroll views affected by the inset safe area." — [safeAreaBar](https://developer.apple.com/documentation/swiftui/view/safeareabar(edge:alignment:spacing:content:))
  - `safeAreaPadding(_:_:)` (iOS 17+): "Adds the provided insets into the safe area of this view" (a fixed amount, e.g. `.safeAreaPadding(.horizontal, 20.0)`). — [safeAreaPadding](https://developer.apple.com/documentation/swiftui/view/safeareapadding(_:_:))
  - `contentMargins(_:_:for:)` (iOS 17+): a scroll view "will automatically inset its content by the safe area plus an additional 20 points" in Apple's example. `.scrollContent` and `.scrollIndicators` placements can be set separately. — [contentMargins(_:_:for:)](https://developer.apple.com/documentation/swiftui/view/contentmargins(_:_:for:))
  - `ignoresSafeArea(_:edges:)`: "By default, the SwiftUI layout system sizes and positions views to avoid certain safe areas. This ensures that system content like the software keyboard or edges of the device don't obstruct your views." — [ignoresSafeArea](https://developer.apple.com/documentation/swiftui/view/ignoressafearea(_:edges:))
- Scroll edge effect: "Prefer the automatic scroll edge effect style." Also "Only use a scroll edge effect when a scroll view is behind floating interface elements," and "Apply one scroll edge effect per view." (Change log: June 8, 2026 updated; July 28, 2025 added.) SwiftUI: `scrollEdgeEffectStyle(_:for:)` (iOS 26+). — [HIG Scroll views](https://developer.apple.com/design/human-interface-guidelines/scroll-views); [scrollEdgeEffectStyle](https://developer.apple.com/documentation/swiftui/view/scrolledgeeffectstyle(_:for:))
- Conflict to flag: WWDC25 356 (June 2025) said "Soft is the default … especially on iOS and iPadOS." The June 2026 HIG revision says prefer `automatic`, which "provides a more opaque visual separation for top toolbars that contain a large number of controls … and pinned table headers." — [WWDC25 356](https://developer.apple.com/videos/play/wwdc2025/356/); [HIG Scroll views](https://developer.apple.com/design/human-interface-guidelines/scroll-views)
- iOS 26 tab bars can minimize on scroll (`.tabBarMinimizeBehavior(.onScrollDown)`), and `tabViewBottomAccessory` places a view above the bar. Apple: "Avoid placing screen-specific actions here." — [WWDC25 323](https://developer.apple.com/videos/play/wwdc2025/323/); [WWDC25 356](https://developer.apple.com/videos/play/wwdc2025/356/)
- macOS-only, for contrast: "Avoid placing controls or critical information at the bottom of a window." — [HIG Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- "Check for crowding or overlapping of controls. Prefer to use standard spacing metrics instead of overriding them." — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)

### Inferences
- Use the system margins: the default `List` and `ScrollView` margins and `.padding()` without arguments, rather than a hard-coded 16. Apple says outright not to write these values into layouts, and the iPhone range is 16 to 20 pt.
- Transcript: a `ScrollView` with `.defaultScrollAnchor(.bottom)`, constrained to a readable width on wide windows. SwiftUI has no direct `readableContentGuide`, so a `.frame(maxWidth:)` on the column approximates it. The bubbles go inside the safe area, and the scroll content runs under the composer.
- Composer: attach it with `.safeAreaBar(edge: .bottom)` on iOS 26, or `.safeAreaInset(edge: .bottom)` before that. The transcript then stays scrollable beneath it and gets the scroll edge effect. The bar also respects the home-indicator safe area automatically.
- Spacing scale: no Apple source on these pages describes an 8 pt grid. Apple's published numbers are 12/24 pt padding around controls, 16 to 20 pt margins, 44 pt targets, and the 20 pt `contentMargins` example. Treat "8 pt grid" as a third-party convention, not HIG.

### Gaps
- Apple doesn't say which iPhones get 16 pt and which get 20 pt. A secondary claim that larger phones get 20 pt is unverified. Read `layoutMargins` at runtime on a Pro Max simulator.
- No current Apple source gives the home-indicator inset or Dynamic Island inset in points. They come from the safe area at runtime.
- No current guidance on keeping controls out of the bottom edge's system-gesture area was found beyond "respect the safe area". The old guidance against full-width buttons was removed in September 2026.
- The September 2026 Layout revision dropped the device-spec tables, and where they moved couldn't be determined.

## Text fields and the composer

### Takeaway
The HIG has no point height for an iOS text field. Its guidance is qualitative: placeholder hints, a trailing Clear button, leading and trailing images, matching the field's size to the expected text, and the right keyboard type. A multi-line composer is either `TextField(axis: .vertical)` (iOS 16+) or a `TextEditor`/text view. Keyboard avoidance comes free from the safe area, and controls above the keyboard should use Liquid Glass and the keyboard layout guide.

### Cited Findings
- "Use a text field to request a small amount of information … To let people input larger amounts of text, use a text view instead." — [HIG Text fields](https://developer.apple.com/design/human-interface-guidelines/text-fields)
- Placeholder: "A text field can contain placeholder text … Because placeholder text disappears when people start typing, it can also be useful to include a separate label." — [HIG Text fields](https://developer.apple.com/design/human-interface-guidelines/text-fields)
- "To the extent possible, match the size of a text field to the quantity of anticipated text." — [HIG Text fields](https://developer.apple.com/design/human-interface-guidelines/text-fields)
- iOS/iPadOS: "Display a Clear button in the trailing end of a text field." Also: "use the leading end of a text field to indicate a field's purpose and the trailing end to offer additional features." — [HIG Text fields](https://developer.apple.com/design/human-interface-guidelines/text-fields)
- "Show the appropriate keyboard type." By default text beyond the field's bounds is clipped; wrapping and truncation are configurable. The Text fields page was last changed June 5, 2023. — [HIG Text fields](https://developer.apple.com/design/human-interface-guidelines/text-fields)
- Text views "can be any height and allow scrolling when the content extends outside of the view," and "if a text view is editable, a keyboard appears when people select the view." — [HIG Text views](https://developer.apple.com/design/human-interface-guidelines/text-views)
- Return key: "Consider customizing the Return key type," via `submitLabel(_:)` in SwiftUI. Keyboard type and semantics are set with `keyboardType(_:)` and `textContentType(_:)`. — [HIG Virtual keyboards](https://developer.apple.com/design/human-interface-guidelines/virtual-keyboards)
- Controls above the keyboard (June 9, 2025): "If other views in your app use Liquid Glass, or if your view looks out of place above the keyboard, apply Liquid Glass to the view that contains your controls … If you use a standard toolbar to contain your controls, it automatically adopts Liquid Glass. Use the keyboard layout guide and standard padding." SwiftUI: `ToolbarItemPlacement` (keyboard placement). — [HIG Virtual keyboards](https://developer.apple.com/design/human-interface-guidelines/virtual-keyboards)
- "Use the keyboard layout guide … to keep important parts of your interface visible while the virtual keyboard is onscreen." — [HIG Virtual keyboards](https://developer.apple.com/design/human-interface-guidelines/virtual-keyboards)
- `TextField.init(_:text:axis:)` (iOS 16+): "Specify a preferred axis in which the text field should scroll its content when it does not fit in the available space. Depending on the style of the field, this axis may not be respected." Use `onSubmit(of:_:)` for submit actions. — [TextField init(_:text:axis:)](https://developer.apple.com/documentation/swiftui/textfield/init(_:text:axis:))
- `scrollDismissesKeyboard(_:)` (iOS 16+): "By default, a TextEditor is interactive while other kinds of scrollable content always dismiss the keyboard on a scroll." Modes include `.immediately`, `.interactively`, and `.never`. — [scrollDismissesKeyboard(_:)](https://developer.apple.com/documentation/swiftui/view/scrolldismisseskeyboard(_:))
- `defaultScrollAnchor(.bottom)` (iOS 17+) starts a vertical scroll view at the bottom. "When the content size of the scroll view changes, it may consult the anchor to know how to reposition the content." — [defaultScrollAnchor(_:)](https://developer.apple.com/documentation/swiftui/view/defaultscrollanchor(_:))
- SwiftUI keeps views out of the keyboard's safe area by default ("system content like the software keyboard … don't obstruct your views"). — [ignoresSafeArea](https://developer.apple.com/documentation/swiftui/view/ignoressafearea(_:edges:))
- Liquid Glass overview, on search: "when a person taps a search field to give it focus, it slides upwards as the keyboard appears." — [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)

### Inferences
- Composer: a `TextField("Message", text:, axis: .vertical)` with `.lineLimit(1...6)` keeps it compact but growable, matching "match the size … to the quantity of anticipated text". Put it in a bottom `safeAreaBar`/`safeAreaInset` beside a 44 pt or larger circular send button. Apply `.scrollDismissesKeyboard(.interactively)` to the transcript, the Messages-style behavior. `lineLimit` ranges are a known SwiftUI API that wasn't fetched here.
- Trailing-end features (send, voice) agree with "the trailing end to offer additional features"; leading-end attach/runtime selection agrees with "leading end … purpose".

### Gaps
- No Apple source gives an iOS text field's default height, internal padding, or corner radius on iOS 26.
- No HIG page addresses chat composers or message bubbles specifically.
- The Text fields page has had no Liquid Glass revision since June 2023, so it says nothing about glass composer backgrounds beyond the Virtual keyboards guidance.
