## Certificates, profiles, and signing for a CLI/script-driven build

### Takeaway
For a scripted build, use Xcode automatic signing: run `xcodebuild archive` and then `xcodebuild -exportArchive -allowProvisioningUpdates` with a team App Store Connect API key passed through `-authenticationKeyPath/-authenticationKeyID/-authenticationKeyIssuerID`. Xcode then creates the App ID, the App Store profile, and a cloud-managed Apple Distribution certificate as needed, so no local Distribution certificate is required. The existing Developer ID Application certificate cannot sign this build. Cloud-managed certificates require an Account Holder or Admin, so the key should carry the Admin role.

### Cited Findings
- `-allowProvisioningUpdates` lets xcodebuild talk to the Apple Developer website. For automatically signed targets it "will create and update profiles, app IDs, and certificates"; for manually signed targets it downloads missing or updated profiles. It needs either an account added in Xcode's Accounts settings or an App Store Connect key passed via `-authenticationKeyPath`, `-authenticationKeyID`, and `-authenticationKeyIssuerID`. Source: local `xcodebuild -help`, Xcode 26.6; see also [Xcode distribution docs](https://developer.apple.com/documentation/xcode/distribution).
- On export, `signingStyle` is `manual` or `automatic`, and archives signed automatically default to automatic. If an archive was signed manually and you choose automatic signing at export, "Xcode will create provisioning profiles and managed cloud signing certificates as necessary, but will not register devices, register app IDs, or modify app ID settings." Source: local `xcodebuild -help` (exportOptionsPlist keys), Xcode 26.6.
- The `signingCertificate` automatic selectors for manual signing include "Apple Development", "Apple Distribution", "Developer ID Application", "iOS Distribution", and others. Source: local `xcodebuild -help`, Xcode 26.6.
- Cloud-managed certificates "are associated with your Apple Developer Program membership and managed remotely." Xcode 13 or later cloud-signs for distribution "if you're using the Xcode Organizer archive and distribution workflow, and a local signing certificate is not found." — [Cloud-managed certificates](https://developer.apple.com/help/account/certificates/cloud-managed-certificates)
- Cloud-managed certificates list "Required role: Account Holder or Admin." The same page adds that "Additional permissions are available in App Store Connect to enable Admins and Developers to sign apps and software with these certificates." A new cloud certificate is created automatically 90 days before expiry. — [Cloud-managed certificates](https://developer.apple.com/help/account/certificates/cloud-managed-certificates)
- Local signing alternative: "add an active Apple Distribution certificate to your keychain before signing for distribution or [use] the manual signing processes." — [Cloud-managed certificates](https://developer.apple.com/help/account/certificates/cloud-managed-certificates). The Account Help navigation lists "Create a certificate signing request", "Register an App ID", and "Create an App Store Connect provisioning profile" as the manual steps. That last name replaces the older "App Store" profile name. — [Apple Developer Account Help](https://developer.apple.com/help/account/certificates/cloud-managed-certificates)
- API key types: a Team key has "access to all apps, with varying levels of access based on selected roles." Individual keys "aren't able to use Provisioning endpoints, access sales-and-finance, or notaryTool." — [Creating API Keys for App Store Connect API](https://developer.apple.com/documentation/appstoreconnectapi/creating-api-keys-for-app-store-connect-api)
- Generating team keys requires "an Admin account in App Store Connect" (Users and Access > Integrations > App Store Connect API > Team Keys). The private key "is available for download a single time" and Apple keeps no copy. Apple says: "Don't share your keys, store keys in a code repository, or include keys in client-side code." Key roles are "the same roles that apply to users on your team." — [Creating API Keys for App Store Connect API](https://developer.apple.com/documentation/appstoreconnectapi/creating-api-keys-for-app-store-connect-api)
- TestFlight requires that builds "include application identifiers in the provisioning profiles"; builds without them are not eligible for TestFlight. — [TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview)

### Inferences
- Recommended path: keep the iOS target on `CODE_SIGN_STYLE = Automatic` with `DEVELOPMENT_TEAM = GJJKL34HCT`. Archive with `-allowProvisioningUpdates` plus the API key flags, then export or upload with the same flags and `method: app-store-connect`. This avoids creating, storing, and rotating an Apple Distribution `.p12` on the build machine. A manual Distribution certificate plus an App Store Connect profile is the fallback when cloud signing is blocked.
- The key must be a Team key, because Individual keys cannot use Provisioning endpoints and automatic signing needs to create profiles, App IDs, and certificates. Cloud-managed certificates require Account Holder or Admin, so an Admin-role team key is the safe choice for archive and export with cloud signing. An App Manager or Developer key may be enough for upload only. Apple's role matrix was not confirmed for that case (see Gaps).
- A Developer ID Application certificate (used by the macOS app per D-039) is for distribution outside the App Store and does not apply to TestFlight or App Store iOS builds. Apple lists it as a separate signing identity from "Apple Distribution" in the selectors above. The owner needs no new certificate if cloud signing works; otherwise they need an Apple Distribution certificate.
- The `.p8` key belongs in the Keychain or a secret store referenced by path at build time, never in the repo. This matches both Apple's guidance and the repo rule against secrets in arguments or logs. `-authenticationKeyPath` takes a file path, so a script can write the key to a temp file with restricted permissions and delete it afterward.
- The iOS target has no entitlements file today. Automatic signing adds `application-identifier` and team identifier entitlements at signing time, so no file is needed unless a capability is added.

### Gaps
- Apple's App Store Connect role-permissions table could not be extracted (the page rendered as navigation only), so this research did not confirm the minimum key role for "upload builds" or for "cloud signing via API key". The Admin recommendation rests on the cloud-certificate page's "Account Holder or Admin" requirement. The name and exact behavior of the App Store Connect permission that lets Developers use cloud-managed distribution certificates was also not confirmed.
- No Apple page found states directly that `xcodebuild -exportArchive` with an API key performs cloud signing without a logged-in Xcode account. The `-help` text implies it ("Requires a developer account ... or an App Store Connect authentication key").

## App Store Connect app record, universal purchase, TestFlight internal vs external

### Takeaway
Create one new iOS app record with name, primary language, bundle id `com.cacheplane.b4app.ios`, SKU, and user access. This needs Account Holder, App Manager, or Admin, and the Account Holder must have signed the latest agreement. Universal purchase with the macOS app does not apply: it needs a shared bundle id and one record, while the Mac app has a different bundle id and ships through Developer ID rather than the Mac App Store. Internal testing (up to 100 App Store Connect users) needs no Beta App Review. External testing (up to 10,000) needs test information and Beta App Review of the first build.

### Cited Findings
- The New App dialog fields are Platforms (iOS, macOS, tvOS, visionOS), App name, Primary language, Bundle ID, SKU, and User Access (Limited or Full). "Required role: Account Holder, App Manager, or Admin." "You can't add an app to your account until the Account Holder signs the latest agreement in the Business section." — [Add a new app](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-a-new-app)
- "If you want to offer an app with multiple platforms as a single purchase, create it as a single record in App Store Connect. All platforms will share the same bundle ID, but you'll add platform-specific information separately." Platforms can be added later to create a universal purchase. — [Add a new app](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-a-new-app)
- "You can use an app name for one app per localization." — [Add a new app](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-a-new-app)
- The first upload of a build creates a beta version of the app in the account. — [Upload builds](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds)
- Internal testers: up to 100 App Store Connect users with access to your content. External testers: up to 10,000, invited by email or public link. — [TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview)
- Beta App Review applies when you add the first build to a group of external testers, testing starts once it is approved, and later builds "may not need a full review". Testers can use a build for up to 90 days. Managed Apple Accounts in reserved domains cannot test. — [TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview)
- External-testing prerequisites, in order: upload a build, determine export compliance, include application identifiers in profiles, provide test information, create a group, pass Beta App Review, invite testers. — [TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview)
- Test information for external testing: "In the Beta App Description text field, enter a description of your beta version. This field is required." The Feedback Email is where testers reach you and is the reply-to address on invitations. You can enter it when adding the app or before inviting external testers. — [Provide test information](https://developer.apple.com/help/app-store-connect/test-a-beta-version/provide-test-information)
- For App Store version submissions, App Review information includes a contact (name, email, and phone in international `+` format), notes up to 4000 bytes, and a sign-in demo account "if your app requires a login", which "must not expire". — [App Review information reference](https://developer.apple.com/help/app-store-connect/reference/app-review-information)
- Xcode 26 exports can set `testFlightInternalTestingOnly`: "When enabled, this build cannot be distributed via external TestFlight or the App Store." — local `xcodebuild -help`, Xcode 26.6.

### Inferences
- A separate iOS-only record is the right setup. Joining the macOS record would mean changing one bundle id to match the other and moving the Mac app to the Mac App Store, which conflicts with the D-039 Developer ID path. The Mac app is not on App Store Connect, so there is nothing to join.
- The SKU is a free-form internal identifier. Something like `b4app-ios` works.
- External Beta App Review is a real hurdle for this app. Every feature needs a paired Mac and a self-hosted hub. The beta review notes or demo info should explain how a reviewer can exercise the app, for example a reachable demo hub and an enrollment code, or a clear explanation that the app is a companion. Without that, review may find the app non-functional. Internal-only testing avoids review entirely.
- Use `testFlightInternalTestingOnly: true` for CI and branch builds so they cannot reach external testers by mistake.

### Gaps
- Whether TestFlight external testing requires a Privacy Policy URL and contact info could not be confirmed from Apple's current help pages; the TestFlight information reference URL returned "Page Not Found". The sources conflict. A secondary/older [Apple Developer Forums thread](https://developer.apple.com/forums/thread/706282) has an accepted answer saying a privacy policy is "not required" for a TestFlight beta, while third-party guides such as [aso.dev](https://aso.dev/developer/beta-information) (secondary) list it among required Beta App Information fields. Owner action: check the TestFlight > Test Information page in App Store Connect.
- No Apple source found states typical Beta App Review turnaround time.

## Required Info.plist and bundle contents for upload

### Takeaway
Add `ITSAppUsesNonExemptEncryption = NO`. An HTTPS-only app using OS encryption (URLSession, Keychain) is typically exempt, though a year-end self-classification report may still apply. Builds must use Xcode 26 and the iOS 26 SDK, which the project already does. Keep `CFBundleShortVersionString` as three integers and `CFBundleVersion` as 1–3 integers, unique per upload (Xcode's export can manage it). The existing single 1024×1024 iOS icon meets the asset-catalog route. Add a `PrivacyInfo.xcprivacy` to the app target, even an empty-reasons one, and declare any required-reason API the statically linked packages call. A privacy policy URL is required for the App Store listing.

### Cited Findings
- Export compliance: set `ITSAppUsesNonExemptEncryption` to `NO` "if your app—including any third-party libraries it links against—doesn't use encryption, or if it only uses forms of encryption that are exempt." "Typically, the use of encryption that's built into the operating system—for example, when your app makes HTTPS connections using URLSession—is exempt from export documentation upload requirements, whereas the use of proprietary encryption is not." — [Complying with encryption export regulations](https://developer.apple.com/documentation/security/complying-with-encryption-export-regulations)
- "If your app uses exempt forms of encryption, you might alternatively be required to submit a year-end self-classification report to the U.S. government." — [Complying with encryption export regulations](https://developer.apple.com/documentation/security/complying-with-encryption-export-regulations)
- Without the key, "App Store Connect walks you through an export compliance questionnaire every time you upload a new version of your app." If `YES`, you typically also set `ITSEncryptionExportComplianceCode` from Apple. — [ITSAppUsesNonExemptEncryption](https://developer.apple.com/documentation/bundleresources/information-property-list/itsappusesnonexemptencryption)
- SDK minimum: "Since April 28, 2026 Apps uploaded to App Store Connect must be built with Xcode 26 or later using an SDK for iOS 26, iPadOS 26, ..." Since September 9, 2026, iOS apps must target iOS 13 or later. — [Upcoming requirements](https://developer.apple.com/news/upcoming-requirements/)
- The upload table lists iOS apps and extensions as "built using Xcode 26 or later". "Upload for all target types is supported for Transporter and altool." — [Upload builds](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds)
- `CFBundleVersion`: "one to three period-separated integers", numeric and periods only, "required by the App Store". — [CFBundleVersion](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion). `CFBundleShortVersionString`: "The required format is three period-separated integers, such as 10.14.1." — [CFBundleShortVersionString](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleshortversionstring)
- App Store Connect matches a build to the app and version record by bundle ID and version number. "The build string is used to uniquely identify the build throughout the system." — [Upload builds](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds)
- The `manageAppVersionAndBuildNumber` export key: "Should Xcode manage the app's build number when uploading to App Store Connect? Defaults to YES." — local `xcodebuild -help`, Xcode 26.6.
- Icons: "iOS, iPadOS, tvOS, and watchOS apps can auto-generate all icon variations from a single 1024×1024 pixel image. This is the default behavior." iOS and iPadOS also support Dark and Tinted variants. Icon Composer is the alternative for all variants. — [Configuring your app icon](https://developer.apple.com/documentation/xcode/configuring-your-app-icon); "You can create your app icon using Icon Composer or add your app icon to an asset catalog." — [Add an app icon](https://developer.apple.com/help/app-store-connect/manage-app-information/add-an-app-icon)
- Privacy manifest contents: `PrivacyInfo.xcprivacy` holds `NSPrivacyTracking`, `NSPrivacyTrackingDomains`, `NSPrivacyCollectedDataTypes` (all platforms), and `NSPrivacyAccessedAPITypes` (required on iOS, iPadOS, tvOS, visionOS, watchOS). Create it with File > New File > App Privacy and add it to the target's resources. — [Privacy manifest files](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files)
- Required-reason enforcement: "Starting May 1, 2024, apps that don't describe their use of required reason API in their privacy manifest file aren't accepted by App Store Connect." "If you use the API in your app's code, then you need to report the API in your app's privacy manifest file." "For each executable or dynamic library in an app that uses a required reason API, the bundle that includes the executable or dynamic library needs to include a privacy manifest file that reports the API." — [Describing use of required reason API](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api)
- Static code: "A static library ... doesn't support resources such as the privacy manifest." A Swift package can carry its manifest in its target's resources. — [Adding a privacy manifest to your app or third-party SDK](https://developer.apple.com/documentation/bundleresources/adding-a-privacy-manifest-to-your-app-or-third-party-sdk)
- Reason codes, quoted from [NSPrivacyAccessedAPIType](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype):
  - `NSPrivacyAccessedAPICategoryUserDefaults`: CA92.1 is to "read and write information that is only accessible to the app itself"; 1GF2.1 is for the same App Group; C56D.1 is the third-party SDK wrapper; AC6B.1 is MDM managed config.
  - `NSPrivacyAccessedAPICategoryFileTimestamp`: C617.1 covers metadata "of files inside the app container, app group container, or the app's CloudKit container"; 3B52.1 covers files the user granted access to; DDA9.1 is for displaying timestamps to the user; 0A2A.1 is the third-party SDK wrapper.
  - `NSPrivacyAccessedAPICategorySystemBootTime` (`ProcessInfo.systemUptime`, `mach_absolute_time()`): 35F9.1 is "to measure the amount of time that has elapsed between events that occurred within the app or to perform calculations to enable timers"; 8FFB.1 is for absolute timestamps; 3D61.1 is for bug reports.
  - `NSPrivacyAccessedAPICategoryDiskSpace`: E174.1 is "to check whether there is sufficient disk space to write files"; 85F4.1 is for displaying disk space; 7D9E.1 is for bug reports; B728.1 is for health research.
- Privacy policy and labels: "A privacy policy URL is required for all apps." For iOS: "You're required to provide a privacy policy URL for your iOS app platform." Data-handling answers are required "if you're distributing your app on the App Store", and "Responses are provided at the app level." — [Manage app privacy](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy)
- Age rating: ratings were updated to a new system, and developers had to answer the updated age rating questions by January 31, 2026 to avoid interruptions when submitting. — [Upcoming requirements](https://developer.apple.com/news/upcoming-requirements/)

### Inferences
- `ITSAppUsesNonExemptEncryption: false` fits if the iOS code uses only URLSession TLS and the Keychain. If any iOS-linked module uses CryptoKit or CommonCrypto for its own scheme (for example payload signing beyond TLS), re-check exemption. Authentication and HTTPS uses are usually exempt, but this research did not fetch the exemption criteria page.
- The local packages are linked statically into the app executable, so any required-reason API they call counts as the app's own use and goes in the app target's `PrivacyInfo.xcprivacy`. The grep found none in iOS-linked sources. Two things should be verified before upload: (a) the SQLite mirror code, if it reads file sizes or attributes of its database (C617.1), and (b) any `Date`/uptime measurement using `systemUptime` (35F9.1). Shipping an app manifest with `NSPrivacyTracking: false`, an empty `NSPrivacyTrackingDomains`, and accurate `NSPrivacyAccessedAPITypes` is low cost and avoids ITMS-91053 rejections. System SQLite and Apple frameworks are Apple's responsibility, not the app's.
- Privacy nutrition label: the app sends data only to a hub the user hosts. The developer collects nothing unless the hub is operated by cacheplane, so "Data Not Collected" is likely accurate for a pure self-hosted model. This must be re-evaluated if a demo hub run by the developer is used for review.
- Bundle contents the project already has: `UILaunchScreen: {}` (a SwiftUI-era launch screen), both orientation arrays (four orientations on iPad supports multitasking), `LSRequiresIPhoneOS`, and a 1024 icon. No `UIRequiredDeviceCapabilities` is needed: no Apple source says it is mandatory, and the device family with iOS 26 already constrains devices.
- With `manageAppVersionAndBuildNumber` defaulting to YES, Xcode may rewrite `CFBundleVersion` at export. For reproducible numbering, either set it to NO and stamp a monotonically increasing build number (for example CI run number or `git rev-list --count HEAD`) at archive time, or accept Xcode's management.

### Gaps
- No Apple primary source was fetched that states CFBundleVersion must strictly increase between uploads of the same version. Apple says only that the build string uniquely identifies the build. Increasing numbers are the conventional practice.
- Icon technical constraints for the 1024 PNG (no alpha, color space) were not confirmed from an Apple page this session. The HIG app-icons page was not fetched.
- The exemption-criteria page ("Determine and upload app encryption documentation") was not fetched.
- ITMS error codes other than ITMS-91053 (for example ITMS-90713 missing info, ITMS-90022 missing icon, ITMS-91061 SDK manifests) were not confirmed from Apple sources this session. Treat them as unverified.

## ATS: localhost exception, NSAllowsLocalNetworking, NSLocalNetworkUsageDescription

### Takeaway
`NSExceptionAllowsInsecureHTTPLoads` is on Apple's list of ATS exceptions that "require you to provide justification, and might trigger additional App Store review". `NSAllowsLocalNetworking` is not on that list. On a real device, `localhost` is the phone itself, so the current exception does nothing useful in TestFlight. Options: keep the exception in Debug only (strip it from Release), or swap it for `NSAllowsLocalNetworking`. `NSLocalNetworkUsageDescription` is needed if the app reaches a hub on the LAN; loopback in the Simulator likely does not need it.

### Cited Findings
- Exceptions that need justification: `NSAllowsArbitraryLoads`, `NSAllowsArbitraryLoadsForMedia`, `NSAllowsArbitraryLoadsInWebContent`, "Per-domain nonsecure connections (NSExceptionAllowsInsecureHTTPLoads)", and `NSExceptionMinimumTLSVersion`. "When submitting your app to the App Store, provide sufficient information for the App Store to determine why your app cannot make secure connections by default." "If you must use an exception, make it as limited in scope as possible." — [Preventing insecure network connections](https://developer.apple.com/documentation/security/preventing-insecure-network-connections)
- `NSAllowsLocalNetworking` "controls whether App Transport Security (ATS) allows your app to connect to unqualified domains, `.local` domains, and IP addresses using IPv4 or IPv6." In iOS 17 and later, "ATS no longer allows connections to IP addresses by default. Add individual IP addresses and classless inter-domain routing (CIDR) ranges in the NSExceptionDomains dictionary." Apple suggests "setting NSAllowsLocalNetworking to YES as a declaration of intent, if appropriate." — [NSAllowsLocalNetworking](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking)
- Global exceptions apply to all connections except domains listed in `NSExceptionDomains`. On iOS 10 and later, if any global exception other than `NSAllowsArbitraryLoads` is set, ATS ignores `NSAllowsArbitraryLoads`. — [NSAppTransportSecurity](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity)
- `NSLocalNetworkUsageDescription`: "Any app that uses the local network, directly or indirectly, should include this description. This includes apps that use Bonjour ... as well as direct unicast or multicast connections to local hosts." — [NSLocalNetworkUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nslocalnetworkusagedescription)

### Inferences
- The current `localhost` exception is a per-domain `NSExceptionAllowsInsecureHTTPLoads`, so a Release build carrying it falls into the "requires justification" category. Review might ask about it, though "localhost" points only at the device itself. The cleanest fix is to set the ATS dictionary only in Debug, for example a Debug-only `INFOPLIST_FILE` or an `INFOPLIST_KEY`/preprocessed plist per configuration in `project.yml`. TestFlight and App Store builds then have no exception. The code-level `HubURL` guard stays.
- `NSAllowsLocalNetworking` is the better key only if the product should support plain HTTP to a hub on the LAN (`.local`, unqualified names, private IPs) from real devices. It needs no justification per Apple's list. It would still need `NSLocalNetworkUsageDescription`, and per the HubURL policy plain HTTP would then be allowed to LAN hosts. If the hub is always HTTPS, even on the LAN, neither ATS key is needed for Release. A hub reached by raw private IP over HTTPS is fine under ATS as long as its certificate validates, since ATS's IP-address default concerns local-networking loads. That nuance is not confirmed (see Gaps).
- `NSLocalNetworkUsageDescription` is needed for any real-device connection to a LAN hub, HTTPS or not, because Apple's wording covers "direct unicast ... connections to local hosts". A hub reached over the internet or Tailscale-style addressing does not need it. Simulator loopback to the Mac's localhost likely does not trigger the local network privacy prompt.

### Gaps
- Apple's docs do not say explicitly whether `localhost` counts as an "unqualified domain" under `NSAllowsLocalNetworking`, nor whether loopback triggers the local network permission prompt. No DTS forum answer was fetched.
- No Apple source quantifies how often a `localhost`-only insecure exception draws a review question. Treat the risk as possible, not certain.

## Upload: export options, altool/Transporter status, processing, common first-upload failures

### Takeaway
In Xcode 26.6 the export method is `app-store-connect` (`app-store` is deprecated). `destination: upload` sends the build directly from `xcodebuild -exportArchive`. Alternatively, export locally and upload with `xcrun altool --upload-package` (still shipped in Xcode 26.6, altool 26.40.1, with API-key auth) or Transporter. altool's retirement applied only to Mac notarization. iOS apps are not notarized, so `notarytool` has no iOS counterpart. Apple gives no fixed processing time; an email arrives when processing finishes.

### Cited Findings
- `method` options: "app-store-connect, release-testing, enterprise, debugging, developer-id, mac-application, and validation ... Additional options include app-store (deprecated: use app-store-connect), ad-hoc (deprecated: use release-testing), and development (deprecated: use debugging)." Source: local `xcodebuild -help`, Xcode 26.6.
- `destination`: "Determines whether the app is exported locally or uploaded to Apple. Options are export or upload. ... Defaults to export." Other relevant keys are `teamID`, `uploadSymbols` (default YES), `stripSwiftSymbols` (default YES), `manageAppVersionAndBuildNumber` (default YES), and `testFlightInternalTestingOnly`. Source: local `xcodebuild -help`, Xcode 26.6.
- altool in Xcode 26.6 (version 26.40.1) lists `--upload-package <file>` (with `--wait` for processing completion), `--upload-app -f <file>`, and `--validate-app`, with JWT auth via `--api-key` and `--api-issuer`. It looks for `AuthKey_<api_key>.p8` in `./private_keys`, `~/private_keys`, `~/.private_keys`, `~/.appstoreconnect/private_keys`, or `$API_PRIVATE_KEYS_DIR`. Source: local `xcrun altool --help`.
- Apple's upload page still names "Xcode, Swift Playground, altool, or Transporter", plus the App Store Connect API and Xcode Cloud, and shows `xcrun altool --upload-app` and `--validate-app` usage. After upload, "the build needs to be processed in Apple's system before it appears in App Store Connect. You'll receive an email when this process is complete." — [Upload builds](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds)
- altool's retirement covered only the notary service: "Starting November 1, 2023, the Apple notary service will no longer accept uploads from altool or Xcode 13 or earlier." That applied to notarizing Mac software. — [Upcoming requirements](https://developer.apple.com/news/upcoming-requirements/)
- Apps missing required-reason declarations "aren't accepted by App Store Connect" (since May 1, 2024). — [Describing use of required reason API](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api)

### Inferences
- A minimal ExportOptions.plist for the script contains `method=app-store-connect`, `destination=upload`, `teamID=GJJKL34HCT`, `signingStyle=automatic`, `uploadSymbols=true`, `testFlightInternalTestingOnly` (true for CI builds), and `manageAppVersionAndBuildNumber` (decide per the versioning note). The command is `xcodebuild -exportArchive -archivePath … -exportOptionsPlist … -exportPath … -allowProvisioningUpdates -authenticationKeyPath … -authenticationKeyID … -authenticationKeyIssuerID …`.
- `destination=upload` is one step. Export plus `altool --upload-package --wait` gives a local `.ipa` to keep and a blocking wait on processing. Either works.
- Most likely first-upload failures for this project: a missing app record for the bundle id (create it first); a missing privacy manifest or reasons (ITMS-91053) if any required-reason API is used; a missing export compliance key (not fatal, but it creates a questionnaire per build); build number reuse; signing failures if the API key role cannot create cloud certificates or profiles. The icon is already present.

### Gaps
- No Apple source was found that marks `altool --upload-app` as deprecated relative to `--upload-package`. Both appear in Xcode 26.6's help, and Apple's upload page still shows `--upload-app`.
- Typical processing durations come only from community anecdote; Apple publishes no figure.

## Keychain on iOS: access groups and capabilities

### Takeaway
A single app storing its device token in the keychain needs no `keychain-access-groups` entitlement and no capability. Every iOS keychain item is in the data-protection keychain, and the app's default access group is its application identifier (`GJJKL34HCT.com.cacheplane.b4app.ios`), which Xcode adds at signing time. Add Keychain Sharing only to share items with another app or extension.

### Cited Findings
- "Xcode automatically adds the `application-identifier` entitlement ... to every app during code signing, formed as the team identifier (team ID) plus the bundle identifier." The system treats this app ID as the app's default keychain access group, and "no other app can use it". "The app is always part of at least one group that contains only itself." — [Sharing access to keychain items among a collection of apps](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps)
- Access-group sharing "applies to all iOS keychain items, and to macOS keychain items when you query with the kSecUseDataProtectionKeychain key." — [Sharing access to keychain items among a collection of apps](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps)
- "If you don't specify any keychain access groups, then the app ID is the default." Using a group the app does not belong to fails with `errSecMissingEntitlement`, and that "includes attempts to 'prime' an entry using a zero-length string" for `kSecAttrAccessGroup`. — [Sharing access to keychain items among a collection of apps](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps)
- "To add this entitlement [keychain-access-groups] to your app, enable the Keychain Sharing capability in Xcode." — [Keychain Access Groups entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/keychain-access-groups)

### Inferences
- `WorkspaceSecrets` should omit `kSecAttrAccessGroup` on iOS, or pass the full `TEAMID.bundleid` string, and never an empty string. On macOS, `kSecUseDataProtectionKeychain: true` makes the Mac app behave the same way, under its own `com.apple.application-identifier`.
- If an extension is added later (widget or notification service extension reading the device token), add Keychain Sharing or an App Group then. That changes the App ID's capabilities, and automatic signing with `-allowProvisioningUpdates` regenerates the profile.
- Keychain items survive app deletion and reinstall in some cases. This did not come up in the sources and may matter for hub re-enrollment logic, but it is outside TestFlight requirements.

### Gaps
- No Apple source was found on whether TestFlight and App Store builds (distribution-signed) and Debug builds (development-signed) share keychain items on the same device. They share the same application identifier, so they likely do, but this was not confirmed.
