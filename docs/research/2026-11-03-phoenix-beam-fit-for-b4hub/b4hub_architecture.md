## 1. What are the hub's responsibilities?

### Takeaway
b4hub is a multi-tenant Rust HTTP + WebSocket service in front of PostgreSQL that does six jobs: change-log sync (push, long-poll pull, snapshot, pruning), a WebSocket relay between a user's Mac and phone (commands, replies, presence, watched-thread live events), device enrollment and QR pairing, accounts and sign-in (passkeys/WebAuthn, Sign in with Apple, account routes with step-up), APNs push notifications with an at-most-once ledger, withdrawal, and an SQL-computed badge, and operability (maintenance mode, request ids, readiness probe, instance heartbeats). Almost all durable state is in PostgreSQL; only relay routing state, rate limits, and the long-poll wakeup are in process memory.

### Cited Findings
- Origin and mandate: the owner's words in the M8 design include "The hub is a multi-tenant onprem solution that is deployable using docker, k8n via helm charts. We will support SSO and enterprise auth." and "The backend should be written in rust." — [docs/superpowers/specs/2026-10-31-m8-hub-design.md:12-17](docs/superpowers/specs/2026-10-31-m8-hub-design.md)
- Roadmap purpose: "A Rust hub service that every device syncs with as a user: multi-tenant from the first migration (shared schema, forced row-level security), deployable on-prem with Docker Compose and Helm and as cacheplane's public cloud from one image, owning its own users, organisations, devices, and credentials with no bundled identity provider." — [docs/roadmaps/Personal_Agent_Workspace_Technical_Spec_and_Roadmap.md:654](docs/roadmaps/Personal_Agent_Workspace_Technical_Spec_and_Roadmap.md)
- Full HTTP surface (one axum router): `/healthz`, `/readyz`, `/v1/enroll`, `/v1/pairing-codes`, `/v1/changes` (push and pull), `/v1/snapshot`, `/v1/devices`, `/v1/devices/self` (revoke), `/v1/devices/self/link` (the relay WebSocket), `/v1/devices/self/push-token`, `/v1/auth/config`, `/v1/auth/passkey/{begin,finish}`, `/v1/auth/apple/{begin,native,start,callback}`, `/v1/auth/handoff`, `/v1/me` (get, delete), `/v1/me/profile`, `/v1/me/passkeys/{begin,finish}`, `/v1/me/apple{,/native,/handoff}`, `/v1/me/identities/{id}`, `/v1/me/step-up/...`, `/v1/sessions/self` — [Hub/crates/b4hub/src/serve.rs:151-185](Hub/crates/b4hub/src/serve.rs)
- **Sync (change log).** One shared schema, `org_id` on every tenant table, RLS forced with `org_id = NULLIF(current_setting('b4hub.org_id', true), '')::uuid`, set per request transaction via `set_config`; `(org_id, device_id, device_seq)` unique for idempotent pushes; per-org `hub_seq` bigserial cursor; per-org advisory lock so commit order equals sequence order; limits 2 MiB per value, 32 MiB per push body, 1000 changes per push/pull page; long-poll `wait` capped at 25 s with the waiter registered before the final emptiness check — [docs/decisions.md:368 (D-043)](docs/decisions.md)
- Pull pages cut at 1000 changes or 8 MiB of stored value bytes; pruning every 24 h (`B4HUB_RETENTION_DAYS`, default 30) under the same per-org advisory lock; a cursor below the horizon gets `410 resync_required` and the client restores from `GET /v1/snapshot` (one `REPEATABLE READ` transaction, not paged) — [docs/decisions.md:355 (D-050)](docs/decisions.md)
- Conflict handling: per-column hybrid logical clocks (last-writer-wins per column), the phone may write a short allowlist of columns, enforced on the hub and the Mac; a refused change is answered in `rejected` without stalling the queue — [docs/decisions.md:356 (D-049)](docs/decisions.md)
- The long-poll wakeup is an in-process `tokio::sync::Notify` per org; its own comment says "the hub runs a single replica in M8a, so an in-process signal is enough (a second replica would need `LISTEN` / `NOTIFY` or the same signal over the database)" — [Hub/crates/b4hub/src/notify.rs:1-3](Hub/crates/b4hub/src/notify.rs); push calls `state.notifier.wake(device.org_id)` after commit, and the pull waits on `notified` / `sleep(wait)` / shutdown — [Hub/crates/b4hub/src/routes/changes.rs:23, 57-59, 141-153](Hub/crates/b4hub/src/routes/changes.rs)
- **Relay.** "The relay is one WebSocket per joined device, and it carries commands, replies, presence, and live progress, never state"; heartbeat 10 s, dead after 30 s silent; "The change log stays the only source of truth: nothing from the relay is written to the mirror, so the relay needs no cursor and a lost frame costs only a moment of streaming" — [docs/decisions.md:296-299 (D-054)](docs/decisions.md)
- Relayed commands are never stored, carry a hub-stamped 10 s deadline the Mac enforces, and are idempotent by phone-minted ids; interrupts and answers are held up to 60 s for an owner seen recently, sends never are — [docs/decisions.md:302-307 (D-055)](docs/decisions.md)
- Only five methods are relayed (`turn.send`, `turn.interrupt`, `request.respond`, `thread.start`, `turn.lookup`), only from `ios`/`cli` clients to a non-revoked `macos` device of the same user; limits in memory: 60 commands/min per device, 20 sends/min per user, 4 watched threads per phone, 64 KiB client frames, 256 KiB host frames — [docs/decisions.md:313-317 (D-057)](docs/decisions.md)
- Catch-up is the Mac's job, not the hub's: for every active turn the Mac sends the whole text so far (`payload.catchUp: true`) then live events, on one ordered queue — [Sources/Coordinator/HubSync/HubLink.swift:78-83](Sources/Coordinator/HubSync/HubLink.swift). The hub forwards only ten event kinds (`turn.*`, `message.started|delta|completed`, `tool.*`, `runtime_request.*`) — [Hub/crates/b4hub-core/src/relay.rs:42-53](Hub/crates/b4hub-core/src/relay.rs)
- **Pairing.** `POST /v1/pairing-codes`: a joined Mac mints a five-minute, single-use code (10 an hour), redeemed at `/v1/enroll` — [Hub/crates/b4hub/src/routes/pairing.rs:1-30](Hub/crates/b4hub/src/routes/pairing.rs); [docs/decisions.md:321-326 (D-058)](docs/decisions.md). Pairing links became `https://<site>/pair#c=<code>` universal links — [docs/decisions.md:265 (D-066)](docs/decisions.md)
- **Accounts and sign-in.** Accounts are created by Apple ID or passkey, each with a private org; the hub verifies both itself — [docs/decisions.md:261 (D-064)](docs/decisions.md). Passkeys use `webauthn-rs =0.6.2`; Apple tokens are verified with `jsonwebtoken =11.1.0` (RS256 and ES256 accepted, D-090) — [Hub/Cargo.toml:20, 38-39](Hub/Cargo.toml); [docs/decisions.md:236 (D-090)](docs/decisions.md). Adding/removing a sign-in method or deleting the account needs a step-up assertion within two minutes (D-150) — [docs/decisions.md:9](docs/decisions.md). Sign-in ceremonies and handoffs live in PostgreSQL, "so sign-in itself is already replica-safe; only the relay and the in-memory per-IP rate limits are per process" — [docs/deployment-architecture.md:52](docs/deployment-architecture.md)
- **Push notifications.** Detection runs inside the push transaction under the org's push lock and records `(org, kind, row id)` in `notifications_sent` (at most once) — [docs/decisions.md:57-61 (D-121)](docs/decisions.md); [Hub/crates/b4hub-db/src/push.rs:1-12](Hub/crates/b4hub-db/src/push.rs). Every notification has a key `request:<id>` or `turn:<id>` and carries the badge (D-142); a notification is withdrawn once when what it announced is over (`notifications_sent.withdrawn_at`, D-143); the badge is computed in SQL on every alert (D-144) — [docs/decisions.md:22-24](docs/decisions.md); [Hub/crates/b4hub-db/src/push.rs:236, 401](Hub/crates/b4hub-db/src/push.rs). Sending happens after commit on a separate task; senders are `SpoolSender` (Simulator files) and `ApnsSender` (HTTP/2 via `reqwest`, cached ES256 provider token reused 50 min) — [Hub/crates/b4hub/src/push.rs:1-9](Hub/crates/b4hub/src/push.rs); [docs/decisions.md:21 (D-141)](docs/decisions.md); [Hub/crates/b4hub/src/routes/changes.rs:60-70](Hub/crates/b4hub/src/routes/changes.rs)
- **Operability.** A hub-minted UUIDv7 request id per request in a tracing span, JSON logs when not a TTY (D-073); maintenance mode is a row in `hub_settings` polled by every instance every 5 s, refusing writes with `503 maintenance` (D-074) — [docs/decisions.md:229-230](docs/decisions.md)

### Inferences
- The hub's durable responsibilities (sync, accounts, notifications, pairing codes) are request/response over PostgreSQL with transactional correctness (RLS, advisory locks, at-most-once ledger in the same transaction). These do not depend on the runtime's concurrency model; a Phoenix port would reimplement them with Ecto/Postgrex and gain little or nothing intrinsic.
- The parts that are long-lived, stateful, and concurrent are the relay (one socket task per device, bounded mailboxes, holds with timers, in-flight maps) and the long-poll wakeup. Those are the parts where BEAM primitives (processes, `Registry`, `Phoenix.PubSub`, `Phoenix.Presence`) map most directly.

### Gaps
- I did not read every route handler; the list of responsibilities is from the router, AGENTS.md, decisions, and module headers.

## 3. The relay in detail: in-memory state, routing, and what M8e did and still requires

### Takeaway
The relay is a hand-built actor system: one tokio task per WebSocket, a bounded `mpsc` (256 frames) per link as its mailbox, a `Mutex<HashMap>` registry of links keyed by device, watcher maps, an in-flight command map of `oneshot` reply channels, a held-command counter with timers, and in-memory sliding-window rate limits. M8e Part B (implemented, D-085/D-086) made it multi-instance **without any inter-instance message bus**: a per-user claim row in PostgreSQL (`user_links`) with instance heartbeats (`hub_instances`), a `409 relocated` refusal at upgrade time, and ALB application-cookie stickiness. The design explicitly rejected forwarding frames between instances, naming Phoenix PubSub with a PG adapter as an example of designs that "pay for a broker". Hosted production still runs one task.

### Cited Findings
**In-memory state (per instance)**
- Module overview: "`registry` holds the live links and the presence they imply, `link` is the endpoint and the task that serves one link, `route` takes a client's command to the Mac that owns its target and the reply back, and `limits` holds the in-memory rate limits" — [Hub/crates/b4hub/src/relay/mod.rs:1-5](Hub/crates/b4hub/src/relay/mod.rs)
- `LinkHandle` = device id, name, generation, role, user id, org id, an `mpsc::Sender<RelayMessage>`, and an `Arc<Mutex<Missed>>` — [Hub/crates/b4hub/src/relay/registry.rs:108-120](Hub/crates/b4hub/src/relay/registry.rs)
- `Missed`: a client whose queue is full loses events but keeps "the latest `presence`, and the threads whose events were dropped (which each want one `stream_gap`)" — [Hub/crates/b4hub/src/relay/registry.rs:174-183](Hub/crates/b4hub/src/relay/registry.rs)
- `Watchers`: `by_host: HashMap<host, HashMap<thread, HashSet<client>>>` and `by_client: HashMap<client, HashMap<thread, host>>` — [Hub/crates/b4hub/src/relay/registry.rs:214-222](Hub/crates/b4hub/src/relay/registry.rs)
- `Inner` of `Relay`: `links: Mutex<HashMap<Uuid, Entry>>`, generation counter, min client protocol, wall clock, upgrade `SlidingWindow`, `watch` channels for live/registered counts, `commands: Commands`, `watchers: Mutex<Watchers>`, `watch_epoch` — [Hub/crates/b4hub/src/relay/registry.rs:331-347](Hub/crates/b4hub/src/relay/registry.rs)
- `register` creates `mpsc::channel(LINK_QUEUE)` and a `oneshot` close channel, inserts into `links`, and tells any older link of the same device to close (`Close::replaced()`) — [Hub/crates/b4hub/src/relay/registry.rs:389-443](Hub/crates/b4hub/src/relay/registry.rs)
- `fan_out` looks up watching clients and calls `deliver_event` on each handle (drop and mark a gap when full) — [Hub/crates/b4hub/src/relay/registry.rs:669-686](Hub/crates/b4hub/src/relay/registry.rs)
- `Commands`: `in_flight: Mutex<HashMap<(Uuid, String), InFlight>>` (reply `oneshot`s), `pending_threads: Mutex<HashMap<(Uuid, String), PendingThread>>`, `held: Mutex<HashMap<Uuid, usize>>` — [Hub/crates/b4hub/src/relay/route.rs:84-102](Hub/crates/b4hub/src/relay/route.rs)
- Constants: heartbeat 10 s, dead link 30 s, command deadline 10 s, reply wait 30 s (start) / 15 s (other), hold window 60 s, pending-thread TTL 300 s, client frame 64 KiB, host frame 256 KiB, 4 watches, 32 held per host, link queue 256 — [Hub/crates/b4hub-core/src/relay.rs:17-40](Hub/crates/b4hub-core/src/relay.rs); `QUEUE_WAIT` 5 s — [Hub/crates/b4hub/src/relay/route.rs:52-54](Hub/crates/b4hub/src/relay/route.rs)
- Rate limits are "in memory, per hub process (a restart forgets them, which only ever lets one extra burst through)": 10 upgrades/min per device, 60 commands/min per device with burst 20, 20 starts/min per user — [Hub/crates/b4hub/src/relay/limits.rs:1-26](Hub/crates/b4hub/src/relay/limits.rs)
- Close codes: 1001 shutdown, 4000 replaced, 4001 revoked, 4002 client too old, 4003 silent — [Hub/crates/b4hub/src/relay/mod.rs:35-48](Hub/crates/b4hub/src/relay/mod.rs)

**Routing**
- Per command, in order: role and method allowlist; in-flight check; rate limits; lookup of thread/request/project in the caller's org and user (pending-thread map first); owner must be a non-revoked `macos` device of the same user or `not_found`; `stale_runtime_request` check; deliver with `deadline` and `from` stamped, or hold `turn.interrupt`/`request.respond` for an owner heard from within 60 s, else `device_offline`; wait for the reply or `relay_timeout`. "Nothing here is stored; a hub restart forgets it all" — [Hub/crates/b4hub/src/relay/route.rs:1-28](Hub/crates/b4hub/src/relay/route.rs)
- Ownership lookups hit PostgreSQL (`owner_device`, `owner_of_project`, `owner_of_request`, `owner_of_thread`) — [Hub/crates/b4hub/src/relay/route.rs:40](Hub/crates/b4hub/src/relay/route.rs); presence reads host devices from the DB and `online` from the in-memory registry — [Hub/crates/b4hub/src/relay/registry.rs:565-600](Hub/crates/b4hub/src/relay/registry.rs)
- D-076: "Nothing here is state, so every rule fails toward 'the phone asks again', which the change log and `turn.lookup` make safe" — [docs/decisions.md:196-200](docs/decisions.md)

**M8e Part B (implemented): multi-instance by user affinity**
- Design constraints recorded before building: "a `NOTIFY` payload is at most 8000 bytes while frames reach 256 KiB; `message.delta` is tens of frames a second and is never stored; commands carry a 10 s hub-clock deadline; in-flight deduplication is keyed by `(caller device, command id)` and must stay on one instance; presence and 'one link per device' must hold across instances" — [docs/superpowers/specs/2026-11-02-m8e-part-b-relay-routing-design.md:9](docs/superpowers/specs/2026-11-02-m8e-part-b-relay-routing-design.md)
- Why not forward frames: "it would need an internal transport for 256 KiB frames and high-rate deltas (a second listener per task with service discovery), it would split the in-flight map, and every design in the research that did this (Phoenix PubSub with PG adapter, Soketi horizontal mode) pays for a broker. Routing by user keeps the M8c code intact and matches what the owner's 'next' tier buys: zero-downtime deploys and zone redundancy, not a bigger relay." — [docs/superpowers/specs/2026-11-02-m8e-part-b-relay-routing-design.md:15](docs/superpowers/specs/2026-11-02-m8e-part-b-relay-routing-design.md)
- D-085 claim: each `serve` registers a UUIDv7 in `hub_instances`, heartbeats every `B4HUB_HEARTBEAT_MS` (default 5000), dead after four heartbeats (20 s); `user_links` names the serving instance; the upgrade claims the user with one upsert after the revocation check and before the socket; another live owner means `409 relocated` — [docs/decisions.md:158-159](docs/decisions.md)
- D-085 cookie: ALB application-cookie stickiness on `b4hub-instance` (on only when `task_count > 1`); the `409` carries no cookie; the device replays the cookies of its last successful upgrade, drops them on `409`, retries at once up to three times, then backs off — [docs/decisions.md:160](docs/decisions.md)
- D-085 drain, rolling deploys, split guard: SIGTERM → answer held commands `device_offline` → close links 1001 → delete claims and instance row, all within `B4HUB_SHUTDOWN_WAIT_MS`; `deregistration_delay` 5 s with >1 task; an instance whose heartbeat recovers closes links of users another instance took — [docs/decisions.md:161-163](docs/decisions.md)
- D-085 accepted edges: "per-instance rate limits, in-flight state, holds lost on a crash, and the pending-thread map (a takeover between a phone's `thread.start` and the thread row's sync answers `not_found` for seconds)" — [docs/decisions.md:165](docs/decisions.md)
- D-086: `/readyz` runs the real link task over an in-memory socket pair as a probe identity, never registered, and reports `"instances": "stale"` + 503 when the heartbeat is older than the window — [docs/decisions.md:167-170](docs/decisions.md)
- Schema: `hub_instances (instance_id, started_at, heartbeat_at, public_url)` and `user_links (user_id PK, instance_id, claimed_at)`, hub-internal, no RLS — [Hub/crates/b4hub-db/migrations/0008_instances.sql:1-29](Hub/crates/b4hub-db/migrations/0008_instances.sql)
- DB functions: `register`, `heartbeat`, `claim_user` (`INSERT ... ON CONFLICT (user_id) DO UPDATE ...`), `owner_of`, `lost_claims`, `release_claims`, `prune` — [Hub/crates/b4hub-db/src/instances.rs:30-172](Hub/crates/b4hub-db/src/instances.rs); instance state and heartbeat loop — [Hub/crates/b4hub/src/instances.rs:1-35](Hub/crates/b4hub/src/instances.rs); heartbeat task spawned in `serve` — [Hub/crates/b4hub/src/serve.rs:224](Hub/crates/b4hub/src/serve.rs)
- Wire reference "More than one instance": "Every link of one user (all of that user's Macs and phones) is served by **one instance at a time**, so commands, replies, watches, events, holds, and presence never cross instances; no frame is ever forwarded between instances." — [Hub/API.md:1253-1285](Hub/API.md)
- Part B explicitly left change-log sync alone: "No change to the change-log sync (HTTP push/pull is stateless and works on any instance already)" — [docs/superpowers/specs/2026-11-02-m8e-part-b-relay-routing-design.md:53](docs/superpowers/specs/2026-11-02-m8e-part-b-relay-routing-design.md)

**What the roadmap's "M8e" still contains (planned)**
- Roadmap: "M8e Deployable: Helm chart with a migration hook and external Postgres, SAML, SCIM, tenant bundle export and import, a published client compatibility window." — [docs/roadmaps/Personal_Agent_Workspace_Technical_Spec_and_Roadmap.md:660](docs/roadmaps/Personal_Agent_Workspace_Technical_Spec_and_Roadmap.md); milestones list it as unchecked, with the hosted hubs, Compose, and Helm built by the deployment project — [docs/milestones.md:318](docs/milestones.md)
- Remaining non-goals for the relay: "Remote B4 threads started from the phone; queuing turns for an offline Mac; several Macs per user; cross-instance routing. `open` by design" — [docs/milestones.md:216](docs/milestones.md)

### Inferences
- **Where BEAM would help.** The relay's state is a set of per-device mailboxes, a device registry with "newest link wins", per-user presence, topic-like watch subscriptions, request/reply correlation with timeouts, and bounded queues with drop-and-mark-gap. In Phoenix these are idiomatic: one Channel process per socket, `Registry` or `:pg` for device lookup, `Phoenix.PubSub` topics per thread for fan-out, `Phoenix.Presence` (CRDT) for cluster-wide presence, `GenServer.call` with timeouts or `Process.send_after` for holds and deadlines. Much of the 1,064-line `registry.rs` and 753-line `route.rs` is hand-written equivalents of those primitives.
- **Distributed Erlang would remove the reason for user affinity.** With a BEAM cluster, `Phoenix.PubSub` (PG2/`:pg` adapter, no external broker) forwards messages between nodes directly, so a phone and its Mac could sit on different nodes; the claim table, `409 relocated`, the ALB cookie dance, the split guard, and the 5 s deregistration trick (D-085) would be unnecessary. But it adds node discovery on Fargate (libcluster with DNS or ECS strategies), open distribution ports between tasks in the security group, a shared cookie secret, and netsplit semantics; Part B's design judged any cross-instance transport not worth it at this scale.
- **Where BEAM would not help much.** The durable parts (RLS-scoped sync with advisory locks, the notification ledger in the same transaction, WebAuthn, Apple, APNs) are PostgreSQL-bound; a runtime change does not simplify them, and in Elixir the WebAuthn and Apple libraries would be different dependencies to evaluate.
- **The one unsolved multi-instance gap is the long-poll wakeup, not the relay.** `Notifier` is in-process ([Hub/crates/b4hub/src/notify.rs:1-3](Hub/crates/b4hub/src/notify.rs)). With two tasks, a Mac's push landing on task A wakes only pulls waiting on task A; a phone pull waiting on task B returns at its timeout (capped at 25 s, [Hub/crates/b4hub/src/routes/changes.rs:23](Hub/crates/b4hub/src/routes/changes.rs)). Whether this happens in practice depends on whether the clients' HTTP requests carry the same ALB stickiness cookies as the link (see Gaps). A Phoenix cluster would solve this with a PubSub broadcast; in Rust the documented option is `LISTEN/NOTIFY` on a dedicated connection.

### Gaps
- I could not confirm whether the phone's or Mac's plain HTTP requests (`HTTPHubAPI`) share the ALB `AWSALBAPP-*` cookies with the WebSocket upgrade; `Sources/WorkspaceSync/HTTPHubAPI.swift` has no explicit cookie or `URLSessionConfiguration` handling (grep found none), and URLSession's default cookie storage behaviour across sessions was not traced. So the long-poll wake gap with two tasks is an inference, not a tested finding; no doc mentions it.
- No load figures (connections, frames per second, messages per user) exist in the repo beyond design statements like "`message.delta` is tens of frames a second".

## 4. Wire protocol and how tightly the Swift clients are coupled

### Takeaway
The wire is plain HTTP+JSON plus one WebSocket carrying JSON frames tagged by `type`, documented in `Hub/API.md` and pinned by shared JSON fixtures that both the Rust and Swift test suites decode. The Swift clients are coupled to the *protocol* (frame shapes, close codes, the `409 relocated` and cookie rules, the `B4-Protocol` header), not to Rust. A Phoenix server could serve the same protocol, but it would have to use raw WebSockets (not Phoenix Channels' own join/topic/ref envelope) to keep the clients unchanged.

### Cited Findings
- Frames in protocol 1: `hello`, `ping`/`pong`, `presence`, `watch`/`unwatch`, `watching`, `event` (host to hub and hub to client), `stream_gap`, plus `command`, `reply`, `error` — [Hub/API.md:1287-1300](Hub/API.md); protocol constants `PROTOCOL = 1`, `MIN_CLIENT_PROTOCOL = 1` — [Hub/crates/b4hub/src/relay/mod.rs:30-33](Hub/crates/b4hub/src/relay/mod.rs)
- Link details: `B4-Protocol` header (missing = 1), 1 MiB socket cap, 64 KiB/256 KiB per-role caps refused with an `invalid_request` frame, close codes 4000-4003 — [docs/decisions.md:189-194 (D-075)](docs/decisions.md); `WIRE_MAX`, `CLOSE_GRACE`, `PROBE_WAIT` — [Hub/crates/b4hub/src/relay/link.rs:43-59](Hub/crates/b4hub/src/relay/link.rs)
- Error envelope `{"error": {"kind", "message", "details": {"code", ...}}}`, including `409 relocated` with `details.instanceId` — [Hub/API.md:73, 1267](Hub/API.md); envelope shared with b4 "so the Swift client decodes both services with one type" — [docs/superpowers/specs/2026-10-31-m8-hub-design.md:142](docs/superpowers/specs/2026-10-31-m8-hub-design.md)
- Shared contracts "both languages decode; edit one only when both suites are updated": `Tests/Fixtures/sync/changes.json`, `relay.json`, `auth.json`, `push.json` (AGENTS.md) — [AGENTS.md:31](AGENTS.md); also `attention.json` (badge/band rules, read by Swift Postgres and SQLite queries and the hub's SQL) and `conflicts.json` (merge rules) — [Tests/WorkspaceStorageTests/ActivityQueryTests.swift:7](Tests/WorkspaceStorageTests/ActivityQueryTests.swift); [Tests/WorkspaceStorageTests/RemoteApplyTests.swift:556](Tests/WorkspaceStorageTests/RemoteApplyTests.swift). Sizes: relay 155, changes 253, auth 279, push 759, attention 522, conflicts 135 lines — computed (`wc -l`)
- Swift `RelayWire.swift` hand-writes the frame types (`RelayMethod`, `RelayRole`, `RelayHostPresence`, `RelayFrom`, ...) and states that `relay.json` "is decoded and re-encoded by both" — [Sources/WorkspaceSync/RelayWire.swift:1-40, 78](Sources/WorkspaceSync/RelayWire.swift)
- `HubLinkConnection` is a protocol seam (`URLSessionHubLinkConnection` in production, a fake in tests) whose `HubLinkSocket` exposes `send`, `receive`, `close(code:)`, and `responseCookies` (the `b4hub-instance` and `AWSALBAPP-*` cookies) — [Sources/WorkspaceSync/HubLinkConnection.swift:1-60](Sources/WorkspaceSync/HubLinkConnection.swift)
- `RelayLink` encodes the multi-instance client rule: keep the last successful upgrade's cookies, drop on `409`, three immediate retries; it does not read `instanceId` because "`URLSessionWebSocketTask` exposes a refused upgrade's status but not its body" — [Sources/WorkspaceSync/RelayLink.swift:24-38, 73-75, 219-224](Sources/WorkspaceSync/RelayLink.swift)
- Swift sync/relay client sizes: `RelayWire.swift` 253, `RelayLink.swift` 387, `HubLinkConnection.swift` 485, `Wire.swift` 482, `AuthWire.swift` 408, `HTTPHubAPI.swift` 313; Mac side `HubLink.swift` 379, `RelayExecutor.swift` 329, `HubSync.swift` 627; phone `MirrorRelay.swift` 331 — computed (`wc -l`)
- Owner policy: there are no users besides the owner, so breaking changes are fine with no shims for old hubs or builds — [user memory, no-backwards-compat-yet (2026-11-02), as summarised in the session's MEMORY.md]

### Inferences
- A Phoenix replacement could keep the clients unchanged only by implementing the existing JSON frames over a raw WebSocket (e.g. `WebSock`/`Bandit` directly rather than `Phoenix.Socket`/Channels, whose wire envelope is `[join_ref, ref, topic, event, payload]`). Adopting Channels' protocol would mean rewriting `RelayLink`, `MirrorRelay`, and `HubLink` on the Swift side (or adopting a Swift Phoenix client).
- The fixtures make the contract language-neutral: an Elixir suite could decode the same JSON files, so the "both suites" rule would extend to a third language rather than break.
- The `409 relocated` cookie rule would become unnecessary with a clustered BEAM relay, which would simplify `RelayLink`.

### Gaps
- I did not diff the full `Hub/API.md` frame table against `RelayWire.swift` field by field.

## 7. Why Rust, and every mention of Elixir/Phoenix/Erlang/BEAM, Redis, NATS, LISTEN/NOTIFY, clustering

### Cited Findings
