# Phoenix and the BEAM for realtime WebSocket relays and multi-node fan-out (as of November 2026)

Context for the reader: b4hub's relay today is a Rust (axum) service. Devices open `GET /v1/devices/self/link` (Bearer token checked before the upgrade, custom `B4-Protocol` header, custom HTTP refusals `401/409 relocated/429/503`, a `Set-Cookie: b4hub-instance=...` on the `101`), then exchange JSON text frames with a `type` discriminator (`hello`, `ping`/`pong`, `presence`, `command`/`reply`/`event`, `watch`/`unwatch`, `error`), use close code 4000 for `link_replaced`, and pin every link of one user to a single instance via a Postgres heartbeat claim plus ALB application-cookie stickiness, so no frame is ever forwarded between instances (from the repo's `Hub/API.md`, "Opening a link", "More than one instance", "Frames in this version"). The notes below are read against that shape.

## 1. Phoenix Channels / Phoenix.Socket protocol, and serving an existing custom WebSocket protocol unchanged

### Takeaway
Phoenix Channels define their own envelope (V2 JSON: `[join_ref, ref, topic, event, payload]` arrays, a `phoenix` topic heartbeat, `phx_join`/`phx_reply`, client-driven rejoin with backoff) and give at-most-once delivery with no persistence. They cannot carry b4hub's `type`-tagged frames unchanged. Phoenix does have a supported layer below Channels: `Phoenix.Socket.Transport` and the WebSock/WebSockAdapter behaviour (Plug-level upgrade). On that layer you can implement an arbitrary JSON-over-WebSocket protocol, so the existing wire contract (`relay.json`) can be kept byte-for-byte.

### Cited Findings
- Current Phoenix on hexdocs is **v1.8.16** (shown on the `Phoenix.Socket.Transport` page header). — [Phoenix.Socket.Transport docs](https://phoenix.hexdocs.pm/Phoenix.Socket.Transport.html)
- Phoenix 1.8.0 requires Erlang/OTP 25+. 1.8.6 (2026-05-05) fixed CVE-2026-32689, a memory exhaustion in the LongPoll transport, and generated apps moved to LiveView 1.1. 1.8.9 (2026-07-07) masks the `token` param in logs by default and fixes "LongPoll being active by default since 1.8.0". 1.8.10 (2026-08-10) fixed "endpoint websocket options" and phoenix.js. (From hex.pm/GitHub changelog fragments as summarised by search; I did not read the full changelog for 1.8.11–1.8.16.) — [Phoenix CHANGELOG 1.8.12 on hex](https://hex.pm/packages/phoenix/1.8.12/files/CHANGELOG.md); [GitHub CHANGELOG v1.8.8](https://github.com/phoenixframework/phoenix/blob/v1.8.8/CHANGELOG.md)
- **V2 JSON wire format** (`Phoenix.Socket.V2.JSONSerializer`): outbound push is `[join_ref, ref, topic, event, payload]`. Replies use event `"phx_reply"` with payload `%{status, response}`. Fastlane broadcasts are `[nil, nil, topic, event, payload]`. Decoding reads the first five positional elements and ignores extras. — [v2_json_serializer.ex (main)](https://raw.githubusercontent.com/phoenixframework/phoenix/main/lib/phoenix/socket/serializers/v2_json_serializer.ex)
- V2 also has a **binary frame** encoding: first byte is the kind (0 push, 1 reply, 2 broadcast), and each of join_ref/ref/topic/event/status has a one-byte length prefix, so those fields are capped at 255 bytes. Server-to-client pushes omit `ref`; client-to-server pushes carry it. Only push is decoded inbound. — [v2_json_serializer.ex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/lib/phoenix/socket/serializers/v2_json_serializer.ex)
- **Heartbeat:** the server treats `"heartbeat"` events on the `"phoenix"` topic as a request that "should just emit an OK reply". — [Phoenix.Socket docs](https://phoenix.hexdocs.pm/Phoenix.Socket.html)
- **phoenix.js client defaults** (main branch): `heartbeatIntervalMs` 30000. `reconnectAfterMs` steps through 10, 50, 100, 150, 200, 250, 500, 1000, 2000 ms, then 5000 ms. `rejoinAfterMs` steps through 1000, 2000, 5000 ms, then 10000 ms. A missed heartbeat reply within the interval makes the client log "heartbeat timeout", close with a normal close code, error the channels with `heartbeat_timeout`, and reconnect. `binaryType` defaults to `"arraybuffer"`. Custom `encode`/`decode` functions can be passed but are ignored for LongPoll. LongPoll fallback (`longPollFallbackMs`) is disabled by default. — [phoenix/assets/js/phoenix/socket.js](https://raw.githubusercontent.com/phoenixframework/phoenix/main/assets/js/phoenix/socket.js)
- **Topics** are strings, conventionally `"topic:subtopic"` (e.g. `"users:123"`). Routes support wildcards (`channel "room:*", RoomChannel`). Authorization happens in `join/3`, which returns `{:ok, socket}` or `{:error, %{reason: ...}}`. — [Phoenix Channels guide](https://phoenix.hexdocs.pm/channels.html)
- **Delivery guarantees:** "Phoenix uses an at-most-once strategy when sending messages to clients" and "Phoenix doesn't persist messages on the server." Client-to-server pushes are buffered in a `PushBuffer` while disconnected, with a default 5000 ms timeout, and are not saved to local storage. — [Phoenix Channels guide](https://phoenix.hexdocs.pm/channels.html)
- **Reconnect/replay:** after a crash, "clients will attempt to reconnect to the server using an exponential backoff strategy" and "attempt to rejoin the topics they had previously subscribed to". There is no built-in replay. The guide suggests passing a `last_seen_id` in join params and having `join/3` fetch missed messages. — [Phoenix Channels guide](https://phoenix.hexdocs.pm/channels.html)
- **Process model:** each socket has a transport process (`transport_pid`). "each channel is spawned under a supervisor", with `:partitions` supervisors (default: number of cores). Channels should monitor `transport_pid`. `socket.id` (e.g. `"users_socket:#{user_id}"`) lets you broadcast `"disconnect"` to kill all of a user's sockets. GC can be forced via `send(socket.transport_pid, :garbage_collect)`, and there is a websocket `:fullsweep_after` option. — [Phoenix.Socket docs](https://phoenix.hexdocs.pm/Phoenix.Socket.html)
- **`Phoenix.Socket.Transport`** is the behaviour that "Outlines the Socket <-> Transport communication". `Phoenix.Socket` (Channels) is just one implementation, and a custom socket can implement it directly and skip Channels. Callbacks: `child_spec/1` (once per socket), `connect/1` (authorize from a map with endpoint/transport/params/options and return `{:ok, state}` or `{:error, reason}`), `init/1` (runs in the process that operates the socket), `handle_in/2` (`{:ok, s}`, `{:reply, status, {opcode, msg}, s}`, `{:stop, reason, s}`), `handle_info/2` (`{:push, {opcode, msg}, s}`, ...), optional `handle_control/2` for ping/pong ("Control frames are only supported when using websockets"), `terminate/2`, and optional `drainer_spec/1` for shutdown draining. The doc includes a raw `EchoSocket` example mounted with `socket "/socket", EchoSocket, websocket: true, longpoll: true`, served at `/socket/websocket`. — [Phoenix.Socket.Transport docs](https://phoenix.hexdocs.pm/Phoenix.Socket.Transport.html)
- Transport helpers: `check_origin` (403 on mismatch), `check_subprotocols` (checks `sec-websocket-protocol`, 403 on mismatch), and `connect_info` (exposes `:peer_data`, `:uri`, `:user_agent`, `:session` and other transport-specific keys, configured via the `:connect_info` option). — [Phoenix.Socket.Transport docs](https://phoenix.hexdocs.pm/Phoenix.Socket.Transport.html)
- An `error_handler` can be set in the websocket config to control the HTTP response when a connection is denied. — [Phoenix.Socket docs](https://phoenix.hexdocs.pm/Phoenix.Socket.html)
- **WebSockAdapter v0.7.0**: `WebSockAdapter.upgrade/4` "returns the passed `conn` set to an `:upgraded` state". It validates the upgrade early by default (`early_validate_upgrade`) and passes `state` to `WebSock.init/1` once the socket is negotiated. Options: `timeout` (default 60_000 ms idle), `compress` (default false), `max_frame_size` (default 10_000_000 octets), `fullsweep_after`, `max_heap_size`, `validate_utf8`, `active_n` (Cowboy only), and `deflate_options`. — [WebSockAdapter docs](https://websock-adapter.hexdocs.pm/WebSockAdapter.html)

### Inferences
- **Can Phoenix serve b4hub's protocol unchanged? Yes, but not through Channels.** Two viable shapes:
  1. **Plug route plus `WebSockAdapter.upgrade/4`** (a `WebSock` handler). The request is an ordinary `Plug.Conn` until the upgrade call, so the router/controller can authenticate the Bearer token, read `B4-Protocol`, rate-limit, and answer `400/401/409/429/503` with b4hub's JSON error bodies before upgrading. After the upgrade, the handler parses each text frame's `type`. This maps most directly onto the Rust `link.rs` design. Whether headers set on the conn (the `Set-Cookie: b4hub-instance`) are emitted on the `101` with Bandit is **not confirmed** by the docs I read; verify in a spike.
  2. **A custom `Phoenix.Socket.Transport`** mounted with `socket/3` in the Endpoint. You keep endpoint-level plumbing (`check_origin`, `connect_info`, `drainer_spec` for graceful drain). But the path is `<mount>/websocket`, and refusals go through `connect/1` plus `error_handler`, which is less direct for the `409 relocated` body and cookie semantics.
- Custom close codes (4000 `link_replaced`) and protocol-level `ping` frames: the WebSock behaviour supports stop-with-close-code returns. I recall this from the WebSock docs but did not fetch that page in this session, so confirm before relying on it. Application-level `ping`/`pong` JSON frames are trivial in `handle_in`.
- Channels' at-most-once, no-persistence model matches b4hub's relay semantics (events may drop and the change log is the durable path). Even so, the Channels envelope, topic join model and phoenix.js heartbeat would mean a new client protocol on both Swift apps. That is a protocol change, not a server swap. A Swift port of the Channels protocol exists in the community (SwiftPhoenixClient), but I did not research its status here.
- One BEAM process per connection, plus one per joined channel under Channels, is the natural home for b4hub's per-link state (watch set of up to 4 threads, presence snapshot, `lastSeenAt`, queued frames). The WebSock handler process holds it directly.

### Gaps
- I did not read the WebSock behaviour page itself (callback return shapes, close-code tuple) or Bandit's handling of response headers on `101`. Both are needed to confirm "unchanged protocol" down to the cookie and close-code level.
- I did not verify the server-side default websocket `timeout` for `Phoenix.Endpoint.socket/3`. WebSockAdapter's default is 60_000 ms, and phoenix.js heartbeats every 30 s.
- I did not find the full changelog for Phoenix 1.8.11–1.8.16 or any announced Phoenix 1.9/2.0 plans.

## 2. Phoenix.PubSub adapters, cross-node fan-out, delivery guarantees, netsplits

### Takeaway
Phoenix.PubSub (v2.4.1) defaults to the `PG2` adapter, which is built on Erlang's `:pg` and distributed Erlang: every node subscribes locally, and a broadcast sends one message per remote node. It is fire-and-forget (no persistence, no ack, at-most-once). The only alternative adapter in the core docs is Redis. Supabase found Erlang distribution's single TCP link per node pair a bandwidth bottleneck and wrote a gen_rpc-based adapter.

### Cited Findings
- Phoenix.PubSub current version **v2.4.1**. The default adapter is **PG2**: "the default adapter that ships as part of Phoenix.PubSub. It uses Distributed Elixir, directly exchanging notifications between servers." — [Phoenix.PubSub docs](https://phoenix-pubsub.hexdocs.pm/Phoenix.PubSub.html)
- Other adapters: **Redis** ("uses Redis to exchange data between servers", needs `:phoenix_pubsub_redis`), or a custom adapter via `Phoenix.PubSub.Adapter`. — [Phoenix.PubSub docs](https://phoenix-pubsub.hexdocs.pm/Phoenix.PubSub.html)
- API: `broadcast/3` "across the whole cluster", `local_broadcast/3` "only for the current node", and `direct_broadcast/4` "to a given node", with the warning "**DO NOT** use this function if you wish to broadcast to the current node, as it is always serialized". `pool_size` "must be the same throughout the cluster", and `broadcast_pool_size` supports two-step pool resizes during rolling deploys ("No messages are lost during the transition"). Duplicate subscriptions "will cause duplicate events to be sent". Custom dispatchers are deprecated in favor of `subscribe/3`'s `:sender` option. — [Phoenix.PubSub docs](https://phoenix-pubsub.hexdocs.pm/Phoenix.PubSub.html)
- The PubSub docs make **no general delivery guarantee**. The Channels guide states at-most-once delivery and no server-side persistence. — [Phoenix.PubSub docs](https://phoenix-pubsub.hexdocs.pm/Phoenix.PubSub.html); [Phoenix Channels guide](https://phoenix.hexdocs.pm/channels.html)
- Fan-out cost: "Broadcasts work even if the application runs on several nodes/computers". PG2 uses native VM messaging, and each additional node needs only one message sent to it, so adding nodes has negligible cost. — [Phoenix Channels guide](https://phoenix.hexdocs.pm/channels.html)
- **Supabase Realtime** replaced Erlang-distribution fan-out with `Realtime.GenRpcPubSub`, "instead of Erlang distribution, so nodes can have more than one TCP connection between them for more bandwidth". Its default is a two-level flood: send to local-region nodes, plus one representative per remote region that re-floods. They call it costly because "every node in every region receives every tenant's broadcast". A component called **Muster** narrows delivery to nodes that hold members of a tenant. Erlang distribution still carries Muster and `:syn` traffic. — [supabase/realtime ARCHITECTURE.md](https://github.com/supabase/realtime/blob/main/ARCHITECTURE.md)
- Discord (2017) needed **Manifold** to batch sends to remote nodes ("distributes the work of sending messages to the remote nodes of the PIDs") at roughly 5M concurrent users. — [Discord blog: How Discord Scaled Elixir to 5,000,000 Concurrent Users](https://discord.com/blog/how-discord-scaled-elixir-to-5-000-000-concurrent-users)

### Inferences
- For b4hub, cross-node PubSub would let any instance accept any device's link: a command from a phone on node A reaches the Mac's link on node B via `broadcast("user:<id>", ...)` or `direct_broadcast`. That would replace today's "pin all of a user's links to one instance" claim plus ALB stickiness (`Hub/API.md`). The price is at-most-once delivery across nodes, with no ack or ordering guarantee beyond Erlang's per-sender-receiver-pair ordering. Command/reply would still need application-level request ids and timeouts, as b4hub already has (`relay_timeout`).
- Erlang's message-ordering guarantee is per pair of processes. Messages from one process to another on a remote node arrive in send order while the connection holds; this is general Erlang semantics, not cited above. Across a disconnect, messages are silently lost.
- **Netsplits:** during a partition, PG2 broadcasts to unreachable nodes are dropped silently, and subscribers on the far side see nothing until distribution reconnects. Nothing replays. This follows from the no-persistence design, but I found no PubSub doc text that describes netsplit behaviour explicitly. Recovery is the client's job (rejoin plus catch-up), which matches b4hub's existing catch-up via the change log.
- At b4hub's scale (one owner, a handful of devices per user), Supabase's and Discord's fan-out optimisations are irrelevant. Plain PG2 over a 2–3 node cluster is far below any known limit.

### Gaps
- The Erlang `:pg` reference page failed to fetch, so I have no cited text on `:pg`'s consistency model (scopes, eventual consistency, behaviour on reconnect).
- I found no maintained Postgres-backed Phoenix.PubSub adapter in the sources I read. Postgres `LISTEN/NOTIFY` adapters exist in the community, but I did not verify any current package or its status.
- I did not confirm the current version or maintenance status of `phoenix_pubsub_redis`.

## 3. Phoenix.Presence / Phoenix.Tracker, and distributed process registries (Horde, :global, :pg, Registry, syn)

### Takeaway
`Phoenix.Tracker` (under `Phoenix.Presence`) is a heartbeat- and delta-replicated CRDT with no leader. It is eventually consistent, and departures are only noticed after a `down_period` (30 s by default), so it suits "which devices are online" as a soft, eventually-correct view. It does not give an authoritative, immediately-consistent answer. For "exactly one process per user/device across the cluster", `syn` (availability-favouring, recovers from netsplits) and Horde (DeltaCrdt-based) are the common choices. Supabase uses `syn` for cluster-wide singletons.

### Cited Findings
- Phoenix.Tracker "Provides distributed presence tracking to processes". Replication is "eventually consistent, conflict-free", with "no single source of truth or global process". Each node runs its own tracker pool, and "node-local changes are replicated across the cluster". — [Phoenix.Tracker docs](https://phoenix-pubsub.hexdocs.pm/Phoenix.Tracker.html)
- Tracker defaults: `broadcast_period` 1500 ms (delta interval). `max_silent_periods` 10 (a heartbeat roughly every 15 s when idle). `down_period` defaults to `broadcast_period * max_silent_periods * 2`, i.e. 30 s, before a replica is "temporarily down". `permdown_period` 1_200_000 ms (20 min) before its state is discarded. `clock_sample_periods` 2. `max_delta_sizes` `[100, 1000, 10_000]` before falling back to full-state transfer. `pool_size` 1. `permdown_on_shutdown` false. — [Phoenix.Tracker docs](https://phoenix-pubsub.hexdocs.pm/Phoenix.Tracker.html)
- The docs say "it is impossible to know if something is just temporarily unavailable or if it has crashed", hence the timing windows. After a graceful shutdown, presences stay visible to other nodes until `down_period` passes unless `permdown_on_shutdown: true`, and the same applies after SIGKILL. `permdown_on_shutdown: false` is recommended when clients reconnect to another node right away. — [Phoenix.Tracker docs](https://phoenix-pubsub.hexdocs.pm/Phoenix.Tracker.html)
- `handle_diff/2` gets joins and leaves by topic and runs inside the tracker server, so "a crash in the `handle_diff/2` will crash the tracker server". Offload heavy work to tasks. — [Phoenix.Tracker docs](https://phoenix-pubsub.hexdocs.pm/Phoenix.Tracker.html)
- Supabase Realtime keeps Presence as per tenant-topic state synced between nodes over PubSub, with diffs on join/leave and periodic syncs. — [supabase/realtime ARCHITECTURE.md](https://github.com/supabase/realtime/blob/main/ARCHITECTURE.md)
- **syn** is described as "a scalable global Process Registry and Process Group manager for Erlang and Elixir, able to automatically manage dynamic clusters (addition / removal of nodes) and to recover from net splits". It favours availability over consistency, with strong eventual consistency. (Via a package-index summary of syn's README.) — [meterian.io syn component page](https://meterian.io/components/erlang/syn)
- Supabase uses `:syn` to enforce cluster-wide uniqueness of per-tenant singletons. If two nodes start the same singleton, "the oldest registration wins", with node name as tiebreak. They also use `:syn` scopes for region membership and lookups. — [supabase/realtime ARCHITECTURE.md](https://github.com/supabase/realtime/blob/main/ARCHITECTURE.md)
- **Horde** is built on DeltaCrdt. From 0.8.0, `Horde.DynamicSupervisor` no longer cleans up duplicate processes when a netsplit heals and leaves that to `Horde.Registry`. — [Horde 0.9.1 docs (epub)](https://hexdocs.pm/horde/0.9.1/Horde.epub)
- `:global` stores names locally on every node and syncs them on topology changes. An informal benchmark calls it "slow, but not unreasonable so" unless registrations per second are very high. (Personal blog comparison; treat with caution.) — [bigardone: Three real-world examples of distributed Elixir pt 2](https://dev.to/bigardone/three-real-world-examples-of-distributed-elixir-pt-2-4ki1)

### Inferences
- For b4hub's "which Macs are online" `presence` frame: Tracker/Presence would give a cluster-wide view, but a hard-killed node's devices stay "online" to other nodes for about 30 s by default. b4hub currently reports offline promptly when a link closes on the single owning instance. A BEAM design would either tune `down_period` down (minimum 2 × `broadcast_period`) or keep the single-owner-per-user model so presence stays node-local. For a few devices per user, node-local `Registry` plus the per-user ownership b4hub already does is simpler and stronger.
- "One link per device, newer replaces older" maps onto a unique `Registry` key on one node. Across nodes, it maps onto `syn`/Horde/`:global` registration with conflict resolution: the newer link kills the older, and after a netsplit heals the registry picks a winner, and the loser can be sent `link_replaced`.
- Elixir's built-in `Registry` is node-local only (general Elixir knowledge, not fetched here).

### Gaps
- No primary-doc text on `:pg` or `:global` netsplit semantics (the `:pg` page fetch failed).
- I did not find current (2026) versions or maintenance status for Horde or syn.

## 4. Clustering on cloud infra (dns_cluster, libcluster, ECS Fargate, ports, distribution security, operational pain)

### Takeaway
New Phoenix apps ship with `dns_cluster` (v0.3.1), which polls DNS A/AAAA (or SRV) records and calls `Node.connect/1` on each IP. Nodes must be named by IP and share a cookie. On ECS Fargate, people have it working with Cloud Map DNS. The usual trap is that EPMD (4369) is not enough: the distribution port range must be pinned and opened in the security group. Plain distribution is cookie-authenticated cleartext TCP. TLS distribution (`inet_tls_dist`) is the hardening option, and it had a 2026 CVE fixed in 29.0.2 / 28.5.0.2 / 27.3.4.13.

### Cited Findings
- **dns_cluster v0.3.1**: queries the configured name(s) every `:interval` (default 5000 ms) and "will try to connect to every IP from the DNS query with `Node.connect/1`". `:resource_types` defaults to `[:a, :aaaa]` and also supports `:srv`. `:connect_timeout` defaults to 10_000 ms. Nodes join only if their basename matches (or pass `{basename, query}`), "all nodes need to share the same secret cookie", and "their FQDN must be their IP address". For richer strategies it points to libcluster. — [DNSCluster docs](https://dns-cluster.hexdocs.pm/DNSCluster.html)
- Fly.io's guide adds `dns_cluster` to the supervision tree with the query from an env var, and names nodes by private IP so DNS records resolve to node names. — [Fly.io: Clustering your application](https://fly.io/docs/elixir/getting-started/clustering/)
- **ECS Fargate field report (thread active to 2025-06-10):** Cloud Map (`service.namespace.local`) plus dns_cluster, with 4369 open, still failed. The fix was pinning `inet_dist_listen_min`/`inet_dist_listen_max` to 9000–9100 in `vm.args.eex` and opening that range: "Clustering worked immediately as soon as the security group was updated to allow my port range." Cookies must match (set `RELEASE_COOKIE`), otherwise `mix release` generates a random cookie per build. — [ElixirForum: Distributed Elixir not connecting between AWS ECS Fargate tasks](https://elixirforum.com/t/distributed-elixir-not-connecting-between-aws-ecs-fargate-tasks/71099)
- Older reports: a 2018 thread used libcluster's DNS polling strategy with ECS service discovery in awsvpc mode successfully. A 2019/2020 thread reports a team that "struggled with this for months" on Fargate. (Dated.) — [ElixirForum: Distributed Elixir in Amazon ECS (2018)](https://forum.elixirforum.com/t/distributed-elixir-in-amazon-ecs/15106); [ElixirForum: Distributed Elixir on AWS Fargate](https://elixirforum.com/t/distributed-elixir-on-aws-fargate/28487)
- **TLS distribution:** with plain `inet_tcp_dist` the cookie is the only credential and the transport provides no real authentication. With `inet_tls_dist` "the actual authentication is done by the TLS handshake", and the cookie is a secondary check. Enabled with `-proto_dist inet_tls` and `-ssl_dist_optfile`, and every node in the cluster must use the same module. — [Erlang docs: Erlang Distribution over TLS (OTP 29)](https://www.erlang.org/docs/29/apps/ssl/ssl_distribution.html)
- **CVE-2026-48860:** `inet_tls_dist:check_ip/1` called `inet:sockname/1` instead of `inet:peername/1`, so any holder of a CA-signed cert could bypass the LAN allowlist. Affects OTP 26.0 up to before 29.0.2, 28.5.0.2 and 27.3.4.13. — [Mondoo: CVE-2026-48860](https://mondoo.com/vulnerability-intelligence/vulnerability/CVE-2026-48860)

### Inferences
- **ECS checklist for b4hub:** Cloud Map private DNS namespace on the hub service (A records, awsvpc). `RELEASE_DISTRIBUTION=name` with `RELEASE_NODE=b4hub@<task IP>` (the IP from the ECS task metadata endpoint in `env.sh`). `RELEASE_COOKIE` from Secrets Manager. `inet_dist_listen_min/max` pinned. A security group self-ingress rule for 4369 plus the dist range. `dns_cluster` querying the Cloud Map name. All of this is Terraform-level work in `Infra/`. The env.sh/metadata details are standard practice and not cited above.
- A single fixed dist port (`inet_dist_listen_min == max`), or running without EPMD (`-start_epmd false` with a fixed port), simplifies security groups. The forum thread notes a single port works; the EPMD-less detail is my own knowledge, so verify it.
- Rolling ECS deploys mean nodes join and leave constantly. Tracker's 30 s `down_period` and PubSub's silent drops during churn are the realistic "pain". A per-user-owner design minimises cross-node dependencies during deploys.
- The intra-VPC dist traffic is cleartext with the default TCP dist. In a private VPC subnet with security-group self-reference, many teams accept that. TLS dist adds certificate management on Fargate (no host-level PKI).

### Gaps
- I did not fetch libcluster's current version or its ECS strategy docs (a community `ClusterEcs` strategy exists, unverified here).
- No first-party AWS guidance on Erlang clustering on ECS was found.
- I did not find recent (2025–2026) write-ups quantifying operational pain (split-brain incidents, deploy churn) on ECS specifically.

## 5. Benchmarks and real-world scale

### Takeaway
The canonical figure is roughly 2M idle WebSocket connections on one 40-core/128 GB box (Phoenix, 2015), and 2.3M on a 20-core/64 GB droplet in a later reproduction. Back-of-envelope, that is about 28–45 KB per idle connection. Discord (Elixir, millions of concurrent users with Rust NIFs for hot data structures), WhatsApp (Erlang) and Supabase Realtime (Elixir/Phoenix, multi-region global cluster) are the production references. All benchmark numbers are old and measure idle connections, not relaying.

### Cited Findings
- Phoenix team blog (Nov 2015), "The Road to 2 Million Websocket Connections in Phoenix": roughly 2M connections, limited by ulimit. One report says "~2 million uses 58GB". — [Phoenix blog](https://phoenixframework.org/blog/the-road-to-2-million-websocket-connections)
- The same experiment as reported by Akita (Oct 2015): under 90 GB on a 40-core, 128 GB machine. — [AkitaOnRails](https://akitaonrails.com/2015/10/29/phoenix-experiment-holding-2-million-websocket-clients/)
- Reproduction (dsander, Tsung on DigitalOcean): on a 64 GB / 20-core droplet "Phoenix was able to accept and maintain 2.3 million websocket connections", limited by memory. The earlier run needed about 84 GB for 2M. The benchmark only opens and holds connections to a chat app. — [dsander/phoenix-connection-benchmark](https://github.com/dsander/phoenix-connection-benchmark)
- Per-connection memory is not stated by the sources. Dividing the totals gives about 29 KB (58 GB/2M), about 45 KB (90 GB/2M), and about 28 KB (64 GB/2.3M). (My arithmetic.) — derived from the three sources above

## 7. Phoenix Sync / Electric SQL relevance to a hub that syncs a change log to devices

### Takeaway
Phoenix.Sync (v0.6.1, beta) wraps ElectricSQL (1.x, stable APIs since March 2025, 1.4.x releases through early 2026) to stream Postgres "shapes" (filtered table subsets) to clients over HTTP/JSON, plus a `Writer` for authorized client writes. It is aimed at JS/TypeScript front ends, with no Swift client named. b4hub already has its own change-log push/pull contract (`changes.json`) and a SQLite mirror on the phone, so Electric would be a different sync model, not a drop-in.

### Cited Findings
- Phoenix.Sync **v0.6.1, beta**: "Real-time sync for Postgres-backed Phoenix applications". It "uses ElectricSQL for core sync, fan-out and data delivery" and maps Ecto queries to Electric Shapes for partial replication. — [Phoenix.Sync README](https://phoenix-sync.hexdocs.pm/readme.html)
- Read-path APIs: `Phoenix.Sync.Client.stream/2`, `LiveView.sync_stream/4`, `Router.sync/2`, and `Controller.sync_render/3`. Write path: `Phoenix.Sync.Writer` "authorizes and validates the writes before applying them to the database", applied atomically via `Ecto.Multi`. — [Phoenix.Sync README](https://phoenix-sync.hexdocs.pm/readme.html)
- Two modes. **Embedded**: Electric runs as a dependency with no external HTTP API. **HTTP**: consumes an external Electric service. Clients can be "any client in any language that speaks HTTP and JSON". Examples are TypeScript and React, and no Swift/native client is named. — [Phoenix.Sync README](https://phoenix-sync.hexdocs.pm/readme.html)
- ElectricSQL 1.0 (2025-03-17) declared the APIs stable and named phoenix_sync as part of the release. Electric 1.4.x releases ran through early 2026 (1.4.12 on 2026-03-04). — [Electric 1.0 released](https://electric.ax/blog/2025/03/17/electricsql-1.0-released.md); [hex: electric](https://www.hex.pm/packages/electric)

### Inferences
- Relevance to b4hub is low-to-moderate. Electric solves "fan out Postgres changes to many clients with partial replication", which overlaps conceptually with the hub's change log. But b4hub's sync is a bidirectional, versioned push/pull with its own conflict rules and a fixture contract shared between Rust and Swift. Adopting Electric would mean rewriting the phone mirror's sync client to Electric's HTTP shape protocol (no first-party Swift client) and depending on a beta Phoenix wrapper. It is better seen as prior art than as a component.
- Electric relies on Postgres logical replication (general knowledge about Electric, not confirmed on the page I read). That would add a replication-slot operational dependency on the hub's RDS.

### Gaps
- I did not read Electric's HTTP shape protocol docs (offsets, live mode, long-poll vs SSE) or its Postgres requirements (`wal_level=logical`, replication slots), and I found no Swift client.
- Phoenix.Sync's 2026 release history and roadmap to 1.0 were not found.
