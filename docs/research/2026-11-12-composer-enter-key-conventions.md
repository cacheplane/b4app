# Return sends, but guard the IME first

Every mainstream desktop AI chat app and coding agent checked defaults to **Return sends, Shift+Return inserts a newline**, and none has changed that default. The products that answered complaints (OpenAI's desktop app, Cursor, Claude Code's VS Code extension, Zed, Slack, Teams, Linear) instead added an **opt-in swap in which Return inserts a newline and Cmd+Return (Ctrl+Enter elsewhere) sends**. On iPhone and iPad the convention reverses: the on-screen Return key inserts a newline and a visible Send button sends. Apple's Messages sends on Return only when a hardware keyboard is attached, with Option+Return for a newline. The most common shipped bug is not about the convention at all. Apps send the message when Return was meant to commit a Japanese, Chinese or Korean input-method candidate, and Claude Code, Claude Desktop, claude.ai, Cursor and ChatGPT have all shipped it. SwiftUI's `TextField`, `TextEditor` and `onKeyPress` expose no composition state, so a correct native composer handles Return inside a wrapped `NSTextView` or `UITextView` and checks for marked text before it sends. For the field's height, the agreed pattern is to grow a line at a time to a cap, then hold that frame and scroll inside it, keeping the caret visible. That pattern is also more reliable in AppKit than in SwiftUI. For a SwiftUI Mac and iOS app with a rounded three-line composer, the result is a short, specific set of key bindings and one architectural change, set out at the end.

## Desktop products agree on Return-to-send; only the modifiers differ

The desktop default is close to universal. Third-party guides document Return-to-send with Shift+Return for a newline on ChatGPT web ([Android Authority](https://androidauthority.com/how-to-enter-new-line-chatgpt-3385526)), claude.ai ([claude-skills-guide](https://claude-skills-guide-3lc.pages.dev/claude-shortcuts-complete-guide/)) and Gemini ([aipicks.jp](https://aipicks.jp/mag/gemini-line-break-2026)). Anthropic's own desktop docs say to type and press Enter to send ([Claude Code desktop docs](https://code.claude.com/docs/en/desktop)). Google stated the rationale in public when AI Studio changed behaviour: "most platforms follow the convention where pressing Enter sends the message, and Shift + Enter creates a new line on desktop. We're aligning with that best practice" ([Google AI dev forum](https://discuss.ai.google.dev/t/sending-messages-ctrl-enter-android-web/102523)). Slack, Teams, Discord, Telegram and WhatsApp share the same default ([Slack help](https://slack.com/help/articles/115005523006); [MC1217643](https://mc.merill.net/message/MC1217643)). One caveat applies: no first-party help page was found for the ChatGPT, claude.ai, Gemini or Perplexity web composers, so their defaults rest on consistent third-party guides and user reports.

The Mac adds one wrinkle. Apple's documented newline keys in Messages are **"Option-Return or Shift-Return"** ([Apple: Messages shortcuts](https://support.apple.com/guide/messages/ichtc78b3bff/mac)). Discord users complain that it ignores the "standard Mac" Option+Return ([Discord community](https://support.discord.com/hc/ko/community/posts/4419611598743-Use-Standard-Mac-Shortcut-for-New-Line-when-Composing-Messages)). WhatsApp for Mac moved its newline to Option+Enter in May 2026 and made Shift+Enter send, which drew complaints of its own ([PiunikaWeb](https://piunikaweb.com/2026/05/16/whatsapp-mac-update-line-break-shortcut/)). A Mac composer that accepts both Shift+Return and Option+Return as a newline satisfies both camps.

Cmd/Ctrl+Return is the contested key. In chat apps it is the send key of the swapped mode. In coding agents that queue messages, it has come to mean "send now". Cursor documents Return as "Queue message (default)" and Cmd+Return as "Force send message" ([Cursor docs](https://www.cursor.com/docs/configuration/kbd)). Claude Code's `chat:sendNow` (Ctrl+Enter) sends queued messages and the draft at once, and when nothing is running it simply submits ([Claude Code keybindings](https://code.claude.com/docs/en/keybindings)). Zed uses a held Cmd/Ctrl at submit to follow the agent ([Zed agent panel](https://zed.dev/docs/ai/agent-panel)). Terminal agents are a separate case. Many terminals send the same byte for Shift+Enter and Enter, so Claude Code and the Codex CLI fall back to **Ctrl+J** or `\`+Return for a newline ([Claude Code interactive mode](https://code.claude.com/docs/en/interactive-mode); [Codex commit](https://forge.lthn.ai/core/core-agent-ide/commit/1bf00a3a95ca533fe98665dc609cfbf0d3e2b3c1)). That constraint does not apply to a native app.

| Product | Return | Shift+Return | Cmd/Ctrl+Return | Swap setting |
|---|---|---|---|---|
| ChatGPT / Codex desktop | Send | Newline | Sends when "require Cmd+Enter" is on | Multiline prompts or every prompt ([settings reference](https://learn.chatgpt.com/docs/reference/settings)) |
| Claude desktop | Send | Newline | Nothing documented | None; request open ([#89673](https://github.com/anthropics/claude-code/issues/89673)) |
| Claude Code VS Code | Send | Newline | Sends when the setting is on | `claudeCode.useCtrlEnterToSend` ([claude-howto](https://claude-howto.vercel.app/ide-extensions/vs-code/)) |
| Cursor | Queue | Newline | Force send | "Submit with Cmd+Enter" ([forum](https://forum.cursor.com/t/make-enter-insert-newline-in-chat-cmd-enter-to-submit/142786)) |
| Zed agent panel | Submit | Newline | Send in modifier mode | `use_modifier_to_send` ([commit](https://git.secluded.site/zed/commit/e1d28ff957dbc16c39e4a8e061e79526f181849a)) |
| Apple Messages (Mac) | Send | Newline | Not documented | None; Option+Return also inserts a newline |
| Slack | Send | Newline | Sends in "Start a new line" mode | "When writing a message, press Enter to…" ([Slack help](https://slack.com/help/articles/115005523006)) |

## Vendors answer complaints with opt-in swaps, never new defaults

Accidental sends of half-written prompts are the standing complaint, and they hit AI tools harder than chat apps because prompts are longer. The Claude desktop request states it plainly: "it's very easy to accidentally send an incomplete message with a reflexive Enter" ([anthropics/claude-code#89673](https://github.com/anthropics/claude-code/issues/89673)). Similar requests sit open or have been answered across ChatGPT, Cursor, Microsoft 365 Copilot and Sourcegraph Cody ([OpenAI Community](https://community.openai.com/t/chatgpt-app-allow-toggle-newlines-and-cmd-ctrl-return-enter-for-submission/1253379); [Cursor forum](https://forum.cursor.com/t/disable-the-enter-key-to-send-the-chat/104598); [MS Tech Community](https://techcommunity.microsoft.com/discussions/microsoft365copilot/allow-new-line-on-enter--ctrl-enter-to-submit-instead-of-enter-submits/4478917)). Every vendor that responded shipped a toggle and kept Return-to-send as the default. Microsoft's Teams setting went GA in February 2026 ([MC1217643](https://mc.merill.net/message/MC1217643)), Linear added one in March 2026 ([Linear changelog](https://linear.app/changelog/2026-03-12-ui-refresh)), and an OpenAI support reply in September 2026 pointed users to the desktop app's General setting ([OpenAI Community](https://community.openai.com/t/chatgpt-app-allow-toggle-newlines-and-cmd-ctrl-return-enter-for-submission/1253379)). In every swapped mode found, the send key becomes **Cmd+Return on the Mac and Ctrl+Enter elsewhere**. No product uses Shift+Return to send. Slack and Teams use identical wording, **"When writing a message, press Enter to… Send the message / Start a new line"**, which has become the de facto label ([Slack help](https://slack.com/help/articles/115005523006)).

State-dependent bindings are the cautionary tale. The Codex app once made Return send a single-line draft but switch to Ctrl+Enter "once the text becomes multiline". One user called that "easy to trigger by accident" and asked for a fixed binding ([OpenAI Community](https://community.openai.com/t/feature-request-allow-a-fixed-ctrl-enter-send-shortcut-in-codex-app-chat/1379225)). The current reference now offers "every prompt" as well as "multiline prompts" ([settings reference](https://learn.chatgpt.com/docs/reference/settings)). A Claude desktop request asks specifically for a "state-independent submit key" and cites the Codex mode as prior art ([claudeissues #74655](https://claudeissues.com/issue/74655-feature-opt-in-state-independent-submit-key-enter-newline-mod-enter-submit-deskt)). The only content-aware rule in a mainstream messenger is Slack's opt-in checkbox that stops Return from sending inside a ``` code block ([Technipages](https://www.technipages.com/slack-how-to-prevent-messages-from-sending-when-you-press-enter-when-sending-a-code-snippet/)). The lesson is that a key should mean the same thing regardless of what is in the draft or what the agent is doing.

## On iPhone, Return is a newline and the button sends

Touch devices invert the desktop rule. In Messages the on-screen Return creates a new paragraph and the blue arrow sends, and "this behaviour is not configurable" ([Apple Community](https://discussions.apple.com/thread/252861769)). ChatGPT's iOS and Android apps behave the same way ([Android Authority](https://androidauthority.com/how-to-enter-new-line-chatgpt-3385526)), and Google moved AI Studio's mobile site to treat Enter as a line break ([Google AI dev forum](https://discuss.ai.google.dev/t/sending-messages-ctrl-enter-android-web/102523)). Teams scopes its Enter setting to desktop and web only ([MC1217643](https://mc.merill.net/message/MC1217643)).

Hardware keyboards on iPad have no system-wide rule. In Messages, "the Return key will send the message", and Option+Return inserts a new paragraph ([Apple Community](https://discussions.apple.com/thread/254104469)). That mirrors the Mac. Other apps split: users report Return sending in Discord and Teams but inserting a newline in Signal and Facebook Messenger ([Apple Community](https://discussions.apple.com/thread/253670900); [Apple Community](https://discussions.apple.com/thread/251678507)). Reports on ChatGPT's iPad app conflict, probably across versions ([OpenAI Community](https://community.openai.com/t/request-enable-shift-enter-to-send-messages-in-mobile-app-bluetooth-keyboard-support/1273619); [BoltAI feedback](https://feedback.boltai.com/p/boltai-mobile-ipad-and-keyboard-shortcut-to-send-a-prompt)). No source documents the Claude iOS app's behaviour. Following Messages is the defensible choice: newline from the software keyboard, send from a hardware Return. The catch is that only key-press handling can tell the two apart, because `pressesBegan` never fires for the software keyboard ([Apple Developer Forums 761622](https://developer.apple.com/forums/thread/761622)). That hardware path is shaky. One report finds `UIKeyCommand`s in a `UITextView` subclass never firing, firing repeatedly or firing late, with `wantsPriorityOverSystemBehavior` making "no difference" (FB13897415, [Apple Developer Forums 757077](https://developer.apple.com/forums/thread/757077)). Whether that is fixed in iOS 18 or 26 is unknown.

## Input-method composition breaks most naive Return handlers

When a Japanese, Chinese or Korean input method is composing, Return commits the candidate. A dead-key accent (Option+E, then a vowel) also creates composing text, even on an English layout ([Apple Developer Forums 808915](https://developer.apple.com/forums/thread/808915)). A handler that sends on Return without checking sends a half-converted message. This bug has shipped repeatedly in Claude Code, Claude Desktop's plan feedback input, claude.ai/code and Cursor ([claudeissues #8455](https://claudeissues.com/issue/8455-bug-ime-enter-key-incorrectly-triggers-message-send-during-japanese-input); [#30540](https://claudeissues.com/issue/30540-bug-claude-desktop-ime-composition-enter-key-triggers-submission-in-plan-feedbac); [Cursor forum](https://forum.cursor.com/t/critical-i18n-ime-enter-key-triggers-unintended-submission-in-chat-and-askquestion-completely-breaks-cjk-input-for-1-5-billion-users/154276)). A 2025 write-up credits Slack and Discord with getting it right years earlier ([dev.to](https://dev.to/yukimi-inu/why-16-billion-east-asians-are-quietly-raging-at-your-enter-key-handler-1po0)). On the web the guard is `isComposing || keyCode === 229`, because Safari reports `isComposing` incorrectly. Chrome's guidance also insists that shortcuts "must not replace native form submit paths", so a visible Send button is mandatory ([Chrome for Developers](https://developer.chrome.com/docs/modern-web-guidance/guides/forms/ime-safe-enter-submit)).

Native apps have the right primitive, but SwiftUI does not expose it. AppKit's `hasMarkedText()` and `markedRange()` report uncommitted text, and a local probe on macOS 26.5 confirmed that `hasMarkedText()` turns true after `setMarkedText` (local probe, `/private/tmp/claude-501/-Users-blove-repos-b4app--claude-worktrees-vigorous-benz-64f0ac/e73e37ff-c797-4029-8a8b-ca7b0d672a44/scratchpad/keytest/main.swift`). UIKit's equivalent is `markedTextRange`, though Apple DTS warns that an app cannot know synchronously, inside `shouldChangeTextIn`, whether incoming text will become marked, and advises deferring the decision ([Apple Developer Forums 808915](https://developer.apple.com/forums/thread/808915)). A November 2024 forum question asking how `onKeyPress` can detect an open candidate window has no answer ([Apple Developer Forums 769925](https://developer.apple.com/forums/thread/769925)). SwiftUI's other options have bugs of their own. On a vertical `TextField` with an iOS hardware keyboard, `onKeyPress(.return)` drops focus and dismisses the keyboard whether the handler returns `.handled` or `.ignored`, and DTS called this "most likely as-designed" ([Apple Developer Forums 760511](https://developer.apple.com/forums/thread/760511)). `onSubmit` on a vertical field never fires from the software keyboard ([danielsaidi.com](https://danielsaidi.com/blog/2023/09/15/dismissing-a-multiline-textfield-with-the-return-key-in-swiftui)). `TextEditor` has no submit hook at all.

The AppKit text system gives a clean hook if the app reads it correctly. The local probe on macOS 26.5 fed key events through `NSTextView.interpretKeyEvents` and recorded which command selector each produced. The selectors come from `StandardKeyBinding.dict`.

| Keys | Selector delivered to `textView(_:doCommandBy:)` |
|---|---|
| Return, Shift+Return, keypad Enter | `insertNewline:` |
| Option+Return, Shift+Option+Return | `insertNewlineIgnoringFieldEditor:` |
| Control+Return | `insertLineBreak:` |
| Command+Return | `noop:` (unless a menu or shortcut claims it first) |

Because **Return and Shift+Return produce the identical selector**, the delegate must read `NSApp.currentEvent?.modifierFlags`, which is what Apple's text-editing guide prescribes ([Apple: Intercepting Key Events](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/TextEditing/Tasks/InterceptKeys.html)). Handling Return in `doCommandBy` has one advantage over a `keyDown` override or a local `NSEvent` monitor: the input method has already had first refusal by the time the command arrives. A 2006 Cocoa-dev report says a Korean input method passed `insertNewline:` through when committing ([Cocoa-dev](https://lists.apple.com/archives/cocoa-dev/2006/Feb/msg00936.html)), so the `hasMarkedText()` check is still needed at that point. No 2024–2026 source says which current input methods do this, and the probe used synthetic events with no input method active. Both points need on-device tests with Kotoeri (Japanese Romaji), Pinyin and 2-Set Korean.

## A capped field must clip and scroll, or text spills out of it

The behaviour at max height is well agreed, even though no vendor publishes its cap. The field starts at one line and grows a line at a time to a cap. Then the outer frame stops growing and the text scrolls inside it, with the caret kept in view, and the field shrinks again as text is deleted ([toolsfuel](https://toolsfuel.com/blog/css-field-sizing-property-explained-2026); [Chrome for Developers: field-sizing](https://developer.chrome.com/docs/css-ui/css-field-sizing?hl=en)). Production caps found run from **88 pt (about four lines) in OpenClaw's Mac composer** through **120 pt in Stream Chat's iOS SDK** to **200 pt in AWS's Bedrock Mac client**, and web guides suggest about six lines ([openclaw](https://github.com/openclaw/openclaw/blob/main/apps/shared/OpenClawKit/Sources/OpenClawChatUI/ChatComposerTextView.swift); [stream-chat-swift](https://github.com/GetStream/stream-chat-swift/blob/develop/Sources/StreamChatUI/CommonViews/InputTextView/InputTextView.swift); [Bedrock client](https://github.com/aws-samples/amazon-bedrock-client-for-mac/blob/main/Sources/Bedrock/Features/Composer/ComposerTextView.swift)). A three-line cap is therefore the tightest found, which raises the stakes on internal scrolling, since the user will spend more time scrolled. Stream scrolls to the caret after every height change. Both Mac examples use an overlay, auto-hiding vertical scroller. The exact caps of ChatGPT, Claude, Slack, Messages and Cursor are unsourced.

SwiftUI's capped field has thin production evidence. Apple documents that a vertical `TextField` past its line limit "becomes scrollable" ([Apple: lineLimit](https://developer.apple.com/documentation/swiftui/view/linelimit(_:)-7ufty)). A September 2025 report, however, finds `TextField(axis: .vertical).lineLimit(3)` inside a `Form` growing past its limit after 10 to 20 newlines on macOS 26 and iOS 26, with no reply or workaround ([Apple Developer Forums 802101](https://developer.apple.com/forums/thread/802101)). Ice Cubes and Exyte Chat, two widely used open-source SwiftUI chat UIs, never cap their vertical `TextField` at all ([Ice Cubes](https://github.com/Dimillian/IceCubesApp/blob/main/Packages/Conversations/Sources/Conversations/Detail/ConversationInputView.swift); [Exyte Chat](https://github.com/exyte/Chat/blob/main/Sources/ExyteChat/Views/InputView/TextInputView.swift)). `TextEditor` does not size to content, so every recipe measures a hidden `Text` and clamps a frame. Commenters report the measured height going stale after a few lines ([Apple Developer Forums 654824](https://developer.apple.com/forums/thread/654824)). The copy must also match the font, the 5 pt line-fragment padding and the insets exactly.

The robust pattern found on the Mac is an `NSTextView` that is the document view of an `NSScrollView`, wrapped in `NSViewRepresentable`. It reports its height through `sizeThatFits(_:nsView:context:)`, clamped to the cap. OpenClaw measures with a separate `NSTextStorage`/`NSLayoutManager` at the proposed width so that SwiftUI's sizing passes "never move the insertion point or change the editor's scroll position" ([openclaw](https://github.com/openclaw/openclaw/blob/main/apps/shared/OpenClawKit/Sources/OpenClawChatUI/ChatComposerTextView.swift)). Reporting the size through `sizeThatFits` keeps SwiftUI's frame, the chrome and the AppKit view in agreement within one layout pass. Writing a `@State` height back asynchronously, as Bedrock does, can lag a frame. The usual cause of text drawing outside the rounded field when Return is pressed past the cap is that the frame was clamped on a view other than the one that clips. Either the text view is not inside a clipping scroll view, or the frame limit sits outside a view that keeps its own unclamped size. The clamped view and the chrome must be the same view. This diagnosis is an inference from the open-source code; no source names that exact symptom. On iOS the equivalent is a `UITextView` whose height is clamped, with scrolling on, and a scroll to the caret after each height change, as in Stream's code. Two details are unverified: whether TextKit 2 changes this measurement (touching `layoutManager` forces a TextKit 1 fallback), and whether `NSTextView` re-scrolls to the caret by itself when its scroll view shrinks in the same pass.

## Recommendation for a rounded, three-line SwiftUI composer

**Keep Return-to-send as the default and make Cmd+Return send in every mode**, so the setting changes only what plain Return does. **Never let Return's meaning depend on the draft or on whether a turn is running.** **Guard every send on marked text.** **Build the Mac editor from AppKit** and use SwiftUI for layout, placeholder and the Send button. Concretely:

| Context | Return | Shift+Return | Option+Return | Cmd+Return |
|---|---|---|---|---|
| Mac, default | Send (no-op on an empty draft) | Newline | Newline | Send |
| Mac, "Start a new line" | Newline | Newline | Newline | Send |
| iPhone/iPad software keyboard | Newline; Send button sends | n/a | n/a | n/a |
| iPad/iPhone hardware keyboard | Send, if the key-command path proves reliable; otherwise newline | Newline | Newline | Send |

On macOS, replace `TextEditor` with an `NSTextView` in an `NSScrollView` (overlay, auto-hiding vertical scroller, `drawsBackground = false`). Report height through `sizeThatFits` as `min(3 × line height + insets, measured)`, measured from the font's line height so it follows Dynamic Type. Put the rounded background and stroke on that same clamped frame, and call `scrollRangeToVisible(selectedRange())` after a height change. In `textView(_:doCommandBy:)`, treat `insertNewline:` as follows. If `hasMarkedText()` is true, return `false` and let the input method commit. If Shift is held, insert a newline. Otherwise send. Let `insertNewlineIgnoringFieldEditor:` and `insertLineBreak:` fall through, so Option+Return and Control+Return keep their system meaning. Bind Cmd+Return with `.keyboardShortcut(.return, modifiers: .command)` on the Send button. Offer the swap in Settings as "When writing a message, press Return to: Send the message / Start a new line". Give the Send button a "Send (Return)" help tag, since a placeholder hint disappears once typing starts. On iOS, keep the current `TextField(axis: .vertical).lineLimit(1...3)` for the software keyboard, outside any `Form`. Move to a `UITextView` representable only if hardware-keyboard send is wanted, gating it on `markedTextRange == nil` and testing on device first, given FB13897415.

Two observations about the current code bear on this. They come from reading `Sources/WorkspaceUI/ComposerField.swift` and `Sources/WorkspaceUI/ComposerView.swift` and have not been tested. First, the Mac sends through `.keyboardShortcut(.return, modifiers: [])` on the Send button, a key equivalent, which AppKit can match before the text view and its input method see the key. That exposes the IME-commit bug and needs a Kotoeri test. Second, the Send button is swapped for Stop while a turn runs and is disabled on an empty draft. In both states plain Return falls through to `TextEditor` and inserts a newline, which is exactly the state-dependent behaviour users of the Codex app reported as a trap. A `doCommandBy` handler that always consumes Return (sending, queueing or doing nothing) closes both gaps.

## Conclusion

The convention question is settled. The open engineering problem is the one most vendors still get wrong: Return has to reach the input method before it reaches the send logic. That reverses the usual SwiftUI instinct to reach for a shortcut modifier. The safest send path on Apple platforms is the oldest one, AppKit's command-selector delegate, because it is the only hook that runs after the input method and can see marked text. The three-line cap fits the rounded design, but it is tighter than any production composer found. It is acceptable only if internal scrolling and caret tracking are solid, which again favours a text view the app controls over SwiftUI's measured or `lineLimit` fields. If the app later adds queueing or steering while a turn runs, Cmd+Return is the slot other coding agents use for "send now". Keeping it as an unconditional send today leaves that path open without retraining anyone.
