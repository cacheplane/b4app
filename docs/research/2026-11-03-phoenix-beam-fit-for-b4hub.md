# Keep b4hub in Rust; fix the wakeup

> Written 2026-11-03, before the work it led to. Since then: the change long-poll wakes across instances (D-161), and the hardening found by reading Phoenix's source (D-162 to D-168, D-172; notes in [`2026-11-03-phoenix-source-hardening/`](2026-11-03-phoenix-source-hardening/)). The source notes for this report are in [`2026-11-03-phoenix-beam-fit-for-b4hub/`](2026-11-03-phoenix-beam-fit-for-b4hub/).


**Don't adopt Phoenix or the BEAM for b4hub, either as a rewrite or as a Phoenix relay edge in front of the Rust core.** The BEAM's real strengths are a process per connection, Phoenix.PubSub forwarding between nodes over distributed Erlang, CRDT-based Presence, and supervision. They map onto one part of the hub, the WebSocket relay, which is **about 4,000 of the hub's 18,000 source lines**. Their headline benefit is letting a phone and its Mac sit on different nodes, and M8e Part B (D-085) already removed that need. It pins every link of a user to one instance with a Postgres claim, a `409 relocated` refusal, and ALB cookie stickiness, in **about 420 lines and no new infrastructure**. The rest of the hub (RLS-scoped change-log sync under advisory locks, the at-most-once notification ledger, passkeys, Sign in with Apple, APNs) depends on PostgreSQL and on libraries. A runtime change doesn't simplify any of it. Elixir's equivalents there are uneven: JOSE, Ecto, and Mint are mature, but the only server-side WebAuthn library has one maintainer and has never been independently reviewed, and the only maintained APNs client moved to a new transport two months ago. A port would also give up sqlx's compile-time-checked queries and the paused-clock relay tests. It would make Elixir the third production language for a solo owner who chose Rust (D-043) to share a toolchain with the b4 codebase. And BEAM clustering on Fargate would add discovery, distribution ports, and a shared cookie to Terraform that has none of these today. The work worth doing is smaller. The hub's one unsolved multi-instance gap is the change long-poll wakeup, which is still an in-process `tokio::sync::Notify`. With two tasks, a phone's pull can sit for up to 25 s after the Mac pushes a change, and a Postgres `LISTEN/NOTIFY` ping fixes that in Rust. The answer changes in three cases: if the product needs live fan-out across users, if the affinity design fails its first live two-task test, or if the owner's everyday stack stops being Rust.

## The BEAM's strengths sit in the relay's 4,000 lines

Phoenix offers four things that matter for a realtime hub. **Channels** multiplex topics over one socket with an at-most-once, no-persistence delivery model and client-driven rejoin with backoff ([Phoenix Channels guide](https://phoenix.hexdocs.pm/channels.html)). **Phoenix.PubSub 2.4.1** broadcasts across a cluster through its default PG2 adapter, which is built on Erlang's `:pg` and sends one message per remote node with no broker ([Phoenix.PubSub docs](https://phoenix-pubsub.hexdocs.pm/Phoenix.PubSub.html)). **Phoenix.Tracker/Presence** is a leaderless CRDT that replicates deltas every 1.5 s ([Phoenix.Tracker docs](https://phoenix-pubsub.hexdocs.pm/Phoenix.Tracker.html)). **dns_cluster** joins nodes by polling DNS ([DNSCluster docs](https://dns-cluster.hexdocs.pm/DNSCluster.html)). Under all four sits OTP's model of one process per connection with a supervisor to restart it. The ecosystem is current: Phoenix 1.8.16, Elixir 1.20 (June 2026), and OTP 29 (May 2026), with three OTP majors patched in parallel ([Elixir v1.20 release](https://elixir-lang.org/blog/2026/06/03/elixir-v1-20-0-released); [erlang/otp releases](https://api.github.com/repos/erlang/otp/releases)).

These primitives fit the relay closely. b4hub's relay is a hand-built actor system. It has one tokio task per WebSocket, a bounded 256-frame `mpsc` mailbox per link, a `Mutex<HashMap>` registry where the newest link for a device replaces the older one, watcher maps for fan-out by thread, an in-flight map of `oneshot` reply channels, and timed holds for interrupts and answers ([registry.rs](../../Hub/crates/b4hub/src/relay/registry.rs), lines 108–443; [route.rs](../../Hub/crates/b4hub/src/relay/route.rs), lines 84–102). **Much of the 1,064-line `registry.rs` and 753-line `route.rs` re-implements things Elixir provides built in**: `Registry`, PubSub topics per thread, and `GenServer.call` with timeouts. The delivery semantics already match Phoenix's. The relay "carries commands, replies, presence, and live progress, never state", and a lost frame "costs only a moment of streaming" because the change log stays the source of truth ([decisions.md](../../docs/decisions.md), D-054). That is the same at-most-once contract Phoenix states.

Outside the relay, the fit disappears. Sync relies on forced row-level security set per transaction, per-org advisory locks so that commit order equals `hub_seq` order, and idempotent `(org_id, device_id, device_seq)` pushes ([decisions.md](../../docs/decisions.md), D-043, D-050). Notification detection writes its at-most-once ledger inside that same push transaction ([b4hub-db/src/push.rs](../../Hub/crates/b4hub-db/src/push.rs), lines 1–12). All of this is PostgreSQL work that runs the same under Ecto or sqlx.

| Hub concern | Rust today | BEAM equivalent | Net for b4hub |
|---|---|---|---|
| Per-link mailbox, heartbeat, close codes | tokio task + bounded `mpsc` | One process per socket (WebSock handler) | Cleaner code, same behaviour |
| Watch fan-out, reply correlation, holds | Hand-written maps and `oneshot`s | PubSub topics, `GenServer.call`, `send_after` | Less code; ~1,800 lines would shrink |
| Cross-instance routing | User affinity: claim table, `409`, ALB cookie | Distributed PubSub, any node serves any link | Removes ~420 lines and the cookie logic; adds a cluster |
| Presence | Exact and immediate on the owning instance | Tracker CRDT, eventually consistent | Worse by default (30 s `down_period`) |
| Change-log sync, ledger, RLS | sqlx + raw SQL, compile-time checked | Ecto/Postgrex + raw SQL, unchecked | No gain; loses query checking |
| Passkeys, Apple, APNs | webauthn-rs, jsonwebtoken, reqwest HTTP/2 | Wax, JOSE/Joken, Pigeon or Finch | Thinner libraries in two of three |

## User affinity already delivers what clustering would sell

The useful question is whether Phoenix beats the design that shipped, not whether it beats a single process. M8e Part B registers each instance in `hub_instances` with a 5 s heartbeat (dead after 20 s) and names each user's serving instance in `user_links`. It claims the user with one upsert at upgrade time, answers `409 relocated` when another live instance owns that user, and relies on ALB application-cookie stickiness on `b4hub-instance` for reconnects. It also drains claims on SIGTERM and closes links that a recovered instance lost while it was presumed dead ([decisions.md](../../docs/decisions.md), D-085, D-086; [Hub/API.md](../../Hub/API.md), "More than one instance"). The design document rejected frame forwarding by name. Forwarding "would need an internal transport for 256 KiB frames and high-rate deltas", "would split the in-flight map", and every surveyed design that forwarded, "Phoenix PubSub with PG adapter" among them, "pays for a broker" ([M8e Part B design](../../docs/superpowers/specs/2026-11-02-m8e-part-b-relay-routing-design.md), line 15).

With a BEAM cluster, the claim table, the `409`, the cookie retry rule in the Swift `RelayLink`, the split guard, and the 5 s deregistration trick would all go away, since PubSub would carry a phone's command to whichever node holds the Mac. **The cost replaces them with harder infrastructure.** The cluster needs a Cloud Map namespace, nodes named by task IP, a `RELEASE_COOKIE` secret, and a security-group rule for EPMD (port 4369) plus a pinned distribution port range. One 2025 ECS Fargate report found that clustering "worked immediately" only after that range was opened, and an earlier team "struggled with this for months" ([ElixirForum, 2025](https://elixirforum.com/t/distributed-elixir-not-connecting-between-aws-ecs-fargate-tasks/71099); [ElixirForum, 2020](https://elixirforum.com/t/distributed-elixir-on-aws-fargate/28487)). Default distribution is cleartext TCP authenticated only by the cookie. TLS distribution fixes that, but it brings certificate management and, in 2026, an allowlist-bypass CVE fixed in OTP 29.0.2 ([Erlang TLS distribution](https://www.erlang.org/docs/29/apps/ssl/ssl_distribution.html); [CVE-2026-48860](https://mondoo.com/vulnerability-intelligence/vulnerability/CVE-2026-48860)). Cross-node delivery stays at-most-once, and broadcasts to an unreachable node are dropped with nothing replayed. Presence would get worse. Tracker treats a node as down only after `down_period`, **30 s by default**, so a hard-killed node's Macs still look online to the phone for that long. Today a closed link reports offline at once on the instance that owns it ([Phoenix.Tracker docs](https://phoenix-pubsub.hexdocs.pm/Phoenix.Tracker.html)).

The wire protocol is the second constraint. Channels use their own `[join_ref, ref, topic, event, payload]` envelope and a `phoenix`-topic heartbeat, so they can't carry b4hub's `type`-tagged frames ([V2 serializer](https://raw.githubusercontent.com/phoenixframework/phoenix/main/lib/phoenix/socket/serializers/v2_json_serializer.ex)). Phoenix can serve the existing protocol through `Phoenix.Socket.Transport` or a plain Plug route with `WebSockAdapter.upgrade/4`, which keeps Bearer-token checks and JSON refusals before the upgrade ([Phoenix.Socket.Transport](https://phoenix.hexdocs.pm/Phoenix.Socket.Transport.html); [WebSockAdapter](https://websock-adapter.hexdocs.pm/WebSockAdapter.html)). That route skips Channels, the part of Phoenix most people mean when they recommend it. Two details remain unconfirmed: whether Bandit sends a `Set-Cookie` on the `101` response, and how WebSock returns custom close codes such as 4000. The other route is adopting Channels on the clients. SwiftPhoenixClient (about 530 stars) has no async/await or Swift 6 story, and the Swift 6 alternative, PhoenixNectar, is new and unproven ([SwiftPhoenixClient](https://github.com/davidstump/SwiftPhoenixClient); [Swift Forums](https://forums.swift.org/t/phoenixnectar-a-swift-6-client-for-phoenix-channels/85396)).

Scale doesn't break the tie. Phoenix's 2M-connection benchmark and its 2.3M reproduction put roughly 28–45 KB on each idle socket ([Phoenix blog](https://phoenixframework.org/blog/the-road-to-2-million-websocket-connections); [dsander benchmark](https://github.com/dsander/phoenix-connection-benchmark)). b4hub serves one owner with one Mac and one or two phones, on a 0.25 vCPU, 512 MB ARM64 task ([ecs.tf](../../Infra/modules/hub/ecs.tf), lines 60–66). That is five or six orders of magnitude below either runtime's limits. Discord's experience points the same way: even at 5M users, BEAM fan-out needed custom Manifold, FastGlobal, and Semaphore libraries ([Discord, 2017](https://discord.com/blog/how-discord-scaled-elixir-to-5-000-000-concurrent-users)). The free distribution is real, but at scale it takes work, and at b4hub's scale nothing calls for it.

## A port would trade proven Rust crates for thinner Elixir ones

An Elixir equivalent exists for every hub dependency, but their maturity varies.

| Need | Rust today | Elixir candidate | Health (hex.pm/GitHub, 2026-11-02) |
|---|---|---|---|
| Passkeys | `webauthn-rs =0.6.2` | `wax_` 0.7.0 | Last release 2025-05-18, one Hex owner, README says it has not been independently reviewed |
| Apple tokens, seals | `jsonwebtoken`, `aes-gcm` | JOSE 1.11.13 / Joken 2.7.0, OTP `:crypto` | Very mature (115M and 59M downloads) |
| APNs HTTP/2 | `reqwest` + cached ES256 | Pigeon 2.1.0, or Finch/Mint + JOSE | Pigeon moved to Mint on 2026-09-08; 30 open issues |
| Postgres | `sqlx =0.8.6`, checked queries | Ecto 3.14 / Postgrex 0.22 | Mature; no compile-time query checking |
| Rate limits | In-memory sliding windows | Hammer 7.5.1 | Active; ETS is per node, like today |

Sources: [wax_ on hex](https://hex.pm/api/packages/wax_) and [README](https://github.com/tanguilp/wax); [jose](https://hex.pm/api/packages/jose); [joken](https://hex.pm/api/packages/joken); [Pigeon changelog](https://github.com/codedge-llc/pigeon/blob/main/CHANGELOG.md) and [repo](https://api.github.com/repos/codedge-llc/pigeon); [ecto](https://hex.pm/api/packages/ecto); [postgrex](https://hex.pm/api/packages/postgrex); [hammer](https://hex.pm/api/packages/hammer); Rust pins from [Hub/Cargo.toml](../../Hub/Cargo.toml).

Sign-in is where the risk concentrates. Wax passes all 170 FIDO conformance tests and supports discoverable credentials, which covers Apple's attestation-"none" passkeys. Its own README still warns users to rely on it "at your own risks". Moving the hub's authentication onto that library would be a step down from `webauthn-rs`. The migration cost is also large. The hub has **about 19,600 lines of Rust tests and 425 passing tests** at the M8f gate ([verification.md](../../docs/verification.md), line 235). The 2,349-line relay suite runs on `tokio::time::pause`, so heartbeats, holds, and rate windows are deterministic ([relay/mod.rs](../../Hub/crates/b4hub/src/relay/mod.rs), lines 7–13). The research found no built-in virtual clock in ExUnit to port those tests onto. Ecto's SQL sandbox wraps every test in a rolled-back transaction, and that conflicts with code that depends on commit-time `NOTIFY` ([Ecto SQL Sandbox](https://ecto-sql.hexdocs.pm/Ecto.Adapters.SQL.Sandbox.html)). Elixir 1.20 now infers types across all constructs, but it has no user annotations yet, so wire contracts would rest on tests rather than types ([Elixir v1.20 release](https://elixir-lang.org/blog/2026/06/03/elixir-v1-20-0-released/)).

Operations would come out about even, and the tooling would expand. A `mix release` bundles ERTS and drops into the same multi-stage Docker image and ECS service. The release docs call hot upgrades "rarely a viable option", which is irrelevant here because deploys are immutable digests ([Mix.Tasks.Release](https://mix.hexdocs.pm/Mix.Tasks.Release.html)). Expect a higher idle memory baseline than the Rust binary, though only forum anecdotes put a number on it ([Elixir Forum](https://elixirforum.com/t/elixir-memory-usage/21444)). OpenTelemetry's Ecto instrumentation hasn't had a release since February 2024 ([opentelemetry_ecto](https://hex.pm/api/packages/opentelemetry_ecto)). The cost that matters most is people, not runtime. D-043 put the hub in Rust "so one toolchain and one set of habits serve both" it and the b4 codebase ([M8 hub design](../../docs/superpowers/specs/2026-10-31-m8-hub-design.md), line 142). Elixir would add a third language to the stack and a third decoder for the shared fixtures in `Tests/Fixtures/sync/`. The case studies that favour Elixir compare it with Java and Ruby, not with tokio. One solo maintainer rewrote a project out of Elixir to consolidate on the language they use every day ([Elixir Forum on Pinterest and Bleacher Report](https://elixirforum.com/t/elixir-saves-pinterest-2-million-year-other-marketing-examples/57909); [Farside](https://git.hackliberty.org/Git-Mirrors/farside/src/branch/main/go.mod)).

None of the partial-adoption options holds up either. A Phoenix edge in front of the Rust core is the Discord and Supabase shape, but for b4hub it would split one small service into two deployables with a shared auth and revocation contract ([Supabase Realtime architecture](https://supabase.com/docs/guides/realtime/architecture)). Its main payoff would be frame forwarding, which affinity was built to avoid needing. Phoenix.Sync and Electric are a different sync model: v0.6.1, beta, aimed at TypeScript, with no Swift client ([Phoenix.Sync](https://phoenix-sync.hexdocs.pm/readme.html)). Managed AWS options don't fit. API Gateway WebSockets cap messages at 128 KB, below the relay's 256 KiB frames, and close connections after 2 hours ([API Gateway quotas](https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-execution-service-websocket-limits-table.html)). AppSync Events is topic pub/sub metered in 5 KB units, not directed request and reply ([AppSync pricing](https://aws.amazon.com/appsync/pricing/)).

## The real multi-instance gap is a 25-second long-poll, not the relay

The research turned up a gap that no document records. The change long-poll wakeup is still an in-process `Notify` per org, and its own comment says "a second replica would need `LISTEN` / `NOTIFY` or the same signal over the database" ([notify.rs](../../Hub/crates/b4hub/src/notify.rs), lines 1–3). A push wakes only the pulls waiting on the same task ([routes/changes.rs](../../Hub/crates/b4hub/src/routes/changes.rs), lines 57–59 and 141–153). Part B left sync untouched because "HTTP push/pull is stateless" ([M8e Part B design](../../docs/superpowers/specs/2026-11-02-m8e-part-b-relay-routing-design.md), line 53). Stateless is correct; prompt is not. **With `task_count = 2`, a phone's pull parked on task B doesn't wake when the Mac's push lands on task A, and it returns only when its wait expires, capped at 25 s.** Whether this happens in practice depends on whether `HTTPHubAPI` requests carry the same ALB cookies as the link upgrade. That code has no explicit cookie handling, so treat the gap as an inference until a two-task test confirms it. Prod still runs one task, and the "next" tier is "Not yet `live-tested` on two tasks" ([deployment-architecture.md](../../docs/deployment-architecture.md), line 218).

The fix belongs in Rust and is small. Send `NOTIFY` with the org id in the push transaction (it is delivered only on commit, in commit order, under the 8,000-byte payload limit), hold one dedicated non-pooled `LISTEN` connection per task, and wake the local `Notify` when a ping arrives ([PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)). Pings sent while that connection is down are lost, the same caveat Postgrex documents for its own listener ([Postgrex.Notifications](https://postgrex.hexdocs.pm/Postgrex.Notifications.html)). The existing 25 s cap already acts as the polling fallback. `NOTIFY` takes a global lock at commit, which collapsed throughput for Recall.ai at tens of thousands of concurrent writers. Sources disagree on whether Postgres 19 removes that lock ([Recall.ai](https://recall.ai/blog/postgres-listen-notify-does-not-scale); [DBOS](https://dbos.dev/blog/postgres-listen-notify-scalability)). At one user's write rate the lock doesn't matter, and the hub already avoids RDS Proxy because of `LISTEN` pinning ([deployment-architecture.md](../../docs/deployment-architecture.md), line 158). Today no `LISTEN`, `NOTIFY`, or `PgListener` appears anywhere in `Hub/crates`.

The research also found stale or conflicting docs. `AGENTS.md` still says the relay's state "is in memory, so it is one process until M8e" ([AGENTS.md](../../AGENTS.md), line 31), and Part B made that false. The deployment doc's list of asks still plans "Cross-instance relay routing over `LISTEN/NOTIFY` on a dedicated connection" ([deployment-architecture.md](../../docs/deployment-architecture.md), line 273), which its own line 218 contradicts. The same doc says "the pool takes 20", but the code sets `max_connections(10)` ([b4hub-db/src/lib.rs](../../Hub/crates/b4hub-db/src/lib.rs), lines 107–109). D-085's accepted edges still apply: rate limits are per instance, and holds, in-flight commands, and pending threads are lost on a crash ([decisions.md](../../docs/decisions.md), D-085). One relay timing flake is on record ([verification.md](../../docs/verification.md), line 122). None of these needs a new runtime, but the long-poll fix and the two-task live test should come before prod's `task_count` goes to 2.

## Three conditions would reopen the question

**Live fan-out across users.** The M8 mandate describes a multi-tenant, enterprise-ready hub with SSO ([M8 hub design](../../docs/superpowers/specs/2026-10-31-m8-hub-design.md), lines 12–17). Affinity is keyed on the user. If org members ever watch one another's threads live, two users' links could sit on different instances and frames would have to cross between them. At that point the choice is between a broker for Rust (NATS core, Redis pub/sub, both at-most-once) and BEAM distribution, and Phoenix PubSub plus Tracker becomes a strong candidate for the relay alone ([NATS docs](https://docs.nats.io/nats-concepts/core-nats)). "Several Macs per user" doesn't trigger this, because all of one user's devices share an instance.

**Affinity failing in the field.** If the first live two-task run shows clients flapping between instances, sticky cookies being lost, or the `409` retry loop misbehaving, the cheapest way out of affinity has to be priced. That still doesn't automatically favour BEAM over a Rust broker.

**A change in the owner's stack.** D-043's case rests on sharing habits with the b4 Rust codebase. If b4 left Rust, or Elixir became the owner's or a future team's everyday language, the switching cost would fall sharply. Even then, the right scope would be a relay rewrite on a raw WebSocket that keeps the existing protocol, with the PostgreSQL-bound sync and sign-in staying in Rust.

Load is deliberately missing from this list. No plausible growth in users brings either runtime near its connection limits, so a traffic increase alone shouldn't reopen the decision.

## Conclusion

The comparison that matters isn't Rust against Elixir on throughput. It is *distribution as a primitive* against *affinity as a design*, and b4hub settled that on November 2 by choosing affinity, so the BEAM's main advantage now fills a need the hub doesn't have. b4hub already carries Phoenix's best idea: at-most-once realtime delivery on top of a durable log that clients catch up from. It got there through D-054 without the framework. Whether the BEAM ever pays off is now a product question, whether users will share live threads, more than an infrastructure one, and that is the signal to watch.

The next steps are concrete and runtime-neutral. Add a `LISTEN/NOTIFY` wakeup for the long-poll, verify whether HTTP requests share the link's ALB cookies, run the two-task live test, and correct `AGENTS.md`, the deployment doc's M8e ask, and the pool-size figure. Each of these is cheaper than the smallest Phoenix spike, and each one would still be needed if Phoenix were adopted.
