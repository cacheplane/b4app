# Ship iOS through TestFlight, keep Mac on Developer ID

The realistic plan for late 2026 is to keep the Mac app on Developer ID plus notarization and send only the iOS companion through TestFlight and the App Store. **TestFlight for Mac only takes a Mac App Store build:** that means Apple Distribution signing, an embedded Mac App Store profile, and App Sandbox on every executable in the bundle. Each pillar of b4app breaks under the sandbox. It cannot run user-installed `codex`, `claude` or `node`, because no sandbox extension grants execute permission. Bundled PostgreSQL cannot create its System V interlock segment. The app cannot write `~/Library/LaunchAgents`. The data-protection keychain does work in the Developer ID app without the Mac App Store, but it needs **two explicit App IDs** (`com.cacheplane.b4app` and a new `com.cacheplane.b4app.coordinator`), each with Keychain Sharing and its own **Developer ID provisioning profile**. The coordinator has to move from a bare Mach-O into an app-like wrapper bundle that can hold its profile, and both executables claim the same `keychain-access-groups` string. Unsigned `swift build` and test binaries must stay on the file-based keychain. The iOS app needs no new entitlements. It needs an App Store Connect record, an Admin-role team API key for headless cloud signing, `ITSAppUsesNonExemptEncryption`, a privacy manifest, a Release build without the `localhost` ATS exception, and a build number that changes on every upload. All of this fits in `project.yml` and the scripts without committing the team ID and without touching CI's `CODE_SIGNING_ALLOWED=NO` builds.

## Every Mac App Store path demands a sandbox that b4app's core features cannot survive

TestFlight for Mac and the Mac App Store go through the same App Store Connect ingestion. App Review Guideline 2.4.5(i) requires Mac App Store apps to be "appropriately sandboxed" ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). Ingestion rejects any executable without the sandbox entitlement with ITMS-90296, and nested helpers are the usual offenders ([Apple Developer Forums 41400](https://developer.apple.com/forums/thread/41400)). TestFlight also requires a Mac App Store distribution profile: without one the upload fails with ITMS-90889 ([Quinn, thread 733942](https://developer.apple.com/forums/thread/733942)). TestFlight also needs the restricted `com.apple.application-identifier` and `com.apple.developer.team-identifier` entitlements, so the same build cannot be both TestFlight-acceptable and locally runnable ([thread 769758](https://developer.apple.com/forums/thread/769758)). Apple has never offered a way to send a Developer ID, non-sandboxed build through TestFlight. The research found no WWDC25 or WWDC26 change. That is absence of evidence, but Apple would have announced such a change, so its absence is telling.

Sandboxing would remove three things the product needs. First, a sandboxed app's children inherit its sandbox. Apple DTS says there is "no way to get a dynamic sandbox extension that grants executable access", so `/opt/homebrew/bin/codex`, `~/.nvm/.../node` and `~/.local/bin/claude` are unreachable whatever the user consents to. DTS's only active recommendation for running developer tools is "to not sandbox your app" ([Quinn, thread 746478](https://developer.apple.com/forums/thread/746478)). Temporary-exception entitlements for `~/.codex` and `~/.claude` would not fix execution. App Review "typically reject[s]" them in any case ([thread 709333](https://developer.apple.com/forums/thread/709333)). Second, **PostgreSQL always creates a small System V shared memory segment** to interlock the data directory. The Darwin sandbox denies it with `shmget ... Operation not permitted`, and System V semaphores are the next failure ([pgsql-bugs, Walther](https://www.postgresql.org/message-id/a90b5411-705f-4286-bd81-a26c520a6cfb%40technowledgy.de); [Munro reply](https://www.postgresql.org/message-id/CA%2BhUKGJoOCA5PmhqU5P8gWe2Am%3DO-f0ubDjUed2kPuLRWe-UEg%40mail.gmail.com)). A sandboxed app may use POSIX IPC only under `<group id>/` names of 31 characters or fewer, and its Unix sockets must sit in the app group container ([App Groups Entitlement](https://developer.apple.com/tutorials/data/documentation/bundleresources/entitlements/com.apple.security.application-groups.md)). That rules out the `$TMPDIR` socket and an unpatched PostgreSQL. This evidence comes from Nix's and Claude Code's Seatbelt sandboxes, not from a test of an App Sandbox–entitled app, but they use the same kernel mechanism. Third, a sandboxed app can register an agent only through `SMAppService` with a bundled plist. Since macOS 14.2 that agent must itself be sandboxed ([release note quoted in thread 743395](https://developer.apple.com/forums/thread/743395)), and it needs an app group authorized by a profile in an app-like wrapper ([Quinn, thread 835003](https://developer.apple.com/forums/thread/835003)).

Two other options exist, and both are worse. A separate sandboxed edition is the dual-pipeline model that BBEdit and Fade In use ([9to5Mac](https://9to5mac.com/2019/02/25/bbedit-12-6-sandboxing-mac-app-store/); [Fade In KB](https://www.fadeinpro.com/kb/content/2/33/en/differences-between-the-mac-app-store-and-non_app-store-versions.html)). For b4app that edition would lose the Codex, Claude and B4 adapters, PostgreSQL and the coordinator. What remains is a hub client close to what the iOS companion already is. It would still face Guideline 2.5.2 risk, and 2.4.5(vii) forbids any non-store updater. Sandboxing the only Mac app removes the product's core function. The cheap way to get Mac testers onto TestFlight is to let the **iOS companion run on Apple silicon Macs**, which TestFlight supports ([Test iPhone and iPad apps on Macs with Apple silicon](https://developer-mdn.apple.com/help/app-store-connect/test-a-beta-version/test-iphone-and-ipad-apps-on-macs-with-apple-silicon)). Whether this app's frameworks behave well that way has not been tested. The decision should go into `docs/decisions.md` with these four reasons: user-CLI exec, SysV IPC, LaunchAgent writes, and the `$TMPDIR` socket.

## Two App IDs, two Developer ID profiles and one shared group unlock the data-protection keychain

On macOS, a program's data-protection keychain access groups come from its code-signing entitlements, in a fixed order. `keychain-access-groups` comes first, then `com.apple.application-identifier`, then App Groups, and **the first entry is the default group for `SecItemAdd`** ([Sharing access to keychain items](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps)). Those entitlements "must be authorized by a provisioning profile", and the program needs "an app-like bundle structure in which to embed that profile", which a command-line tool lacks ([TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)). `keychain-access-groups` is restricted so that other developers "can't impersonate your app in order to steal its keychain items" ([TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles)). Apple's support table lists Keychain Sharing and App Groups as available for **Developer ID** profiles ([Supported capabilities (macOS)](https://developer.apple.com/help/account/reference/supported-capabilities-macos/)). The documented route is an explicit `keychain-access-groups` value, and both executables claim the same one. An iOS-style `group.` App Group has been usable as a Mac keychain access group since February 2025, but Quinn says of it "I've not actually tried it" ([thread 721701](https://developer.apple.com/forums/thread/721701)). It also brings container-protection semantics the coordinator does not need.

| Entitlement (expanded, as written into the plist) | Outer app `Agent Workspace.app` | Coordinator wrapper `B4AppCoordinator.app` |
|---|---|---|
| `com.apple.application-identifier` | `GJJKL34HCT.com.cacheplane.b4app` | `GJJKL34HCT.com.cacheplane.b4app.coordinator` |
| `com.apple.developer.team-identifier` | `GJJKL34HCT` | `GJJKL34HCT` |
| `keychain-access-groups` | `[GJJKL34HCT.com.cacheplane.b4app.shared]` | `[GJJKL34HCT.com.cacheplane.b4app.shared]` |

The values are literal because `Scripts/package.sh` signs with `codesign`, not Xcode. `$(AppIdentifierPrefix)` is an Xcode build-setting expansion, and Apple's distribution example shows fully expanded values in the signature ([Creating distribution-signed code for macOS](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac)). The script already reads the team ID from the certificate (D-039), so it can generate both entitlements plists at package time with `plutil`, and the repository never contains `GJJKL34HCT`. The code should pass `kSecAttrAccessGroup` explicitly on every add and query rather than rely on ordering, and never pass an empty string, which fails with `errSecMissingEntitlement` ([Sharing access to keychain items](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps)). The table does not cover the `agent-workspace` CLI. It stays a bare Mach-O, cannot reach the data-protection keychain, and gets secrets through the coordinator.

### The coordinator becomes a nested app so it has somewhere to keep a profile

macOS looks for a profile only at `Contents/embedded.provisionprofile`. "A standalone executable can't claim a restricted entitlement because there's no place to embed the provisioning profile" ([TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles)). Each restricted-entitlement bundle gets its own profile. Apple's example gives an app and its share extension separate profiles that share a keychain group ([Creating distribution-signed code for macOS](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac)). Apple's daemon recipe is the model here. It is an app-shaped bundle with no app-specific Info.plist keys and the hardened runtime on, and launchd's `Program` points straight at `X.app/Contents/MacOS/X` ([Signing a daemon with a restricted entitlement](https://developer.apple.com/documentation/xcode/signing-a-daemon-with-a-restricted-entitlement)). A nested "help app" belongs in `Contents/Helpers/` ([Placing content in a bundle](https://developer.apple.com/documentation/bundleresources/placing-content-in-a-bundle)). The target layout:

```
Agent Workspace.app/Contents/
  embedded.provisionprofile                      # Developer ID profile for com.cacheplane.b4app
  MacOS/Agent Workspace
  Helpers/agent-workspace                        # bare tool, no restricted entitlements
  Helpers/B4AppCoordinator.app/Contents/
    Info.plist                                   # CFBundleIdentifier com.cacheplane.b4app.coordinator,
                                                 # CFBundleExecutable b4app-coordinator, CFBundlePackageType APPL,
                                                 # CFBundleName, versions, LSMinimumSystemVersion, LSUIElement true
    MacOS/b4app-coordinator
    embedded.provisionprofile                    # Developer ID profile for com.cacheplane.b4app.coordinator
  SharedSupport/postgres/...
```

`LSUIElement` is a precaution, not an Apple requirement. Keep the bundle identifier, the code-signing identifier and the App ID identical, because no source settles which of them AMFI compares. The D-042 LaunchAgent plist that the app writes must point `ProgramArguments[0]` at the wrapper's executable. The app must rewrite already-installed plists on upgrade. The CLI's coordinator lookup (D-040) must learn the new path.

Signing still goes inside-out, without `--deep`, as `package.sh` does today. Each profile is copied into place before its bundle is signed, so the seal covers it:

```sh
ID="Developer ID Application: … (${TEAM_ID})"           # TEAM_ID read from the certificate, as today
# 1. PostgreSQL Mach-Os (unchanged): --timestamp -o runtime, no entitlements
# 2. Bare CLI, with an explicit identifier
codesign -f -s "$ID" --timestamp -o runtime -i com.cacheplane.b4app.agent-workspace "$APP/Contents/Helpers/agent-workspace"
# 3. Coordinator wrapper
ditto "$B4APP_COORDINATOR_PROFILE" "$COORD/Contents/embedded.provisionprofile"
codesign -f -s "$ID" --timestamp -o runtime --entitlements "$TMP/coordinator.entitlements" "$COORD"
# 4. Outer app
ditto "$B4APP_APP_PROFILE" "$APP/Contents/embedded.provisionprofile"
codesign -f -s "$ID" --timestamp -o runtime --entitlements "$TMP/app.entitlements" "$APP"
# 5. Verify, notarize, staple (existing steps), then:
syspolicy_check distribution "$APP"
```

Apple's guidance supplies the extra details: `-i` for non-bundled code, `ditto` instead of `cp`, and no entitlements on library code ([Creating distribution-signed code for macOS](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac)). Moving off `cp -R` for the PostgreSQL tree also preserves its symlinks. Notarization accepts these entitlements: Developer ID profiles exist so that notarized apps can use restricted capabilities ([Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/)). Archive-plus-export is not worth adopting for the Mac. The helpers and PostgreSQL are added after the Xcode build, so the bundle would need re-signing anyway. And DTS confirms a known bug: "You can't cloud sign with a Developer ID cert when authenticating with an App Store Connect API key" ([thread 776036](https://developer.apple.com/forums/thread/776036)). The research did not find whether Xcode 26.x fixes it. The Developer ID certificate in the login keychain stays the signing source.

### Profiles outlive certificates, but an expired profile stops the app launching

**Developer ID profiles made after 22 February 2017 last 18 years**, and Gatekeeper checks them "at every app launch". If the profile expires, "the app will no longer launch". An expired certificate does not stop an app that was signed while it was valid, and a revoked certificate stops everything ([Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/)). Profiles created before that date were tied to certificate expiry, and in 2017 that broke shipping apps such as PDFpen ([Michael Tsai](https://mjtsai.com/blog/2017/02/18/fixing-and-explaining-pdfpen-8-3-1s-crash-on-launch/)). A profile lists its certificates, so renewing the Developer ID certificate means regenerating both profiles before the next build. Record both `ExpirationDate`s in `docs/compatibility.md` and have the package script fail when either is near.

There are two failure modes, and they look different. **Over-claiming** means the signature claims a group but the profile is missing, wrong or expired. The trusted-execution system SIGKILLs the process at exec ([Quinn, thread 706442](https://developer.apple.com/forums/thread/706442)), so a `KeepAlive` LaunchAgent would crash-loop. **Under-claiming** means no entitlement at all. The process runs, and keychain calls return -34018 ([errSecMissingEntitlement](https://developer.apple.com/documentation/security/errsecmissingentitlement)). The package script should catch both before notarizing. It should dump each bundle's claimed entitlements with `codesign -d --entitlements - --xml`, and decode each profile with `security cms -D -i` to confirm that its `Entitlements` cover the claimed `keychain-access-groups` and application identifier ([TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles)). The research could not confirm whether a Developer ID profile allowlists `GJJKL34HCT.*` or only named groups, so this check is the first thing to run on the real profiles.

## One-time migration and an entitlement check keep unsigned builds on the old keychain

No API moves an item between the file-based keychain and the data-protection keychain. SecItem calls default to the file-based keychain, and code reading old items "must target the file-based keychain" ([TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)). DTS describes the pattern in forum threads, which this research read only through search summaries ([thread 697317](https://developer.apple.com/forums/thread/697317); [thread 733767](https://developer.apple.com/forums/thread/733767)). Query the data-protection keychain in the shared group first. On `errSecItemNotFound`, read the same service and account from the file-based keychain. `SecItemAdd` the value into the shared group, then delete the legacy copy only after the add succeeds. Use `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, the class `KeychainSecretStore` already uses on iOS, so the agent can read at login without UI. The coordinator owns secrets and should run the migration idempotently per item. Expect one "wants to use your confidential information" prompt per legacy item. The file-based ACL trusts the old code identity, and the coordinator's identifier changes when it moves into the wrapper. That expectation comes from the ACL model rather than from Apple text. "Always Allow" is unnecessary, since the item is deleted straight after.

Unsigned `swift build` binaries and the `xctest` runner can never claim `keychain-access-groups`, so they keep the file-based path that D-008 introduced. The public `SecTaskCopyValueForEntitlement` returns the calling process's own entitlement value ([SecTaskCopyValueForEntitlement](https://developer.apple.com/documentation/security/sectaskcopyvalueforentitlement(_:_:_:))). That gives `WorkspaceSecrets` a clean selection order. An explicit override comes first. Next, the data-protection keychain, when the process's `keychain-access-groups` contains the expected group. Otherwise, the file-based keychain. The chosen backend is logged without values. A -34018 from the data-protection path should be a configuration error, not a silent fallback, or secrets fork between two stores. Apple neither recommends nor discourages self-inspection for this, and its behaviour under the hardened runtime on macOS 26 should be confirmed in the packaged build. The data-protection keychain is available only in a user login context ([TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)). An Aqua-session LaunchAgent qualifies. An SSH session or a LaunchDaemon does not. That is one more reason the CLI always goes through the coordinator. Because the Xcode-built Debug app is ad hoc signed, its entitlements file must stay empty. Claiming the group without a profile would get it SIGKILLed. The keychain entitlements appear only in `package.sh`'s Developer ID branch.

## The iOS companion needs an app record, an Admin API key and four plist fixes

**Signing needs no new certificate.** For automatically signed targets, `xcodebuild -allowProvisioningUpdates` "will create and update profiles, app IDs, and certificates" when given an App Store Connect key through `-authenticationKeyPath/-authenticationKeyID/-authenticationKeyIssuerID` (local `xcodebuild -help`, Xcode 26.6; [Xcode distribution docs](https://developer.apple.com/documentation/xcode/distribution)). When no local Apple Distribution certificate exists, Xcode cloud-signs. Cloud-managed certificates require the Account Holder or Admin role ([Cloud-managed certificates](https://developer.apple.com/help/account/certificates/cloud-managed-certificates)). The key must therefore be a **Team key with the Admin role**, because Individual keys "aren't able to use Provisioning endpoints". Only an Admin can generate one, and the `.p8` downloads exactly once ([Creating API Keys for App Store Connect API](https://developer.apple.com/documentation/appstoreconnectapi/creating-api-keys-for-app-store-connect-api)). The forum thread that documents the Mac bug reports cloud signing via API key working for iOS as "Apple Distribution (Managed)" ([thread 776036](https://developer.apple.com/forums/thread/776036)). The fallback is a manually created Apple Distribution certificate plus an App Store Connect profile. The Developer ID Application certificate cannot sign an iOS store build. The minimum role for upload alone was not confirmed. The iOS keychain needs nothing new either. Every iOS item is in the data-protection keychain. The default group is the application identifier that Xcode adds at signing, `GJJKL34HCT.com.cacheplane.b4app.ios`. Keychain Sharing matters only if an extension is added later ([Sharing access to keychain items](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps)).

The App Store Connect record is a new iOS app with name, primary language, bundle ID `com.cacheplane.b4app.ios`, SKU (for example `b4app-ios`) and user access. Creating it needs Account Holder, App Manager or Admin, and nothing can be added until the Account Holder signs the latest agreement ([Add a new app](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-a-new-app)). App names are unique per localization, so "Agent Workspace" may already be taken. Universal purchase does not apply, because it needs one shared bundle ID across platforms in one record. **Internal testing** reaches up to 100 App Store Connect users with no review. **External testing** reaches up to 10,000. The first build in an external group goes through Beta App Review, needs a Beta App Description and a feedback email, and every build expires after 90 days ([TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview); [Provide test information](https://developer.apple.com/help/app-store-connect/test-a-beta-version/provide-test-information)). External review is a real hurdle for a companion that does nothing without a paired Mac and a hub. A reviewer needs a reachable demo hub and an enrollment code, or the app will look broken. The research could not settle whether external TestFlight needs a privacy policy URL, because sources conflict. Check the Test Information page. The App Store listing does require one ([Manage app privacy](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy)), along with answers to the age-rating questionnaire ([Upcoming requirements](https://developer.apple.com/news/upcoming-requirements/)).

The bundle needs four changes. **`ITSAppUsesNonExemptEncryption = NO`** stops a compliance questionnaire on every upload. HTTPS through URLSession and the Keychain count as exempt OS encryption, though a year-end self-classification report may still apply ([Complying with encryption export regulations](https://developer.apple.com/documentation/security/complying-with-encryption-export-regulations); [ITSAppUsesNonExemptEncryption](https://developer.apple.com/documentation/bundleresources/information-property-list/itsappusesnonexemptencryption)). A **`PrivacyInfo.xcprivacy`** belongs in the app target's resources, with `NSPrivacyTracking` false, empty tracking domains, collected data types, and `NSPrivacyAccessedAPITypes`. Since May 2024, apps that use a required-reason API without declaring it "aren't accepted" ([Describing use of required reason API](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api); [Privacy manifest files](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files)). The local packages link statically, so any use counts as the app's own. A grep of the iOS-linked sources found none. Before the first upload, confirm the SQLite mirror does not stat its database (reason C617.1) and nothing reads `systemUptime` (35F9.1) ([NSPrivacyAccessedAPIType](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype)). The **ATS `localhost` exception** is a per-domain `NSExceptionAllowsInsecureHTTPLoads`. Apple lists that among exceptions that "require you to provide justification, and might trigger additional App Store review" ([Preventing insecure network connections](https://developer.apple.com/documentation/security/preventing-insecure-network-connections)). On a phone, `localhost` is the phone itself, so Release builds lose nothing by dropping it, and the exception should be kept in Debug only. Plain HTTP to LAN hubs would call for `NSAllowsLocalNetworking`, which needs no justification ([NSAllowsLocalNetworking](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking)). Any real-device connection to a LAN hub, HTTPS or not, needs `NSLocalNetworkUsageDescription` ([NSLocalNetworkUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nslocalnetworkusagedescription)). Finally, **version numbers**: `CFBundleShortVersionString` must be three integers and `CFBundleVersion` one to three. The build string uniquely identifies each upload ([CFBundleVersion](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion); [Upload builds](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds)). Today `project.yml` hardcodes `CFBundleVersion: "1"` in `info.properties`, so overriding `CURRENT_PROJECT_VERSION` changes nothing. Bind both keys to `$(MARKETING_VERSION)` and `$(CURRENT_PROJECT_VERSION)`. Then either stamp a monotonic number such as `git rev-list --count HEAD` and set `manageAppVersionAndBuildNumber` to false, or let Xcode manage it (the default). The 1024-pixel icon already present is enough, and the project already builds with Xcode 26 and the iOS 26 SDK, as required since 28 April 2026 ([Configuring your app icon](https://developer.apple.com/documentation/xcode/configuring-your-app-icon); [Upcoming requirements](https://developer.apple.com/news/upcoming-requirements/)).

For upload, Xcode 26.6's export `method` is `app-store-connect` (`app-store` is deprecated), and `destination: upload` sends the build straight from `-exportArchive` (local `xcodebuild -help`). `xcrun altool --upload-package --wait` with `--api-key/--api-issuer` remains a supported alternative that leaves a local `.ipa`. altool's retirement covered only Mac notarization ([Upcoming requirements](https://developer.apple.com/news/upcoming-requirements/); [Upload builds](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds)). `testFlightInternalTestingOnly: true` keeps routine builds away from external testers and the store. Processing finishes when Apple's email arrives, and Apple publishes no typical duration.

## A gitignored xcconfig carries the team ID while CI keeps building unsigned

XcodeGen expands `${VAR}` from the environment, but **an unset variable stays as literal `${VAR}` text** ([XcodeGen SpecFile.swift](https://github.com/yonaskolb/XcodeGen/blob/master/Sources/ProjectSpec/SpecFile.swift)). That makes `DEVELOPMENT_TEAM: ${B4APP_TEAM_ID}` fragile. The robust pattern is a committed xcconfig with an optional include, which produces no warning when the file is absent ([Adding a build configuration file](https://developer.apple.com/documentation/xcode/adding-a-build-configuration-file-to-your-project); [XcodeGen ProjectSpec](https://github.com/yonaskolb/XcodeGen/blob/master/Docs/ProjectSpec.md#config-files)). Settings in the pbxproj override xcconfig values, so `DEVELOPMENT_TEAM` and the base `CODE_SIGN_IDENTITY: "-"` must leave `settings.base` ([Cog Shared.xcconfig, community](https://forge.losno.co/chris/Cog/src/branch/main/Xcode-config/Shared.xcconfig)). The Mac target keeps ad hoc signing at target level, because `package.sh` re-signs it. Scripts pass `DEVELOPMENT_TEAM="$B4APP_TEAM_ID"` on the command line, which beats both.

```yaml
# project.yml (excerpt)
configFiles:
  Debug: Config/Signing.xcconfig
  Release: Config/Signing.xcconfig
settings:
  base:
    CODE_SIGN_STYLE: Automatic          # DEVELOPMENT_TEAM and CODE_SIGN_IDENTITY removed from base
targets:
  B4App-macOS:
    settings:
      base:
        CODE_SIGN_IDENTITY: "-"         # ad hoc; package.sh re-signs with Developer ID (D-039)
  B4App-iOS:
    sources:
      - path: Apps/iOS/B4App            # now also holds PrivacyInfo.xcprivacy
    info:
      properties:
        CFBundleShortVersionString: $(MARKETING_VERSION)
        CFBundleVersion: $(CURRENT_PROJECT_VERSION)
        ITSAppUsesNonExemptEncryption: false
        # NSAppTransportSecurity moves to a Debug-only plist or preprocessed Info.plist
```

```
// Config/Signing.xcconfig (committed)
DEVELOPMENT_TEAM =
#include? "Signing.local.xcconfig"     // gitignored: DEVELOPMENT_TEAM = <team id>
```

The iOS release script then runs these two commands, with the `.p8` read from a path outside the repo, such as `~/.appstoreconnect/private_keys/`, so that only the path appears in arguments:

```sh
xcodebuild archive -project B4App.xcodeproj -scheme B4App-iOS -configuration Release \
  -destination 'generic/platform=iOS' -archivePath build/B4App-iOS.xcarchive \
  DEVELOPMENT_TEAM="$B4APP_TEAM_ID" CURRENT_PROJECT_VERSION="$BUILD_NUMBER" -allowProvisioningUpdates \
  -authenticationKeyPath "$ASC_KEY_PATH" -authenticationKeyID "$ASC_KEY_ID" -authenticationKeyIssuerID "$ASC_ISSUER_ID"
xcodebuild -exportArchive -archivePath build/B4App-iOS.xcarchive \
  -exportOptionsPlist Config/ExportOptions-AppStore.plist -exportPath build/export-ios -allowProvisioningUpdates \
  -authenticationKeyPath "$ASC_KEY_PATH" -authenticationKeyID "$ASC_KEY_ID" -authenticationKeyIssuerID "$ASC_ISSUER_ID"
```

`ExportOptions-AppStore.plist` needs only four keys: `method` `app-store-connect`, `destination` `upload`, `signingStyle` `automatic`, and `testFlightInternalTestingOnly`. `teamID` defaults to the archive's team, so it never appears in the file (local `xcodebuild -help`, Xcode 26.6). CI stays as it is. `CODE_SIGNING_ALLOWED=NO` skips signing, so an empty team and missing profiles never matter, and Simulator builds sign ad hoc anyway. CI must never pass `-allowProvisioningUpdates`, which needs an account or key. That `CODE_SIGNING_ALLOWED=NO` also skips entitlement processing is inferred from the current green Mac build, not from an Apple statement. A future release job should run only when the key secrets exist, write the `.p8` to `$RUNNER_TEMP`, and write `Signing.local.xcconfig` from a secret, so forks skip it cleanly.

## Conclusion

The notes change the shape of the work. The App Store question is settled by the product's own architecture, not by App Review's discretion. Every feature that defines b4app on the Mac, from exec'ing user CLIs to running PostgreSQL, is technically impossible inside the sandbox, so no amount of entitlement justification would buy a Mac TestFlight build. The keychain work, which looked like a signing tweak, is really a bundle-structure change. The coordinator's move into `B4AppCoordinator.app` ripples into the LaunchAgent plist, the CLI's coordinator lookup, the file-based ACL migration prompts, and an 18-year expiry that becomes a hard launch dependency. That expiry is the easiest of these to forget, and the costliest when it lapses.

Three questions remain open and should be tested early on real artifacts rather than assumed. Does the Developer ID profile allowlist the specific `.shared` group or a team wildcard? Does `SecTaskCopyValueForEntitlement` behave under the hardened runtime on macOS 26? Can external Beta App Review exercise a companion that needs a hub? Internal-only TestFlight sidesteps the last one entirely, and for a personal tool it is likely the right default.
