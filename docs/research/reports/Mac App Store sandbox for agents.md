# Keep the agents outside the App Store sandbox

No: b4app as built cannot ship through the Mac App Store or TestFlight for Mac, and no entitlement, user consent flow, or App Review argument changes that. Both channels require App Sandbox on every executable in the bundle. Under the sandbox, **no mechanism grants execute permission outside the app's static allowlist**, so the user's `/opt/homebrew/bin/codex`, `~/.local/bin/claude` and `node` are unreachable. Every child process inherits the sandbox, with `HOME` remapped into the container. PostgreSQL fails on System V IPC. A LaunchAgent plist cannot be written. The `$TMPDIR` socket lands at a path too long for `sun_path`. The precedents agree. None of the third-party agent GUIs examined (T3 Code, the ChatGPT app that absorbed Codex, Claude desktop, Zed, Warp, Conductor) is on the Mac App Store, and none of those inspected is sandboxed. Xcode is in the store and runs Claude and Codex, but only because Apple's own app ships unsandboxed with private entitlements. To the owner's two direct questions: **b4app does not run its own `codex` and `claude`**; it spawns the user's installed binaries, which use the user's own logins and config. T3 Code works the same way and avoids the problem by never entering the store. The recommendation follows. The notarized Developer ID download from b4.run stays the only Mac build that runs agents. Any App Store or TestFlight Mac presence becomes a **sandboxed client of the hub** that sends turns through the M8c relay to a Developer ID Mac, and the cheapest version of that is the existing iOS app made available on Apple silicon Macs.

## b4app runs the user's own agents, as T3 Code does, while the vendors ship private copies

Today b4app owns no agent binary. The coordinator finds `codex` and `claude` on the user's machine and drives them over their native protocols: `codex app-server` JSON-RPC on stdio (D-011) and Claude Code's stream-json (D-002). It takes approval policy and sandbox mode from the user's own Codex configuration (D-012). The agents authenticate with whatever `codex login` or `claude auth login` the user already ran, and their sessions, MCP servers and skills live in the user's real `~/.codex` and `~/.claude`. That design is what the sandbox breaks, and it is also the one the most similar product uses.

**T3 Code is architecturally almost identical to b4app.** It controls agents "set up on your computer", authenticates each provider through that provider's own CLI login, and says it "works with your subscriptions" ([T3 Code GitHub](https://github.com/pingdotgg/t3code)). Its server launches `codex app-server` over stdio JSON-RPC and expects the Codex CLI on PATH and already signed in ([Mintlify T3 Code docs](https://www.mintlify.com/pingdotgg/t3code)). The answer to "how does this work for T3?" is that T3 never meets the sandbox. It ships through GitHub Releases, a Homebrew cask, winget, scoop, Nix and `npx t3@latest`, plus a hosted web app and mobile apps, and has no Mac App Store build ([T3 Code GitHub](https://github.com/pingdotgg/t3code)). Conductor follows the same model: it runs Claude Code, Codex and Cursor agents in parallel git worktrees ([Conductor](https://www.conductor.build/workflows/run-parallel-codexes)) and, by a third-party account, reuses the logins already on the machine ([codepick.dev](https://codepick.dev/en/guides/conductor-build-intro/)).

The agent vendors made a different choice: they bring their own binary. A local `codesign` and bundle inspection on the owner's Mac on 2026-11-01 found the following. ChatGPT.app 26.1023.51421, bundle id `com.openai.codex`, bundles `Contents/Resources/codex-cli/bin/codex` and its own `rg`, and declares `com.apple.security.app-sandbox = false`. That bundle id fits the July 2026 merger of the Codex app into ChatGPT for macOS ([Addigy](https://support.addigy.com/hc/en-us/articles/53439709931155-ChatGPT-and-Codex-Desktop-App-Merger-What-This-Means-for-Your-Fleet)). Claude.app 4.4212.0 has no sandbox key and keeps versioned Claude Code builds under `~/Library/Application Support/Claude/claude-code/`. Claude desktop also offers cloud and SSH sessions alongside local ones, and installs Claude Code on the remote host for SSH ([Claude Code desktop docs](https://code.claude.com/docs/en/desktop)). Zed installs its own `codex-acp` and `claude-agent-acp`, which vendors Claude Code, and uses that managed copy even when a global install exists ([Zed external agents](https://zed.dev/docs/ai/external-agents)). Xcode 26.3 and later download "Claude Agent" and "Codex" from Settings > Intelligence ([Apple Newsroom](https://apple.com/newsroom/2026/02/xcode-26-point-3-unlocks-the-power-of-agentic-coding)). The same local inspection found strings in Xcode 26.6 for overriding `CLAUDE_CONFIG_DIR` and `CODEX_HOME`, so Xcode isolates its copies from the user's terminal state.

| App | Mac App Store | Sandboxed | Agent binary | Login |
|---|---|---|---|---|
| T3 Code | No (GitHub, Homebrew, npx, web, mobile) | Not checked; Electron, outside the store | User's `codex`, `claude`, others on PATH | User's CLI logins |
| Conductor | No (direct download) | Not checked | User's Claude Code, Codex, Cursor | User's existing logins (third-party report) |
| ChatGPT (incl. Codex) | No (Developer ID) | **No** (`app-sandbox = false`) | Bundled `codex` in the .app | ChatGPT account |
| Claude desktop | No (Developer ID) | **No** | Downloaded Claude Code in Application Support | Claude account |
| Zed | No | **No** | Self-installed ACP adapters, ignores global installs | Provider login |
| Warp | No | **No** | User's shells, so anything on PATH | Warp account |
| Xcode 26.6 | **Yes** | **No**, plus private Apple entitlements | Downloaded Claude Agent and Codex, private config dirs | Separate in-Xcode sign-in |
| b4app today | No (Developer ID, D-051) | No (D-006) | User's `codex`, `claude`, `node` | User's CLI logins |

Every one of these still runs the native agent protocol, whether app-server, stream-json or ACP; none reimplements the agent loop on raw model APIs. The split that matters is user binary versus private copy, and the vendors' private-copy choice has a reason b4app would inherit. A private copy pins the protocol version and isolates config, which is also the only shape a sandboxed build could take. Nobody in the table has paired that shape with the sandbox. Xcode is the closest design, and it is unsandboxed: **Xcode 26.6 carries no `app-sandbox` entitlement** and holds dozens of `com.apple.private.*` entitlements (local inspection), so it proves nothing about what a third-party store app may do. No developer statement explaining any of these distribution choices was found.

## Five sandbox walls stand between b4app and the store

The first wall is execution, and it is absolute. Apple DTS: "There is currently no way to get a dynamic sandbox extension that grants executable access." An open panel or bookmark extends read and write, never execute. Tools in `/Applications` work only because that folder is in the static allowlist, and `/usr/bin` developer tools are `xcrun` trampolines that fail with "cannot be used within an App Sandbox" ([DTS, thread 746478](https://developer.apple.com/forums/thread/746478)). The `com.apple.security.files.user-selected.executable` entitlement sounds like the fix but is not. It lets an app *write* files that keep their execute bit ([Enabling App Sandbox, archived](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html)), and a developer who combined it with NSOpenPanel still could not run the chosen binary ([thread 677172](https://developer.apple.com/forums/thread/677172)). DTS's only active recommendation for apps that run developer tools is "to not sandbox your app" ([thread 746478](https://developer.apple.com/forums/thread/746478)). The same rule blocks repo-local executables: `./gradlew`, `node_modules/.bin/*` and `.venv/bin/python` cannot exec from a granted project folder. By inference from the `otool` case, an Xcode-supplied `/usr/bin/git` trampoline fails the same way; that was not tested for git.

The second wall is inheritance. A child "inherits the sandbox from its parent, and thus is subject to the same rules" ([DTS, thread 677025](https://developer.apple.com/forums/thread/677025)), and a bundled helper must carry exactly `app-sandbox` and `inherit` ([Embedding a helper tool in a sandboxed app](https://developer.apple.com/documentation/xcode/embedding-a-helper-tool-in-a-sandboxed-app)). `HOME` points into `~/Library/Containers/<bundle-id>/Data`, so an agent's `~/.codex` and `~/.claude` resolve to empty directories. The escape hatch, `temporary-exception.files.home-relative-path`, is now a rejection. In April 2026 App Review rejected PolyPilot, an agent-CLI app with a helper reading `~/.copilot/`, under Guideline 2.4.5(i) because the exception "is not permitted"; the fix was to drop it and copy the folder into the container once ([PolyPilot PR #578](https://github.com/PureWeen/PolyPilot/pull/578)). An Apple engineer describes temporary exceptions as a stopgap from before security-scoped bookmarks existed, which App Review "typically" rejects ([thread 709333](https://developer.apple.com/forums/thread/709333)).

The third wall is PostgreSQL. It always allocates a small System V shared-memory segment as a data-directory interlock, and on macOS it uses System V semaphores ([PostgreSQL 17 kernel resources](https://www.postgresql.org/docs/17/kernel-resources.html)). A developer who sandboxed Postgres 18 in February 2026 hit `semctl ... Operation not permitted`. DTS replied that System V IPC "doesn't have a good story regarding the App Sandbox" and that POSIX IPC works only under app-group-prefixed names ([thread 816782](https://developer.apple.com/forums/thread/816782)). A PostgreSQL committer confirms the interlock has no alternative on any Unix today ([pgsql-bugs, Munro](https://www.postgresql.org/message-id/CA%2BhUKGJoOCA5PmhqU5P8gWe2Am%3DO-f0ubDjUed2kPuLRWe-UEg%40mail.gmail.com)). Making it work means maintaining a PostgreSQL fork: remove the interlock, use named POSIX semaphores under `<group-id>/` names, and move dynamic shared memory to mmap. **No shipped sandboxed app embedding a PostgreSQL server was found.** Postgres.app itself is direct-download only.

The fourth wall is the background service. Guideline 2.4.5(ii) bars installing code in shared locations, (iii) bars running at login or after quit without consent, and 2.5.2 bars writing outside the container ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). D-042's app-written `~/Library/LaunchAgents` plist is therefore impossible. DTS calls "a sandboxed login item, as installed by Service Management" the only App Store-compatible approach ([thread 706112](https://developer.apple.com/forums/thread/706112)). Since macOS 14.2, an `SMAppService` agent registered by a sandboxed app must itself be sandboxed ([release note quoted in thread 743395](https://developer.apple.com/forums/thread/743395)). Login items are not relaunched after a crash.

The fifth wall is the socket and the CLI. A sandboxed listener must put its Unix socket in the app group container to be reachable by group peers ([thread 133543](https://developer.apple.com/forums/thread/133543)), and a sandboxed `$TMPDIR` is so deep that clients fail with `invalid argument` against the 104-byte `sun_path` ([DTS, thread 756756](https://developer.apple.com/forums/thread/756756)). An `agent-workspace` binary bundled in a store app must be sandboxed with `inherit`. Started from Terminal, such a tool "is immediately terminated with a sandbox initialization error" ([thread 771117](https://developer.apple.com/forums/thread/771117)). The CLI would have to ship separately, unsandboxed, through Homebrew or a pkg, the way BBEdit's store edition once shipped its tools as a separate installer ([BBEdit 12.6 notes](https://barebones.com/support/bbedit/notes-12.6.html)). It also could no longer spawn the coordinator, since the coordinator would be a login item only the app can register. Touching another app's group container from an unsandboxed process on macOS 15 and later can trigger an "access data from other apps" TCC prompt attributed to Terminal ([hermes-webui #1485](https://github.com/nesquena/hermes-webui/issues/1485)). Whether that prompt fires on `connect()` to a socket, rather than on file reads, is unconfirmed.

## Each sandbox-compatible workaround fixes one wall and leaves the agents crippled

The table below scores every architecture the research identified. Each one clears at least one wall. None restores the product's core function, which is an agent that runs the user's toolchain in the user's repo with the user's login.

| Mechanism | What it fixes | What it leaves broken | Review risk |
|---|---|---|---|
| Bundled `codex`/`claude` signed `app-sandbox` + `inherit` | Execution of the agent itself | Agent tools limited to `/bin`, `/usr/bin` system binaries; no Homebrew, nvm, cargo, repo scripts; container login; pinned versions | Low for bundling, but 2.4.5(iv)/(vii) forbid self-update |
| Security-scoped bookmarks for project folders | Read/write in chosen repos | Nothing in the repo can exec; dynamic grants to inherited children are untested | Low |
| `NSUserUnixTask` + Application Scripts shim | Runs the user's real `codex app-server` unsandboxed with pipes | User installs the script by hand; no PID, env or cwd control; breaks LocalServerService's identity rule | **High**: DTS calls it "not a general-purpose sandbox bypass" |
| Temporary exceptions (`home-relative-path`, SysV `sbpl`) | Access to `~/.codex`, `~/.claude`, possibly SysV IPC | Execution still blocked | **Rejected** for new submissions (PolyPilot, April 2026) |
| `SMAppService` login item + XPC/app-group socket | Background coordinator, CLI reachability | Coordinator still sandboxed; no crash relaunch; CLI shipped separately | Medium: consent toggle required by 2.4.5(iii) |
| SQLite/GRDB in the group container | Database | Reverses D-041 and rewrites WorkspaceStorage | Low |
| Remote execution through the hub (M8c relay) | All of them: agents run on an unsandboxed Mac | Needs a Developer ID Mac online (D-045 refuses offline turns) | Low technical risk; reviewer needs a live demo |

The Application Scripts route deserves a closer look, because it is the only sanctioned way to run unsandboxed user code. The SDK header says these classes "will execute them outside of the application's sandbox". A sandboxed app may read the `~/Library/Application Scripts/<code-signing-id>` folder but not write it ([NSUserScriptTask](https://developer.apple.com/documentation/foundation/nsuserscripttask)). `NSUserUnixTask` exposes stdin, stdout and stderr as file handles ([NSUserUnixTask](https://developer.apple.com/documentation/foundation/nsuserunixtask)). A user-installed `#!/bin/zsh -l` shim that runs `exec codex app-server` would therefore give a pipe-connected, unsandboxed Codex with the real PATH, `~/.codex` and login keychain. DTS endorses those mechanics for script attachment. It then warns that `NSUserScriptTask` "is intended to be used to implement script attachment, not as a general-purpose sandbox bypass mechanism" ([DTS, thread 794355](https://developer.apple.com/forums/thread/794355)). An app that does nothing until the user hand-installs an exec shim is exactly that bypass. No app was found that hosts an agent or any long-lived stdio server this way. Its behavior with long-lived bidirectional JSON-RPC on macOS 26 is also unverified.

The bundled-agent edition is the steelman, and it is technically buildable. Codex is Apache-2.0 native Rust with arm64 and x86_64 release archives ([openai/codex](https://github.com/openai/codex)). `claude` is a native single-file executable that "does not itself invoke Node" ([Claude Code setup](https://code.claude.com/docs/en/setup)), so neither agent needs a bundled Node. PolyPilot shows a bundled agent helper reaching review. Auth can work inside the container. Codex app-server exposes `account/login/start` for browser ChatGPT login with a localhost callback, a device-code variant, and API keys ([Codex app-server docs](https://learn.chatgpt.com/docs/app-server)). The browser flow listens on `localhost:1455` ([Codex auth](https://learn.chatgpt.com/docs/auth)), so the app would likely need `network.server` as well as `network.client`. The costs are steep. The agents could edit files in granted repos but not build, test or install packages, which are the jobs coding agents exist for. Users would sign in a second time inside the app, and their terminal sessions, MCP servers and skills would be invisible. Codex's own Seatbelt sandbox would be nested inside App Sandbox, which is untested and may force `danger-full-access`. Claude Code's Bun-compiled runtime likely needs JIT under the hardened runtime ([DEV Community](https://dev.to/frr149/claude-code-native-build-100mb-binary-to-ditch-node-for-good-2gi6)), which is also untested.

Licensing and cadence add two more costs. Claude Code is proprietary. Anthropic permits "preinstalling or running Claude Code in your products" only if "the Claude Code binary must not be modified" and each user authenticates with their own key or plan ([Claude Code legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). Store submission requires re-signing every nested executable with b4app's Team ID, and whether Anthropic counts a replaced signature as modification is unanswered. The same page bars third parties from offering their own claude.ai login or touching its tokens. It does allow a user "signing in to the unmodified Claude Code binary with their own Claude subscription", so any bundled copy must trigger Claude Code's own login flow. Cadence is the other cost. Anthropic warns that "a newly launched model can require a Claude Code version newer than the stable channel serves," and documents `DISABLE_UPDATES` for vendors who pin a version ([Claude Code setup](https://code.claude.com/docs/en/setup)). Codex app-server schemas are "specific to the Codex version you ran" ([Codex app-server docs](https://learn.chatgpt.com/docs/app-server)). A store build would wait on App Review for every model launch, while the Developer ID build follows the user's own updates.

## The relay turns a store build into a remote client, not a runner

The one architecture that clears every wall moves execution off the sandboxed machine. The sandboxed Mac build would hold no agents, no PostgreSQL, no coordinator and no socket. It would be a client of the hub, like the iOS companion. b4app is already shaped for this. D-046 has the iOS app read a SQLite mirror fed by the hub through an in-process `WorkspaceTransport`, so the SwiftUI shell is the same on both platforms. `WorkspaceProtocol`, `WorkspaceClient`, `WorkspaceUI`, `WorkspaceSync`, `WorkspaceMirror` and `WorkspaceSecrets` are all Foundation-level modules that link on iOS. The sandbox would cost the client only `network.client`, a container SQLite file and keychain items. The M8c relay is the missing half: it routes `turn.send`, `turn.interrupt` and `request.respond` to the owning Mac. Claude desktop's cloud and SSH sessions ([Claude Code desktop docs](https://code.claude.com/docs/en/desktop)) and T3 Code's hosted web and mobile apps ([T3 Code GitHub](https://github.com/pingdotgg/t3code)) are the precedents. In both, the UI that runs in restricted places drives agents that run somewhere unrestricted.

The limit is that a store client is useless alone. D-045 refuses a turn for an offline Mac, so the App Store Mac app does nothing unless a Developer ID b4app is running somewhere. That makes it a second window onto a Mac the user already has. App Review would need a demo hub, an account and a live runner, the same burden the earlier signing research flagged for external TestFlight review of the iOS app. There is a cheaper first step than a new Mac target. TestFlight already lets iPhone and iPad apps run on Apple silicon Macs ([Test iPhone and iPad apps on Macs with Apple silicon](https://developer-mdn.apple.com/help/app-store-connect/test-a-beta-version/test-iphone-and-ipad-apps-on-macs-with-apple-silicon)), and the store can offer the iOS app on the Mac the same way. That gives "b4app in the Mac App Store and in TestFlight for Mac" with no new code. A dedicated sandboxed macOS client target is worth building only if the iPad-style UI proves inadequate on the Mac.

The owner's four targets map onto this split cleanly once one rule is fixed: **only Developer ID and local builds run agents.**

| Target | Signing | Hub | Role |
|---|---|---|---|
| Direct download from b4.run | Developer ID, notarized, unsandboxed (D-051) | Prod, b4.run | The runner: agents, PostgreSQL, coordinator, CLI |
| App Store | Apple Distribution, sandboxed | Prod, b4.run | iOS companion, also offered on Apple silicon Macs; optionally a sandboxed Mac client later |
| TestFlight | Apple Distribution, sandboxed | Test hub | Same client builds for testers |
| Local | Ad hoc (`swift build`, Xcode Debug) | `localhost:8080` | Development runner and client |

Two consequences follow from the table. First, a TestFlight client on the test hub can relay only to a runner joined to the test hub. Testers therefore need the Developer ID download joined to the test hub. `agent-workspace hub join <url>` already takes the hub URL, so the runner does not need a separate beta build, but the app's own join flow and docs must let a tester pick the test hub. Second, a store-signed Mac client and the Developer ID runner must not share a bundle identifier. DTS traced a silently dead login item to Developer ID and App Store builds sharing bundle IDs ([thread 727785](https://developer.apple.com/forums/thread/727785)). Distinct IDs also keep their containers, keychain groups and App Store Connect records apart. Use something like `com.cacheplane.b4app.remote` for the client, and keep `com.cacheplane.b4app` for the runner.

## Conclusion

The sandbox question turns out to be a deployment-topology question. The research began by asking whether b4app could fit inside App Sandbox. It ends showing that b4app's value lies in running the user's own toolchain with the user's own credentials, and that is the exact capability App Sandbox exists to remove. The vendors who own the agents reached the same conclusion for their own apps. So the right response is not to fight the sandbox but to give each channel a role: sandboxed channels carry clients, and the notarized download carries the runner. That makes M8c the critical path for any App Store ambition. Without the relay, a store build can only read threads. With it, the App Store and TestFlight builds become thin front ends to the Mac the user already trusts. The bundled-agent edition stays a fallback with a known price list: a SQLite port that reverses D-041, a login-item coordinator, a separately shipped CLI, written permission from Anthropic, and agents that cannot run builds.

Record this as a decision that amends D-051: a store-distributed Mac build, if one ships, is a hub client and never runs agents. Several open points should be settled before anyone revisits the bundled path. Can Codex's Seatbelt sandbox nest inside App Sandbox? Does Claude Code's runtime run sandboxed? Do inherited children receive bookmark extensions? Does Anthropic treat re-signing as modification? No source answered any of these, and each could be settled in an afternoon with a test build rather than more reading.
