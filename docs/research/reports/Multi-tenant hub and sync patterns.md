# Build the Hub as a Device Router on Row-Level Tenancy

The state of the art for a hub that native Mac, iOS, and CLI clients sync with and act through is not a sync engine at all: it is a server-authoritative, append-only change log keyed by tenant and device, fronted by a thin device router, on a single shared PostgreSQL schema with forced row-level security. **No off-the-shelf local-first engine supports a Swift client that writes into a local PostgreSQL**; PowerSync is the only one with a production Swift SDK and it requires SQLite and routes writes through your own API, so the hand-rolled log (server-assigned cursor per device, hybrid logical clocks only on the few mutable metadata columns, per-column last-writer-wins with a device-id tie-break) is the mainstream answer and is exactly what Linear, Figma, and the vendor's own reference product converged on. Every comparable developer tool that lets a phone continue a Codex or Claude Code thread that lives on one Mac does it by treating the remote surface as a **"window into the running process"**: the owning machine stays online, the hub relays commands to it and events back, and if the process dies the remote view becomes a stale transcript until the same machine resumes it; none migrates a live shell, and hand-over to another machine exists only as a git-carried fork. For identity, the surviving pattern is to **own organizations, domains, memberships, invitations, devices, refresh-token families, and the SCIM endpoint in the hub** and bundle only a protocol-facing authorization server, because every bundled open-source IdP would otherwise force the hub to mirror that model; Dex is the smallest on-prem broker, Keycloak 26.8 the most complete, and Zitadel's AGPL relicensing makes it awkward to redistribute. Deployment converges on one image exposing `serve` and `migrate`, external Postgres by default with an `existingSecret` idiom, a `pre-install,pre-upgrade` Helm hook Job and a Compose `migrate` service calling the same subcommand, offline-verifiable licences, and a published client-skew window. The reference product's data-layer and chart conventions transfer almost verbatim to a Swift hub; its authorization, which trusts a caller-supplied `x-tenant-id` header and ships without row-level security, is the pattern to avoid.

## Shared schema with forced RLS wins for thousands-of-rows tenants

For tenants that are organizations holding users whose data is thousands of small rows, every vendor rule of thumb lands on one shared schema with a `tenant_id` column and row-level security. AWS states that **"Row-level security (RLS) is required to maintain tenant data isolation in a pool model with PostgreSQL"** and that RDS and Aurora support all three models (silo, bridge, pool) ([AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/best-practices.html)), while conceding that "the noisy neighbor phenomenon cannot be completely eliminated in a pool model" and that per-tenant metering needs application instrumentation ([AWS pool model](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/pool.html)). The alternatives pay costs that have nothing to do with data volume. Schema-per-tenant multiplies migrations by N and makes catalog operations scale with the whole database rather than the schema touched: a 2026 PostgreSQL 18.6 bug report describes `pg_dump --schema` calling `pg_get_sequence_data()` for every one of roughly **142,000 sequences** across hundreds of tenant schemas during daily per-schema backups ([BUG #19688](https://www.postgresql.org/message-id/19688-e90025dc375a22a3@postgresql.org)), and older threads report **12 minutes to dump a near-empty schema in a 20,000-schema database** ([pgsql-performance 2012](https://postgrespro.com/list/id/1337843209018-5709766.post@n5.nabble.com)). Database-per-tenant gives the strongest isolation and the simplest per-tenant restore (Neon markets per-project point-in-time restore "within seconds" ([Neon](https://neon.com/use-cases/database-per-tenant))) at the price of connection fragmentation, backups × N, and fleet migrations ([Bytebase](https://www.bytebase.com/blog/multi-tenant-database-architecture-patterns-explained.md)). The migration direction in the literature runs from RLS toward more isolation only when an enterprise contract demands it, and Citus's `isolate_tenant_to_new_shard` plus Microsoft's per-tenant choice at provisioning time are both ways to carve out the few tenants that need it while keeping `tenant_id` on every row ([Citus](https://docs.citusdata.com/en/stable/use_cases/multi_tenant.html); [Microsoft Learn](https://learn.microsoft.com/en-us/azure/sql-database/saas-tenancy-app-design-patterns)). No controlled benchmark compares the three models on one workload; the cost figures are anecdotal or vendor marketing, which is itself a finding: the choice is driven by operational shape, not throughput.

The single-tenant on-prem bundle should be a tenant count of one, not a second code path. GitLab is the only product-scale example found that documents this explicitly: **"GitLab Self-Managed and GitLab Dedicated legitimately run inside the default organization"** and `Current.organization` "is always set, falling back to the default organization when none applies" ([GitLab organization development](https://docs.gitlab.com/development/organization/)), with a rule that every table storing customer data must declare an immutable sharding key attributable to one organization ([GitLab sharding guidelines](https://docs.gitlab.com/development/organization/sharding/)). The installer creates the one organization row at first boot; the only deployment-specific code is "which tenant does this request belong to" (the sole org on-prem, the token's `org_id` in the cloud). This also turns every on-prem install into an RLS test bed where a missing tenant context surfaces as zero rows before it becomes a cross-tenant leak in the cloud. Do not disable RLS "because there is only one org."

The RLS mechanics have three documented footguns and one settled form. Superusers and `BYPASSRLS` roles always bypass policies, and **table owners bypass them too unless `FORCE ROW LEVEL SECURITY` is set**; referential-integrity checks "always bypass row security," so a cross-tenant unique constraint or foreign key is a covert channel; and policies that reference other tables can race ([PostgreSQL docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). AWS's sample sets a GUC per session and warns this "may be incompatible with server-side connection pooling such as pgBouncer" ([AWS Database Blog](https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/)), and PgBouncer's own matrix lists session `SET/RESET` as **"Never"** supported in transaction pooling ([PgBouncer features](https://www.pgbouncer.org/features.html)), so the tenant must be set with `SET LOCAL` or `set_config(..., true)` as the first statement of each request transaction. A PostgreSQL quirk makes the policy expression matter: after a custom GUC has once been set locally, `current_setting(name, true)` returns `''` rather than NULL on that backend ([pgsql thread](https://postgrespro.com/list/thread-id/2631762)), which is why Crunchy Data's form `org_id = NULLIF(current_setting('rls.org_id', TRUE), '')::uuid` bound `TO application` is the robust one: an unset or empty context matches no rows instead of throwing a cast error ([Crunchy Data](https://www.crunchydata.com/blog/row-level-security-for-tenants-in-postgres)). Performance is a non-issue once two rules are followed. Supabase's benchmarks show indexing the policy column took a policy from **171 ms to under 0.1 ms**, and wrapping a per-query-constant function in `(select ...)` took `has_role() = role` from **178,000 ms to 12 ms**; they also advise "Do not rely on RLS for filtering but only for security," meaning application queries keep an explicit `WHERE tenant_id = $1` so the planner hits the `(tenant_id, ...)` index directly and RLS stays a backstop ([Supabase RLS performance](https://supabase.com/docs/guides/troubleshooting/rls-performance-and-best-practices-Z5Jjwv)). Any export or backup path should run with `row_security = off`, which does not bypass policies but throws an error if a query would be filtered, so a scoped dump fails loudly instead of silently omitting rows ([PostgreSQL docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)).

The key convention follows from the sync layer rather than the database. Sync engines want client-generated, globally unique, single-column ids: PowerSync says "Each model used with PowerSync needs to have a UUID id column" and "does not perform any validation that IDs are unique" ([PowerSync Client ID](https://docs.powersync.com/usage/sync-rules/client-id)), and Electric's shapes are "single table only" with cheap equality filters ([Electric shapes](https://electric-sql.com/docs/guides/shapes)). That favours `id uuid PRIMARY KEY DEFAULT uuidv7()` (native in PostgreSQL 18, with `gen_random_uuid()` as the fallback on older on-prem servers) plus `tenant_id uuid NOT NULL` denormalized onto every synced table including leaf rows such as transcript lines, and a `(tenant_id, id)` index so tenant scans stay time-ordered ([Neon PG 18 UUIDv7](https://neon.com/postgresql/postgresql-18/uuidv7-support)). Composite primary keys are only required if a sharding layer demands them. `tenant_id` should be immutable; moving a conversation between organizations is a copy-plus-delete. With volumes this small, the highest-value investment is not a tenancy model change but a tested logical "tenant bundle" export and import (every table filtered by `tenant_id` under one `REPEATABLE READ` transaction), because that one path serves GDPR export, deletion verification, on-prem-to-cloud migration, and the shared schema's genuinely weak spot, per-tenant restore from a scratch instance. Whether erasure must also purge backups is a legal question no engineering source answered.

## Native and CLI clients should authenticate with PKCE, a device grant, and per-device token families

The standards are unambiguous and the shipping CLIs follow them. RFC 8252 says native apps **"MUST use an external user-agent"** and must not embed one, because an embedding app "can access the user's full authentication credential"; it requires authorization servers to accept loopback redirects at `http://127.0.0.1:{port}` on any port, recommends claimed `https` callbacks where possible, and says "the use of localhost is NOT RECOMMENDED" ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html)). RFC 9700 adds that **public clients MUST use PKCE with S256**, that "Refresh tokens for public clients MUST be sender-constrained or use refresh token rotation," that access tokens should be audience-restricted to one resource server, and that the password grant "MUST NOT be used" ([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)). The device authorization grant covers the headless and SSH case: the client polls with a default 5-second interval, must handle `slow_down` by adding 5 seconds, and user codes are low-entropy enough that servers must rate-limit guesses (an 8-character base-20 code is about 34.5 bits) and warn users they are authorizing a device ([RFC 8628](https://www.rfc-editor.org/rfc/rfc8628.html)). GitHub's CLI library tries **"Device flow... first, and the localhost server is used as fallback"** and notes GitHub "rotates refresh tokens on every refresh, so always persist the refresh token" ([cli/oauth](https://github.com/cli/oauth)); `gcloud` offers `--no-browser`, which prints a `--remote-bootstrap` command to run on a second trusted machine ([gcloud auth login](https://docs.cloud.google.com/sdk/gcloud/reference/auth/login)). For this project's three clients one authorization-server configuration serves all: a public client with PKCE required, redirect URIs of a claimed `https` callback (Apple's `ASWebAuthenticationSession.Callback.https(host:path:)` exists from **iOS 17.4 and macOS 14.4**, with a reverse-domain scheme fallback earlier ([Apple](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession/callback/https(host:path:).md))) plus `http://127.0.0.1:*` and `http://[::1]:*` for the CLI, and the device grant enabled for the CLI's remote case. Note that the `https` callback can fail on the Simulator with a "not associated with domain" error ([Apple forums](https://developer.apple.com/forums/thread/763621)).

Storage is settled on Apple platforms: set `kSecUseDataProtectionKeychain` to true, which Apple says "It's highly recommended" for all keychain operations and which makes the iOS accessibility classes apply on macOS without iCloud synchronization ([Apple](https://developer.apple.com/documentation/security/ksecusedataprotectionkeychain.md)), and store refresh tokens with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, whose items "do not migrate to a new device" and so never leave the machine via backup ([Apple](https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlockthisdeviceonly.md)). Two desktop products offer stronger models worth weighing. 1Password's CLI never holds the secret: on macOS the CLI and app both connect to an XPC service and "Authenticity of both is confirmed by verifying the code signature," authorization lasts 10 minutes of inactivity with a 12-hour cap and is revoked when the app locks ([1Password security model](https://www.1password.dev/cli/biometric-security)). This repository already has a code-signed coordinator process sitting between the CLI and everything else, so brokering hub credentials through it is a natural fit; the trade-off is that the CLI then only works while the app is installed and running, so a fallback keychain item signed by the same team is still needed. Tailscale's model is the right mental model for "per-device credentials": each machine generates a key pair, the control server "ties a node key to a human identity," keys expire by default after **180 days**, and "Revocation messages are delivered the moment the key is automatically rotated or manually disabled" ([Tailscale key management](https://tailscale.com/blog/tailscale-key-management); [Tailscale key expiry](https://tailscale.com/kb/1028/key-expiry)). Claude Code's Trusted Devices beta stores "Only the device's public key and basic metadata," lists every enrolled device, and "Removing a device revokes its credential immediately" ([Claude Code Remote Control](https://code.claude.com/docs/en/remote-control)). The practical minimum for a small team is a `devices` table with one refresh-token family per device (RFC 9700 rotation already produces the family), so "sign out device X" is "revoke that family," and the CLI token can carry narrower scopes than the desktop app. DPoP with a Secure Enclave key is the only widely specified way to actually bind a token to hardware, but which bundled IdPs support it for public clients was not verified, so treat it as a later hardening step.

The token contract that every shipping product uses puts **exactly one active organization in a token**. Auth0 includes `org_id` by default, scopes `permissions` to "only the roles held within the active Organization," and tells API authors "Your API servers must also segment access to data and resources based on the `org_id`" ([Auth0](https://auth0.com/docs/manage-users/organizations/using-tokens)); WorkOS's session JWT carries `sub`, `sid`, `org_id`, `role`, `permissions`, switches organizations by refreshing with `organization_id`, caps rendered templates at **3,072 bytes**, and recommends resolving permissions from `sub` and `org_id` server-side rather than trusting claims ([WorkOS sessions](https://workos.com/docs/authkit/sessions.md); [WorkOS FGA](https://workos.com/docs/fga/authkit-integration.md)). Keycloak and Zitadel can instead list all memberships in one claim, which grows with the user ([Zitadel claims](https://zitadel.com/docs/apis/openidoauth/claims)). The recommended contract for the hub is therefore `iss`, `aud` = the hub API, `sub`, one `org_id`, that org's roles, `sid`, and a hub-issued `device_id`; the on-prem single-org deployment carries the same `org_id`, just constant. Membership should be re-read from the hub's own tables on sensitive writes, and the `org_id` from the verified token, never a request parameter, drives the `SET LOCAL` in the previous section. That is the exact binding the reference product lacks.

## Own the organization model in the hub; bundle only a thin OIDC broker

Every product surveyed keeps organizations, verified domains, SSO connections, invitations, and roles inside the product and exposes the customer's IdP as a per-organization attribute. The data model to copy is Organization → verified Domains (unique per deployment) → each Domain optionally bound to an OIDC or SAML connection with an auto-redirect flag, plus Invitations as the out-of-band override, and an identifier-first login screen that routes by email domain. Keycloak 26.8, released 2026-10-01, moved exactly here: "Identity providers can now be linked to multiple organizations" and **"Domain routing has been moved from the identity provider to the domain entity"** ([Keycloak 26.8.0](https://www.keycloak.org/2026/10/keycloak-2680-released)); Zitadel derives the organization from the login name, auto-redirects when an org has one external IdP and no password login, and keeps "all unmatched users" in a default organization ([Zitadel domain discovery](https://zitadel.com/docs/guides/solution-scenarios/domain-discovery)). WorkOS supplies the guardrails: "Only one organization can hold a given verified domain," consumer domains such as gmail.com are rejected for domain claims, guests on unverified domains "have to be invited first," and email domain should not be the tenant boundary, so validation keys on organization ID ([WorkOS access decisions](https://workos.com/blog/how-workos-decides-organization-access); [WorkOS AuthKit](https://workos.com/blog/add-sso-b2b-saas-authkit)). Identifier-first UI is a hard requirement rather than a nicety: Keycloak, Zitadel, Ory, and Auth0 all gate per-org routing on it ([Auth0 identifier first](https://auth0.com/docs/authenticate/login/auth0-universal-login/identifier-first)). The on-prem single-org install skips discovery (one org, one domain list, one connection, auto-redirect on) through the same code path.

SCIM belongs in the hub too, and the minimum viable surface is small. Entra requires POST/GET/PATCH on `/Users` and `/Groups`, filtering by `userName` and `externalId`, `excludedAttributes=members` on groups, soft-delete via `active=false` ("The user object should be returned in a request whether or not the user is active"), `/Schemas`, `/ServiceProviderConfig`, `/ResourceTypes`, and "a single bearer token"; PATCH `op` values arrive as `Add`/`Replace`/`Remove` so matching must be case-insensitive ([Microsoft Learn](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups)). Okta sends `GET /Users?filter=userName eq "..."` before every create, pages with `startIndex` and `count=100` requiring "the same ordering of results," and **"doesn't perform DELETE operations on user objects"** ([Okta SCIM 2.0](https://developer.okta.com/docs/api/openapi/okta-scim/guides/scim-20/)). Google Workspace "does not push SCIM events," so it needs a pull adapter or JIT provisioning on first login ([WorkOS Directory Sync](https://workos.com/blog/directory-sync-beyond-scim)). The SCIM token must be scoped to one organization so provisioned users land as that org's managed members and deprovisioning is bounded. The public cloud adds, on top of the shared core, identifier-first self-registration with **email verification enforced before any domain-based auto-join** (otherwise anyone can claim membership in an org whose domain matches), a default personal org for consumer domains, an outbox of domain events (`user.created`, `org.created`, `membership.changed`, `device.registered`) emitted by the hub rather than the IdP because Keycloak's event SPI misses API-created users ([Keycloak Discourse](https://keycloak.discourse.group/t/user-creation-through-keycloak-rest-api-doesnt-produce-register-event-for-spi/12333)), and layered signup abuse controls: Stripe's guidance is rate limits by IP, account, device, and email domain plus MX and disposable-domain checks before progressive verification ([Stripe](https://stripe.com/de-li/resources/more/how-to-prevent-free-trial-abuse-in-saas-and-ai-products)), and Arcjet's reference blocks invalid, disposable, or MX-less addresses with a 5-per-10-minutes-per-IP example limit ([Arcjet](https://docs.arcjet.com/signup-protection/reference)). The device-code verification page needs the same protection, since anyone can start a device flow against a public issuer.

What is worth bundling is the protocol-facing authorization server (OIDC with PKCE, device grant, refresh rotation, JWKS, and OIDC/SAML brokering to the customer's IdP), because writing a correct SAML SP and an OIDC AS is where a small team loses months and inherits security-review burden. The comparison below is the basis for the recommendation; footprint figures come from one single-VPS measurement and vendor sizing, and disagree with other third-party numbers by 2× or more, so treat them as ordinal.

Offer Keycloak as the alternative image for customers who already standardize on it, and never expose a bundled IdP's admin UI to tenants. Notably, none of the product charts surveyed (Coder, GitLab, Supabase, Mattermost, Sourcegraph) bundles a third-party IdP; each ships its own user store plus federation, and the one platform suite that does bundle Keycloak, Camunda, still recommends an external instance for production ([Camunda](https://docs.camunda.io/docs/self-managed/deployment/helm/configure/authentication-and-authorization/using-external-keycloak)). Every one of the five candidates publishes `linux/arm64` images, verified directly against the registries, so Apple Silicon development is not a differentiator. No source compares total engineering effort of building the AS in-house against bundling; the recommendation is a judgement from feature, licence, and footprint facts.

## No engine fits a Swift client on local Postgres, so hand-roll a server-ordered log

The engine survey eliminates itself quickly against this product's hard constraints. PowerSync has a supported Swift SDK (iOS 15, macOS 12; natively Swift since v1.14, HTTP only), but its client store is SQLite with the schema applied as views over JSON, every write goes to an upload queue that your `uploadData` endpoint applies to Postgres, and the service is under the Functional Source License converting to Apache 2.0 two years after each release with a "Competing Use" prohibition before then ([PowerSync Swift SDK](https://docs.powersync.com/client-sdk-references/swift); [powersync-service LICENSE](https://raw.githubusercontent.com/powersync-ja/powersync-service/main/LICENSE)). Adopting it means SQLite on macOS too and no reduction in write-side authorization work. ElectricSQL is Apache 2.0 and its protocol is plain HTTP (`GET /v1/shape` with `offset` and `handle`, long-poll with a **45-second default timeout** or SSE), but the official clients are TypeScript and Elixir; the only Swift consumer is a 20-star community package whose README says initial sync "is a bit slow... and needs a bit of attention," and "Electric does not do write-path sync" ([Electric TypeScript client](https://electric.ax/docs/api/clients/typescript); [ElectricSync](https://github.com/paulharter/ElectricSync); [Electric writes](https://electric.ax/docs/guides/writes)). Zero reached general availability in March 2026 but documents no Swift client and rejects offline writes outright because "the cost to support offline is extremely high" ([Zero status](https://zero.rocicorp.dev/docs/status); [Zero offline](https://zero.rocicorp.dev/docs/offline)); Replicache's repository was **archived on 10 June 2026** ([rocicorp/replicache](https://github.com/rocicorp/replicache)); Ditto has a Swift SDK and HLC-based CRDTs but no Postgres connector and self-managed servers only at the Enterprise tier ([Ditto pricing](https://ditto.com/pricing)); Turso's Swift SDK is "currently in technical preview" and its sync unit is a whole database ([libsql-swift](https://github.com/tursodatabase/libsql-swift)); Automerge and Yjs are document CRDTs whose Swift bindings are unstable or incomplete ([automerge-repo-swift](https://github.com/automerge/automerge-repo-swift); [yswift](https://github.com/y-crdt/yswift)). The credible middle path is Electric for the read path with a hand-written Swift shape consumer, plus your own write API; Electric's documented "through-the-DB sync" pattern (immutable synced table, shadow table for local changes, merging view, change-log triggers) is essentially the hand-rolled design with the download half replaced ([Electric writes](https://electric.ax/docs/guides/writes)). That is worth prototyping only if the Postgres-target sync on the Mac proves valuable; otherwise the simpler plan is to own both halves.

The teams that built their own converged on one architecture and the same pitfalls. Figma's server keeps the latest value per property per object so "changes are atomic at the property value boundary," object IDs embed a client ID so creation works offline, and reconnect downloads a fresh copy and reapplies offline edits ([Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). Linear keeps an immutable ordered log of sync actions per workspace above the Postgres WAL, has returning clients send a checkpoint, and learned that the read path breaks first: the largest workspaces produce **close to one million sync actions per day**, clients offline a few hours return "hundreds of thousands of actions behind," the store exceeds 20 TB, and the lesson is that **"storing a change log and serving a change log are different problems"** ([Linear](https://linear.app/blog/rebuilding-delta-sync-read-path)). Replicache's generic design, per-client sequential mutation IDs with a server-stored `lastMutationID` so "a change is never applied twice," is the idempotency primitive to copy ([Replicache](https://doc.replicache.dev/concepts/how-it-works)); the reverse-engineered Linear client documents the bug you get without it, where "some transactions are not idempotent" and a resend after a crash tries to delete an already-deleted model ([reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine)). cr-sqlite's change table (`col_version`, `db_version`, `site_id`, causal length) is the row-level template for per-column versions with a writer id ([crsql_changes](https://vlcn.io/docs/cr-sqlite/api-methods/crsql_changes)). For the clock, HLC packs 48 bits of physical time and 16 bits of counter so timestamps respect happened-before while staying within clock uncertainty of wall time ([Demirbas](https://muratbuffalo.blogspot.com/2014/07/hybrid-logical-clocks.html)); a practical string encoding is a zero-padded millisecond timestamp, a base-36 counter, and a node id joined so plain string comparison orders them, with the advice to check client timestamps server-side and flag drift ([Forsyth](https://jaredforsyth.com/posts/hybrid-logical-clocks/)). The server must clamp or reject HLCs far in the future, otherwise one skewed device's writes beat everyone's forever. Tombstones can only be dropped once every replica has seen them or been forced to resync; Cassandra's `gc_grace_seconds` defaults to ten days and a node down longer resurrects deleted data ([Cassandra](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/compaction/tombstones.html)), Ditto uses 7 days on edge and 30 in the cloud ([Ditto delete](https://docs.ditto.live/crud/delete)), and the clean implementation is a per-tenant horizon where any cursor older than it receives `resync_required` ([baukit-sync](https://docs.rs/crate/baukit-sync/latest)).

The synthesis that matters for this product is that most of its data does not need merging at all. A Codex or Claude Code thread is an append-only transcript with exactly one writer, the coordinator on the owning Mac, which this repository already enforces by making `SessionService` the only writer of turns and display items. An append-only, single-owner turn log needs a server-assigned monotonic cursor (Linear's sync id, PowerSync's op_id, Electric's offset) and idempotent per-device sequence numbers, but no HLC and no LWW; vendors of conversation tools avoid merging entirely by forking or by single-writer rules. HLC plus per-column LWW with a device-id tie-break is needed only for the small mutable surface: thread titles, archive and pin flags, and user settings. Even there, LWW is wrong for counters, ordered lists, rich text, and structural moves, where it "silently drops updates" by definition ([arXiv 2602.19231](https://arxiv.org/pdf/2602.19231)); those should be modelled as increments in the log, fractional indices, or a CRDT document column. Secrets are a third class that never enters the log, which `SecretStore` references already guarantee. For schema evolution no engine solves mixed-version sync; the minimum is a schema version stamped on every batch, additive-only changes that old clients tolerate by ignoring unknown columns, a server minimum-supported-client-version that forces re-bootstrap, and destructive changes staged as expand, dual-write, backfill, contract. Replicache's choice to include `schemaVersion` on every push and pull and to make upgraded clients "download a new copy of the data" rather than migrate local state is "much more robust than trying to migrate" ([Replicache launch checklist](https://doc.replicache.dev/howto/launch)), and Zero's warning that without event triggers "any schema change triggers a full reset of all server-side and client-side state" shows the cost of getting this wrong ([Zero Postgres](https://zero.rocicorp.dev/docs/connecting-to-postgres)). On transport, both vendors with Swift SDKs chose HTTP long-poll or streaming over WebSockets for Apple platforms, Notion abandoned periodic polling because it "wouldn't scale to millions of users and devices" in favour of per-page push channels ([Notion](https://www.notion.com/blog/how-we-made-notion-available-offline)), and none relies on push alone: a durable `GET /changes?cursor=…` long-poll with an opaque per-device cursor plus a contentless "poke" accelerator is the shape to copy. Every read filter must derive server-side from token claims; PowerSync states flatly that client parameters "should not be used for access control purposes" ([PowerSync Sync Rules](https://docs.powersync.com/usage/sync-rules)), and the write endpoint should stamp `org_id`, `user_id`, and `device_id` from the token rather than the payload.

## Machine-bound sessions need a device router, not a merge algorithm

Comparable tools split into three tiers on what they sync. Claude Code stores sessions locally as JSONL with 30-day default retention and uploads a transcript only while Remote Control is connected, when it "keeps the conversation in sync across your devices and lets the session reconnect after a network drop" ([Claude Code sessions](https://code.claude.com/docs/en/sessions.md); [Remote Control](https://code.claude.com/docs/en/remote-control)); GitHub Copilot CLI "by default syncs sessions to your GitHub account" ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/chronicle)); Warp syncs agent conversations only when a privacy setting is on ([Warp](https://docs.warp.dev/agents/local-agents/cloud-conversations.md)). Codex has no official cross-device story for local CLI sessions as of mid-2026; a community thread offering a `.codexbundle` export warns bundles "may contain prompts, code, terminal output, absolute paths, and secrets" ([openai/codex discussion](https://github.com/openai/codex/discussions/28140)), and Cursor and Zed sync neither settings nor chat history ([Cursor forum](https://forum.cursor.com/t/we-need-ability-to-sync-settings-between-devices/153503); [Zed community](https://github.com/zed-industries/community/issues/952)). Secret handling ranges from "prevent upload" (Raycast: "Credentials and passwords are never synced" ([Raycast](https://manual.raycast.com/cloud-sync.md))) through best-effort scrubbing (Copilot "might not detect every secret" ([VS Code](https://code.visualstudio.com/docs/agents/run/sessions/session-history.md))) to explicitly unprotected (Warp: "Secret Redaction isn't applied to Session Sharing" ([Warp](https://docs.warp.dev/agent-platform/local-agents/session-sharing/))); a store-by-reference design is stricter than any of them. Per-item size limits for large tool outputs are an unaddressed design space in every product's documentation, so budget for one.

Continuing a machine-bound thread from another device has exactly one production answer in 2026: the **live window**. Claude Code states that "The web and mobile interfaces are a window into that local session, so your computer has to stay on and the `claude` process has to keep running"; sessions show a green dot when online, go offline when the process stops, can be reattached "for about four hours after the server stopped," and a second terminal resuming the same conversation gets "Remote Control not started here" rather than stealing it ([Remote Control](https://code.claude.com/docs/en/remote-control)). Copilot CLI is read-only on GitHub.com unless remote control is enabled, "The CLI session must be actively running in a terminal on a machine with an internet connection," session events are sent to GitHub and **the CLI polls for commands**, and when both surfaces are active "the first response to a prompt or permission request is the one Copilot uses" ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-remote-control)). Codex's mobile preview keeps "the machine's files and credentials... local, while updates flow back to your phone in real time," an eligible task can fall back to a cloud container that "can't reach your files or tools," and "Work can't switch from local to cloud execution during a turn" ([OpenAI blog](https://openai.com/blog/work-with-codex-from-anywhere); [learn.chatgpt.com](https://learn.chatgpt.com/docs/projects)). Hand-over to a different machine exists only as a fork carried by git: Claude Code `--teleport` is one-way, requires clean git state and a pushed branch, and "The terminal gets its own copy of the session" ([Claude Code cloud](https://code.claude.com/docs/en/claude-code-on-the-web.md)); Cursor's "Move to Cloud" "does not snapshot your local uncommitted changes" ([Cursor](https://cursor.com/help/ai-features/cloud-agents)); opening a Warp conversation on two machines "creates independent branches" ([Warp](https://docs.warp.dev/agents/local-agents/cloud-conversations.md)). No product documents what happens to a pending permission prompt when the owning machine disconnects mid-prompt, and status indication is binary everywhere. Two further observations shape the opportunity: **no surveyed product offers a self-hostable sync hub** (VS Code: "Custom backends are not supported" ([VS Code](https://code.visualstudio.com/docs/configure/settings-sync.md)); Tailscale's coordination server is proprietary with Headscale an independent community project ([Tailscale](https://tailscale.com/opensource))), and enterprise controls are coarse kill-switches plus SSO rather than per-category policy. Self-hosting the hub itself is a differentiator against every tool here.

The routing design to borrow is, perhaps surprisingly, the reference product's realtime contract, which already solves "clients act through an executing process they do not host." Its contract declares that PostgreSQL "is the source of truth for durable thread history," that a Redis replay list per thread "is a replay cache for websocket reconnects, not the authoritative REST read model," and that the live metadata feed is "live-only" so clients fetch lists via REST and apply incremental updates (reference repo: `docs/thread-realtime-contract.md`). A `POST /api/threads/:threadId/connect { lastSeenEventId? }` negotiation returns `204` when the cursor is current and no run is active, a `bootstrap` snapshot when idle, or a `live` mode with a short-lived join token when a run is active, reusing the client cursor only when it falls inside the replay window (reference repo: `apps/app-api/src/routes/threads-routes.ts`); the replay list has a 4-hour TTL, join tokens 300 seconds, and a per-thread `SET NX` lock holds the active run id (reference repo: `apps/realtime-gateway/lib/realtime_gateway/consumers/redis_writer.ex`). On join the gateway captures a high-watermark, replays `(last_seen, high_watermark]` from Redis or Postgres, buffers live broadcasts meanwhile, and flushes only those after the watermark (reference repo: `apps/realtime-gateway/lib/realtime_gateway/client/replay.ex`). Events are deduplicated on `(tenant_id, event_id)` with `ON CONFLICT DO NOTHING`, a client `stop_run` is written to Redis and relayed to the runner socket, and a runner disconnect without a terminal event synthesizes a `RUN_ERROR` with code `RUNNER_CONNECTION_DROPPED` (reference repo: `apps/realtime-gateway/lib/realtime_gateway/sources/runner_channel.ex`). Mapped onto this product, the owning Mac's coordinator is the "runner": it holds an outbound, hub-authenticated connection; the hub addresses commands (new turn, interrupt, approval response) to a `device_id`, the coordinator executes them against Codex or Claude Code through its existing adapters, and emits the resulting `AdapterEvent`s back as the thread's append-only log, which the hub persists under the tenant and fans out to the iOS app and CLI. The recommended semantics are the live-window plus read-only mirror: when the owning device is online, remote clients steer it with first-responder-wins on prompts; when it is offline, the thread renders from the durable log with an explicit "last seen on <device>" status richer than today's binary dot. The open trade-off is command queueing. Queueing new turns to an offline device risks executing stale instructions hours later, which is why neither Claude Code nor Copilot does it; a defensible middle is to reject new turns with an explicit offline error and queue only interrupt and approval responses with a short TTL. True hand-over to another Mac should be modelled honestly as a fork, exactly as teleport and Move to Cloud do, with git as the carrier of repository state.

Settings sync is the one place where the merge literature does apply, and the user-visible failure mode is the same everywhere: a stale device coming online overwrote the good copy (VS Code #183485, JetBrains IJPL-200976, Raycast's documented re-enable behaviour, Obsidian on iPhone), followed by "a toggle that shouldn't have synced did" (Warp #6692, reopened by the CEO) ([microsoft/vscode #183485](https://github.com/microsoft/vscode/issues/183485); [YouTrack IJPL-200976](https://youtrack.jetbrains.com/issue/IJPL-200976); [Raycast](https://manual.raycast.com/cloud-sync.md); [warpdotdev/warp #6692](https://github.com/warpdotdev/warp/issues/6692)). The mitigations vendors actually shipped are server-side version history with restore (VS Code keeps "the latest 20 versions of each data category" ([VS Code](https://code.visualstudio.com/docs/configure/settings-sync.md))), a visible last-synced time per device, an explicit Push/Get choice on first enable, and, Obsidian's answer, keeping sync preferences themselves device-local ([Obsidian](https://obsidian.md/help/sync/settings)). A per-column LWW log with HLCs removes the overwrite class by construction, but the version history and per-device status are still worth shipping because users need to recover from merges they disagree with.

## One image with serve and migrate keeps Helm and Compose from drifting

The 2025–2026 consensus is "bundled Postgres is for quickstart only; production is bring-your-own via a Secret," and an event in August 2025 hardened it. Effective **2025-08-28 Bitnami stopped publishing new images**, moved existing ones to `docker.io/bitnamilegacy`, which "will receive no further updates or support," and kept only `latest` tags free, so every umbrella chart depending on `bitnami/postgresql` now ships a frozen image unless overridden ([bitnami/charts #35164](https://github.com/bitnami/charts/issues/35164)); Coder's own install docs now show the proof-of-concept Postgres with `image.repository=bitnamilegacy/postgresql` while stating "Coder does not manage a database server for you" ([Coder](https://coder.com/docs/install/kubernetes)). Every mature product chart treats the external database as the production path and references credentials through an existing Secret: Zitadel's optional subchart is quickstart-only ([Zitadel](https://zitadel.com/docs/self-hosting/deploy/kubernetes)), "The Keycloak Operator does not manage the database" ([Keycloak Operator](https://www.keycloak.org/operator/basic-deployment)), Sourcegraph and GitLab take host plus a password Secret ([Sourcegraph](https://sourcegraph.com/docs/admin/external_services/postgres); [GitLab](https://docs.gitlab.com/charts/charts/gitlab/migrations/)). The replacement for in-cluster Postgres is CloudNativePG, whose `Cluster` CRD generates its own connection Secret and supports a logical `initdb` import "from an existing PostgreSQL cluster, even if it's outside Kubernetes" ([CNPG bootstrap](https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/main/docs/src/bootstrap.md)). A 2026 chart should therefore expose `database.existingSecret` plus key names first, an opt-in CNPG cluster second, and no Bitnami dependency. Helm 4 reached GA on 2025-11-12 and `--wait` now needs the `watch` verb on chart resources ([wz-it](https://wz-it.com/en/knowledge/kubernetes/migrate-helm-3-to-helm-4/)), which a chart's RBAC must anticipate.

Migrations split into two camps and one hard rule. Rails and Django products run a separate Job before rollout: GitLab's migrations sub-chart "creates a new migrations Job each time the chart is installed" and leaves completed Jobs visible until the next upgrade ([GitLab](https://docs.gitlab.com/charts/charts/gitlab/migrations/)); Sourcegraph's `migrator` image offers `up`, `upgrade`, `downgrade`, and a `drift` check where "if schema drift is detected it must be resolved before completing the upgrade," and the same image is used as a Compose container, a Kubernetes Job, and a Helm value ([Sourcegraph migrator](https://sourcegraph.com/docs/admin/updates/migrator/migrator-operations)). Go products migrate at process start under a database lock, and the failure mode is documented: Grafana's `locking_attempt_timeout_sec` defaults to 0, and with two instances starting against Postgres the second "tries 5 times within 1-2 seconds and then fails" ([Grafana configuration](https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/); [Grafana community](https://community.grafana.com/t/database-locking-attempt-timeout-sec-purpose/142001)); Coder raised golang-migrate's lock timeout from 15 seconds to two minutes after a long batch exceeded it ([Coder commit](https://git.dragonfruit.dev/mirror/coder/commit/8cc64737362f67af0bf31cedd9f1dc44afea070e)). The hard rule is never to use `post-install`/`post-upgrade` hooks for migrations: with `--wait` they deadlock against pods that cannot become ready without the schema, which Airflow users hit and fixed by moving to `pre-*` ([apache/airflow #33888](https://redirect.github.com/apache/airflow/discussions/33888); [Helm hooks](https://helm.sh/docs/topics/charts_hooks/)). Nobody relies on Helm rollback to undo schema changes; Upbound states plainly that migrations are forward-only and a non-compatible rollback requires a database restore ([Upbound](https://docs.upbound.io/hub/howtos/upgrades/)). The cleanest pattern that works for both packagings is a single image with a `migrate` subcommand: Helm runs it as a `pre-install,pre-upgrade` hook Job with `hook-delete-policy: before-hook-creation`, Compose runs it as a `migrate` service that the app `depends_on` with `condition: service_completed_successfully`, since "Compose does not wait until a container is 'ready', only until it's running" ([Docker](https://docs.docker.com/compose/how-tos/startup-order/)). The Postgres healthcheck must be `pg_isready -h 127.0.0.1`, because without `-h` it probes the Unix socket, which answers during the image's init phase while TCP is still closed ([DEV](https://dev.to/ji_ai/docker-compose-dependson-doesnt-wait-neither-does-pgisready-179b)); PostHog's base Compose is the worked example ([PostHog](https://raw.githubusercontent.com/PostHog/posthog/master/docker-compose.base.yml)), and Mattermost's adds `read_only`, `no-new-privileges`, and tmpfs hardening ([Mattermost](https://github.com/mattermost/docker/blob/main/docker-compose.yml)). Compose backups are universally left to the operator; a documented `pg_dump` sidecar is a differentiator, not table stakes.

Secrets and keys follow three patterns. GitLab's shared-secrets hook "runs on every install and upgrade. It never rotates a value" and its outputs "are not owned by the Helm release" ([GitLab shared-secrets](https://docs.gitlab.com/charts/charts/shared-secrets/)); Helm's `lookup`-with-fallback alternative breaks under ArgoCD, where "Helm's lookup function always returns an empty result in client-side rendering, so every ArgoCD sync generates new random values" ([CrewAI](https://enterprise-docs.crewai.com/configuration/argocd)); External Secrets Operator covers install-time generation GitOps-safely with a Password generator plus `refreshPolicy: CreatedOnce` and `immutable: true` ([ESO](https://external-secrets.io/latest/api/externalsecret/)). The binary should also generate its own missing secrets on first boot into a persisted location for Compose, with `secrets.create` and `secrets.existingSecret` separated in values. JWT signing keys need a JWKS state machine, not a shared secret: Supabase's keys move standby → current → previously used → revoked, standby exists because discovery is cached "for 10 minutes" at the edge plus up to 10 more in clients, and for one-hour tokens you wait "at least 1 hour and 15 minutes" before revoking ([Supabase signing keys](https://supabase.com/docs/guides/auth/signing-keys)). A single `JWT_SECRET` cannot be rotated without a logout storm. Air-gapped installs expect a machine-readable image list with digests, the chart as an OCI artifact (Helm now recommends OCI registries and notes "Installing a chart with a digest is more secure than a tag" ([Helm registries](https://helm.sh/docs/topics/registries/))), a `global.imageRegistry` override that rewrites every image, and offline licence verification: Coder's "License keys are validated locally using cryptographic signatures. No outbound connection to Coder is required" is the model for gating, and GitLab's approval-only Offline Cloud License with monthly manual usage export is the model for seat billing without connectivity ([Coder offline](https://coder.com/docs/install/offline); [GitLab](https://about.gitlab.com/pricing/licensing-faq/cloud-licensing/)). Coder's env-var list (`CODER_TELEMETRY_ENABLE=false`, `CODER_UPDATE_CHECK=false`, and so on) is a compact checklist of outbound paths to turn off.

Client and server skew is handled with a published window, which matters more for this product than most because the vendor cloud will usually be newer than on-prem clients while on-prem hubs may be older than App Store clients. GitLab's agent supports **the same minor ±1** with a UI warning ([GitLab agent](https://docs.gitlab.com/user/clusters/agent/install/)); Mattermost's mobile app pins its minimum server to the most recently end-of-lifed ESR and from October 2026 "users won't be able to sign in from the mobile app, and anyone already signed in will be signed out" below v10.11 ([Mattermost forum](https://forum.mattermost.com/t/starting-in-october-2026-the-mattermost-mobile-app-will-require-mattermost-server-v10-11-or-later/26039)); Immich's "match the major" rule produces hard errors when packaged servers lag ([immich discussion](https://github.com/immich-app/immich/discussions/29051)). The combination the evidence supports is a protocol and schema version on every sync request, the hub advertising `minClientVersion`/`maxClientVersion`, a symmetric ±1 minor window, additive-only wire changes inside it, and local client data keyed by schema version so an upgrade re-syncs rather than migrates.

## The reference product's data layer transfers; its authorization does not

The vendor's reference product is an enterprise agent-interaction hub (Express API, Angular SPA, Elixir realtime gateway, PostgreSQL, Redis, external OIDC) whose declared tenancy model is "Hosted cloud default: shared multi-tenant infrastructure with logical tenant isolation. Self-hosted: single-tenant deployment per customer," with parity required between the two (reference repo: `AGENTS.md`). The checkout is early-stage (chart version 0.1.0, uncommitted migrations, hard-coded tenant overrides), so its patterns are more valuable than its implementation state, and several of the most instructive findings are discrepancies between its documents and its code.

What to borrow is concentrated where one engineer could enforce a convention in one place. The SQL primitives are directly reusable in a Swift hub: a schema-level `update_updated_at()` trigger, a `non_empty_text` domain, a uniform soft-delete triple (`deleted_at`, `deleted_by`, `deleted_reason`) with `CHECK (num_nulls(...) IN (0, 3))`, a `BEFORE DELETE` trigger that raises, and a `soft_delete(regclass, id, user, reason)` function that application code calls inside a tenant-scoped CTE so scoping and deletion are one statement; tenant-scoped partial unique indexes such as `UNIQUE (tenant_id, event_id) WHERE deleted_at IS NULL`; `(created_at DESC, id DESC)` keyset indexes with opaque base64url cursors; `pg_trgm` GIN for search; and `pg_notify` triggers carrying semantic operations (`created|deleted|archived|renamed`) (reference repo: `db-migrations/migrations/committed/000002.sql`, `db-migrations/migrations/current/006-thread-metadata-notify.sql`, `libs/threads/src/threads.ts`). The identity model is sound and portable: `tenants`, `users(tenant_id)`, `user_identities(issuer, subject) UNIQUE`, `tenant_email_domains(domain UNIQUE, verified)`, a principal reduced to `(issuer, subject, email, displayName)` with `userId = "${issuer}:${subject}"`, OIDC authorization code with `checks: ['pkce', 'state']`, and a first-login resolver that matches a verified email domain to link an identity to an existing user (reference repo: `libs/auth-server/src/oidc/provider.ts`, `libs/auth-server/src/express/userResolutionMiddleware.ts`). The API-key scheme (prefix, 8-character short lookup token, 24-character long secret, only `sha256(long)` stored, constant-time compare, collision retry, hash never returned, `expires_at NOT NULL`) is a good design for machine clients (reference repo: `apps/app-api/src/api-keys.ts`). The typed error registry yielding one envelope `{ error: { code, message, category, retryable }, requestId, traceId }`, mirrored in Markdown, maps cleanly onto a Swift enum (reference repo: `apps/app-api/src/errors/registry.ts`). The chart idioms are the strongest part: no subcharts and no bundled Postgres, `database.existingSecret` plus `secretKeys.url`, a values file whose header reads "This file provides cloud-agnostic defaults. It contains NO secrets, NO real endpoints," an ESO mapping table in values with an `existingSecret` fallback, one ConfigMap with a checksum annotation that rolls pods, `required` and `fail` guards, non-root read-only pods dropping all capabilities, per-component HPA/PDB/anti-affinity toggles, an opt-in NetworkPolicy, `values-onprem-example.yaml` and cloud overlays, `helm lint` plus `kubeconform -strict` in CI, OCI publication on tags, and a preflight script that checks cluster, secrets mode, Postgres version, Redis, and object storage (reference repo: `charts/<product>/values.yaml`, `charts/<product>/templates/_helpers.tpl`, `.github/workflows/helm-lint.yml`, `scripts/preflight.sh`). The realtime protocol described in the previous section is the final borrow; a single-process Swift hub can keep the same Redis keys and the same `connect` negotiation, and PG `LISTEN/NOTIFY` is available from any Postgres client.

What to avoid is everything that depends on each call site doing the right thing. In hosted mode the tenant is an **unauthenticated `x-tenant-id` header**: middleware order is request-id → tenant header → Auth.js routes → session → user resolution, and nothing checks that the session's user belongs to the header's tenant (reference repo: `apps/app-api/src/main.ts`). Thread routes replace the middleware with a hard-coded seed tenant under a "TODO: Replace this local testing override with tenant resolution before shipping" and accept an `x-user-id` header as fallback identity; API-key routes take `tenant_id`, `organization_id`, and `user_id` from the request body; `/api/keys/*` and `/api/threads/*` are registered with no auth guard; and the WebSocket thread channel carries `# TODO: Validate thread belongs to socket.assigns.tenant_id` while the broadcaster fans out by thread id alone (reference repo: `apps/app-api/src/routes/threads-routes.ts`, `apps/app-api/src/routes/api-keys-routes.ts`, `apps/realtime-gateway/lib/realtime_gateway/client/thread_channel.ex`). A grep for `ROW LEVEL`, `CREATE POLICY`, `SET LOCAL`, and `current_setting` across the repository returns nothing, so there is no second line of defence. Because a fresh Auth.js config is built per request from the tenant header but all tenants share one `AUTH_SECRET`, a session cookie minted under tenant A validates under tenant B (reference repo: `libs/auth-server/src/express/mountAuth.ts`). A `tenant_oidc_connections` table stores `client_secret` as plain `TEXT` that no code reads (reference repo: `db-migrations/migrations/committed/000002.sql`), and the gateway configures Postgres TLS with `verify: :verify_none` (reference repo: `apps/realtime-gateway/config/runtime.exs`). The migrations Helm hook Job is disabled by default and depends on a separate image whose Dockerfile copies directories that no longer exist (reference repo: `charts/<product>/values.yaml`, `infra/docker/migrations.Dockerfile`), which is the decision most worth reversing: with a compiled Swift binary, ship the SQL inside the hub image and expose a `migrate` subcommand. The auth library queries `organization_id`, `name`, and `email` columns and an `organization_email_domains` table that the committed schema does not have, the README calls the frontend React when it is Angular, and `AGENTS.md` lists packages and apps that do not exist (reference repo: `libs/auth-server/src/user/resolveUser.ts`, `README.md`, `AGENTS.md`); documentation that describes the intended architecture rather than the implemented one is itself a risk for an on-prem product, because customers install from the docs. Finally, the reference product has no roles, permissions, memberships, invitations, SCIM, token refresh, or IdP logout; a reader should not infer that it does. The single most valuable correction for a new hub is to bind tenant to principal centrally, derive `org_id` from the verified token, reject any client-supplied tenant that disagrees, and add RLS with per-transaction `SET LOCAL` as the backstop the reference lacks.

## Conclusion

The six threads of this question resolve into one architectural object: the device. Tenant isolation becomes "which organization does this principal belong to," client authentication becomes "which device is this principal on, and can it be revoked alone," sync becomes "what is this device's cursor into a per-tenant log," and machine-bound sessions become "which device owns this thread and is it online." Once the hub models devices as first-class rows with their own token families, cursors, presence, and ownership of threads, the hard problems that defeat settings-sync products (stale overwrites) and conversation tools (merging) mostly disappear: transcripts are single-owner and append-only, so they need ordering rather than merging, and the mutable residue is small enough that per-column LWW with HLCs is sufficient. This also explains why no existing sync engine fits: they are built to replicate shared mutable tables, which is the minority of this product's data.

Three things remain genuinely unsolved in the sources and should be decided deliberately rather than discovered. No product documents what happens to a pending permission prompt when the owning machine disconnects, so the hub needs an explicit policy (expire it, or let the next online surface answer it). No published account shows a per-column LWW log surviving a column rename across mixed client versions, so the additive-only rule and the re-bootstrap path are load-bearing, not nice-to-have. And per-tenant restore inside a shared schema has no good answer except a first-class tenant-bundle export, which is why that feature should exist before the first paying organization, not after. Two facts also need local verification before they become decisions: the actual RLS overhead on this schema with `EXPLAIN (ANALYZE)`, since every published number is from another stack, and the PostgreSQL major version on-prem customers will run, which determines whether `uuidv7()` is native or application-generated.
