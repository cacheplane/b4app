### Timings

On an Apple M1 Max, with other work running on the machine. Every number below was measured for this update, after the final review's fixes, except the two the text names as the earlier version of this record's.

- **The parser in the test suite, debug.** `B4APP_TIMING=1 B4APP_TIMING_DIR=<dir> swift test --filter ParserTimingTests`, alone in its process: each test streams a workload of size n and of size 16n, five rounds interleaved, and takes the fastest of each by the thread's CPU time; linear work gives a ratio of about 16, and the test fails at 64. Ratios: a fence pushed line by line 16.0 (16n is 8,000 lines of 300 characters, 116 ms), a fence in a list item 16.0 (133 ms), a table row by row 16.3 (216 ms), a fence in pieces without reads 15.9 (89 ms), one line in 64-character pieces with a read after each push 20.0 for prose ending in a space, 20.6 for markup ending in spaces and 19.0 for the JSON-like line (about 100,000 characters at 16n, 56 to 72 ms), backtick runs on one 400,000-character line 14.9 (56 ms), and the mixed reply one character at a time with a read every 16 pushes 17.3 (100,000 characters, 1.38 s). With the old trim restored for a check, the three one-line tests failed at 212, 219 and 120.
- **The parser, optimised.** A release build of the test suite cannot run (in a release build the test runner starts the `agent-workspace` executable's entry point, which rejects `--test-bundle-path`), so the parser's sources were compiled with `xcrun swiftc -O` beside a small program, and again with `-Onone`; the fastest of five runs by the thread's CPU time:

  | Workload | 25,000 | 50,000 | 100,000 | 200,000 | 400,000 characters |
  | --- | --- | --- | --- | --- | --- |
  | Mixed reply, one character a push, a read every 16 pushes, `-O` | 0.073 s | 0.157 s | 0.355 s | 0.867 s | |
  | One JSON-like line (`` {"k":"v **x** `y` [z](u)", `` repeated), 64-character pushes, a read after each, `-O` | 0.005 s | 0.012 s | 0.028 s | 0.073 s | 0.212 s |
  | The same line, no reads, `-O` | 0.004 s | 0.008 s | 0.017 s | 0.039 s | 0.100 s |
  | One line of prose ending in a space, 64-character pushes, a read after each, `-O` | 0.005 s | 0.011 s | 0.026 s | 0.069 s | 0.200 s |
  | Mixed reply as above, `-Onone` | 0.325 s | 0.659 s | 1.368 s | 2.925 s | |
  | One line with reads, `-Onone` | 0.015 s | 0.032 s | 0.068 s | 0.153 s | 0.375 s |

  Before the trim fix the same `-O` one-line case took 0.72 s at 100,000 characters and 2.84 s at 200,000 (the earlier version of this record). The cost is now near linear but not exactly: from 200,000 to 400,000 characters the one-line cases take 2.6 to 2.9 times as long, and from 100,000 to 200,000 the mixed reply takes 2.4 times as long. What is left on one line is that a push into an open line still copies that line (`buffer + text`), a memory copy bounded by the open line's length, which the design allows. The mixed reply's growth was not traced to a cause.
- **A tick in a hosted transcript, debug.** `StreamingTickTimingTests` hosts `TranscriptView` (normal density, 720 by 480 pt) over 150 rows, the last a running reply; it streams every block kind three times over (1,366 characters) 24 characters a tick with a paced store and a `ManualTicker`, then completes it and ticks until the reveal stops. Each tick's time is the reveal and parse plus the layout passes before and after one turn of the run loop. Three runs, 66 ticks each, with `B4APP_TIMING_DIR`: median 7.4 to 7.8 ms, 95th percentile 12.0 to 13.4 ms, worst 17.5 to 19.1 ms. The worst debug tick sits at the 16 ms line of a 60 Hz frame. The test asserts the worst tick is under 250 ms, a guard against a gross regression only. This is a hosted view in a test process, debug build, not a frame-time measurement of the running app, and it does not separate our code's time from SwiftUI's and AppKit's; the release build of this test cannot run, for the reason above.

### Not verified

- The design's budget, no frame over 16 ms from our code on the Mac in a release build: not measured. The running app was not profiled with Instruments, on the Mac or an iPhone Simulator.
- The pacing numbers (a twelfth of the backlog a tick, the drain within 9 ticks) on a live stream: not tuned. This is gate step 3, waiting on the owner (his Mac and a live Claude Code session); the numbers are the design's first guess.
- Any live runtime session: no Codex, Claude Code or B4 reply was streamed through this code. The phone's relay-gap handling is tested with the sequences the design reads from `MirrorTransport`, not over a real relay.
- An iPhone on hardware, and the iOS app at all beyond its build: the phone-width captures are the macOS view.
- VoiceOver: the task marks' "Done" and "Not done", headings as headers, and tables were not heard. Dynamic Type at accessibility sizes was not looked at.
- CI: nothing has been pushed, so the new third process of CI's Test step (`B4APP_TIMING=1 swift test --skip-build --filter ParserTimingTests`) has not run on a runner.
- Left open from the final review: settled replies are parsed on the main thread and the parse cache is dropped on every thread switch (0.115 s for 150 rows of 6 KB, `-O`, the reviewer's measurement); `DisplayTicker` is not frame-aligned (a display link is to be considered during live tuning); and the other minor items the review marked "stay deferred".
