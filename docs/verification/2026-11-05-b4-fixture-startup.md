## 2026-11-05: B4 fixture startup and deleted-thread publication controls

Both fake B4 entry points bind without reverse DNS. The two additive Python regression methods use real loopback bind/listen, require readiness with `socket.getfqdn` disabled, and require an occupied port to fail before readiness. Both original entry points failed the DNS control; the corrected entries pass. HTTP/SSE fixture behavior remains covered by the Swift suites.

D-119 requires late events for a deleted thread to be suppressed. SessionService now decides visibility at publication, rather than trusting an earlier thread snapshot. WorkspaceStorage takes the existing shared remote-apply advisory lock before a live-thread `FOR SHARE` row lease, runs a synchronous memory-publication callback in the event-log actor, then commits. Local and pulled deletions therefore either precede publication or wait for that lease. The callback must not suspend or reenter storage. Explicit deletion notifications in their separate owner remain unchanged. No schema, HLC, application-data or change-log mutation is introduced by this guard; row locking can still incur physical storage work.

The original three-second slow-stream deletion race and every original assertion/deadline remain. An atomic producer cursor and additional nonnil replay assertion distinguish delayed client collection and expose real late publication. A local initial-publication pause reproduced a stale undeleted snapshot publishing after deletion; the production guard passes that same original race. The held-fixture replacement was rejected because it excluded the in-flight race. No diagnostic delay, print, injection or narrowed replacement is retained.

Two added real-PostgreSQL controls cover visible/deleted/missing/closed storage and observe local/pulled deletions actually waiting for a publication lease. Removing the row lease makes the local deletion control fail. Deliberately blocking test callbacks use dedicated threads and are joined, keeping those waits off Swift's cooperative executor. These new controls do not alter any existing test deadline.

The guard adds database round trips while the event-log actor is occupied. A local sequential probe separately measured that boundary; it is not a production throughput or contention bound. Existing database/pool/row lock waits remain possible, so the transaction is not claimed to have a hard wall-clock limit. Full hosted comparison includes the integrated guard and the two added tests.
